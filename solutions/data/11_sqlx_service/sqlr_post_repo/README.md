# Репозитории постов и лайков

Соцсеть растёт, и сервис постов больше не может позволить себе простые решения. Пост с тегами должен
появляться целиком или не появляться вовсе. Лайки приходят пачками от тысяч людей одновременно, а база по
требованию админов работает на уровне изоляции SERIALIZABLE и время от времени отвечает «попробуй ещё раз».
Лента не должна ходить в базу столько раз, сколько в ней постов. Всё это прячется за двумя трейтами:
сервис вызывает `repo.create_with_tags(...)` и `likes.like(...)` и не знает, что внутри.

## Что уже есть

- `schema.sql`: пользователи, посты, теги, связь постов с тегами, лайки. Ограничения имеют имена
  (`posts_author_fk`, `posts_body_not_blank`, `likes_pk` и так далее).
- `src/lib.rs`: типы `Post`, `FeedItem`, `Cursor`, ошибка `RepoError`, исход `LikeOutcome`, два трейта и
  `apply_schema`. Этот файл менять не нужно.
- `src/postgres.rs`: заготовки `PgPostRepository` и `PgLikeRepository` с `todo!()`. Вся работа здесь.
- `tests/acceptance.rs`: приёмочные тесты. Каждый тест создаёт свою схему в Postgres курса
  (`RUSTLINGS_PG_URL`), и часть тестов считает команды, которые ушли в базу, через маленький прокси.

## Что нужно сделать

1. SQL лежит в константах наверху `src/postgres.rs`, значения передаются через `$n` и `bind`.
   `format!(` в этом файле нельзя, тест это проверяет.
2. `create_with_tags` создаёт пост и привязывает теги одной транзакцией. Несуществующие теги создаются,
   существующие переиспользуются, повторы в списке схлопываются, пустой список допустим. Число
   команд, ушедших в базу, не зависит от числа тегов. Нет автора (внешний ключ) это `NotFound`, пустой
   текст (CHECK) это `Invalid`. После неудачи не остаётся ни поста, ни тегов.
3. `feed` отдаёт страницу ленты: сначала новые, при равном времени больший `id` раньше. После `Cursor` (время и id
   последнего поста прошлой страницы) возвращается продолжение без пропусков и повторов, даже если у нескольких
   постов одно и то же время. Каждый элемент содержит пост, имя автора и теги по алфавиту. Команд не больше трёх
   независимо от размера страницы.
4. `like` ставит лайк и увеличивает счётчик `likes_count` одной транзакцией. Повторный лайк того же человека
   это `AlreadyLiked`, счётчик не растёт. Лайк несуществующему посту или от несуществующего пользователя
   это `NotFound`. `unlike` снимает лайк и уменьшает счётчик, возвращает `false`, если снимать нечего.
5. В боевой конфигурации база по умолчанию работает в SERIALIZABLE. При конфликтах она отвечает 40001 или 40P01.
   `like` и `unlike` обязаны повторять транзакцию (с пределом попыток), чтобы десять одновременных лайков
   одного поста все прошли, а счётчик остался равен числу строк в `likes`.
6. Ничто внутри транзакции не просит у пула второго соединения: репозиторий должен работать и на пуле из
   одного соединения.

## Критерии приёмки

`cargo test` в корне проекта: все тесты из `tests/acceptance.rs` проходят. Они проверяют атомарность
создания, перевод ошибок, порядок и курсор, отсутствие N+1 (по числу команд на проводе), корректность счётчика
под конкурентной нагрузкой и отсутствие `format!` в SQL.

## Структура

```
sqlr_post_repo/
  Cargo.toml
  schema.sql
  src/lib.rs          типы, трейты, apply_schema (готово)
  src/postgres.rs     PgPostRepository и PgLikeRepository (твоя работа)
  tests/acceptance.rs приёмочные тесты (не менять)
```

## Как запускать

Postgres курса должен работать (`docker compose up -d` в папке курса). Потом `cargo test`.

## Подсказки по теории

Все приёмы есть в README главы: транзакция на `&mut *tx` и ни одного обращения к пулу внутри неё, массивы
через `UNNEST` для тегов, гидрация через `ANY($1)` и словарь для ленты, повтор по кодам 40001 и 40P01 с
пределом попыток. Одна ловушка отдельно: если в одной команде `INSERT ... ON CONFLICT DO UPDATE` дважды встречается
один и тот же тег, Postgres откажет, поэтому повторы убирай заранее.
