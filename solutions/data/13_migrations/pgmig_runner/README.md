# Раннер миграций

Соцсеть переезжает на несколько сервисов, у каждого своя схема в Postgres, и применять миграции руками уже никто не
хочет: на проде кто-то забывает файл, у кого-то схема расходится, а при выкатке трёх копий сервиса они мигрируют
одновременно и роняют друг друга. Пора написать раннер: библиотеку, которую сервис вызывает при старте, а она сама
решает, что применить, в каком порядке и как не навредить работающим запросам.

## Что уже есть

- `src/lib.rs`: типы `Migration`, `Options`, `Report`, `Status`, `State`, ошибка `MigrateError`. Менять не нужно.
- `src/files.rs`: заготовка `parse_dir` с `todo!()`.
- `src/runner.rs`: заготовка `Migrator` (`new`, `run`, `status`) с `todo!()`.
- `tests/acceptance.rs`: приёмочные тесты. Каждый тест создаёт свою схему в Postgres курса (`RUSTLINGS_PG_URL`) и
  удаляет её в конце.

## Что нужно сделать

1. `parse_dir(dir)` читает из каталога файлы `*.sql` с именами `NNNN_имя.sql`: номер из цифр (любой длины, `0001` и `1`
   это версия 1), потом подчёркивание, потом непустое имя. Результат отсортирован по версии как по числу (10 после 2).
   Файлы с другими расширениями пропускаются. `.sql` с неподходящим именем это `BadFileName(имя файла)`, две
   одинаковые версии `DuplicateVersion(версия)`.
2. `Migrator::run(&[Migration])` применяет то, чего ещё нет, по возрастанию версии. Журнал это таблица
   `schema_migrations(version, name, checksum, applied_at)`, которую раннер создаёт сам. Контрольную сумму считай
   как `md5` текста, её можно взять у самого Postgres.
3. Перед применением новых раннер проверяет уже применённые: файл исчез из списка это `MissingFile`, текст изменился
   это `Drift`. Если среди новых есть версия меньше уже применённой, это `OutOfOrder`. Пока проверки не прошли, ничего
   не применяется.
4. Каждая миграция идёт в своей транзакции вместе с записью в журнал. Если она упала, от неё не остаётся ничего,
   следующие не запускаются, ошибка `Failed { version, error }`, а `Report.applied` перечисляет применённые в этот
   запуск версии (при успехе).
5. Файл, первая строка которого `-- no-transaction`, выполняется вне транзакции, команда за командой (разделитель `;`),
   потом пишется запись в журнал. Так проходит `CREATE INDEX CONCURRENTLY`.
6. Несколько копий сервиса стартуют одновременно: мигрирует одна, остальные ждут и, дождавшись, видят, что
   делать нечего. Замок общий на базу (консультативный, ключ в `Options::lock_key`), снимается при любом исходе.
7. На время каждой миграции ставится `lock_timeout` из `Options`. Если замок на таблицу не получен
   (SQLSTATE `55P03`), миграция повторяется до `Options::attempts` раз с паузой `retry_pause_ms`, потом ошибка
   `LockTimeout { version }`. Остальные ошибки возвращаются сразу.
8. `Migrator::status(&[Migration])` ничего не меняет и не создаёт: возвращает по записи на файл со состоянием
   `Applied` или `Pending`. Если таблицы журнала ещё нет, всё `Pending`.

## Критерии приёмки

`cargo test` в корне проекта: все тесты из `tests/acceptance.rs` проходят. Они проверяют порядок, повторный запуск,
атомарность, расхождение, потерянные и вставленные задним числом файлы, гонку копий, файлы вне транзакции, повторы
по таймауту замка и снятие замка.

## Структура

```
pgmig_runner/
  Cargo.toml
  src/lib.rs          типы и ошибки (готово)
  src/files.rs        parse_dir (твоя работа)
  src/runner.rs       Migrator (твоя работа)
  tests/acceptance.rs приёмочные тесты (не менять)
```

## Как запускать

Postgres курса должен работать (`docker compose up -d` в папке курса). Потом `cargo test`.

## Подсказки по теории

Все приёмы есть в README главы: журнал и порядок версий, транзакция на миграцию вместе с записью, контрольная сумма,
консультативная блокировка на отдельном соединении с обязательным снятием, `lock_timeout` через `set_config`, повтор по
коду `55P03`, файлы без транзакции. Параметры нельзя передавать в `SET`, зато можно в `set_config`.
