# nws_engine: websocket-engine

Проверочная задача главы. Соцсеть переезжает с голого TCP на WebSocket, а значит нужен крейт, который умеет рукопожатие поверх
http-engine, читает и пишет фреймы, склеивает сообщения, держит закрытие и умеет быть клиентом. Готовых библиотек (tungstenite и
компания) нет и не будет: всё, что в главе было отдельными задачами, собирается здесь в один крейт.

## Что уже есть

Движок http-engine версии 0.4.0 лежит в `http-engine/` целиком (он ровно тот, что ты написал в прошлых главах, плюс одна новая
возможность). Если обработчик возвращает ответ со статусом 101 и вешает на него `Response::on_upgrade(...)`, сервер отправляет
этот ответ, а сокет вместе с байтами, которые он уже успел прочитать за запросом, отдаёт обработчику в виде `Upgraded { stream, rest }`
и больше не трогает. Это задача nws7 и nws8 в рабочем виде.

В `src/` готовы типы (`Opcode`, `Frame`, `ProtoError`, `Role`, `Message`, `WsConfig`, `WsError`, поля `WsStream`) и сигнатуры.
Тела функций с `todo!()` пишешь ты.

## Что сделать

1. `base64.rs`: `encode` и `decode` (строгий: длина кратна четырём, `=` только в конце, нулевые хвостовые биты).
2. `handshake.rs`:
   - `accept_key(ключ)`: sha1 от ключа и GUID (крейт `sha1`), результат в base64;
   - `check_upgrade(&Request) -> Result<ключ, Response>`: GET, HTTP/1.1, `Upgrade` и `Connection` как списки токенов (по всем строкам
     заголовка, без учёта регистра), ровно один `Sec-WebSocket-Key` на 16 байт, версия `13`. Отказы: 405 с `Allow: GET`, 400, 426 с
     `Sec-WebSocket-Version: 13`;
   - проверка Origin по `WsConfig`: чужой, `null` и (если запрещено) отсутствующий это 403;
   - `upgrade(&Request, &WsConfig, on_connect) -> Response`: готовит ответ 101 с `Upgrade`, `Connection` и `Sec-WebSocket-Accept`, а
     обработчик `on_connect` получает `WsStream` уже в роли сервера.
3. `frame.rs`: `Decoder::decode` над `BytesMut` (частичные данные оставляют буфер нетронутым; маска обязательна от клиента и запрещена
   от сервера; кратчайшая запись длины; отказ по заявленной длине больше лимита до получения данных; проверки управляющих фреймов по
   заголовку: только `FIN=1` и не длиннее 125 байт), `encode_frame` (кратчайшая длина, маска по ключу), `MaskGen` (случайное зерно,
   свежий ключ на каждый вызов), `close_code` (1002 для нарушений, 1007 для плохого UTF-8, 1009 для слишком большого).
4. `assembler.rs`: `Assembler` склеивает фрагменты в `Message`, отдаёт управляющие фреймы насквозь, проверяет порядок фрагментов,
   потоково проверяет UTF-8 (хороший текст, разрезанный где угодно, проходит, плохой отвергается на первом же плохом фрагменте) и
   считает лимит по сумме фрагментов до того, как лишнее накопится.
5. `close.rs`: `valid_close_code`, `parse_close`, `encode_close` (причина обрезается по границе символа, тело не длиннее 125 байт) и
   автомат `Closing` (`start`, `on_close`).
6. `stream.rs`: `WsStream`. `recv` возвращает `Ok(Some(сообщение))`, `Ok(None)` после закрытия по всем правилам, `Err` при нарушении (перед
   этим собеседнику уходит Close с нужным кодом, и сокет закрывается: сначала `shutdown` записи, потом короткое вычитывание остатка,
   иначе Close потеряется в RST). Ping получает pong с тем же телом, пока приложение просто ждёт в `recv`; pong игнорируется.
   `send` пишет одним фреймом (Text или Binary), после закрытия возвращает `WsError::Closed`. `ping` отправляет ping. `close(код, причина)`
   отправляет Close и ждёт ответный в пределах `close_timeout` (общий срок на ожидание), потом закрывает сокет. `close_code()` отдаёт
   код закрытия. Клиентские фреймы маскируются свежим ключом, серверные нет. Байты `rest` читаются раньше, чем сокет.
7. `client.rs`: `new_key`, `client_request`, `verify_response` (101, `Upgrade`, `Connection`, ровно один `Sec-WebSocket-Accept`, равный
   ожидаемому, никаких расширений и подпротоколов) и `connect(addr, host, path, origin, config)`: после `101` байты, пришедшие сразу
   за ответом, остаются в `WsStream`.

## Критерии приёмки

`cargo test`. Проверяется по настоящей сети (127.0.0.1:0) и без внешних клиентов:

- base64 по эталонным векторам и строгие отказы, `accept_key` по примеру из RFC;
- рукопожатие: 101 с верными заголовками, `Connection: keep-alive, Upgrade`, 405, 400, 426, политика Origin;
- обмен: текст, пустой текст, эмодзи, 70 КБ текста, 200 КБ двоичных данных, первое сообщение в одном сегменте с рукопожатием;
- фрагменты с ping посередине, эмодзи, разрезанный по байтам, автоматический pong, pong без ping;
- нарушения протокола и коды закрытия: 1002, 1007, 1009 (в том числе по заявленной длине без данных);
- закрытие: инициатор клиент и сервер, эхо кода, плохие тела Close, молчаливый собеседник не держит закрытие дольше срока;
- клиент: корректный запрос, маска на каждом фрейме со свежими ключами, отказ от чужих ответов, потерянный хвост после 101;
- 30 клиентов одновременно, обычный HTTP рядом с открытыми сокетами, кодек при случайных нарезках потока.

```
      frame.rs, assembler.rs,

```

## Подсказки по теории

README главы и задачи nws1 до nws20: base64 (nws1, nws2), рукопожатие (nws3 до nws8), фреймы (nws9 до nws14), управляющие фреймы,
сборка, лимиты и закрытие (nws15 до nws19), клиент (nws20). Отдельные решения из задач можно переносить сюда почти без изменений:
главная работа здесь в том, чтобы склеить их в `WsStream` и не потерять байты на стыках.
