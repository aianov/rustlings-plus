# npb_contracts: proto

Проверочная задача главы. Крейт `proto` это контракты соцсети: пользователи, посты и сообщения чата, общие для всех будущих
сервисов. Первая версия схемы уже в `proto/social/v1/social.proto`, и по ней в базах и очередях лежат байты. Продукт требует
изменений, а сервисы будут выкатываться по очереди: часть уже на новой схеме, часть ещё на старой. Твоя задача внести правки в
схему так, чтобы никто никого не сломал, и доказать это тестами по сохранённым байтам.

## Что уже есть

- `build.rs` и `src/lib.rs`: генерация кода и модуль `proto::social::v1`. Для map включён `btree_map`, поэтому равные сообщения
  кодируются одинаковыми байтами.
- Первая версия `proto/social/v1/social.proto` (User, Post, ChatMessage).
- `tests/compat.rs`: сохранённые байты первой версии, согласованные байты новой и копии структур первой версии для проверки
  «старый читатель читает новое».

## Что сделать

Правка идёт в том же файле и в том же пакете `social.v1` (совместимое развитие, не новая версия). Ровно эти изменения:

| сообщение | изменение |
|-----------|-----------|
| User | поле `legacy_flag` (4) больше не нужно: удалить, но номер и имя зарезервировать |
| User | `followers` (3) переполняется у крупных аккаунтов: тип `uint64` |
| User | новое `bio` (5) со смыслом «пусто» и «не задано» по отдельности |
| User | новое `role` (6): перечисление `Role` со значениями `ROLE_UNSPECIFIED = 0`, `ROLE_MEMBER = 1`, `ROLE_MODERATOR = 2` |
| Post | `likes` (4) переименовать в `like_count` и расширить до `int64` |
| Post | новые `hashtags` (5, список строк), `reactions` (6, map из строки в `uint32`) |
| Post | новая группа `media` (oneof): `image_url` (7) или `video_url` (8) |
| ChatMessage | `from` (2) переименовать в `sender` |
| ChatMessage | новое `sent_at` (5): `google.protobuf.Timestamp` |

Номера остальных полей не меняются. Переименование не ломает ничего (имён на проводе нет), а смена типа допустима только внутри
группы совместимых (целые между собой).

## Критерии приёмки

`cargo test`:

- байты первой версии читаются новыми типами (поля на своих местах, неизвестный номер 4 пропускается);
- новые типы кодируются в согласованные байты (проверяются номера и типы всех полей);
- читатель первой версии понимает байты новой версии;
- номер 4 и имя `legacy_flag` объявлены в `reserved`, и в `User` нет поля с номером 4;
- `bio` отличает пустую строку от отсутствующей; неизвестное значение `role` от более нового сервиса не теряется;
- в oneof побеждает последний вариант; map кодируется детерминированно.

## Структура

```
npb_contracts/
  Cargo.toml, build.rs, src/lib.rs      готово
  proto/social/v1/social.proto          правишь ты
  tests/compat.rs
```

## Подсказки по теории

Правила совместимости схем собраны в README главы и в задаче npb14. Если тест говорит «номера и типы не совпали с таблицей»,
сверь номер и тип поля с таблицей выше: на проводе важны именно они. Для `bio` нужно слово `optional` перед типом.
