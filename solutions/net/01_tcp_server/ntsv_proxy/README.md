# ntsv_proxy: TCP-прокси

Прокси стоит между клиентом и настоящим сервером (upstream) и просто гоняет байты в обе
стороны. Так работают балансировщики, туннели и отладочные прокси. Ничего не парсит, но
должен быть аккуратен в трёх вещах: закрытие одной стороны (half-close), ошибки и счётчики.

## Что уже есть

Крейт `ntsv-proxy`: структура `Totals` с четырьмя атомарными счётчиками и заготовка `run` в
`src/lib.rs`. Приёмочные тесты в `tests/acceptance.rs` восстанавливаются перед проверкой.

## Что сделать

`run(listener, upstream, totals, shutdown)` принимает клиентов, пока не завершится `shutdown`.
Для каждого клиента:

1. Подключиться к `upstream`. Если не вышло: увеличить `totals.failed`, закрыть клиента
   (просто отпустить сокет) и выйти. Если вышло: увеличить `totals.connections`.
2. Гнать байты в обе стороны одновременно. Каждый переданный байт учитывать: клиент к серверу
   в `totals.up`, сервер к клиенту в `totals.down`.
3. Когда одна сторона закрыла свою запись (прочитан EOF), закрыть запись в другую сторону
   (`shutdown`), но другое направление не трогать: оно живёт, пока не дойдёт до своего EOF.
   Только когда закончились оба направления, соединение завершено.
4. Если любое направление упало с ошибкой (сброс, разрыв), оборвать оба: ждать оставшееся
   направление бессмысленно, клиент не должен зависнуть.
5. По `shutdown` перестать принимать, дождаться текущих соединений и вернуть `Ok(())`.
   Слушателя отпустить, чтобы порт закрылся.

Готовый `tokio::io::copy_bidirectional` здесь не используй: он делает ровно это, а цель задачи
пройти путь руками. После того как тесты пройдут, сравни своё решение с ним.

## Критерии приёмки

`cargo test`. Тесты проверяют:

- байты ходят туда и обратно;
- закрытие записи клиента доходит до upstream (иначе тот вечно ждёт конца запроса);
- закрытие записи upstream доходит до клиента, а клиент после этого ещё может писать;
- недоступный upstream: клиент получает закрытие, `failed` растёт;
- мегабайт туда и мегабайт обратно: содержимое целое, счётчики точные;
- 20 клиентов параллельно, данные не путаются;
- сброс на стороне upstream не оставляет клиента висеть;
- остановка закрывает порт.

Все ожидания ограничены 5 секундами.

## Подсказки

Удобно написать одну функцию, которая переливает байты из читающей половины в пишущую и сама
делает `shutdown` на EOF, и запустить её дважды (в каждую сторону). Склеить результаты можно
через `tokio::try_join!`: он ждёт оба, но при первой ошибке бросает второе. Для этого сокеты
делятся через `into_split`. Счётчики это `AtomicU64` с `fetch_add`.
