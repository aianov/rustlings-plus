# ntn_shared_proto: одна схема на всех

Сервисы users и posts говорят друг с другом, и пост хранит автора как сообщение `users.v1.User`. Если каждый сервис соберёт `.proto`
сам, у него появится свой тип `User`: одинаковый по виду и разный для компилятора. Передать пользователя из одного сервиса в
другой без копирования по полям не выйдет, а ещё хуже, когда схемы начнут расходиться. Решение: один крейт `proto`, собирающий все
`.proto` разом, и все сервисы зависят от него.

## Что уже есть

Воркспейс с тремя крейтами: `crates/proto` (только `Cargo.toml` и схемы в `crates/proto/proto/`), `crates/users-service` и
`crates/posts-service` с готовым кодом сервисов и приёмочными тестами. Код сервисов уже ссылается на `proto::users::v1::...` и
`proto::posts::v1::...`.

## Что сделать

1. `crates/proto/build.rs`: собирает **оба** файла схем одним вызовом; корнем для `import` служит `crates/proto/proto`.
2. `crates/proto/src/lib.rs`: подключает сгенерированный код, модули повторяют пакеты (`proto::users::v1`, `proto::posts::v1`).
3. Сервисы должны зависеть от `proto` через `path` и сами ничего не собирать: ни `build.rs`, ни `tonic-prost-build` у них быть не должно.

## Критерии приёмки

`cargo test --workspace`: `User`, который отдаёт users-service, подставляется в `Post` posts-service без преобразований (это один тип);
клиент и сервер каждого сервиса работают по сети; у сервисов нет своих `build.rs`.

## Структура

```
ntn_shared_proto/
  Cargo.toml                           готово
  crates/proto/                        proto/*.proto готовы; build.rs и src/lib.rs твои
  crates/users-service/                код готов; Cargo.toml дополни сам
  crates/posts-service/                код готов; Cargo.toml дополни сам
```

## Подсказки по теории

Если схема `posts.proto` импортирует `users.proto`, сгенерированный код ссылается на `User` по пути `super::super::users::v1::User`,
то есть относительно расположения модулей. Поэтому вложенные модули должны повторять пакеты ровно, иначе путь не разрешится.
