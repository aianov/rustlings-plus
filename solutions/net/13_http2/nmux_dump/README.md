# nmux_dump: h2dump

Проверочная задача главы. В три часа ночи в чате перестали приходить сообщения, и никто не понимает почему: клиент говорит
«сервер молчит», сервер говорит «клиент ничего не просил». Но у тебя есть запись разговора: два набора байтов, всё, что клиент отправил
серверу, и всё, что сервер отправил клиенту. Нужна программа, которая прочитает такой дамп и скажет по-человечески: какие
gRPC-методы вызывались, с какими сообщениями и сроками, чем закончились и не обрывал ли кто-то вызов.

## Что уже есть

`Cargo.toml`, публичные типы в `src/lib.rs` (`Report`, `Call`, `GrpcStatus`, `Goaway`, `DumpError`) и приёмочные тесты. Функция
`analyze` пока заглушка. Всё остальное (чтение кадров, HPACK, gRPC-сообщения) ты уже написал в задачах главы, теперь это нужно
собрать в один крейт. Можно разложить по модулям (`frame.rs`, `hpack.rs`, `grpc.rs`) и перенести свои решения.

## Что сделать

`analyze(client: &[u8], server: &[u8]) -> Result<Report, DumpError>`.

1. `client` начинается с прелюдии HTTP/2, иначе `DumpError::BadPreface`. Дальше в обоих направлениях идут кадры подряд.
   Дамп, оборвавшийся посреди кадра, это `DumpError::Incomplete`. Кадр с нарушенным устройством тела (PING не из восьми байтов,
   SETTINGS не кратно шести и тому подобное) это `DumpError::Frame`.
2. Поддерживаются кадры DATA и HEADERS (с выравниванием и полями приоритета), RST_STREAM, SETTINGS, PING, GOAWAY.
   Остальные типы пропускаются. Блок заголовков, разбитый на несколько кадров (HEADERS без END_HEADERS), честно называется
   `DumpError::Unsupported`.
3. У каждого направления своя динамическая таблица HPACK, и блоки разбираются строго по порядку, в том числе для потоков, которые
   потом оборвали: иначе таблица разъедется. Ошибка HPACK это `DumpError::Hpack`. Сжатие по Хаффману в дампах не встречается.
4. Вызов (`Call`) создаётся на первом блоке заголовков клиента для потока: путь из `:path`, срок из `grpc-timeout` (нет заголовка или
   он невнятный: `None`).
5. Сообщения запроса и ответа собираются из DATA с учётом того, что границы DATA и границы сообщений не совпадают. Сжатое
   сообщение это `DumpError::Grpc`.
6. Итог вызова берётся из любого блока заголовков сервера с `grpc-status`: это и трейлеры, и «trailers only». Текст `grpc-message`
   раскодируется из процентной записи.
7. RST_STREAM из любой стороны записывается в `reset`. В `Report` также попадают настройки (только не подтверждения),
   число PING без ACK в обоих направлениях и последний GOAWAY. Вызовы идут по возрастанию номера потока.

## Критерии приёмки

`cargo test`. Дампы собирает сам тест своим кодировщиком кадров и HPACK:

- простой унарный вызов со сроком, сообщением и ответом;
- два перемешанных вызова: заголовки второго ссылаются на динамическую таблицу, сообщение разрезано между двумя DATA, два сообщения
  лежат в одном DATA, ответы идут не в порядке запросов;
- вызов, закончившийся «trailers only» с процентно закодированным текстом ошибки;
- обрыв вызова клиентом (CANCEL) и отказ сервера (REFUSED_STREAM);
- настройки, PING, GOAWAY; кадры с выравниванием и приоритетом, неизвестные типы кадров;
- битые дампы: чужая прелюдия, обрыв, плохая ссылка HPACK, сжатое сообщение, CONTINUATION, плохой PING, случайный мусор без паник.

## Структура

```
nmux_dump/
  Cargo.toml                  готово
  src/lib.rs                  типы готовы, analyze твой
  src/frame.rs, hpack.rs, grpc.rs   по желанию
  tests/dump.rs
```

## Подсказки по теории

Для каждой части уже есть задача: кадры (nmux1, nmux2), HPACK (nmux6, nmux7, nmux8), сообщения (nmux9), срок (nmux10), итог и
процентная запись (nmux11). Читай клиентский и серверный потоки независимо, одним и тем же устройством разбора, но с двумя
отдельными таблицами HPACK.
