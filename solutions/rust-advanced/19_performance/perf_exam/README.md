# Экзамен раздела: logq, запросы к журналу

Экзамен по всему разделу «Rust углублённо». Тема новая: небольшая библиотека для разбора и сводок по
журналам сервиса. Подсказок нет, пустая папка и это ТЗ. Проект собираешь с нуля: манифесты, модули, типы,
итераторы, обобщения, ошибки, потоки, макрос, тесты и документация. Приёмочные тесты уже лежат в
`crates/logq/tests/acceptance.rs`, менять их нельзя.

## Формат журнала

Одна запись на строку: `<метка времени> <УРОВЕНЬ> <источник> <сообщение>`. Метка это целое число секунд
(`u64`). Уровни `DEBUG`, `INFO`, `WARN`, `ERROR` (регистр важен). Источник одно слово. Сообщение это весь
остаток строки, с пробелами, не пустой. Пример: `1700000003 WARN db медленный запрос: 120 мс`.
Пустые (из одних пробелов) строки пропускаются.

## Что нужно сделать

1. **Манифесты.** Воркспейс в корне с единственным членом `crates/logq`. Пакет `logq`, редакция 2024.
   Feature `json` включена по умолчанию и тянет необязательные зависимости `serde` (с derive) и `serde_json`.
   Без неё крейт собирается без serde. В пакете линт `unsafe_code = "deny"` в `[lints.rust]`.
2. **Типы и ошибки.** `Level` (`Debug < Info < Warn < Error`, `Copy`, `Ord`, `Hash`, `Display` печатает
   `WARN` и так далее, `FromStr` принимает только точное написание). `ParseError`: `MissingField(&'static str)`
   с именами `timestamp`, `level`, `target`, `message` (проверяются в этом порядке), `BadTimestamp(ParseIntError)`,
   `UnknownLevel(String)`. Это настоящая ошибка: `Display` по-русски (в тексте есть имя поля, сам уровень, слово
   «метка»), `std::error::Error` с `source` у `BadTimestamp`, `From<ParseIntError>`.
3. **Разбор без копий.** `Entry<'a> { ts, level, target, message }` (`target` и `message` это `&'a str`).
   `parse_line(&str) -> Result<Entry<'_>, ParseError>`. Разбор не выделяет память.
4. **Ленивый обход.** `entries(&str)` возвращает итератор по `Result<Entry, LineError>`, где
   `LineError { line, error }`, номера строк с единицы (пустые строки номер занимают, но записей не дают).
   Первые элементы журнала в миллион строк читаются, не разбирая остальное.
5. **Свёртки.** Трейт `Aggregate { type Out; fn add(&mut self, &Entry); fn finish(self) -> Out }` и
   `run(записи, агрегат)`. Агрегаты `CountByLevel` (карта уровень в число, только встреченные) и
   `TopTargets::new(n)` (n самых частых источников, при равенстве по имени, пары `(String, usize)`).
   `only(записи, LevelSet)` оставляет записи нужных уровней. Любой потребитель может написать свой агрегат.
6. **Набор уровней и макрос.** `LevelSet` (`empty`, `with`, `contains`, `len`, `is_empty`; `Copy`, `Default`,
   `PartialEq`) и макрос `level_set![Warn, Error]` (любое число уровней, в том числе ноль, завершающая запятая
   допустима).
7. **Сводка.** `Report { total, bad_lines, by_level }` (`Default`, `Clone`, `PartialEq`, `Debug`),
   `merge`, `summarize(&str)`. При feature `json` метод `to_json()` даёт ровно
   `{"total":5,"badLines":1,"byLevel":{"INFO":3,"WARN":1,"ERROR":1}}` (имена в `camelCase`, уровни
   заглавными).
8. **Параллельность.** `par_map_chunks(текст, workers, f)` режет текст по границам строк на
   `min(workers, строк)` кусков (при нуле потоков один) примерно поровну по числу строк (первые куски получают
   лишние строки), вызывает `f` для каждого куска в своём потоке одновременно и возвращает результаты в порядке
   кусков. Паника в `f` пробрасывается вызывающему. `summarize_parallel(текст, workers)` даёт тот же
   результат, что `summarize`.
9. **Тесты и документация.** В `src` свои юнит-тесты (не меньше трёх `#[test]` в `#[cfg(test)]`). Примеры
   в документации у `parse_line` и `entries` (минимум два, с `assert`).

## Критерии приёмки

`cargo test --workspace` проходит целиком. Тесты проверяют каждый пункт выше, включая поведение:
отсутствие копий и ленивость (счётчик аллокаций), настоящую одновременность кусков, совпадение сводок,
сборку без feature `json` и отказ компилятора на `unsafe`.

## Как запускать

```
cargo test --workspace
```
