# Видно всё: логи, трейс и метрики соцсети

Пост опубликован, а подписчик не получил уведомление. Кто виноват: шлюз, сервис постов, шина или сервис уведомлений? Сегодня ответ
ищется руками: открыть логи четырёх сервисов, найти нужную минуту, угадать, какая строка чья. Нужно, чтобы у запроса был номер, по
которому в логах всех сервисов собирается его путь, а у каждого сервиса была страница `/metrics`, на которой видно, сколько
запросов, сколько из них ломаются и сколько они длятся. Сервисы здесь маленькие и живут в одном процессе, шина (аналог NATS)
устроена в памяти. Твоя часть: инструменты наблюдаемости и их подключение.

## Как устроено

```
клиент ──HTTP + traceparent──► шлюз ──«gRPC», metadata: traceparent──► posts ──шина, заголовок traceparent──► notify
                                │                                        │                                      │
                          RED + hop-span                           RED + hop-span                        RED + hop-span
                                └─ GET /metrics ─ текст Prometheus       └─ metrics()                           └─ metrics()
```

Каждый сервис при обработке запроса открывает span `hop` с полями `service`, `trace_id`, `span_id` и `parent_id` (готовая функция
`obs::hop_span`) и пишет внутри хотя бы одно событие. Готовый JSON-слой `obs::logs::JsonLines` кладёт span в массив `spans`
каждой строки, поэтому тест собирает трейс запроса только из логов: он смотрит, какие `hop` встречались и кто чей родитель.

## Что уже есть

- Воркспейс из двух пакетов: `src/crates/obs` (инструменты) и `src/crates/social` (три сервиса и шина).
- Готово: JSON-слой логов `obs::logs`, `hop_span`, шина `Bus`, тела запросов-ловушек в `PostService::save` (пустой пост даёт 422, тело
  `boom` даёт 500, тело `slow` отвечает через 5 секунд), типы запроса и ответа шлюза.
- Приёмочные тесты: `src/crates/obs/tests/units.rs` и `src/crates/social/tests/flow.rs`. Править их нельзя, CLI восстанавливает их
  перед проверкой. Сеть и брокер не нужны.
- Заготовки с `todo!()` в остальном. Предупреждения о неиспользуемом исчезнут по мере работы.

## Что сделать (везде, где `todo!()`)

1. `obs::trace`. `parse` разбирает `traceparent` строго (как в `svobs7`), `header` собирает его обратно, `root`, `child` и `incoming`
   выдают контексты (случайные числа подаются функцией `ids`), `enter` возвращает контекст и номер родителя (`None` для корня).
2. `obs::metrics::Registry`. `inc` увеличивает счётчик с метками, `gauge_add` двигает gauge без меток, `observe` кладёт значение в
   гистограмму с метками. Метки сортируются по имени, значения экранируются (`\`, `"`, перевод строки). `render` выводит всё в формате
   Prometheus: семейства по алфавиту, у каждого `# HELP` и `# TYPE`, ряды по меткам, у гистограммы накопительные бакеты, `+Inf`, `_sum`
   и `_count` для каждого набора меток.
3. `obs::red::Red::track(route, работа)`. Работа возвращает `(код, значение)`. Для завершённой работы увеличивается
   `http_requests_total{route,status}` и в `http_request_duration_seconds{route}` попадает длительность в секундах; пока работа идёт,
   `http_requests_in_flight` больше нуля, а если ждать надоело и работу бросили, он возвращается к прежнему значению и в завершённые
   работа не попадает. Значение работы `track` возвращает как есть.
4. `obs::redact::access_line`. Строка вида `GET /export?page=2&token=[redacted] 200 user-agent="curl/8.0"`: секретные параметры запроса
   и секретные заголовки (по списку из `svobs16`) скрыты, а данные клиента не могут разорвать строку.
5. `Gateway::handle`. `GET /metrics` отвечает текстом реестра шлюза и в RED не считается. Остальное: продолжить трейс клиента (или начать
   новый), открыть span `hop`, внутри пройти по маршрутам `POST /posts` (зовёт `PostService::create`, передав `traceparent` в metadata),
   `GET /health`, всё прочее 404 с меткой маршрута `unmatched`, написать событие со строкой доступа, и всё это завернуть в `Red::track`.
6. `PostService::create` и `NotifyService::run_once`. Продолжают трейс из metadata и из заголовка сообщения, открывают свой `hop`,
   пишут событие, считают RED (маршруты `create` и тема сообщения). Сервис постов при успехе публикует `post.created` с заголовком
   `traceparent` своего перехода.

## Критерии приёмки

`cargo test --workspace` проходит и `cargo clippy --workspace --all-targets -- -D warnings` чист. Тесты проверяют:

- один запрос это один трейс на трёх сервисах, собранный только из логов; родитель каждого перехода это предыдущий, а клиентский
  `traceparent` продолжается; без заголовка и с мусором в нём начинается новый трейс, запрос при этом не отвергается;
- два запроса не смешивают трейсы;
- токены, ключи, `Authorization` и `Cookie` не попадают в логи, а строка доступа при этом есть; поддельный перевод строки не создаёт
  второй записи, каждая строка лога это один JSON-объект;
- `/metrics` шлюза показывает по маршрутам счёт запросов с кодами, длительности и нуль «в работе»; пути клиентов в метки не попадают;
- у сервисов свои метрики; длительность считается в секундах; брошенный клиентом запрос не оставляет «в работе» выше нуля.

## Подсказки

Строгий разбор и новые span_id это `svobs7`; правила деления на метки и экранирование это `svobs10` и `svobs13`; накопительные бакеты
это `svobs11`; обёртка с «в работе» через `Drop` это `svobs14`; скрытие секретов это `svobs16`. Работу сервиса оборачивай в
`.instrument(span)` (а не держи `span.enter()` через `await`: это `svobs3`). Разбирать заголовок трейса для родителя и для нового
контекста можно один раз: `enter` возвращает обе половины.
