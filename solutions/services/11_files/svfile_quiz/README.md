# Аватары: загрузка через шлюз, проверка, хранение и подписанная ссылка

Пользователи хотят аватары. Шлюз принимает картинку потоком, user-service решает, годится ли она, кладёт её на диск и записывает
ссылку в профиль, а потом шлюз же выдаёт подписанную ссылку на скачивание и раздаёт файл безопасно. Всё, что ты делал в главе
по отдельности, теперь работает вместе. Сеть и gRPC здесь не нужны: между шлюзом и сервисом обычный вызов функции, а настоящий
клиентский стрим в gRPC будет в вехе. Диск настоящий (каталог во временной папке).

## Что уже есть

- Воркспейс из трёх пакетов: `src/crates/files` (всё про файлы), `src/microservices/user-service` (аватары пользователей),
  `src/microservices/api-gateway` (входная точка).
- `files`: трейт `FileStore`, готовы `FsStore::get/exists/rename/delete`, `sniff`, `Kind`, `hmac_sha256`, `ct_eq`, типы ошибок и `Response`.
- `user-service`: готовы `Db` (в памяти: аватары, записи «ожидает», счёт ссылок на ключ, флаг `fail_commit` для тестов), `avatar_link`, `open`, `read`.
- Приёмочные тесты: `src/crates/files/tests/units.rs` и `src/microservices/api-gateway/tests/acceptance.rs`. Править их нельзя,
  CLI восстанавливает их перед проверкой.
- Заготовки с `todo!()` в остальном. Предупреждения компилятора о неиспользуемом исчезнут по мере работы.

## Что сделать (везде, где `todo!()`)

1. `files::limit::limit(body, max, declared)`. Заявленный размер больше предела: отказ до чтения. Иначе байты считаются по ходу, кусок,
   который выводит за предел, превращается в ошибку `FileTooLarge`, после неё поток заканчивается. Заявленному размеру не верят.
2. `files::store::FsStore::put`. Запись атомарна: временный файл в том же каталоге, подтверждение на диск и переименование. Любая неудача
   (ошибка тела, диска, отмена задачи) не оставляет ни временного файла, ни изменений в итоговом.
3. `files::content::put_content(store, body, temp_key)`. Тело пишется под временным ключом, хеш считается по ходу. Ключ это sha256 в hex.
   Такой ключ уже есть: временный удаляется, `existed: true`. Иначе переименование. Ошибка тела не оставляет временного.
4. `files::image::check_avatar(bytes)`. Не больше `MAX_BYTES`, тип по сигнатуре (PNG и JPEG; WebP это `Unsupported`), размеры из заголовка:
   ширина и высота не нули, не больше `MAX_SIDE`, площадь не больше `MAX_PIXELS`. Обрубленный заголовок: `Truncated`.
5. `files::sign::Signer::{link, verify}`. Ссылка `/files/<ключ>?exp=<срок>&name=<имя>&sig=<hex>`, подпись HMAC-SHA256 покрывает ключ, срок и имя
   однозначно. Порядок проверок: формат, подпись, срок (в момент `exp` уже просрочено).
6. `files::serve::serve(meta, content)`. Картинка PNG/JPEG/WebP по сигнатуре: настоящий тип и `inline`. Всё остальное: `application/octet-stream`
   и `attachment`. Всегда `nosniff` и `Content-Security-Policy: default-src 'none'; sandbox`. Имя в `Content-Disposition` в двух безопасных формах.
7. `AvatarService::set_avatar(user, body, now)`. Собрать тело под лимитом `MAX_BYTES`, проверить `check_avatar` (ошибки перевести в `AvatarError`),
   завести запись «ожидает» на временный ключ, записать `put_content`, перенести запись «ожидает» на итоговый ключ, записать ссылку в `Db`.
   Прежний файл пользователя удалить, только если больше никто на него не ссылается. Сбой базы оставляет запись «ожидает».
8. `AvatarService::sweep(now)`. Записи «ожидает» старше `GRACE` секунд: удалить файл (если на него никто не ссылается), забыть запись. Вернуть,
   сколько файлов удалено. Свежие записи не трогать.
9. `Gateway::put_avatar(user, declared_len, body, now)`. Обернуть тело в `limit`, передать сервису, вернуть подписанную ссылку на аватар.
   `Gateway::download(path_and_query, now)`. Ссылка не прошла проверку: 400 (формат), 403 (подпись), 410 (срок). Файла нет: 404.
   Иначе 200 и ответ `serve`.

## Критерии приёмки

`cargo test --workspace` проходит и `cargo clippy --workspace --all-targets -- -D warnings` чист. Тесты проверяют:

- лимит на лету и отказ по заявленному размеру до чтения тела, ложь в `Content-Length`;
- атомарность записи: читатель не видит половину, оборванная загрузка ничего не меняет, отмена не оставляет мусора;
- ключ по содержимому: один файл на одинаковые аватары, общий файл не удаляется, пока на него кто-то ссылается;
- проверку картинки по заголовку: бомба, переполнение площади, поддельный маркер внутри JPEG, HTML под видом PNG;
- ссылки: срок, подмену срока и имени, перенос границы между полями, подделку с просроченным сроком;
- безопасную раздачу: тип выбирает сервер, `nosniff`, имя без перевода строки и вырвавшейся кавычки;
- сирот: запись «ожидает», `sweep` после `GRACE` и никогда раньше, завершённые загрузки не трогаются;
- восемь параллельных загрузок одной картинки: один файл, ни одного временного.

## Подсказки

Почти каждый пункт это задача главы: `limit` это `svfile4`, `put` это `svfile3` и `svfile5`, `put_content` это `svfile8`, `check_avatar`
это `svfile6` и `svfile7`, `Signer` это `svfile10` и `svfile11`, `serve` это `svfile13`, `set_avatar` и `sweep` это `svfile12`.
Прежний ключ удаляют по числу ссылок на него (`Db::refs_to`), а не по тому, чей он был.
