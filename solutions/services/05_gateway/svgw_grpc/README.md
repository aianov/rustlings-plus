# Шлюз и gRPC: общий канал, дедлайн, перевод ошибок

Шлюз получает от клиента JSON, а user-service говорит на gRPC. Сейчас каждый вызов собирает соединение с нуля
(рукопожатие дороже самого запроса), ждёт ответа сколько понадобится (завис сервис, завис и клиент) и сообщает клиенту
то, что написал сосед. Нужен аккуратный клиент `UserGateway`: одно общее соединение, дедлайн на вызов, metadata
запроса и перевод `Status` в ошибки шлюза.

## Что уже есть

- Воркспейс с пакетом `src/microservices/api-gateway` и `build.rs`, который генерирует код из `proto/user.proto`
  (`api_gateway::pb`: клиент `UsersClient`, сервер `UsersServer`).
- `src/common.rs`: `GwError { code, message }` и `RequestCtx { request_id, user_id }`.
- `src/user_client.rs`: заготовка `UserGateway` с константой `CALL_DEADLINE` (300 мс).
- Приёмочные тесты `tests/acceptance.rs` (поднимают настоящий tonic-сервер на `127.0.0.1:0`). Править их нельзя.

## Что сделать

1. `UserGateway::new(addr)`: создаёт один `Channel` лениво (`Endpoint::connect_lazy`), соединение откроется при первом
   вызове. Канал дёшево клонируется, и все вызовы идут по одному соединению, в том числе параллельные.
2. `UserGateway::get_user(data, ctx)`: из `data` берётся числовой `id` (иначе ошибка `invalid_argument` без обращения к
   сервису), собирается запрос с дедлайном `CALL_DEADLINE` на самом вызове (`Request::set_timeout`) и metadata
   `x-request-id` и `x-user-id` (второй только для вошедшего), ответ превращается в JSON `{"id", "name"}`.
3. Статус сервиса переводится в ошибку шлюза: `NotFound` в `not_found`, `InvalidArgument` в `invalid_argument`,
   `Unavailable` в `unavailable`, `DeadlineExceeded` и `Cancelled` (так tonic сообщает о сработавшем таймауте) в `deadline_exceeded`, всё остальное (включая `PermissionDenied` и
   `Unauthenticated`: при служебном вызове это поломка на нашей стороне) в `internal`. Сообщение сервиса клиенту не
   передаётся, у ошибок шлюза свои тексты.

## Критерии приёмки

`cargo test --workspace` проходит и `cargo clippy --workspace --all-targets -- -D warnings` чист. Тесты считают принятые
сервером TCP-соединения (25 вызовов, в том числе параллельных, это одно соединение), проверяют metadata, срабатывание
дедлайна на медленном сервисе, перевод статусов без утечки текста, отсутствие обращений к сервису при плохих данных и
быстрый отказ, когда на порту никто не слушает. Первая сборка тянет tonic и prost, это может занять несколько минут.

## Подсказки

README главы: разделы про общий канал и дедлайны. `Channel` в tonic клонируется и мультиплексирует запросы по одному
HTTP/2-соединению; создавать клиента (`UsersClient::new(channel.clone())`) на каждый вызов дёшево.
