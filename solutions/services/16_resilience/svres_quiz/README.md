# Шлюз, который переживает соседей

Шлюз соцсети ходит в user-service и post-service. Сегодня оба здоровы, а завтра один из них тормозит, второй перезапускается, а клиент мобильного приложения теряет ответ
на «создать пост» и повторяет его. Сейчас шлюз либо падает вместе с соседом, либо плодит дубли. Твоя часть: собрать вызовы шлюза в одну защищённую функцию, которая
использует все приёмы главы и доказывает это на подменах, умеющих падать, зависать и терять ответы.

## Как устроено

```
Gateway::call(dep, req, idempotent, budget)
  1. Shedder        вход шлюза: больше max_in_flight запросов одновременно нельзя, отказ сразу (Overloaded)
  2. переборка      у каждой зависимости свои места, нет места, отказ сразу (Full); незнакомая зависимость (UnknownDep)
  3. Deadline       один срок на запрос со всеми повторами; он едет в Backend::call вторым аргументом
  4. цикл попыток:
       Breaker::allow          открыт, отказ сразу (CircuitOpen)
       run_with(срок, вызов)   срок вышел, отказ (DeadlineExceeded), попытка считается неудачей
       исход                   успех, ошибка клиента (не вина зависимости), ошибка зависимости
       should_retry + RetryBudget + пауза с джиттером   повторить или вернуть Failed
```

- `src/crates/guard/src/deadline.rs`, `retry.rs`, `breaker.rs`, `shed.rs`: готовые кирпичи из задач главы. Читать и менять их не нужно, но заглянуть полезно.
- `src/crates/guard/src/backend.rs`: типаж `Backend`, за которым стоят настоящие сервисы. В тестах за ним подмена.
- `src/crates/guard/src/gateway.rs`: `Gateway`. Конструктор готов. Тебе нужны два метода, `call` и `create_post`.
- `src/crates/guard/tests/gateway.rs`: приёмочные тесты. Править их нельзя, CLI восстанавливает их перед проверкой. Сеть и брокер не нужны.

## Что сделать

1. `Gateway::call` по схеме выше. Если ошибка клиента (неверный аргумент, не найдено и так далее), зависимость в этом не виновата: для предохранителя это не неудача.
2. `Gateway::create_post`: создание поста с ключом идемпотентности. Ключ придумывает шлюз, один на запрос, общий для всех попыток этого запроса и разный у разных запросов.
   Запрос с ключом можно безопасно повторять и после неоднозначных ошибок.

После работы `cargo test --workspace` проходит и `cargo clippy --workspace --all-targets -- -D warnings` чист.

## Критерии приёмки

- две временные ошибки подряд и успех: запрос успешен, обращений к зависимости три;
- ошибки клиента не повторяются и не открывают предохранитель; неидемпотентный запрос после `Internal` не повторяется;
- зависший вызов обрывается ровно в срок, после срока попыток нет; зависимость видит оставшийся срок, а не новый бюджет;
- лежащая зависимость открывает предохранитель, пока он открыт, вызовы в неё не уходят, через паузу проба закрывает его; предохранитель одной зависимости не трогает другую;
- 200 запросов к лежащему сервису порождают не больше 235 обращений (бюджет повторов);
- зависшая зависимость занимает только свои места, пятый вызов к ней отвергается сразу, вызовы к другой проходят; сверх лимита шлюза отказ тоже мгновенный;
- потерянный ответ на «создать пост» после повтора даёт ровно один пост, разные запросы получают разные ключи.
