# JetStream для notify-service: уведомления без потерь

Вчера notify-service перезапустили на минуту, и все лайки за эту минуту пропали: core NATS ничего не хранит. Теперь события
соцсети идут через JetStream. В слое `nats-engine` нужно добавить модуль `js`, который берёт на себя всё хрупкое:
подготовку stream при запуске, публикацию с подтверждением, постоянного читателя с подтверждением после работы, повторы с
паузами, мёртвую тему для ядовитых событий и сигналы «я ещё работаю». notify-service в проекте уже переписан поверх этого
слоя, поэтому его тесты проверяют твой модуль в сборе.

## Что уже есть

- Воркспейс из двух пакетов: `src/crates/nats-engine` (шина из прошлого проекта плюс заготовка `js.rs`) и
  `src/microservices/notify-service` (готов целиком: события читает через `js::open_feed`, запросы о непрочитанных
  по-прежнему отвечает через `Bus::serve`).
- В `js.rs` готовы типы (`StreamSpec`, `Published`, `FeedSpec`, `Verdict`, `Handler`, `Feed`), константы `MAX_DELIVER`
  (пять доставок), `PUBLISH_ATTEMPTS` (три попытки) и функция `backoff()` (паузы повторов 100, 200, 400, 800 мс), а также
  `Feed::stop`.
- Приёмочные тесты: `nats-engine/tests/js_acceptance.rs` и `notify-service/tests/acceptance.rs`. Править их нельзя.
  Они ходят в настоящий NATS с JetStream на `127.0.0.1:54222` (адрес из `RUSTLINGS_NATS_URL`).

## Что сделать (везде, где `todo!()`)

1. `ensure_stream`. Stream с именем, темами и окном дубликатов из `StreamSpec`: нет, создаётся; есть и темы совпадают, не
   трогается; есть, темы изменились, обновляются без потери записей. Что брокер менять запрещает, это ошибка
   `BusError::Transport`. Никакого удаления.
2. `publish_event`. Без связи сразу `Unavailable`. Тело сериализуется в JSON, заголовки идентификаторов запроса из `Meta`,
   плюс `Nats-Msg-Id` равный `event_id`. Ждёт подтверждения записи и возвращает `Published` (номер и признак дубликата).
   При таймауте повторяет до `PUBLISH_ATTEMPTS` попыток с тем же идентификатором и паузой 50 мс; все попытки истекли это
   `Timeout`; любая другая ошибка (например, тему не ловит ни один stream) возвращается сразу как `Transport`.
3. `dead_letter`. Публикует копию сообщения в `dead_subject` и ждёт подтверждения. Заголовки копии: `X-Original-Subject`
   (исходная тема), `X-Delivery-Count` (сколько раз доставлялось), `X-Error` (причина без переводов строки).
4. `open_feed`. Находит stream, получает или создаёт durable consumer с именем `spec.durable`: явные подтверждения,
   `ack_wait` из спецификации, `max_deliver = MAX_DELIVER`, фильтр по `spec.filter`. Дальше фоновая задача читает пачками
   по `spec.batch` с коротким ожиданием и обрабатывает сообщения по одному:
   - тело разбирается в `Envelope<T>`; не разобралось, это сразу мёртвая тема и `term` без вызова обработчика;
   - пока работает обработчик, раз в треть `ack_wait` брокеру отправляется «ещё работаю»;
   - `Done` подтверждается; `Retry` возвращается через паузу из `backoff()` по номеру доставки, а на последней
     доставке (`MAX_DELIVER`) уходит в мёртвую тему с причиной и получает `term`; `Poison(причина)` сразу в мёртвую тему
     и `term`;
   - если копию в мёртвую тему опубликовать не удалось, сообщение возвращается с паузой, а не теряется;
   - сигнал остановки проверяется между пачками.

## Критерии приёмки

`cargo test --workspace` проходит и `cargo clippy --workspace --all-targets -- -D warnings` чист. Тесты проверяют:
`ensure_stream` не стирает историю, расширяет темы и отказывает при конфликте; повторная публикация с тем же именем
распознаётся брокером и повтор тему не удваивает; публикация без связи отказывает сразу; читатель получает каждое событие
один раз по порядку, а после перезапуска продолжает с места остановки; повторы идут с растущими паузами; исчерпанные
повторы и ядовитые события, включая битый JSON, оказываются в мёртвой теме с историей, не задерживая остальных;
медленный обработчик (втрое дольше `ack_wait`) не получает дубль; два экземпляра с одним именем делят поток; в notify-service
перезапуск посреди работы не теряет и не повторяет уведомления.

## Подсказки

Задачи `svjs3`, `svjs4`, `svjs5`, `svjs6`, `svjs7`, `svjs9`, `svjs11` и `svjs12` складываются в этот модуль почти буквально. Сначала
`ensure_stream` и `publish_event`, потом `dead_letter`, и только потом цикл `open_feed`.
