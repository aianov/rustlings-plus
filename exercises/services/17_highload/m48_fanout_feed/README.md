# Веха 48. Лента для нагрузки

Лента из m40 собирается при каждом чтении: feed-service перебирает все посты сети, фильтрует по подпискам и сортирует. Пока постов сотни, это незаметно; при миллионе каждое открытие ленты перебирает миллион. Страницы листаются номером, и глубокая страница читает и выбрасывает всё, что до неё. id постов это номер в списке одного экземпляра post-service, и второй экземпляр выдаст те же номера. Шлюз берёт профиль каждого автора страницы отдельным вызовом (N+1), кэш профилей не знает о переименованиях, а каждый лайк это отдельная запись в журнал.

Эта веха готовит ленту к нагрузке. feed-service раскладывает пост по лентам подписчиков при записи и обрезает каждую ленту до N; посты знаменитостей не раскладываются, а подмешиваются при чтении; большие раскладки идут фоновыми пачками. Лента листается непрозрачным курсором (время, id), битый курсор отвергается. id постов сортируемые: время, узел, счётчик, и откат часов не даёт дублей. Авторы страницы приходят одним вызовом, кэш профилей шлюза это LRU за O(1) с разбросом TTL, кэшем промахов, single-flight и инвалидацией по `user.profile_changed` на всех экземплярах с учётом версии. Лайки копятся в памяти и пишутся в журнал пачкой, в том числе при остановке.

Всё собирается из главы 17_highload: задачи с svhl1 по svhl16 и проект svhl_quiz.

## Что сделать

1. **service-runtime**:
   - `ids/`: `SortableIds::new(node)` (`next`, `next_at(ms)`, `observe(id)` после перезапуска), `compose`, `split`, `IdParts { millis, node, counter }`: 41 бит миллисекунд от `EPOCH_MS` (2025-01-01), `NODE_BITS` = 10, `COUNTER_BITS` = 12; время генератора не идёт назад (откат часов продолжает старую миллисекунду), переполнение счётчика сдвигает миллисекунду вперёд;
   - `cache/`: `Lru<K, V>` (`new(ёмкость)`, `get` освежает, `peek` нет, `put` возвращает вытесненный ключ, `remove`, `len`, `keys_newest_first`): двусвязный список на индексах в `Vec` и `HashMap` ключ → индекс, все операции O(1).

2. **journal**: `append_all(&[E])` пишет пачку строк одним сбросом; `append` это пачка из одной.

3. **post-service**:
   - посты хранятся списком с индексом id → место; id из `SortableIds`, узел из `POSTS_NODE` (0..=1023, по умолчанию 1), `MemoryPosts::on_node`; после восстановления генератор продолжает за последним id;
   - лайк меняет счётчик и множество лайкнувших сразу, а запись в журнал и событие откладывает: накопленные лайки сбрасываются одной пачкой перед любой другой записью, при выборке релея (`unpublished`), по таймеру `LIKE_FLUSH` (100 мс), при `LIKE_BATCH` = 256 и при остановке; `PostRepository::flush`;
   - `idempotency` и всё прежнее работают с новыми id.

4. **feed-service**:
   - `FeedLimits { max, celebrity, inline }` (500, 1000, 256) из `FEED_MAX`, `FEED_CELEBRITY`, `FEED_FANOUT_INLINE`; `MemoryFeed::with_limits`;
   - `repository/state.rs`: ленты читателей `BTreeSet<Cursor>` с обрезкой до `max`, свежие посты автора; пост ложится в ленту автора и подписчиков: первым `inline` сразу, остальным в очередь пачек; у знаменитости (подписчиков не меньше `celebrity`) не раскладывается вовсе; подписка дозаполняет ленту свежими постами автора; при чтении к ленте подмешиваются посты знаменитостей из подписок, скрытые и удалённые отбрасываются;
   - `common/cursor.rs`: `Cursor { at, post }`, `encode` (`c1.<at>.<post>.<проверка>` в hex), `decode` с `BrokenCursor` на любом искажении;
   - `FeedRepository::after(viewer, before, take) -> (посты, следующий курсор)`, `drain(budget)`, `pending()`; фоновая задача раскладывает очередь пачками по `FAN_OUT_BATCH` = 512;
   - `FeedRequest.cursor`, `FeedReply.next`; пустой курсор это первая страница, битый это ошибка `validation`; старый номер страницы работает для совместимости;
   - слова `offset` в коде feed-service нет.

5. **user-service**: `GetProfiles(ProfilesRequest { ids })` отдаёт существующие профили пачкой (до 100 id).

6. **Шлюз**:
   - `common/profiles.rs`: `ProfileCache` на `Lru` (`PROFILE_CAPACITY` = 10 000), свежесть с разбросом ±10%, `Known { Found, Missing }` (промах живёт `MISS_FOR` = 5 с), `claim(id) -> Claim { Mine(Flight), Wait(watch) }` и `finish(flight, known)`: одновременные промахи по одному id ждут одного запроса; `invalidate(id, version)` принимает только версию новее виденной и поднимает эпоху ключа, поэтому ответ, начатый до инвалидации, в кэш не попадает; `stale(id)` отдаёт протухший профиль на случай отказа;
   - `routes/profiles.rs`: авторы страницы одним вызовом `GetProfiles` под переборкой, предохранителем и повторами из m47;
   - `controller/invalidate.rs`: каждый экземпляр подписан на `<корень>.events.user.profile_changed.*` и инвалидирует профиль по версии события;
   - `posts.feed` принимает `cursor`, `FeedPage` несёт `next`.

7. **contracts**: `FeedPage.next: Option<String>`.

8. **Окружение**: `FEED_MAX`, `FEED_CELEBRITY`, `FEED_FANOUT_INLINE`, `POSTS_NODE`, `GATEWAY_PROFILE_FRESH_MS` и для стенда нагрузки `GATEWAY_USER_RATE=2000`, `GATEWAY_USER_BURST=4000` в `.env.example` и `.env`.

Клиент курса приходит готовым: id постов длинные, поэтому клиент нумерует посты сеанса коротко (`[1]`, `[2]`) и сам переводит номер в настоящий id в `like`, `comment`, `show`, `delete`; лента подсказывает «… дальше: more», а `more` листает по курсору.

## Приёмка

Тестам нужен NATS курса с JetStream на `127.0.0.1:54222` (адрес из `RUSTLINGS_NATS_URL`).

- `service-runtime/tests/journey/m48_fanout_feed.rs`: порядок id, откат часов и переполнение без повторов, продолжение после перезапуска, LRU.
- `feed-service/tests/journey/m48_fanout_feed.rs`: курсор и отказ на битом; лента совпадает с моделью на случайных последовательностях (seed в сообщении, `E2E_SEED` повторяет); знаменитость видна сразу и новому подписчику; фоновые пачки; обрезка до N и конец ленты.
- `post-service/tests/journey/m48_fanout_feed.rs`: сортируемые id с узлом; сорок лайков одной пачкой, сброс при выборке релея, все лайки после перезапуска.
- `api-gateway/tests/journey/m48_fanout_feed.rs`: single-flight, кэш промахов, эпоха и версии, LRU и протухший профиль; лента по курсору без пропусков и повторов, битый курсор это `validation`; переименование доходит до авторов ленты через событие.
- `loadgen/tests/journey/m48_fanout_feed.rs`: восемь пользователей три секунды, без ошибок, p99 ленты меньше 500 мс.
- новые версии тестов прошлых вех: m31, m38 шлюза (короткие номера постов в клиенте, настоящий id из карточки), m45 шлюза (прогрев перед проверкой трейса), m46 loadgen (стенд с широкими вёдрами), m30 и m40 (`FeedRequest` с курсором), `fakes.rs` (`GetProfiles`, `next`).
- тесты прошлых вех проходят, `cargo make check` зелёный.

Архитектура: файлы по дереву; `offset` нет в feed-service; обрезка ленты, знаменитости, фоновые пачки, проверка курсора; биты id и монотонность времени; id из генератора; LRU на индексах; батч авторов, single-flight, разброс TTL, кэш промахов, версия инвалидации, подписка на `profile_changed`; пачка лайков и сброс при остановке; и все договорённости прошлых вех.

## Как запустить

NATS курса должен работать: `127.0.0.1:54222`.

```
cd backend
cargo make check
FEED_CELEBRITY=1 cargo make demo
```

alice пишет десяток постов, bob подписывается и открывает `feed`: внизу «… дальше: more», и `more` листает дальше, пока лента не кончится. С `FEED_CELEBRITY=1` alice знаменитость с первого подписчика: её новый пост виден bob сразу, хотя по лентам не раскладывался. `cargo make load` с полоской `feed` в отчёте показывает p99 ленты под нагрузкой.
