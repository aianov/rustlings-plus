# Наблюдаемость: что на самом деле происходит в живой системе

Пиццерия с доставкой. Сервисов четыре: приём заказов, кухня, курьеры, уведомления. Звонит клиент: «Заказ 4812 был час назад, пиццы нет». Что
ты знаешь? Ничего. Заказ принят? Кухня его видела? Курьер назначен или все курьеры заняты? А может, уведомление «заказ готов» просто не
дошло, а пицца давно у двери? Без наблюдаемости ответ добывается так: открыть логи четырёх сервисов, найти нужную минуту, угадывать,
какая строка относится к какому заказу. С ней: ввести номер, увидеть путь заказа через все сервисы и место, где он застрял.

Наблюдаемость это способность понять, что происходит внутри системы, глядя только на то, что она сама о себе рассказывает. Рассказывает она
тремя способами, и у каждого свой вопрос.

```
   логи       «что произошло?»        события с подробностями: курьер 9 назначен на заказ 4812
   трейсы     «как это прошло?»       путь одного запроса через сервисы: кто кого звал и сколько ждал
   метрики    «как дела вообще?»      числа во времени: сколько заказов в минуту, сколько падает, как долго
```

Метрики говорят, что что-то не так (график ошибок пополз вверх). Трейс указывает, где именно (кухня отвечает по 12 секунд). Логи объясняют,
почему (у этого заказа пустой адрес, и кухня три раза перебирала варианты). Глава строит все три, начиная с самого простого.

## Логи: события с полями

Самый частый способ испортить лог такой:

```rust
println!("courier {} assigned to order {} in {} ms", courier, order, ms);
```

Человеку читать можно. Машине нет: чтобы найти все назначения курьера 9, нужна регулярка, и она ломается, когда кто-то поправит слова.
Крейт `tracing` отделяет данные от текста:

```rust
tracing::info!(courier_id = 9, order_id = 4812, took_ms = 37, "курьер назначен");
```

У события есть уровень, цель (обычно путь модуля), текст и именованные поля с типами. Текст постоянный, данные в полях: так события
группируются, считаются и ищутся. Короткая запись `info!(order_id, "...")` берёт переменную с тем же именем. Значение можно обернуть:
`%x` печатает через `Display`, `?x` через `Debug`; ошибку передают как `error = %e`.

Уровни выбирают по тому, кто должен среагировать:

```
ERROR   сервис не смог сделать то, что обязан; кто-то должен посмотреть (упала база, сломан инвариант)
WARN    запрос отклонён или система деградирует, но сервис работает как задумано (неверный ввод, повтор, медленно)
INFO    важные события жизни: запустились, заказ принят, курьер назначен
DEBUG   подробности для разработчика; в продакшене выключено
TRACE   ещё подробнее, обычно построчно
```

Ошибка клиента (неверный пароль, пустой заказ) это WARN или даже INFO, а не ERROR: сервис сработал верно. Иначе дежурный, которого будит
ERROR, привыкнет игнорировать их, и пропустит настоящий.

## Span: контекст, который прилипает к событиям

Пять заказов обрабатываются одновременно, строки перемешаны. Чтобы каждая знала, чья она, не передавать же `order_id` в каждый вызов. Для этого
есть **span**: интервал времени с именем и полями, внутри которого пишутся события. Все события внутри получают его поля.

```rust
let span = tracing::info_span!("order", order_id = 4812, status = tracing::field::Empty);
```

Поле можно объявить пустым и заполнить позже (`span.record("status", "готов")`): ответ известен только в конце. Span начинается при
создании, **входит** (enter), когда в нём работают, **выходит**, когда уходят, и закрывается, когда исчезает последняя ссылка на него.

Теперь важное про `async`. Вот интуитивный код:

```rust
async fn cook(order: u64) {
    let _guard = tracing::info_span!("order", order).enter();
    oven().await;
    tracing::info!("испечено");
}
```

`enter()` делает span текущим **для потока** и держит его, пока жив guard. Но guard лежит внутри состояния future и переживает `await`.
Задача A вошла в span и уснула на `oven().await`; поток пошёл выполнять задачу B, и та вошла в свой span поверх. Когда A проснулась, текущим
в потоке считается span B:

```
поток:   A.enter ─ A спит ─┐ B.enter ─ B спит ─┐ A проснулась: «испечено»
стек:    [A]               [A, B]              [A, B]   ← событие A записано в span B
```

Лог правдоподобный, но врёт: запись одного заказа получила номер другого. Правильный способ для async это не входить руками, а **подклеить**
span к future: расширение `Instrument` входит в span на время каждого опроса и выходит при возврате.

```rust
async { oven().await; tracing::info!("испечено") }.instrument(span).await;
```

Второй случай той же беды: `tokio::spawn` запускает новую независимую задачу, и контекст в неё не переходит. Явно переносят текущий span:
`.in_current_span()` на запускаемой future.

Синхронный код, где нет `await`, спокойно обходится `enter()`; правило касается именно async.

## Подписчик, слои, фильтры

Макросы только создают события и span. Что с ними делать, решает **подписчик** (subscriber), устанавливаемый один раз при старте. В
`tracing-subscriber` он собирается из слоёв (layers) поверх реестра span (`Registry`): один слой печатает в консоль, другой пишет JSON в файл,
третий считает ошибки.

```rust
let subscriber = tracing_subscriber::registry().with(console_layer).with(json_layer);
tracing::subscriber::set_global_default(subscriber)?;   // один раз на процесс
```

В тестах подписчик ставят локально (`with_default` или `set_default`) и собирают события в свой слой, чтобы проверять логи как данные.

**Фильтр** решает, какие события доходят. `EnvFilter` читает его из переменной окружения `RUST_LOG`: список директив `цель=уровень` через запятую.
`warn` это общий уровень, `info,kitchen=debug` включает подробности одного модуля, а директива действует и на вложенные модули по префиксу
пути. Более точная директива побеждает более общую. Оператор правит `RUST_LOG` без пересборки, поэтому в аварии подробные логи включаются за
секунды. Опечатка в директиве не должна ронять сервис или молча глушить логи: безопасный режим по умолчанию и сообщение о причине.

**Свой слой** нужен, когда стандартного вывода мало: формат JSON, список последних ошибок для страницы, счётчик событий по уровням. Слой
реализует `Layer` и получает события и span. Поля события он читает через посетителя (`Visit`): `tracing` не складывает их в словарь, а
вызывает метод на каждое значение по типу (`record_str`, `record_i64`, `record_debug` и другие). Метод `record_debug` получает всё, для чего
нет точного метода, а текст сообщения приходит как поле с именем `message`. Для ошибок есть отдельный `record_error`, а по умолчанию он
печатает отладочный дамп, поэтому его переопределяют, если нужен текст.

Один неочевидный факт: уровни упорядочены от **ERROR (наименьший) к TRACE (наибольший)**. «WARN или важнее» поэтому пишется как «не больше WARN».

## Сквозной трейс: один номер на весь путь

Заказ прошёл четыре сервиса, и каждый написал свой лог. Чтобы склеить строки в историю, нужен общий номер, который сервисы передают друг другу.
Стандарт W3C Trace Context делает это заголовком `traceparent`:

```
00 - 4bf92f3577b34da6a3ce929d0e0e4736 - 00f067aa0ba902b7 - 01
версия     trace-id (128 бит, 32 hex)   span-id (64 бит)    флаги (бит 0: sampled)
```

`trace-id` один на весь путь запроса. `span-id` у каждого перехода свой: когда сервис получил запрос, он оставляет `trace-id`, придумывает
новый `span-id` для своей работы и записывает чужой `span-id` как **родителя**. Из пар «span и его родитель» в логах потом собирается
дерево вызовов. В дальнейший вызов сервис отправляет `traceparent` со своим `span-id`.

```
клиент ──traceparent──► приём заказов ──metadata──► кухня ──заголовок NATS──► уведомления
 span A                  span B (родитель A)         span C (родитель B)       span D (родитель C)
 trace T                 trace T                     trace T                   trace T
```

Контекст не переходит границу процесса сам. На каждом транспорте нужна пара: **положить** в исходящее (HTTP-заголовок, metadata gRPC,
заголовок сообщения NATS) и **достать** из входящего. Забыл одну сторону на одном транспорте, и трейс рвётся именно там: после NATS потребитель
начинает новый трейс, и найти, из-за какого заказа ушло уведомление, нельзя. В заголовок кладут контекст того перехода, который отправляет, а не
того, что пришёл ему на вход.

Три правила надёжности. Разбор строгий: заглавные буквы, неверные длины, нулевые идентификаторы, версия `ff` означают «заголовка нет». Мусор
не повод отвечать клиенту ошибкой: просто начинается новый трейс. Решение о выборке (бит `sampled`) принимает тот, кто начал трейс. И сообщение без
заголовка (его отправил старый сервис) обрабатывается как обычно, но с новым трейсом.

Из логов дерево собирают так: все записи со своим `trace-id`, по `span-id` и родителю в дерево, потерянные родители становятся корнями. «Самый
медленный переход» это тот, где ушло больше всего собственного времени: длительность минус время, покрытое детьми (параллельные дети считаются
по объединению интервалов, а не по сумме).

## Метрики: числа во времени

Лог одного заказа не ответит, как идут дела в целом. Метрики это числа, которые сервис держит в памяти, а система сбора (Prometheus) раз в
15 секунд приходит на `/metrics` и записывает. Три вида:

- **счётчик** (counter): только растёт (заказов принято). Интересна не величина, а скорость роста; при перезапуске он обнуляется, и Prometheus это знает;
- **gauge**: растёт и падает (заказов в работе, размер очереди). Интересна сама величина;
- **гистограмма**: распределение (сколько ответов уложилось в 0.1 с, в 0.5 с, в 1 с).

Формат текстовый и простой:

```
# HELP orders_accepted_total Принятые заказы
# TYPE orders_accepted_total counter
orders_accepted_total{channel="app"} 1840
orders_accepted_total{channel="phone"} 212
```

Счётчики и gauge это атомарные числа: увеличить без замка и без потерь можно из любого потока. Имя метрики состоит из букв, цифр, `_` и
`:` и не начинается с цифры; в тексте HELP экранируют перевод строки и обратную черту.

### Метки и кардинальность

`{channel="app"}` это **метка**. Каждая комбинация значений меток создаёт отдельный ряд во времени, и все ряды хранятся в памяти. Если в метку
попадает значение, которое выбирает клиент (путь `/orders/4812`, номер заказа, адрес клиента), рядов становится столько же, сколько клиентов, и
система сбора задыхается. Это называется **взрывом кардинальности**, и это самая частая авария в метриках. Правило: в метки идёт только то, что
сервис перечислил сам заранее (шаблон маршрута `/orders/:id`, а не путь; известные методы; код ответа; тип заказа). Чужое сворачивается в одно
значение («unmatched»). «Кто именно» живёт в логах и трейсах: они дешёвые по ряду, метрики нет.

### Гистограмма и перцентили

Среднее время ответа врёт: девяносто девять заказов по 100 мс и один на 10 секунд дают среднее 200 мс, а клиент ждал десять секунд. Поэтому смотрят
на **перцентили**: p99 это время, быстрее которого отвечают 99% запросов. Хранить все значения нельзя, и гистограмма хранит только счёт по
корзинам-бакетам. Бакеты **накопительные**: строка `le="0.5"` («меньше или равно») считает все наблюдения до 0.5 включительно, и последняя
`le="+Inf"` равна общему числу.

```
orders_seconds_bucket{le="0.1"}  700        700 заказов не дольше 0.1 с
orders_seconds_bucket{le="0.5"}  985        ещё 285 от 0.1 до 0.5 с
orders_seconds_bucket{le="1"}    998
orders_seconds_bucket{le="+Inf"} 1000
orders_seconds_sum   142.7                  сумма всех значений
orders_seconds_count 1000                   число наблюдений
```

Перцентиль оценивается интерполяцией внутри бакета: p99 это 990-е из 1000, оно лежит в бакете между 0.5 и 1, и Prometheus считает его по
пропорции. Результат точен ровно настолько, насколько мелки бакеты. Отсюда три правила. Границы должны покрывать реальный диапазон (всё, что
выше последней границы, превращается в «больше потолка», и перцентиль упирается в него). Шаг растёт в разах, а не на штуки: 1 мс, 2.5 мс, 5 мс,
10 мс и так до 10 с. Бакетов не слишком много: каждый стоит отдельного ряда. Время измеряют в **секундах** с дробной частью и называют метрику
`..._seconds`: это общее соглашение, на котором построены чужие дашборды.

## RED, SLO и бюджет ошибок

Что мерить у сервиса, чтобы не утонуть? Три вопроса к каждому маршруту, метод **RED**: Rate (сколько запросов в секунду), Errors (сколько из них
ошибок) и Duration (сколько они длятся). Реализуют их один раз, обёрткой вокруг любого обработчика, а не копипастой. Три тонкости: учёт
должен срабатывать при любом исходе (успех, ошибка, ранний `?`), «запросов в работе» уменьшается через `Drop`, чтобы отмена клиентом не оставила
его навсегда выше нуля, а ошибками сервера считаются коды от 500 (404 это ошибка клиента).

Метрики становятся управляемыми, когда есть обещание. **SLO**: «99.9% запросов отвечают без ошибки за 30 дней». Обратная сторона это **бюджет
ошибок**: можно провалить 0.1%, это около 43 минут полного простоя в месяц. Пока бюджет есть, можно выкатывать смелые изменения; кончился, и
надёжность важнее новых функций.

Будить дежурного по каждой ошибке бессмысленно. Будят, когда бюджет сгорает слишком быстро. **Скорость сгорания** (burn rate) это доля плохих
запросов, делённая на разрешённую долю: единица значит «ровно успеем до конца периода», 14.4 значит «2% месячного бюджета за час». Смотрят два
окна сразу (скажем, 5 минут и час): короткое отсекает давно починенное, длинное отсекает случайный всплеск, и будят, когда горят оба.

Тоже частая ловушка: доля быстрых ответов берётся из накопительного бакета, граница которого равна порогу («уложились в 0.3 с»). Порога внутри
бакета нет, гистограмма не хранит значения между границами, и честный ответ тогда «нельзя оценить», а не округление.

## Гигиена логов

Логи читают десятки людей и, часто, сторонние сервисы, их копируют, пересылают и хранят годами. Поэтому:

- **Секреты не пишутся никогда.** Токены, пароли, заголовки `Authorization` и `Cookie`, параметры `?token=` в адресе. Надёжнее список секретных имён, которые скрываются (значение заменяется на `[redacted]`, имя остаётся, чтобы было видно, что параметр был), чем список безопасных: новое поле, добавленное через год, иначе утечёт. Имя сравнивают после раскодирования процентной записи и без учёта регистра, иначе `%74oken` его обойдёт.
- **Чужие данные не доверяются.** Перевод строки в имени, заголовке или тексте превращается в поддельную запись («log forging»), а кавычка рвёт JSON. Всё, что пришло от клиента, печатается с экранированием; в JSON строки формируют структурой, а не склейкой.
- **Тексты пользователей в логи не пишутся.** Там бывает всё: пароли, адреса, чужие тайны. Пишут длину, идентификатор, тип.
- **Один вызов одно событие.** Десять `debug!` на запрос превращаются в терабайты, которые платят деньги и прячут важное.

## Типичные ошибки

- Данные склеены в текст сообщения вместо полей; в тексте меняются слова от запроса к запросу.
- `span.enter()` держится через `await`: события одного запроса подписаны чужим номером.
- `tokio::spawn` без переноса контекста: в запущенной задаче span пропал.
- Опечатка в `RUST_LOG` роняет запуск или молча отключает логи.
- Трейс рвётся на границе транспорта: положили заголовок, но не достали (или наоборот); кладут контекст не того перехода.
- В метку попадает путь, идентификатор или адрес клиента (взрыв кардинальности).
- Гистограмма в миллисекундах вместо секунд, границы не покрывают реальные значения, бакеты не накопительные.
- Учёт стоит после `?`: ошибки и отменённые запросы в метрики не попадают.
- Среднее вместо перцентиля; 404 считаются ошибками сервера.
- Секреты и тексты пользователей в логах; перевод строки из данных клиента.
