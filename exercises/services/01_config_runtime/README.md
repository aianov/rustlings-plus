# Конфиг и жизнь процесса

Пятница, вечер, выкатка. Новая версия сервиса постов поднимается, оркестратор убивает старую, и в этот
момент у пятидесяти пользователей пропадают только что отправленные посты: запрос дошёл, а ответ не
вернулся. Через минуту новая версия падает: в конфиге у `SMTP_PORT` опечатка, и на неё ругнулись только после
того, как сервис успел отнять место у предыдущей копии. Откатили, и тут база на пару секунд пропала: все
экземпляры перезапустились по кругу и ещё десять минут не могли подняться.

Ничего из этого не про бизнес-логику. Это жизнь процесса: как он узнаёт настройки, как просыпается,
как отвечает «я готов», как засыпает и что делает, когда падает его часть. Сервис живёт днями, и
если эти вещи сделаны плохо, никакие красивые слои не спасут. Основа, которую получит каждый сервис курса, называется
крейт `service-runtime`, и мы его соберём.

## Конфиг: откуда берутся настройки

Сервис получает настройки из переменных окружения. Так принято: оркестратор (Docker, Kubernetes) умеет
задавать их без пересборки образа, и они не лежат в репозитории.

```rust
let host = std::env::var("SMTP_HOST")?;
```

`env::var` возвращает `Result<String, VarError>`, и у `VarError` два лица:

```
   NotPresent        переменной нет            лечится: задать значение
   NotUnicode(os)    в ней байты не из UTF-8   лечится: чинить кодировку у того, кто задаёт
```

Сообщения для них нужны разные, и оба должны называть переменную. Третий случай, который сам `env::var` не
различает: переменная есть, но пустая (`SMTP_HOST=`). Обычно это забытая подстановка в шаблоне.

### Типизированный разбор

Окружение отдаёт строки, а сервису нужны число, длительность, флаг. Разбор работает так:

```
   нет переменной        берём значение по умолчанию
   есть и разобралась    берём
   есть, но не разобралась   ОШИБКА, а не молчаливое умолчание
```

Последняя строка самая важная. Если `SMTP_PORT=smtp` молча превращается в 25, опечатку найдут через месяц, когда
письма перестанут уходить. Ошибка называет переменную, значение и то, что ожидалось:
`SMTP_PORT: значение "smtp" не подходит, ожидается порт 1..=65535`.

### Источник значений параметром

```rust
impl MailConfig {
    pub fn from_source(get: impl Fn(&str) -> Option<String>) -> Result<MailConfig, ConfigError> { ... }
    pub fn from_env() -> Result<MailConfig, ConfigError> {
        MailConfig::from_source(|name| std::env::var(name).ok())
    }
}
```

Конфиг не знает, откуда значения. В проде источник это окружение процесса, в тесте обычный `HashMap`.
Это не вопрос вкуса. Окружение одно на весь процесс, а тесты Cargo идут параллельно потоками одного
процесса. Если тест А ставит `SMTP_HOST=a.example`, а тест Б в то же время читает `SMTP_HOST`, они увидят друг друга. В
Rust 2024 даже `std::env::set_var` помечен `unsafe`, именно потому, что менять окружение при работающих потоках
нельзя безопасно.

Самая коварная версия беды: `env::var` прячется глубоко внутри вспомогательной функции («да мне всего
один флаг прочитать»). Источник её обходит, и тест, который подал значение через `HashMap`, видит
умолчание. Правило: окружение читается ровно в одном месте, при сборке конфига. Дальше значения передаются
аргументами.

### Все ошибки сразу

```
   $ ./mailer
   ошибка: SMTP_PORT: неверное значение "smtp"
   $ SMTP_PORT=25 ./mailer
   ошибка: RENDER_THREADS: неверное значение "-3"
   $ SMTP_PORT=25 RENDER_THREADS=4 ./mailer
   ошибка: SMTP_HOST не задана
```

Каждый запуск у некоторых систем стоит минуты (контейнер, очередь деплоя). Хороший сервис при старте
вычисляет все поля, собирает ошибки в `Vec` и показывает их одним списком. Для этого не ставь `?` на каждое
поле: посчитай все результаты, потом смотри, все ли `Ok`.

### Файл .env и слои

Локально удобно держать настройки в файле `.env`, а не экспортировать десять переменных. Формат прост, но
с подвохами:

```
   # комментарий
   SMTP_PORT=2525
   export SMTP_HOST = localhost
   SEARCH_URL=http://s:9200/idx?refresh=true&x=1             знак = внутри значения
   SIGNATURE="С уважением # отдел писем"                    кавычки защищают пробел и решётку
   SENDER=robot # а это хвостовой комментарий
```

Делим строку по ПЕРВОМУ `=`: всё, что после него, это значение, включая другие `=`. Если значение начинается и
заканчивается кавычкой, его внутренность берётся как есть. Без кавычек пробел и решётка начинают
хвостовой комментарий.

И порядок слоёв: сначала настоящее окружение, потом файл, потом умолчания.

```
   source(name) = окружение(name)  или  файл(name)  или  умолчание
```

Почему окружение выше файла? На проде переменные задаёт тот, кто запустил процесс. Если в образ случайно попал
`.env` с локальными настройками, он не должен перебить то, что оркестратор сказал прямо сейчас.

### Секреты

Ключ почтового API живёт в конфиге, а конфиг при старте печатают в лог через `{:?}`. Логи читает много народу,
и так секреты утекают чаще всего. Лечение типом:

```rust
pub struct Secret<T>(T);

impl<T> Secret<T> {
    pub fn expose(&self) -> &T { &self.0 }
}

impl<T> fmt::Debug for Secret<T> { ... "Secret(***)" ... }
impl<T> fmt::Display for Secret<T> { ... "***" ... }
```

Теперь `#[derive(Debug)]` на конфиге безопасен: ключ выводится как `Secret(***)`. Достать значение можно
только явным `.expose()`, и по этому слову секреты легко найти поиском по коду. Дисциплина «никогда не пиши
`info!("{config:?}")`» работает до первого уставшего разработчика, а тип работает всегда.

## Сигналы

Оркестратор останавливает сервис сигналом `SIGTERM`, разработчик в терминале жмёт Ctrl+C и шлёт `SIGINT`.
Реагировать нужно на оба одинаково.

```rust
let mut term = signal(SignalKind::terminate())?;
let mut int = signal(SignalKind::interrupt())?;
tokio::select! {
    _ = term.recv() => ...,
    _ = int.recv() => ...,
}
```

Важная деталь: подписка происходит в момент вызова `signal(...)`, а не при первом `recv()`. Если подписаться
позже, чем сигнал придёт, процесс умрёт от него по умолчанию, и «плавной остановки» не будет. Поэтому
`ShutdownListener::new()` вызывают в самом начале `main`.

## Плавная остановка

Сигнал пришёл. Что делать? Простое «выйти» теряет запросы, которые обрабатываются прямо сейчас (скажем, генерацию отчёта на двадцать секунд). Правильный
порядок такой:

```
   время ──────────────────────────────────────────────────────────────▶

   SIGTERM
     │
     ▼
   [1] ready = false         балансировщик на следующей проверке перестаёт слать трафик
     │
     │  grace (пауза)        он ещё не заметил, запросы ещё приходят: принимаем
     ▼
   [2] accepting = false     перестаём принимать новые подключения
     │
     │  дренаж               ждём запросы, которые уже в работе, но не дольше дедлайна
     ▼
   [3] фон остановлен        вспомогательные задачи нужны обработчикам, пока те работают
     │
     ▼
   выход
```

Почему именно так. Снять готовность нужно первым: до тех пор балансировщик продолжает слать запросы. Но
он узнаёт об этом не мгновенно (проба раз в несколько секунд), поэтому после снятия готовности выдерживаем
паузу `grace` и всё ещё принимаем. Потом закрываем приём: теперь число запросов в работе только убывает,
и «дождаться их» имеет конец. Ждём с дедлайном, потому что один зависший запрос не должен держать процесс
вечно: оркестратор всё равно убьёт его через `terminationGracePeriodSeconds` (срок на остановку у оркестратора) без разговоров. Фон (рассылка, кэш,
метрики) останавливаем последним: обработчики дренируемых запросов часто на него опираются.

Типичная ошибка: цикл приёма вышел по команде остановки, `main` вернулся, и рантайм молча уничтожил все
задачи, которые ещё обрабатывали запросы.

```rust
loop {
    select! {
        _ = stop.changed() => break,
        Some(order) = orders.recv() => { tokio::spawn(render(order)); }   // эти задачи никто не ждёт
    }
}
// здесь main возвращается, и задачи убиты
```

Починка: складывать задачи в `JoinSet` и после цикла дождаться их: `while set.join_next().await.is_some() {}`.

В коде `in_flight` считается счётчиком, а запрос держит охранника (`RequestGuard`), который вычитает единицу
в `Drop`. Так счётчик не забудет уменьшиться ни при раннем `return`, ни при панике.

## live и ready

Оркестратор задаёт сервису два разных вопроса.

```
   live    «ты жив?»        нет  ->  процесс убивают и запускают заново
   ready   «ты готов?»      нет  ->  трафик на него не шлют, но процесс живёт
```

Живость отвечает за зависание процесса: дедлок, бесконечный цикл. Готовность отвечает за то, может ли
экземпляр сейчас делать полезную работу: доступна ли база, без которой работать нельзя, не идёт ли остановка.

Зависимости бывают обязательные и необязательные. Без обязательной (основная база) работать нельзя: она
входит в `ready`. Без необязательной (кэш) сервис работает, только медленнее: её недоступность видна в
метриках и логах, а в `ready` её нет, иначе снятие трафика со всех экземпляров превратит замедление в отказ.

Теперь сценарий, который портит жизнь чаще всего. Кто-то решил, что `/health` должен проверять брокера сообщений «для
надёжности». Брокер упал на десять секунд.

```
   брокер упал
      │
      ▼
   все экземпляры отвечают на /health плохо
      │
      ▼
   оркестратор убивает ВСЕ экземпляры
      │
      ▼
   они стартуют, не видят брокер, снова плохо...   цикл смерти
      │
      ▼
   брокер вернулся, и на него одновременно бросаются все подключения заново
```

Перезапуск процесса не лечит чужой брокер. Поэтому зависимости входят только в `ready`: оркестратор
перестаёт слать трафик, а процесс спокойно ждёт. В `live` нет ни базы, ни кэша, ни других сервисов, и он не
ходит ни к каким проверкам: зависшая зависимость не должна подвесить даже ответ про живость.

Проверки готовности запускай одновременно (`join_all`), каждую со своим лимитом времени: три проверки по
400 мс подряд это 1200 мс, а оркестратор ждёт ответ около секунды. Зависшая проверка это провал с причиной
`timeout`, а не зависший `/ready`. А при остановке `ready` всегда отвечает «не готов», что бы ни говорили
зависимости (это первый шаг плавной остановки).

## Старт с ожиданием зависимостей

Оркестратор поднимает всё вперемешку, и сервис может стартовать раньше своей базы. Падать сразу нельзя: он
поднялся бы по кругу. Ждать вечно тоже нельзя.

```
   попытка, пауза interval, попытка, пауза, ...  пока не прошёл общий дедлайн total
```

Правила хорошего ожидания:

- попытки с паузой, а не плотным циклом;
- дедлайн общий на всё ожидание (на все зависимости вместе, а не по минуте на каждую);
- при провале сообщение называет, чего не дождались и какая была последняя ошибка;
- кривой конфиг не лечится ожиданием: он проверяется первым и падает сразу, без единой попытки.

Состояние «запускаюсь» без конца хуже падения. Оркестратор терпеливо ждёт, алерты молчат, причина зарыта
в логах. Упавший с понятной причиной сервис можно перезапустить автоматически и показать в мониторинге.

Время в тестах таких задач заморожено (`#[tokio::test(start_paused = true)]`): `sleep` не ждёт на самом
деле, виртуальные часы перепрыгивают вперёд, когда все задачи заснули. Поэтому число попыток и длительность
паузы можно проверять точно.

## Супервизор фоновых задач

В сервисе живут фоновые задачи: пересчёт ленты, отправка писем, очистка. Что делать, когда одна падает?

```
   задача упала  ->  пауза  ->  запустить снова  ->  ... до max_restarts
                                                         │
                                  некритичная ───────────┤ осталась выключенной, процесс живёт
                                  критичная   ───────────┘ процесс падает целиком
```

Критичная задача это та, без которой сервис врёт или бесполезен (индексатор, из которого читает поиск).
Пусть лучше упадёт процесс, и оркестратор поднимет его заново, чем он тихо отдаёт устаревшие данные.

Две ловушки. Первая: паника в `tokio::spawn` не роняет программу, она превращается в `JoinError` у того,
кто держит `JoinHandle`. Если результат выбросить (`while set.join_next().await.is_some() {}`), задача умрёт
молча, а сервис продолжит жить без неё. Результат ожидания надо разбирать. Вторая ловушка: если
надзирателя остановили, а саму задачу запустили отдельным `tokio::spawn`, она продолжит работать брошенной.
Поэтому панику удобнее ловить внутри цикла надзирателя (`FutureExt::catch_unwind`): тогда отмена
надзирателя отменяет и задачу.

## Типичные ошибки

- `env::var` в глубине кода: тесты начинают зависеть от окружения процесса.
- Молчаливое умолчание при кривом значении переменной.
- Конфиг сообщает о первой ошибке, а не обо всех.
- Секрет напечатан через `{:?}` конфига.
- Подписка на сигналы позже, чем нужно.
- `main` возвращается, пока запросы ещё в работе.
- Остановка фоновых задач раньше, чем закончились запросы.
- Зависимости в `live`: цикл смерти.
- Ожидание зависимости без дедлайна.
- Результат `join_next()` выброшен: паника в задаче прошла молча.
