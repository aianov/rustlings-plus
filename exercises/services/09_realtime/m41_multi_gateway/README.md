# Веха 41. Несколько шлюзов

Одного шлюза соцсети стало мало, рядом поднят второй. И сразу всё поехало. Телефон alice сидит на первом шлюзе, планшет на втором, а сообщение приходит только туда, где был отправитель: поток Subscribe из chat-service открывает каждый шлюз сам, и порядка в этом нет. «В сети» никто не видит: таблица соединений у каждого шлюза своя. Alice нажала «выйти» на телефоне, а планшет на другом шлюзе продолжает получать сообщения. Телефон alice проехал тоннель, вернулся, и всё, что пришло за это время, пропало: живой поток ничего не хранит.

Эта веха делает доставку общей для всех шлюзов. Сообщения чата идут через JetStream: chat-service пишет их через outbox в stream чата, а stream сам повторяет каждое записанное сообщение в живую тему получателя с его номером. Шлюз подписывается на тему пользователя, когда у него появилось первое устройство этого пользователя, и снимает подписку с последним. Присутствие лежит в KV со сроком жизни: пока соединение открыто, шлюз шлёт за него сигнал. Вернувшийся клиент называет номер последнего увиденного сообщения, и шлюз досылает пропущенное без дыр и повторов. Отзыв сессии auth-service объявляет всем шлюзам. «Печатает…» идёт обычной публикацией и нигде не хранится.

Всё собирается из главы 09_realtime: задачи с svrt1 по svrt10 и проект svrt_quiz, плюс KV из svjs14 и svjs15. Реестр без утечек, подписка по счётчику с кругом до брокера, присутствие по сигналам, порядок «подписка, история, склейка», отзыв на всех шлюзах и разделение эфемерного и надёжного там уже были, здесь они встают в соцсеть на настоящем NATS.

## Что сделать

1. **contracts**:
   - факт `MessageSent { from_id, to_id, text }`, тип `chat.sent`, схема 1, агрегат это получатель: версия считается по его входящим. В `KINDS` теперь десять типов;
   - темы: stream чата `<КОРЕНЬ>_CHAT` (`chat_stream()`) ловит `<корень>.chat.>` (`chat_subjects()`, `chat_all()`), сообщение получателю пишется в `<корень>.chat.<получатель>` (`chat(to)`), живая тема `<корень>.live.<пользователь>` (`live(user)`, все сразу `live_all()`), «печатает» `<корень>.typing.<пользователь>` (`typing(user)`), отзывы `<корень>.session.revoked` (`revoked()`), бакет присутствия `<КОРЕНЬ>_PRESENCE` (`presence()`);
   - модуль `realtime/`: `TypingNote { from, to }`, `SessionRevoked { user, sessions }`, `OnlineView { user, online }`, `MAX_REVOKED` (1000), `REALTIME_METHODS` (`chat.typing` и `users.online`, как `LIVE_METHODS` для живой ленты);
   - `Push::Message { to, from, seq, text }`: в пуше теперь текст и номер сообщения в stream чата; новый `Push::Typing { to, from }`. `Push` больше не `Copy`.

2. **nats-engine**, модуль `js/`:
   - `StreamSpec::republish(from, to)`: stream повторяет каждое записанное сообщение из `from` в `to` (подстановка `>` переносит хвост темы), `ensure_stream` сверяет и темы, и повтор;
   - `live.rs`: `live::<T>(&bus, &subject) -> Live<T>`, подписка с кругом до брокера; `next()` отдаёт `Stored { sequence, item }`, номер берётся из заголовка `Nats-Sequence` (константа `async_nats::header::NATS_SEQUENCE`: по строке async-nats его не найдёт); без номера это ошибка разбора; `stop()` отписывается и ждёт брокер;
   - `history.rs`: `history::<T>(&bus, stream, &subject, after, limit) -> Vec<Stored<T>>`: временный читатель с номера `after + 1` по теме, без подтверждений, читает не больше `limit` из того, что было в stream на момент создания, и удаляется после запроса;
   - `kv.rs`: `open_bucket(&bus, name, ttl) -> Bucket` (берёт существующий бакет или заводит новый со сроком жизни записи `ttl` и историей 1), `touch(key)`, `forget(key)`, `alive(prefix) -> usize`: сколько ключей `<prefix>.*` сейчас живы (последняя запись не удаление), читатель тоже временный.

3. **chat-service**:
   - журнал: строка `Line::Sent { from, to, text, outbox }` (старые строки без outbox читаются) или `Line::Published { published }`. Сообщение и его событие `chat.sent` пишутся одной строкой, как посты в m40; `MemoryChats` реализует `OutboxRepository`;
   - `client/relay.rs`: релей как в m40, но в тему получателя `topics.chat(агрегат)` и в stream чата с повтором `<корень>.chat.>` в `<корень>.live.>`;
   - `Typing`: новый RPC в `chat.proto` (`TypingRequest { peer_id }`, `TypingReply { sent }`), `Subscribe` и `SubscribeRequest` удалены. Сервис проверяет собеседника (себе нельзя, несуществующему нельзя) и пропускает не чаще раза в `TYPING_PACE` (3 с) на пару «кто, кому»; повтор раньше срока это `sent = false`. Порт `Typist`, адаптер `client/typing.rs` публикует `TypingNote` обычной публикацией в `typing(to)`. Без NATS `Offline`: «печатает» не доставить, это `unavailable`;
   - конфиг: `NATS_URL` и `EVENTS_ROOT`, как у user-service. Хаба и `ChatError::Closing` больше нет.

4. **auth-service**:
   - в токене поле `sid`: сессия это один вход и все его обновления по refresh. `ValidateToken` отдаёт её в `Account.session`, `Principal.session`;
   - порт `Revoker` (в `service/exits.rs`, без брокера `Unheard`), адаптер `client/revoker.rs` публикует `SessionRevoked` в `revoked()`. Объявляют выход (`logout`), выход везде (`logout-all`, все сессии одним сообщением), смена и сброс пароля, повтор старого refresh. Не дошло, только запись в лог: соединения закроются по сроку токена;
   - `revoke_user` возвращает закрытые сессии, а не их число; у хранилища сессий есть `row(refresh_hash)`.

5. **api-gateway**:
   - `controller/presence.rs` (`Realtime`), рядом `subs.rs` и `revoked.rs`. `Realtime::start` заводит stream чата и бакет присутствия, подписывается на отзывы и запускает сигналы. `join(principal, outbox, after)` под одной асинхронной блокировкой поднимает счётчик подписок пользователя: первое устройство на шлюзе открывает живую тему `live(user)` и `typing(user)` с кругом до брокера, следующие только увеличивают счёт. Последнее устройство снимает обе подписки и ждёт, пока брокер их отпустит. Устройство в KV это ключ `<пользователь>.<шлюз>-<соединение>`, имя шлюза `fresh_id("gw")`: номера соединений у шлюзов совпадают, а ключи нет. Сигнал за каждое открытое соединение идёт раз в треть срока (`GATEWAY_PRESENCE_TTL_MS`, 30 с; меньше 300 мс отвергается), закрытие убирает только своё устройство, упавший шлюз просто перестаёт слать сигналы;
   - догон: `?after=<номер>` при открытии WebSocket. Устройство сначала встаёт в реестр с курсором и копит живые сообщения, потом шлюз читает историю страницами по `CATCH_UP_PAGE` (100) и шлёт её с ожиданием места в очереди, потом отдаёт накопленное. Всё по возрастанию номера, номер не больше уже отданного не шлётся;
   - реестр (`common/registry.rs`, очередь в `common/outbox.rs`): у соединения есть сессия; отправка убирает соединения с закрытым каналом и пустых пользователей; `revoke(sessions)` закрывает соединения кодом 4003 (`REVOKED`). Отзыв помнится, не больше `MAX_REVOKED`: отозванная сессия получает 401 при открытии WebSocket на любом шлюзе;
   - маршруты `users.online { target } -> OnlineView` и `chat.typing { peer } -> Changed`; без NATS «в сети» отвечает `unavailable`;
   - `client/inbox.rs` удалён.

6. **Окружение**: `GATEWAY_PRESENCE_TTL_MS` в `.env.example` и `.env`; в `Makefile.toml` задача `api-gateway-2` (`127.0.0.1:7890`, admin `127.0.0.1:9890`), второй шлюз в `run-all` и `demo`.

Клиент курса (`tools/social-cli`) приходит готовым: печатает сообщение из пуша с текстом, показывает «печатает…», помнит номер последнего сообщения и при новом входе открывает WebSocket с `after`, знает команды `typing <ник>` и `online <ник>` и код закрытия 4003.

## Приёмка

Тестам нужен NATS курса с JetStream на `127.0.0.1:54222` (адрес из `RUSTLINGS_NATS_URL`).

- `contracts/tests/journey/m41_multi_gateway.rs`: формы тем и бакета; `chat.sent` это факт о получателе; пуши сообщения и «печатает», отзыв и «в сети» на проводе.
- `nats-engine/tests/journey/m41_multi_gateway.rs`: записанное повторяется в живую тему один раз и с номером, дубль по `Nats-Msg-Id` не повторяется; история только своя, строго после номера, по страницам, без лишних читателей; ключ живёт, пока его обновляют, и истекает без сигналов.
- `chat-service/tests/journey/m41_multi_gateway.rs`: сообщение и событие одной строкой журнала доходят до живой темы получателя с номером, релей отмечает отправленное; «печатает» уходит один раз за 3 секунды на пару, проверяет собеседника и в stream не пишется.
- `auth-service/tests/journey/m41_multi_gateway.rs`: у каждого входа своя сессия, refresh её сохраняет; выход, повтор refresh и выход везде объявляют закрытые сессии; отзыв доходит через брокер.
- `api-gateway/tests/journey/m41_multi_gateway.rs` (два шлюза на одном стенде): сообщение приходит на все устройства на всех шлюзах ровно один раз и с одним номером; подписка на шлюзе одна на пользователя и пропадает с последним устройством (брокер отвечает no responders); «печатает» доходит через другой шлюз, второе за 3 секунды не уходит, в stream ничего не пишется; «в сети», пока жив хоть один шлюз с устройством, и дольше срока записи; вернувшееся устройство догоняет по порядку и без повторов, в том числе сообщение, отправленное во время догона, а новое с `after=0` получает всю переписку; выход закрывает сессию на обоих шлюзах кодом 4003, вторая сессия живёт, выход везде закрывает и её; клиенты курса на разных шлюзах переписываются, видят «печатает…» и «в сети».
- новые версии тестов прошлых вех: m13 и m15 contracts (новая форма `Push::Message`, `Push` без `Copy`), m31 proto (`TypingRequest` вместо `SubscribeRequest`), m31 и m33 chat-service (потока Subscribe и хаба нет, сообщение ложится в outbox), m36 auth-service (`sid` в `Claims`), шлюз: `fakes.rs` (фейковый chat считает «печатает», у `Account` есть сессия), `support.rs` (chat-service и auth-service с NATS, второй шлюз `twin`, вход с `after`, очистка stream чата и бакета присутствия, `plain` и `letter` для сравнения сообщений без номера), m24, m29, m30, m31, m38 и m39 (сообщение с текстом, в таблице маршрутов `REALTIME_METHODS`; тест подписки через поток Subscribe ушёл в m41), m36 (обновление токена: access живёт 3 секунды, а не одну: срок в токене в целых секундах, и обновлённый токен под нагрузкой не доживал до «logout all»; при таймауте тест печатает экран клиента).
- тесты прошлых вех проходят, `cargo make check` зелёный.

Архитектура: файлы по дереву; в `chat.proto` нет `rpc Subscribe`, есть `rpc Typing`; stream чата с `republish`, номер из `NATS_SEQUENCE`, история с `ByStartSequence` и `delete_consumer`, присутствие с `max_age` и `LastPerSubject`; в шлюзе счётчик подписок, закрытие подписки с ожиданием, имя шлюза из `fresh_id("gw")`, сигнал раз в треть срока, курсор номеров, код 4003, `is_revoked` при открытии; релей чата пишет в `topics.chat(..)`, «печатает» обычной публикацией и не через `publish_event`; в токене `sid`; в `cargo make demo` два шлюза; и все договорённости прошлых вех.

## Как запустить

NATS курса должен работать: `127.0.0.1:54222`.

```
cd backend
cargo make check
cargo make demo
```

`cargo make demo` поднимает два шлюза: `127.0.0.1:7880` и `127.0.0.1:7890`, клиент открывается на первом. Это alice: `register alice correct-horse`, `login alice correct-horse`. Во втором окне клиент на втором шлюзе: `cargo run -p social-cli -- --addr 127.0.0.1:7890 --admin 127.0.0.1:9890`. Это bob: `register bob correct-horse`, `login bob correct-horse`, `online alice` (в сети), `typing alice` (у alice «* @bob печатает…»), `msg alice привет`. Alice на другом шлюзе видит «* @bob: привет». Теперь останови второй шлюз (`lsof -ti tcp:7890 | xargs kill`): клиент bob скажет, что соединение оборвалось. Пусть alice напишет `msg bob где ты?` и `msg bob ау`. Подними второй шлюз снова (`GATEWAY_HTTP_ADDR=127.0.0.1:7890 GATEWAY_ADMIN_ADDR=127.0.0.1:9890 cargo run -p api-gateway`), и bob входит заново: `login bob correct-horse`. Клиент скажет «догоняю сообщения после №…», и оба пропущенных сообщения придут по порядку.
