# DTO и свой валидатор

Интернет-магазин принимает заказ. Клиент присылает JSON, и однажды в нём приходит вот что:

```json
{"items":[{"sku":"A-1","qty":-3}], "promo":"<пять тысяч символов>", "address":{"zip":"  "},
 "total":0, "status":"paid"}
```

Количество отрицательное, промокод размером с главу книги, индекс из пробелов, а в конце клиент сам
записал себе `total: 0` и `status: "paid"`. Если сервер разобрал это в структуру `Order` и положил в базу,
заказ на минус три штуки оплачен и стоит ноль рублей. Ничего из этого не про «злых хакеров»: так ведут себя
обычные кривые клиенты, устаревшие версии приложений и опечатки.

Правило простое: **на границе системы никому не верим**. Всё, что пришло снаружи (HTTP, gRPC, очередь),
проходит через одно узкое место, где данные разбираются, приводятся к нормальному виду и проверяются. Внутрь
сервиса попадает только то, что прошло проверку.

## Конвейер

```
   байты из сети
       │  serde разбирает в форму
       ▼
   DTO                     то, что пришло: строки, числа, Option, всё сырое
       │  нормализация     trim, регистр, невидимые символы
       ▼
   нормальный вид
       │  правила          длина, диапазон, формат, размер списков
       ▼
   доменный тип            Username, Email, Quantity: уже проверены, повторно не проверяются
   или список ошибок       по каждому полю: путь, машинный код, сообщение
```

Каждая ступень отвечает за своё. Serde проверяет «это вообще JSON с такими полями и типами». Правила отвечают на
вопрос «разумное ли это значение». Домен ничего не проверяет повторно: он получает уже проверенные типы.

## DTO и атрибуты serde

DTO это структура, которая описывает внешний формат. Она живёт на границе (в `dto/`) и отличается от доменной:
у неё свои имена полей, и она готова принять любую ерунду, лишь бы она была похожа на форму.

```rust
#[derive(Deserialize)]
#[serde(rename_all = "camelCase")]
struct CheckoutDto {
    promo_code: Option<String>,       // можно не присылать
    gift_wrap: bool,                  // а вот это обязательное
    #[serde(default)]
    notify_by_sms: bool,              // не прислали: false
}
```

- `rename_all = "camelCase"` разводит стиль клиента (`promoCode`) и стиль Rust (`promo_code`).
- `Option<T>` значит «можно не присылать». `#[serde(default)]` подставляет `Default` для отсутствующего поля.
- Неверный тип (число строкой) это ошибка разбора. Serde не превращает `"5"` в 5 молча: это защита от клиентов, которые
  путают форматы.

### Лишние поля

Что делать с полем, которого в DTO нет? Два ответа, и оба правильные в своём месте.

```rust
#[derive(Deserialize)]
#[serde(deny_unknown_fields)]          // строго: лишнее поле это ошибка
struct ChangePasswordDto { old: String, new: String }

#[derive(Deserialize)]                 // терпимо: лишнее игнорируется
struct CatalogQueryDto { text: String }
```

Строгий разбор подходит там, где обе стороны договорились о каждом поле: лишнее тут либо опечатка, либо попытка
протащить своё. Терпимый нужен там, где формат живёт по чужому расписанию (параметры поиска, которые клиенты
дополняют аналитикой; события внешнего провайдера): падать на новом поле значит ломать клиентов при каждом релизе.

### Mass assignment

В примере заказа клиент записал себе `total` и `status`. Это называется mass assignment: разбор тела в доменную
структуру делает доступным клиенту каждое её поле. Защита одна: входной DTO описывает **только то, что клиенту
разрешено менять**, а доменная структура с `total` и `status` отдельный тип. Прислал лишнее поле, получил ошибку, а не
молчаливое игнорирование: молчание прячет и опечатки клиента, и попытки взлома. Связка с прошлым разделом одна: для DTO
своих клиентов строго, для чужих событий, формат которых растёт без твоего участия, терпимо.

## Валидатор: собирать все ошибки

Форма с пятью ошибками, которая показывает по одной за отправку, раздражает сильнее любой из них. Поэтому валидатор
не прерывается: каждая проверка независима, добавляет запись и идёт дальше, а решение «прошло или нет» принимается в
конце.

```rust
struct FieldError { path: String, code: &'static str, message: String }

fn validate(&self) -> Result<(), Vec<FieldError>> {
    let mut errors = Vec::new();
    if /* проверка 1 */ { errors.push(...); }
    if /* проверка 2 */ { errors.push(...); }
    if errors.is_empty() { Ok(()) } else { Err(errors) }
}
```

У ошибки три части, и у каждой своя читательница. **path** (`address.zip`) нужен клиенту, чтобы подсветить поле.
**code** (`too_short`) нужен клиентскому коду: по нему переводят на нужный язык и выбирают реакцию, и он не меняется,
сколько бы ни переписывали текст. **message** для человека, который читает лог.

Правила удобно делать значениями, а не макросами: структура `CharLen { min, max }` с общим трейтом `Rule<T>`
легко хранить, комбинировать и проверять по отдельности. А валидатор прогоняет правила поля по порядку и записывает
ошибку только от первого сработавшего: если значение пустое, незачем ещё и жаловаться на формат.

## Длина: символы, а не байты

```rust
"привет".len()            // 12: это байты
"привет".chars().count()  // 6:  это символы
"👍".chars().count()      // 1,  а len() это 4
```

Человек считает видимые символы, поэтому лимит считается по `chars()`. Пробелы по краям обрезаются **до** подсчёта:
иначе «  ab  » пройдёт как шесть символов. Обратная сторона той же монеты: срез `&s[..10]` берёт байты и
паникует, если граница попала внутрь символа, и паника в обработчике это отказ в обслуживании. Префикс берут
итератором: `s.chars().take(10).collect::<String>()`.

Договорённость курса: считаем скалярные значения Unicode (`char`). Буква с диакритикой, записанная как две части,
считается за две. Настоящие графемы требуют таблиц Unicode, и для лимита поля это обычно не нужно.

## Диапазоны и размеры

Ограничения нужны не для красоты, а для защиты. Без предела на `limit` один запрос положит базу, без предела на число
тегов один запрос съест память, без предела на глубину вложенности стек. Для каждого числа и каждого списка в DTO
должен быть явный предел. Умолчания применяют первыми (`limit.unwrap_or(20)`), и проверяют уже итоговое значение.

## Форматы руками

Ник это просто: `[a-z0-9_]`, длина, первая буква. С почтой хуже: настоящий формат (RFC) чудовищен, и всё равно
не говорит, существует ли ящик. Это знает только письмо с подтверждением. Поэтому проверяем «похоже на адрес»: один `@`,
непустая локальная часть, домен из непустых меток через точку, меток не меньше двух. Строже не нужно: `a+tag@mail.example.co` настоящий
адрес, и отказывать пользователю из-за плюса значит терять пользователя.

## Мини-шаблон

Правила вида «ник это буква, потом от 2 до 19 букв, цифр или подчёркиваний» удобнее записывать шаблоном, чем кодом:
`[a-z][a-z0-9_]{2,19}`. Полная регулярка нам не нужна, хватит малого: литералы, `.`, классы `[a-z0-9_]` и `[^ ]`,
экранирование `\.`, повторы `? * + {m} {m,} {m,n}`, совпадение всей строки.

Устройство простое. Шаблон разбирается в список элементов: каждый «что сопоставляем» (символ, любой, класс) плюс
границы повтора `min` и `max`. Сопоставление рекурсивное:

```
   элемент: a*      остаток шаблона: ab        строка: aaab
   жадно берём все 3 «a»  →  остаток «ab» против пустого хвоста: не сошлось
   отдаём одну: берём 2   →  остаток «ab» против «ab»: сошлось
```

Жадный повтор обязан уметь отдавать символы назад, иначе `a*ab` не совпадёт с `aaab`. Это откат, и у отката есть
цена: на шаблоне вроде `a*a*a*a*a*a*a*a*b` и строке из шестидесяти `a` перебор вариантов растёт экспоненциально, и один
запрос занимает минуты. Так устроены атаки ReDoS. Лечится запоминанием: если из состояния «элемент номер i, позиция j»
совпасть не вышло, этот факт кладут в множество и при возвращении туда отвечают «нет» сразу. Состояний
всего (число элементов) × (длина строки), перебор становится полиномиальным.

## Вложенные DTO и пути

Заказ содержит адрес, адрес содержит индекс, в заказе список позиций. Когда клиент получает «слишком длинное»,
ему нужно знать где. Для этого у ошибки путь: `address.zip`, `items[2].sku`, `delivery.slots[1].from`.

```
   путь = префикс + имя поля          для вложенной структуры префикс передают вниз
   путь = префикс + [индекс]          для элемента списка, индекс с нуля
   ошибка самого списка               items            (слишком много позиций)
   ошибка элемента списка             items[1].sku
```

Путь строят рекурсивно из префикса: функция получает префикс родителя и дописывает своё имя, и тот же приём
работает на любую глубину. Порядок ошибок идёт по порядку полей структуры: так их проще читать и сравнивать в тестах.

## Нормализация

«Maria@Mail.RU» и «maria@mail.ru» это один адрес, «Maria» и «maria» один ник. Если привести значение к единому виду
**до** проверок и сохранения, всё остальное (уникальность, длина, формат) становится проще. Нормализуют так:

- ник и почта: `trim` и `to_lowercase` (он понимает Unicode, кириллицу в том числе);
- отображаемое имя: убрать невидимые символы, схлопнуть повторные пробелы (`split_whitespace` и `join(" ")`);
- тег: убрать ведущие `#`, пробелы внутри заменить на `-`, нижний регистр.

Невидимые символы ловушка. Нулевой пробел (`U+200B`) делает «Maria» и «Ma<нулевой пробел>ria» разными строками, которые
выглядят одинаково: так подделывают имена. Проверка того, что нормализация сделана правильно: она идемпотентна,
повторное применение ничего не меняет.

Порядок важен. Сначала нормализация, потом формат, потом уникальность по нормализованному значению, и в хранилище
пишется только нормальный вид. Если проверить уникальность по сырому вводу, «Maria» пройдёт мимо «maria», и ты
получите двойников. А атомарность вставки (прошлая глава) нужна по-прежнему: нормализация не отменяет гонку.

## Parse, don't validate

Строка `String` не говорит, проверена ли она. Каждая функция, принявшая её, вынуждена то ли верить, то ли
проверять заново. Решение: проверка превращается в преобразование типа.

```rust
pub struct Quantity(u32);                    // поле приватное

impl TryFrom<i64> for Quantity {
    type Error = FieldError;
    fn try_from(raw: i64) -> Result<Self, FieldError> {
        if (1..=999).contains(&raw) { Ok(Quantity(raw as u32)) } else { Err(/* ... */) }
    }
}
```

Создать `Quantity` можно только через `try_from`: конструктора без проверки нет, потому что поле приватное. Значит,
всякий код, принявший `Quantity`, точно получил допустимое значение, и перепроверять его не нужно. Если сервис принимает
`Quantity`, а не `i64`, непроверенное значение просто **не скомпилируется**. Проверка внутри сервиса «на всякий
случай» держится на дисциплине (следующий разработчик добавит новый путь и забудет), а тип держится на компиляторе.

## PATCH в три состояния

PATCH меняет часть полей. У каждого поля три состояния, и каждое что-то значит:

```
   поле не прислано      «не трогай»
   прислан null          «очисти» (если поле можно очищать)
   прислано значение     «проверь и поставь»
```

Обычный `Option<T>` различает только два. Хуже того, serde сливает «нет поля» и `null` в `None`: по
`{"note": null}` и `{}` ты получишь одно и то же, и потеряете намерение клиента. Нужно что-то с тремя состояниями.

Всё держится на разделении ролей. serde вызывает `deserialize` **только для присланных** полей: у отсутствующего поля
он не вызывается вообще, и вместо него берётся `Default` (для этого на поле нужен `#[serde(default)]`). А «пришёл `null`»
против «пришло значение» различает `Option` внутри. Классический короткий приём это двойной `Option`:

```rust
fn double_option<'de, T: Deserialize<'de>, D: Deserializer<'de>>(d: D) -> Result<Option<Option<T>>, D::Error> {
    Option::<T>::deserialize(d).map(Some)       // прислали: Some(null или значение)
}

#[serde(default, deserialize_with = "double_option")]
note: Option<Option<String>>,                    // None: нет поля, Some(None): null, Some(Some(x)): значение
```

Он работает, но читается плохо: `Some(None)` ничего не говорит человеку. Поэтому в коде для трёх состояний заводят
свой тип с понятными именами (`Missing`, `Null`, `Value`) и реализуют для него `Deserialize` по той же схеме.

Применяют PATCH на **копии**: `let mut next = current.clone()`, меняют, собирая ошибки, и записывают обратно только
если ошибок нет. Частично применённый PATCH хуже отказа: клиент не знает, что из присланного сработало.

## Ловушки proto3

В gRPC те же вопросы, но у protobuf свои правила. В proto3 у скалярного поля нет состояния «не прислано»:

```proto
message ProductPatch {
  string description = 2;        // "" это «не прислали» или «очисти»? Неразличимо
  uint32 stock = 3;              // 0 это «не прислали» или «товара нет»? Неразличимо
}
```

Решение называется `optional`: `optional string description = 2;`. Тогда prost генерирует `Option<String>`, и «не
прислано» (`None`) отличается от пустой строки (`Some("")`). А `null` в protobuf не бывает, поэтому «очисти» выражают
отдельно, например списком `repeated string clear_fields` с именами очищаемых полей.

Код из `.proto` генерирует `build.rs` (`tonic_prost_build::compile_protos(...)`), а в крейт он подключается макросом
`tonic::include_proto!("имя.пакета")`: там лежат сообщения и трейт сервиса, который реализует контроллер.
Ошибки проверки возвращают как `Status::invalid_argument(...)` с перечнем «поле: код» через `; `: клиент видит не
«неверный запрос», а какое поле исправить. Если профиля нет, это `Status::not_found`. Дальше контроллер делает то
же, что и HTTP: превращает proto в DTO, DTO в домен, а ошибки в статус.

## Типичные ошибки

- Разбор в доменную структуру: клиент получает доступ к любому её полю (mass assignment).
- Остановка на первой ошибке, ошибка без пути и без машинного кода.
- `len()` вместо `chars().count()`, срез строки по байтам, отсутствие пределов на числа и списки.
- Проверка уникальности по сырому вводу, до нормализации.
- Проверка внутри сервиса «на всякий случай» вместо типа, который нельзя создать непроверенным.
