# gRPC-контроллер профиля

Мобильное приложение обновляет профиль через gRPC. Сообщение `UpdateProfileRequest` описано в proto3,
и там есть ловушка: у скалярного поля нет состояния «не прислано». Пустая строка и отсутствие поля
выглядят одинаково (в Rust это `""`), число `0` и отсутствие тоже. Значит, по такому сообщению нельзя
понять, хотел ли клиент оставить био как есть или записать пустое, и PATCH из предыдущих задач
превращается в угадайку. Твоя задача: починить контракт и контроллер так, чтобы три состояния
поля (не прислано, очистить, значение) снова различались.

## Что уже есть

- Воркспейс с пакетом `src/microservices/profile-service`.
- `build.rs`, генерирующий код из `proto/profile.proto`; сгенерированное лежит в `profile_service::pb`.
- Доменный слой `src/domain.rs`: `ProfileService`, `PatchSet` с полями типа `Patch<T>` (`Missing`, `Null`,
  `Value`), проверка значений и ошибки `FieldError { field, code }`. Его менять не нужно.
- Рабочий, но наивный `src/controller.rs`: он считает пустую строку и `0` отсутствием поля.
- Приёмочные тесты `tests/acceptance.rs`. Править их нельзя.

## Что сделать

1. В `proto/profile.proto` сделай так, чтобы присутствие полей `display_name`, `bio`, `birth_year` различалось
   (в proto3 для этого есть ключевое слово `optional`). Поле `repeated string clear_fields = 5` уже есть, не трогай его: в нём
   имена полей (`displayName`, `bio`, `birthYear`), которые клиент хочет очистить.
2. В `src/controller.rs` собери `PatchSet` из запроса:
   - поле прислано: `Patch::Value`, даже если это пустая строка или `0`;
   - имя поля есть в `clear_fields`: `Patch::Null`;
   - ни того ни другого: `Patch::Missing`;
   - и значение, и очистка для одного поля: ошибка `<поле>: conflict`;
   - в `clear_fields` неизвестное имя: ошибка `<имя>: unknown_field`.
3. Ошибки превращаются в `Status::invalid_argument(...)`. Сообщение это перечень `поле: код`, разделённый
   `"; "`, в порядке полей (`displayName`, `bio`, `birthYear`); неизвестные имена из `clear_fields` идут после ошибок полей. Ошибки доменного слоя (`UpdateError::Invalid`)
   перечисляются так же; нет профиля это `Status::not_found`.

## Критерии приёмки

`cargo test --workspace` проходит и `cargo clippy --workspace --all-targets -- -D warnings` чист. Тесты вызывают
контроллер напрямую (без сети) и проверяют: изменяются только присланные поля; пустая строка и `0` это
значения, а не отсутствие; `clear_fields` очищает `bio` и `birthYear`, но не `displayName`; конфликт и
неизвестное поле отклоняются; все ошибки приходят одним статусом; профиль при ошибке не меняется.
