# Аутентификация и права

У приложения для записи в спортзал украли таблицу `members`. В ней лежали почта, телефон и пароли в виде `md5`.
За вечер по словарю вскрыли две трети аккаунтов, а утром выяснилось, что украденные refresh-токены из соседней таблицы
подходят для входа прямо сейчас, потому что лежали там как есть. Пока команда меняла ключ подписи, все 40 тысяч клиентов
вылетели из приложения: старый ключ из конфига выбросили, и ни один выданный токен больше не проверялся.

Ни одна из этих бед не про хитрую криптографию. Это пять скучных решений: как хранить пароль, как подписывать токен,
в каком порядке его проверять, как менять ключ и как отзывать то, что уже выдано. Пройдём их по очереди.

## Где живёт вход

В нашей соцсети вход и регистрация идут только по HTTP, в `auth-service`. Клиент получает токен, дальше ходит с ним на
шлюз, а шлюз и другие сервисы спрашивают у auth по gRPC две вещи: «чей это токен?» (`ValidateToken`) и «расскажи про
аккаунт» (`GetAccount`). Пароли за пределы auth-service не выходят никогда.

```
   клиент --HTTP--> auth-service        регистрация, вход, refresh, выход
   клиент --WS----> шлюз --gRPC--> auth-service    ValidateToken, GetAccount
                         \--gRPC--> остальные сервисы (с проверенным пользователем)
```

## Пароли

Пароль нельзя хранить, нельзя шифровать, его можно только хешировать, и хеш должен быть медленным. Быстрый хеш
(`md5`, `sha256`) считается миллиарды раз в секунду на видеокарте, поэтому перебор по словарю идёт мгновенно. Соль
(случайная строка у каждой записи) убирает общие таблицы и прячет одинаковые пароли, но скорость перебора не меняет.
Нужны оба: соль и намеренно дорогой алгоритм. Современный выбор это argon2id: он требует много памяти, и видеокарты
теряют преимущество.

Крейт `argon2` хранит всё в одной строке формата PHC:

```
$argon2id$v=19$m=19456,t=2,p=1$<соль>$<хеш>
```

В строке алгоритм, параметры (память `m` в КиБ, проходы `t`, параллельность `p`) и соль. Отсюда два следствия.
Проверка использует параметры из записи, а не из конфига: пароли, сохранённые вчера, должны проходить сегодня.
А когда параметры в конфиге выросли, при успешном входе (единственный момент, когда пароль известен) запись пересчитывают
по новым параметрам и сохраняют. Неверный пароль записи не меняет.

Вызовы крейта выглядят так (на примере ключа заметки):

```rust
use argon2::password_hash::rand_core::OsRng;
use argon2::password_hash::{PasswordHash, SaltString};
use argon2::{PasswordHasher, PasswordVerifier};

let salt = SaltString::generate(&mut OsRng);
let record = argon.hash_password(b"note-key", &salt)?.to_string();
let parsed = PasswordHash::new(&record)?;
let same = argon.verify_password(b"note-key", &parsed).is_ok();
```

`argon` это `Argon2::new(Algorithm::Argon2id, Version::V0x13, params)`. Запись из базы может оказаться мусором,
тогда `PasswordHash::new` вернёт ошибку, и паниковать из-за этого не нужно.

### Хеш нельзя считать в async-функции

Один argon2 это десятки миллисекунд процессора и десятки мегабайт памяти. Внутри `async fn` без `.await` поток рантайма
занят, пока вычисление не кончится: замирают соседние запросы, `/health` и таймеры. Тяжёлое выносят на отдельный пул:

```rust
let verified = tokio::task::spawn_blocking(move || check(&password, &stored)).await?;
```

Пул блокирующих потоков большой, и без ограничения сотня одновременных входов съест всю память. Поэтому поверх ставят
`Semaphore`: разрешение берётся до запуска и держится до конца вычисления.

```rust
let permit = limiter.clone().acquire_owned().await?;
let out = tokio::task::spawn_blocking(move || {
    let _permit = permit;
    heavy(&input)
}).await?;
```

### Неизвестный ник и время ответа

Если для несуществующего пользователя сервис отвечает за 2 мс, а для существующего с неверным паролем за 90 мс, по времени
можно перебирать ники. Тексты ответов одинаковые, а время выдаёт. Лечение: для неизвестного ника выполнять такую же
дорогую проверку против заранее посчитанного фальшивого хеша тех же параметров.

### Сравнение за постоянное время

Сравнение секретов через `==` останавливается на первом отличающемся байте. Чем дольше ответ, тем длиннее угаданный
префикс. Правильное сравнение читает все байты и накапливает разницу:

```rust
a.iter().zip(b).fold(0u8, |acc, (x, y)| acc | (x ^ y)) == 0   // длины сравнены раньше
```

Длина не секрет, поэтому её можно проверять заранее. В боевом коде для этого берут проверенный крейт, а вручную
полезно увидеть, где пряталась утечка.

## Подпись: HMAC и base64url

Токен должен проверяться без похода в базу, поэтому его подписывают. Подпись по общему ключу это HMAC:
`HMAC(K, m) = H((K ^ opad) || H((K ^ ipad) || m))`. Двойной хеш нужен против атаки удлинения сообщения, которая ломает
наивное `sha256(ключ + сообщение)`. Ключ длиннее блока (64 байта для SHA-256) сначала хешируется, короче дополняется нулями.
Реализация сходится с векторами RFC 4231, и других способов убедиться, что ты совпадаешь с чужими реализациями, нет.

Base64 берёт три байта (24 бита) и режет их на четыре группы по 6 бит, каждая группа это индекс в алфавите из 64
символов. Если последняя порция короче трёх байтов, остаются 2 или 4 лишних бита: у корректной записи они нулевые,
по ним декодер и ловит «похожие» подделки.

Части токена пишутся в base64url: алфавит с `-` и `_` и без паддинга `=`, чтобы токен жил в заголовках и адресах.
Декодер должен быть строгим: любое «похожее» значение (с `=`, с пробелом, с ненулевыми хвостовыми битами) отвергается,
иначе у одного набора байтов появляются две записи, а подписи и списки отзыва сравнивают строки.

## Токен: части и порядок проверки

```
   eyJhbGci…      .   eyJzdWIi…           .   q3xk…
   заголовок          данные (claims)         подпись
   alg, kid           sub, iss, aud,          HMAC(ключ, "заголовок.данные")
                      exp, nbf, jti, role
```

Проверка идёт в таком порядке, и порядок важен:

1. Разобрать части. Мусор это `Malformed`.
2. Алгоритм. Он у нас один, и сравнивается строго. `none` и любое другое значение это отказ. Заголовок присылает клиент,
   и выбирать метод проверки ему нельзя.
3. `kid` выбирает ключ из связки. Неизвестный `kid` это отказ.
4. Подпись пересчитывается и сравнивается без раннего выхода.
5. И только теперь можно читать данные: срок (`exp`, `nbf`), издатель (`iss`), аудитория (`aud`).

Пока подпись не сошлась, всё в токене написано кем угодно: срок, роль, издатель. Если проверять срок раньше подписи,
подделка получает ответ, значит, сервис её «понял». Отдельная история с аудиторией: токен, выданный для платёжного
сервиса, не должен открывать соцсеть, и `aud` проверяют всегда.

Сроки сравнивают с допуском на рассинхрон часов (leeway, обычно секунд тридцать): токен считается просроченным, когда
`now >= exp + leeway`, и ещё не действующим, когда `now + leeway < nbf`. Время берут не из `SystemTime::now()` в глубине
функции, а из `Clock` за трейтом: тогда тест двигает время секунда в секунду и проверяет границы.

### Смена ключа без разлогина

Ключ надо менять: он мог утечь, и чем он старше, тем длиннее окно атаки. Сервис держит связку: текущий ключ (им
подписывают) и прошлые (ими ещё проверяют). `kid` в заголовке подсказывает, какой брать. Через время, равное максимальной
жизни токена, прошлый ключ выводят из оборота, и все токены, подписанные им, перестают приниматься. `kid` приходит от
клиента, поэтому он только указатель: подпись проверяется выбранным ключом так же строго.

## Сессии: access, refresh, ротация

Access-токен короткий (минут пятнадцать) и проверяется без обращения к таблице сессий: подпись и срок, плюс сверка
со списком отозванных `jti` (о нём ниже). Refresh-токен долгий (недели), случайный и лежит в
базе. По нему клиент получает новую пару, когда access протух. Правила:

- В базе хеш refresh, а не он сам. Токен случайный и длинный, поэтому хватает быстрого `sha256` без соли и без argon2.
  Тест на это простой: строка из дампа таблицы, использованная как токен, не должна ничего открывать.
- Ротация: каждый обмен выдаёт новую пару, а использованный refresh помечается и больше не работает. Строки не удаляют,
  а помечают: без пометки нельзя отличить «такого не выдавали» от «его уже предъявили».
- Срок вышел, когда `now >= expires`: ровно в секунду окончания токен уже не годится. Так же для access, refresh и
  одноразовых токенов.
- Повтор использованного refresh это сигнал кражи: у токена две копии у разных людей, оба предъявляют верный секрет, и
  сервер не знает, кто из них хозяин. Безопасный ответ: погасить всё семейство токенов этого входа, включая свежий,
  и потребовать пароль. Другие устройства пользователя (другие семейства) не трогают.
- Проверка и пометка делаются одной неделимой операцией (одна блокировка в памяти, одна транзакция в базе). Иначе два
  одновременных запроса с одним токеном видят его непомеченным, и оба проходят.

### Выход и отзыв

Подпись нельзя «забыть», поэтому для досрочного отзыва access добавляют минимум состояния: список отозванных `jti`
(denylist). Запись нужна ровно до срока токена: после него токен и так недействителен, а список не должен расти вечно,
поэтому его регулярно чистят. Выход гасит семейство и кладёт `jti` в список. «Выйти везде» делает то же для всех сессий
пользователя. Смена пароля делает то же для всех, кроме текущей, иначе пользователь выкинет сам себя.

## Роли и права

Права оформляют таблицей «роль, действие» с запретом по умолчанию: забытая строка делает систему строже, а не слабее.
Роль из токена разбирают точно: незнакомая, пустая, отсутствующая роль это гость без прав. Ветка `_ => Admin` в разборе
роли открывает всё первому, кто ошибётся в токене. Не нормализуй то, что подписываешь сам: токен выдан нами, и прощать
в нём нечего.

Проверка прав на ресурс живёт в сервисе, а не в контроллере. Контроллер защищает один вход, и когда появляется второй
(gRPC, фоновая задача), про проверку забывают. Правила бывают разные: «правит текст только автор», «удаляет автор или
модератор», «заблокированному нельзя ничего», и проверка бана идёт первой.

На границе стоит middleware: он разбирает `Authorization: Bearer <токен>`, проверяет токен и либо возвращает 401, либо
вызывает обработчик. У защищённого маршрута обработчик получает `Principal`, а не `Option<Principal>`: в нём нельзя
оказаться без пользователя. Присланный испорченный токен на публичном маршруте это тоже 401, а не тихий «аноним»:
клиенту надо показать, что его сессия сломана. Для просроченного токена нужен отдельный код, чтобы клиент обновил
токен, а не выкидывал пользователя на экран входа.

## Одноразовые токены и случайность

Письма «подтвердите почту» и «сбросьте пароль» содержат ссылку с одноразовым токеном. Токен случайный, хранится хешем,
живёт ограниченное время (час для сброса пароля), привязан к назначению (ссылка сброса не подтверждает почту) и сгорает
при использовании. Новая ссылка отменяет прежнюю. Проверка и удаление опять неделимы.

Все секреты берутся из системного источника случайности (`rand::rngs::OsRng`). Генератор, засеянный числом (`seed_from_u64`),
выдаёт детерминированную последовательность: если атакующий знает алгоритм и примерное время выдачи письма, он перебирает
несколько секунд и получает список всех возможных токенов. Удлинить такой токен не лечит: детерминизм остаётся.

## Типичные ошибки

- Пароли в `sha256` и `md5`, соль общая или её нет.
- Argon2 прямо в async-обработчике.
- Разный ответ или разное время для «нет такого ника» и «неверный пароль».
- Токен проверяется по заголовку: `alg: none` проходит.
- Срок читается раньше подписи.
- Один ключ подписи без `kid`: смена ключа разлогинивает всех.
- Refresh лежит в базе как есть, без хеша.
- Проверка refresh и пометка в разных блокировках.
- Ветка по умолчанию `Admin` в разборе роли.
- Проверка прав только в контроллере.
- Токены сброса пароля из генератора с seed от времени.
