# Аудит сервиса соцсети

К тебе пришёл сервис, который «вроде работает». Его написали быстро, и в нём есть почти все дыры главы: справочник аккаунтов при входе, подбор паролей, чужие права на комментарии и
черновики, поля, которые клиент ставит за сервер, неэкранированный HTML, внедрение в заголовки и журнал, SSRF в превью, открытые WebSocket, CORS и обновление сессии, слишком
большие сообщения. Твоя работа аудитора: для каждой дыры есть тест-эксплойт, он сейчас падает. Закрой все и не сломай обычную работу сервиса.

## Как устроено

```
Req (метод, путь с запросом, заголовки, куки, тело, адрес клиента, пользователь от шлюза, время)  ─►  App::handle  ─►  Resp
  POST /login                 вход
  POST /posts                 создать пост (JSON)
  GET  /posts/{id}/html       пост в виде HTML
  DELETE /comments/{id}       удалить комментарий
  GET  /drafts/{id}           прочитать черновик
  GET  /preview?url=...       превью ссылки (заголовок страницы)
  GET  /ws                    рукопожатие WebSocket (101 или 403)
  POST /auth/refresh          обновление сессии по куки
  GET  /me                    кто я (с заголовком X-Nick)
  OPTIONS ...                 preflight CORS (и CORS-заголовки на каждом ответе)
```

- `src/crates/socialsec/src/api.rs`: всё приложение. Править нужно этот файл.
- `ssrf.rs` (`check_url`, `is_public`), `throttle.rs` (задержки после неудач), `net.rs` (типажи `Net` и `Hasher`): готовые кирпичи из задач главы.
- `src/crates/socialsec/tests/audit.rs`: тесты-эксплойты и проверки обычной работы. Править их нельзя, CLI восстанавливает их перед проверкой. Сеть не нужна.

## Что сделать

Пройди `api.rs` как аудитор: найди каждую дыру, закрой её и проверь тест. Подсказок по местам нет, только по симптомам: каждый тест назван тем, что должно быть невозможно.
После работы `cargo test --workspace` проходит и `cargo clippy --workspace --all-targets -- -D warnings` чист.

## Критерии приёмки

- вход отвечает одинаково для несуществующего имени и неверного пароля, делает одинаковую работу, а подбор пароля замедляется для атакующего, не мешая хозяину;
- клиент не может задать автора, лайки, закрепление и признак черновика поста; тело поста и список тегов ограничены;
- текст и ник в HTML экранированы; чужие комментарии и черновики недоступны (чужой черновик выглядит несуществующим);
- превью не ходит во внутренние адреса, включая обходы через DNS и записи адреса числом;
- WebSocket, CORS и обновление сессии защищены от чужих сайтов (Origin, белый список, свой заголовок, атрибуты куки);
- ник не внедряет заголовок ответа, а путь запроса не подделывает журнал.

## Подсказки

Каждая дыра уже встречалась: вход (`svsec1` ... `svsec4`), владельцы (`svsec5`), заголовки и журнал (`svsec6`, `svsec7`), превью (`svsec8`, `svsec9`), Origin, CORS, CSRF (`svsec10` ... `svsec12`), размеры
(`svsec13`). Mass assignment и экранирование HTML были в главах про DTO и ошибки API.
