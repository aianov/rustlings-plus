# Слои сервиса

Представь сервис библиотеки. Читатель берёт книгу, и вот обработчик «выдать книгу», каким его пишут в
первый вечер. Всё рядом, всё работает:

```rust
async fn lend(req: HttpRequest, db: &Pool) -> HttpResponse {
    let body: serde_json::Value = match serde_json::from_str(&req.body) {
        Ok(v) => v,
        Err(_) => return HttpResponse::new(400, "bad json"),
    };
    let isbn = body["isbn"].as_str().unwrap_or("").trim().replace('-', "");
    if isbn.len() != 13 {
        return HttpResponse::new(422, "bad isbn");
    }
    let taken = db
        .fetch_optional("SELECT 1 FROM loans WHERE isbn = $1 AND returned IS NULL", &[&isbn])
        .await
        .unwrap();
    if taken.is_some() {
        return HttpResponse::new(409, "already lent");
    }
    db.execute("INSERT INTO loans (isbn, member) VALUES ($1, $2)", &[&isbn, &req.member]).await.unwrap();
    HttpResponse::new(201, &format!("{{\"isbn\":\"{isbn}\"}}"))
}
```

Через месяц у библиотеки появляется второй вход: приложение на gRPC для киосков. Правило «ISBN это
13 цифр» нужно в двух местах, и его копируют. Ещё через неделю выясняется, что `len()` считает байты:
ISBN с неразрывным дефисом (он занимает три байта) проходит как нормальный. Чинят в одном месте, во
втором забывают. Тест на правило надо писать с поднятой базой и настоящим HTTP-запросом, поэтому тестов
нет. А между `SELECT` и `INSERT` проходит второй киоск, и одну книгу выдали двум читателям.

Слои нужны не из любви к папкам. Каждый слой принимает одно решение и знает про мир ровно столько,
сколько нужно для него. Меняется транспорт: трогаем только его слой. Меняется база: трогаем только свой.
Правило живёт в одном месте и проверяется обычным `#[test]` без сети.

## Четыре слоя и три папки рядом

```
        снаружи (HTTP, gRPC, NATS)
                  │  байты
                  ▼
        ┌────────────────────┐
        │ controller         │  разобрал вход, позвал service, собрал ответ
        │   (dto рядом)      │  dto: типы, которые видны снаружи
        └─────────┬──────────┘
                  │  доменные значения
                  ▼
        ┌────────────────────┐
        │ service            │  правила: срок выдачи, лимит книг на читателя,
        │                    │  читатель должен существовать
        └─────────┬──────────┘
                  │  трейт-порт
                  ▼
        ┌────────────────────┐
        │ repository         │  как хранить: Mutex<HashMap>, Postgres, Scylla
        └────────────────────┘
```

**controller** принимает то, что пришло из сети, превращает в значения, понятные сервису, и превращает
результат в ответ. Правил библиотеки в нём нет. Если ты поймал себя на `if isbn.len() != 13` в контроллере,
это уже service.

**dto** (data transfer object): формы данных на границе, то есть что клиент присылает и что мы
отвечаем. У них свои атрибуты serde и свои имена полей. Внутрь service они не заходят. Разбирает тело в
DTO controller (например, через serde), а DTO это только форма.

**service**: сердце. Здесь живут правила, и только здесь. Он не знает про HTTP, статус-коды, JSON и SQL.
Получает доменные значения и возвращает доменный результат или доменную ошибку.

**repository** прячет хранилище за трейтом. Service говорит «сохрани выдачу», а где она окажется, ему
всё равно.

Рядом лежат три папки, это не слои. **bootstrap** собирает сервис при старте: кто какой репозиторий
получит, откуда конфиг. **common** это то, что нужно всем слоям: доменные типы (`Book`, `Loan`, идентификаторы)
и общие ошибки. **client** нужен, когда сервису надо позвать другой сервис: готовый клиент за трейтом, о
котором ниже.

## Куда смотрят стрелки

Зависимости идут только вниз. Controller знает про service и dto, service знает про порт репозитория,
repository не знает ни про кого сверху. Все трое могут знать про `common`, а `common` не знает ни про кого.

```
   разрешено                              запрещено
   ─────────                              ─────────
   controller ──▶ service                 service ──▶ controller
   controller ──▶ dto                     service ──▶ dto
   service ──▶ repository (трейт)         repository ──▶ service
   service, repository, dto ──▶ common    controller ──▶ repository
   bootstrap ──▶ всё                      common ──▶ любой слой
```

Проверка на глаз: открой `service/` и поищи `http`, `json`, `status`, `tonic`, `serde_json`. Нашёл,
значит транспорт просочился в правила. Открой `controller/` и поищи `repository::`. Нашёл,
значит контроллер пошёл в хранилище в обход правил, и первая же выдача без проверки читателя это покажет.

В этом курсе стрелки проверяют и приёмочные тесты: они читают исходники слоёв и ищут запрещённые `use`.
Это грубо, зато честно.

## Репозиторий как трейт

Сервис не должен знать, что под ним `HashMap`. Он знает контракт:

```rust
pub trait BookRepository: Send + Sync {
    fn find(&self, isbn: &Isbn) -> Option<Book>;
    fn add(&self, book: Book);
}
```

И рядом реализация для тестов и первого запуска:

```rust
pub struct InMemoryBooks {
    state: Mutex<HashMap<Isbn, Book>>,
}
```

Методы берут `&self`, а не `&mut self`: репозиторий общий для всех запросов, а изменяемость спрятана внутри
(`Mutex`). Супертрейты `Send + Sync` нужны, чтобы `Arc<dyn BookRepository>` можно было отдать другому
потоку или `tokio::spawn`: без них компилятор не разрешит такой `Arc` куда-либо отправить.

Зачем in-memory, когда есть Postgres? Затем, что тест правила не должен ждать базу. Сервис, написанный
против трейта, получает в тесте `InMemoryBooks`, а в проде `PgBooks`, и не замечает разницы.

## Дженерик или dyn

Есть два способа отдать сервису репозиторий.

```rust
struct LoanService<R: LoanRepository> { repo: R }            // дженерик
struct LoanService { repo: Arc<dyn LoanRepository> }          // трейт-объект
```

Дженерик быстрее (вызов известен при компиляции) и проще для компилятора. Но тип репозитория становится
частью типа сервиса: `LoanService<InMemoryLoans>` и `LoanService<PgLoans>` это разные типы. Выбрать
реализацию по конфигу при запуске в одну переменную не выйдет.

`dyn` платит одним косвенным вызовом и взамен даёт один тип: `Arc<dyn LoanRepository>` собирается из чего
угодно. Сервисы курса принимают порты как `Arc<dyn Trait>`: в `bootstrap` реализация выбирается по конфигу, а
цена вызова рядом с походом в базу не видна. Чистая логика и мелочи в горячих местах идут дженериком,
порты ввода-вывода идут за `dyn`.

## async-порты: dyn, BoxFuture и Send

Репозиторий, который ходит в базу, асинхронный. Первая мысль:

```rust
pub trait BookRepository: Send + Sync {
    async fn find(&self, isbn: &Isbn) -> Option<Book>;
}
```

Для дженерика это работает. Для `Arc<dyn BookRepository>` нет: компилятор скажет, что трейт не
dyn-совместим. Вызов через `dyn` идёт по таблице методов (vtable): один адрес функции и один известный
размер результата. А у каждого `async fn` свой анонимный тип future, и размеры у них разные. Выход: вернуть
future в коробке с затёртым типом.

```rust
use futures::future::BoxFuture;

pub trait BookRepository: Send + Sync {
    fn find(&self, isbn: Isbn) -> BoxFuture<'_, Option<Book>>;
}

impl BookRepository for InMemoryBooks {
    fn find(&self, isbn: Isbn) -> BoxFuture<'_, Option<Book>> {
        Box::pin(async move { self.state.lock().unwrap().get(&isbn).cloned() })
    }
}
```

`BoxFuture<'a, T>` это `Pin<Box<dyn Future<Output = T> + Send + 'a>>`. Обрати внимание на `Send`: он зашит
в псевдоним, поэтому каждый такой future обязан быть `Send`, иначе компилятор не даст его вернуть.

Когда у метода несколько ссылок, `'_` не подходит: он берёт время жизни из `&self`, а future хранит и
остальные ссылки.

```rust
fn find_by_title<'a>(&'a self, title: &'a str) -> BoxFuture<'a, Vec<Book>>;
```

Здесь `'a` стоит и на `&self`, и на `title`: future живёт не дольше обеих ссылок, и компилятор следит за этим.

Самая частая причина «future не `Send`»: `std::sync::MutexGuard` пережил `.await`.

```rust
Box::pin(async move {
    let books = self.state.lock().unwrap();     // guard живёт дальше
    tokio::time::sleep(delay).await;            // ошибка: guard не Send
    books.get(&isbn).cloned()
})
```

Решения два: взять замок после `.await` или закрыть его блоком `{ ... }` до `.await`. Держать
`std::sync::Mutex` через `.await` нельзя ещё по другой причине: задача заснула с замком в руках, соседняя
задача на этом же потоке ждёт замок, и всё встало.

Цена `BoxFuture` одна аллокация на вызов. Рядом с запросом в сеть это копейки.

## Типы: домен, DTO и транспорт

Одна и та же выдача книги в трёх видах. Читай сверху вниз, как путь запроса.

```
   вход
     байты из сети             {"isbn": "978-5-17-090000-1"}
        │ controller разбирает
        ▼
     DTO                       LendDto { isbn: String }        форма на границе
        │ controller превращает
        ▼
     домен                     Isbn, Loan { member, isbn, due }  с этим работает service
        │ service возвращает
        ▼
     DTO ответа                LoanDto { isbn, due_date }
        │ controller сериализует
        ▼
     байты в сеть              {"isbn":"9785170900001","due_date":"2026-11-01"}
   выход
```

Почему не один тип на всех? Потому что причины меняться у них разные. Клиент просит переименовать поле
`isbn` в `book`: это про DTO, домен не при чём. В `Loan` появилось внутреннее поле `penalty_cents`:
клиенту его видеть не надо, а один общий тип выдал бы его наружу.

Переходы между типами пишутся как `From` / `TryFrom` на границах:

```rust
impl From<Loan> for LoanDto {
    fn from(loan: Loan) -> Self {
        LoanDto { isbn: loan.isbn.to_string(), due_date: loan.due.to_string() }
    }
}
```

Доменная ошибка (`LoanError::Overdue`) превращается в статус-код тоже в контроллере. Service не знает, что на
свете есть число 422.

## Тонкий controller

Хороший контроллер читается за десять секунд:

```rust
pub fn get_member(svc: &MemberService, raw_id: &str) -> Result<MemberDto, ApiError> {
    let id = parse_id(raw_id)?;
    let member = svc.get(id)?;
    Ok(member.into())
}
```

Разобрал, позвал, собрал. Ошибки идут как значения: `?` вызывает `From<MemberError> for ApiError`, а одна
функция `render` превращает любой `Result<T, ApiError>` в ответ. Если в контроллере вырос `match` на десять
веток с правилами, правила пора вынести в service.

## Composition root

Кто создаёт репозиторий и отдаёт его сервису? Одно место: функция сборки при старте, в нашей раскладке
`bootstrap`.

```rust
pub fn build(config: &Config) -> App {
    let books: Arc<dyn BookRepository> = Arc::new(InMemoryBooks::default());
    let loans: Arc<dyn LoanRepository> = Arc::new(InMemoryLoans::default());
    App::new(LoanController::new(LoanService::new(books, loans)))
}
```

Все зависимости приходят в конструкторы явно: внедрение зависимостей без фреймворка и магии, просто
аргументы функций.

Противоположность: глобальное состояние. Соблазн велик:

```rust
static BOOKS: LazyLock<Mutex<HashMap<String, Book>>> = LazyLock::new(Default::default);
```

Работает, пока тест один. Cargo запускает тесты параллельно в одном процессе, и все они делят одну таблицу.
Один тест добавил книгу, второй ждёт пустой каталог: падает то один, то другой, и ровно тогда, когда
запускаешь всё сразу. Плюс невозможно создать две независимые копии сервиса. Поэтому состояние живёт в
значениях, а значения собирает bootstrap.

## Атомарность: «проверь и вставь» это гонка

Вернёмся к началу главы. Код такой:

```
   if не занято(isbn) { занять(isbn) }
```

Два киоска просят одну книгу одновременно:

```
   киоск A: занято("9785170900001")?  → нет
   киоск B: занято("9785170900001")?  → нет          ← A ещё не записал
   киоск A: занять(...)               → ok
   киоск B: занять(...)               → ok            ← одну книгу выдали двоим
```

Каждый шаг по отдельности правильный, ошибка живёт в паузе между ними. Починить паузу в service нельзя:
замок в service не спасёт, когда экземпляров сервиса два. Единственное место, которое видит все записи
сразу, это хранилище, поэтому «занять, если свободно» становится одной операцией репозитория:

```rust
// синхронный порт
fn lend_if_free(&self, isbn: &Isbn, member: MemberId) -> Result<Loan, RepoError>;   // Conflict, если занято

// тот же контракт в async-версии: то же самое, но через BoxFuture
fn lend_if_free<'a>(&'a self, isbn: &'a Isbn, member: MemberId) -> BoxFuture<'a, Result<Loan, RepoError>>;
```

В in-memory реализации это одна секция под одним замком: проверил, записал, отпустил. В Postgres это
`UNIQUE` индекс и `INSERT ... ON CONFLICT`: базу не обмануть, она сама отвергнет второго. Service лишь
переводит `RepoError::Conflict` в доменное `AlreadyLent`.

Формула: **правило, которое проверяется по данным, и запись по результату проверки должны быть одной
атомарной операцией там, где живут данные.**

Как отловить такую гонку в тесте? Подождать и надеяться, что планировщик подставит нужный момент, ненадёжно.
Надёжнее сделать окно гонки управляемым: в тестовое хранилище вставляют остановку (барьер) после
каждого обращения к данным. Тогда решение «проверил, отпустил замок, записал» гарантированно даёт
дубликаты, а решение с одной секцией проходит. Этим приёмом пользуются тесты главы.

## Чужие данные: порт к соседу

Библиотека разрезана на сервисы: `member-service` хранит читателей, `loan-service` хранит выдачи. Для
выдачи нужно знать, существует ли читатель. Искушение: открыть у `loan-service` соединение с базой читателей
и выполнить `SELECT`. Не делай так.

```
   плохо                                    хорошо

   loan-service ───────▶ members DB         loan-service ──▶ MemberDirectory (порт)
        │                                        │
        └──▶ loans DB                            │ gRPC
                                                 ▼
   member-service тоже ходит в members DB   member-service ──▶ members DB
```

Данные принадлежат одному сервису. Только он знает, как они устроены, и только он вправе менять схему.
Остальные ходят к нему через его API. Если `loan-service` читает таблицу напрямую, любое переименование
колонки ломает чужой сервис, и об этом никто не узнает до продакшена.

В коде это порт, трейт на стороне потребителя:

```rust
pub trait MemberDirectory: Send + Sync {
    fn exists(&self, id: MemberId) -> BoxFuture<'_, Result<bool, DirectoryError>>;
}
```

Service пользуется только им. За трейтом стоит `client`: реализация, которая ходит по gRPC. В тестах на его
месте заглушка.

Обрати внимание на `Result<bool, _>`. «Читателя нет» и «не смогли спросить» это разные факты. Первый
превращается в 404, второй в 503. Склеишь их, и при падении соседа каждый читатель внезапно «исчезнет».
Ошибки соседа переводят по смыслу, а не пересылают как есть. И порядок: сначала дешёвая проверка у себя,
потом дорогой поход к соседу: незачем гонять запрос по сети ради выдачи, которую всё равно отклонят.

## Раскладка воркспейса

```
   backend/
   ├── Cargo.toml                       виртуальный воркспейс
   └── src/
       ├── crates/                      общие библиотеки (движки, контракты)
       │   └── contracts/               идентификаторы и всё, что знают оба сервиса
       └── microservices/
           ├── member-service/
           └── loan-service/
               ├── Cargo.toml
               ├── src/
               │   ├── main.rs          тонкий: конфиг, bootstrap, слушаем
               │   ├── lib.rs           pub mod для тестов и для main
               │   ├── bootstrap/       сборка
               │   ├── controller/      вход
               │   ├── dto/
               │   ├── service/         правила
               │   ├── repository/      хранение
               │   ├── client/          клиенты соседей
               │   └── common/          доменные типы и общие ошибки
               └── tests/
```

`main.rs` тонкий нарочно: бинарь нельзя подключить к интеграционному тесту, а библиотеку можно. Вся
настоящая работа в `lib.rs`, а `main` только запускает её.

Внутри каждой папки слоя либо только файлы (`loan.rs`, `member.rs`), либо только папки-модули, а не
смешанно: `service.rs` рядом с папкой `service/` это путаница, её в этой главе проверяют.

## Типичные ошибки

- Правило прячется в контроллере («это же просто проверка длины»): потом появляется второй вход, и правило
  копируется. Сюда же: service принимает `HttpRequest` или один `Serialize`-тип ходит через все слои.
- «Проверь, потом вставь» вместо одной атомарной операции репозитория и `std::sync::MutexGuard` через `.await`.
- Глобальные `static` под данные и чтение чужой базы «одним запросом, это же быстрее».
