# Событийные шаблоны: идемпотентность, outbox, порядок

Интернет-магазин: покупатель оформил заказ, и это знают сразу три сервиса. Склад должен зарезервировать товар, почтовый
сервис отправить письмо, сервис бонусов начислить баллы. Пока всё работает, события из прошлых глав доезжают, и
кажется, что дело сделано. А потом в один вечер у покупателей по два письма «заказ принят», у одного человека баллы
начислены дважды, а на склад не пришёл заказ, который в базе есть. Никто не падал с ошибкой. Просто доставка
«хотя бы раз», процессы, которые умирают в самый неудобный момент, и порядок, который никто не обещал.

Эта глава о том, как жить с такими гарантиями. Четыре идеи, и у каждой своё место в конвейере:

```
 сервис-владелец            брокер                    потребитель
+------------------+                          +---------------------------+
| данные + outbox  | --релей--> JetStream --> | inbox + порядок + эффект  |
| одной транзакцией|  хотя бы раз             | проекция (можно пересобрать)|
+------------------+                          +---------------------------+
```

Хранилища в задачах пока лежат в памяти, а «одну транзакцию» изображает метод `Db::transaction`, который либо применяет
изменения целиком, либо не применяет ничего. Настоящие транзакции придут в разделе про данные, суть от этого не изменится.
Открой визуализации (клавиша `v`): `dual_write.html`, `outbox_flow.html` и `saga_steps.html` показывают то же самое по шагам.

## Событие это факт

Команда говорит «сделай»: `ReserveStock`. Её можно отклонить, у неё один адресат. Событие говорит «случилось»: `order.placed`.
Оно не отклоняется, потому что прошлое не отменишь, и у него сколько угодно читателей. Из этого следуют правила имени и
содержимого. Имя в прошедшем времени и по смыслу бизнеса (`order.placed`, а не `order.insert`). Содержимое: что произошло и
над чем, а не что с этим делать.

У каждого события одинаковый конверт, иначе потребители гадали бы, где что лежит:

```json
{"event_id": "e-8841", "type": "order.placed", "schema": 1, "version": 1,
 "occurred_at": 1700000000000, "aggregate_id": "o-77", "payload": {"order_id": "o-77", "total": 1200}}
```

`event_id` уникален и не меняется при повторной отправке (это ключ идемпотентности). `schema` версия формата payload.
`version` номер изменения агрегата (заказа, пользователя): у первого события 1, у второго 2. `occurred_at` время факта,
взятое производителем один раз. Идентификатор и время приходят в функцию аргументами, а не берутся из часов внутри: так
событие воспроизводимо в тесте.

Что класть в payload, зависит от потребителей. **Событие-уведомление** («заказ o-77 оформлен») мало весит, но каждый
читатель идёт за подробностями к владельцу: тот должен быть доступен и помнить заказ. **Событие с состоянием** («заказ
o-77: товар, сумма, адрес») развязывает сервисы: читатель ничего не спрашивает. Цена: данные дублируются, и каждое поле
становится контрактом. Поэтому кладём то, что нужно читателям для работы, и не кладём личное и лишнее: событие читает
каждый, кто подписан.

## Формат живёт дольше кода

Событие, записанное сегодня, лежит в журнале годами, а сервисы выкатываются каждый день. Поэтому читатель должен быть
терпимым: берёт нужные поля, остальные игнорирует.

```rust
#[derive(Deserialize)]
struct Placed {
    order_id: String,
    total: u64,
}
// лишнее поле "coupon" в JSON этот разбор не смутит: serde пропускает неизвестное сам
```

Опасны два атрибута. `#[serde(deny_unknown_fields)]` превращает любое новое поле производителя в ошибку у всех
потребителей. Закрытый `enum` для типа события делает ошибкой любой новый тип. Остаётся правило: нужное обязательно
(нет поля, ошибка, а не подставленное значение), лишнее не мешает, незнакомый тип пропускается и не разбирается.
`#[serde(default)]` помогает там, где поле появилось позже и у старых событий его нет по-честному.

Если формат изменился несовместимо (было `name`, стало `first_name` и `last_name`), поднимают версию `schema` и добавляют
**апкаст**: функцию «событие схемы N в событие схемы N+1». Применяется она на входе читателя, и дальше по коду все знают только
последний формат.

```rust
fn upcast_order(mut e: Event) -> Result<Event, Error> {
    if e.schema == 1 {
        let cents = e.payload["total"].as_u64().ok_or(Error::Bad("total"))? * 100;
        e.payload["total_cents"] = json!(cents);
        e.payload.as_object_mut().unwrap().remove("total");
        e.schema = 2;
    }
    Ok(e)
}
```

Апкаст не трогает конверт (идентификатор, время и версия остаются теми же, иначе сломаются дедупликация и порядок) и не
угадывает будущее: схема, которой код не знает, это явная ошибка.

## «Хотя бы раз» значит «иногда дважды»

Брокер доставляет, пока не получит подтверждение. Подтверждение потерялось, обработчик завис дольше `ack_wait`,
сервис перезапустили посреди обработки: событие придёт снова. Отказаться от повторов нельзя, их надо переживать. Обработчик,
которому всё равно, сколько раз его вызвали, называется **идемпотентным**.

Бывает идемпотентность по природе операции («установить статус shipped», «положить в множество»). С остальными помогает
ключ: запомнить `event_id` и не обрабатывать увиденное. Но память конечна. Хранить идентификаторы в окне последних N это
компромисс: повтор, пришедший за пределами окна, пройдёт как новый. Окно выбирают с запасом по самому позднему повтору.
Для критичного хранят идентификаторы в базе.

Важно выбрать, что считать ключом. Повтор это то же событие, а не то же содержимое: покупатель
честно может положить в корзину один и тот же товар дважды, и это два события с разными идентификаторами. Дедупликация по
содержимому (или по состоянию «товар уже в корзине») ломается именно на этом, а запоздавший повтор после смены состояния
ломает состояние. Рабочий ключ один: идентификатор, назначенный производителем.

### Inbox: эффект и отметка неделимы

```
проверил: id не видел  ->  применил эффект  ->  записал: id обработан
                                   ^ падение здесь: эффект есть, отметки нет, повтор применит его ещё раз
```

Если записать отметку раньше эффекта, падение между ними теряет событие (повтор решит, что оно уже обработано). Если позже,
дублирует. Выход один: сделать два изменения одним: **inbox**. Эффект и отметка в одной транзакции базы, либо обе записаны,
либо ни одной. И проверка «видел ли» с записью отметки тоже одним шагом: два параллельных обработчика, которые сначала оба
проверили, а потом оба записали, применят событие дважды. Точный инструмент в памяти: `HashSet::insert` возвращает `false`,
если значение там уже было, то есть проверка и запись в одной операции. В базе то же делает уникальный индекс.

Внешние эффекты (письмо, платёж, вебхук) в транзакцию базы не включишь. Для них ключ идемпотентности отдают получателю:
«платёж с этим ключом уже проведён, вот результат». Если получатель так не умеет, «ровно один раз» недостижимо, выбирают
между «возможно дважды» и «возможно ни разу».

В Rust конкурентность проверяется тестом, а не взглядом. Типичный приём: восемь потоков, `std::sync::Barrier`, чтобы
стартовали одновременно, и пауза внутри окна, которое хочется поймать:

```rust
let barrier = Arc::new(Barrier::new(8));
let handles: Vec<_> = (0..8).map(|_| {
    let (shared, barrier) = (shared.clone(), barrier.clone());
    std::thread::spawn(move || { barrier.wait(); shared.handle("e1") })
}).collect();
```

## Двойная запись и outbox

Заказ сохранили, событие отправили. Два действия в двух разных системах (база и брокер), общей транзакции у них нет:

```
сохранить, потом опубликовать:  падение между -> заказ есть, события нет (склад не узнает никогда)
опубликовать, потом сохранить:  отказ базы    -> события есть, заказа нет (призрак)
```

Поменять шаги местами не помогает, дефект просто переезжает. Решение называется **outbox** («исходящие»): событие записывают
в ту же базу и той же транзакцией, что и данные, в таблицу `outbox`. Теперь «заказ есть» и «событие запланировано»
неразделимы. Дальше отдельный процесс, **релей**, читает неотправленное по порядку, публикует и помечает отправленным:

```
UPDATE orders ... ; INSERT INTO outbox ... ;   -- COMMIT одним куском
релей:  выбрать sent=false по seq  ->  publish(Nats-Msg-Id = event_id)  ->  дождаться подтверждения  ->  sent=true
```

Порядок действий релея важен. Пометка только после подтверждения, иначе упавшая публикация потеряет событие. Остановка на
первой ошибке, иначе следующие события обгонят застрявшее и нарушат порядок. И неизменный идентификатор: релей может
опубликовать, упасть до пометки и после перезапуска опубликовать то же снова, а JetStream в окне дубликатов (по умолчанию две
минуты) отбросит повтор по заголовку `Nats-Msg-Id`. Публикация в JetStream двухшаговая, как ты знаешь из прошлой главы:
`js.publish_with_headers(...).await?` отправляет, а `.await?` на результате ждёт подтверждения записи. Константа имени
заголовка есть в самой библиотеке: `async_nats::header::NATS_MESSAGE_ID`.

Итоговая гарантия: **«хотя бы раз» с редкими дублями** (за пределами окна брокера). Дубли гасит потребитель своим inbox. Эти
механизмы не заменяют, а дополняют друг друга.

## Порядок: версия агрегата

Брокер сохраняет порядок публикации в одном stream, но потребитель с несколькими экземплярами, повторами и ретраями видит
события в другом порядке. Чем измерять «раньше»? Не временем: часы двух серверов расходятся, событие со «вторым» временем
может предшествовать «первому». Мерой служит **версия агрегата**: номер события внутри одного заказа (пользователя, поста),
который производитель назначает в той же транзакции, где пишет данные.

Что делать с событием не по порядку, зависит от его природы.

- **Снимок** (в событии новое значение целиком: «имя теперь Анна»): достаточно запомнить версию применённого и отбрасывать
  всё, что не новее. Промежуточные версии можно пропустить, снимок их заменяет.
- **Дельта** (в событии изменение: «добавь товар», «+1»): нужно применять каждое и ровно по порядку. Событие из будущего
  придерживают в буфере (по версиям, `BTreeMap` держит их отсортированными), а когда приходит недостающее, отдают всю
  цепочку. Буфер ограничивают: потерянное событие иначе превратится в утечку памяти, и честнее потребовать пересборки.

Версия принадлежит агрегату, а не потребителю. Производитель считает её по числу событий агрегата в outbox внутри той же
транзакции, что и запись данных: предыдущая плюс один. Поэтому потребитель, которому событие незнакомого типа не нужно, всё
равно обязан «пройти» его номер и сдвинуть ожидаемую версию. Иначе дыра в нумерации навсегда оставит все следующие события
агрегата в буфере. Либо порядок считается только по типам, которые потребитель читает, и тогда это отдельная договорённость
с производителем.

Агрегаты независимы, задержка одного не тормозит остальные. И не всякое изменение зависит от порядка: прибавления и вычитания
коммутируют, присваивания нет. Прежде чем строить машинерию, подумай, на каком из двух случаев ты стоишь.

## Проекции

Сервис, которому нужны чужие данные для чтения, не ходит за ними на каждый запрос. Он держит свою копию в удобной форме
(склад: остатки по товарам, строящиеся из событий заказов и поставок) и обновляет её по событиям. Это **проекция**.
Её главное свойство: состояние зависит только от журнала событий. Тогда проекцию можно выбросить и построить заново, перечитав
журнал с начала, например после исправленной ошибки в обработчике или когда нужно новое поле.

Из этого следует требование детерминизма. Обработчик не смотрит на часы (время берёт из события), не использует случайные числа
и не зависит от порядка обхода `HashMap` (он в Rust случаен от запуска к запуску: порядок задают явным ключом сортировки).
Проверка простая: собери проекцию дважды из одного журнала, подожди и сравни. Имена и прочее, что меняется, подставляют на момент
чтения, а не копируют в старые записи: одно событие смены имени тогда исправляет всю историю.

## Сага

Операция, которая задевает несколько сервисов («оформить заказ»: зарезервировать товар, списать деньги, создать доставку),
не может быть одной транзакцией. Это **сага**: цепочка локальных шагов, у каждого есть обратное действие, **компенсация**.
Оркестратор запускает шаги по очереди, а при сбое откатывает уже сделанное в обратном порядке: поздние шаги могли
опираться на ранние. Упавший шаг не откатывают, он не завершился.

```
шаги вперёд:    резерв -> оплата -> доставка (сбой)
компенсации:                резерв <- оплата отменена
```

Компенсации тоже падают, поэтому их повторяют, но не бесконечно, и застрявшую выносят наружу (отчёт, мёртвая очередь, дежурный),
не бросая остальной откат. Шаги, которые нельзя отменить (письмо клиенту, списание у внешнего провайдера без возврата),
ставят как можно позже, когда все остальные уже удались. Оркестратор пишет журнал `Started`, `Done`, `Compensated`, чтобы
после собственного падения продолжить: откатить стоит всё начатое и ещё не откатанное, включая шаг, у которого нет записи
`Done` (падение могло случиться после действия, но до записи), а запись `Compensated` защищает от повторного отката. Сами
компенсации должны выдерживать повтор.

## Типичные ошибки

- Публикация события из обработчика запроса после `INSERT`. Работает, пока ничто не падает.
- Строгий разбор (`deny_unknown_fields`, закрытый enum): первый же новый тип или поле останавливает потребителя.
- Дедупликация по содержимому или состоянию вместо `event_id`.
- Отметка «обработано» отдельной записью до или после эффекта; проверка и запись двумя шагами.
- Время в обработчике проекции из `SystemTime::now()`: пересборка даёт другой результат.
- Порядок по времени события вместо версии агрегата.
- Неограниченный буфер ожидающих событий и неограниченное окно идентификаторов.
- Необратимый шаг саги в начале.
