# Шлюз

В приложении онлайн-кинотеатра экран «Главная» собирается из шести вызовов: каталог, рекомендации, продолжить просмотр,
профиль, баланс, уведомления. Мобильный клиент знал адреса всех шести сервисов, у каждого было своё соединение,
своя проверка токена и свой формат ошибок. Когда команда поменяла адрес сервиса рекомендаций, пришлось выпускать новую
версию приложения, а старые версии ещё месяц показывали пустую главную. Когда у «баланса» начались перебои, экран не
открывался вовсе, хотя каталог был жив.

Шлюз решает эти проблемы одним приёмом: у клиента одна дверь. Клиент говорит с шлюзом на одном протоколе, а шлюз
знает, куда идти, проверяет, кто пришёл, собирает ответ из частей и не даёт одному клиенту занять всё. Дальше разберём, из
чего он состоит и где в нём прячутся ошибки.

## Протокол: кадр с id

В соцсети клиент держит с шлюзом WebSocket и обменивается кадрами JSON:

```
   клиент -> шлюз:   {"id": 7, "service": "catalog", "method": "list", "data": {"genre": "drama"}}
   шлюз -> клиент:   {"id": 7, "ok": true, "data": [...], "request_id": "gw-41"}
                     {"id": 7, "ok": false, "error": {"code": "not_found", "message": "..."}}
```

Кадр без `id` и JSON, который не объект, это ошибка клиента (`invalid_argument` с `id: null`), а не падение.

Поле `id` придумывает клиент, а шлюз возвращает его без изменений (число числом, строку строкой). Зачем он нужен, видно, когда
запросы идут по одному соединению одновременно: ответы приходят в порядке готовности, и клиент находит свой по `id`.
Если `id` испорчен, ответить на него нечем, и отвечают с `id: null`. Вход и регистрация идут не по этому протоколу, а по обычному
HTTP через прокси (см. ниже): у клиента без токена ещё нет соединения.

## Таблица маршрутов и стирание типов

Маршрут это пара (`service`, `method`) и асинхронный обработчик. Обработчики приходят от разных людей, и у каждого `async`-блока
свой анонимный тип future, а в `HashMap` все значения должны быть одного типа. Выход один: стереть тип.

```rust
type Handler = Box<dyn Fn(Value) -> BoxFuture<'static, Result<Value, GwError>> + Send + Sync>;
table.insert(key, Box::new(move |data| handler(data).boxed()));
```

`BoxFuture` и `.boxed()` из крейта `futures` (дополнение к tokio): `BoxFuture` это `Pin<Box<dyn Future + Send>>`, а `.boxed()`
упаковывает обычный future. Цена одна аллокация на вызов, рядом с сетью её не видно.

Руками разбирать `Value` в каждом обработчике скучно и чревато опечатками, поэтому добавляют типизированный `route`: обработчик
принимает `Req: Deserialize` и возвращает `Resp: Serialize`, а обёртка сама делает serde в обе стороны. Данные, которые не
разобрались, это ошибка клиента (`invalid_argument`), а не 500, и текст ошибки `serde` в ответ не идёт: он цитирует присланное.

Две вещи про таблицу. Дубликат маршрута (`HashMap::insert` молча заменяет старое) нужно ловить при сборке роутера и падать при
старте, называя все задвоенные пары: ошибка конфигурации должна умирать в тесте, а не жить в проде. И неизвестный маршрут это
`not_found`, а не молчание.

## Кто пришёл: проверка на соединении

Токен проверяется один раз, при подключении, потому что кадров будут тысячи, а проверка это сетевой вызов (`ValidateToken` в
auth-service). Токен приходит заголовком `Authorization: Bearer ...` или параметром `token=` в строке запроса (браузерный
WebSocket не умеет ставить заголовки). Нет токена: анонимное соединение. Токен есть, но плохой: соединение не открывается, и
код различает «просрочен» (клиент обменяет refresh и придёт снова) и «неверен» (нужен новый вход).

Результат проверки лежит в контексте соединения: `Principal` и срок токена. Защищённые методы регистрируются отдельно,
`route_authed`, и их обработчик получает `Principal`, а не `Option<Principal>`. Это не вкусовщина: с `Option` кто-нибудь
забудет `None`, и аноним начнёт создавать посты от «пустого» пользователя. Проверку делает шлюз и делает её до разбора
данных: иначе по ошибкам разбора аноним изучает схему защищённых методов.

Соединение живёт часами, а токен минут пятнадцать, поэтому срок сверяют на каждом кадре: `now >= exp` закрывает соединение
(ответом `token_expired` и закрытием), и закрытое остаётся закрытым, даже если часы ушли назад. Такая проверка срабатывает по
сроку, но не по отзыву: если токен отозвали раньше срока (бан), шлюз этого не увидит. Для быстрого отзыва нужен второй канал:
сверять список отозванных на кадрах или получать сигнал «закрой соединения пользователя».

## Параллельная обработка и лимит

Если читать кадры по одному и ждать ответа, быстрый запрос стоит за медленным. Правильная схема такая: каждый кадр обрабатывается
в своей задаче, задачи собираются в `JoinSet`, ответы уходят по готовности. Цикл слушает два события: пришёл новый кадр и
закончилась какая-то задача (`tokio::select!`). Когда вход закрыт, нужно дождаться всех начатых запросов: иначе отключившийся
клиент оставит потерянные ответы и недоделанные побочные эффекты.

Паника в обработчике убивает задачу, и `JoinError` не знает, на какой кадр отвечать. Поэтому `id` кадра запоминают заранее, в словаре
`task::Id -> id` (`join_next_with_id` возвращает идентификатор и для упавшей задачи).

Без лимита один клиент поднимает тысячу задач и вытесняет остальных. Лимит запросов в полёте на соединение делают семафором:
`try_acquire_owned` не ждёт, и если мест нет, клиент сразу получает `resource_exhausted` со своим `id`. Очередь вместо отказа не
лечит, а прячет проблему: растут память и задержка, а клиент ждёт ответа, который ему уже не нужен. Разрешение живёт внутри
задачи и возвращается всегда, в том числе при панике.

Скелет цикла (на другом примере, очереди печати):

```rust
let mut jobs = JoinSet::new();
let mut owners: HashMap<task::Id, u64> = HashMap::new();
loop {
    tokio::select! {
        Some(job) = incoming.recv() => {
            let id = job.id;
            let handle = jobs.spawn(print(job));
            owners.insert(handle.id(), id);
        }
        Some(done) = jobs.join_next_with_id() => match done {
            Ok((task_id, page)) => { owners.remove(&task_id); reply_ok(page) }
            Err(error) => reply_internal(owners.remove(&error.id())),
        },
        else => break,
    }
}
```

## Вызовы сервисов

Соединение к сервису дороже самого запроса (TCP, TLS, HTTP/2), поэтому оно одно на адрес, открывается лениво и переиспользуется:
в tonic `Channel` дёшево клонируется и пускает запросы параллельно по одному соединению. Тонкости три. Первое открытие должно
случиться один раз при любой гонке: ячейка `tokio::sync::OnceCell` на адрес. Ошибка открытия не запоминается (ячейка остаётся
пустой, следующий вызов пробует снова). И замок на карте адресов держится только на время поиска ячейки, а не на время открытия:
иначе один медленный сервис тормозит вызовы ко всем остальным.

На каждый вызов ставят дедлайн (в tonic `request.set_timeout`): зависший сервис должен стоить ровно отведённое время, а не вечность.

Вместе с вызовом едет metadata: `x-request-id` (сквозной номер, по которому поддержка находит записи всех сервисов) и
`x-user-id` с ролью. Сервисы позади шлюза читают их без проверки, значит, граница доверия проходит по шлюзу, и всё, что клиент мог
подложить сам, надо срезать. Внутренние ключи (`x-user-id`, `x-user-role`, `x-request-id`, всё с префиксом `x-internal-`) берутся
только из проверенного контекста, а клиентские metadata пропускаются по белому списку: чёрный список забывает новый внутренний
ключ, а белый нет. Значения проверяются на длину и управляющие символы: перевод строки это вставка заголовков.

## Аккуратная агрегация

Экран собирается из нескольких запросов, которые друг от друга не зависят, а значит, идут одновременно (`tokio::join!`), и вся
сборка стоит время самого медленного. Но параллельность без решения «что обязательно» даёт половину пользы. Обязательная часть
(пользователь) валит весь ответ, если не получена. Необязательные (рекомендации, счётчики) заменяются `null`, а их имена
попадают в список `partial`, чтобы клиент нарисовал остальное. Необязательным частям дают бюджет времени (`tokio::time::timeout`):
зависший сосед не должен задерживать ответ, ради которого пользователь пришёл. Обязательную часть бюджет не режет.

## Обратный прокси для входа

Вход и регистрация проксируются в auth-service: `/auth/login` уходит туда как `/login`. «Передал запрос, передал ответ» выглядит
просто, а ловушек четыре.

- Заголовки уровня соединения (`Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailer`,
  `Transfer-Encoding`, `Upgrade` и все, что перечислены в значении `Connection`) описывают один участок пути. Дальше они не
  передаются, ни в запросе, ни в ответе: иначе апстрим получает инструкции не по адресу, а это классический путь к смуглингу запросов.
- Адрес клиента. Шлюз стоит на границе сети, и единственный надёжный адрес это адрес TCP-соединения. Всё, что клиент прислал про
  себя (`X-Forwarded-For`, `X-Real-IP`, `Forwarded`, `X-Forwarded-Proto`, `X-Forwarded-Host`), ложь, и это выбрасывается. Если же перед шлюзом
  стоит свой балансировщик, список `X-Forwarded-For` разбирают справа налево, пропуская доверенные адреса, и клиентом считают первый недоверенный.
- Проверки без апстрима идут первыми: чужой путь это 404, слишком большое тело это 413. Апстрим защищён от мусора.
- Апстрим недоступен: 502. Апстрим не ответил за `timeout`: 504. Тело этих ошибок пишет шлюз, подробности внутренней сети клиенту не нужны.

## Типичные ошибки

- Клиент знает адреса сервисов, а не один шлюз.
- Дубликаты маршрутов затирают друг друга молча.
- Данные клиента, которые не разобрались, дают 500.
- `Option<Principal>` в обработчике защищённого метода.
- Токен проверен при подключении, и соединение живёт дольше токена.
- Кадры одного соединения обрабатываются по очереди или без лимита.
- Паника в обработчике оставляет клиента без ответа.
- Соединение к сервису на каждый вызов или замок на всю карту на время открытия.
- Клиентские metadata копируются в вызов целиком.
- Прокси передаёт `Connection`, `Upgrade` и верит `X-Forwarded-For` от клиента.
