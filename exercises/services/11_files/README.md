# Файлы: как не стать открытой дверью

Платёжный сервис хранит квитанции в PDF, а клиенты их скачивают. Первая версия пишется за вечер:

```rust
async fn save_receipt(root: &Path, name: &str, pdf: Vec<u8>) -> io::Result<()> {
    tokio::fs::write(root.join(name), pdf).await
}
```

Через месяц список бед такой. Бухгалтерия открыла квитанцию, пока она ещё писалась, и увидела обрубок. Пользователь с именем
файла `../../etc/cron.d/x` записал что-то в планировщик сервера. Кто-то загрузил двухгигабайтный «PDF», и процесс умер от нехватки
памяти, потому что `Vec<u8>` целиком живёт в оперативной памяти. Под видом квитанции приехал HTML со скриптом, и сервис отдал его
браузеру как страницу. Ссылка «скачать» уже месяц ходит по чатам и по-прежнему открывается. Каждая беда решается отдельным приёмом,
и все они про одно: файл приходит от человека, а человеку верить нельзя, зато можно построить вокруг него конвейер, где каждый шаг
отвечает за одну опасность.

```
клиент ──► [лимит] ──► [сигнатура и размеры] ──► [хеш и временный файл] ──► [rename] ──► [запись в базе]
            байты        что это на самом        одним проходом,           имя         файл теперь
            по ходу      деле, не по имени       без памяти                появилось   принадлежит кому-то
```

## Хранилище за трейтом и ключи вместо путей

Остальной сервис не должен знать, где лежат файлы: на диске, в S3 или на другом сервере. Он знает три действия: положи по ключу,
дай по ключу, удали. Это порт, и первая его реализация (каталог на диске) завтра заменяется другой без правки остального кода.

```rust
trait ReceiptStore: Send + Sync {
    async fn save(&self, key: &str, body: ByteStream) -> io::Result<u64>;
    async fn open(&self, key: &str) -> io::Result<Option<ByteStream>>;
    async fn remove(&self, key: &str) -> io::Result<bool>;
}
```

Тело ходит потоком кусков, а не `Vec<u8>`: файл в 200 МБ при пятидесяти параллельных загрузках занял бы десять гигабайт, а поток держит
в памяти один кусок за раз. Кусок пришёл, ушёл на диск, забыт. Отсутствие файла это нормальный ответ (`None`, `false`), а не ошибка:
вызывающему удобнее обычный `if`, чем разбор причины сбоя. Ключ это то, что выбирает сервер. Хороший ключ состоит из безопасных
символов и разбрасывает файлы по подкаталогам (первые два символа), иначе в одном каталоге их станет миллион, и каждая операция
с ним замедлится.

## Запись: либо целиком, либо никак

Запись прямо в итоговое имя ломается двумя способами. Пока она идёт, читатель видит половину файла. Если она оборвётся, половина
там и останется, а если файл уже существовал, `File::create` обнулила его в первую же миллисекунду. Единственная операция, которая в
файловой системе атомарна, это переименование: имя указывает либо на старый файл, либо на новый, середины нет. Поэтому
запись идёт в сторону, а имя переключается в самом конце:

```
receipts/7f/7f31c9.pdf            (старый, читатели видят его)
receipts/7f/.7f31c9.pdf.4.tmp     (новый, пишется здесь; читатели о нём не знают)
   ... дописали ...  sync_all  ...  rename(.tmp, 7f31c9.pdf)  ──►  имя мгновенно указывает на новый
```

Три тонкости. Временный файл лежит в том же каталоге: переименование между каталогами или дисками может быть не атомарным. Перед
переименованием нужен `sync_all` (подтверждение, что данные дошли до диска): без него система может сохранить новое имя раньше
содержимого, и после отключения питания под ним окажется пустой файл. Имя временного файла уникально (счётчик или случайное число),
иначе две параллельные записи одного ключа испортят друг друга.

Остаётся мусор. Упавшая загрузка оставляет временный файл, и через месяц их тысячи. Убрать его в ветке ошибки недостаточно: когда клиент
закрыл вкладку, обработчик запроса просто перестаёт выполняться, будущее уничтожается, и код после точки ожидания не запустится
никогда. В Rust по-настоящему надёжно работает только `Drop`: значение, уходящее из области видимости, вызывает свой деструктор,
что бы ни случилось с потоком управления. Поэтому временный файл охраняет «страж»:

```rust
struct TempGuard { path: PathBuf, armed: bool }

impl Drop for TempGuard {
    fn drop(&mut self) {
        if self.armed {
            let _ = std::fs::remove_file(&self.path);
        }
    }
}
```

В `Drop` нельзя ждать (`.await`), поэтому удаление синхронное, и это нормально: оно быстрое. После успешного переименования страж
разоружается, чтобы не трогать то, что уже стало настоящим файлом.

## Лимиты на лету

У запроса есть заголовок `Content-Length`, и очень хочется на него положиться: «заявлено 5 МБ, лимит 10, пропускаем». Нельзя.
Клиент может написать в заголовке что угодно, а тело прислать совсем другое. Может не писать его вовсе (потоковая отправка в
`Transfer-Encoding: chunked`). Заявленный размер годится для дешёвого раннего отказа («заявлено 5 ГБ, даже не начинаем»), а
настоящая защита это счётчик на самих байтах:

```
seen = 0
для каждого куска:  seen += длина;  если seen > лимит → ошибка, дальше не читаем
```

Адаптер над потоком, который считает и обрывает, пишется на `futures::stream::unfold`: состояние (источник, счётчик, флаг «уже
сломались») переходит от шага к шагу. Источник читается не дальше, чем нужно: на кусок, выведший за предел, мы останавливаемся и
остаток тела не качаем. Граница «ровно лимит ещё можно» ошибочно сдвигается на единицу чаще, чем хочется признавать, поэтому её
проверяют тестом.

## Что внутри файла

Расширение `.pdf` и заголовок `Content-Type: application/pdf` пишет клиент. Это пожелания. Факт один: что лежит в первых байтах.
Большинство форматов начинаются с «магического числа» (сигнатуры). PDF начинается с `%PDF-`, ZIP с `PK`, PNG с восьми байт,
первый из которых `0x89`. Решение «принимаем или нет» принимается по сигнатуре, а тип и расширение потом берутся у распознанного
формата, не у клиента. Короткий вход (пустая загрузка, обрыв) это обычная жизнь, и срез без проверки длины превращает его в панику.

Сигнатура отвечает лишь на вопрос «как это начинается». Внутри может быть что угодно. Классика: «бомба декомпрессии», файл на
килобайт, который в заголовке объявляет размеры 60000 на 60000 и, будучи открытым, съедает гигабайты памяти. Лечится это чтением
размеров из заголовка до декодирования и лимитом на стороны и площадь. Два типичных промаха: искать нужный маркер как подстроку по
всему файлу (он встретится и в чужих данных, надо идти по структуре) и считать площадь в 32 битах (65536 на 65536 даёт ровно ноль и
проходит любой лимит; считай в 64). И ещё «полиглоты»: файл, который одновременно валидная картинка и HTML. Против него не поможет
никакая проверка начала, помогает только то, как ты его потом отдаёшь (ниже).

## Ключ: не от клиента, а по содержимому

Имя файла от клиента это не путь. `root.join("/etc/x")` возвращает `/etc/x` (абсолютный путь вытесняет корень), а `root.join("../../x")`
выходит из хранилища. Попытки «почистить» имя проигрывают: удалили `../`, а из `....//` после удаления получился `../`. Список обходов
бесконечен (обратные слеши, кодирование, нулевые байты). Надёжна одна мысль: данные клиента никогда не становятся частью пути.
Ключ строит сервер, а клиентское имя остаётся строкой для показа, которую всё равно чистят (последний компонент, без управляющих
символов, ограниченной длины), потому что она попадёт в заголовки и в интерфейс.

Ключ можно строить из самого содержимого: sha256 файла, записанный в hex. Тогда два одинаковых файла получают один ключ и хранятся
один раз, а проверка целостности достаётся бесплатно. Но ключ известен только после последнего байта, а память под целый файл мы
пожалели. Выход: писать под временным ключом, а хеш считать по пути. Для этого у потока есть адаптер `inspect`, который смотрит
на каждый элемент и пропускает его дальше. Когда запись кончилась, остаётся одно из двух: такой ключ уже есть (временный удаляем),
либо нет (переименовываем).

У общего файла есть цена: его нельзя удалить, когда один из владельцев «убрал свой». Два пользователя ссылаются на один ключ.
Первый сменил картинку, и если удалить файл, у второго пропадёт. Нужен счётчик ссылок на ключ или уборка, которая сверяет файлы с
базой.

## Подписанные ссылки

Файл должен открываться по ссылке без входа в аккаунт (её откроет почтовый клиент, плеер, друг), но не вечно и не кому угодно.
Решение: ссылка несёт срок и подпись, которую умеет ставить только сервер. Подпись это HMAC от секрета сервера и того, что нельзя
менять. Главный вопрос: от чего именно? От всего, что влияет на поведение: ключ, срок, имя для скачивания. Любой параметр вне
подписи пользователь вправе поправить в адресной строке, и первое, что он сделает, это продлит срок.

Вторая тонкость: строка, от которой считается подпись, должна читаться однозначно. Если склеить поля без разделителя, наборы
`("ab", 12)` и `("ab1", 2)` дадут одну и ту же строку `ab12`, и подпись одного сойдёт за подпись другого. Нужен разделитель из
символа, которого в самих полях быть не может. Порядок проверок при открытии такой: формат, подпись, срок. Подпись идёт раньше
срока, чтобы подделка не узнала, просрочена она или нет. Сами подписи сравнивают за постоянное время.

Отозвать одну ссылку из тысяч нельзя: сервер ничего про них не хранит, в этом их достоинство. Отозвать все ссылки разом можно сменой
секрета. А точечно (ссылки на один файл) помогает версия, которую берут из базы и включают в подпись: увеличил число, и старые ссылки
этого файла перестали проходить проверку.

## Два хранилища и сироты

Файл лежит на диске, ссылка на него в базе, и транзакции на оба сразу не существует. Порядок «сначала файл, потом база» при отказе
базы оставляет сироту: файл есть, а владельца нет, и никто об этом не знает. Порядок «сначала база, потом файл» оставляет ссылку на
пустое место. Выход: двухфазная загрузка. Перед первым байтом в базе заводится запись «ожидает» (ключ и время). После успешной
записи ссылки запись снимается. Фоновая уборка периодически берёт записи «ожидает» старше разумного срока (за который любая
нормальная загрузка успела бы завершиться), удаляет их файлы и записи. Свежие записи она пропускает, потому что файл мог ещё
писаться. Это тот же приём, что outbox из главы про событийные шаблоны: след в базе превращает «возможно потеряли» в «знаем и
найдём».

Старый файл при замене удаляют только после успешной записи новой ссылки. Иначе при отказе базы профиль остаётся без картинки.

## Раздача

Браузер выполняет то, что считает страницей. Если сервис отдал загруженный HTML или SVG со скриптом и заголовком `text/html`,
скрипт запустится на нашем домене со всеми нашими cookie. Правила раздачи:

- Тип выбирает сервер, по сигнатуре, а не по тому, что прислал клиент. Распознанные картинки отдаются со своим типом и
  `Content-Disposition: inline`. Всё остальное как `application/octet-stream` и `attachment`: браузер предложит сохранить.
- Всегда `X-Content-Type-Options: nosniff`. Без него браузер вправе «догадаться» по содержимому и увидеть в вашем «текстовом» файле HTML.
- Политика `Content-Security-Policy: default-src 'none'; sandbox` запрещает исполнение и подгрузку, даже если страница всё-таки открылась.
- Имя файла в `Content-Disposition` это тоже вход для атаки: перевод строки в нём дописывает чужие заголовки, а кавычка закрывает
  значение. Поэтому имя идёт в двух формах: безопасный ASCII в `filename="..."` и настоящее в `filename*=UTF-8''...` с кодированием
  каждого небезопасного байта как `%XX`. Управляющие символы убираются до всего остального.
- Файлы пользователей раздают с отдельного домена (не с того, где живёт приложение): cookie сессии на него не уходят, и даже
  выполнившийся там скрипт не получит чужой сессии. Это не замена остальным мерам, а ещё один слой.

Про `Range`, потоковую отдачу и `multipart` в этом курсе уже говорилось в разделе про сеть. Здесь они лежат поверх: безопасность
файла решается до того, как первый байт ушёл клиенту.

## Типичные ошибки

- `Vec<u8>` и `collect()` на теле запроса. Память умножается на число одновременных загрузок.
- Запись в итоговое имя, а потом `rename` из другого каталога. Первое показывает половину, второе не атомарно.
- Очистка временного файла только в ветке ошибки: отмена задачи её обходит.
- Верить `Content-Length`, расширению, `Content-Type` из формы.
- Чистить `../` из имени вместо того, чтобы не брать путь у клиента вовсе.
- Подпись ссылки без срока или без каких-то параметров, склейка полей без разделителя, сравнение подписей через `==`.
- Удалять общий файл, не проверив, кто ещё на него ссылается.
- Отдавать загруженное с тем типом, который назвал клиент, и без `nosniff`.
