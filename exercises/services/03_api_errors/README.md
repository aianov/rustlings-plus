# Ошибки API

В приложении для записи к мастеру пользователь жмёт «Записаться» и видит плашку «Что-то пошло не так».
Он жмёт ещё раз. И ещё. Через пять минут пишет в поддержку, а поддержка не может найти запись в логах: ни
времени, ни номера запроса, ни какой из трёх сервисов отказал. Выяснилось потом, что слот просто был занят
(обычная ситуация, ей надо было показать «выбери другое время»), но сервер ответил 500 на любую беду.
А когда копирайтер поправил слово «занят» на «недоступен», сломался экран, который искал это слово в тексте.

Ошибки в API это такой же контракт, как успешные ответы. У ошибки два читателя: человек (ему нужен
понятный текст) и программа (ей нужен код, по которому она выбирает поведение). Третий читатель, о котором
забывают, это тот, кто ищет чужую слабость, и ему не надо подсказывать устройство системы.

## Что случилось, то и отвечаем

Первое решение: какой статус. Не угадывай, держи таблицу в одном месте.

```
   что случилось                          HTTP    gRPC               чья вина
   ------------------------------------------------------------------------------
   тело не прочитать (битый JSON)         400     InvalidArgument    клиента
   прочитали, но поля не годятся          422     InvalidArgument    клиента
   не знаю, кто ты                        401     Unauthenticated    клиента
   знаю, кто ты, но тебе нельзя           403     PermissionDenied   клиента
   такого нет                             404     NotFound           клиента
   уже есть, состояние не позволяет       409     AlreadyExists      клиента
   слишком часто                          429     ResourceExhausted  клиента
   у нас сломалось                        500     Internal           наша
   зависимость недоступна, подожди        503     Unavailable        наша
   зависимость не успела                  504     DeadlineExceeded   наша
```

Граница 4xx и 5xx важна не для красоты. По ней мониторинг решает, будить ли дежурного. Если считать
ошибки клиентов нашими, алерты шумят всю неделю, и однажды настоящую поломку примут за очередной шум.
Если считать наши ошибки клиентскими, поломка прячется среди 404.

Пары, которые чаще всего путают:

- 401 и 403. 401 значит «представься» (клиент может обновить токен и повторить). 403 значит «я знаю тебя,
  но нельзя», и обновление токена ничего не изменит. Отдашь 401 вместо 403, и клиент пойдёт в бесконечный цикл
  входа. К 401 принято добавлять заголовок `WWW-Authenticate`, к 429 и 503 заголовок `Retry-After` с числом секунд.
- 400 и 422. 400: тело вообще нельзя разобрать, это баг приложения. 422: форма верная, значения нет. Первое лечится
  обновлением версии, второе подсказкой под полем.
- 404 и 403 для чужих приватных ресурсов. Иногда 404 нарочно: «этого для тебя нет», чтобы не подтверждать
  существование. Решай осознанно и один раз для всех сервисов.
- 500 и 503. 503 это «временно, повтори». Клиенты с умными повторами разгружают сервис сами, а на 500
  разумно не повторять: неизвестно, что сломалось.

Повторять имеет смысл только то, что может пройти позже без изменений: 429, 503, 504. Повтор остальных
в лучшем случае бесполезен, в худшем создаст ту же запись дважды.

## Конверт и каталог кодов

Тело ошибки одного вида на весь API:

```json
{"error": {
  "code": "booking.slot_taken",
  "message": "это время уже занято",
  "request_id": "req-8f21",
  "details": [{"field": "slot", "code": "taken"}]
}}
```

`code` для программ, `message` для людей, `request_id` для поддержки, `details` по полям (только когда есть что
сказать). Программа ветвится по `code` и никогда по `message`: текст можно переводить, править, переписывать.

Коды живут в каталоге: один файл, один `enum`, у каждого варианта стабильная строка. Это публичный контракт:
переименовать значит сломать чужой код, поэтому в тестах строки пишут литералами. Клиент, в свою очередь,
не должен падать на коде, которого не знает: сервер обновили раньше приложения. Поэтому на проводе код это
строка, а `enum` лишь знает известные:

```rust
fn from_wire(text: &str) -> Option<Code> {
    Code::ALL.into_iter().find(|c| c.as_str() == text)
}
```

(Для клиента удобнее вариант `Unknown`, а на сервере `Option`: незнакомая строка там просто ошибка.)
Если сделать поле `code: Code` с `#[derive(Deserialize)]`, первый же новый код сломает разбор целого ответа.
Строку сохрани (её можно показать в отчёте), а решать по ней научится следующая версия клиента.

## Доменная ошибка и транспортная

Репозиторий отвечает на языке базы («нарушено ограничение bookings_slot_key»), сервис на языке предметной
области («слот занят»), HTTP-слой на языке статусов. Каждый слой переводит ошибку соседа и не знает
чужой словарь.

```
   repository         service                controller / transport
   RepoError    ->    BookingError    ->     ApiError   ->  HTTP 409 + конверт
   UniqueViolation    SlotTaken              Code::SlotTaken   gRPC AlreadyExists + метаданные
```

На каждый сервис один `enum` ошибок. Строки и `Box<dyn Error>` везде не годятся: верхний слой не может
выбрать поведение через `match`. Для enum нужны `Display` (что сказать человеку) и `Error` с методом `source()`
(что сломалось на самом деле):

```rust
#[derive(Debug)]
enum BookingError {
    SlotTaken,
    MasterNotFound(u64),
    Internal(Box<dyn std::error::Error + Send + Sync>),
}

impl std::error::Error for BookingError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            BookingError::Internal(cause) => Some(cause.as_ref()),
            _ => None,
        }
    }
}
```

`Display` у варианта с причиной не должен повторять её текст: цепочка `source()` и так попадёт в лог, а в других местах (ответ, метрика) короткая общая фраза безопаснее. `Send + Sync` нужны, чтобы ошибка свободно пересекала границы задач и потоков. Переход от ошибки репозитория
к ошибке сервиса пишется один раз как `impl From<RepoError> for BookingError`, и в сервисе остаётся короткое
`repo.insert(slot)?`. Внутри `From` держи две дисциплины.

Первая: переводи по смыслу, а не «всё во внутреннюю». Нарушенное ограничение по имени надёжнее, чем разбор текста
сообщения базы. Незнакомое ограничение честно считается нашей ошибкой: если назвать его «слот занят», клиент
будет менять время, которое не виновато.

Вторая: причину не выбрасывай. В `Internal` клади сам исходный `RepoError`, а не `to_string()` от него.
Тогда `source()` и `downcast_ref` увидят настоящий тип, и логи получат полную цепочку.

И ещё одна ловушка: `.ok()`, `unwrap_or_default()` и `if let Ok(..)` на результате репозитория выбрасывают
причину совсем. Сбой базы превращается в «ничего не найдено», и клиент выкидывает живые данные.
Ветка `_ =>` в маппинге ошибок такая же: она выключает проверку полноты, и новый вариант ошибки
молча становится 500. Пиши варианты явно, компилятор потребует решения для нового.

## Лог и ответ клиенту: разное

Из одной ошибки получаются два текста для разных людей.

```
              ┌──────────────────────────────┐
   ошибка --> │ лог: request_id, вся цепочка │   для инженера, полно
              │ причин, путь, DSN, стек      │
              ├──────────────────────────────┤
              │ ответ: code, общий текст,    │   для клиента, безопасно
              │ request_id                   │
              └──────────────────────────────┘
```

`request_id` связывает их: пользователь называет номер, поддержка находит запись. Цепочку причин вынимают
циклом по `source()` до `None`. Уровень записи тоже решение: клиентские ошибки (4xx) идут спокойным уровнем,
серверные на уровне ошибки. Иначе дежурного будят из-за чужих опечаток.

Утечки случаются не только в `message`. Проверь все места, куда попадает текст:

- сообщение ошибки (`err.to_string()` у `io::Error` содержит путь, у ошибки базы адрес и пользователя);
- заголовки «для отладки» (`x-debug-error`);
- `details` с эхом введённого значения (пароль, оказавшийся в «поле password: слишком короткий»);
- тексты `serde_json::Error`: они цитируют присланное значение;
- `{:?}` внутренних типов в теле: формат ответа привязывается к именам Rust.

Правило простое: наружу уходит только то, что собрано из безопасных кусочков (код, имя поля, константа), а не
отформатировано из внутренней ошибки. Одинаковый ответ на любые внутренние сбои тоже защита: по различиям
атакующий понял бы, что у нас сломалось.

## Паника это тоже ответ

Паника в обработчике (`items[0]` на пустом списке, `unwrap` на `None`) убивает задачу, а клиент получает оборванное
соединение: ни статуса, ни номера запроса. Ловят её один раз на границе сервера и превращают в обычную
внутреннюю ошибку: статус 500, конверт, подробности в лог.

Крейт `futures` это дополнение к tokio: `BoxFuture` это `Pin<Box<dyn Future + Send>>` (future со стёртым типом, который можно хранить в поле или возвращать из замыкания), а `.boxed()` упаковывает в него обычный future. `FutureExt::catch_unwind` ловит панику внутри future.

```rust
use futures::FutureExt;
use std::panic::AssertUnwindSafe;

let outcome = AssertUnwindSafe(handler(request)).catch_unwind().await;
```

Ловить надо оба места: обработчик может запаниковать и до того, как вернул future, тогда `catch_unwind` на future
ничего не увидит, и нужен ещё `std::panic::catch_unwind` вокруг самого вызова. Другой способ: запускать обработчик
в `tokio::spawn` и смотреть `JoinError::is_panic()`. Содержимое паники это `Box<dyn Any + Send>`, текст достают через
`downcast_ref::<&str>()` и `downcast_ref::<String>()`. `AssertUnwindSafe` это обещание, что после паники
ты не будешь читать полуобновлённое состояние.

Подводный камень: `std::sync::Mutex`, в котором держали блокировку во время паники, остаётся отравленным, и
каждый следующий `lock().unwrap()` паникует тоже. Сервер жив, но отвечает 500 всем, кто касается этого мьютекса.
Выход: не паникуй под блокировкой, а на пути обработки ошибки бери данные через
`lock().unwrap_or_else(|p| p.into_inner())` (или используй `tokio::sync::Mutex`, который отравления не знает).

## Разбор входа: 400, 422 и чужие значения

`serde_json::Error` умеет сказать, что случилось: у него есть `classify()` с вариантами `Syntax`, `Eof`, `Data`, `Io`.
Синтаксис и обрыв это 400. `Data` (JSON корректен, но тип или набор полей не тот) это 422. Значения дальше
проверяет валидатор из прошлой главы, и его нарушения собираются все сразу и кладутся в `details`:
пользователю удобнее увидеть три ошибки за раз, чем исправлять по одной.

Текст ошибки `serde` в ответ не отдавай. Сообщение `invalid type: string "hunter2", expected u8` прекрасно
помогает разработчику, а вместе с тем возвращает клиенту (и прокси по дороге) присланный пароль.

## gRPC: код в метаданных

В gRPC ошибка это `Status`: код (`Code::NotFound` и остальные из таблицы выше), текст и метаданные. Прикладной
код кладут в метаданные, например `x-error-code`, рядом `x-request-id` и при нужде `retry-after`. Они
доезжают до клиента вместе со статусом.

```rust
let mut status = tonic::Status::new(tonic::Code::NotFound, "запись не найдена");
status.metadata_mut().insert("x-error-code", "booking.not_found".parse().unwrap());
```

Значения метаданных это ASCII, поэтому из чужой строки их собирают через `MetadataValue::try_from`, а не `unwrap`.

На стороне клиента не доверяй метаданным слепо. Статус могла сгенерировать не наша программа: прокси и балансировщик
отвечают `Unavailable` с собственным текстом и без наших ключей. Поэтому разбор клиента двухуровневый: прикладной код
из метаданных, а если его нет, значение по умолчанию по gRPC-коду. Решение «повторять ли запрос» принимай по gRPC-коду
(`Unavailable`, `DeadlineExceeded`, `ResourceExhausted`), а не по тексту.

## Ошибка соседа: переводи по смыслу

Когда сервис зовёт соседа, ответ соседа описывает вызов между сервисами, а не запрос клиента. Передать его вверх как есть
значит сказать клиенту неправду.

```
   клиент -> шлюз -> post-service -> user-service
                                          NotFound (нет автора 77)
                      AuthorNotFound  <-  |       «автор» это поле запроса клиента
   422 post.author_not_found <- InvalidArgument
```

- «Не найдено» от соседа не значит «не найден ресурс, который просил клиент». Если сосед не нашёл автора, а клиент
  просил создать пост, это ошибка в запросе: 422 с понятным кодом.
- «Недоступен» и «не успел» остаются временными: 503 и 504, и клиент знает, что повторять можно.
- `PermissionDenied`, `Unauthenticated` и `InvalidArgument` при служебном вызове значат, что сломали мы (протух токен
  сервиса, неверно собран запрос). Права пользователя проверены раньше. Клиенту отдают 500, а настоящую причину
  пишут в лог.
- Шлюз отвечает за каждое слово наружу. Коды соседа проверяет по списку публичных и сверяет с gRPC-статусом:
  код `post.not_found` при статусе `Internal` противоречит сам себе. Незнакомый код заменяется кодом по умолчанию.
  Сообщение соседа не пересылается, оно уходит в лог вместе с его номером запроса. Свой `request_id` в ответе,
  чужой в логе: тогда обращение в поддержку приводит к одной записи шлюза, а из неё видна и запись соседа.

## Типичные ошибки

- Ветвление клиента по тексту сообщения.
- 500 на любую беду и 404 при сбое базы.
- 401 вместо 403 и бесконечный цикл входа.
- `err.to_string()` или `{:?}` в теле ответа.
- Только `match` с `_ =>` в маппинге ошибок.
- Эхо присланных значений (в том числе в тексте ошибки `serde`).
- Паника без перехвата или перехват только вокруг future, а не вызова обработчика.
- Пересылка чужого `message` и чужого `request_id` клиенту.
- Один и тот же код на разные ситуации: клиент не отличит «слот занят» от «мастер уволен».
