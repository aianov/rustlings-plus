# nhs_router: крейт http-engine, часть 1

Проверочная задача главы. Из кусочков главы собирается первая половина HTTP-движка, на котором
потом вырастут keep-alive, лимиты, middleware и мягкая остановка. Здесь сервер простой: одно
соединение, один запрос, один ответ, закрытие. Но уже настоящий: параллельный, с роутером, JSON и
защитой от паники.

## Что уже есть

Крейт `http-engine` с готовым разбором запросов (`src/parse.rs`: тот самый парсер из прошлых глав
с лимитами, `Request`, `Response`, `StatusCode`, `Headers`, `Params`), типами `Handler` и
`BoxFuture` и функцией `handler(...)` в `src/lib.rs`. Тебе остаются роутер, сервер и JSON-помощники:
эти функции падают через `todo!()`. Приёмочные тесты лежат в `tests/acceptance.rs` и
восстанавливаются перед каждой проверкой.

## Что сделать

1. `Response::error(status, message)` отвечает JSON `{"error": "<сообщение>"}` с
   `Content-Type: application/json`, `Response::json(status, &value)` отвечает значением; если значение
   не сериализуется, это 500 и `{"error":"internal error"}`.
2. `Request::json::<T>()`: нет Content-Type, чужой тип или кодировка не utf-8 это ответ 415;
   нечитаемый JSON и неподходящая форма это 400 с понятным текстом. Тип сравнивается без учёта
   регистра, параметры после `;` допустимы.
3. `Router::route(method, pattern, handler)` регистрирует маршрут. Шаблон начинается с `/`, сегмент
   `:имя` захватывает непустой сегмент. Путь не нормализуется: `/a/` и `/a` разные пути.
4. `Router::dispatch(request)`:
   - сегменты пути раскодируются по отдельности (`%2F` внутри сегмента остаётся частью значения, а не
     разделителем); плохое кодирование это 400;
   - из маршрутов, подходящих под метод и путь, побеждает самый конкретный: сегменты сравниваются слева
     направо, статичный сильнее параметра. Порядок регистрации не влияет;
   - параметры попадают в `request.params`;
   - путь есть, а подходящего метода нет: 405 и `Allow` (методы по алфавиту, без повторов, для GET
     добавляется HEAD); пути нет совсем: 404. Тело обеих ошибок в формате `{"error": ...}`;
   - HEAD без собственного обработчика обрабатывается обработчиком GET.
5. `serve(listener, router)` принимает соединения, каждое в своей задаче:
   - запрос собирается из кусков (`parse_request` вызывается на накопленном буфере);
   - ошибка разбора отвечает кодом из `ParseError::status()` и закрывает соединение; клиент, ушедший
     на полуслове, не ошибка;
   - обработчик запускается отдельной задачей: паника превращается в 500 `{"error":"internal error"}`;
   - на HEAD тело не пишется (`to_bytes(true)`), в каждом ответе есть `Connection: close`;
   - после ответа запись закрывается, а остаток запроса вычитывается (`finish`, готового нет, пиши сам): иначе ответ на
     слишком большой запрос теряется, когда ядро сбрасывает соединение с непрочитанными данными.

## Критерии приёмки

`cargo test`. Проверяется:

- маршруты, 404 и 405 с `Allow`, HEAD;
- параметры пути, приоритет статичных сегментов независимо от порядка регистрации, `%2F` в параметре;
- JSON на входе и выходе, коды 400 и 415;
- паника в обработчике даёт 500, а сервер живёт;
- медленные обработчики не блокируют друг друга, запрос приходит по три байта;
- 431 на огромную голову, 413 до получения тела, 400, 501 и 505 на мусор;
- общее состояние (`Arc` в обработчиках) видно всем соединениям.
