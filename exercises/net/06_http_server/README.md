# Свой HTTP-сервер

Откроем окно терминала и поговорим с кофейней:

```
$ curl -i http://127.0.0.1:8080/menu/latte
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 37
Connection: close

{"drink":"latte","price":250,"ml":300}
```

Между байтами, вышедшими из сети, и этим JSON работает конвейер из пяти ступеней. Запомни его
порядок, дальше вся глава это его детали (смотри визуализацию `http_server_pipeline`).

```
 сокет ──> буфер ──> парсер ──> роутер ──> обработчик ──> ответ ──> сокет
 байты     копим     "целый    какой       бизнес-       байты
 приходят  до конца  запрос?"  маршрут?     логика        уходят
           запроса
```

Парсер у тебя уже есть: он берёт накопленный буфер и отвечает «пока мало», «запрос готов» или «ошибка».
Роутеру достаётся готовый `Request`, обработчику тоже. Сокета они не видят, и это хорошо: их можно
проверять без сети. Сервер это всё, что склеивает ступени: принять соединение, накопить байты,
передать запрос, записать ответ, закрыть.

## Как не потерять запрос по дороге

`read` возвращает сколько получилось, а не сколько нужно. Запрос из 300 байтов может прийти как
200 + 100 или как 3 + 297. Поэтому цикл чтения кладёт всё в один буфер и каждый раз спрашивает
парсер, целый ли запрос. Искать конец головы (`\r\n\r\n`) надо во всём накопленном, а не в свежем
куске: терминатор мог разрезаться посередине. Если клиент закрылся (`read` вернул 0) до того, как
запрос собрался, это обычный уход, а не авария сервера.

Каждое соединение живёт в своей задаче: `tokio::spawn(connection(stream, app.clone()))`. Один
медленный клиент или один долгий обработчик не мешает остальным. Если обработчик вызвать прямо в
цикле `accept`, весь сервер будет обслуживать одного человека за раз.

## Обработчики в одной таблице

Роутеру нужна таблица «маршрут → обработчик». Обработчиков будет много, и они разные:

```rust
async fn menu(req: Request) -> Response { /* ходит в память */ }
async fn order(req: Request) -> Response { /* ждёт кассу по сети */ }
```

У каждой `async fn` свой безымянный тип будущего (компилятор строит для неё конечный автомат), поэтому
`Vec` из них собрать нельзя. Нужно стереть тип: убрать будущее в кучу за указателем. Получается такая
сигнатура:

```rust
type BoxFuture<T> = Pin<Box<dyn Future<Output = T> + Send>>;
type Handler = Box<dyn Fn(Request) -> BoxFuture<Response> + Send + Sync>;
```

Разберём слова. `dyn Future` стирает тип; `Box` кладёт значение в кучу, потому что размер у разных
конечных автоматов разный; `Pin` обещает, что будущее не сдвинется с места в памяти (внутри него могут быть
ссылки на само себя). `Fn`, а не `FnOnce`, потому что обработчик вызывают на каждый запрос. Ты обычно не
пишешь `Box::pin` руками: маленькая функция-обёртка принимает любую подходящую `async fn` или
замыкание и прячет это за собой.

### Почему `Send` и `'static`

Эти два слова из границ вызывают больше всего ошибок.

`Send` значит «можно передать другому потоку». Многопоточный рантайм вправе начать выполнять будущее на
одном потоке, а после очередного `.await` продолжить на другом. Поэтому всё, что будущее хранит между
`.await`, обязано быть `Send`. Типичный нарушитель: `Rc`, который считает ссылки без атомарных операций.
Второй нарушитель: guard от `std::sync::Mutex` (его нельзя отдать другому потоку), если он живёт через
`.await`.

`'static` значит «не держит ссылок на чужие локальные переменные». Задача, запущенная через
`tokio::spawn`, живёт сколько захочет, возможно дольше, чем функция, которая её запустила. Если в
замыкании лежит `&str`, который указывает в стек вызывающего, этот стек к тому времени исчезнет.
Лекарство: владеть значением (`String` вместо `&str`, `Arc` вместо `&`).

Пример на кофейне. Очередь заказов хотят показывать на табло:

```rust
fn queue_view(title: &str) -> Handler {
    let queue = Rc::new(RefCell::new(Vec::<String>::new()));
    handler(move |_req| {
        let queue = queue.clone();
        async move { Response::text(200, &format!("{title}: {}", queue.borrow().len())) }
    })
}
```

Две ошибки в одной функции: `Rc` не `Send`, а `title` не `'static`. Компилятор назовёт обе, но не там,
где они написаны, а там, где их требует `tokio::spawn`. Читай сообщение до конца: нужные слова в нём есть.

## Общее состояние

Состояние приложения (меню, очередь, счётчики) лежит в структуре, которую обернули в `Arc` и раздали
каждому обработчику:

```rust
struct Shop {
    queue: Mutex<VecDeque<Order>>,
    served: AtomicU64,
}
```

Блокировку из `std` держат коротко, без `.await` внутри: взял, поменял, отпустил. Если внутри секции надо
подождать (например, база), блоком отделяют секцию и ждут уже снаружи. Асинхронный мьютекс
`tokio::sync::Mutex` умеет держаться через `.await`, но он дороже и нужен редко. Правило для
счётчиков: атомик, если достаточно одного числа; для составных данных блокировка, в которой операция
«проверил и записал» делается одним куском. Выдать номер заказа и положить заказ в очередь в два
отдельных захвата значит рано или поздно получить два заказа с одним номером.

## Роутер

Роутер сначала находит путь, потом смотрит на метод. Три исхода:

| путь | метод | ответ |
|------|-------|-------|
| нет  | любой | 404 |
| есть | не подходит | 405 и заголовок `Allow` со списком методов этого пути |
| есть | подходит | вызываем обработчик |

Шаблон `"/menu/:item"` разбивается по `/` на сегменты. Статичный сегмент сравнивается точно, сегмент с
двоеточием захватывает любое непустое значение под этим именем. Число сегментов обязано совпасть, так что
`/menu/latte/` (слеш в конце) это уже другой путь. Параметры раскодируют уже после разбиения: `%2F`
внутри сегмента остаётся символом внутри значения и не делит путь.

Когда под путь подходит несколько шаблонов (`/menu/:item` и `/menu/today`), выбирает не порядок строк в
коде, а конкретность: сегменты сравниваются слева направо, статичный сильнее параметра. Смотри визуализацию
`router_match`. Так добавление нового маршрута в середину файла не меняет поведение старых.

Параметры пути приходят строками. Приведение к числу делает обработчик, а ошибка пользователя это 400
с именем параметра («bad parameter 'id'»), не 500 и не паника. Различай: опечатка клиента 400;
в шаблоне нет такого имени (ошибка программиста) 500.

Параметры запроса (`?cups=2&milk=oat`) разбирают в структуру один раз, на входе:

```rust
struct OrderQuery { cups: u32, milk: Milk }   // дальше код работает с типами, а не со строками
```

Умолчания для необязательных, диапазоны, отказ при повторе параметра и при мусоре: всё в одной функции.
Цифры проверяй явно: `"+5".parse::<u32>()` удаётся, а в URL знак числа обычно ошибка.

## JSON на входе и выходе

Тело запроса читают три вопроса подряд, и каждый заслуживает своего кода:

1. Это вообще JSON? Заголовок `Content-Type: application/json` (регистр не важен, после `;` могут быть
   параметры, кодировка только UTF-8). Нет: **415**.
2. Это корректный JSON? Нет: **400**, в тексте позиция ошибки.
3. Это то, что я жду? Нет нужного поля или неверный тип: **400** с названием поля.

Ответы тоже JSON, и ошибки одного вида: `{"error": "что случилось"}`. Собирать такое склейкой строк
нельзя: кавычка или перевод строки в сообщении превращает ответ в мусор. Сериализуй через `serde_json`.
Если сериализация не удалась, это вина сервера (500), и клиенту внутренности не показывают.

## HEAD

`HEAD /menu/latte` значит «покажи заголовки, которые были бы у GET, но без тела». Ответ идентичен GET по
заголовкам, включая `Content-Length` настоящего тела, а самих байтов тела в нём нет. Поэтому для HEAD
запасной обработчик это GET-обработчик, а в `Allow` к GET добавляется HEAD. Лишний байт тела в ответе
на HEAD не мелочь: на открытом соединении он будет прочтён как начало следующего ответа.

## Паника в обработчике

Обработчики пишут люди, и один из них однажды сделает `unwrap()` на пустом месте. Паника в задаче tokio
уничтожает только эту задачу. Остальные соединения и сам сервер живы, но клиент, чей запрос
обрабатывался, остаётся без ответа: просто оборванное соединение. Нам хочется вежливого 500.

Граница задачи как раз и есть перегородка: `tokio::spawn` возвращает `JoinHandle`, а его `.await` отдаёт
`Result`, в котором паника задачи приходит как `JoinError` (у него есть `is_panic`). Значит, обработчик
надо запускать отдельной задачей и разбирать, чем она закончилась. Что именно положить внутрь задачи,
решай сам: паниковать может и вызов замыкания, пока оно строит будущее, и само будущее. Текст паники клиенту не показывают, ему хватит «internal error», подробности
идут в журнал.

## Не теряй ответ об ошибке

Клиент отправил запрос на 5 МБ, сервер на 8 КБ понял «слишком большая голова», отправил 431 и сразу закрыл
сокет. Но во входном буфере ядра ещё лежат непрочитанные байты клиента. Закрытие сокета с непрочитанными
данными заставляет ядро ответить на них RST (сброс соединения), и клиент может потерять уже полученный
ответ: вместо 431 он увидит «connection reset». Правильное закрытие после ответа об ошибке:

1. закрыть только запись (`shutdown`): клиент прочтёт ответ и увидит конец потока;
2. ещё немного читать и выбрасывать входящее (ограничив объём и время, иначе это дыра для атаки);
3. закрыть сокет.

## Типичные ошибки

- Ответить после первого `read`, не дождавшись конца головы.
- Вызвать обработчик в цикле `accept` вместо отдельной задачи.
- Держать guard от `std::sync::Mutex` через `.await` (и получить ошибку про `Send`).
- Положить в замыкание-обработчик `Rc`, `RefCell` или ссылку на локальное значение.
- Выбирать маршрут «первый подошёл»: поведение зависит от порядка регистрации.
- Считать Content-Length по символам, а не по байтам.
- Отвечать 404 там, где путь есть, а метод не тот (и забыть `Allow`).
- Отдавать клиенту текст паники или сообщение внутренней ошибки.
- Закрывать сокет сразу после ответа об ошибке, не вычитав остаток запроса.

  когда какой выбрать.
