# HTTP для браузера и больших файлов

Фотохостинг `catpics.example`. Страницы отдаются с одного домена, JSON-API живёт на другом, а пользователи
выкладывают снимки по 8 МБ. Через неделю после запуска приходит письмо от фронтендера: «В консоли CORS error, но сервер
отвечает 200». Ещё через неделю: «Фотку на телефоне не докачать, обрыв связи начинает заново». Ещё через неделю в
журналах появляется запрос `GET /admin`, которого никто не отправлял. Всё это одна история: сервер для браузера и для
больших файлов устроен чуть сложнее, чем сервер для curl. Глава разбирает пять механизмов, которые это закрывают.

## Cookie

Сервер выдаёт cookie заголовком `Set-Cookie: name=value; атрибуты`, браузер хранит и возвращает её заголовком
`Cookie: a=1; b=2` в каждом запросе к тому же сайту. Выдача строгая, возврат терпимый.

Из атрибутов важны пять:

| атрибут | зачем |
|---|---|
| `Max-Age=N` | срок жизни в секундах; `0` значит «удалить»; без него cookie живёт до закрытия браузера |
| `Path=/x` | куда cookie отправляется; по умолчанию путь страницы, выдавшей её |
| `HttpOnly` | JavaScript страницы cookie не видит: кража через XSS становится сложнее |
| `Secure` | только по HTTPS |
| `SameSite=Lax/Strict/None` | отправлять ли cookie на запросы, начатые с чужого сайта (защита от CSRF) |

`Strict` не отправляет cookie вообще никогда при переходе с чужого сайта, `Lax` отправляет только при обычных переходах по
ссылке (GET), `None` отправляет всегда, но браузеры требуют к нему `Secure`. Токен сессии или refresh-токен кладут в cookie
с `HttpOnly`, `Secure` и `SameSite=Lax`.

Префиксы `__Host-` и `__Secure-` в имени это обещания, которые проверяет браузер: `__Host-` соглашается жить
только с `Secure`, `Path=/` и без `Domain`, поэтому поддомен не сможет его перезаписать. Удалить cookie можно только тем
же `Set-Cookie` с `Max-Age=0` и тем же `Path` (и `Domain`), иначе браузер не найдёт, что удалять.

Значение cookie не URL-кодируется само по себе, но в нём нельзя ни пробела, ни кавычки, ни запятой, ни точки с запятой, ни
обратной косой. Всё остальное (JSON, русский текст) нужно кодировать самому, например в base64. А вот на входе
цель обратная: разбирать терпимо, пропускать мусорные пары, не терять остальные, ничему не доверять без проверки.

## CORS

Браузер запрещает JavaScript-у страницы читать ответ с чужого источника (origin: схема, хост, порт вместе).
Запрос при этом уходит и сервер его выполняет, запрещено только чтение. Чтобы разрешить, сервер добавляет в ответ
`Access-Control-Allow-Origin: <origin страницы>`. Это не защита сервера, а согласие, которое проверяет браузер, так что
curl, скрипты и другие серверы про CORS ничего не знают.

```
 страница https://shop.example         API https://api.example
        │ fetch('/orders', {method:'PUT', headers:{Authorization}})
        │
        │ ─── OPTIONS /orders ──────────────────────────────>   (предзапрос: «можно ли мне так?»)
        │     Origin, Access-Control-Request-Method: PUT
        │     Access-Control-Request-Headers: authorization
        │ <── 204, Allow-Origin, Allow-Methods, Allow-Headers, Max-Age
        │
        │ ─── PUT /orders ──────────────────────────────────>   (настоящий запрос)
        │ <── 200, Allow-Origin
        ▼ JavaScript получает ответ
```

Предзапрос браузер шлёт перед «непростыми» запросами: любым методом, кроме GET, HEAD и POST, заголовком `Authorization`,
`Content-Type: application/json` и некоторыми другими. На предзапрос токена нет (браузер его не шлёт), поэтому слой CORS
стоит снаружи слоя авторизации и отвечает сам, не доходя до обработчика.

Три правила, на которых ломаются чаще всего.

**Разрешение нужно на каждом ответе, в том числе на ошибках.** Если у 401 или 500 нет `Allow-Origin`, фронт увидит в консоли
«CORS error» и не узнает настоящий статус. Диагностика превращается в мучение.

**Если в запросах участвуют cookie (`credentials: 'include'`), разрешать надо конкретный origin, не `*`.** Спецификация
запрещает звёздочку вместе с `Access-Control-Allow-Credentials: true`, и браузер просто отбросит ответ.

**`Vary: Origin` нужен всегда, когда ответ зависит от Origin.** Иначе общий кеш (CDN, прокси) запомнит ответ с разрешением
для одного сайта и отдаст его всем, или запомнит ответ без разрешения и отдаст его тому, кому оно положено.
Постоянная звёздочка от Origin не зависит, и Vary ей не нужен.

Сравнение origin точное, строка в строку. `endswith` и `contains` пропускают `https://app.example.evil.com`.

## Условные запросы

Профиль, который запрашивают каждые пять секунд, а меняют раз в неделю: качать его целиком каждый раз незачем. Сервер вместе
с ответом присылает `ETag: "v7"`, отпечаток версии. Клиент в следующем запросе пишет `If-None-Match: "v7"`. Если версия не
изменилась, сервер отвечает `304 Not Modified` без тела, и по сети едет пара сотен байт вместо десятков килобайт.

В `If-None-Match` может быть несколько тегов, слабый тег с префиксом `W/` («по смыслу то же самое») и звёздочка. Для GET
сравнение слабое: `W/` отбрасывается. Заголовок `Cache-Control: no-cache` не запрещает хранить копию, а требует
перед использованием спросить сервер: ровно то, что нужно данным, которые могут измениться. ETag можно строить из чего
угодно, лишь бы разное содержимое давало разные отпечатки: хеш тела, номер версии строки в базе.

## Range и докачка

`Range: bytes=1000-1999` просит кусок файла. Три записи: `A-B` (с A по B включительно), `A-` (с A до конца), `-N` (последние N).
Сервер отвечает `206 Partial Content` с `Content-Range: bytes A-B/ВСЕГО`. Просьба за концом файла получает `416 Range Not
Satisfiable` с `Content-Range: bytes */ВСЕГО`: клиент узнаёт, какой размер у файла на самом деле.

Правило, которое легко забыть: что сервер не понимает в `Range`, он **игнорирует** и отвечает обычным `200` с целым файлом. Много
диапазонов, чужая единица, перевёрнутый диапазон (`5-2`): всё это 200. Отказывать (416) можно только на корректный
запрос, который невозможно выполнить. А в обычном `200` стоит `Accept-Ranges: bytes`, чтобы клиент знал, что докачка возможна.
Так работают перемотка в видео, `curl -C -` и менеджеры загрузки.

## Тело запроса потоком

Аватар 5 МБ, видео 500 МБ. `Vec<u8>` с телом целиком на каждую загрузку означает, что тысяча одновременных
загрузок съест память, и о лимите приходится думать уже после того, как всё прочитано. Поэтому большие тела читают
порциями: читатель знает, по какому правилу тело кончается (`Content-Length` или chunked), отдаёт по куску за раз
(писать в файл, считать хеш, отправлять дальше) и следит за лимитом.

Лимит проверяют вперёд: по заявленному `Content-Length` до первого прочитанного байта, по размеру каждого chunked-куска до того,
как кусок прочитан, и накопительно по сумме, потому что chunked позволяет присылать бесконечно много малых кусков. Остаток
за телом читателю не принадлежит: там уже лежит следующий запрос на этом соединении.

## Недочитанное тело

Обработчик, который ответил `401` до того, как прочитал тело, оставил это тело в соединении. На keep-alive сервер дальше
берётся разбирать «следующий запрос» и разбирает его из середины чужой загрузки. В лучшем случае получается `400`. В худшем
загрузка содержит строку `GET /admin HTTP/1.1`, и сервер её выполнит. Атака называется request smuggling, и защита одна:
тело запроса принадлежит запросу, пока оно не вычитано до конца, и никакой ответ этого не отменяет.

Поэтому после ответа, не читавшего тело, его вычитывают и выбрасывают. Но не любой ценой: клиент может заявить терабайт,
чтобы сервер впустую читал его. Тело больше разумного предела не глотают, а отвечают с `Connection: close` и закрывают
соединение. Решение «держать ли соединение» принимается до записи ответа, потому что о закрытии клиент должен узнать из
заголовка.

## Типичные ошибки

- `Access-Control-Allow-Origin: *` вместе с cookie.
- Разрешение CORS только на успешных ответах.
- Забытый `Vary: Origin`.
- Требовать токен на предзапрос.
- Сравнивать `Origin` по `contains` или `ends_with`.
- Сравнивать весь `If-None-Match` с ETag вместо разбора списка.
- Отвечать 416 на испорченный `Range`, вместо того чтобы его проигнорировать.
- Удалять cookie без правильного `Path`.
- Класть в cookie значения с пробелами и точкой с запятой.
- Читать всё тело в память до проверки лимита.
- Оставлять непрочитанное тело в keep-alive соединении.
