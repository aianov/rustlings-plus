# nhc_client: крейт http-client и утилита fetch

Проверочная задача главы. Кирпичи из задач (адрес, запрос, голова и тело ответа, пул, таймауты, редиректы,
повтор) складываются в крейт `http-client`. Им дальше пользуются интеграционные тесты и маленькие утилиты нашей
соцсети: они ходят в HTTP-сервисы настоящим клиентом, а не руками собранными строками. Рядом с крейтом лежит
консольная утилита `fetch`, похожая на урезанный curl.

## Что уже есть

Каркас крейта и всё, что в главе было разминкой: `src/url.rs` (`parse_url`, `resolve`), `build_request` в
`src/wire.rs`, типы ошибок, `Config`, `Request`, `Response`, определение протухшего соединения (`exchange` в
`src/client.rs`). Остальное падает через `todo!()`. Приёмочные тесты лежат в `tests/acceptance.rs` и восстанавливаются
перед каждой проверкой.

## Что сделать

1. `src/wire.rs`: `parse_head` (инкрементальный разбор головы ответа, `Ok(None)` пока она неполная, предел
   `MAX_HEAD`), `read_body` (chunked, `Content-Length`, до закрытия; остаток буфера не теряется; лимит `max`;
   пара «chunked вместе с длиной» и тело до закрытия делают соединение непригодным) и `read_response` (промежуточные
   `1xx` пропускаются, у ответа на `HEAD`, у `204`, `304` и `101` тела нет, `reusable` означает «соединение чистое»).
2. `src/pool.rs`: `Pool::take` и `Pool::put`: ключ «хост и порт», самое свежее первым, простой считается
   от возврата, просроченные закрываются, лимит на ключ.
3. `Client::send` ставит общий срок `total_timeout` на весь запрос вместе с редиректами и подключением.
   `Client::follow` ходит по редиректам: 301, 302 и 303 меняют метод по правилам главы, 307 и 308 сохраняют
   метод и тело, `Authorization`, `Cookie` и `Proxy-Authorization` не уезжают на другой хост или порт,
   лимит `max_redirects`. `Response::url` это последний адрес, `Response::redirects` число переходов.
4. `Client::send_once` берёт соединение из пула или открывает новое (срок `connect_timeout`), делает обмен,
   чистое соединение возвращает в пул. Протухшее соединение из пула повторяется один раз и только для
   идемпотентного метода. Ошибки: `InvalidData` из чтения становится `Error::Protocol`, остальные `Error::Io`.
5. `get_json` и `post_json`: JSON в запросе и ответе, `Accept` и `Content-Type`. Не 2xx это `Error::Status` с
   текстом тела, непонятный JSON это `Error::Decode`.
6. `src/bin/fetch.rs`: `fetch [-v] [-X МЕТОД] [-d ТЕЛО] [-H 'Имя: значение']... URL`. Тело ответа идёт в stdout
   как есть. Метод по умолчанию GET, а с `-d` без `-X` POST. С `-v` в stderr печатаются строки `> МЕТОД ПУТЬ`,
   `> Host: ...`, `> Имя: значение` для каждого заголовка из `-H`, `< СТАТУС` и `< Имя: значение` для каждого
   заголовка ответа. Код выхода: 0 при статусе ниже 400, 1 при 400 и выше, 2 при ошибке клиента (не
   подключились, таймаут и так далее), 64 при неверных аргументах.

## Критерии приёмки

`cargo test`. Проверяется:

- JSON в обе стороны, правильные заголовки; разные ошибки для статуса, разбора, подключения и неверного адреса;
- одно соединение на много запросов (`idle_connections`), ответы без тела (HEAD, 204, 304) не зависают, `100 Continue`
  пропускается, chunked и тело до закрытия;
- мусор и слишком большое тело это `Error::Protocol`, испорченное соединение в пул не возвращается;
- цепочки редиректов, смена метода, сохранение тела при 307, утечка токена на чужой хост, циклы;
- общий срок обрывает капающий ответ;
- повтор на протухшем соединении для GET и его отсутствие для POST;
- `fetch` печатает тело, объясняется в `-v` и возвращает нужные коды выхода.

## Структура

```
nhc_client/
  Cargo.toml                  пакет http-client (tokio, serde, serde_json, bytes)
  src/lib.rs, url.rs          готово
  src/wire.rs                 build_request готов, три функции твои
  src/pool.rs                 две функции твои
  src/client.rs               пять методов твои, остальное готово
  src/bin/fetch.rs            твоя утилита
  tests/acceptance.rs
```

## Как запускать

`cargo test`, а руками: `cargo run --bin fetch -- -v http://127.0.0.1:8080/health`. Зависимости крейта фиксированы
(`tokio`, `serde`, `serde_json`, `bytes`): готовых HTTP-клиентов (`reqwest`, `hyper`, `ureq`) подключать нельзя.

## Подсказки по теории

README главы: конец тела ответа, три вида ошибок, два срока, редиректы и безопасность, чистота соединения в пуле,
идемпотентность и повтор. Задачи nhc3, nhc4, nhc5 для `wire.rs`, nhc9 для пула, nhc7, nhc8 и nhc11 для клиента.
