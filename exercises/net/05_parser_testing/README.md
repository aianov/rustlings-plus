# Тестирование парсеров

У тебя есть парсер версий вида `1.12.3-beta`, десять тестов с примерами, и все зелёные. Через месяц
выясняется, что строка `1.2.3-` роняет сервис паникой, а `99999999999.0.0` молча превращается в `0.0.0`.
Тесты не врали: они проверяли то, что ты придумал. Баги парсеров живут в том, чего ты не придумал:
в обрезанном вводе, в числах за пределами разумного, в байтах, которые не бывают в строках из учебника.

Парсер читает чужие данные, а чужие данные это противник по определению. Эта глава про инструменты,
которые придумывают входы за тебя: перебор разрезов, случайная генерация, мутации, сжатие находок и
сравнение с эталоном. Всё пишется своими руками, без внешних крейтов: это пара десятков строк на
инструмент, а понимание дороже.

## Почему примеры не хватает

Пример проверяет одну точку из огромного пространства входов. Парсер сетевого протокола ещё и
получает вход кусками: тот же запрос может прийти целиком, по байту, по 5 байт, разрезанным ровно между
`\r` и `\n`. Результат обязан быть одним и тем же. Ручной тест выбирает «удобное» место разреза и
проходит, а баг сидит в неудобном.

## Разрезание во всех точках

Самый дешёвый и самый результативный приём главы. Для входа длиной `n`:

1. прогнать целиком: это эталон;
2. для каждой позиции `1..n` разрезать на два куска и прогнать: результат должен совпасть;
3. прогнать по одному байту: результат должен совпасть.

```
вход:   a b \r \n c d
разрез 3 части:  [a b \r] [\n c d]     <- граница внутри CRLF
```

Смотри визуализацию `split_points`. Тест не знает, где баг, он знает только инвариант: «куски не влияют на
результат». Поэтому баги на границах находятся сами. Заметь, что некоторые баги видны только при
побайтовой подаче (три куска и больше), а некоторые уже при двух: проверять нужно оба режима.

## Случайность, которую можно повторить

Системный генератор даёт случайность, которую нельзя повторить, а упавший тест, который не
воспроизводится, бесполезен. Нужен генератор с seed: одно число полностью определяет последовательность.
В главе ты пишешь splitmix64: состояние это одно `u64`, а каждый вызов прибавляет константу и
перемешивает результат умножениями. Арифметика здесь намеренно переполняется, поэтому в Rust это
`wrapping_add` и `wrapping_mul` (обычный `+` в debug-сборке паникует при переполнении).

Правило воспроизводимости: каждый случай получает **свой** `Rng::new(seed + i)`, а не берёт общий. Сложение простое и в задачах его хватает, но прогоны с соседними seed тогда пересекаются (seed 7, случай 1 это seed 8, случай 0); зрелые инструменты смешивают seed и номер хешем.
Тогда упавший случай номер 41732 можно запустить одним вызовом, не прогоняя 41731 предыдущих, а в отчёте
пишут seed.

Равномерное число в `0..n` нельзя получать как `x % n`: при `n`, не делящем `2^64`, малые остатки выпадают
чуть чаще. Для маленьких `n` перекос ничтожен, для больших заметен. Правильный способ: отбросить самые
верхние числа, которые не укладываются в целое число раз по `n`, и выбрать заново.

## Генераторы и свойства

Генератор строит валидный вход по описанию: «версия это три числа через точку, к ним необязательный
суффикс». Свойство это утверждение о парсере для любого такого входа. Классическое: **туда и обратно**,
`parse(print(x)) == x`. Оно ловит потерянные поля, перепутанный порядок, лишние пробелы, то есть всё, что
парсер делает «по дороге» с данными.

```
for i in 0..1000:
    x = generate(Rng::new(base + i))
    assert parse(print(x)) == x        # при падении сообщи i и сам x
```

Хороший генератор не копирует единственный типичный вход. Он порождает пустые значения, повторы,
максимумы, и ты проверяешь это тестом на разнообразие: все ли варианты встретились, не слиплись ли
тысячи случаев в десяток разных.

## Мутационный фаззинг

Генератор даёт только валидное, а баги живут в соседстве с валидным. Мутационный фаззер берёт хороший
вход (из «корпуса») и портит его по мелочи: переворачивает бит, подменяет байт, вставляет и удаляет,
дублирует кусок, вклеивает кусок другого входа, подставляет «интересные» числа (0, 0xFF, `\r`, `\n`).
Дальше он скармливает результат цели и ловит панику через `std::panic::catch_unwind`.

```rust
let result = catch_unwind(AssertUnwindSafe(|| target(&input)));
if let Err(payload) = result { /* вот падение: input, сообщение */ }
```

Три замечания. Мутации должны быть мелкими: если портить всё сразу, вход перестаёт быть похожим на
валидный, и фаззер ходит по одной ветке «отказ». Должно быть и валидное, и невалидное. Каждая итерация
выводится из `(seed, номер)`, чтобы падение воспроизводилось. И `catch_unwind` не ловит `abort` и зависания:
бесконечный цикл цели остановится только таймаутом уровнем выше, а бюджет фаззера (число итераций, время)
проверяется между итерациями.

## Сжатие находки

Фаззер нашёл падение на входе в 4000 байт. Читать его нельзя, нужен минимум, на котором ошибка всё
ещё есть. Сжатие (shrinking) в духе delta-debugging: пробуй выбросить половину входа, потом четверть,
потом восьмую, и так до одного байта; выброс, после которого цель всё ещё падает, оставляй.
Смотри визуализацию `shrink_loop`. Большие куски убирают сразу, поэтому на входе в миллион байт нужны сотни проверок,
а не миллион. В конце упрощают оставшиеся байты (заменяют на `a`, если падение сохраняется), и получается
читаемый минимум.

Ловушка: предикат «цель падает» легко подменить другим багом. Если сжатие превращает падение «выход за
границы» в падение «деление на ноль», ты сжал в соседнюю ошибку. Сравнивай причину (сообщение паники).
Найденный минимум сохраняй как обычный регрессионный тест.

## Дифференциальный тест

Если есть медленная, но очевидно верная реализация (эталон), быстрая сравнивается с ней на тех же входах,
и любое расхождение это баг в одной из них. Паника тоже исход: «эталон вернул ошибку, быстрая упала»
считается расхождением. Сравнивать надо контракт (значение или факт ошибки), а не тексты сообщений.
Найденное расхождение сжимают тем же `shrink`.

## Типичные паники парсеров

Фаззер на парсерах постоянно находит одно и то же. Запомни, чтобы не писать:

- `a * 16 + digit` над числом из сети: переполнение (в debug паника, в release тихая порча). Нужны
  `checked_mul` и `checked_add`;
- `&text[..n]` по байтовому индексу: паника, если `n` попало в середину многобайтного символа. Режь по
  символам (`chars().take(n)`) или проверяй `is_char_boundary`;
- `total - consumed` при `consumed > total`: вычитание ниже нуля. Сначала сравни;
- `Vec::with_capacity(len)` по длине из заголовка (см. прошлые главы);
- индексация `buf[i + 1]` без проверки, что байт пришёл;
- рекурсия по вложенности без лимита глубины.

## Типичные ошибки

- Резать вход только в «удобных» местах.
- Random без seed или с seed, который не напечатан.
- Один общий `Rng` на весь прогон: упавший случай не восстановить.
- Генератор, который порождает только типичное.
- Сжатие, которое проверяет «падает» вместо «падает так же».
- Сравнивать в дифф-тесте тексты ошибок.
- Забыть, что `catch_unwind` не спасёт от зависания.
