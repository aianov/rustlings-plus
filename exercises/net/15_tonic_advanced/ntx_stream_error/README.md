# ntx_stream_error: экспорт, который оказался неполным

Выгрузка постов в файл: клиент просит десять тысяч строк, сервер шлёт их потоком. На четвёртой тысяче источник данных упал. Получилась тихая
катастрофа: в файле три тысячи девятьсот девяносто девять строк, никто не заметил, отчёт посчитан по неполным данным. Весь вопрос в том,
**чем отличается нормальный конец потока от аварийного**, и что именно увидит клиент.

## Что сделать

В `src/lib.rs` есть сервер экспорта (если `fail_at = Some(k)`, источник «падает» на строке `k`) и клиентский помощник `collect_rows`.
Запусти тесты: в обеих половинах есть дефект. Исправь так, чтобы:

1. сервер, у которого упал источник, сообщал об этом клиенту ошибкой в потоке: код `Unavailable`, а не молчаливым завершением;
2. клиент, получивший ошибку посреди потока, возвращал `ExportError::Truncated { got, cause }` (сколько строк успел получить и какая ошибка),
   а не список строк, как будто всё хорошо;
3. ошибку самого вызова (до первой строки) клиент отдаёт как `ExportError::Failed(status)`, как и раньше.

## Критерии приёмки

`cargo test`: сервер проверяется «сырым» клиентом (последний элемент потока ошибка); клиентский помощник проверяется против поддельного сервера,
который шлёт три строки и `DataLoss`; успешный экспорт даёт все строки; обе половины вместе.

## Подсказки по теории

В gRPC у потока ответа два конца. Нормальный: сервер вернул из обработчика, трейлеры содержат `grpc-status: 0`, клиент видит `Ok(None)`. Аварийный: в трейлерах
ненулевой статус, и клиент видит `Err(status)` вместо следующего сообщения. Если серверная задача просто тихо вышла и закрыла канал, клиент не
отличит это от нормального конца.
