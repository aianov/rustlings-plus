# ntx_server_stream: лента, которая сама приходит

Клиент открывает приложение и хочет, чтобы новые события появлялись без обновления страницы. Вызов, который отвечает один раз, для этого не годится:
нужно, чтобы сервер мог писать в ответ много раз, пока вызов открыт. Это **server streaming**: клиент присылает один запрос, а в ответ получает поток
сообщений, который сервер закрывает сам или который обрывается ошибкой.

## Что сделать

В `src/lib.rs` есть `Hub`: рассылка событий всем подписчикам (внутри `tokio::sync::broadcast`) и счётчик `subscribers()`. Допиши
`Feed::subscribe`:

1. подписка на хаб оформляется **до** возврата из обработчика: события, опубликованные сразу после того, как клиент получил поток, не должны теряться;
2. клиенту уходят только события его `user_id`, в том порядке, в каком они были опубликованы;
3. когда клиент закрыл поток, подписка на хаб снимается **сразу**, даже если новых событий больше нет;
4. если подписчик отстал от рассылки так, что хаб выбросил события (`RecvError::Lagged`), он получает ошибку `DataLoss` и поток закрывается:
   молча пропустить сообщения нельзя.

## Критерии приёмки

`cargo test`: фильтрация и порядок; сто событий сразу после открытия потока доходят все; после `drop` потока число подписчиков хаба падает до
нуля без единого нового события; два подписчика одного пользователя получают одно и то же.

## Подсказки по теории

Поток ответа это любой `Stream<Item = Result<T, Status>>`. Обычный способ собрать его вручную: канал `mpsc` и обёртка `ReceiverStream`. Конец потока
получается сам, когда отправитель сброшен. Клиент, закрывший вызов, это закрытый приёмник: у отправителя `closed()` завершается, а `send` возвращает ошибку.
