# UDP: датаграммы без соединения

Метеостанция на крыше шлёт коллектору температуру раз в секунду. Потерялось одно показание из
шестидесяти? Не страшно, через секунду придёт следующее. Заводить ради этого TCP с рукопожатием,
повторами и ожиданием на каждый потерянный пакет значит платить за гарантию, которая станции не
нужна. Для такого случая и придуман UDP: отправил и забыл.

UDP это тонкая обёртка над IP. У него нет соединения, нет потока, нет порядка, нет повторных
отправок. Зато есть порты (чтобы несколько программ на одной машине не мешали друг другу),
контрольная сумма (повреждённый пакет выбросят) и **границы сообщений**.

```
TCP:  [ поток байтов .................................................. ]
UDP:  [ пакет 1 ]   [ пакет 2 ]        [ пакет 3 ]      пакет = одно сообщение, целиком
```

## Сокет, который ни с кем не связан

```rust
let socket = UdpSocket::bind("0.0.0.0:0").await?;       // порт 0: любой свободный
socket.send_to(b"T=21.5", "10.0.0.7:9000").await?;      // кому отправить, указываем каждый раз

let mut buf = [0u8; 2048];
let (n, from) = socket.recv_from(&mut buf).await?;      // и узнаём, от кого пришло
```

Нет `accept` и нет «принятого» сокета на клиента: один сокет получает пакеты от всех сразу, а
отличает собеседников по адресу `from`. Ответить значит `send_to(.., from)` с этого же сокета. `bind` на
порт 0 просит систему выбрать свободный порт, поэтому для клиента он годится.

Что важно в `recv_from`: возвращённое `n` это длина **этой** датаграммы, и пустая датаграмма
(`n == 0`) совершенно законна. В TCP ноль означал «собеседник закончил», здесь это просто пустое
сообщение. Конца у UDP нет вообще.

## Что UDP делает с сообщениями

Сеть между двумя сокетами может сделать с пакетами вот что, и приложение узнает о происшедшем,
только если это предусмотрело:

```
отправлено:   1   2   3   4   5
пришло:       1   3   2   2       5?      потеря (4), перестановка (3 и 2), дубль (2), опоздание (5)
```

Рассмотри визуализацию `udp_vs_tcp`: те же пять сообщений по обоим протоколам. На loopback на
машине всё почти всегда проходит идеально, и это обманчиво: код, который «работает» локально, на
живой сети начинает терять данные. Поэтому проверять надо нарочно испорченной сетью (в тестах
главы сервер сам теряет и задваивает пакеты).

Два следствия, которые надо знать назубок:

**Размер.** Датаграмма до 65 507 байт теоретически, но уже после примерно 1472 байт (MTU Ethernet 1500
минус заголовки) ядро разбивает её на фрагменты IP, и потеря любого куска означает потерю всего
сообщения. Поэтому в реальных протоколах сообщение стараются держать меньше 1200 байт (консервативный безопасный размер, его берёт QUIC).

**Буфер.** Если буфер `recv_from` меньше пришедшей датаграммы, ядро кладёт в него начало, а
остаток выбрасывает **молча**. Следующий вызов прочитает уже следующую датаграмму, а не остаток. (На Windows вместо молчаливого обрезания будет ошибка, поэтому
полагаться на это поведение нельзя.)
Ядро о превышении не сообщает, поэтому узнавать о нём приходится самому: как именно, придумай сам (ответ в подсказке к `nudp3`).

## connect у UDP

```rust
let socket = UdpSocket::bind("0.0.0.0:0").await?;
socket.connect("10.0.0.7:9000").await?;     // по сети ничего не уходит
socket.send(b"T=21.5").await?;               // адрес больше не нужен
let n = socket.recv(&mut buf).await?;
```

Этот `connect` не устанавливает соединения: он записывает в ядро «мой собеседник вот он». Что
меняется:

- пакеты от других адресов ядро отбрасывает, и случайная или подделанная чужая датаграмма не
  попадёт в программу;
- если в ответ на отправку пришёл ICMP «порт недоступен» (на том конце никто не слушает), этот
  сигнал превращается в ошибку `ConnectionRefused` на следующем `send`/`recv`. Без `connect` ты
  его никогда не увидишь, и клиент будет ждать вечно;
- можно писать `send` и `recv`, не таская адрес.

Для сервера, который говорит со многими, `connect` не годится: ему нужен `recv_from`. Для клиента,
который говорит с одним, почти всегда уместен.

## Надёжность это твоя забота

Нужна гарантия доставки? Строй её сам, а вот из чего она состоит:

1. **Таймаут и повтор.** Отправил, ждёшь не дольше `T`, молчание значит «повторяю». Число попыток
   ограничено.
2. **Номера.** Каждый запрос получает номер, ответ его возвращает. Тогда запоздавший ответ прошлого
   вызова, дубль и чужой пакет отличаются от нужного ответа.
3. **Идемпотентность.** Если ответ потерялся, повтор доставит запрос второй раз. Операции, которые
   нельзя выполнять дважды (списание, заказ), требуют id, а сервер должен помнить, что уже делал.
4. **Срок на весь вызов, а не на одно чтение.** Читая в цикле и выбрасывая чужое, считай дедлайн
   один раз (`tokio::time::timeout_at`), иначе поток мусора продлит ожидание до бесконечности.

В tokio каждый `recv` можно обернуть в `tokio::time::timeout(d, socket.recv(&mut buf))`: результат
это `Result<io::Result<usize>, Elapsed>`, и два слоя ошибок нельзя путать. Таймаут означает
«ничего не пришло», а `io::Error` внутри означает «сокет сломан».

Для пинга, где важно, сколько пакетов ушло, пришло, опоздало или задвоилось, нужно ждать сразу
двух событий: «время слать следующий» и «что-то пришло». Это `tokio::select!` с `interval` и
`recv`. Следи за тем, что `interval` первым тиком срабатывает сразу, и что у веток можно ставить
условие: `ветка = future, if условие => ...`.

## Где UDP живёт

- **DNS.** Вопрос и ответ помещаются в один пакет, повтор по таймауту делает клиент.
- **Метрики и логи** (statsd и подобные): потеря одного значения не стоит соединения.
- **Игры и звонки.** Позиция игрока 50 раз в секунду: старая уже не нужна, и ждать её повтора
  вредно. Нужен только самый свежий номер.
- **QUIC и HTTP/3.** Надёжность, порядок и шифрование строятся поверх UDP, потому что своя
  реализация в пространстве приложения быстрее эволюционирует, чем TCP в ядрах.

## Типичные ошибки

- Принять первый пришедший пакет за ответ: не проверили ни адрес, ни номер.
- Читать буфер, равный размеру сообщения: слишком длинное молча режется.
- Считать `n == 0` концом: это просто пустое сообщение.
- Один таймаут на весь цикл чтения в одном месте и новый на каждую итерацию в другом: ожидание
  то обрывается слишком рано, то не кончается.
- Повторять без предела или пачкой за один раз.
- Обрабатывать повтор как новый запрос там, где действие нельзя выполнять дважды.
- Проверять код только на loopback без потерь.
