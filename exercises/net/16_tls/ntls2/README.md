# ntls2: читаем PEM и понимаем, что с ним не так

Сервис запускается и должен прочитать два файла: цепочку сертификатов и закрытый ключ. Типичные поломки: файл пуст (забыли смонтировать секрет), в нём не то (в `server.pem` лежит ключ), он обрезан при копировании,
сертификат от одного ключа, ключ от другого. С голой ошибкой `unexpected end of file` на старте в три часа ночи разобраться трудно. Хорошая загрузка называет причину по-человечески.

## Что сделать

В `src/lib.rs` перечисление `TlsError` с текстами для людей уже готово. Допиши:

1. `load_certs(pem)`: все сертификаты из PEM-данных в порядке файла (первым сертификат сервера, дальше промежуточные).
   Ни одного сертификата (пустой файл, текст без PEM-блоков, в файле только ключ) это `NoCertificates`. Блок, который начат, но повреждён (обрезан, плохой base64) это `BadPem`.
2. `load_key(pem)`: закрытый ключ из PEM. Ключа нет (в файле только сертификат, файл пуст) это `NoPrivateKey`. Повреждённый блок это `BadPem`.
3. `server_config(cert_pem, key_pem)`: собирает `ServerConfig` без проверки клиентов. Если ключ не от этого сертификата: `KeyMismatch`.

## Критерии приёмки

`cargo test`: цепочка из двух сертификатов читается в порядке файла; пустые и мусорные файлы, обрезанные блоки, сертификат вместо ключа и ключ вместо сертификата дают свои ошибки; чужой ключ даёт `KeyMismatch`; собранный конфиг действительно проходит рукопожатие.

## Подсказки по теории

PEM это текст: между строками `-----BEGIN ...-----` и `-----END ...-----` лежит base64 от DER. В одном файле таких блоков может быть несколько. Библиотека `rustls-pki-types` умеет читать их типизированно:
у типов `CertificateDer` и `PrivateKeyDer` есть методы разбора PEM через трейт `PemObject`.
