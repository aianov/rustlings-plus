# ntls_mtls: сервисы доверяют друг другу по сертификатам

Шлюз зовёт сервис постов. До сих пор сервис постов верил любому, кто смог добраться по сети. Теперь между сервисами нужен mTLS: у каждого сервиса свой сертификат от общего CA, сервис постов принимает вызовы только от шлюза,
а сами сертификаты не лежат в репозитории и выпускаются одной командой. Это то, из чего состоит шифрование между сервисами соцсети в курсе.

## Что уже есть

Воркспейс с тремя крейтами. `crates/proto` готов (схема `posts.v1`). В `crates/posts-service` лежит готовый `identity.rs` (чтение имён из SAN) и приёмочные тесты, а в `crates/certgen` только тесты. Остальное пишешь ты.

## Что сделать

**`crates/certgen`** (библиотека на `rcgen`):

1. `issue_all(dir)`: создаёт каталог и пишет в него `ca.pem`, `ca.key` и для каждого сервиса `gateway`, `posts`, `users` по паре `<имя>.pem` и `<имя>.key`. Сертификат сервиса выпущен CA, в SAN у него `<имя>.social.test`, а ещё `localhost` и `127.0.0.1`. Сертификаты шлюза и клиентов
   помечены для клиентской аутентификации, сертификат сервиса постов ещё и для серверной (а у остальных назначение любое из двух). Все `.key` доступны только владельцу (`0600`).
2. `ensure_gitignore(repo_root)`: гарантирует, что в `.gitignore` корня репозитория есть строка `certs/`. Файла нет: создаётся. Строка уже есть: ничего не меняется (второй вызов не дублирует). Другие строки сохраняются.

**`crates/posts-service`**:

3. `serve(listener, certs_dir)`: загружает `ca.pem`, `posts.pem`, `posts.key` из каталога и поднимает gRPC-сервер `Posts` под mTLS: клиент обязан предъявить сертификат, подписанный этим CA.
4. Вызывать методы может только шлюз: у клиентского сертификата в SAN должно быть `gateway.social.test`. Сертификат с другим именем (например, `users.social.test`) даёт `PermissionDenied`, хотя рукопожатие и прошло: CA один.

## Критерии приёмки

`cargo test --workspace`: файлы и права после `issue_all`; `ensure_gitignore` идемпотентен и не теряет чужих строк; шлюз получает пост; клиент с сертификатом сервиса пользователей получает `PermissionDenied`; клиент без сертификата и клиент с сертификатом
другого CA не подключаются; клиент проверяет сервер по имени `posts.social.test`, и имя `users.social.test` не проходит.

## Структура

```
ntls_mtls/
  crates/proto/                        готово
  crates/certgen/src/lib.rs            твой
  crates/posts-service/src/lib.rs      твой
  crates/posts-service/src/identity.rs готово
```

## Подсказки по теории

Рукопожатие mTLS отвечает на вопрос «этот клиент есть в нашей системе», а не «этому клиенту можно это делать». Второй вопрос решается отдельно, по имени из сертификата. В tonic сертификаты клиента доступны через `request.peer_certs()` (в обработчике и в перехватчике).
