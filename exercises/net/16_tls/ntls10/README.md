# ntls10: взаимная проверка

Обычный TLS проверяет только сервер: любой клиент, знающий адрес, может подключиться. Внутри системы этого мало. Сервис постов должен пускать к себе шлюз и ещё два-три доверенных сервиса, а не всех, кто попал в сеть. В **mTLS**
(взаимный TLS) проверка идёт в обе стороны: сервер требует от клиента сертификат, выданный его CA, и без него не говорит. Личность клиента при этом доказывается не паролем и не токеном, а ключом, который не покидает клиента.

## Что сделать

В `src/lib.rs`:

1. `server_config(cert_pem, key_pem, client_ca_pem)`: сервер предъявляет свой сертификат и **требует** от клиента сертификат, подписанный `client_ca_pem`. Нечитаемый PEM, пустой список доверия клиентам и неподходящая пара сертификат с ключом это ошибки.
2. `client_config(server_ca_pem, identity)`: клиент доверяет серверному CA и, если передана пара `(сертификат, ключ)`, предъявляет её серверу. Без пары это обычный клиент, и сервер его отвергнет.

## Критерии приёмки

`cargo test`: клиент с сертификатом нужного CA получает эхо; клиент без сертификата, с сертификатом чужого CA, с просроченным сертификатом и с серверным сертификатом (не для клиентов) получает отказ; клиент, не доверяющий серверу, отказывается сам.

## Подсказки по теории

Проверкой клиентских сертификатов на сервере занимается `WebPkiClientVerifier`. Его строят из хранилища доверенных корней, и вместо `with_no_client_auth()` подставляют `with_client_cert_verifier(..)`.
Клиент предъявляет сертификат вызовом `with_client_auth_cert(цепочка, ключ)`.

Обрати внимание, что в TLS 1.3 клиент считает рукопожатие успешным раньше, чем сервер проверил его сертификат. Отказ сервера обычно проявляется при первом чтении или записи, а не в `connect`. Поэтому тесты проверяют целый обмен.
