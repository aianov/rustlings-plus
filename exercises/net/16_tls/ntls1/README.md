# ntls1: свой удостоверяющий центр

Для внутренних сервисов не нужен публичный CA: сервисы доверяют одному вашему корневому сертификату, и им не нужны ни Let's Encrypt, ни интернет. Свой CA это пара «сертификат и закрытый ключ», которой
подписывают сертификаты остальных. В этой задаче ты напишешь маленький центр сертификации на `rcgen`: выпустишь CA, сертификат сервера с нужными именами, и запишешь файлы так, чтобы закрытый ключ не лежал на виду.

## Что сделать

В `src/lib.rs`:

1. `Ca::new(common_name)`: самоподписанный сертификат центра. Это именно **CA**: ему разрешено подписывать другие сертификаты.
2. `Ca::cert_pem()`: сертификат CA в PEM (его раздают всем клиентам).
3. `Ca::issue_server(names)`: сертификат сервера для перечисленных имён, подписанный этим CA. Имена могут быть DNS-именами (`localhost`) и IP-адресами (`127.0.0.1`): клиент проверяет имя, к которому подключился, по этому списку (SAN).
   Сертификат сервера не должен быть CA. Возвращает `Leaf` с сертификатом и закрытым ключом в PEM.
4. `write_pems(dir, ca, leaf)`: пишет в каталог ровно три файла: `ca.pem`, `server.pem`, `server.key`. Ключ сервера доступен только владельцу (на Unix права `0600`). Закрытого ключа CA в каталоге быть не должно: он остаётся в памяти.

## Критерии приёмки

`cargo test`: настоящий TLS-обмен между сервером и клиентом (через `tokio::io::duplex`, без сокетов): клиент, доверяющий CA, подключается к `localhost` и к `127.0.0.1`; к чужому имени не подключается; чужой CA не доверен;
в сертификатах правильные SAN и флаг CA; файлы лежат с правильными правами.

## Подсказки по теории

Сертификат связывает имя и открытый ключ подписью издателя. Клиент строит цепочку от сертификата сервера до корня, которому доверяет, и проверяет: подпись, срок, назначение и то, что имя из запроса есть в SAN. Пока CA не помечен
как CA, подписывать им нельзя. Подробнее в README главы.
