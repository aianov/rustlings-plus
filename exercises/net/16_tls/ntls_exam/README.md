# Экзамен: сборщик метрик

Сервису нужен свой сборщик метрик. Приложения шлют ему числа по UDP в формате statsd (быстро, без ожидания ответа, потери допустимы), Prometheus раз в 15 секунд забирает сводку по HTTP,
а дежурные ходят в административный gRPC, чтобы посмотреть конкретную метрику или сбросить её. Всё в одном процессе, один набор данных, три порта. Подсказок нет, это экзамен по всему разделу: UDP, свой HTTP,
gRPC на tonic с токеном и стримом, TLS, здоровье и мягкая остановка.

## Что надо создать

Папка пуста, кроме приёмочного теста. Создай сам:

```
ntls_exam/
  Cargo.toml                     один пакет `metricsd` со своим [workspace]
  build.rs                       сборка .proto
  proto/metrics/v1/metrics.proto схема из этого файла (ниже), без изменений
  src/lib.rs                     решение
  tests/acceptance.rs            приёмочные тесты (уже лежат, менять нельзя)
```

Редакция 2024. Зависимости ровно такие:

```toml
[dependencies]
tonic = { version = "=0.14.6", features = ["tls-ring"] }
tonic-prost = "=0.14.6"
tonic-health = "=0.14.6"
prost = "=0.14.4"
tokio = { version = "1", features = ["full"] }
tokio-stream = { version = "0.1", features = ["net"] }

[build-dependencies]
tonic-prost-build = "=0.14.6"

[dev-dependencies]
rcgen = { version = "=0.13.2", default-features = false, features = ["ring", "pem"] }
```

Другие крейты не нужны. Нужен `protoc`.

## Схема gRPC

```proto
syntax = "proto3";

package metrics.v1;

service Admin {
  rpc Get (GetRequest) returns (Metric);
  rpc List (ListRequest) returns (stream Metric);
  rpc Reset (ResetRequest) returns (ResetReply);
}

message GetRequest { string name = 1; }
message ListRequest { string prefix = 1; }
message ResetRequest { string name = 1; }
message ResetReply {}

enum Kind {
  KIND_UNSPECIFIED = 0;
  KIND_COUNTER = 1;
  KIND_GAUGE = 2;
  KIND_TIMER = 3;
}

message Metric {
  string name = 1;
  Kind kind = 2;
  double value = 3;
  uint64 count = 4;
}
```

## Открытый интерфейс

Тесты используют ровно это, имена и сигнатуры менять нельзя.

```rust
pub mod pb { tonic::include_proto!("metrics.v1"); }

#[derive(Clone)]
pub struct Config { pub admin_token: String, pub cert_pem: String, pub key_pem: String }

pub struct Running { pub udp: SocketAddr, pub http: SocketAddr, pub grpc: SocketAddr, /* что угодно ещё */ }

pub async fn start(config: Config) -> std::io::Result<Running>;
impl Running { pub async fn shutdown(self); }
```

`start` занимает три порта на `127.0.0.1` (порт 0, то есть свободные), запускает сервис в фоне и возвращает адреса. `shutdown` останавливает всё и возвращается, когда всё остановилось.

## Требования

**1. UDP, формат statsd.** В датаграмме строки, разделённые `\n` (в конце строки может быть `\r`). Пустые строки пропускаются. Строка: `имя:значение|тип`.

| тип | значение | эффект |
|-----|----------|--------|
| `c` | целое со знаком (`i64`) | счётчик: значения складываются (с насыщением) |
| `g` | число (`f64`) | датчик: без знака в записи значение задаёт, со знаком `+` или `-` меняет текущее (`g:10`, затем `g:+5`, затем `g:-3` даёт 12). Знак у несуществующего датчика считается от нуля |
| `ms` | неотрицательное число | замер времени: растут число замеров и сумма |

Имя: от 1 до 100 символов из `A-Z a-z 0-9 _ .`. Любая другая строка (нет `:` или `|`, плохое имя, нечисло, `NaN`, бесконечность, неизвестный тип, лишние части после типа вроде `|@0.5`, отрицательный замер, тип не совпал с типом уже существующей метрики) это плохая строка: она не применяется, но считается. Остальные строки датаграммы применяются как обычно.
Датаграмма с неверным UTF-8 не роняет сервис: её строки с мусором просто плохие. Датаграммы больше 2048 байтов можно обрезать.

**2. Лимит имён.** Различных имён не больше 1000. Строки с новым именем сверх лимита не применяются и считаются отдельным счётчиком «отброшенных имён»; уже известные имена продолжают обновляться.

**3. HTTP.** Свой простой сервер HTTP/1.1 на отдельном порту (готовых HTTP-крейтов нет). Одно соединение один запрос, ответ всегда с `Connection: close`, `Content-Length` и `Content-Type: text/plain; version=0.0.4; charset=utf-8`.

- `GET /metrics` (строка запроса `?...` после пути игнорируется): сводка. Метрики идут по алфавиту исходных имён, `.` в именах заменяется на `_`. Формат:

  ```
  # TYPE <имя> counter
  <имя>_total <целое>
  # TYPE <имя> gauge
  <имя> <число>
  # TYPE <имя> summary
  <имя>_count <целое>
  <имя>_sum <число>
  ```

  Числа с плавающей точкой печатаются как `{}` в Rust (`512`, `350.5`). После всех метрик два служебных счётчика: `statsd_bad_lines_total` и `statsd_dropped_names_total`, оба в формате `# TYPE <имя> counter` и строки `<имя> <целое>` (без добавочного `_total`, у них оно уже в имени).
- `GET /healthz`: `200`, тело `ok\n`.
- Любой другой путь: `404`. Известный путь с другим методом: `405` с заголовком `Allow: GET`.
- Строка запроса не из трёх частей или версия не `HTTP/1.0` и `HTTP/1.1`: `400`.
- Голова запроса (до пустой строки) длиннее 8 КиБ: `431`. Ответ об ошибке не должен теряться из-за недочитанного хвоста запроса.
- Клиент, не закончивший голову за 2 секунды (или подключившийся и молчащий), получает `408` и закрытие. Он не должен мешать остальным ни секунды.

**4. gRPC-администрирование.** Сервис `metrics.v1.Admin` на отдельном порту, только по **TLS** (сертификат и ключ приходят в `Config`). Каждый вызов обязан нести заголовок `authorization: Bearer <admin_token>`, иначе `Unauthenticated`.
Сервис здоровья (`grpc.health.v1`) открыт без токена; состояние `metrics.v1.Admin` в начале `SERVING`.

- `Get(name)`: метрика; плохое имя это `InvalidArgument`, неизвестная `NotFound`. В `Metric` поле `value`: счётчик его сумма, датчик значение, таймер сумма замеров; `count`: у таймера число замеров, у остальных 0.
- `List(prefix)`: поток метрик, имя которых начинается с префикса, по алфавиту (снимок на момент вызова).
- `Reset(name)`: метрика удаляется (в `/metrics` её больше нет). Плохое имя `InvalidArgument`, неизвестная `NotFound`.

**5. Остановка.** `shutdown`: сначала состояние `metrics.v1.Admin` становится `NOT_SERVING`, после короткой паузы (100 мс) gRPC-сервер перестаёт принимать новое и дорабатывает идущее. HTTP перестаёт принимать новые соединения, но дообслуживает уже принятые (до 3 секунд). UDP перестаёт читать.
После возврата из `shutdown` порты HTTP и gRPC закрыты, а датаграммы на UDP-порт не вызывают паник.

**6. Эксплуатация.** Одно хранилище метрик на все три входа, обновления потокобезопасны. Тысячи датаграмм от нескольких отправителей не теряются из-за самого сервиса. Паника или ошибка одного соединения не влияет на остальные.
