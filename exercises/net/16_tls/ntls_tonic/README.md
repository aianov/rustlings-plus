# ntls_tonic: gRPC по TLS

Для gRPC шифрование включается настройками `Endpoint` и `Server`, а не кодом рукопожатия: tonic сам делает работу, которую в предыдущих задачах делал ты. Зато настроек несколько, и каждую можно перепутать так, что всё либо не подключится
вообще, либо подключится без проверки. В этой задаче сервер настроен, а клиент написан неправильно: вызовы не проходят.

## Что сделать

В `src/lib.rs` `serve_tls` уже запускает сервис пользователей под TLS, а `client_channel(addr, ca_pem, domain)` строит канал клиента. Запусти тесты и найди, что в клиенте не так. Дефектов два, каждый ловится своим тестом. Исправь так, чтобы:

1. клиент действительно говорил по TLS;
2. проверка сертификата шла по имени `domain` (а не по адресу подключения): сервис доступен по IP, а сертификат выписан на имя;
3. сертификат с чужого CA, с чужим именем и не-TLS подключение не проходили.

## Критерии приёмки

`cargo test`: вызов по TLS проходит; тест с сертификатом, выписанным только на имя `users.social.test` (подключение идёт по `127.0.0.1`), проходит при `domain = "users.social.test"` и не проходит с другим именем; чужой CA не доверен; клиент, говорящий открытым текстом, не получает ответа.

## Подсказки по теории

Схема адреса определяет, пойдёт ли соединение через TLS: `https://` включает его, `http://` нет, и настройки TLS к открытому соединению молча не применяются. Имя для проверки задаётся в `ClientTlsConfig::domain_name`;
если его не задать, tonic берёт имя из адреса. На сервере `ServerTlsConfig` получает `Identity` (сертификат и ключ), а для mTLS ещё и CA для проверки клиентов.
