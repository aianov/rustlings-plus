# ntn_status: пользователь не найден или сервис упал

В gRPC у ошибки нет тела, как в HTTP, есть код `Status` и сообщение. Клиент решает, что делать дальше, по коду: «не найден» это
нормальный ответ, который надо показать пользователю, «недоступен» это повод повторить вызов, «неверный аргумент» это баг
вызывающего. Если сервер на всё отвечает `Internal`, клиент не отличит первое от последнего.

## Что сделать

В `src/lib.rs` сервис пользователей и два помощника для клиента.

**Сервер**

- `get_user`: неизвестный номер это `NotFound`, в сообщении есть номер.
- `create_user`: ник от 3 до 20 символов из `A-Z a-z 0-9 _`, иначе `InvalidArgument`, и в сообщении названо поле `handle`.
  Ник уникален без учёта регистра: `Ann` занят, если есть `ann`, тогда `AlreadyExists`. Сохраняется ник так, как его написали.

**Клиент**

- `find_user(client, id) -> Result<Option<User>, Status>`: `NotFound` превращается в `Ok(None)`, остальные ошибки возвращаются как есть.
  «Пользователя нет» это не поломка, а `Unavailable` это именно поломка, и скрывать её нельзя.
- `register(client, handle) -> Result<Registration, Status>`: `AlreadyExists` превращается в `Registration::HandleTaken`, всё остальное
  (включая `InvalidArgument`) возвращается как есть.

## Критерии приёмки

`cargo test`: коды сервера проверяются настоящим клиентом по сети; `find_user` и `register` проверяются против поддельного сервера,
который отвечает заданным кодом, и ни один код не должен потеряться по дороге.

## Подсказки по теории

`Status::code()` возвращает `tonic::Code`, а `message()` текст. Коды выбирай по смыслу, а не по привычке: `NotFound` когда сущности нет,
`InvalidArgument` когда аргумент плох независимо от состояния системы, `AlreadyExists` когда конфликт с тем, что есть, `Unavailable`
когда стоит повторить позже.
