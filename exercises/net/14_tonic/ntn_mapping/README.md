# ntn_mapping: на границе сервиса

Всё, что приходит по gRPC, это сообщение protobuf, у которого любое поле может быть нулём, пустой строкой или числом, которого
нет в перечислении (клиент новее сервера). Внутри сервиса такие значения жить не должны: домену нужны типы, в которых
невозможное невозможно. Превращать одно в другое надо на границе, один раз, и оттуда же возвращать клиенту понятную ошибку.

## Что сделать

В `src/lib.rs` доменные типы `AuthorId` (ненулевое число), `Visibility` и `NewPost` уже описаны, обработчик `create_post` вызывает
`NewPost::try_from(request)`. Допиши два преобразования:

1. `TryFrom<pb::CreatePostRequest> for NewPost` с ошибкой `Status`. Правила:
   - `author_id` равен 0: `InvalidArgument`, в сообщении `author_id`;
   - текст после обрезки пробелов по краям пуст или длиннее 280 **символов**: `InvalidArgument`, в сообщении `text`.
     В домен попадает обрезанный текст;
   - `visibility` не `PUBLIC` и не `FOLLOWERS` (в том числе `UNSPECIFIED` и число, которого в перечислении нет):
     `InvalidArgument`, в сообщении `visibility`.
2. `post_to_proto(id, &NewPost) -> pb::Post`: обратное направление, уже без ошибок.

## Критерии приёмки

`cargo test`: каждый тип плохого ввода отдельным тестом, в том числе 280 русских букв (проходят) и 281 (нет); весь путь через
настоящего клиента по сети.

## Подсказки по теории

В сгенерированной структуре перечисление хранится как `i32`. Метод `Visibility::try_from(i32)` вернёт ошибку для неизвестных
значений, а геттер `request.visibility()` молча подставит значение по умолчанию. Для границы нужен первый, иначе плохой ввод
сойдёт за `UNSPECIFIED` без единого предупреждения.
