# gRPC на tonic

Склад интернет-магазина: сервис заказов должен узнать у сервиса остатков, сколько штук товара осталось. Если описать это ручным HTTP+JSON,
придётся договариваться обо всём сразу: какой путь, какие поля в теле, как называется поле с ошибкой, что вернуть на «товара нет» и
чем отличить «товара нет» от «склад лёг». Через полгода окажется, что заказы считают остаток целым числом, а склад начал отдавать
дробные килограммы.

gRPC забирает эти договорённости в схему. Описываешь вызов один раз, в `.proto`:

```proto
service Stock {
  rpc GetItem (GetItemRequest) returns (Item);
}
```

Из схемы генерируются клиент и каркас сервера на Rust, а на проводе работает то, что ты разобрал в двух прошлых главах: protobuf в
теле, HTTP/2 в качестве транспорта, статус вызова в трейлерах. Библиотека для всего этого в Rust называется **tonic**. Эта глава о том,
как собрать из неё работающую пару «сервер и клиент», не наступив на самые частые грабли, а следующая о том, чем сервисы пользуются в бою.

## От схемы до вызова

```
 stock.proto ──► build.rs (tonic-prost-build) ──► OUT_DIR/stock.v1.rs
                                                        │ include_proto!
         ┌──────────────────────────────────────────────┤
         ▼                                              ▼
  трейт Stock                                  StockClient<Channel>
  (его реализует сервер)                       (его вызывает клиент)
         │                                              │
         ▼                                              ▼
  StockServer::new(impl)  ◄──── HTTP/2, protobuf ────►  Channel
```

Кодогенерация запускается из `build.rs`, как в главе про protobuf, только вместо `prost_build` вызывается `tonic_prost_build`.
Он порождает всё, что порождал prost (структуры сообщений), и добавляет два модуля: `stock_server` с трейтом `Stock` и обёрткой
`StockServer`, и `stock_client` с клиентом `StockClient`. Подключаются они тем же `tonic::include_proto!("stock.v1")`, где в
скобках имя пакета из `.proto`. Модули вокруг макроса повторяют пакет (`stock::v1`), иначе другие схемы не найдут типы.

Версии в курсе закреплены: `tonic`, `tonic-prost` и `tonic-prost-build` версии `=0.14.6`, `prost` версии `=0.14.4`. Пакеты tonic
в последних версиях разделены: сам tonic знает про HTTP/2 и транспорт, а формат protobuf подключает `tonic-prost`. Для сборки нужен
`protoc`.

## Сервер

Сервер это структура, реализующая сгенерированный трейт. Каждый метод получает `Request<T>` и возвращает `Result<Response<U>, Status>`:

```rust
#[tonic::async_trait]
impl Stock for Warehouse {
    async fn get_item(&self, request: Request<GetItemRequest>) -> Result<Response<Item>, Status> {
        let sku = request.into_inner().sku;
        // ...
    }
}
```

`Request` несёт тело (`into_inner()`), метаданные (`metadata()`) и расширения, `Response` то же самое в обратную сторону. Метод
вызывается из многих задач сразу, поэтому изменяемое состояние живёт под `Mutex` или в атомиках, а замок не держится через `.await`.

Запустить сервер можно двумя способами. `Server::builder().add_service(..).serve(addr)` открывает порт сам. Но в тестах и в сервисах
с динамическим портом нужно знать адрес заранее, и тогда слушатель открывают руками и отдают серверу готовым:

```rust
let listener = TcpListener::bind("127.0.0.1:0").await?;
let addr = listener.local_addr()?;
Server::builder()
    .add_service(StockServer::new(Warehouse::default()))
    .serve_with_incoming(TcpListenerStream::new(listener))
    .await?;
```

`TcpListenerStream` приходит из `tokio-stream` (с флагом `net`). Порт 0 просит у системы свободный, как в тестах всего курса. Метод
трейта можно вызвать и напрямую, без сети: это обычный `async fn`, и юнит-тесты логики не обязаны поднимать сервер.

## Клиент: Endpoint, Channel и лень

`StockClient::connect("http://127.0.0.1:50051").await` открывает соединение и возвращает клиента. Для сервиса, который будет вызывать
соседей постоянно, это неудачная форма. Гибче два шага:

```rust
let channel = Endpoint::from_shared("http://stock:50051")?
    .connect_timeout(Duration::from_secs(1))
    .timeout(Duration::from_secs(2))
    .connect_lazy();
let client = StockClient::new(channel);
```

**`Endpoint`** описывает, куда и как ходить. **`Channel`** это ручка к HTTP/2-соединению с пулом внутри. **`connect_lazy`** откладывает
подключение до первого вызова: сервис стартует при любом порядке запуска соседей, а недоступность проявляется как `Unavailable` у
конкретных вызовов, и канал сам переподключается, когда сосед вернулся. Два срока разные: `connect_timeout` про установку
соединения, `timeout` про весь вызов целиком. Без второго зависший обработчик на другой стороне держит вызывающего вечно.

`Channel` и клиент дёшево клонируются, и все клоны делят одно соединение: HTTP/2 раскладывает вызовы по потокам. Поэтому на сервис
заводят **один** канал при старте, а в обработчики раздают клоны. Методы клиента требуют `&mut self`, и это не повод ставить клиента
под общий замок: клон каждому вызову решает ту же задачу без очереди. Обратная ошибка так же распространена: `connect()` в начале каждого
обработчика открывает новое соединение на каждый запрос, и сервер тонет в рукопожатиях.

## Status: что пошло не так

У ответа gRPC нет тела ошибки как у HTTP. Есть **код** из фиксированного набора и **сообщение**. Клиент решает, что делать, по коду,
поэтому выбирать его надо по смыслу:

| код | когда |
|-----|-------|
| `InvalidArgument` | аргумент плох сам по себе, как ни меняй состояние системы |
| `NotFound` | запрошенной сущности нет |
| `AlreadyExists` | создаваемое уже есть |
| `PermissionDenied` | личность известна, прав нет |
| `Unauthenticated` | личность не установлена |
| `FailedPrecondition` | система сейчас в состоянии, при котором так нельзя |
| `ResourceExhausted` | квота или лимит закончились |
| `Unavailable` | временный отказ, имеет смысл повторить |
| `DeadlineExceeded` | не уложились в срок |
| `OutOfRange` | значение за допустимым диапазоном (так tonic сообщает о слишком большом сообщении) |
| `Internal` | наша внутренняя поломка |

Сообщение читает человек, но не только тот, кого оно касается. Всё, что ты вписал в текст, видит любой клиент: адрес базы, текст
запроса, существование закрытого ресурса. Поэтому у ошибок наружу два лица. Клиент-видимые (чужой ввод, чужой выбор, «такого нет») несут
понятный текст с именем поля или значением. Остальное (сломалась база, упал сосед) превращается в `Internal` с общим текстом, а
подробности пишутся в журнал.

Удобно держать доменную ошибку и одно место, которое переводит её в `Status`: `impl From<DomainError> for Status`. Тогда все
обработчики пишут `?`, а политика «что можно показывать наружу» живёт в одном месте, где её видно и проверяют тестом.

Ошибка вызова зависимого сервиса переводится так же. `NotFound` от соседа не обязан оставаться `NotFound` у тебя: для твоего клиента
это может быть его собственный плохой аргумент. Недоступность соседа остаётся недоступностью (клиент может повторить), а непонятное
становится `Internal` без чужого текста.

## Граница сервиса: protobuf не доверяет никому

Каждое поле protobuf3 может оказаться нулём, пустой строкой или числом, которого нет в перечислении (клиент новее сервера). Внутри
сервиса такого быть не должно. На входе сообщение превращается в доменные типы через `TryFrom`, который отвергает плохое с
`InvalidArgument` и именем поля. В структуре перечисление хранится как `i32`, и `Enum::try_from(i32)` вернёт ошибку для неизвестных
значений, а геттер молча подставит значение по умолчанию. Для проверки на границе нужен первый.

Длину текста считай в символах, а не в байтах: русская буква весит два байта, и лимит «280 знаков» должен быть про знаки.

## Метаданные

Метаданные это заголовки HTTP/2 вызова: ключ и значение вне тела сообщения. Через них идёт сквозной идентификатор запроса,
токен авторизации, срок вызова. Ключи в нижнем регистре, значения обычных ключей ASCII. Ключ на `-bin` бинарный: значение
кодируется в base64 само, а работать с ним нужно отдельными методами (`insert_bin`, `get_bin`). Значения приходят снаружи,
поэтому `to_str()` возвращает `Result` и ему нельзя делать `unwrap`.

## Размер сообщения

tonic по умолчанию не принимает сообщение больше 4 МиБ и отвечает `OutOfRange`. Это защита: без неё один клиент мог бы заставить
сервер выделить гигабайты. Лимит поднимается осознанно и на каждой стороне отдельно: `max_decoding_message_size` про входящие,
`max_encoding_message_size` про исходящие, на обёртке сервера и на клиенте. Если большие файлы нужны всерьёз, правильный ответ не
гигантское сообщение, а стрим кусками (об этом следующая глава).

## Общий крейт со схемами

Если сервисы users и posts собирают `.proto` каждый у себя, у каждого появится свой тип `User`: похожий и несовместимый для
компилятора. Схемы собирает один крейт `proto`, сервисы зависят от него по `path`. Папки со схемами повторяют пакеты и версии
(`users/v1/users.proto`), корнем для `import` служит папка выше, а сгенерированные модули повторяют пакеты, потому что код одной
схемы ссылается на типы другой относительными путями.

## Типичные ошибки

- `connect().await` на каждый вызов вместо одного канала при старте.
- Клиент под `Mutex`, и параллельные вызовы выстроились в очередь.
- `Status::internal(e.to_string())` на ошибке базы или чужого сервиса: утечка деталей.
- Геттер перечисления вместо `try_from`: плохое значение сошло за «не задано».
- Поднятый лимит размера только с одной стороны или снятый совсем.
- Все ошибки под одним кодом: клиент не отличает «нет» от «лёг».
- Нет срока вызова: зависший сосед подвешивает вызывающего.
