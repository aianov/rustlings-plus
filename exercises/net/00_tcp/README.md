# Адреса и TCP-соединение

Ты написал сервер, запустил его и открыл в браузере `http://localhost:3000`. Тишина. Запускаешь
из контейнера, порт проброшен, а снаружи опять тишина. Меняешь `127.0.0.1` на `0.0.0.0`, и всё
вдруг работает. Через неделю тесты на CI падают с «address already in use», потому что кто-то
захардкодил порт 8080. Через месяц клиент молча теряет хвост большого сообщения, а сервер
крутит процессор на 100% на уже закрытом соединении.

Все эти истории про одно и то же: ты не знаешь, что на самом деле происходит между
`connect` и `accept`. Эта глава про это. Сначала адреса, потом соединение, потом байты,
которые по нему идут, и все способы, которыми оно ломается.

## Как найти процесс на машине

В сети процесс определяется парой: **IP-адрес** (какая машина, а точнее какой её сетевой
интерфейс) и **порт** (какой процесс на ней, число от 0 до 65535). В std такая пара называется
`SocketAddr`, а IP отдельно `IpAddr`.

```rust
use std::net::{IpAddr, SocketAddr};

let a: SocketAddr = "127.0.0.1:8080".parse().unwrap();
let b: SocketAddr = "[::1]:443".parse().unwrap();
assert_eq!(a.port(), 8080);
assert!(b.is_ipv6());
```

IPv6 записывают в квадратных скобках. Причина простая: в IPv6 двоеточия живут внутри самого
адреса (`2001:db8::1`), и без скобок не понять, где кончается адрес и начинается порт.
Поэтому `"::1:443"` не разберётся, а `"[::1]:443"` разберётся.

Важное: `parse` ничего не ищет в сети. Строка `"localhost:80"` для него ошибка, потому что
`localhost` это имя, а не адрес. Превратить имя в адреса умеет только резолвер, об этом ниже.

## Куда слушать

Когда сервер делает `bind`, он выбирает, на каких сетевых интерфейсах принимать
соединения. Вот адреса, которые встречаются чаще всего:

```
адрес для bind     кто достучится
-----------------  --------------------------------------------------
127.0.0.1:P        только процессы на этой же машине (loopback)
192.168.1.5:P      те, кто видит этот конкретный интерфейс (локальная сеть)
0.0.0.0:P          все интерфейсы сразу: loopback, локальная сеть, весь мир
[::1]:P            то же, что 127.0.0.1, но для IPv6
[::]:P             то же, что 0.0.0.0, но для IPv6
```

`0.0.0.0` это не «адрес сервера», а «любой». Подключаться к нему как к адресу нельзя (на
некоторых системах получится, но это случайность), клиенту нужен конкретный адрес:
127.0.0.1 с той же машины, 192.168.1.5 из локальной сети. Поэтому адрес для `bind` и адрес для
`connect` нельзя брать из одного поля конфига без перевода. Этим занимается задача `ntcp2`.

Есть и обратная ловушка: слушать `0.0.0.0` по привычке «чтобы работало» значит открыть сервис
всему, что видит твою машину. В кафе это весь зал. Для локальной разработки хватает
`127.0.0.1`. А в Docker нужен как раз `0.0.0.0`: у контейнера свой loopback, и снаружи (с хоста)
он не виден. В продакшене слушают `0.0.0.0` внутри контейнера, а наружу порт выставляют
правилами оркестратора.

## Порт 0 и тесты

Фиксированный порт в тесте это бомба: два теста запустились параллельно, один получил
`AddrInUse`. Решение встроено в ОС: попроси порт 0, и система сама выберет любой свободный.
Какой именно, узнаешь у слушателя:

```rust
let listener = TcpListener::bind("127.0.0.1:0").await?;
let addr = listener.local_addr()?;   // 127.0.0.1:51432, например
```

Весь курс тестирует сеть так, и ты тоже будешь. Заодно в тестах всегда слушай только
`127.0.0.1`, а не `0.0.0.0`: тест не должен открывать порт всей сети.

## Что такое TCP-соединение

TCP это договор между двумя сокетами: байты дойдут целыми, по порядку и без дублей, а если
не получится, ты узнаешь об этом ошибкой. Ради этого ядра обеих машин ведут переписку, которую
твой код не видит.

Соединение начинается с рукопожатия из трёх пакетов. Его делает ядро, пока твой код ещё
спит в `connect` или `accept`:

```
клиент                                  сервер
  |                                       | LISTEN (после bind и listen)
  |----------- SYN ---------------------->|
  |<---------- SYN + ACK -----------------|
  |----------- ACK ---------------------->|
  | connect() вернулся                    | accept() вернёт сокет
  |                                       |
  |==== байты ============================|
  |                                       |
  |----------- FIN ---------------------->|   клиент закрыл запись
  |<---------- ACK -----------------------|   сервер: read вернёт 0
  |<---------- FIN -----------------------|   сервер закрыл свою запись
  |----------- ACK ---------------------->|
```

Откуда следует важное. `connect` успевает вернуться до того, как сервер вызвал `accept`: ядро
уже завершило рукопожатие, и готовое соединение ждёт в очереди. Поэтому в тесте можно
сначала подключиться, а потом принять.

Закрытие у каждой стороны своё. FIN означает «я больше ничего не отправлю», но слушать я
продолжаю. Это называется half-close, и дальше из него вырастет целая задача. Есть и грубое
закрытие: RST, «этого соединения нет, забудь». Его присылают, когда пришли данные на
закрытый порт и когда сокет закрыли с непрочитанными данными (процесс, который просто упал,
закрывает сокеты вежливо, через FIN). Для твоего кода это `ConnectionReset`.

## TcpListener и TcpStream

Две структуры в `tokio::net`, и почти вся работа с TCP это они:

```rust
use tokio::net::{TcpListener, TcpStream};

// сервер
let listener = TcpListener::bind("127.0.0.1:0").await?;
let (mut stream, peer) = listener.accept().await?;   // peer это адрес клиента

// клиент
let mut stream = TcpStream::connect(addr).await?;
```

У `TcpStream` две пары адресов: `local_addr()` (мой конец) и `peer_addr()` (чужой). Они
зеркальны: `local_addr` клиента равен `peer_addr` сервера. У клиента порт временный:
система выдаёт его сама из эфемерного диапазона, а порт сервера остаётся портом слушателя.

Читать и писать нужно через трейты `AsyncReadExt` и `AsyncWriteExt`. Без `use` этих трейтов
методов `read` и `write_all` у сокета «нет», и компилятор честно скажет, что метод не найден.
Это первое, во что упрёшься.

## TCP это поток байтов

Самая важная мысль главы. Вот что делает клиент:

```rust
stream.write_all(b"ab").await?;
stream.write_all(b"cd").await?;
```

А вот что может увидеть сервер:

```
read -> "abcd"             (оба write склеились)
read -> "ab", read -> "cd" (как отправили)
read -> "a", "bc", "d"     (как угодно)
```

Порядок и целостность гарантированы, границы между `write` не гарантированы никак. TCP не
знает слова «сообщение». Склеивает и режет всё подряд: буферы ядра, алгоритм Nagle, размер
пакета в сети (MTU), загруженность получателя. На localhost маленькие сообщения чаще всего
приходят как отправлены, поэтому тесты на ноутбуке зелёные, а в проде один раз в тысячу
сообщение приходит куском. Это ровно тот баг, который невозможно воспроизвести, если не
знать про него заранее.

Следствие для кода: нельзя писать «я отправил 100 байт, значит одним `read` получу 100».
Читать нужно либо до тех пор, пока не набралось нужное количество (`read_exact`), либо до
границы, о которой договорились клиент и сервер в протоколе (перевод строки, длина в заголовке), либо до
конца потока. Про границы поговорим в главе про фрейминг.

### read и Ok(0)

```rust
let n = stream.read(&mut buf).await?;
```

`read` кладёт в начало буфера сколько есть и возвращает `n`. Не больше `buf.len()`, но
и не обязательно столько. Данные в `buf[..n]`, остальное мусор.

Если `n == 0`, это **конец потока**: собеседник закрыл свою сторону записи. Не «пока нет
данных» (в этом случае `read` просто ждёт), а «данных больше не будет». Забыть проверить
это значит получить цикл, который на закрытом соединении крутится вечно, получая `Ok(0)`,
и жжёт процессор. Такой цикл ты найдёшь в `ntcp7`. Ноль означает EOF и в одном
редком случае ещё: ты передал пустой буфер. Поэтому буфер всегда непустой.

Три способа читать, от простого к тонкому:

```rust
stream.read(&mut buf)          // сколько-то, от 1 до buf.len(), или 0 на EOF
stream.read_exact(&mut buf)    // ровно buf.len() байт, иначе ошибка UnexpectedEof
stream.read_to_end(&mut vec)   // всё до EOF
```

### write и write_all

С записью зеркально. `write(data)` возвращает, **сколько байтов принято**, и это может быть
меньше `data.len()`: буфер отправки ядра заполнен, потому что получатель читает медленнее, чем
ты пишешь. Если проигнорировать результат, хвост теряется без единого предупреждения.
`write_all` сам повторяет запись, пока не отдаст всё. Почти всегда тебе нужен именно он.
(Clippy, кстати, ругается на проигнорированный результат `write`: он знает эту ловушку.)

## Half-close: «я всё сказал, но слушаю»

Бывает протокол «запрос, потом EOF, потом ответ». Клиент отправляет весь запрос и закрывает
свою сторону записи, сервер читает до EOF и отвечает, клиент читает ответ.

Вот сервер такого протокола, который считает контрольную сумму присланного файла:

```rust
let mut body = Vec::new();
stream.read_to_end(&mut body).await?;     // вернётся, только когда клиент закроет запись
let sum: u32 = body.iter().map(|b| *b as u32).sum();
stream.write_all(format!("{sum}\n").as_bytes()).await?;
```

Теперь вопрос к клиенту: как он скажет «файл кончился», если дальше хочет ещё читать
ответ? Закрыть только свою сторону записи умеет `shutdown` из `AsyncWriteExt`: он отправляет
FIN, и читать после этого можно по-прежнему.

Забудешь `shutdown`, и сервер вечно ждёт конца запроса, а клиент вечно ждёт ответа. Ни ошибки,
ни паники, просто тишина. Такие зависания самые неприятные.

А `drop(stream)` закрывает сразу обе стороны. И вот тонкость: если в буфере приёма на тот
момент ещё лежали непрочитанные данные, ядро вместо вежливого FIN отправит RST. Собеседник
получит `ConnectionReset`, и даже ответ, который ты успел отправить, может потеряться. Правило:
дочитывай, что тебе шлют, прежде чем закрыться.

И ещё одна ловушка с мегабайтами. Допустим, клиент и сервер делают эхо: клиент пишет, сервер
читает и сразу пишет обратно. Если клиент сначала отправит целиком несколько мегабайт, а читать начнёт
потом, то сервер заполнит свой буфер отправки (клиент же не читает), перестанет читать, заполнится
буфер клиента, и оба заснули навсегда. Лечится тем, что запись и чтение идут одновременно, в
разных задачах. Сокет для этого делится на половинки методом `into_split`: каждая половинка
владеет своей частью сокета и спокойно переезжает в `tokio::spawn`. Пример на другом деле,
клиент мессенджера: одна задача печатает всё, что шлёт сервер, а основная отправляет своё.

```rust
let (reader, mut writer) = stream.into_split();
let printer = tokio::spawn(async move {
    let mut lines = BufReader::new(reader).lines();
    while let Some(line) = lines.next_line().await? {
        println!("{line}");
    }
    Ok::<_, io::Error>(())
});
writer.write_all(b"привет\n").await?;
writer.shutdown().await?;
printer.await??;
```

У `printer.await` два уровня результата: внешний `JoinError` (задача запаниковала или её
отменили) и внутренний `io::Error` из самой задачи. Отсюда два вопросительных знака.

## Имена и адреса: lookup_host

Строка `"localhost:8080"` или `"example.com:443"` это просьба найти адреса. Имя может вести на
несколько:

```
localhost  ->  ::1        (IPv6, часто первым)
               127.0.0.1  (IPv4)
```

```rust
let addrs: Vec<SocketAddr> = tokio::net::lookup_host("localhost:8080").await?.collect();
```

Если сервер слушает только `127.0.0.1`, а клиент взял первый адрес из списка (`::1`), получится
`ConnectionRefused`, хотя сервер жив и здоров. Поэтому клиент перебирает адреса по очереди
(`TcpStream::connect`, получив имя вместо адреса, перебирает все адреса из списка по очереди и
берёт первый, который ответил), а если ты резолвишь вручную, перебор пишешь ты.
Резолвинг идёт через блокирующий вызов системного resolver'а в отдельном потоке, так что он
может занимать заметное время. Таймаут нужен и здесь.

## Ошибки соединения

Почти все сетевые ошибки приходят как `io::Error`, а смысл у них в `kind()`:

```
ConnectionRefused   по этому адресу и порту никто не слушает (ответили RST на SYN)
ConnectionReset     собеседник оборвал соединение (RST)
ConnectionAborted   соединение прервано локально или по пути; обычно трактуют как Reset
UnexpectedEof       поток кончился раньше, чем ты ждал (read_exact)
BrokenPipe          пишешь в соединение, которое собеседник уже закрыл
TimedOut            ждали и не дождались (ядро или наш таймаут)
AddrInUse           порт для bind уже занят
```

Ошибка Refused и тишина это разные болезни. Refused быстрая: сервер не поднят, повтори
позже или сообщи пользователю. Тишина (SYN ушёл, ответа нет) это фаервол или мёртвая машина,
и без таймаута `connect` будет ждать минутами.

## Таймауты

Любое ожидание из сети нужно ограничить временем: подключение, чтение, запись. Иначе молчащий
собеседник держит твою задачу и память сколько угодно. В tokio для этого есть
`tokio::time::timeout`:

```rust
use tokio::time::{timeout, Duration};

match timeout(Duration::from_secs(5), listener.accept()).await {
    Ok(Ok((stream, peer))) => { /* пришёл клиент */ }
    Ok(Err(e)) => { /* ошибка accept */ }
    Err(_elapsed) => { /* никто не пришёл за 5 секунд */ }
}
```

Результат двухэтажный: внешний `Result` говорит, уложились ли во время, внутренний
это результат самой операции. Два уровня удобно свести в один `io::Result`, а истечение
времени выразить как `ErrorKind::TimedOut`. Все тесты курса тоже оборачивают
ожидания в `timeout`: зависший тест превращается из бесконечного зависания в строчку с
понятной причиной.

Если тебе нужен тест, в котором таймаут большой (30 секунд), используй
`#[tokio::test(start_paused = true)]`: время в тесте идёт виртуальное и перескакивает само,
когда все задачи ждут. Работает только там, где нет настоящего сокета.

## Потрогать руками

Лучший способ понять TCP посмотреть на него живьём. Два терминала:

```
# терминал 1: сервер, который печатает всё, что пришло
nc -l 127.0.0.1 9000

# терминал 2: клиент, набирай строки и жми Enter
nc 127.0.0.1 9000
```

Закрой клиента через Ctrl+D: он отправит FIN, и `nc` сервера увидит EOF. Попробуй и в другую
сторону: останови сервер и перезапусти его, а клиент, который ещё держит старое соединение,
при следующей отправке получит ошибку.

`curl` тоже умеет говорить на сыром TCP: `curl -v http://127.0.0.1:9000/` против запущенного
`nc -l 9000` покажет, что HTTP это просто текст в потоке. Увидеть, кто слушает порты, можно так:

```
lsof -iTCP -sTCP:LISTEN -n -P        # macOS и Linux
```

Визуализации к этой главе: `tcp_handshake` показывает рукопожатие и закрытие шаг за шагом,
`tcp_stream_bytes` показывает, как два `write` склеиваются в один `read` и как один `write`
режется на несколько.

## Типичные ошибки

- Фиксированный порт в тесте. Всегда `127.0.0.1:0`.
- Забыть про `Ok(0)` в цикле чтения. Бесконечный цикл на закрытом соединении.
- Один `read` вместо цикла или `read_exact`. Работает на localhost, падает в проде.
- `write` вместо `write_all`. Теряется хвост большого сообщения.
- Отправлять всё и только потом читать в протоколах «запрос и ответ параллельно». Взаимное
  зависание на больших объёмах.
- Не сделать `shutdown` там, где сервер ждёт EOF.
- Брать только первый адрес из `lookup_host`. Сломается на машинах, где `::1` стоит первым.
- Читать весь `buf`, а не `buf[..n]`.
- Ждать сеть без таймаута.
- Слушать `0.0.0.0` в разработке без причины. Или `127.0.0.1` в контейнере, где как раз нужен `0.0.0.0`.
