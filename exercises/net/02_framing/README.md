# Границы сообщений

TCP отдаёт тебе поток байтов, а не сообщения. Ты уже видел это: два `write` склеиваются в один
`read`, один `write` рвётся на несколько. Из-за этого любой протокол поверх TCP начинается с
вопроса: «где кончается одно сообщение и начинается следующее?». Ответ называется фреймингом.
HTTP, WebSocket, gRPC, Redis, PostgreSQL отвечают на него по-разному, но по сути всеми тремя
способами из этой главы. Научишься их писать, и разбор любого протокола перестанет быть магией.

## Три способа проставить границы

**Разделитель.** Сообщение кончается особым символом, чаще всего `\n`. Просто, читается глазами,
удобно для `nc` и `curl`. Платить приходится двумя вещами: тело не может содержать разделитель
(нужно экранирование), а чтобы найти конец, надо просмотреть каждый байт. Так устроены заголовки
HTTP (`\r\n`), SMTP, inline-команды Redis.

**Длина впереди.** Сначала число (сколько байтов дальше), потом тело. Тело может быть любым, а
чтобы получить сообщение, не нужно ничего искать: прочитал число, отсчитал столько байтов.
Размер заранее известен, значит память можно выделить один раз. Так устроены WebSocket, gRPC,
PostgreSQL. Платить приходится двоичностью (глазами не прочитать) и осторожностью: число пришло
от чужого человека.

**Тип, длина, тело (TLV).** Тот же приём, но в начале ещё и тип сообщения. Один формат несёт
много разных сообщений, и по типу получатель знает, как разбирать тело. Почти все двоичные
протоколы устроены так.

Порядок байт в числах договаривается заранее. В сети принят big-endian (старший байт первым):
число 258 это байты `0x01 0x02`. В Rust это `258u32.to_be_bytes()` и `u32::from_be_bytes(..)`.

## Пример: netstring

Чтобы увидеть всё на другом формате, возьмём netstring. Сообщение `hello` записывается как
`5:hello,`: десятичная длина, двоеточие, тело, запятая в конце (она нужна как контрольный байт).
Декодер для такого потока живёт на одном правиле: **пока сообщение не пришло целиком, ничего не
трогай и скажи «пока нет».**

```
буфер: "5:he"     длину прочитали (5), но тела 2 из 5      -> пока нет, буфер как был
буфер: "5:hello"  тело есть, а запятой ещё нет             -> пока нет
буфер: "5:hello,7:wor"  первое готово                      -> "hello", в буфере "7:wor"
буфер: "99999999999:" длина больше лимита                  -> ошибка сразу, тело не ждём
```

Почему нельзя «читать понемногу и убирать прочитанное»: пришла длина, ты её убрал, дальше
пусто, а при следующем вызове ты уже не знаешь, что это было за число. Состояние, которое
нужно сохранить, проще всего хранить в самом буфере: пока кадр неполон, байты остаются на месте.

## BytesMut и его друзья

Крейт `bytes` даёт тип для буфера накопления: `BytesMut`. Вот что от него нужно:

```rust
let mut buf = BytesMut::new();
buf.extend_from_slice(b"20.5;21.0;22");   // дописать в конец
let i = buf.iter().position(|b| *b == b';').unwrap();
let mut first = buf.split_to(i + 1);       // вынуть первые i+1 байт: в buf остаётся остаток
first.truncate(i);                         // отрезать разделитель с конца вынутого куска
buf.advance(2);                            // выбросить 2 байта с начала (трейт Buf)
let frozen = first.freeze();               // неизменяемый Bytes: дёшево клонируется
```

`split_to(n)` забирает `n` байтов с начала без копирования: возвращённый `BytesMut` указывает
на ту же память, а `buf` сдвигается вперёд. Именно поэтому это быстро, и именно поэтому вместо
`buf.clear()` (который выбросит и хвост, принадлежащий следующему сообщению) нужно
`split_to` или `advance`. Для записи чисел и кусков есть трейт `BufMut`: `put_u32(n)` пишет число в
big-endian, `put_slice(..)` дописывает байты. `buf.reserve(n)` готовит место заранее.

Читать из сокета прямо в буфер умеет `read_buf`:

```rust
let n = stream.read_buf(&mut buf).await?;   // дописывает прочитанное в конец buf
```

Он сам увеличивает буфер и возвращает, сколько байтов добавилось (ноль это EOF, как и раньше).
Важное свойство: если вызов отменили, всё уже прочитанное осталось в `buf`. К этому мы вернёмся.

## Декодер как функция над буфером

Самая полезная форма разбора протокола такая:

```rust
fn decode(buf: &mut BytesMut) -> Result<Option<Message>, Error>
```

Три исхода. `Ok(Some(m))`: в начале буфера лежало целое сообщение, оно вырезано, остаток на месте.
`Ok(None)`: сообщение пришло не целиком, буфер не тронут, надо читать дальше. `Err(e)`:
поток испорчен, соединение пора закрывать. У функции нет сокета, нет `async`, нет времени. Её
можно проверить скармливая куски байтов, и это главный способ тестировать протоколы: **результат
не должен зависеть от того, как поток нарезан**. Проверяют так: разрезать поток в каждой
возможной позиции и сравнить результат с эталоном (в этой главе ты так делаешь), а потом
пустить по одному байту.

Над декодером стоит тонкий слой, который читает сокет и кормит им буфер:

```
loop {
    if let Some(m) = decode(&mut buf)? { return Some(m) }   // вдруг уже есть
    if stream.read_buf(&mut buf).await? == 0 { конец потока }
}
```

Сначала декодируем, и только потом читаем: после предыдущего чтения в буфере могло остаться
несколько сообщений. Эту пару (кодек и слой вокруг сокета) в tokio-util называют `Framed`, а
сама идея лежит в основе `hyper`, `tonic` и тысяч других мест.

## Конец потока

Конец потока бывает двух видов. Чистый: собеседник закрылся, а буфер пуст. Грязный: буфер не пуст,
то есть сообщение оборвалось посреди. Первое это штатный выход (`Ok(None)`), второе ошибка
(`UnexpectedEof`). Различать нужно обязательно: иначе «пришло полсообщения и конец» молча
выглядит как «всё хорошо», и данные теряются без следа. Читая построчно через `read_line`,
помни: последняя строка без `\n` вернётся как обычная, и отличить обрыв от нормального конца
придётся самому.

## Чужие длины и лимиты

Длина в заголовке это то, что написал собеседник. Если сделать `vec![0; len]` по этому числу,
клиент, который присылает `FF FF FF FF`, заставляет тебя зарезервировать четыре гигабайта на
одно соединение. Операционная система может отдать адресное пространство лениво, но под лимитом
памяти контейнера или когда буфер начнёт заполняться, процесс убьют. Лимит проверяется **сразу, как стала известна длина**, до выделения памяти и до
ожидания тела. То же и для разделителя: строка без `\n` не должна расти без предела, лимит
срабатывает по накопленному размеру, не дожидаясь символа конца. Для чтения построчно с лимитом
пригодятся методы `fill_buf` и `consume` трейта `AsyncBufRead`: они дают заглянуть во внутренний
буфер, найти границу и забрать ровно нужное, не читая больше.

```rust
let chunk = reader.fill_buf().await?;               // что сейчас в буфере (пусто = EOF)
let n = chunk.iter().position(|b| *b == b';').map_or(chunk.len(), |i| i + 1);
reader.consume(n);                                   // забрать n байт, остальное осталось
```

## Отмена и select!

В прошлой главе мы выяснили, что когда в `select!` побеждает одна ветка, остальные future
выбрасываются. Теперь понятно, как жить с этим при разборе кадров. `read_exact` для заголовка
в `select!` опасен: он мог вынуть из сокета три байта из четырёх, и вместе с future они
исчезнут. А `read_buf` безопасен: прочитанное уже лежит в твоём буфере, снаружи future. Поэтому
схема «буфер живёт вне вызова, в него дописывает `read_buf`, декодер разбирает» годится для
`select!`, а схема «читаем кадр одной функцией через `read_exact`» нет. Сам `Framed` по той же
причине держит буфер в структуре, а не в локальных переменных `recv`.

Полезное правило: кроме `read`, `read_buf`, `accept` и `recv` почти всё, что читает «до чего-то»
(`read_exact`, `read_u32`, `read_line`, `read_to_end`), небезопасно к отмене. Доки tokio у каждого
метода пишут это отдельным абзацем.

## Ответы, которые приходят вперемешку

Пока на соединении один запрос за раз, всё просто: послал, жди. Когда запросов много,
ответы нужно сопоставлять с запросами, и для этого у каждого запроса есть номер (`id`), который
сервер копирует в ответ. Ожидающие лежат в таблице `id -> oneshot::Sender`, а `oneshot` это
канал на одно значение, как раз для «положи сюда ответ, когда придёт». Пример на другом деле:
касса с талонами.

```rust
struct Counter {
    waiting: Mutex<HashMap<u64, oneshot::Sender<String>>>,
    next: AtomicU64,
}

impl Counter {
    async fn take_ticket(&self) -> (u64, oneshot::Receiver<String>) {
        let id = self.next.fetch_add(1, Ordering::Relaxed);
        let (tx, rx) = oneshot::channel();
        self.waiting.lock().unwrap().insert(id, tx);
        (id, rx)
    }

    fn forget(&self, id: u64) {
        self.waiting.lock().unwrap().remove(&id);
    }

    fn serve_ticket(&self, id: u64, answer: String) {
        if let Some(tx) = self.waiting.lock().unwrap().remove(&id) {
            let _ = tx.send(answer);      // Err значит «клиент ушёл», это нормально
        }
    }
}
```

Три момента. Ответ может прийти на запрос, который никто уже не ждёт (вызов отменили по таймауту):
`send` вернёт ошибку, её игнорируют. Запись в таблице у отменённого вызова нужно убирать (метод `forget` выше),
причём делать это надо и тогда, когда future просто выбросили. Для такого случая заводят маленькую
структуру-гард с `Drop`, которая зовёт `forget` в деструкторе: деструктор сработает при любом выходе,
в том числе при отмене. Иначе таблица растёт. А когда соединение умерло, всех ожидающих нужно разбудить ошибкой: уничтожение
`Sender` делает это само, приёмник возвращает `Err`.

Чтобы читать ответы и писать запросы одновременно, сокет делят на половинки методом
`TcpStream::into_split()`: читающая половина уезжает в задачу-читателя, пишущая лежит под
`tokio::sync::Mutex` (или за каналом `mpsc`, из которого её читает одна задача-писатель, тогда кадры
разных вызовов не перемешиваются без блокировки).

## Тесты без сети

В этой главе почти всё проверяется без сокетов. Обычный срез байтов `&[u8]` уже реализует
`AsyncRead`, поэтому его можно отдать любой функции, читающей поток. `tokio::io::duplex(n)` даёт
пару связанных потоков в памяти. `tokio::io::repeat(b'a')` это бесконечный источник одного байта,
а `.take(n)` (из `AsyncReadExt`) обрезает его до `n`. С `#[tokio::test(start_paused = true)]`
время в тесте виртуальное: ожидания длиной в секунды проходят мгновенно и детерминированно, если
в тесте нет настоящих сокетов.

## Типичные ошибки

- `buf.clear()` после вынутого сообщения. Теряется хвост, принадлежащий следующему.
- Декодер, который убирает заголовок из буфера, не убедившись, что кадр пришёл целиком.
- `vec![0; len]` по длине из заголовка. Нужна проверка лимита до выделения.
- Читать «одно сообщение» одним `read`. Работает на localhost, ломается в проде.
- Принять конец потока без проверки буфера: полсообщения и EOF это ошибка, а не конец.
- Декодировать UTF-8 из кусков, пришедших по сети. Символ может оказаться разрезан между двумя
  чтениями. Преобразуй в строку только собранное целиком сообщение.
- `read_exact` или `read_line` в `select!`. Потеря частично прочитанного при отмене.
- Два `write` на один кадр (заголовок и тело отдельно). Два мелких пакета вместо одного, привет Nagle.
- Ответы сопоставляются с запросами по порядку, а не по `id`. Первый же медленный запрос ломает всё.
- Записи в таблице ожидающих не убираются при отмене вызова. Утечка.
