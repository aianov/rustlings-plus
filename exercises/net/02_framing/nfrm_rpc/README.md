# nfrm_rpc: мини-RPC поверх кадров

Один клиент, одно соединение, много вызовов сразу. Классическая ошибка новичка: вызвал, дождался
ответа, вызвал следующий. Соединение простаивает, пока ты ждёшь, а медленный запрос тормозит
все остальные. Настоящий RPC шлёт запросы, не дожидаясь ответов, и сопоставляет приходящие ответы
со своими вызовами по номеру. Ответы при этом могут идти в любом порядке.

## Что уже есть

Крейт `nfrm-rpc`:

- `src/wire.rs` (готов, менять не нужно): `Frame { id, body }`, функция `encode(&Frame)` и
  `FrameReader<R>` с методом `next()` (безопасен к отмене, буфер хранит внутри). Кадр на проводе:
  четыре байта длины, потом восемь байт `id` и тело.
- `src/lib.rs`: `RpcError`, заготовки `Client` и `serve`, которые падают через `todo!()`.

Приёмочные тесты лежат в `tests/acceptance.rs`, их править не нужно.

## Что сделать

1. `Client::connect(addr)`: подключиться и запустить всё, что нужно для приёма ответов. `Client`
   дёшево клонируется, и клоны работают с одним соединением.
2. `Client::call(body)`: отправить запрос с новым уникальным `id` и дождаться ответа именно с этим
   `id`. Много вызовов одновременно (из разных задач) должны идти по одному соединению, не
   дожидаясь друг друга. Если соединение закрылось, а ответа нет, вызов получает
   `Err(RpcError::Closed)`, а не повисает. Вызов после закрытия соединения тоже возвращает ошибку.
3. `Client::pending()`: сколько вызовов сейчас ждут ответа (записей в таблице). Отменённый вызов (например,
   по таймауту) не должен оставлять запись.
4. `serve(listener, handler)`: принять соединения и на каждый запрос вызвать `handler(body)`.
   Запросы одного соединения выполняются параллельно, ответ уходит, как только готов, и может
   обогнать более ранние. Запись в сокет ведёт одна задача, чтобы кадры не перемешивались.

## Критерии приёмки

`cargo test`. Тесты проверяют:

- обычный вызов и повторные вызовы, мегабайтное тело;
- 20 параллельных вызовов, сервер отвечает вперемешку: каждый получает свой ответ, и всё идёт
  параллельно (по времени);
- быстрый вызов не ждёт медленного;
- три запроса уходят подряд, сервер отвечает в обратном порядке, ответы находят свои вызовы;
- закрытие соединения даёт `Closed` ожидающим и новым вызовам;
- 100 вызовов, отменённых по таймауту на молчащем сервере, не оставляют записей (`pending() == 0`);
- подключение к закрытому порту это ошибка.

## Подсказки

Ожидающие вызовы лежат в таблице `id -> oneshot::Sender`. Вызов кладёт туда отправителя и ждёт на
приёмнике, задача-читатель при каждом ответе достаёт отправителя по `id` и передаёт ответ. Когда
читатель закончился (EOF или ошибка), таблицу нужно закрыть и разбудить всех ожидающих: если
отправитель уничтожен, приёмник возвращает ошибку. Запись убирай гардом с `Drop`: деструктор срабатывает и при отмене. Подумай, что будет с вызовом, который
положил запись в таблицу уже после закрытия. Сокет делят на читающую и пишущую половины (`into_split`). Для записи в общий сокет из многих вызовов нужна
блокировка на время одной записи, а запросы должны уходить кадром целиком.
