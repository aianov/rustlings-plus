# nrt_chat: chat-gateway

Проверочная задача главы. Соцсеть растёт, и чат пора выносить с голого TCP на WebSocket. Нужен шлюз реального времени:
клиент подключается по токену, вызывает методы через конверт `{id, service, method, data}`, получает события, а медленный
или пропавший клиент не мешает остальным. Это ровно та форма, в которой потом заработает api-gateway соцсети. Сторонних
WebSocket-библиотек в курсе нет, поэтому в проекте лежит твой `websocket-engine` и клиент из него же для тестов.

## Что уже есть

- `websocket-engine/` с вложенным `http-engine/`: движки из прошлой главы в рабочем виде. В `WsStream` добавлен метод
  `idle_for()`: сколько времени с последнего байта, прочитанного из сокета (pong тоже считается).
- `src/lib.rs`: `Config`, трейт `Tokens`, счётчики `Stats` (в тестах их читают).
- `src/envelope.rs`: разбор запроса и сборка ответов, ровно как в задаче nrt9.
- `src/router.rs`: таблица методов (`Router`, `Ctx`, `ApiError`), упрощённый вариант nrt10: все методы здесь «с входом»,
  потому что токен проверяется ещё до апгрейда.
- Сигнатуры и типы остальных файлов. Тела с `todo!()` пишешь ты.

## Что сделать

1. `hub.rs`, очередь клиента `Outbox`: ограниченная очередь на `Config::outbox` сообщений. Когда места нет, клиент
   отключается: в очередь кладётся `Out::Close(1008)`, поднимается флаг, будится `kicked()`, растёт `Stats::kicked`.
   Отключённому больше ничего не кладётся. `event` нумерует события с единицы внутри соединения (как в nrt12), `reply` нет.
2. `hub.rs`, реестр `Hub`: пользователи и их устройства, комнаты по именам пользователей. `connect` возвращает гард, при
   его Drop устройство исчезает; когда ушло последнее устройство пользователя, он выходит и из комнат (пустые комнаты
   удаляются). `say` кладёт событие `chat.message` во все устройства всех участников комнаты, кроме соединения, из которого
   пришло сообщение, и возвращает число доставок. Писать в комнату, где тебя нет, нельзя.
3. `methods.rs`: таблица методов. `chat.join {room}`, `chat.leave {room}`, `chat.who {room}`, `chat.say {room, text}`,
   `sys.sleep {ms}` (ждёт и отвечает, нужен для проверки параллельности), `sys.whoami`. Формат ответов и коды ошибок
   смотри в `tests/acceptance.rs`.
4. `conn.rs`: цикл одного соединения. В одном `select!` живут: остановка сервера, очередь исходящих (запись в сокет не должна
   зависать, если клиент не читает: отключение медленного должно её прервать), чтение запросов (параллельно, с потолком
   `Config::max_in_flight`; пока потолок достигнут, новые запросы не читаем), завершённые задачи, таймер ping. Нет вестей
   дольше `idle_limit`: закрываем и считаем в `Stats::timed_out`. Паника обработчика становится ответом `internal` на тот
   же id.
5. `server.rs`: `run`. Токен берётся из `Authorization: Bearer ...` или из `?token=`, проверяется через `Tokens::check`
   до ответа 101 (иначе 401). Путь `/ws`. Когда `shutdown` сработает, всем соединениям уходит Close с кодом 1001, а `run`
   возвращается после того, как они закрылись (но не позже `Config::grace`).

## Критерии приёмки

`cargo test`. Всё идёт по настоящей сети (127.0.0.1:0) и через клиент из `websocket-engine`:

- 401 до апгрейда на отсутствующий, пустой и чужой токен, 404 на другой путь, 101 на токен из адреса и из заголовка;
- `sys.whoami`, неизвестный метод, мусор вместо JSON, запрос без метода (ошибка с известным id), двоичное сообщение;
- комнаты: вход, состав, выход, сообщения с `seq` с единицы, запрет писать в чужую комнату, лимит длины текста;
- несколько устройств: сообщение уходит на все устройства всех участников, кроме того, с которого его отправили;
- уход клиента убирает его из реестра и из комнат, но пользователь с ещё одним устройством остаётся;
- три запроса одного соединения идут параллельно, ответы приходят по готовности; лимит в полёте соблюдается;
- клиент, который не читает, отключается, остальные получают всё по порядку без потерь;
- клиент, который не отвечает на ping, отключается, отвечающий живёт; остановка сервера объявляется кодом 1001.

## Структура

```
nrt_chat/
  Cargo.toml

```

## Подсказки по теории

- Очередь клиента и отключение медленного: задача nrt6. Номера событий: nrt12. Комнаты и устройства: nrt3, nrt4, nrt5.
- Цикл соединения: nrt7 (ping, срок молчания, отмена в `select!`) и nrt11 (параллельные запросы с потолком).
- `ws.recv()` внутри `select!`: пока он ждёт данные, его можно отменить без потерь. Единственное исключение, запись pong
  в момент отмены; в настоящих библиотеках чтение и запись разделены, у нашего `WsStream` для чата этого компромисса достаточно.
- Остановка: nrt13 в миниатюре. Движок `http-engine` сам ждёт обработчики до `drain_timeout`, поэтому сначала сообщи
  соединениям, что пора, а `serve_with` отдай готовый сигнал.
