# Сервер реального времени

Представь приложение доставки. Курьер едет по городу и каждые две секунды присылает координаты. Тысяча клиентов смотрит на карту и
хочет видеть, как точка ползёт к дому. Если у тебя один курьер и один зритель, всё решается циклом `loop { recv; send }`. Если зрителей
тысяча, а курьеров двести, начинаются вопросы, на которые в учебных примерах не отвечают.

Кто кому что шлёт? Что делать, когда телефон зрителя вошёл в лифт и перестал читать? Как отличить зависшее соединение от тихого? Как
остановить сервер так, чтобы тысяча зрителей не ринулась обратно в ту же секунду? В прошлой главе ты написал WebSocket: фреймы,
рукопожатие, закрытие. Теперь это нужно превратить в сервер, который живёт сутками.

```
            +-------------------- один процесс --------------------+
  телефон 1 |  задача соединения 1 --+                              |
  телефон 2 |  задача соединения 2 --+--> реестр (кто где подключён)|
  ноутбук   |  задача соединения 3 --+       |                      |
            |          ^                     v                      |
            |          +---- очереди <--- рассылка событий          |
            +-------------------------------------------------------+
```

У каждого соединения своя задача и своя очередь исходящих. Реестр знает, кто подключён, и по нему рассылка находит адресатов. Всё
остальное в главе это ответы на вопрос «что сломается, когда это увидит живой интернет».

## Реестр, который чистится сам

Реестр это карта «id соединения → очередь». Запись добавляют при подключении и убирают при отключении. Самый частый баг: убирают
вручную в конце функции, а функция выходит через `?` на полпути.

```rust
async fn follow_courier(map: &Tracker, link: Link) -> Result<(), LinkError> {
    map.watchers.lock().unwrap().insert(link.id, link.sender.clone());
    let first = link.read_hello().await?;
    run_session(&link, first).await?;
    map.watchers.lock().unwrap().remove(&link.id);
    Ok(())
}
```

Любой из двух `?` оставляет зрителя в карте навсегда. Рассылка продолжает слать координаты в очередь, которую никто не читает, и память
течёт по килобайту на каждого, кто когда-то обиделся на сеть. Лечится это не аккуратностью, а устройством: запись привязывают к
значению с `Drop`.

```rust
struct Lease { map: Tracker, id: u64 }

impl Drop for Lease {
    fn drop(&mut self) {
        self.map.watchers.lock().unwrap().remove(&self.id);
    }
}
```

`Lease` создаётся вместе с записью, и деструктор срабатывает при возврате, при `?`, при панике и даже при `abort()` задачи (будущее
просто уничтожается, а локальные значения роняются). Не сработает он только при `mem::forget`, `process::exit` и `panic = "abort"`.

Одна тонкость. Если замок в `drop` берётся через `lock().unwrap()`, а другой поток когда-то упал, держа этот же замок, замок
«отравлен» и `unwrap` паникует. Паника в `drop` во время паники обрывает весь процесс. Данные в отравленном замке остаются целыми,
отравление это только метка, поэтому в деструкторах берут `lock().unwrap_or_else(|e| e.into_inner())`.

Реестр не бессмертен: он живёт в памяти процесса и пропадает вместе с ним. Это нормально, но помни: «кто в какой комнате» после
перезапуска надо собирать заново, когда клиенты переподключатся.

## Писатель и ограниченная очередь

Писать в одно соединение хотят сразу несколько мест: ответ на запрос, событие от рассылки, ping. Если каждое пишет в сокет само, они
дерутся за него, а половина записи одного сообщения может смешаться с началом другого. Поэтому сокетом владеет одна задача, а остальные
кладут сообщения в очередь:

```
  ответ на запрос ----+
  рассылка -----------+--> mpsc::channel(N) --> задача-писатель --> сокет
  ping ---------------+
```

Очередь делают ограниченной. Безграничная очередь выглядит удобно, пока не появится зритель, который не читает: сообщения копятся в
памяти сервера без предела, и через час процесс убивает OOM-killer. Ограниченная очередь превращает ту же ситуацию в сигнал: `try_send`
возвращает `Full`, и теперь можно решать.

Решение обычно одно: отключить медленного клиента. Молча выбрасывать сообщения нельзя (клиент увидит дыру в переписке и не поймёт, что это
сбой), ждать места нельзя (о том, почему, следующий раздел). Отключают с кодом 1008, чтобы причина попала в логи и клиент мог показать
понятное сообщение. Но тут ловушка: объявление о закрытии тоже едет по очереди, а в очереди нет места. Поэтому одно место резервируют:
канал создают на одно место больше, чем нужно под сообщения, а `Sender::capacity()` (сколько мест свободно сейчас) подсказывает, когда
остаётся только резервное.

Ещё одно следствие: писатель, застрявший в записи в забитый сокет, не заглянет в очередь. Чтобы отключение сработало, запись надо
выполнять в `select!` вместе с сигналом отключения (`Notify`, `watch` или флаг) или давать ей срок.

## Не держи замок, пока ждёшь

Самый коварный баг этой главы выглядит невинно:

```rust
async fn announce(&self, order: OrderId, status: &str) {
    let subs = self.subscribers.lock().await;
    for tx in subs.get(&order).into_iter().flatten() {
        tx.send(status.to_string()).await.ok();
    }
}
```

Пока все читают, всё хорошо. Как только у одного подписчика очередь заполнилась, `send().await` засыпает, а замок остаётся у задачи.
Теперь никто не может подписаться, отписаться или получить свой статус: все ждут замок. На стенде такого не бывает, потому что нет клиента
с забитой очередью, а в бою он находится в первый же час. Заметь, что `tokio::sync::Mutex` ничего не лечит: он разрешает `await` под
замком, но не делает ожидание короче. Тот же эффект у `RwLock`: читатель, который держит замок через ожидание, блокирует писателя, а
справедливый замок не пускает новых читателей вперёд ждущего писателя.

Правило такое: под замком только быстрые действия без `await`. Копии отправителей (`Sender` клонируется дёшево) забираем внутрь блока,
замок отпускаем, и только потом рассылаем, причём через `try_send`, который не засыпает.

```rust
let targets: Vec<Sender<String>> = {
    let subs = self.subscribers.lock().unwrap();
    subs.get(&order).map(|v| v.to_vec()).unwrap_or_default()
};
for tx in &targets {
    let _ = tx.try_send(status.to_string());
}
```

Блок `{ ... }` здесь важен: гард замка умирает на закрывающей скобке, до рассылки.

## Люди, устройства и комнаты

Адресат сообщения человек, а не соединение: у него телефон, ноутбук и планшет, и личное сообщение должно прийти на все. Значит, реестр
двухэтажный: пользователь, под ним его соединения. Когда уходит последнее соединение, запись пользователя тоже должна исчезнуть. Иначе
реестр «пустых людей» растёт без видимых признаков.

Комната это просто имя и набор участников. Те же правила уборки: пустая комната удаляется, а выходящее соединение выходит из всех
комнат. Имена комнат присылает клиент, поэтому без уборки ему достаточно придумать миллион названий, чтобы раздуть карту. Отправителя
из рассылки обычно исключают: он и так знает, что написал. Но если у отправителя есть другое устройство, оно сообщение получить должно,
поэтому исключается соединение, а не пользователь.

## Heartbeat: как понять, что клиента уже нет

TCP не сообщает, что телефон пропал в тоннеле: пока никто не пишет, соединение выглядит живым часами. Поэтому сервер сам проверяет
живость: раз в интервал шлёт ping, а если от клиента нет вестей дольше срока, считает соединение мёртвым.

```rust
let mut tick = tokio::time::interval_at(Instant::now() + every, every);
loop {
    tokio::select! {
        frame = lines.next_line() => { /* что-то пришло: сдвинуть срок */ }
        _ = tick.tick() => { /* послать ping */ }
        _ = tokio::time::sleep_until(deadline) => { /* молчит слишком долго */ }
    }
}
```

Три детали, на которых спотыкаются:

- Первый `tick()` у обычного `interval` срабатывает сразу, а не через интервал. Хочешь первый ping через интервал, возьми
  `interval_at(старт, период)`.
- Срок молчания хранится как момент (`deadline`) и сдвигается при любой вести от клиента. Если на каждом круге цикла писать
  `sleep(срок)`, любой тик таймера будет его сбрасывать, и молчун никогда не будет пойман.
- Внутри `select!` проигравшая ветка отбрасывается, а значит все данные, которые она успела прочитать, пропадают, если её операция не
  рассчитана на отмену. Чтение, которое откладывает недочитанное в собственное состояние, называют безопасным при отмене (cancel safe).
  У `Lines::next_line` это так, у «`read_line` с новым буфером на каждый круг» нет, и половина строки теряется ровно тогда, когда сработал
  таймер.

Любая весть от клиента продлевает ему жизнь, не только pong: занятому клиенту, который шлёт данные, отвечать на ping отдельно незачем.
И ещё: pong отвечает сетевой стек браузера, а не код страницы. Замороженная вкладка отвечает на ping протокола как ни в чём не бывало.
Проверить, что работает само приложение, можно только прикладным сообщением с ответом.

## Токен до апгрейда

После `101 Switching Protocols` у клиента уже есть открытое соединение и кусок памяти на сервере. Выяснять, кто он, по первому сообщению
значит дать анонимам занять место. Поэтому токен проверяют ещё в обычном HTTP-запросе: плохой токен получает честное `401` и никакого
сокета.

Откуда токен? Мобильные клиенты кладут его в `Authorization: Bearer ...`. Но у браузерного `new WebSocket(url)` заголовков нет, и остаётся
адрес: `wss://api.example/live?token=...`. У адреса есть цена: он попадает в логи прокси, балансировщика и шлюза, в историю браузера.
Поэтому токен не печатают в логах и в тексте ошибок, а если можно, делают короткоживущим: клиент по HTTP получает одноразовый «билет» на
полминуты и подключается с ним.

Проверка токена это обычно поход в другой сервис, поэтому у неё три исхода, а не два: токен хороший, токен плохой (`401`), сервис
проверки недоступен (`503`). Если слить два последних, при каждом сбое на нашей стороне клиенты решат, что токен испорчен, и сотрут его.

## Конверт: id, сервис, метод, данные

Через одно соединение ходят запросы разных сервисов, поэтому каждый запрос несёт адрес и номер:

```
запрос:  {"id": 12, "service": "orders", "method": "track", "data": {"order": 881}}
ответ:   {"id": 12, "ok": true,  "data": {"lat": 55.7, "lon": 37.6}}
ошибка:  {"id": 12, "ok": false, "error": {"code": "not_found", "message": "..."}}
событие: {"event": "courier.moved", "data": {...}, "seq": 41}
```

Номер нужен, потому что ответы приходят не по порядку. Клиент ведёт таблицу «id → ожидающий запрос» и раздаёт входящие: есть `id`
значит закрыть своё ожидание, есть `event` значит отдать подписчикам. Сообщения нельзя различать по порядку прихода: порядок байтов в
соединении сохраняется, а порядок смысла нет.

Клиенты бывают кривыми, и разбор обязан отвечать на мусор. Главный вопрос: можно ли привязать ошибку к `id`. Если запрос разобрался
до номера и сломался дальше, ошибка несёт этот номер, и клиент закроет нужное ожидание. Если номера нет, остаётся ответ с `"id": null`.
Поэтому такой разбор делают вручную по `serde_json::Value` (у него есть `as_u64`, `as_str`, `get`), а не через `#[derive(Deserialize)]`:
derive при любой ошибке возвращает просто `Err`, и номер теряется. Сообщения собирают макросом `json!`, который понимает `Option`
(`None` станет `null`).

События (`seq`) нумеруются внутри соединения подряд: по дырам в нумерации клиент понимает, что что-то потерял, и перезапрашивает состояние.
Номер надо выдавать и класть сообщение в очередь одной операцией под замком. Атомарный счётчик здесь обманчив: каждая операция по
отдельности атомарна, а пара из двух нет, и два потока легко положат номера в очередь не по порядку.

## Таблица методов

Когда методов становится сотня, `match` на строку превращается в свалку, а проверка «нужен ли вход» забывается в сто первом
обработчике. Поэтому методы регистрируют в таблице: ключ `"сервис.метод"`, значение обработчик.

```rust
let table = Table::new()
    .open("orders.status", |data| async move { /* доступно всем */ })
    .private("orders.cancel", |user, data| async move { /* только для вошедших */ });
```

Обработчики разные по типу (каждое замыкание и каждое асинхронное тело имеют свой тип), поэтому в таблице они хранятся стёртыми:
`Arc<dyn Fn(Args) -> Pin<Box<dyn Future<Output = Reply> + Send>> + Send + Sync>`. Регистрирующая функция принимает любое замыкание и
оборачивает его: `Box::pin(f(args))`. При вызове обработчик сначала клонируют из таблицы (`Arc` дёшево), чтобы не держать заимствование
таблицы через `.await`.

Пользователя обработчик получает из сессии соединения, которую заполнил сервер при проверке токена. Брать «кто я» из присланных
данных нельзя: всё, что лежит в `data`, написал клиент, и любой напишет туда чужой номер.

## Параллельные запросы и потолок

Клиент открыл экран и отправил пять запросов. Если сервер выполняет их по одному, экран ждёт сумму задержек, а один медленный запрос
запирает остальные. Нужно запускать каждый запрос отдельной задачей и отправлять ответ, как только он готов, с его собственным `id`.

Но «каждый запрос в `tokio::spawn`» без потолка даёт злому клиенту рычаг: десять тысяч запросов превращаются в десять тысяч задач.
Поэтому на соединение выдаётся пачка разрешений, `Semaphore`. Разрешение берут до чтения следующего запроса и возвращают, когда
ответ отправлен. Тогда давление идёт по цепочке назад: запросы остаются во входной очереди, дальше в буфере TCP, и клиент упирается
в потолок сам, а память сервера не растёт.

- `Semaphore::acquire_owned()` отдаёт разрешение, которое можно унести в задачу и которое вернётся само при её завершении (в том числе
  при панике).
- `JoinSet` собирает запущенные задачи в одно место; `join_next().await` отдаёт результат очередной готовой. Когда вход закончился,
  цикл не завершают сразу, а дожидаются всех задач в `JoinSet`: иначе принятые запросы останутся без ответа.
- Паника обработчика не должна ломать соединение и терять разрешение. Если запустить обработчик отдельной задачей и дождаться её
  `JoinHandle`, паника придёт в виде `Err(JoinError)`, и на этот `id` можно ответить ошибкой.

## Push: сервер говорит первым

Кроме ответов, шлюз сам шлёт события, и они идут по тому же соединению вперемешку с ответами. Клиенту нужно отличать их по форме (у
ответа `id`, у события `event`), а серверу нужно, чтобы очередь была одна: тогда два сообщения не перемешиваются на уровне байтов, и не
нужно придумывать, кто пишет в сокет первым.

## Остановка без шторма

Деплой новой версии: старый процесс должен уйти, а у него тысячи соединений. Вежливый порядок такой:

1. Перестать принимать новые подключения.
2. Каждому открытому соединению отправить Close с кодом 1001 («сервер уходит»). Код говорит клиенту «это не сбой, переподключись».
3. Подождать, пока соединения закроются сами. Срок общий на всех: `deadline = now + grace` и `timeout_at(deadline, ...)` для
   каждой задачи по очереди. Иначе остановка с десятью упрямыми соединениями длилась бы десять сроков.
4. Оставшихся оборвать: `JoinHandle::abort()` и дождаться завершения, чтобы деструкторы точно отработали.

Порядок важен: сначала всем отправить Close, потом ждать. Если ждать после каждой отправки, один упрямый клиент задержит Close для всех
остальных.

Теперь клиентская сторона. Если после 1001 все тысяча клиентов переподключатся в ту же миллисекунду, новый экземпляр захлебнётся, часть
получит отказ и снова повторит ту же попытку залпом. Это называют thundering herd. Лекарство на клиенте: пауза между попытками растёт
(1, 2, 4 секунды) и содержит случайную добавку (jitter), чтобы клиенты рассеялись по времени.

## Типичные ошибки

- Чистка реестра в конце функции вместо `Drop`. Утечка копится месяцами.
- `send().await` под замком. Работает на стенде, замораживает всё при первом медленном клиенте.
- Безграничная очередь исходящих. Работает, пока клиенты читают.
- Таймер, сбрасываемый на каждом круге цикла. Молчуны живут вечно.
- Чтение внутри `select!`, которое теряет недочитанное.
- Токен в тексте ошибки или в логе. Он живёт там дольше, чем сам токен.
- Ответ на мусорное сообщение без `id`, когда `id` можно было достать.
- `unwrap()` на замке в `Drop`. Падает как раз тогда, когда уже что-то упало.
