# TCP-сервер на много клиентов

В прошлой главе ты научился говорить с одним собеседником. Настоящий сервер говорит с
тысячей одновременно и не имеет права упасть, зависнуть или тихо потерять чьи-то байты, пока
ты спишь. Эта глава про то, как сделать сервер, которому можно доверить ночное дежурство:
цикл accept, изоляция сбоев, лимиты, таймауты, настройка сокета и аккуратная остановка.

## Цикл accept и задача на соединение

Простейший сервер выглядит почти очевидно:

```rust
loop {
    let (stream, _) = listener.accept().await?;
    send_greeting(stream).await;
}
```

И работает, пока клиент один. Пока `send_greeting` занимается первым (а он, скажем, медленно
пишет приветствие), второй ждёт в очереди ядра: `accept` просто не вызывается. Нужно, чтобы
работа над соединением шла отдельно от цикла. Для этого в tokio есть `tokio::spawn`: он
запускает future как самостоятельную задачу и сразу возвращает управление.

```rust
loop {
    let (stream, peer) = listener.accept().await?;
    tokio::spawn(async move {
        println!("клиент {peer}");
        send_greeting(stream).await;
    });
}
```

Теперь цикл тратит на каждого клиента микросекунды: принял, отдал задаче, вернулся за
следующим. Задача tokio стоит в несколько сотен байт, а не в мегабайт стека, как поток, поэтому
десятки тысяч соединений это нормально.

```
          очередь ядра              цикл accept            задачи
клиент ->  [ A, B, C ]  --accept-->   принял A  --spawn-->  задача A
                                      принял B  --spawn-->  задача B
                                      ...                   ...
```

## Один сбой не роняет остальных

Самая частая ошибка новичка выглядит невинно: `handle(stream).await?` в самом цикле. Клиент
прислал мусор, `handle` вернул ошибку, `?` вынес её из цикла, `serve` завершилась, сервер
перестал принимать всех. Один злой или просто кривой клиент положил сервис.

Правило простое. На `accept` (и то осторожно, ниже) знак `?` допустим, на обработке
соединения нет. Ошибка соединения логируется и забывается. Паника тоже: если обработчик
живёт в своей `tokio::spawn`, паника кончит только эту задачу, и tokio вернёт её в
`JoinHandle` как `JoinError`, а цикл ничего не заметит.

Теперь про сам `accept`. Он тоже может вернуть ошибку, и ошибки бывают двух сортов. Сломанный
слушатель это постоянная беда, тут выходить правильно. Но есть и временные: клиент ушёл, пока
соединение лежало в очереди (`ConnectionAborted`), или кончились дескрипторы файлов
(`EMFILE` у процесса, `ENFILE` у системы; в Linux и macOS это коды 24 и 23, их отдаёт `e.raw_os_error()`). Дескрипторы освободятся, когда часть клиентов
уйдёт. Если выйти, сервер умрёт ровно когда ему тяжело. Если тут же звать `accept` снова, он
мгновенно вернёт ту же ошибку, и цикл превратится в горячий, который доест остатки процессора.
Правильный ответ: короткая пауза (десятки миллисекунд) и снова accept.

## Обработчик не обязан знать про сокет

Функция, которой нужны только «читать» и «писать», не должна принимать `TcpStream`:

```rust
async fn handle<S: AsyncRead + AsyncWrite + Unpin>(stream: S) -> io::Result<()> { ... }
```

Тогда её можно проверять на `tokio::io::duplex`, паре связанных в памяти потоков: быстро,
без портов, без таймаутов, сколько угодно раз. А позже под тем же обработчиком окажется TLS
или WebSocket, и он не заметит разницы. Чтобы читать и писать из одной переменной
`S`, её делят: `tokio::io::split(stream)` работает для любого потока.

## Две половинки одного сокета

Читать и писать сразу нужно постоянно: сервер шлёт уведомления, пока клиент присылает
команды. Для сокета есть два способа разделить его, и оба о том, кто чем владеет:

```
stream.into_split()   ->  (OwnedReadHalf, OwnedWriteHalf)   владеют сокетом, можно в разные задачи
stream.split()        ->  (ReadHalf<'_>, WriteHalf<'_>)      заимствуют, живут в одной задаче
```

`into_split` нужен, когда читать и писать должны разные `tokio::spawn`: половинки `'static`
и их можно переезжать. `split` дешевле (без `Arc` внутри) и подходит, когда обе половинки
остаются в одной задаче и ты ждёшь их через `select!`:

```rust
let (mut rd, mut wr) = stream.split();
loop {
    tokio::select! {
        n = rd.read(&mut buf) => { /* пришли данные от клиента */ }
        msg = outbox.recv()   => match msg {        // outbox это mpsc::Receiver<String>
            Some(line) => wr.write_all(line.as_bytes()).await?,
            None => break,
        },
    }
}
```

Про `select!` важная вещь. Когда одна ветка выигрывает, остальные future просто выбрасываются.
Если у выброшенного future была недоделанная работа (например `read_exact` уже вынул пять
байт из восьми), эта работа теряется вместе с ним. Поэтому в `select!` ставят операции,
безопасные к отмене: `read`, `accept`, `recv`, `Lines::next_line`, `interval.tick()` (первый `tick` срабатывает сразу, а не через период). А
`read_exact`, `read_line` или `write_all` в `select!` без особой нужды не ставят. Документация
tokio у каждого метода пишет, безопасен ли он к отмене.

## Одна writer-задача на соединение

Пока в сокет пишет одна задача, всё просто. Когда пишут многие (ответ на запрос, рассылка
из чата, пульс), прямая запись из каждого места ломается: нужна блокировка сокета на время
всей строки, а ещё нужно как-то узнавать, что сокет умер. Принятое решение другое:
сокетом владеет **одна задача-писатель**, а остальные отправляют ей строки через `mpsc`.

```
 задача A ──┐
 задача B ──┼─ mpsc ──>  writer-задача  ──write_all──>  сокет
 рассылка ──┘
```

Строки не перемешиваются (пишет только один), порядок каждого отправителя сохраняется, а
когда сокет умирает, writer завершается, канал закрывается, и все отправители узнают об этом
по ошибке `send`. Канал делают **ограниченным**: медленный клиент иначе накопит в памяти
сколько угодно сообщений и убьёт весь сервер. Дальше выбор политики: ждать (`send().await`),
выкинуть новое (`try_send`) или отключить медленного.

## Лимит соединений

Любой ресурс конечен: дескрипторы, память, процессорное время. Сервер, который принимает всех,
умирает от тысячи медленных клиентов. Лимит ставят `tokio::sync::Semaphore`:

Семафор это счётчик свободных мест. `acquire().await` берёт место или ждёт, пока оно появится,
а когда «квитанция» (permit) уничтожается, место возвращается. Пример на другом деле: не больше
трёх одновременных загрузок на диск, как бы много задач их ни просило.

```rust
let slots = Arc::new(Semaphore::new(3));

async fn save(slots: Arc<Semaphore>, data: Vec<u8>) {
    let _permit = slots.acquire_owned().await.unwrap();   // ждём свободное место
    write_to_disk(&data).await;
}                                                         // _permit уничтожен, место свободно
```

Для лимита соединений тот же семафор ставят в accept-цикл, и здесь важен порядок действий.
Если взять место после `accept`, то сервер уже принял сокет (дескриптор, буферы ядра) и
просто стоит с ним в руках. А если до, то пока мест нет, лишние клиенты ждут в
очереди ядра (backlog) и ничего серверу не стоят. Квитанцию держит задача соединения, и она
возвращается сама при завершении задачи, даже если та запаниковала.

## Тишина тоже расход: таймаут простоя

Подключившийся и молчащий клиент занимает место под лимитом навсегда. Поэтому на каждое
чтение вешается таймаут (`tokio::time::timeout(idle, stream.read(&mut buf))`), и простой
считается от **последнего принятого байта**: клиент, который шлёт хоть по байту, жив. По
истечении времени соединение закрывают. Это тот же приём, что keep-alive в HTTP и ping в
WebSocket, только на уровне TCP.

## Опции сокета: TcpSocket

`TcpListener::bind` делает всё сразу и не оставляет места для настройки. Часть опций работает
только до `bind` или `connect`, поэтому для них есть «сырой» `TcpSocket`:

```rust
let socket = TcpSocket::new_v4()?;
socket.set_keepalive(true)?;               // ядро само проверит, что собеседник жив
socket.set_recv_buffer_size(256 * 1024)?;  // размер буфера приёма
let stream = socket.connect(addr).await?;  // клиентский сокет с этими настройками
```

Для сервера то же самое, только вместо `connect` идут `bind(addr)` и `listen(backlog)`,
которые возвращают `TcpListener`.

Опции, которые стоит знать:

- **SO_REUSEADDR.** После закрытия соединения сторона, закрывшая первой, ещё около минуты
  помнит его в состоянии TIME_WAIT: ядро защищается от запоздавших пакетов. Сервер, который
  перезапустили сразу после остановки, без этой опции получит `AddrInUse`. С ней bind
  проходит. (tokio включает эту опцию для `TcpListener::bind` на Unix, но с `TcpSocket` её надо
  ставить самому.)
- **backlog.** Размер очереди соединений, для которых ядро уже сделало рукопожатие, а твой
  `accept` их ещё не взял. Если очередь полна, новые SYN игнорируются, и клиент видит
  странные задержки в секунду-другую.
- **TCP_NODELAY.** Про него ниже. Его можно поставить прямо на `TcpSocket` до `connect`: `socket.set_nodelay(true)?`.

## Алгоритм Nagle: почему «два мелких write» иногда медленные

Отправлять по пакету на каждый байт расточительно: в пакете заголовки в 40 байт. Алгоритм
Nagle экономит: если есть неподтверждённые данные, новые мелкие кусочки копятся в буфере и
уходят одним пакетом, когда придёт подтверждение (ACK). Получатель, в свою очередь, не торопится
с ACK: ждёт до 40 мс, вдруг будет ответ, к которому его можно прицепить (отложенный ACK).
Вместе два разумных правила дают неожиданную паузу в десятки миллисекунд: «я отправил два
мелких сообщения подряд и жду ответа, а ответ не идёт».

Для интерактивных протоколов (чат, RPC, игры, всё, что построено на «запрос и быстрый ответ»)
включают `set_nodelay(true)`: мелкие записи уходят сразу. Для потока больших данных не нужно:
там пакеты и так полные. Самое надёжное лечение вообще не писать мелкими кусками: собери
сообщение целиком и сделай один `write_all`. Смотри визуализацию `nagle_delay`.

## Подсмотреть байты: обёртка над потоком

Когда протокол «не работает», первый вопрос: что на самом деле шло по проводу? Ответ это
обёртка `Tap<S>`: она сама реализует `AsyncRead + AsyncWrite`, вызывает внутренний поток
и записывает, что через неё прошло. Обёртка не знает, что внутри, сокет или `duplex`. Идея для записи или чтения: запомнить, сколько байтов уже лежало (`buf.filled().len()`), вызвать внутренний метод и посмотреть только то, что добавилось после.
Она пригодится в каждой следующей главе.

Трейты `AsyncRead` и `AsyncWrite` устроены на `poll`-методах: они не `async`, а возвращают
`Poll::Ready(..)` или `Poll::Pending`. Вот обёртка на другом деле, которая переводит всё
прочитанное в верхний регистр, это покажет все приёмы:

```rust
struct Shout<S> { inner: S }

impl<S: AsyncRead + Unpin> AsyncRead for Shout<S> {
    fn poll_read(self: Pin<&mut Self>, cx: &mut Context<'_>, buf: &mut ReadBuf<'_>) -> Poll<io::Result<()>> {
        let this = self.get_mut();                     // можно, потому что S: Unpin
        let before = buf.filled().len();               // сколько уже лежало в буфере
        let poll = Pin::new(&mut this.inner).poll_read(cx, buf);
        if let Poll::Ready(Ok(())) = poll {            // Pending значит «пока ничего не случилось»
            buf.filled_mut()[before..].make_ascii_uppercase();
        }
        poll
    }
}
```

У записи (`poll_write`) то же, только возвращается `Poll<io::Result<usize>>`, где число это
сколько байтов **реально принято**. Оно вправе быть меньше, чем предложено, и журналить нужно
ровно принятые. Методы `poll_flush` и `poll_shutdown` у обёртки обычно просто передают вызов внутрь.

## Мягкая остановка

Остановка сервера тоже часть его работы. Убить процесс резко значит оборвать чьи-то запросы
на полуслове, а ждать без дедлайна значит застрять навсегда на клиенте, который не уходит.
Правильный порядок такой:

```
SIGTERM -> выйти из цикла accept -> закрыть слушателя (порт закрыт, новые получат Refused)
        -> дать текущим соединениям время (grace) -> оборвать оставшихся -> выйти
```

В коде это `select!` между `accept` и сигналом, потом `drop(listener)`, потом ожидание задач
с `timeout(grace, ...)`. Задачи хранят в `JoinSet`: он знает, сколько их осталось, умеет
дождаться каждой и оборвать всех разом (`abort_all`). Завершённые задачи лежат в нём, пока их не забрали через `join_next` или `try_join_next`, поэтому в долгоживущем цикле их собирают, иначе память растёт. Есть и вторая половина: сигнал должен
добраться до самих соединений, иначе молчащий клиент удержит остановку на весь дедлайн. Для
этого годится `tokio::sync::watch`: он хранит последнее значение, поэтому даже опоздавший
подписчик увидит, что остановка уже объявлена. Соединение ждёт данных и изменения `watch` в
`select!` и, увидев сигнал, прощается с клиентом.

Если этого не делать, `main` просто вернётся, и tokio при закрытии рантайма отменит все
задачи: соединения оборвутся без единого слова. Смотри визуализацию `graceful_stop`.

## Прокси: две стороны одного разговора

Прокси соединяет два сокета и гонит байты в обе стороны. Тонкостей три. Закрытие записи
(EOF) с одной стороны нужно передать вперёд, как `shutdown` на противоположной стороне: иначе
собеседник вечно ждёт конца сообщения. При этом встречное направление живёт дальше: пока не
пришёл свой EOF, оно может нести ответ. Любая ошибка (сброс, обрыв) означает, что ждать вторую
сторону незачем: оба направления нужно оборвать, иначе клиент повиснет. Для «дождись двух
future, но брось второе при первой ошибке» в tokio есть `tokio::try_join!`.

## Типичные ошибки

- `?` на результате `handle` в самом цикле. Один плохой клиент останавливает сервер.
- Обработчик без `spawn`. Клиенты ждут друг друга.
- Выход из цикла на `EMFILE`, либо повтор без паузы.
- Permit семафора после `accept`. Лимит есть, защиты нет.
- `Mutex` через `.await`. Держи блокировку коротко, рассылай через `try_send`.
- Неограниченные очереди на соединение. Медленный клиент ест память без предела.
- `read_exact` или `read_line` в `select!`. Пропадают частично прочитанные байты.
- Забытый `shutdown` у writer-задачи. Читатель на другом конце не получает EOF.
- Остановка без дедлайна или сигнал, который не дошёл до соединений.
- Закрыть оба направления на первом EOF в прокси. Ответ, который ещё в пути, потеряется.
