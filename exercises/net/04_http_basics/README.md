# HTTP/1.1 изнутри

Ты набираешь `curl http://recipes.test/recipes/7`, и через мгновение приходит JSON. Между этими двумя
событиями по сети пробежало вот что (это настоящие байты, так выглядит всё общение):

```
GET /recipes/7?lang=ru HTTP/1.1\r\n
Host: recipes.test\r\n
Accept: application/json\r\n
\r\n

HTTP/1.1 200 OK\r\n
Content-Type: application/json\r\n
Content-Length: 26\r\n
\r\n
{"id":7,"title":"Borscht"}
```

Весь HTTP это текст поверх TCP. Тебе уже знакомо главное из прошлых глав: TCP отдаёт поток байтов
без границ сообщений, а HTTP как раз договаривается, где эти границы. Значит, сервер это цикл: накопил
байты, понял, что запрос целиком пришёл, разобрал, ответил. Эта глава про «понял» и «разобрал», и про то,
как это делать, чтобы тебя не обманул чужой клиент. Подсказка: любой парсер, глядящий в сеть, читает
входные данные противника.

Ты можешь открыть сырые байты сам. Запусти любой сервер и подключись так: `nc 127.0.0.1 8080`, набери
запрос руками (Enter в `nc` отправляет `\n`, а нужен `\r\n`, для этого есть `nc -C` на macOS или
`printf 'GET / HTTP/1.1\r\nHost: x\r\n\r\n' | nc ...`). Или `curl -v`: он показывает отправленное строками `>`.

## Устройство запроса

```
 строка запроса   GET /recipes/7?lang=ru HTTP/1.1 CRLF
 заголовки        Host: recipes.test CRLF
                  Accept: application/json CRLF
 пустая строка    CRLF
 тело (если есть) ...байты...
```

Смотри визуализацию `http_request_anatomy`: на ней запрос раскрашен по частям.

**Строка запроса.** Три части через один пробел: метод (`GET`, `POST`, ... чувствителен к регистру),
цель и версия. Цель в обычном запросе это путь с необязательным запросом после `?`. Фрагмента (`#...`)
в запросе не бывает: его оставляет браузер у себя.

**Заголовки.** `Имя: значение`. Имя без пробелов и без учёта регистра, значение без пробелов по
краям. Одно имя может быть много раз (`Set-Cookie`), порядок сохраняют. Между именем и двоеточием пробела
быть не должно. Это правило не прихоть: на разных толкованиях такого пробела строили атаки.

**Конец головы** это пустая строка, то есть четыре байта `\r\n\r\n`. Данные приходят кусками, поэтому
их искать надо во всём накопленном буфере: терминатор может прийти разрезанным. А ещё голове нужен
предел размера и числа заголовков, иначе клиент, который никогда не присылает пустую строку, заставит
сервер копить память бесконечно. Одного размера мало: медленный клиент (slowloris) укладывается во все
размеры и всё равно держит соединение, для него нужен ещё дедлайн на получение головы.

## Процентное кодирование

В адресе нельзя прямо писать пробел, `&`, `#` и не-ASCII. Их записывают как `%XX`, где `XX` это байт в hex:
пробел `%20`, `/` `%2F`, `я` это два байта UTF-8, `%D1%8F`. В части после `?` (форма) пробел часто пишут
плюсом, а в пути плюс остаётся плюсом.

```
/search?q=cats+%26+dogs&lang=en       ->   q = "cats & dogs",  lang = "en"
```

Две ловушки. Раскодировать нужно **после** разбиения на структуру: `%26` это амперсанд внутри
значения, а не разделитель. И раскодировать надо один раз: `%252F` это `%2F`, а не `/`. Плюс ловушка с
байтами: последовательность `%C3` сама по себе не UTF-8, и она обязана стать ошибкой, а не мусором.

## Где кончается тело

Это главный вопрос парсера. Тело бывает тремя видами, смотри `http_body_framing`:

1. **Content-Length: N.** Ровно N байтов. Считаются **байты**, не символы. Всё после этого принадлежит
   следующему запросу на том же соединении. Заявленную длину сверяют с лимитом сразу, не ожидая данных:
   иначе `Content-Length: 4000000000` заставит сервер ждать и выделять память.
2. **Transfer-Encoding: chunked.** Тело идёт кусками, когда длина заранее неизвестна:

   ```
   4\r\n
   Wiki\r\n
   5\r\n
   pedia\r\n
   0\r\n
   \r\n
   ```

   Размер каждого куска в hex, потом данные, потом CRLF; кусок нулевого размера закрывает тело (после
   него могут быть трейлеры, строки заголовков). Данные куска могут содержать CRLF: полагаться можно
   только на размер. После hex-размера может стоять расширение (`5;name=value`): его принято
   игнорировать. Строка размера ограничена по длине, иначе клиент, не присылающий CRLF, копит память.
3. **Закрытие соединения.** Для ответа без длины и без chunked тело кончается, когда сервер закроет
   соединение. Тогда keep-alive невозможен. Запросы так не бывают: тело запроса без длины пусто.

Если указаны сразу и длина, и chunked, или два разных `Content-Length`, это двусмысленный запрос.
Фронтовой прокси и бэкенд могут прочитать его по-разному, и тогда хвост, который один считает телом, другой
примет за новый запрос. Это контрабанда запросов (request smuggling), и лечится она только отказом:
двусмысленное не принимают.

## Инкрементальный парсер

Парсеры сети почти всегда устроены одинаково: функция берёт накопленный буфер и отвечает одно из трёх:

```
Ok(Partial)                  пока мало, позови, когда придёт ещё
Ok(Complete(запрос, n))      запрос готов, он занял первые n байтов буфера
Err(...)                     вход нарушает правила, дальше ждать бессмысленно
```

Число `n` говорит вызывающему коду, сколько байтов выбросить из буфера: ровно один запрос уйдёт, и можно сразу разбирать следующий, лежащий в
том же буфере (клиент вправе слать запросы подряд, не дожидаясь ответа: pipelining). Хороший парсер
обязан проходить простое испытание: возьми готовый запрос, отрежь любой префикс, и ответ должен быть
`Partial`. А ошибки (плохая версия, два Content-Length) он находит сразу, как только голова пришла,
не дожидаясь тела.

## Ответ

Ответ устроен так же: строка статуса, заголовки, пустая строка, тело.

```
HTTP/1.1 404 Not Found\r\n
Content-Length: 0\r\n
\r\n
```

Самые частые коды и причины (имена из RFC 7231): 200 OK, 201 Created, 204 No Content, 301 Moved Permanently,
302 Found, 304 Not Modified, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found,
405 Method Not Allowed, 408 Request Timeout, 413 Payload Too Large, 431 Request Header Fields Too Large,
500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable. Новые RFC местами переименовали причины
(413 теперь Content Too Large), клиенты на причину не опираются: важен только код.

Код ответа делится на классы по первой цифре: 1xx информация, 2xx успех, 3xx перенаправление, 4xx вина клиента,
5xx вина сервера. Неизвестный код имеет класс, даже если его причину ты не знаешь. У `204` и `304` (и у всех `1xx`) тела
нет, и Content-Length там не пишут. Ответ на `HEAD` устроен как на `GET`, включая Content-Length, но тела нет:
клиент так узнаёт размер, не скачивая файл. Тело, сгенерированное из ввода пользователя, и заголовки, в которые
попал его ввод (редирект на `?next=`, имя в cookie), опасны: если во вводе есть CR или LF, он закончит заголовок
и допишет чужие. Это расщепление ответа, и сборщик ответа должен сам отвергать управляющие символы.

## Keep-alive и Host

В HTTP/1.1 соединение по умолчанию остаётся открытым на несколько запросов; в 1.0 по умолчанию закрывается.
Заголовок `Connection` с токенами (`close`, `keep-alive`, через запятую, в любом регистре, возможно в нескольких
строках) меняет это. `Host` в 1.1 обязателен ровно один раз и не может быть пустым: по нему сервер выбирает, какому из своих сайтов
отвечать.

## Типичные ошибки

- Искать `\r\n\r\n` только в новом куске, а не во всём буфере.
- Использовать `split_whitespace` вместо одиночного пробела: он прощает то, что прощать нельзя.
- Раскодировать процентные последовательности до разбиения на параметры.
- Считать Content-Length в символах.
- Доверять числу из сети: размер куска или длина тела никогда не определяют размер выделения памяти.
- Брать первый из двух Content-Length «на всякий случай» вместо отказа.
- Копаться в теле запроса по строкам: тело это байты, в них бывает что угодно, включая `\r\n\r\n` и нули.
- Подставлять ввод пользователя в заголовок ответа без проверки на CR и LF.
