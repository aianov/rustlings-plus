# Итераторы углублённо

Сервер за ночь накопил миллион строк лога, а утром нужны три вещи: последние пять ошибок, сколько их было
всего и от какого модуля пришла самая первая. Можно прочитать всё в вектор, отфильтровать в другой вектор и
так далее, но каждая промежуточная коллекция это память и время на то, что в итоге выбросят. Итераторы
позволяют описать «что сделать со строками» цепочкой, а исполнить её ровно настолько, насколько нужно ответу:
пять ошибок найдены, на пятой всё останавливается. Анимация (клавиша `v`) показывает, как элементы тянутся через
цепочку по одному.

```rust
let last_errors: Vec<&str> = log.lines()
    .filter(|l| l.contains("ERROR"))
    .map(|l| l.trim())
    .take(5)
    .collect();
```

## Как устроен Iterator

```rust
trait Iterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;     // единственный обязательный метод
    // ...сотни готовых методов, построенных на next
}
```

`next` отдаёт `Some(элемент)`, пока есть что отдавать, и `None`, когда кончилось. Цикл `for x in it` это
`while let Some(x) = it.next()`. Всё остальное (`map`, `filter`, `sum`) написано поверх `next`, поэтому своя
структура с одним методом получает их все бесплатно. Итератор хранит состояние («где я»), поэтому
`next` берёт `&mut self`, а сам итератор для вызова `next` должен быть объявлен `mut`.

Договор такой: после первого `None` итератор *может* продолжить отдавать `Some` (стандартные так не делают,
но язык этого не запрещает). Когда нужна гарантия, пользуются `.fuse()`: он после первого `None` отвечает
`None` всегда.

## Ленивость

Адаптеры (`map`, `filter`, `take`, `zip`, `enumerate`) ничего не делают. Они оборачивают итератор в новый
итератор. Работа начинается, только когда кто-то **потребляет**: `collect`, `sum`, `count`, `for`, `last`, `find`.

```rust
let doubled = numbers.iter().map(|n| { println!("double {n}"); n * 2 });   // тишина
let first = doubled.take(1).count();                                       // «double» напечатано один раз
```

Из-за этого `map` с побочным эффектом без потребителя не выполнится вообще (компилятор предупредит:
`unused_must_use`), а цепочка с `take` или `find` просматривает ровно столько элементов, сколько нужно. Побочные эффекты в
`map` вообще лучше не прятать: `for` или `for_each` читаются честнее. Элементы идут через цепочку **по одному**
от источника к потребителю, а не «сначала весь `map`, потом весь `filter`».

## iter, iter_mut, into_iter

```
  .iter()        &T      читаем, коллекция остаётся
  .iter_mut()    &mut T  меняем на месте
  .into_iter()   T       забираем элементы, коллекция съедена
```

`for x in &v` это `v.iter()`, `for x in &mut v` это `v.iter_mut()`, `for x in v` это `v.into_iter()` и вектор
после цикла недоступен. Известная ловушка: цикл по значению внутри другого цикла забирает коллекцию на
первой же итерации, а на второй компилятор говорит «value moved in previous iteration». Для своего типа
эти три формы дают три реализации `IntoIterator`: для `Type`, для `&Type` и для `&mut Type`. Тип итератора
записывают в `type IntoIter`, чаще всего это `std::slice::Iter<'a, T>`, `IterMut<'a, T>` или `vec::IntoIter<T>`.

Скелет для обёртки над вектором такой:

```rust
struct Bag(Vec<u8>);
impl IntoIterator for Bag { type Item = u8; type IntoIter = std::vec::IntoIter<u8>; fn into_iter(self) -> Self::IntoIter { self.0.into_iter() } }
impl<'a> IntoIterator for &'a Bag { type Item = &'a u8; type IntoIter = std::slice::Iter<'a, u8>; fn into_iter(self) -> Self::IntoIter { self.0.iter() } }
impl<'a> IntoIterator for &'a mut Bag { type Item = &'a mut u8; type IntoIter = std::slice::IterMut<'a, u8>; fn into_iter(self) -> Self::IntoIter { self.0.iter_mut() } }
```

## Словарь

Адаптеры, которые меняют поток:
- `map`, `filter`, `filter_map` (map и отбрасывание `None`), `flat_map`, `flatten` (раскрыть вложенность);
- `enumerate` (пары с номером), `zip` (две последовательности в пары, короткая определяет конец),
  `chain` (одна за другой), `rev` (с конца, если итератор умеет), `skip`, `take`, `step_by`;
- `take_while`, `skip_while`, `map_while` (остановиться, когда `map` вернул `None`): `take_while` и `map_while` **съедают**
  первый элемент, который не подошёл, а `skip_while` его **отдаёт** (пропускает, пока условие истинно, и с
  первого ложного отдаёт всё подряд);
- `inspect` (подсмотреть), `peekable` (заглядывать вперёд), `fuse`, `cloned` и `copied` (превратить `&T` в `T`).

Потребители:
- `collect`, `sum`, `product`, `count`, `last`, `nth` (отдать n-й и забрать все до него), `min`, `max`;
- `min_by_key`, `max_by_key`, `min_by`, `max_by`. Важная мелочь: при равенстве `max_*` отдают
  **последний** из равных, а `min_*` **первый**;
- `find`, `find_map`, `position`, `any`, `all` останавливаются, как только знают ответ;
- `fold`, `reduce`, `try_fold`, `partition`, `unzip`, `for_each`.

Чаще всего ошибаются на границах: пустой ввод (`all` на пустом всегда `true`, `max` даёт `None`), `step_by(0)`
паникует, `zip` обрывается по короткой стороне.

## collect и его цели

`collect` собирает в любой тип, умеющий `FromIterator`, а выбирается тип по ожиданию: аннотации, турбофишу
или возвращаемому типу.

```rust
let names: Vec<&str> = line.split(',').collect();
let letters: String = word.chars().rev().collect();
let by_id: HashMap<u32, &User> = users.iter().map(|u| (u.id, u)).collect();
let uniq = words.iter().copied().collect::<BTreeSet<_>>();
```

Подвохи. При сборе пар в `HashMap` или `BTreeMap` повторяющийся ключ **затирает** прежнее значение:
суммировать или группировать приходится вручную через `entry`. А `Result<Vec<T>, E>` и `Option<Vec<T>>` тоже
цели `collect`: сбор прерывается на первой ошибке (`Err` или `None`) и отдаёт её, остальные элементы не
разбираются. Если нужно не прервать, а разделить, есть `partition` (по предикату в две коллекции) и
`unzip` (поток пар в две коллекции).

## fold, scan, try_fold

`fold(начало, |накопитель, элемент| ..)` сворачивает поток в одно значение; `reduce` то же без начального
(первый элемент становится им, результат `Option`); `scan` похож на `fold`, но отдаёт каждое промежуточное
состояние как элемент и может остановиться, вернув `None`. Когда шаг может провалиться и остановка нужна
на первой ошибке, пишут `try_fold`: замыкание возвращает `Result` или `Option`, а `?` внутри прерывает обход.
`fold` с `Result` в накопителе работает, но **не** останавливается: он дочитает все элементы до конца.

## peekable, by_ref и «кто съел элемент»

`peekable()` добавляет `peek` (заглянуть, не забирая) и `next_if(условие)` (взять, только если подходит):

```rust
let mut it = text.chars().peekable();
while let Some(&c) = it.peek() {
    if c.is_ascii_digit() { digits.push(c); it.next(); } else { break; }
}
```

Так читают токены: нельзя понять, что число кончилось, не посмотрев на следующий символ. Другая тонкость:
адаптеры берут итератор по значению, и `it.take(3)` забирает `it` целиком. Чтобы взять часть и продолжить
с остатка, дают адаптеру ссылку: `it.by_ref().take(3)`. Для `take_while` помни, что первый непрошедший
элемент уже прочитан и потерян. Если он нужен, используют `peekable` и `next_if`.

## Итераторы без структур

```rust
let evens = std::iter::successors(Some(0u32), |&n| n.checked_add(2));      // из предыдущего следующее
let mut n = 0;
let ids = std::iter::from_fn(|| { n += 1; Some(n) });                      // замыкание с состоянием
let one = std::iter::once(7);  let noise = std::iter::repeat_with(|| rand());
```

`successors` заканчивается, когда замыкание вернуло `None`, `from_fn` когда `None` вернуло оно само. Оба могут быть
бесконечными, и обычно после них стоит `take` или `take_while`.

## impl Iterator в аргументах и результатах

```rust
fn cheap(items: &[Item]) -> impl Iterator<Item = &Item> { items.iter().filter(|i| i.price < 10) }
fn total(it: impl Iterator<Item = u32>) -> u32 { it.sum() }
```

В результате `impl Iterator` значит «один конкретный тип, которого я не называю». Вызывающий получает ленивый
итератор и сам решает, собирать ли его. Если итератор заимствует из `self` или из аргумента, он живёт не дольше
заимствованного. В редакции 2024 это записывается само (результат захватывает все lifetime из сигнатуры),
в старых писали `impl Iterator + '_`. Из этого следует главное ограничение: итератор не может ссылаться
на то, что создано внутри функции. Типичные ошибки: замыкание в `filter` держит локальную переменную
(лечится `move`, тогда замыкание владеет ею) или итератор вернул `.iter()` локального вектора (вернуть надо
владеющий `into_iter()` или не создавать вектор). Когда типов бывает несколько, нужен `Box<dyn Iterator>`.

## size_hint, ExactSizeIterator, DoubleEndedIterator

`size_hint()` возвращает `(минимум, Some(максимум))`: подсказка для `collect`, сколько выделить памяти.
Для честных итераторов с точной длиной границы совпадают, и тогда можно добавить `ExactSizeIterator` (метод `len`).
`DoubleEndedIterator` (метод `next_back`) позволяет брать с конца, а вместе с ним заработает `rev`. Они не
независимы: `enumerate().rev()` и `zip(..).rev()` работают только если источники умеют и то, и другое. Поэтому
`"abc".chars().enumerate().rev()` не собирается, а `[1, 2, 3].iter().enumerate().rev()` собирается.
Концы не должны пересекаться: если спереди взяли два элемента из трёх, сзади остался один.

## FromIterator и Extend

Чтобы твой тип собирался через `collect`, реализуют `FromIterator<Item>`; чтобы работал `extend` (дописать
из итератора), реализуют `Extend<Item>`. Обычно одно выражается через другое: `from_iter` создаёт пустой
экземпляр и вызывает `extend`. Можно реализовать для нескольких типов элементов сразу (например, `String` и `&str`).

## Свой адаптер

Адаптер это структура, которая владеет исходным итератором и сама тоже итератор:

```rust
struct Every<I> { inner: I, n: usize }
impl<I: Iterator> Iterator for Every<I> {
    type Item = I::Item;
    fn next(&mut self) -> Option<I::Item> { /* прочитать n элементов из inner, отдать последний */ }
}
```

Чтобы писать `.every(3)` у любого итератора, добавляют трейт-расширение с общей реализацией:

```rust
trait EveryExt: Iterator + Sized { fn every(self, n: usize) -> Every<Self> { Every { inner: self, n } } }
impl<I: Iterator> EveryExt for I {}
```

Трейт нужно импортировать там, где метод вызывается. Три правила хорошего адаптера: не читать источник
больше, чем нужно для очередного элемента (иначе он не работает на бесконечных), не терять неполный хвост и
не опрашивать источник после его конца (помечай флагом или оборачивай в `fuse`).

## Типичные ошибки

Смещение страницы `номер * размер` может переполниться на больших числах: считай через `checked_mul` (получишь `None`) или `saturating_mul` (упрёшься в потолок). 
Ждать, что `map` без потребителя выполнится. Складывать промежуточные результаты в `Vec` посреди
цепочки, хотя дальше идёт ещё один адаптер. Пользоваться `fold` с `Result`, когда нужен `try_fold`. Перебирать
по значению то, что нужно ещё раз. Брать `max_by_key` и забывать, что при равенстве он отдаёт последнего.
Менять вектор, пока по нему идёшь (сначала собери, что менять, потом меняй). Терять элемент в `take_while`.
Возвращать итератор по локальной переменной.
