# unsafe без страха

Кто-то в игровом сервисе заменил `scores[i]` на `scores.get_unchecked(i)`: профилировщик показывал, что проверка
границ съедает три процента. Всё работало месяц. Потом таблица результатов опустела (сезон закончился),
функция «лучший игрок» прочитала нулевой элемент пустого массива и вернула чужие четыре байта из соседней
структуры. Сервис не упал, не записал ничего в журнал, а в рейтинге появился игрок с именем из мусора. Три
процента скорости стоили трёх дней поиска.

`unsafe` в Rust не злодей, а инструмент: примерно так же в безопасных языках устроена виртуальная машина.
Стандартная библиотека на нём стоит целиком (`Vec`, `Rc`, `Mutex`, `HashMap`), а ты в бэкенде будешь писать его
редко. Но чтобы читать чужой код, понимать `Pin`, `Waker` и аллокаторы в следующих главах и вовремя остановиться,
нужно знать правила игры.

## Что разрешает unsafe

Ровно пять вещей:

1. разыменовать сырой указатель (`*const T`, `*mut T`);
2. вызвать `unsafe fn`;
3. обратиться к изменяемой статической переменной (`static mut`);
4. реализовать `unsafe trait` (`Send`, `Sync`, `GlobalAlloc`);
5. прочитать поле `union`.

И это всё. Блок `unsafe { ... }` не отключает проверки заимствований, типов, владения и времён жизни. Внутри него
по-прежнему нельзя использовать значение после перемещения и нельзя держать две `&mut` на одно через обычные
ссылки. Поэтому `unsafe` не «выключатель», а расписка: «в этих нескольких строках я сам ручаюсь за то, что
компилятор доказать не может». Чем меньше строк в блоке, тем меньше место для ошибки и тем проще
ревью.

## Сырые указатели

```rust
let mut scores = [10, 20, 30];
let first: *const i32 = scores.as_ptr();        // создать указатель можно в безопасном коде
let last: *mut i32 = scores.as_mut_ptr().wrapping_add(2);

let value = unsafe { *first };                   // разыменовать только в unsafe
unsafe { *last = 99 };
```

В отличие от ссылки, сырой указатель ничего не обещает: он может быть нулевым, висячим (память уже
освобождена), не выровненным под тип, или указывать за конец массива. Всё, что ссылка гарантирует, ты проверяешь
сам. Основные операции:

```
p.is_null()           проверка на ноль (безопасная)
p.add(n)              сдвинуть на n ЭЛЕМЕНТОВ (не байт); unsafe: результат обязан остаться в том же выделении
p.offset_from(q)      расстояние в элементах между указателями на один массив; unsafe
p.read() / p.write(v) прочитать / записать без разыменования ссылкой; unsafe
ptr::copy(src, dst, n)              копирование, диапазоны МОГУТ пересекаться (как memmove)
ptr::copy_nonoverlapping(src, dst, n)   диапазоны НЕ должны пересекаться (как memcpy)
slice::from_raw_parts(p, len)       собрать срез из указателя и длины; unsafe
NonNull<T>            указатель, который не бывает нулевым; удобен как поле структуры
```

Типичные ошибки: сдвинуть `add` за конец массива (уже это неопределённое поведение, даже если не читать),
перепутать байты и элементы, забыть, что `u32` по нечётному адресу читать нельзя (нужен `read_unaligned`), использовать
указатель на локальную переменную после выхода из функции.

## unsafe fn и контракт

Функцию, чей вызов с «неудачными» аргументами ломает память, отмечают `unsafe fn`. Условия, при которых вызывать
её можно, записывают в документации в разделе `# Safety`. Каждый `unsafe`-блок у вызывающего сопровождают
комментарием `// SAFETY:` с объяснением, почему здесь условие выполнено.

```rust
/// Возвращает слово без проверки номера.
///
/// # Safety
///
/// `n` должно быть меньше `words.len()`.
pub unsafe fn word_at(words: &[&str], n: usize) -> &str {
    // SAFETY: вызывающий гарантирует n < words.len().
    unsafe { words.get_unchecked(n) }
}

pub fn word_or_empty(words: &[&str], n: usize) -> &str {
    if n < words.len() {
        // SAFETY: границу проверили строкой выше.
        unsafe { word_at(words, n) }
    } else {
        ""
    }
}
```

Видно главное устройство: опасная функция переносит доказательство на вызывающего, а безопасная обёртка
делает проверку сама. Снаружи библиотеки торчит только обёртка, и вся остальная программа остаётся
безопасной. Паника при выходе за границу, кстати, не проблема безопасности: она определённо останавливает
программу. Проблема в чтении чужой памяти без остановки. В редакции 2024 даже тело `unsafe fn` требует
собственных блоков `unsafe { }` вокруг опасных операций: сигнатура говорит про контракт, блок про то, где именно
он используется.

## Неопределённое поведение

UB (undefined behavior) это нарушение правил языка, после которого результат программы не определён вообще. Не «может
упасть», а «компилятор вправе считать, что этого не случится». Поэтому он строит оптимизации на допущениях,
и когда допущение ложно, получается что угодно: верный на вид ответ, мусор, падение через час, исчезнувшая
проверка в другом месте функции.

К UB относятся: чтение или запись за границей выделения, разыменование нулевого или висячего указателя,
невыровненное чтение через обычную ссылку, значение, которое не бывает (`bool` не 0 и не 1, `str` не в UTF-8,
`char` из суррогата), гонка данных, **две живые `&mut` на одни данные** и `&mut` вместе с `&`, которые пересекаются.

Из этого следует неприятное: зелёный тест ничего не доказывает. Код с UB может проходить любые тесты, пока
сборка, флаги и железо складываются удачно, а в другой сборке ломаться. Единственная защита это рассуждение
(условия безопасности записаны и выполняются) и специальные инструменты. Стандартная библиотека в отладочной сборке сама
ловит часть нарушений (например, пересекающиеся диапазоны в `copy_nonoverlapping` или чтение за границей в
`get_unchecked`) и останавливает программу: если видишь «unsafe precondition(s) violated», это не баг
стандартной библиотеки, а подсказка. Отдельный инструмент `miri` (нужен nightly) интерпретирует программу и ищет UB
по-настоящему. В реальных проектах его гоняют в CI на всех тестах с `unsafe`.

## Уникальность &mut

Главное допущение, на котором держится Rust: пока жива `&mut T`, никто другой не видит это значение. Поэтому
компилятор держит значение в регистре, переставляет записи, выбрасывает «лишние» чтения. Два сырых указателя
на одно число спокойно сосуществуют. А вот превратить оба в `&mut` и пользоваться, значит нарушить допущение:

```rust
fn bump_twice(a: &mut i32, b: &mut i32) {
    *a += 1;
    *b += 1;
    *a += 1;
}
```

Оптимизатор вправе сократить это до `*a += 2; *b += 1`, потому что `a` и `b` разные. Если на самом деле это одна
переменная, результат будет другим, а какой именно, зависит от сборки. Именно поэтому безопасная функция,
выдающая две `&mut` (на одни индексы, на пересекающиеся окна), обязана проверять, что цели различны.

## UnsafeCell

Если у тебя есть `&T`, компилятор считает данные за ней неизменными. Привести `&T` к `*mut T` и записать, значит
нарушить это допущение. Единственное исключение, встроенное в язык, это `UnsafeCell<T>`: при его наличии
компилятор отключает допущение «за `&` ничего не меняется». Метод `get(&self) -> *mut T` и есть единственная
законная дорога от общей ссылки к записи.

```
Cell<T>, RefCell<T>, Mutex<T>, RwLock<T>, AtomicU32, OnceCell<T>  ←  все построены на UnsafeCell
```

Сам `UnsafeCell` не обещает ничего: за корректность отвечает обёртка. `Cell` корректна, потому что она не `Sync`
(один поток) и не выдаёт ссылки наружу. `Mutex` корректен, потому что выдаёт доступ только держателю замка.
Свой примитив такого рода пишут по тем же двум вопросам: кто может обратиться к значению одновременно и не
вышла ли наружу ссылка, которая переживёт изменение.

## unsafe impl Send и Sync

`Send` и `Sync` выводятся из полей, а сырые указатели не `Send` и не `Sync`. Структура с `*mut T` внутри не
пройдёт в поток, пока ты не напишешь `unsafe impl`. Это твоё слово против проверки компилятора, и оно
должно повторять поведение настоящего владельца:

```
владеет T как Box<T>         unsafe impl<T: Send> Send,   unsafe impl<T: Sync> Sync
замок с T внутри (как Mutex) unsafe impl<T: Send> Send + Sync    (доступ по очереди, поэтому Sync хватает T: Send)
```

Без границы на `T` impl пропустит через потоки всё, включая `Rc`, и компилятор промолчит. Проверка простая:
после любого `unsafe impl` пробуй «отрицательные» случаи (`Rc` внутри не должен проходить) и записывай, почему
impl верен.

## Безопасная обёртка над небезопасным ядром

Хороший `unsafe` это маленькое ядро с описанными инвариантами и безопасный API вокруг.

```rust
/// Строка, в которой гарантированно только ASCII.
pub struct Ascii(Vec<u8>);

impl Ascii {
    pub fn new(text: &str) -> Option<Ascii> {
        text.is_ascii().then(|| Ascii(text.as_bytes().to_vec()))
    }

    pub fn as_str(&self) -> &str {
        // SAFETY: поле приватное, а единственный конструктор принимает только ASCII,
        // значит байты всегда валидный UTF-8.
        unsafe { std::str::from_utf8_unchecked(&self.0) }
    }
}
```

Инвариант («только ASCII») устанавливает конструктор, поле приватное, поэтому снаружи его не нарушить, и
`unsafe` внутри оправдан. Рецепт для любой такой обёртки:

1. Запиши инварианты (что хранят поля, какие индексы допустимы, какие байты инициализированы).
2. Сделай поля приватными: нарушить инвариант можно будет только из модуля.
3. Проверяй вход безопасным кодом, а в `unsafe` оставляй только то, чего компилятору не доказать.
4. К каждому блоку и `unsafe impl` добавь `// SAFETY:` с причиной.
5. Тестируй границы (пусто, одна штука, ровно ёмкость, через границу кольца) и сравнивай с простой моделью
   (`Vec`, `VecDeque`) на случайных операциях.

## Типичные ошибки

- `get_unchecked`, `from_utf8_unchecked`, `unwrap_unchecked` «для скорости», без замеров и без проверки входа.
- Две `&mut` из одного указателя в безопасной функции, проверяющей только границы.
- `unsafe impl Send` без границы на параметры типа.
- Освобождение ресурса вручную в конце функции вместо `Drop`: паника или ранний выход оставляют его занятым.
- Блок `unsafe` на всю функцию вместо двух строк.
- Приведение `&T` в `&mut T` вместо `UnsafeCell`.
- Мысль «тесты зелёные, значит безопасно».
