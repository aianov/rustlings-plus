# Воркспейсы и модули

Пока проект умещается в один крейт, жить просто. Потом в нём появляется платёжная логика, которую
хочется использовать и из сервиса, и из утилиты. Её выносят в отдельную папку со своим `Cargo.toml`.
Потом в отдельную папку уходит общий код, потом ещё один сервис. Через месяц у тебя шесть пакетов,
и начинаются странности. В одном `tokio` версии 1.30, в другом 1.38. Запуск `cargo build` в корне
собирает не всё, а один пакет. В двух папках лежат два `Cargo.lock`, и CI собирает не то, что ты
проверял. Кто-то добавил крейт, но не указал его нигде, и его тесты не запускаются уже неделю.

Воркспейс решает именно это: он объединяет много крейтов в одну сборку с общими версиями и общим
набором проверок. Вторая половина главы про то, что внутри каждого крейта: как устроены модули, как
ограничить доступ и как отдать наружу аккуратный фасад. Обе половины про одно: границы. Граница между
крейтами, граница между модулями, граница между «пользуйся» и «не лезь».

Две анимации к главе открываются клавишей `v`: как устроен воркспейс, и как features от двух крейтов
сливаются в одну сборку.

## Воркспейс

**Воркспейс** (workspace) это набор пакетов, которые cargo собирает как одно целое. Корнем служит
`Cargo.toml` с таблицей `[workspace]`. Если корень ещё и сам пакет, в нём есть `[package]`. Но чаще
делают **виртуальный** корень, где одна таблица `[workspace]` и больше ничего: корень не программа, а
оглавление.

```toml
# Cargo.toml в корне
[workspace]
resolver = "3"
members = ["crates/*", "tools/*"]
```

Члены (members) задают путями или масками с `*`. Маска хороша тем, что новый крейт, положенный в
`crates/`, попадает в сборку без правок корня. Забыть про него невозможно. Явный список надёжен, пока
крейтов три, а на тридцати кто-нибудь да забудет дописать строку.

Строка `resolver` выбирает алгоритм объединения features и версий. В обычном пакете cargo берёт
значение по умолчанию из edition, а у виртуального корня edition нет, поэтому без явной строки он
выберет resolver 1 и напишет предупреждение. Пиши её всегда и ставь `"3"` для современных проектов.

Что даёт общий корень:

```
my-workspace/
  Cargo.toml            [workspace]
  Cargo.lock            один на всех
  target/               одна папка сборки на всех
  crates/
    pay-core/           lib
    pay-api/            lib, зависит от pay-core
  tools/
    refund/             bin, зависит от pay-api
```

Один `Cargo.lock` означает, что у всех членов одна и та же версия каждой общей зависимости. Один
`target` означает, что общая зависимость собирается один раз, а не по разу на крейт. Эти два файла
живут в корне, где бы ты ни запускал cargo: даже из `crates/pay-core` команда `cargo build` найдёт корень,
поднявшись по папкам вверх.

Как выбрать, что собирать:

```
cargo build                    все члены (в виртуальном воркспейсе)
cargo build -p pay-api         один пакет (и то, от чего он зависит)
cargo test --workspace         тесты всех членов
cargo run -p refund -- args    запустить бинарник пакета
cargo metadata --no-deps       JSON: кто в воркспейсе и как связан
```

В воркспейсе, чей корень сам пакет, `cargo build` без флагов собирает только корневой
пакет, остальные нужно звать через `--workspace` или `-p`. В виртуальном такого различия нет: по
умолчанию собирается всё.

## Зависимости между членами

Член воркспейса подключает соседа тем же `[dependencies]`, только путём:

```toml
# crates/pay-api/Cargo.toml
[dependencies]
pay-core = { path = "../pay-core" }
```

Каждая такая запись это стрелка в графе. Cargo требует, чтобы граф был **ациклическим**: если `pay-core`
зависит от `pay-api`, а `pay-api` от `pay-core`, воркспейс не откроется вообще. Это не прихоть: крейт
нельзя скомпилировать, пока не собраны его зависимости, и при круге строить было бы не с чего.

Цикл почти всегда означает, что два крейта делят какую-то мелочь, и её нужно вынести вниз. Типичная
картина. Крейт заказов хочет знать про клиентов, крейт клиентов хочет знать про заказы. Но заказу нужен
не весь клиент, а его идентификатор. Идентификатор переезжает в третий крейт (обычно его называют
`contracts`, `types` или `common`), на который смотрят оба. Нижний слой при этом должен быть тонким:
типы и ошибки, никакой бизнес-логики и никаких тяжёлых зависимостей. А функция, которой нужны оба
домена сразу, поднимается на уровень выше, туда, где видны оба.

```
        app  (видит всё)
       /    \
   orders   customers     (знают только contracts)
       \    /
      contracts           (ни от кого не зависит)
```

Полезное правило: стрелки идут только вниз. Если ты ловишь себя на мысли «этому крейту нужно
вызвать вон тот сверху», вызываемое выносят вниз или передают в виде параметра.

## Наследование: workspace.package, workspace.dependencies, workspace.lints

Когда крейтов много, одни и те же строки копируются в каждый манифест. Корень умеет их хранить:

```toml
# корень
[workspace.package]
version = "0.9.0"
edition = "2024"
license = "Apache-2.0"

[workspace.dependencies]
anyhow = "1"
regex = { version = "1", default-features = false, features = ["std"] }
pay-core = { path = "crates/pay-core" }

[workspace.lints.rust]
unsafe_code = "forbid"

[workspace.lints.clippy]
unwrap_used = "deny"
```

Таблицы по линтерам называются так же, как инструменты: `rust` для правил компилятора, `clippy` для
clippy. Уровни те же, что в `#![deny(...)]`: `allow`, `warn`, `deny`, `forbid`.

```toml
# член
[package]
name = "pay-api"
version.workspace = true
edition.workspace = true
license.workspace = true

[dependencies]
anyhow.workspace = true
pay-core.workspace = true
regex = { workspace = true, features = ["unicode"] }

[lints]
workspace = true
```

Три вещи, которые важно понимать. Первая: пути внутри `[workspace.dependencies]` отсчитываются от
корня, а не от члена. Вторая: член может **добавить** features к общей записи, но не может убрать
или заменить версию; итоговый набор это объединение. Третья: наследование включается явно. Правила из
`[workspace.lints]` действуют только на тех, у кого есть `[lints] workspace = true`, и забытая строка
значит, что крейт живёт без правил, а ты об этом не узнаешь.

Выгода от общей записи не в экономии набранных символов. Обновление зависимости становится одной
правкой в одном месте, и разъехаться версиям негде.

## Features в воркспейсе

В прошлой главе мы выяснили, что features аддитивны. В воркспейсе это свойство начинает кусаться,
потому что крейтов много и зависимости у них общие.

Cargo собирает каждую версию зависимости один раз. Если один член просит у нее feature `a`, а другой
feature `b`, то сборка получает `a` и `b` сразу. Но что значит «все члены»? Feature resolver
(начиная с версии 2; третья добавляет к нему только учёт `rust-version` при выборе версий)
объединяет features только среди тех пакетов, которые реально собираются в этот запуск. Команда
`cargo test -p quiet-app` собирает один пакет и видит features только его цепочки. Команда
`cargo test --workspace` собирает всех и видит сумму.

```
cargo test -p b                cargo test --workspace
  b ── lib []                    a ── lib [json]
                                 b ── lib []        ┐
  lib собран с []                                   ├─►  lib собран с [json]
                                                    ┘
```

Отсюда класс багов «одиночный тест зелёный, общий красный». Причина всегда в том, что feature не
добавляет, а меняет смысл существующего. Например, `greet()` возвращает одну строку без feature и
другую с ней. Тогда результат зависит от соседей, которых ты не выбирал. Лекарство то же самое: feature
добавляет новую функцию, новый вариант, новую ветку, но не подменяет старое поведение. Хорошая
проверка: прогнать тесты крейта с `--all-features` и убедиться, что они не поменялись.

## Ловушки воркспейсов

Забытый член. Крейт лежит внутри папки воркспейса, но не назван в `members` и никто не зависит от него
по path. Тогда `cargo test --workspace` его не видит и не запускает его тесты, а зелёный результат
врёт. Заодно запущенный внутри его папки cargo жалуется: «current package believes it's in a workspace
when it's not». Лечится маской в `members`.

Вложенный воркспейс. В манифесте утилиты кто-то написал `[workspace]`, чтобы «отвязать» её. Теперь это
отдельный воркспейс, у него свой `Cargo.lock` и свой `target`, где зависимости собираются заново,
возможно, другой версии. Если же такой крейт ещё и попал под маску членов корня, cargo ответит ошибкой
«multiple workspace roots». Секция `[workspace]` пишется ровно в одном месте: в корне.

Путь в зависимости. Внутри члена `path = "../pay-core"` отсчитывается от папки члена, а в
`[workspace.dependencies]` от корня. Спутать эти два режима легко.

## Модули: пути и имена

Теперь внутрь одного крейта. Модули образуют дерево, корень которого `lib.rs` или `main.rs`. Имя любого
элемента можно записать путём. Есть три способа его начать.

```rust
mod library {
    pub const LIMIT: u32 = 3;

    pub mod loans {
        pub fn can_borrow(count: u32) -> bool {
            count < super::LIMIT              // на уровень вверх
        }

        pub fn report() -> String {
            format!("limit {}", crate::library::LIMIT)    // от корня крейта
        }

        pub fn twice() -> bool {
            self::can_borrow(1) && can_borrow(2)           // от текущего модуля
        }
    }
}
```

`crate::` начинается с корня текущего крейта и не зависит от того, где написан код. `super::` поднимается
к родительскому модулю. `self::` означает текущий модуль и чаще всего опускается. Перед началом пути
можно написать `use`, чтобы дальше называть элемент коротко: `use super::LIMIT;`.

Правило выбора такое. Для далёких друг от друга частей крейта берут `crate::`, потому что такой путь не
ломается, когда файл переезжает. Для близких родственников (функция и её тесты, модуль и его детали)
берут `super::`, потому что так видно тесную связь.

Имена крейтов в путях подчиняются одному правилу. Идентификатор Rust не может содержать дефис, поэтому
пакет `pay-core` подключается в коде как `pay_core`: `use pay_core::charge;`. Дефис превращается в
подчёркивание. Для бинарника, который хочет пользоваться библиотекой того же пакета, действует то же
самое: `use pay_api::handle;`, а `mod pay_api;` ничего не даст.

## Видимость

По умолчанию всё в модуле приватно: видно самому модулю и его вложенным модулям, никому больше.
Слово `pub` открывает наружу. Но между «никому» и «всему миру» есть полутона:

```rust
pub struct Account { /* ... */ }            // видно всем, кто видит модуль
pub(crate) fn audit() {}                    // видно во всём крейте, но не снаружи
pub(super) fn tweak() {}                    // видно родительскому модулю и его потомкам
pub(in crate::billing) fn rate() {}         // видно модулю billing и его потомкам
pub(self) fn helper() {}                    // то же, что без pub
```

Выбирай самую узкую видимость, которой хватает. Для библиотеки это особенно важно: всё, что вышло
наружу как `pub`, становится обещанием, и менять его без последствий уже нельзя. `pub(crate)` позволяет
крейту пользоваться своими помощниками и ничего не обещать.

### Приватные поля и инварианты

Приватное поле запрещает собирать структуру литералом вне её модуля. На этом держатся типы, у которых
есть правило значения:

```rust
pub mod units {
    #[derive(Debug, Clone, Copy)]
    pub struct Celsius(f64);

    impl Celsius {
        pub fn new(v: f64) -> Option<Celsius> {
            (v >= -273.15).then_some(Celsius(v))
        }
        pub fn get(self) -> f64 { self.0 }
    }
}
```

Значения ниже абсолютного нуля больше не существуют: единственный вход это `new`, и он проверяет. Но
держать инвариант нужно от всех способов получить значение. Литерал закрыт приватным полем, а вот
`#[derive(Default)]` создаст `Celsius(0.0)` без вопросов (здесь нормально, для других типов нет),
`Deserialize` соберёт значение из чужого JSON, а `unsafe` позволит превратить байты в что угодно. Каждый
метод, возвращающий новое значение, обязан сам вернуть допустимое.

### Приватный тип в публичной сигнатуре

Если публичная функция возвращает приватный тип, вызывающий получает значение, которое не может назвать:
ни положить в структуру, ни передать в обобщённую функцию, ни описать в своей сигнатуре. Компилятор
предупреждает об этом (`private_interfaces` для типов в сигнатуре, `private_bounds` для трейтов в
ограничениях). Сегодня это предупреждение, но почти всегда это ошибка проектирования. Способов лечения
два: сделать тип публичным (поля при этом можно оставить приватными, и структура видна, а устройство
нет) или не показывать его в сигнатуре.

Обратный случай: тип `pub`, но лежит в приватном модуле, а наружу не реэкспортирован. Компилятор тут
молчит, потому что формально тип публичный. Но путь к нему закрыт, и вызывающий снова держит значение
безымянного типа: методы звать может, назвать тип не может. Если функция его отдаёт, тип нужно
вывести через `pub use`.

## Фасад: pub use и prelude

Дерево модулей это план хранения, а не интерфейс. Пользователю не интересно, что `Cart` лежит в
`shop::orders::cart::model`. Поэтому внутренние модули закрывают, а нужные имена выставляют наружу
**реэкспортом**:

```rust
// lib.rs
mod orders;          // приватный: пути orders::... снаружи не существуют
mod payment;

pub use orders::cart::Cart;
pub use payment::{charge, Receipt};
```

Реэкспорт умеет и переименовывать: `pub use orders::cart::Cart as Basket;` выдаёт наружу имя `Basket`,
внутри остаётся `Cart`. Имя модуля и имя функции могут совпасть, ведь модули и функции живут в разных
пространствах имён: `mod totals;` и `pub use pricing::sum_all as totals;` не мешают друг другу.

Пользователь пишет `shop::Cart` и ничего не знает о папках. Завтра ты перенесёшь `cart.rs` куда угодно,
и пользователь этого не заметит. Приватный модуль плюс `pub use` это стандартный приём, и именно он
отличает крейт с продуманным интерфейсом от крейта «как получилось».

`prelude` это маленький модуль-подборка самых ходовых имён, которые подключают одной строкой:

```rust
pub mod prelude {
    pub use super::{Cart, Receipt, charge};
}
```

Держи его небольшим: каждое имя из prelude попадает в пространство имён пользователя, и чем оно больше,
тем выше риск столкновений.

## Раскладка модулей по файлам

Модуль может быть блоком `mod name { ... }` внутри файла, а может жить в отдельном файле. Если в
`lib.rs` написано `mod orders;`, компилятор ищет код в `orders.rs` или в `orders/mod.rs`. Для вложенных
модулей то же самое глубже. В эдиции 2018 появился ещё один стиль: `orders.rs` рядом с папкой `orders/`,
где лежат вложенные. Оба работают, и смешивать их в одном проекте не стоит.

Договорись об одном правиле на весь проект. Наше: модуль, у которого есть вложенные модули, это папка с
`mod.rs`, а модуль без вложенных это файл.

```
src/
  lib.rs             только mod и pub use
  orders/
    mod.rs           pub mod cart; pub mod totals;
    cart.rs
    totals.rs
  payment.rs         лист: вложенных нет
```

У `lib.rs` в такой раскладке особая роль: это оглавление крейта. В нём объявляются модули и
собирается фасад, а кода нет. Длинные файлы почти всегда значат, что пора выделять модуль: в нашей
шкале это около 50 строк. Это не закон, а тревожный звонок.

При переезде кода по файлам ломаются пути. Абсолютные (`crate::...`) переживают его без правок.
Относительные (`super::...`) нужно перепроверить, потому что один и тот же `super` после переезда
может указывать уже на другой модуль.

## Типичные ошибки

Забыть крейт в `members` или написать в нём `[workspace]`. Скопировать версию зависимости в каждый
манифест вместо `workspace = true`. Забыть `[lints] workspace = true`, и тогда правила не действуют. Сделать
feature, меняющую поведение существующей функции: одиночный `-p` пройдёт, общий `--workspace` упадёт.
Лечить цикл зависимостей хитрой обёрткой вместо переноса общего вниз. Открыть всё как `pub`, чтобы
заработало. Вернуть из публичной функции приватный тип. Оставить в `lib.rs` код, а не оглавление.
Написать `mod x;` для библиотеки в `main.rs` вместо `use pkg_name::x`.

## Сеть при приёмке

Приёмки проектов этой главы собираются с крейтами с crates.io (`serde_json`, `toml`), поэтому при
первом запуске cargo ходит в сеть за индексом. Офлайн приёмка упадёт на ошибке cargo, а не на тесте:
запусти её один раз с сетью, дальше кэш работает без неё.
