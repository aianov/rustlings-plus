# Проект: шина событий

В ядре соцсети происходят события: новый пост, лайк, подписка. Одним они нужны для уведомлений,
другим для статистики, третьим для журнала, и ядро не хочет знать всех по имени. Классическое
решение: шина событий. Кто-то подписывается на тему и оставляет обработчик, кто-то публикует событие
в тему, и шина вызывает всех подписанных. Ни издатель, ни подписчики друг о друге не знают.

## Что нужно сделать

Библиотека `event-bus` с типами из `src/lib.rs`. Заготовка собирается, но методы пустые.

1. `subscribe(topic, handler) -> SubId` запоминает обработчик и возвращает числовой id подписки.
   Обработчик это замыкание `FnMut(&Event)`: оно может накапливать состояние между вызовами. Id начинаются
   с единицы, растут и никогда не выдаются повторно, даже после отписки.
2. `unsubscribe(id) -> bool` убирает подписку, `true` если она была.
3. `publish(topic, data) -> usize` вызывает всех подписчиков темы и возвращает, сколько обработчиков
   вызвано. Порядок вызова это порядок подписки.
4. Подписка на тему `"*"` получает события всех тем. Публикация в саму тему `"*"` ничем не особая:
   её получают подписчики `"*"`, по одному разу каждый. Порядок вызова общий: подписки на тему и на `*`
   идут в том порядке, в котором их сделали.
5. `subscribers(topic) -> usize` сколько обработчиков получит событие этой темы (с учётом `*`).
6. Шина пригодна для передачи в другой поток, чтобы её можно было положить в `Arc<Mutex<EventBus>>` и
   публиковать из нескольких потоков. Подумай, какие границы это требует от обработчиков.

## Как проверить

```
cargo test
cargo clippy --all-targets -- -D warnings
```

## Подсказки по теории

Обработчики разных типов хранят в `Box<dyn ..>`, потому что у каждого замыкания свой размер и тип.
Какой из трёх `Fn`-трейтов нужен и какие границы добавить для потоков, реши сам по пунктам 1 и 6.
При публикации удобно пройти по подпискам с `iter_mut()` и фильтром по теме.
