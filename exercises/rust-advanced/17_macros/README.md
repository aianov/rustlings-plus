# Макросы

В коде соцсети нашлось одиннадцать структур-идентификаторов: `UserId`, `PostId`, `ChatId` и так далее. Каждая
это `struct X(u64)` с одними и теми же `Display`, `From<u64>` и `FromStr`. Копировать это одиннадцать раз скучно,
а когда в одной копии забыли `Display`, логи стали печатать `UserId(42)` вместо `42`. Функцией здесь не обойтись:
нужно генерировать не значения, а сам код (типы, `impl`-блоки). Это работа для макросов.

В Rust две семьи макросов. Декларативные (`macro_rules!`) работают по шаблону: «если вход выглядит так, выдай вот
такой код». Процедурные пишутся как обычные функции на Rust, которые получают токены и возвращают токены;
к ним относится `#[derive(...)]`. В этой главе мы пишем много декларативных и один маленький процедурный.

## Что такое макрос

Макрос работает до проверки типов. Компилятор читает исходный текст в токены, встречает `имя!(...)` и подставляет
вместо вызова результат раскрытия. Только потом начинается обычная работа: типы, заимствования, оптимизации.
Поэтому макрос видит код (слова, скобки, знаки), а не значения. И поэтому макрос может сделать то, чего функция
не может: объявить тип, принять неизвестное число аргументов, использовать имя как параметр.

```rust
macro_rules! newtype_id {
    ($name:ident, $inner:ty) => {
        #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
        pub struct $name(pub $inner);

        impl std::fmt::Display for $name {
            fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
                write!(f, "{}", self.0)
            }
        }
    };
}

newtype_id!(UserId, u64);
newtype_id!(ChatId, u32);
```

Макрос состоит из правил `(шаблон) => { расширение }`. Компилятор пробует правила сверху вниз и берёт первое,
под которое подошёл вход. В шаблоне `$имя:вид` называет кусок входа, а все остальные токены должны совпасть
буквально. В расширении `$имя` подставляется обратно. Если подошло, правило срабатывает и на этом всё: ниже
по списку другие правила уже не смотрят.

## Виды фрагментов

Вид после двоеточия говорит, как разбирать кусок.

| вид       | что ловит                              | пример входа              |
|-----------|----------------------------------------|---------------------------|
| `expr`    | выражение целиком                      | `a + b * 2`, `f(x)`       |
| `ident`   | имя (переменной, типа, функции)        | `user_id`                 |
| `ty`      | тип                                    | `Vec<(u8, String)>`       |
| `literal` | литерал                                | `5`, `"text"`, `true`     |
| `tt`      | один токен или группа в скобках        | `+`, `foo`, `(1, 2)`      |
| `pat`     | образец для `match`                    | `Some(x)`, `1 \| 2`       |
| `path`    | путь                                   | `std::fmt::Display`       |
| `block`   | блок в фигурных скобках                | `{ do_it(); }`            |
| `stmt`    | оператор                               | `let a = 1`               |
| `item`    | элемент (fn, struct, impl)             | `fn f() {}`               |
| `vis`     | видимость (может быть пустой)          | `pub`, `pub(crate)`       |
| `meta`    | содержимое атрибута                    | `derive(Debug)`           |
| `lifetime`| время жизни                            | `'a`                      |

`expr` вставляется в расширение как одно дерево, как если бы стояло в скобках: `$a * $b` на входе `1 + 2` и `3`
даст `(1 + 2) * 3`, а не `1 + 2 * 3`. Зато вычисляется выражение там, где его вставили, и если `$a` встречается
в расширении дважды, оно вычислится дважды. Привычка `let v = $a;` в расширении это лечит.

### Что можно ставить после фрагмента

Чтобы разбор оставался однозначным, после некоторых фрагментов разрешены только определённые токены (это называют
«follow set»). После `expr` и `stmt` можно ставить только `=>`, `,` и `;`. После `ty` и `path` разрешены ещё `{`,
`[`, `=`, `:`, `>`, `|`, `as`, `where`. После `ident`, `tt`, `block`, `vis`, `lifetime` ограничений нет. Если
написать `($a:expr and $b:expr)`, компилятор откажет с понятным сообщением про `and`: перепиши разделителем из
разрешённых.

## Повторения

Часть шаблона, обёрнутая в `$( ... ) разделитель квантор`, повторяется. Квантор: `*` ноль и больше, `+` один и
больше, `?` ноль или один. Разделитель (чаще всего запятая) необязателен и ставится перед квантором.

```rust
macro_rules! pairs {
    ($($key:expr => $value:expr),* $(,)?) => {
        vec![$(($key.to_string(), $value)),*]
    };
}

pairs!();                          // пустой Vec
pairs!("a" => 1, "b" => 2,);       // запятая в конце допустима благодаря $(,)?
```

В расширении тот же `$( ... )*` повторяется столько раз, сколько совпало в шаблоне. Повторения можно вкладывать:
переменная повторения подставляется на той глубине, на какой объявлена. Использовать её на другой глубине нельзя
(«still repeating at this depth»). Опциональные части входа пишутся через `$( .. )?` и в расширении тоже оборачиваются в
`$( .. )?`.

## Гигиена

Макросы Rust гигиеничны для локальных переменных: имя, которое создал макрос, и имя с теми же буквами у
вызывающего это разные имена.

```rust
macro_rules! timed {
    ($label:expr, $body:block) => {{
        let start = std::time::Instant::now();      // своя start у макроса
        let result = $body;
        println!("{}: {:?}", $label, start.elapsed());
        result
    }};
}

let start = 10;                                     // своя start у вызывающего
let doubled = timed!("calc", { start * 2 });        // блок видит start вызывающего: 20
```

У гигиены две стороны. Макрос не может случайно затереть переменную вызывающего. Но и подсмотреть её без
спроса тоже не может: если макросу нужна чужая переменная, имя передаётся параметром вида `ident`. И обратно,
если вызывающий хочет видеть переменную, созданную макросом (например, счётчик цикла), её имя тоже приходит
параметром.

Гигиена касается только локальных переменных и меток. Пути (типы, функции, трейты) читаются в месте
вызова. Отсюда правило для библиотечных макросов: пути до `std` пиши от корня (`::std::collections::HashMap`), до
собственных функций через `$crate`. `$crate` это путь к корню того крейта, где макрос определён, и он работает
из любого места любого крейта.

## Порядок и область видимости

`macro_rules!` видны текстуально: только ниже места определения, в этом модуле и во вложенных. Определять макрос
ниже его использования нельзя. Чтобы макрос вышел за пределы модуля, на модуль ставят `#[macro_use]`. Чтобы он
вышел за пределы крейта, на сам макрос ставят `#[macro_export]`: тогда он лежит в корне крейта и вызывается как
`имя_крейта::макрос!` или импортируется `use имя_крейта::макрос;`. Всё, что макрос использует из своего крейта,
должно быть публичным: если нужно спрятать, заводят `#[doc(hidden)] pub mod __private` и ходят через него.

Порядок правил внутри макроса важен так же, как порядок веток `match`: частные случаи выше общих. Литерал это
тоже выражение, имя тоже, поэтому правило с `literal` ставят выше правила с `expr`. И последнее: если разбор
фрагмента (`expr`, `ty`) уже начался и сорвался, компилятор не переходит к следующему правилу, а сообщает об
ошибке, так что жадные фрагменты лучше ставить ниже тех, что разбирают конкретные токены.

## Рекурсия и внутренние правила

Макрос может вызывать сам себя. Так обходят списки: правило «первый элемент плюс остаток» вызывает макрос на остатке.

```rust
macro_rules! last_of {
    ($only:expr) => { $only };
    ($head:expr, $($tail:expr),+) => { last_of!($($tail),+) };
}

last_of!(1, 2, 3);     // 3: первые два отброшены по одному за шаг
```

Вспомогательные правила принято помечать токеном `@имя`: `(@step ...)`. Пользователь такой вход не напишет случайно,
а свои правила он найдёт по меткам. Накопитель (текущий результат) передают в первом параметре. Глубина рекурсии
ограничена (`recursion_limit`, по умолчанию 128, поднимается атрибутом `#![recursion_limit = "256"]`). Для сотен
элементов лучше обходиться без неё.

«Едоки токенов» (tt-munchers) это макросы, которые разбирают сложный вход по одному кусочку: общий вход собирает все
токены в `$($t:tt)*`, внутренние правила откусывают начало и вызывают макрос на остатке. Так делаются мини-языки:
таблица маршрутов, описание схемы, DSL тестов. Внутренние правила должны стоять выше общего, иначе оно
перехватит и их.

## Макросы std, которые стоит знать

- `stringify!(токены)`: текст токенов как `&'static str`. `concat!("a", "b", 1)`: склеивает литералы при компиляции.
- `line!()`, `file!()`, `column!()`, `module_path!()`: место вызова. Внутри макроса они раскрываются там, где макрос
  вызвали, а не где написан.
- `matches!(значение, образец)`: подходит ли значение под образец. `compile_error!("текст")`: остановить сборку с
  твоим сообщением; в `macro_rules!` так выдают понятную ошибку на неверный вызов.
- `env!`, `option_env!`, `include_str!`, `cfg!`: данные окружения и файлов на этапе компиляции.
- `vec!`, `format!`, `assert!` и друзья написаны на `macro_rules!`, их исходники полезно читать.

## Кортежи и макросы для impl

Стандартная библиотека реализует трейты для кортежей длиной до двенадцати, и вручную это были бы двенадцать
копий. Делается макросом, который получает список имён параметров. Ловушка: `(A)` в Rust не кортеж, а просто `A` в
скобках. Кортеж из одного элемента пишется `(A,)`. Поэтому в макросах пишут запятую после каждого элемента:
`($($name,)+)`.

## Что делает derive

`#[derive(Debug, Clone, PartialEq)]` это не часть компилятора, а процедурные макросы из `std`. Они получают описание
типа (имя, поля, варианты) и добавляют рядом реализацию трейта. Для структуры `Debug` вызывает `f.debug_struct(..)` и по
одному `.field(..)` на поле (для кортежных вариантов `debug_tuple`); `Clone` клонирует поле за полем; `PartialEq` сравнивает все. Поэтому derive требует,
чтобы каждое поле само умело `Debug`, `Clone` и `PartialEq`: он буквально вызывает их методы. Свои реализации (тот же
код руками) нужны, когда поведение особенное: например, не печатать пароль в `Debug`.

## Процедурные макросы

Три вида: derive (`#[derive(Name)]`, добавляет `impl` рядом с типом), макросы-атрибуты (`#[route(GET, "/")]`, могут
переписать элемент) и функциональные (`name!(..)`, как `macro_rules!`, но программой). Всё живёт в отдельном крейте
с `[lib] proc-macro = true`. Внутри доступен крейт `proc_macro`: `TokenStream` (поток токенов), `TokenTree` (слово, знак,
литерал или группа в скобках). Код работает при сборке пользователя, поэтому ошибки в нём это ошибки компиляции у
пользователя, и дружелюбные сообщения делают через `compile_error!`.

Обычно процедурные макросы пишут с крейтами `syn` (разбор синтаксиса) и `quote` (сборка кода), но на проекте главы
можно убедиться, что внутри нет магии: токены можно разобрать руками. Сложные места там такие, какие и были в языке:
запятые внутри `<...>`, стрелки `->`, атрибуты и видимость перед полями.

Серьёзные макросы тестируют, но не обычными юнит-тестами: процедурные макросы не вызвать как функции вне компилятора.
Их подключают к настоящим типам в интеграционных тестах (`tests/`) и сравнивают результат.

## Когда макрос нужен, а когда нет

Макрос нужен, когда функция не справляется: нужно объявить тип или `impl`, принять разное число аргументов, работать
с именами, получить текст выражения или место вызова, повторить код для набора типов. Не нужен, когда справится
обычная функция или обобщённый код: макросы хуже читаются, сообщения об ошибках в них туманнее, инструментам труднее
с ними. Первое правило: сначала пиши функцию, макрос заводи, когда стало больно.

## Типичные ошибки

- Вычислить аргумент дважды из-за повторного `$e` в расширении. Лечится `let`.
- Поставить после `expr` слово вместо `,`, `;` или `=>`.
- Общее правило поставить выше частных. Оно перехватывает всё.
- Не поставить `$(,)?` и удивляться, что запятая в конце не принимается.
- Забыть двойные скобки `{{ .. }}`, когда расширение это несколько операторов, а вызов стоит в позиции выражения.
- Названия из своего крейта писать без `$crate`, а названия из `std` без `::std::`.
- Определить макрос ниже места использования.
- Надеяться, что макрос увидит локальную переменную вызывающего (или что блок вызывающего увидит переменную макроса).
- Забыть запятую в кортеже из одного элемента.
- Писать рекурсию на сотни элементов и упереться в `recursion_limit`.
