# Трейты углублённо и dyn

Отчёты можно выгружать в CSV, в JSON, в PDF, а завтра добавится ещё один формат. Код, который выбирает
формат по настройке и вызывает `export`, не должен знать про каждый из них. Есть два способа это
написать, и они ведут себя совершенно по-разному.

```rust
trait Exporter { fn export(&self, rows: &[Row]) -> String; }

fn run_static<E: Exporter>(e: &E, rows: &[Row]) -> String { e.export(rows) }   // тип известен при компиляции
fn run_dynamic(e: &dyn Exporter, rows: &[Row]) -> String { e.export(rows) }    // тип известен только при запуске
```

Первая функция **обобщённая**: компилятор создаёт отдельную копию под каждый `E`, вызов получается
прямым и может быть встроен. Вторая работает с **трейт-объектом**: одна копия кода на все типы, а
нужный метод находится во время работы по таблице. Эта глава про то, как устроен второй способ, чем он
хорош, где ломается и как с ним жить. Две анимации открываются клавишей `v`: толстый указатель и
вызов через таблицу методов, и стирание типа у обработчиков.

## Что такое dyn Trait

`dyn Exporter` это «какое-то значение, о котором известно только то, что оно умеет `Exporter`». Размер у
него неизвестен, поэтому напрямую его не положить в переменную, только за указателем: `&dyn Exporter`,
`Box<dyn Exporter>`, `Rc<dyn Exporter>`, `Arc<dyn Exporter>`. Такой указатель **толстый**: два слова вместо
одного.

```
 &dyn Exporter                     данные конкретного типа
 ┌──────────┬──────────┐          ┌─────────────┐
 │ data ptr │ vtable   │───┐      │ CsvExporter │
 └────┬─────┴──────────┘   │      └─────────────┘
      └──────────────────────────────▲
                           │   vtable для (CsvExporter, Exporter)
                           └─► ┌─────────────────────────┐
                               │ drop                    │
                               │ size, align             │
                               │ export  ─► CsvExporter::export
                               └─────────────────────────┘
```

Vtable это таблица, которую компилятор строит для каждой пары «тип и трейт»: деструктор, размер,
выравнивание и адреса методов. Вызов `e.export(rows)` превращается в «возьми из таблицы адрес метода и
прыгни туда». Разница с обобщённым вызовом небольшая (косвенный переход, нет встраивания), но она есть.
Взамен вектор `Vec<Box<dyn Exporter>>` может держать значения разных типов, а тип выбирается во время
работы, например из конфигурации.

Из какого указателя что получается. `&dyn T` заимствует, ничем не владеет. `Box<dyn T>` владеет единолично
и освобождает значение при уничтожении. `Arc<dyn T>` (и `Rc<dyn T>`) делят владение: клонируется указатель, а не
объект. Создаются они одинаково: сначала обычный указатель на конкретный тип, затем неявное
приведение: `let e: Box<dyn Exporter> = Box::new(CsvExporter);`.

## impl Trait против Box&lt;dyn Trait&gt;

В возвращаемом типе `impl Exporter` значит «один конкретный тип, имя которого я не говорю». Он
один: функция не может вернуть `Csv` в одной ветке и `Json` в другой.

```rust
fn pick(fmt: &str) -> impl Exporter { if fmt == "csv" { Csv } else { Json } }   // ошибка: разные типы
fn pick(fmt: &str) -> Box<dyn Exporter> { if fmt == "csv" { Box::new(Csv) } else { Box::new(Json) } }
```

Выбор зависит от того, когда известен тип. Известен при компиляции: бери `impl` (нет выделения памяти,
нет косвенности). Выбирается при запуске: нужен `Box<dyn Trait>`.

## Generics или dyn

Обобщения быстрее и точнее: компилятор знает всё, может встроить вызов, трейт может быть какой
угодно (с `Self` в результате, с generic-методами). Цена в размере кода (копия на тип) и в том, что в
одном списке живут только значения одного типа. Трейт-объекты дают разнородные коллекции, стабильные
интерфейсы между модулями, меньший двоичный файл. Цена косвенный вызов и ограничения на сам трейт
(следующий раздел). Практическое правило: по умолчанию generics; `dyn` там, где нужна разнородность,
выбор при запуске или хранение обработчиков в структуре.

## Что делает трейт совместимым с dyn

Не каждый трейт можно превратить в `dyn Trait`. По vtable должно быть возможно вызвать метод, не зная
конкретного типа. Поэтому «ломают» совместимость:

```rust
trait Bad {
    fn create() -> Self;                          // нет self: нечем выбрать таблицу
    fn dup(&self) -> Self;                        // Self в результате: размер неизвестен
    fn same(&self, other: &Self) -> bool;         // Self в аргументе: тип другого неизвестен
    fn show<T: Display>(&self, t: T);             // generic-метод: нельзя заготовить таблицу на все T
    const LIMIT: u32;                             // константа: у dyn нет типа, из которого её взять
}
```

Лечится по-разному. Метод, который нужен только на конкретном типе, помечают `where Self: Sized`: он
остаётся для конкретных типов и пропадает из vtable, не мешая `dyn`. Метод, возвращающий `Self`, часто
превращают в возврат `Box<dyn Trait>`. А `Clone` в супертрейте делает `dyn Trait` невозможным совсем (`Clone`
требует `Sized`). Копирование трейт-объектов делают приёмом «клонируй в ящик»:

```rust
trait Plugin: PluginClone { fn run(&self) -> String; }
trait PluginClone { fn clone_box(&self) -> Box<dyn Plugin>; }
impl<T: Plugin + Clone + 'static> PluginClone for T {
    fn clone_box(&self) -> Box<dyn Plugin> { Box::new(self.clone()) }
}
impl Clone for Box<dyn Plugin> { fn clone(&self) -> Self { self.clone_box() } }
```

## Ассоциированные типы, константы и методы по умолчанию

Если у реализации ровно один осмысленный «выходной» тип, его делают не параметром трейта, а
**ассоциированным типом**: `trait Sensor { type Reading; fn read(&self) -> Self::Reading; }`. Параметр
(`Sensor<T>`) позволил бы одному типу реализовать трейт много раз и требовал бы указывать `T` на каждом
шагу. Ассоциированный тип определяется самой реализацией, и вызывающий код его просто выводит.
Используется как `S::Reading` и так же участвует в ограничениях: `where S: Sensor<Reading = f32>`.

Константы бывают ассоциированными тоже: `const LIMIT: u32;` принадлежит типу, читается как
`T::LIMIT` без объекта. Методы с телом в определении трейта это поведение **по умолчанию**; реализация
вправе его переопределить. Такой метод может вызывать другие методы и константы трейта.

## Супертрейты и приведение

`trait Pet: Named` значит «питомец обязан уметь назвать себя»: все методы `Named` доступны через `Pet`.
Реализовать `Pet` для типа без `Named` не выйдет. Начиная с Rust 1.86 объект `&dyn Pet` можно привести
к `&dyn Named` (и `Box<dyn Pet>` к `Box<dyn Named>`): компилятор достроит нужную часть таблицы.

## Blanket impl, правило сироты и расширения

**Blanket impl** это реализация трейта сразу для всех типов с некоторым свойством:
`impl<T: Display> Pretty for T { .. }`. Одна реализация покрывает бесконечно много типов, и ты получаешь
метод у чужих типов (`42.pretty()`). Цена: теперь для типа, который реализует `Display`, нельзя написать
свою `impl Pretty`, это конфликт («conflicting implementations»). Компилятор осторожен и там, где
реализация могла бы появиться в будущем у чужого типа: `impl<T: Debug> Pretty for Vec<T>` рядом с
реализацией для `Display` тоже конфликтует, потому что у `Vec` теоретически может появиться `Display`.
Выход: тип-обёртка. `struct Debugged<T>(T)` с отдельной реализацией для себя не пересекается ни с чем.

**Правило сироты**: реализовать трейт для типа можно, только если хотя бы один из них (трейт или тип)
определён в твоём крейте. `impl Display for Vec<Post>` запрещено: оба чужие. Разрешены
`impl MyTrait for Vec<Post>` (трейт свой), `impl Display for Post` (тип свой), и даже
`impl From<Post> for String` или `impl PartialEq<Post> for u8` (чужие трейт и тип, но свой тип стоит в параметре трейта). Выход, когда оба чужие: **newtype**,
`struct Feed(Vec<Post>)`; чтобы читать как вектор, добавляют `Deref<Target = Vec<Post>>`.

**Трейт-расширение**: свой трейт, реализованный для чужого типа, добавляет ему методы:
`trait StrExt { fn is_tag(&self) -> bool; } impl StrExt for str { .. }`. Метод виден там, где трейт
импортирован в область видимости.

## ?Sized и пробрасывающие реализации

В обобщённой функции параметр `T` по умолчанию подразумевает `T: Sized`. Поэтому `fn show<T: Display>(x: &T)`
не принимает `&str` (там `T = str`, размер которого неизвестен) и не принимает `&dyn Trait`. Правка:
`T: Display + ?Sized` («можно и без известного размера»). Но и это не всё. Если функция обобщена по
`E: Exporter` и принимает значение, то `Box<dyn Exporter>` не подойдёт, пока сам `Box` не реализует трейт.
Стандартный приём: пробрасывающие реализации. Для `Rc` и `Arc` они пишутся по тому же образцу.

```rust
impl<T: Exporter + ?Sized> Exporter for Box<T> { fn export(&self, rows: &[Row]) -> String { (**self).export(rows) } }
impl<T: Exporter + ?Sized> Exporter for &T     { fn export(&self, rows: &[Row]) -> String { (**self).export(rows) } }
```

Похоже сделано в стандартной библиотеке: `Iterator` и `Read` реализованы для `&mut I`, `&mut R` и для `Box`.

## Send и Sync у трейт-объектов

`Arc<dyn Exporter>` нельзя отправить в поток, потому что про сам трейт-объект неизвестно, `Send` ли он.
Есть два места, где это можно сказать. В сигнатуре: `Arc<dyn Exporter + Send + Sync>`, и тогда
ограничение пишут везде, где объект передают. Или в самом трейте: `trait Exporter: Send + Sync`, и тогда
любой `dyn Exporter` потокобезопасен автоматически, а реализовать трейт для `Rc`-типа компилятор не
позволит. Первое гибче (трейт остаётся применимым и в однопоточном коде), второе надёжнее (забыть
нечего). Выбирай по тому, будет ли трейт вообще использоваться вне потоков. Заметь, что `Arc<dyn Exporter + Send + Sync>`
и `Arc<dyn Exporter>` это разные типы: из первого во второй приведение есть (ослабляем гарантию), обратно нет.

Приведение конкретного `Arc<Mailbox>` к трейт-объекту тоже неявное, если тип известен из аннотации:
`let n: Arc<dyn Notifier> = Arc::clone(&mailbox);` или `Arc::clone(&mailbox) as Arc<dyn Notifier>`. Счётчик
ссылок один и тот же, данные не копируются.

И про потоки: `thread::spawn` требует `'static`, а аргументы функции чаще заимствованы. Либо копируй нужное
в свои `String` до `spawn`, либо используй `std::thread::scope`: потоки внутри него обязаны закончиться
до выхода из области, и заимствования разрешены.

## Время жизни трейт-объекта

`Box<dyn Trait>` в типе по умолчанию значит `Box<dyn Trait + 'static>`: внутри нет ссылок на чужие
данные. Поэтому объект, который держит `&'a str`, туда не положить:

```rust
struct Tag<'a>(&'a str);
fn make(s: &str) -> Box<dyn Show> { Box::new(Tag(s)) }        // ошибка: объект может прожить дольше s
fn make<'a>(s: &'a str) -> Box<dyn Show + 'a> { Box::new(Tag(s)) }   // честно: не дольше s
```

Для ссылок `&'a dyn Trait` граница по умолчанию `'a`. В структурах, которые хранят такие объекты,
появляется параметр времени жизни: `struct Pipeline<'a> { steps: Vec<Box<dyn Fn(&str) -> String + 'a>> }`.

## Any и приведение вниз

`dyn Any` это единственный способ узнать конкретный тип трейт-объекта. Через `TypeId` и `downcast_ref`:

```rust
let mut map: HashMap<TypeId, Box<dyn Any>> = HashMap::new();
map.insert(TypeId::of::<Limits>(), Box::new(Limits { max: 5 }));
let limits = map.get(&TypeId::of::<Limits>()).and_then(|b| b.downcast_ref::<Limits>());
```

Это основа типизированных карт «расширений» в контексте запроса. Ловушка: у `Box<dyn Any>` метод
`type_id()` берёт **тип самого ящика**, потому что и `Box<dyn Any>` тоже `Any` (все `'static`-типы
такие). Как добраться до `TypeId` именно содержимого, продумай сам, это тема задачи. `downcast_ref` про эту ловушку
знает, ошибка бывает только при ручном сравнении.

## Стирание типа: замыкание становится обработчиком

Планировщик принимает в качестве задания обычную функцию или замыкание, а хранит их в списке как
`Box<dyn Job>`. Мост между ними называется **стиранием типа**.

```rust
trait Job { fn run(&self, ctx: &Ctx) -> Report; }
struct FnJob<F>(F);
impl<F: Fn(&Ctx) -> Report> Job for FnJob<F> {
    fn run(&self, ctx: &Ctx) -> Report { (self.0)(ctx) }
}
queue.push(Box::new(FnJob(|ctx| Report::done(ctx.name()))));
```

Идём дальше: пусть задание возвращает не `Report`, а что угодно, что умеет `IntoReport` (строку, пару
«код и текст», `Result`). Обёртка при этом не меняется, меняется только реализация. Новый параметр `R`
вводится в `impl`, а определяется границей на функцию, и этого компилятору достаточно:

```rust
struct FnJob<F>(F);
impl<F, R> Job for FnJob<F>
where
    F: Fn(&Ctx) -> R,
    R: IntoReport,
{
    fn run(&self, ctx: &Ctx) -> Report { (self.0)(ctx).into_report() }
}
```

Параметр реализации обязан откуда-то определяться: типом, на который реализуем, параметрами трейта или
ассоциированным типом в границе. Здесь `R` это `Output` у `F: Fn(&Ctx) -> R`, поэтому в самой структуре
его хранить не нужно. Если бы ты объявил `struct FnJob<F, R>` и ни одно поле не использует `R`, получишь
ошибку «parameter `R` is never used», и тогда нужен маркер `PhantomData<fn() -> R>` (ноль байт; форма
`fn() -> R` не требует от `R` ни `Send`, ни `Sync`).

Последняя тонкость: две общие реализации одного трейта почти всегда конфликтуют, и компилятор
сообщает «conflicting implementations». Если нужно принять функции с разным набором аргументов (`Fn(&Ctx)` и
`Fn(&Ctx, &Db)`), одного `impl<F> Job for F` на оба семейства не напишешь. Различие выносят в параметр
трейта: `trait Job<Args>`, и тогда `impl<F: Fn(&Ctx) -> R, R> Job<(Ctx,)> for F` и
`impl<F: Fn(&Ctx, &Db) -> R, R> Job<(Ctx, Db)> for F` не пересекаются. Так устроены обработчики в
веб-фреймворках, а когда параметр трейта приходится ещё хранить в обёртке, как раз и нужен `PhantomData`.

## Типичные ошибки

Возвращать `impl Trait` из `if`/`match` с двумя разными типами. Забывать `'static` в `Box<dyn Trait>` в
структуре и ловить непонятную ошибку про время жизни. Класть `Clone` в супертрейт трейта, который
нужен как `dyn`. Писать `T: Trait` вместо `T: Trait + ?Sized`, когда функцию зовут с `&dyn Trait` или
`&str`. Брать `type_id()` у `Box<dyn Any>`. Делать две blanket-реализации «для всех Display» и «для всех
Debug». Требовать `Send + Sync` не в том месте и получать ошибки в трёх модулях сразу.
