# Проект: ускоряем построитель ленты

Лента нашей соцсети собирается так: берём все посты, оставляем те, чьи авторы в подписках и не в блокировках,
сортируем «новые сверху» и из первых `limit` делаем карточки для интерфейса. Код правильный и стал причиной
жалоб: на 200 тысячах постов страница грузится минутами, а память растёт, как будто лента строится заново для
каждого пользователя. Пора разобраться, куда уходит время и память, и привести всё в порядок, ничего не
сломав.

## Что уже есть

`crates/feed-builder/src/lib.rs` содержит функцию `build_feed` и обе структуры. Результат верный. Рядом лежит
`examples/bench.rs`: небольшой замер на двадцати тысячах постов.

## Что нужно сделать

1. Прогони замер до правок: `cargo run --release --example bench`. Запиши цифры (медиана и худший).
2. Найди в `build_feed` все места, где время или память тратятся впустую: поиск по спискам, лишние копии
   постов, сортировка того, что на страницу не попадёт, заголовки для невидимых карточек, расширение
   векторов по одному элементу. Исправь их. Сигнатуры функций и структур не меняй.
3. Прогони замер после правок. Должно стать заметно быстрее.
4. Результат лент остаётся прежним: порядок «новые сверху» (по убыванию `id`), заголовок
   `<автор>: <первые 40 символов текста в верхнем регистре>`, символы считаются в символах, а не в байтах.

## Критерии приёмки

Тесты в `crates/feed-builder/tests/acceptance.rs` проверяют: совпадение с эталоном на малых и больших
данных (в том числе пустые подписки, `limit = 0`, повторы в подписках), время на ленте из двухсот тысяч постов
(после ускорения она строится за доли секунды, квадратичное решение не укладывается в восемь секунд), число
аллокаций на ленту из двадцати карточек (не больше ста, при том что постов двадцать тысяч) и то, что
входные данные не изменились.

## Как проверить

```
cargo test --workspace
```

Для замеров нужна релизная сборка (`--release`): в отладочной цифры другие. Тесты в `acceptance.rs`
менять нельзя.
