# Future и Pin без рантайма

Пиццерия принимает заказы по телефону. Повар у одной печи может стоять и смотреть на пиццу, пока она печётся
(тогда за вечер он приготовит двенадцать штук), а может поставить таймер, взять следующий заказ и вернуться к
печи, когда зазвенит. Второй повар не быстрее руками. Он просто не простаивает. Сервер, который держит тысячи
соединений, устроен как второй повар: пока один клиент молчит, он обслуживает других.

В Rust эта идея упакована в трейт `Future`. Слова `async` и `await` красиво прячут механику, а в этой главе
мы её достанем и разберём: что такое `poll`, кто и зачем будит задачу, почему `Pin` вообще существует и как из
пары десятков строк получается рабочий исполнитель. Рантайма (tokio) здесь нет, его подробности ждут в разделе
tokio. Нам хватит `std`.

## Future и Poll

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> { Ready(T), Pending }
```

Future это не поток и не задача, а обычное значение с одним методом. Его вызывает тот, кто хочет узнать:
«ты уже готов?». Ответ `Ready(значение)` значит да, ответ `Pending` значит нет, спроси позже. Сам по себе
future ничего не делает: пока его не опрашивают, он просто лежит. Это главное отличие от потока, который
запускается сразу.

Простейший future, чайник, который закипает на третьем опросе:

```rust
struct Kettle { polls_left: u32 }

impl Future for Kettle {
    type Output = &'static str;

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<&'static str> {
        if self.polls_left == 0 {
            return Poll::Ready("кипит");
        }
        self.polls_left -= 1;
        cx.waker().wake_by_ref();   // «опроси меня ещё раз», об этом ниже
        Poll::Pending
    }
}
```

Состояние между опросами хранится в полях. Каждый `poll` делает небольшой шаг и либо заканчивает, либо
возвращает `Pending`. Если вызвать `poll` ещё раз после `Ready`, договор ничего не обещает. Обычно это паника,
и настоящие `async fn` именно так и делают. Ручной опрос выглядит так:

```rust
let mut kettle = Kettle { polls_left: 2 };
let mut cx = Context::from_waker(Waker::noop());       // контекст, который никого не будит
let first = Pin::new(&mut kettle).poll(&mut cx);       // Pending
```

`Waker::noop()` и `Context::from_waker` дают контекст для тестов и учебного кода. `Pin::new` работает для
типов, которые можно свободно двигать (`Unpin`), подробнее в разделе про `Pin`.

## Waker: кто разбудит

Если future ответил `Pending` и всё, как исполнитель узнает, когда спрашивать снова? Опрашивать в цикле, пока
не повезёт, можно, но это жжёт процессор. Поэтому у `poll` есть второй аргумент `Context`, а в нём `Waker`:
«номерок», по которому можно вернуть задачу в очередь. Договор такой.

1. Если future возвращает `Pending`, он обязан позаботиться, чтобы когда-нибудь позвали `wake` у переданного
   Waker (или у его клона). Иначе никто его больше не опросит.
2. Тот, кто следит за событием (поток с таймером, сокет), хранит клон Waker и вызывает `wake`, когда событие
   случилось.
3. При каждом опросе Waker мог поменяться (задачу переложили на другой поток). Сохраняй всегда последний.

```rust
struct Mailbox<T> { queue: VecDeque<T>, waiting: Option<Waker> }

struct Recv<T> { shared: Arc<Mutex<Mailbox<T>>> }

impl<T> Future for Recv<T> {
    type Output = T;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<T> {
        let mut mailbox = self.shared.lock().unwrap();
        match mailbox.queue.pop_front() {
            Some(letter) => Poll::Ready(letter),
            None => {
                mailbox.waiting = Some(cx.waker().clone());   // запомнили, кого будить
                Poll::Pending
            }
        }
    }
}

// в другом потоке, когда письмо пришло:
fn deliver<T>(shared: &Mutex<Mailbox<T>>, letter: T) {
    let waker = {
        let mut mailbox = shared.lock().unwrap();
        mailbox.queue.push_back(letter);
        mailbox.waiting.take()
    };
    if let Some(waker) = waker { waker.wake(); }
}
```

Два места, где обычно ошибаются. Во-первых, проверка события и сохранение Waker должны быть неделимы
(один замок на оба действия): иначе звонок успеет прозвучать между ними, и пробуждение потеряется навсегда.
Во-вторых, `wake` «без повода» превращает ожидание в крутилку: исполнитель опросит future снова, получит
`Pending`, и всё повторится на полной скорости. Будить нужно по событию. Есть единственное законное исключение:
future вообще не ждёт внешнего события, а лишь уступает очередь соседям. Тогда он будит сам себя, и это
называется `yield_now`.

Пробуждение ничего не гарантирует о состоянии. Будить могут лишний раз, после завершения, из чужого потока.
Опросивший должен переживать любое `wake`.

## async fn как автомат

Что делает компилятор с таким кодом?

```rust
async fn order(menu: Menu, pay: Payment) -> Receipt {
    let dish = menu.pick().await;      // точка 1
    let paid = pay.charge().await;     // точка 2
    Receipt::new(dish, paid)
}
```

Он строит enum состояний и реализует для него `Future`:

```
 Start ──poll──▶ WaitMenu{menu, pay} ──ready──▶ WaitPay{dish, pay} ──ready──▶ Done
                      ▲   │ Pending                    ▲   │ Pending
                      └───┘                            └───┘
```

В каждый вариант попадает всё, что живёт через соответствующий `.await`: параметры, которые ещё пригодятся,
результаты предыдущих шагов, локальные переменные. Поэтому размер future это размер самого большого
состояния. Каждый опрос продолжает с того места, где остановились. Из этого вытекает несколько вещей.

- `async fn` ленива. Вызов функции только собирает автомат в состоянии `Start`. Тело начнёт выполняться на
  первом `poll`. Если вызвал и не дождался (забыл `.await`), работа не сделается, а компилятор предупредит
  `unused_must_use`.
- `.await` не блокирует поток. Он означает «опроси внутренний future; если он `Pending`, верни `Pending`
  наружу, запомнив, где я». Стек вызовов при этом освобождается.
- После `Ready` автомат в состоянии `Done`. Повторный опрос паникует.

Такие автоматы можно писать руками, и в главе ты сделаешь это на маленьком примере. Приём такой: enum состояний,
в `poll` цикл `loop { match ... }`, на каждый `Ready` внутреннего future записываешь следующее состояние. Если нужное поле
надо забрать из старого варианта, пока `self` всего лишь заём, выручает `std::mem::replace(&mut *self, State::Done)`. Типичная
ошибка ручных автоматов это забыть записать новое состояние и опросить закончившийся future ещё раз.

## Pin и Unpin

Теперь ловушка. Допустим, внутри `async`-блока есть ссылка на локальную переменную, и она живёт через `.await`:

```rust
async fn echo() -> usize {
    let text = String::from("привет");
    let view = &text;             // ссылка на поле автомата
    network_pause().await;
    view.len()                    // после .await ссылка должна быть цела
}
```

В автомате поля `text` и `view` лежат рядом, и `view` указывает на `text` внутри того же автомата.
Если такой автомат переложить в другое место памяти (отдать в функцию, положить в `Vec`), байты скопируются,
а указатель `view` останется на старом адресе. Получится висячая ссылка. Поэтому такой автомат нельзя двигать
после первого опроса.

Для этого есть `Pin`. `Pin<&mut T>` это ссылка, у которой нельзя забрать значение целиком и переложить. Метод
`poll` принимает именно её: опросчик закрепляет future и не двигает его, пока он не закончится.

```
 обычное &mut T:     можно  mem::swap(a, b)   ──▶  значение переехало
 Pin<&mut T>:        нельзя (если T: !Unpin)  ──▶  адрес стабилен
```

`Unpin` это пометка «мне двигаться безопасно, ссылок на себя я не храню». Её имеет почти всё: числа, `String`,
`Vec`, `Box<T>` при любом `T`, `&mut T`, `Pin<Box<T>>`. Автоматы из `async` её не имеют (`!Unpin`). Для `Unpin`-типов
закрепление ничего не значит: `Pin::new(&mut x)` строит его бесплатно. Для остальных надо закрепить явно.

```rust
let fut = order(menu, pay);

let boxed = Box::pin(fut);                    // в куче; тип Pin<Box<..>>, адрес не меняется
let mut on_stack = std::pin::pin!(fut2);      // на стеке; тип Pin<&mut ..>, пока жива функция
on_stack.as_mut().poll(&mut cx);              // as_mut даёт новый Pin, чтобы не расходовать этот
```

`Box::pin` удобен, когда future надо хранить или перекладывать: в `Vec<Pin<Box<dyn Future<Output = T>>>>` лежат
указатели, и двигать их можно сколько угодно, автоматы на месте. `pin!` не требует кучи, но привязывает
future к кадру функции: вернуть такую ссылку из функции не получится.

Если пишешь комбинатор вроде `Map<F, G>` (обёртка над чужим future), нужно уметь опрашивать внутренний `F`
через закреплённую ссылку. Пути три. Первый: потребовать `F: Unpin`, тогда `Pin::new(&mut self.inner)` и всё
(подходит для простых типов, но не для `async`-блоков). Второй: хранить `Pin<Box<F>>`, одна аллокация зато
любой `F`. Третий: «проекция пина» через `unsafe`, как в крейте `pin-project` (без аллокации, но с
доказательством, что поле не двигают); руками её пишут редко, поэтому мы идём по первым двум.

## Комбинаторы

Из `poll` собираются все знакомые операции. `map` опрашивает внутренний future и преобразует его результат.
`join` опрашивает двух участников в каждом своём опросе и хранит готовые результаты, а `select` возвращает того,
кто закончил первым. Правила одни: опрашивать всех, кому ещё нужно, не опрашивать закончивших, пробрасывать
`Pending`, пока ждёт хоть кто-то, а для результата, который уже получен, держать место (`Option`).

Три готовых помощника из `std` в тестах и примерах: `std::future::ready(x)` (готов сразу),
`std::future::poll_fn(|cx| ..)` (future из замыкания) и `Poll::is_ready`/`is_pending`.

Одновременность здесь не про потоки. `join` двух future работает на одном потоке: он просто не ждёт первого,
чтобы начать второго.

## Отмена это drop

Как отменить ожидание? Бросить future (`drop`). Всё. Автомат остановится на том `.await`, где был, и
деструкторы сработают у всех живых в этот момент локальных переменных, в обратном порядке создания.
Код после `.await` не выполнится никогда.

```rust
async fn upload(slot: &Slots) {
    let reserved = slot.reserve();      // занять место
    send_over_network().await;          // если отменят здесь...
    reserved.commit();                  // ...сюда мы не дойдём
}
```

Отсюда правило надёжной отмены: после любого `.await` future может не вернуться, и мир должен остаться
согласованным. Откат кладут в `Drop` охранника (как с `MutexGuard`), а не в код после `.await`. Это тот же RAII,
только последствия серьёзнее: на отмене держатся таймауты и `select!` в рантаймах.

## block_on: самый маленький рантайм

Чтобы запустить `async`-код из обычной функции, нужен «внешний» опросчик. Это `block_on`:

```
 loop {
     poll(future, cx)
     если Ready  ─▶ вернуть результат
     если Pending ─▶ уснуть, пока Waker не разбудит
 }
```

Сон «пока не разбудят» можно собрать из `thread::park` и `thread::unpark`: Waker хранит `Thread`, `wake` делает
`unpark`. Тонкость в том, что `unpark` до `park` оставляет жетон, и тогда `park` вернётся сразу. Благодаря этому
пробуждение, которое пришло между опросом и сном, не теряется. Ложные пробуждения `park` возможны, но
безвредны: мы всё равно делаем `poll` и спокойно уснём снова.

Waker для таких случаев делают из типа с трейтом `std::task::Wake`: `Waker::from(Arc::new(MyWaker { .. }))`.
Хочешь считать пробуждения (удобно в тестах): внутри `AtomicUsize` и `fetch_add`.

Крутить цикл без сна нельзя, даже с `thread::yield_now()`: пока future ждёт сеть, один поток будет жечь
ядро на сто процентов. Ещё один способ ошибиться: сбросить флаг «меня разбудили» после опроса. Пробуждение,
пришедшее во время самого `poll`, пропадёт, и поток уснёт навсегда. Сбрасывать надо перед опросом.

## Исполнитель

Один `block_on` ведёт один future. Чтобы вести много, нужны очередь готовых задач и способ её пополнять:

```
         spawn(fut) ───────────┐
                               ▼
   ┌───────────────────── очередь ─────────────────────┐
   │  T1  →  T4  →  T2                                 │
   └──────────────────────────┬────────────────────────┘
                              │ достать, poll(T)
              ┌───────────────┴───────────────┐
              │ Ready: задача снята           │ Pending: задача лежит в слоте,
              │                               │ у неё есть Waker, который при wake
              └───────────────────────────────┘ положит её обратно в очередь
```

Задача это `Arc<Task>`: future в слоте под `Mutex<Option<..>>` и отправитель очереди. Её `Waker` при вызове
`wake` кладёт `Arc<Task>` обратно в очередь. Пока очередь пуста, а задачи ещё живы, исполнитель спит: на
`recv` канала или на `Condvar`. Принципы те же, что у `block_on`, только будить нужно не поток, а задачу.

Полезные следствия для устройства исполнителя.

- Справедливость. Задача, получившая `Pending`, встаёт в хвост, и соседи не голодают.
- Лишние пробуждения безвредны. Задачу могут разбудить дважды, или после её завершения. Слот хранит
  `Option`, пустой слот означает «пропусти».
- Порядок действий при `spawn`: сначала счётчик живых задач, потом отправка в очередь. Иначе другой поток
  увидит ноль и решит, что работа кончилась.
- Задачам не обязательно быть `Send`, если исполнитель однопоточный: Waker хранит только номер задачи, а сами
  future лежат в таблице исполнителя.

Многопоточные исполнители, work-stealing, async в трейтах, `Send` у future, планировщик и реактор разбираются
в разделе tokio. Таймер на отдельном потоке из этой главы это ровно то, что в настоящем рантайме делает
реактор: один поток следит за событиями и будит нужные задачи.

## Типичные ошибки

- Вернуть `Pending` и не позаботиться о пробуждении. Задача зависает навсегда.
- Сохранить Waker только при первом опросе. Второй опрос мог прийти с другим Waker.
- Проверить событие, потом (отдельным захватом) сохранить Waker. Между шагами событие теряется.
- Будить без повода. Исполнитель крутится на полной скорости.
- Опрашивать future после `Ready`. У `async` это паника «resumed after completion».
- В ручном автомате не записать новое состояние после `Ready` внутреннего future.
- Передавать `!Unpin`-future туда, где требуется `Unpin` (`Pin::new(&mut fut)` на `async`-блоке).
  Закрепляй `Box::pin` или `pin!`.
- Возвращать из функции `pin!(..)`: ссылка на мёртвый стек.
- Откат состояния после `.await` вместо `Drop`: при отмене он не выполнится.
- Сбрасывать флаг пробуждения после опроса, а не перед.
