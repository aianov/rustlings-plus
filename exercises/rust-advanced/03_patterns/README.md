# Сопоставление с образцом углублённо

Возьми любой разбор команд, написанный на скорую руку. Вот термостат принимает строки вроде
`set 21.5` и `mode eco`:

```rust
let parts: Vec<&str> = line.split_whitespace().collect();
if parts.len() == 2 && parts[0] == "set" {
    let t: f32 = parts[1].parse().unwrap();
    // ...
} else if parts.len() == 2 && parts[0] == "mode" {
    // ...
}
```

Всё работает, пока кто-то не напечатает `set` без числа, и тогда `unwrap` роняет программу. Проверка
длины стоит отдельно от доступа по индексу, и компилятор не следит, что они согласованы. Образцы
переворачивают это: ты описываешь форму данных, а компилятор разбирает её и гарантирует, что
привязанные имена существуют только там, где форма совпала. Эта глава про то, как пользоваться этим
на полную: от `let ... else` до автоматов состояний. На образцах держатся парсеры протоколов,
обработчики команд и конечные автоматы соединений, которые мы будем писать до конца курса.

Две анимации открываются клавишей `v`: как значение проходит ветки `match` сверху вниз и как
работает автомат на `(состояние, событие)`.

## Где живут образцы

Образец это не только то, что стоит слева от `=>`. Он встречается везде, где что-то привязывается:

```rust
let (low, high) = (10, 20);              // let
fn dist(&(x, y): &(f32, f32)) -> f32 {   // параметр функции
    (x * x + y * y).sqrt()
}
for (i, door) in doors.iter().enumerate() {}   // for
points.iter().map(|&(x, _)| x)                 // параметр замыкания
```

Образцы бывают двух видов. **Неопровержимый** подходит всегда: `(a, b)` для кортежа, имя
переменной, `_`. Его можно ставить в `let` и в параметры. **Опровержимый** может не подойти:
`Some(x)`, `Ok(n)`, `1..=5`. Ему нужен `match`, `if let`, `while let` или `let ... else`, иначе
компилятор спросит, что делать в остальных случаях. Эту границу полезно держать в голове: вся глава
о том, как красиво обращаться с опровержимыми образцами.

## let-else: ранний выход

Допустим, разбираем строку конфигурации `key=value`. Лесенка из `if let` выглядит так:

```rust
fn parse_pair(line: &str) -> Result<(String, u32), String> {
    if let Some((key, raw)) = line.split_once('=') {
        if let Ok(value) = raw.trim().parse::<u32>() {
            Ok((key.trim().to_string(), value))
        } else {
            Err(format!("bad value: {raw}"))
        }
    } else {
        Err(format!("no '=' in: {line}"))
    }
}
```

Успех уехал вглубь, ошибки разбросаны по краям. `let ... else` сохраняет успех слева, а неудачу
отправляет сразу наружу:

```rust
fn parse_pair(line: &str) -> Result<(String, u32), String> {
    let Some((key, raw)) = line.split_once('=') else {
        return Err(format!("no '=' in: {line}"));
    };
    let Ok(value) = raw.trim().parse::<u32>() else {
        return Err(format!("bad value: {raw}"));
    };
    Ok((key.trim().to_string(), value))
}
```

Правила простые. Блок `else` обязан завершить выполнение: `return`, `break`, `continue`,
`panic!` или другой вызов, который не возвращается. Привязанные имена (`key`, `raw`, `value`)
живут после `let` до конца блока, как у обычного `let`. А слева может стоять любой опровержимый
образец, в том числе с литералами: `let Some("go") = words.next() else { ... };` проверит, что
первое слово именно `go`, и ничего не привяжет.

Когда `?` не годится: он превращает ошибку одного типа в другой механически. `let ... else` нужен, когда
на неудачу надо отреагировать по-своему (особая ошибка, `continue` в цикле, пропуск записи) или когда
исходного значения нет в `Result` вообще (`Option`, срез, перечисление).

## if let цепочками и while let

В edition 2024 (она у нас в курсе) условия `if` и `while` могут сочетать `let` и обычные булевы
выражения через `&&`:

```rust
if let Some(door) = doors.get(id)
    && door.locked
    && let Some(code) = &door.master_code
{
    println!("открываем {id} кодом {code}");
}
```

Каждый шаг видит привязки предыдущих: `door` уже есть при проверке `door.locked`, а `code` виден в
теле. Раньше это были три вложенных `if`. Привязки существуют только в ветке успеха. В `else` их
нет, потому что неизвестно, на каком шаге цепочка оборвалась.

`while let` крутит цикл, пока образец подходит. Классическое применение: обход структуры
с явным стеком вместо рекурсии.

```rust
let mut pending = vec![root_dir];
while let Some(dir) = pending.pop() {
    for entry in dir.entries() {
        if entry.is_dir() { pending.push(entry); } else { count += 1; }
    }
}
```

Стек вызовов ограничен, а вектор растёт в куче. Обход через `while let` не упадёт на глубокой
вложенности. Обрати внимание на порядок: `pop` забирает последний элемент, поэтому то, что положили
в стек последним, будет обработано первым. Если нужен естественный порядок, детей кладут в обратном.

## Guards, @-привязки, диапазоны

К ветке можно приставить условие `if`, которое видит привязки образца:

```rust
fn describe(temp: i32) -> &'static str {
    match temp {
        t if t < -30 => "опасный мороз",
        i32::MIN..=0 => "холодно",
        1..=24 => "нормально",
        _ => "жарко",
    }
}
```

Диапазоны `a..=b` работают для чисел и символов (`'a'..='z'`), и для байтов `b'0'..=b'9'`. Конец
диапазона включённый; полуоткрытые `..b` и `a..` тоже допустимы. Если нужно и проверить диапазон, и
получить число, пригодится `@`: «привяжи значение к имени и одновременно проверь образец».

```rust
match port {
    p @ 1..=1023 => println!("системный порт {p}"),
    p @ (8000 | 8080 | 8888) => println!("похоже на разработку: {p}"),
    p => println!("обычный {p}"),
}
```

Скобки в `p @ (8000 | 8080 | 8888)` нужны: без них компилятор прочитает `(p @ 8000) | 8080 | 8888`, и `p` окажется не во всех альтернативах.

Три ловушки у guards. Первая: **порядок**. Ветки проверяются сверху вниз, побеждает первая
подошедшая, и более частный случай обязан стоять выше общего. Если выше стоит безусловный диапазон
(`400..=499` над `404`), компилятор предупредит, что нижняя ветка недостижима. Но если выше стоит
ветка с guard или с побочной логикой, он промолчит, и порядок придётся ловить тестами. Вторая: **guard и
`|`**. Условие относится ко всему образцу целиком, а не к последней альтернативе: в
`1 | 2 | 3 if flag =>` флаг проверяют для каждой из трёх. Более того, если образец подходит
несколькими способами (например, `(1, _) | (_, 1)` на `(1, 1)`), а guard вернул `false`, компилятор
попробует следующий способ и вызовет guard ещё раз. Поэтому в guard не стоит класть побочных
эффектов. Третья: **исчерпываемость не учитывает guard**. Ветка с условием компилятору как
гарантия не засчитывается, `x if x > 0 =>` вместе с `x if x <= 0 =>` всё равно потребует ещё
одной ветки.

## Вложенная деструктуризация

Образец повторяет форму данных, и поэтому может залезать глубоко:

```rust
enum Item { Book { title: String, pages: Option<u32> }, Dvd(String, u32) }
struct Loan { item: Item, member: Member }
struct Member { name: String, vip: bool }

match &loan {
    Loan { item: Item::Book { title, pages: Some(n) }, member: Member { name, .. } } if *n > 500 => {
        println!("{name} взял толстую книгу {title}");
    }
    Loan { item: Item::Dvd(title, _), member: Member { vip: true, .. } } => {
        println!("для vip: {title}");
    }
    Loan { member: Member { name, .. }, .. } => println!("выдано {name}"),
}
```

`..` означает «остальные поля мне не нужны» (в структуре и кортеже) и может стоять один раз. Поля
структуры можно называть в любом порядке; `Member { vip: true, .. }` проверяет значение поля прямо
в образце. Те же образцы стоят в параметрах замыканий, и там они особенно хороши:

```rust
let loud = readings.iter().filter(|(_, db)| *db > 70).map(|(room, _)| room);
```

Здесь `readings: Vec<(String, u32)>`, `iter()` отдаёт `&(String, u32)`, а `filter` передаёт в
замыкание ещё одну ссылку, то есть `&&(String, u32)`. Образец-кортеж «проходит сквозь» обе ссылки
сам (об этом ниже), поэтому `db` будет `&u32` (отсюда и звёздочка). Писать `|&(_, db)|` в `filter`
тоже можно, но тогда нужно снять обе ссылки: `|&&(_, db)|`. В `map` ссылка одна, и `|(room, _)|`
даёт `room: &String`.

Деструктуризация через `Box` ограничена: образца «внутри Box» у stable нет. Если внутри ветки лежит
`Box<Post>`, его сначала разыменовывают (`match &**boxed { ... }`), а образцы применяют к содержимому.

## Срезовые образцы

Срез можно разбирать по форме, как кортеж, только с переменной длиной:

```rust
match words {
    [] => println!("пусто"),
    [one] => println!("одно слово: {one}"),
    [first, second] => println!("пара: {first}, {second}"),
    [first, .., last] => println!("от {first} до {last}"),
}
```

`..` в срезе съедает «сколько угодно» элементов (в том числе ноль), и такой образец может быть один на
срез. Если хвост нужен, его привязывают через `@`: `[head, rest @ ..]` даёт `head` (элемент) и
`rest` (подсрез, `&[T]`). Работает и в середине: `[first, middle @ .., last]`. Все ветки выше
покрывают срез любой длины: компилятор это проверяет сам, и пропущенный случай не даст собраться.

На этом строится разбор команд:

```rust
match words {
    ["set", value] => set_target(value),
    ["mode", name] => set_mode(name),
    ["schedule", day, times @ ..] => plan(day, times),
    ["set" | "mode", ..] => usage_error(),
    [other, ..] => unknown(other),
    [] => {}
}
```

Образцы-строки сравнивают содержимое, так что `"set"` отлично работает на `&str`. А `Vec<&str>`
в `match` не подставишь напрямую: сначала `.as_slice()` или `&words[..]`.

## Байты: match по &[u8]

Тот же приём работает на сырых байтах, и в сетевом коде это основной способ разбора:

```rust
match packet {
    [0xAA, 0x55, kind, len, payload @ ..] if payload.len() == *len as usize => decode(*kind, payload),
    [0xAA, 0x55, ..] => Err(Error::Truncated),
    [] => Err(Error::Empty),
    [first, ..] => Err(Error::BadMagic(*first)),
}
```

Здесь и литералы-байты, и привязки (`kind`, `len` это `&u8`, поэтому звёздочки), и guard на длину. Порядок
критичен: общая ветка `[0xAA, 0x55, ..]` стоит после той, что с guard. Поменяй их, и «Truncated»
получат даже правильные пакеты.

Отдельная возможность: **байтовая строка как образец**. Литерал `b"PING"` в образце совпадает со срезом
**целиком**, а не с началом:

```rust
match line {
    b"PING" => ...,                              // только ровно 4 байта "PING"
    [b'P', b'U', b'T', b' ', rest @ ..] => ...,  // префикс "PUT " и остаток
    _ => ...,
}
```

Префикс байтовой строкой в образце не записывается, поэтому его разворачивают в байты. Если префикс
длинный, удобнее `line.strip_prefix(b"PUT ")` с `if let`. Выбирай то, что читается лучше.

## Режимы привязки: что в имени, значение или ссылка

Вот место, где образцы и владение сталкиваются. Правило называется **default binding modes**
(режимы привязки по умолчанию). Если образец без ссылки (`Some(x)`, `(a, b)`, `Point { x, .. }`)
применяется к значению типа `&T`, компилятор автоматически «проходит сквозь» ссылку, а все привязки
становятся ссылками:

```rust
let slot: Option<String> = Some("hall".into());
match &slot {
    Some(name) => println!("{}", name.len()),   // name: &String, slot не тронут
    None => {}
}
let pair = &(String::from("a"), 7u32);
let (text, number) = pair;                       // text: &String, number: &u32
```

То же с `&mut`: привязки становятся `&mut`, и значение можно менять на месте:

```rust
if let Some(name) = &mut slot {
    name.push_str("-way");
}
```

Если без ссылки, то значение **перемещается** из исходного, и исходное, если не `Copy`, больше
использовать нельзя:

```rust
match slot {
    Some(name) => consume(name),   // строка уехала из slot
    None => {}
}
println!("{slot:?}");              // ошибка: slot частично перемещён
```

Перемещение отслеживается по полям. `let Loan { member, .. } = loan;` забирает только `member`:
остальные поля `loan` остаются живыми, и `loan.item` ещё можно читать, а вот `loan.member` и
`loan` целиком уже нельзя.

Три инструмента, когда надо взять управление в руки. Первый: `.as_ref()` и `.as_mut()` у `Option` и
`Result` превращают `&Option<T>` в `Option<&T>` и `&mut Option<T>` в `Option<&mut T>`, и такой `match` не
трогает исходник. Второй: ключевые слова **`ref`** и **`ref mut`** внутри образца просят ссылку на
поле вместо перемещения: `Loan { ref member, .. }`. Сегодня их почти вытеснила автоматика, но в
чужом коде они встречаются, а в смешанных образцах (часть полей по значению, часть по ссылке) нужны.
(В edition 2024 внутри образца, который и так работает через ссылку, писать `ref` и `&` уже нельзя:
компилятор откажет.) Третий: когда нужно **вынуть** значение из места за `&mut` (как поле перечисления), используют
`std::mem::replace(&mut x, замена)` или `std::mem::take`, которые оставляют на месте допустимое
значение (для самого `Option` короче `opt.take()` и `opt.replace(новое)`, clippy предложит их сам):

```rust
let old = std::mem::replace(&mut self.phase, Phase::Idle);
match old {
    Phase::Running { job, .. } => self.phase = Phase::Done(job),
    other => self.phase = other,
}
```

И одна мелочь, на которой спотыкаются все: `let _ = s;` значение **не** перемещает (подчёркивание не
привязывает ничего), а `let _s = s;` перемещает (`_s` обычное имя, просто с намёком «не
используется»). Это важно для блокировок и guard-ов: `let _ = mutex.lock();` отпускает замок сразу.

## Исчерпываемость: `_ =>` и её цена

`match` обязан покрыть все значения. Компилятор следит за этим сам, и это одно из лучших свойств
языка: добавил вариант в `enum`, и компилятор показывает каждый `match`, где его забыли.

Ветка `_ =>` выключает эту проверку. Она ловит «всё остальное», в том числе и то, чего ещё нет:

```rust
enum Door { Open, Closed, Locked }                 // позже добавят Jammed
fn can_push(d: &Door) -> bool { match d { Door::Open => true, _ => false } }
```

Когда появится `Jammed`, `can_push` по-прежнему соберётся и скажет «нельзя». Это может быть верно, а может
быть багом, и никто не заставил об этом подумать. Правило: если значения enum разные по смыслу,
перечисляй их явно (`Door::Closed | Door::Locked => false`), а `_ =>` оставляй для действительно
открытых типов (числа, строки, байты) или осознанной политики «всё неизвестное отклоняем».

Предупреждение `unreachable_patterns` показывает ветки, которые никогда не сработают, потому что
выше стоит более общая. Читай его внимательно: обычно это ошибка порядка.

Для библиотек есть атрибут `#[non_exhaustive]` на enum или структуре:

```rust
#[non_exhaustive]
pub enum Plan { Free, Pro }
```

Внутри своего крейта ничего не меняется. А **в чужом крейте** `match` по такому enum обязан иметь
ветку `_ =>`, потому что библиотека вправе добавить вариант в минорной версии. Это обещание
автора: «будущие варианты не ломают совместимость».

## Автоматы: match по (состояние, событие)

Многие задачи это автоматы: соединение, загрузка, заказ. Состояния и события описывают двумя
`enum`, а переход функцией, которая матчится по паре:

```rust
enum Lock { Locked, Open { since: u32 }, Alarm }
enum Input { Code(u32), Push, Reset }

fn step(lock: Lock, input: Input) -> Result<Lock, (Lock, Input)> {
    match (lock, input) {
        (Lock::Locked, Input::Code(1234)) => Ok(Lock::Open { since: 0 }),
        (Lock::Locked, Input::Code(_)) => Ok(Lock::Alarm),
        (Lock::Open { since }, Input::Push) => Ok(Lock::Open { since: since + 1 }),
        (Lock::Alarm, Input::Reset) => Ok(Lock::Locked),
        (lock, input) => Err((lock, input)),
    }
}
```

Что тут важно. Все допустимые переходы перечислены, и таблицу видно целиком, одним взглядом.
Недопустимое сочетание **не молчит**: последняя ветка называет и состояние, и событие, и возвращает
их вызывающему. Это «закрытое по умолчанию» поведение: если завтра в `Input` появится новое событие,
оно попадёт в последнюю ветку и будет отклонено, а не принято по ошибке. Для автоматов именно так и
хочется, и поэтому здесь `(lock, input) => Err(...)` это осознанный выбор, а не лень. Сравни с
`_ => false` из примера выше: там замалчивание ведёт к багу, тут оно безопасно, потому что значит
«отказ». Привязки `lock` и `input` в последней ветке возвращают значения целиком: именно поэтому
переход берёт состояние и событие по значению.

Второй вариант, когда автомат живёт в структуре и меняется на месте (`&mut self`): тогда
переходы пишут как `self.state = ...`, а недопустимое событие возвращают как `Err`, ничего не меняя.
Следи, чтобы счётчики и прочие поля менялись только в допустимых ветках.

## Типичные ошибки

Забыть, что порядок веток важен, и поставить общий образец выше частного. Ставить `_ =>` в `match`
по enum и потом удивляться, что новый вариант обработан «не так». Писать `unwrap()` после проверки
длины вместо срезового образца. Пытаться вынуть `String` из поля через `&self` и бороться с
`cannot move out of`. Класть побочный эффект в guard. Путать `b"GET"` как образец (совпадение
целиком) с проверкой префикса. Забывать, что `let _ = x` и `let _x = x` ведут себя по-разному.
