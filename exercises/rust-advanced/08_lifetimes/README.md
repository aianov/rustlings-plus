# Времена жизни углублённо

Магазин хранит каталог товаров, и покупатель просит самый дешёвый товар дороже заданной суммы:

```rust
fn cheapest_over(items: &[Product], min: u32) -> Option<&Product> {
    items.iter().filter(|p| p.price > min).min_by_key(|p| p.price)
}
```

Функция ничего не копирует: она возвращает ссылку прямо на товар в каталоге. Это быстро, но возникает
вопрос, на который в других языках отвечает сборщик мусора: сколько живёт эта ссылка и что будет, если
каталог обновят, пока ссылка лежит в корзине? Rust отвечает на это при сборке. Время жизни это не секунды,
а участок программы, на котором ссылка действует. Компилятор сопоставляет эти участки у всех ссылок и
отказывает, если где-то ссылка могла бы пережить то, на что указывает. Две анимации (клавиша `v`) показывают
отрезки жизни на шкале и причину, по которой структура не может ссылаться на саму себя.

## Что аннотация делает, а чего нет

`'a` ничего не продлевает. Это имя, которым сигнатура связывает ссылки между собой: «вот эта ссылка на входе
и вот этот результат живут по одной шкале».

```rust
fn cheapest_over<'a>(items: &'a [Product], min: u32) -> Option<&'a Product>
```

Читается так: «результат вернётся из `items` и не переживёт `items`; про `min` я ничего не обещаю, он
не ссылка». Тело функции при этом компилятор не читает, он верит сигнатуре и проверяет, что тело
её не нарушает. Поэтому сигнатура должна говорить правду: если результат может прийти из любого из двух
входов, имя ставят на оба.

## Пропуск (elision): три правила

Чаще всего `'a` писать не надо, потому что компилятор подставляет его сам по трём правилам:

```
1. Каждая ссылка на входе получает своё время жизни.
2. Если на входе ровно одно время жизни, оно же достаётся всем ссылкам в результате.
3. Если среди входов есть &self или &mut self, результату достаётся время жизни self.
```

Если после этого у результата всё ещё неизвестное время жизни, будет ошибка «missing lifetime specifier».

```rust
fn trim_tag(tag: &str) -> &str { .. }            // правило 2: вход один
fn label(&self, suffix: &str) -> &str { .. }     // правило 3: результат привязан к self, не к suffix
fn merge(a: &str, b: &str) -> &str { .. }        // ошибка: два входа, self нет
fn banner() -> &str { "hi" }                     // ошибка: входов нет, брать не у кого: нужен 'static
```

Правило 3 любит подводить. Если `label` вернёт `suffix`, получится «lifetime may not live long enough»:
сигнатура обещала `self`, а в теле лежит другая ссылка. Решение одно: назвать время жизни явно на обоих.

## Результат берёт взаймы не у всех

Два входа не значит, что результат зависит от обоих. Если из списка команд выбирается команда по имени, имя
нужно только на время поиска. Давать ему то же `'a` значит без нужды привязывать результат к короткой жизни
строки ввода.

```rust
fn lookup<'a>(table: &'a [Entry], key: &str) -> Option<&'a Entry>      // key независим
fn lookup_bad<'a>(table: &'a [Entry], key: &'a str) -> Option<&'a Entry> // результат не переживёт key
```

Когда нужны два имени (`'a`, `'b`) и когда они связаны, пишут `'a: 'b` («`'a` живёт не меньше `'b`»).
Это нужно, если функция может вернуть ссылку из любого из двух входов под более коротким именем:
`fn pick<'a, 'b>(x: &'a T, y: &'b T) -> &'b T where 'a: 'b`.

Отдельная ловушка: `&'a mut Vec<&'a str>`. Здесь одно имя стоит и на заёме вектора, и на ссылках внутри.
Раз слова живут долго, заём вектора тоже должен длиться «столько же», то есть вектор оказывается занят до
конца жизни слов, и второй вызов невозможен. Изменяемая ссылка к тому же не позволяет компилятору втихую
сократить `'a` (так называемая инвариантность). Правильно разделять: `&mut Vec<&'a str>`.

## Структуры со ссылками

Если структура хранит ссылку, у неё появляется параметр времени жизни. Он говорит: «я не могу пережить
то, на что смотрю».

```rust
struct Tokens<'a> { src: &'a str, pos: usize }

impl<'a> Tokens<'a> {
    fn next_word(&mut self) -> Option<&'a str> { .. }      // кусок исходной строки, живёт 'a
    fn next_word_short(&mut self) -> Option<&str> { .. }   // кусок привязан к заёму self: после следующего next не удержать
}
```

Разница между этими двумя методами и есть главная мысль раздела. `&'a str` внутри структуры это копируемая
ссылка, поэтому достать из неё кусок с полным `'a` можно, и этот кусок не зависит от самой структуры:
парсер можно выбросить, а слова останутся. Элизия по правилу 3 даст второй вариант (привязка к `&mut self`),
и результатом можно будет пользоваться только до следующего вызова метода. Когда нужен первый, пиши `'a`
явно. Итераторы по заимствованным данным устроены так же: `Item = &'a T`, а не `&'self T`.

## 'static

У `'static` два смысла, и их путают.

`&'static str` это ссылка, которая действительна всю программу: литералы и данные, размещённые в самом
бинарнике. Именно её возвращает функция без входных ссылок.

`T: 'static` это условие на тип: «внутри `T` нет коротких ссылок». Ему удовлетворяют `String`, `Vec<u32>`,
структуры без ссылок и `&'static str`. Не удовлетворяют `&String` на локальную переменную и структура с
полем `&'a str`. Условие не значит «живёт вечно»: `String` можно спокойно освободить в любой момент.
`Box<dyn Trait>` без пометки означает `Box<dyn Trait + 'static>`, поэтому `T` перед упаковкой в такой
ящик нужно ограничить тем же `'static`.

`std::thread::spawn` требует `'static` от замыкания, потому что поток может пережить функцию, которая его
запустила. Отсюда типичная ошибка «borrowed data escapes outside of function» (E0521). Лечится
двумя путями: отдать потоку владение (`move` и клонирование) или использовать `thread::scope`:

```rust
let totals: Vec<u64> = std::thread::scope(|s| {
    let handles: Vec<_> = chunks.iter().map(|c| s.spawn(|| c.iter().sum::<u64>())).collect();
    handles.into_iter().map(|h| h.join().unwrap()).collect()
});
```

Все потоки, запущенные через `s.spawn`, гарантированно закончатся до выхода из `scope`, поэтому замыкания
могут брать `chunks` по ссылке.

## Разделение заимствований

Компилятор отслеживает заёмы по путям. Два поля структуры это два непересекающихся пути:

```rust
let a = &mut state.queue;
let b = &mut state.stats;      // можно: queue и stats разные
```

Но метод `state.queue_mut()` занимает `state` целиком, ведь компилятор смотрит на сигнатуру, а не на тело.
Поэтому внутри impl, где нужны сразу и поле, и счётчик рядом, обращайся к полям напрямую, а методы-геттеры
оставь для внешнего кода.

С элементами среза то же: `&mut v[0]` и `&mut v[1]` одновременно не пропустят, потому что индексы
вычисляются во время работы. Для этого есть `split_at_mut`, `split_first_mut`, `split_last_mut`,
`chunks_mut`, `iter_mut` и `swap`:

```rust
let (left, right) = scores.split_at_mut(3);   // два непересекающихся &mut [T]
transfer(&mut left[1], &mut right[0]);
```

## Пределы NLL

Современная проверка заимствований (NLL) считает, что заём живёт до последнего использования, а не до
конца блока:

```rust
let first = &list[0];
println!("{first}");
list.push(1);            // можно: first больше не нужен
```

Исключение: если у значения есть `Drop`, оно «использует» ссылку ещё и при уничтожении в конце блока, и тогда
заём длится до закрывающей скобки.

Второе ограничение известно как «условный возврат ссылки»:

```rust
fn get(&mut self, k: &str) -> &V {
    if let Some(v) = self.map.get(k) { return v; }   // эта ветка возвращает заём из функции
    self.map.insert(k.into(), make());                // ошибка: заём «якобы» ещё жив
    &self.map[k]
}
```

Хотя в ветке, которая вставляет, ссылки уже нет, компилятор не умеет это различить, потому что вернувшийся
заём обязан жить до конца функции. Обходят порядком действий: сначала `contains_key` (заём кончился), потом
вставка, потом одно обращение за ссылкой; или `entry(..).or_insert_with(..)`.

## Самоссылки нельзя

Структура не может хранить ссылку на собственное поле. Дело не в придирчивости компилятора: такая
ссылка всегда ломается: значение перемещают (возвращают из функции, кладут в вектор), и поле переезжает на
новый адрес, а ссылка остаётся на старом. Даже у `String`, у которой текст лежит в куче и при перемещении
не двигается, ссылку на него нельзя хранить рядом: первый же `push` может перевыделить буфер. Компилятор
запрещает такую структуру сразу.

```rust
struct Doc { text: String, title: &str }   // на кого указывает title? нельзя
```

Что делают вместо этого: хранят не адреса, а позиции (`Range<usize>` или длину), а `&str` вырезают в момент
чтения, когда адрес известен.

```rust
struct Doc { text: String, title_end: usize }
impl Doc { fn title(&self) -> &str { &self.text[..self.title_end] } }
```

Для тех, кому действительно нужны самоссылки (асинхронные состояния, интрузивные списки), есть `Pin`
и `unsafe`, об этом отдельная глава.

## Cow: копируем, только когда нужно

`Cow<'a, str>` (clone on write) это либо `Borrowed(&'a str)`, либо `Owned(String)`. Подходит для функций,
которые в большинстве случаев возвращают вход без изменений, и лишь иногда создают новое:

```rust
fn lower_nick(nick: &str) -> Cow<'_, str> {
    if nick.chars().any(char::is_uppercase) {
        Cow::Owned(nick.to_lowercase())      // пришлось менять: собираем новую строку
    } else {
        Cow::Borrowed(nick)                  // менять нечего: отдаём вход как есть
    }
}
```

`Cow` разыменовывается в `&str`, поэтому читать его можно как обычную строку; `to_mut()` при первой записи
клонирует содержимое (если оно было заимствованным) и отдаёт `&mut String`; `into_owned()` забирает строку.
Ставь `Cow` в результат, когда копия нужна редко и дорога, и не ставь, если почти всегда создаёшь новое.

## Для любого времени жизни: HRTB

Условие `F: Fn(&str) -> &str` пишут без `'a`, и это не упрощение. Сахар раскрывается в `for<'x> Fn(&'x str)
-> &'x str`: «для любой ссылки любой длины жизни». Явное `for<'x>` нужно, когда условие записано через
имена, и функции требуется вызывать `f` на значениях, которые родились внутри неё.

```rust
fn run_all<'a, F: Fn(&'a str) -> &'a str>(f: F) {   // 'a выбирает вызывающий: одно на все вызовы
    let local = String::from("x");
    f(&local);                                       // ошибка: local не живёт 'a
}
fn run_all<F: for<'x> Fn(&'x str) -> &'x str>(f: F) { .. }  // правильно
```

## edition 2024: что захватывает `impl Trait`

В старых редакциях `impl Trait` в результате «видел» только те времена жизни, которые прописаны в его
границах. В редакции 2024 он по умолчанию захватывает **все** времена жизни из входов. Обычно это то, что
нужно, но иногда итератор не держит часть входов (например, свою копию набора разделителей), а привязанным
к ним оказывается:

```rust
fn words<'a>(text: &'a str, sep: &str) -> impl Iterator<Item = &'a str> { .. }
// в 2024 результат считается зависящим и от sep: sep нельзя выбросить, пока итератор жив

fn words<'a>(text: &'a str, sep: &str) -> impl Iterator<Item = &'a str> + use<'a> { .. }
// точный список: только 'a
```

`use<..>` перечисляет захватываемые времена жизни и типовые параметры полностью, лишнего в списке не будет.

## Типичные ошибки

Гасить ошибку времён жизни клонированием, не поняв, чьё это время. Ставить одно `'a` на всё в сигнатуре.
Возвращать из метода `&str` по правилу 3, когда кусок на самом деле живёт дольше `&self`. Писать
`&'a mut Vec<&'a str>`. Принимать `T: 'static` как «живёт вечно». Пытаться хранить `&str` на собственное
поле. Вызывать геттер `fields_mut()` там, где рядом нужен другой `self.field`. Оборачивать в `Cow` то, что
копируется всегда.
