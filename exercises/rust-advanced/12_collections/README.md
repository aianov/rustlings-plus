# Коллекции и их цена

Склад интернет-магазина получает тысячу заказов в минуту. Кладовщик спрашивает: «сколько осталось
товара с этим артикулом?», «какие заказы пришли после обеда?», «какие пять товаров продаются лучше всего?».
Каждый вопрос можно решить обходом всего списка, и все они выглядят одинаково безобидно, пока список
не вырастет. Правильная коллекция делает вопрос дешёвым, неправильная превращает его в тормоз или, хуже,
в тихую ошибку: товар «пропал», хотя он лежит на полке.

В этой главе нет новой магии. `Vec` и `HashMap` ты знаешь. Здесь главное: что стоит каждая операция, чем
порядок отличается от случайности и какие правила нужно соблюдать, чтобы коллекции не врали.

## Цена операций

```
                      поиск        вставка      порядок       заметка
Vec                   O(n)         O(1) в конец  как вставили  вставка в середину сдвигает хвост
Vec (отсортированный) O(log n)     O(n)          по ключу      binary_search, partition_point
VecDeque              O(n)         O(1) с краёв  как вставили  очередь с двух концов
HashMap / HashSet     O(1) средн.  O(1) средн.   НЕТ           нужны Hash + Eq
BTreeMap / BTreeSet   O(log n)     O(log n)      по ключу      нужен Ord, умеет диапазоны
BinaryHeap            O(1) верх    O(log n)      только вершина нужен Ord
```

«Порядка нет» у `HashMap` означает буквально: порядок обхода зависит от случайного зерна и меняется даже
между запусками одной программы. Тест, который сравнивает вывод обхода карты со строкой, то зелёный,
то красный. Всё, что выходит наружу (ответ, лог, сравнение в тесте), упорядочивай явно.

## entry: найти и решить за один проход

Подсчёт товаров по артикулам «в лоб»:

```rust
if !stock.contains_key(&sku) {
    stock.insert(sku, 0);
}
*stock.get_mut(&sku).unwrap() += qty;
```

Ключ хешируется и ищется три раза, а `unwrap` лежит в коде без причины. `entry` находит место один раз и
возвращает `Entry`: либо `Occupied` (запись есть), либо `Vacant` (места нет, его можно занять).

```rust
*stock.entry(sku).or_insert(0) += qty;      // завести нулём, если нет
stock.entry(sku).or_default().push(qty);    // завести значением по умолчанию (пустой Vec)
stock.entry(sku).and_modify(|n| *n += qty).or_insert(qty);   // изменить, если есть, иначе вставить
```

`or_insert(x)` получает значение сразу, то есть вычисляется всегда, даже если запись уже есть. Если значение
дорого строить, бери `or_insert_with(|| ...)`: замыкание вызовется только на пустом месте. Когда нужны разные
действия на двух ветках (например, убрать запись при нуле), разбери `Entry` по вариантам:

```rust
use std::collections::hash_map::Entry;

match stock.entry(sku) {
    Entry::Occupied(mut e) => {
        if *e.get() <= qty { e.remove(); } else { *e.get_mut() -= qty; }
    }
    Entry::Vacant(_) => {}
}
```

Пока жив `Entry`, карта занята им: это и есть причина, почему `entry` проще для борроу-чекера, чем связка
`get_mut` и `insert`. Старая запись вида «если `get_mut` вернул `Some`, вернуть ссылку, иначе вставить и вернуть
ссылку» не собирается, и `entry` решает её.

## Множества и группировка

`HashSet` хранит уникальные значения. Операции над парой множеств возвращают ленивые итераторы по ссылкам:

```rust
let a: HashSet<u32> = [1, 2, 3].into();
let b: HashSet<u32> = [2, 3, 4].into();
a.intersection(&b)   // 2, 3
a.union(&b)          // 1, 2, 3, 4
a.difference(&b)     // 1
a.symmetric_difference(&b) // 1, 4
```

Порядок в итераторе не определён, поэтому, если результат уходит наружу, собери в `Vec` и отсортируй.
`insert` возвращает `false`, если значение уже было: это удобный фильтр «видел ли я такое».

Группировка `ключ -> список` идёт через `entry(..).or_default().push(..)`: за один проход, без проверок.
Если ключом служит строка из исходных данных, храни `&str`, а не `String`: копировать нечего, пока исходные
данные живут.

## BTreeMap: порядок и диапазоны

`BTreeMap` держит ключи отсортированными. За это платишь логарифмом на каждую операцию (против «почти
константы» у хеша), зато получаешь то, что хеш дать не может: соседей и диапазоны.

```rust
let mut sales: BTreeMap<u64, &str> = BTreeMap::new();   // время продажи -> товар
sales.range(100..200)      // от 100 включительно до 200 не включая
sales.range(..=100)        // всё до 100 включительно
sales.range(..100).rev()   // идти от 100 вниз
sales.first_key_value()    // самая старая
sales.last_key_value()     // самая новая
sales.pop_first()          // снять самую старую
```

`range` не обходит всё дерево: он спускается к началу диапазона и идёт дальше. Если начало больше конца,
вызов паникует, а не возвращает пустое. Ключом может быть кортеж, и тогда порядок лексикографический: сначала
первая часть, потом вторая. Это способ держать записи с одинаковым временем: ключ `(время, номер)`.

Границы бывают включённые и исключённые. Для верхней границы есть короткая запись `..x`, для нижней
исключённой короткой записи нет, там пара `Bound`:

```rust
use std::ops::Bound::{Excluded, Unbounded};

sales.range((Excluded(100), Unbounded))    // строго больше 100
```

Отсюда **курсорная пагинация**. Клиент присылает ключ последней записи, которую он уже видел, и просит
следующие `n`: `range(..cursor).rev().take(n)`. Курсор не включается (его запись уже показана). Номер
страницы так не работает: пока читатель на странице 2, сверху добавляются новые записи, и страница 3 уже
начинается не там. Чтобы узнать, есть ли продолжение, запроси на одну запись больше, чем отдаёшь: если получилось
`n + 1`, продолжение есть, лишнюю запись отбрось.

```
дерево:  10  20  30  40  50  60  70  80
страница 1 (n = 3, с конца):          [60 70 80]   курсор = 60
страница 2: range(..60).rev().take(3): [30 40 50]  курсор = 30
```

## VecDeque

Очередь с двух концов на кольцевом буфере. `push_back`, `pop_front`, `push_front`, `pop_back` стоят `O(1)`.
Берёшь, когда нужна очередь «первым пришёл, первым ушёл»: у `Vec` та же `remove(0)` сдвигала бы все элементы.
Буфер «последние N» делается так: `if len == cap { pop_front() }` и `push_back`. Нулевую ёмкость проверь
отдельно, иначе элемент всё равно попадёт в буфер. Неудавшийся элемент возвращают на голову (`push_front`),
чтобы он сохранил своё место.

## BinaryHeap и Reverse

Куча отдаёт наибольший элемент за `O(log n)`, а посмотреть на него можно за `O(1)` (`peek`). Остальные
элементы не упорядочены, обходить кучу в порядке нельзя; `into_sorted_vec` собирает всё по возрастанию.

Чтобы получить наименьший, оберни значения в `std::cmp::Reverse`: это обёртка, переворачивающая сравнение.
Кортежи сравниваются по частям, и порядок критериев можно собрать из вложенных кортежей:

```rust
use std::cmp::Reverse;
use std::collections::BinaryHeap;

let mut orders = BinaryHeap::new();
orders.push((5, Reverse(103)));    // приоритет 5, номер 103
orders.push((5, Reverse(101)));
orders.pop();                      // (5, Reverse(101)): при равном приоритете раньше меньший номер
```

**Топ N из потока.** Хранить поток нельзя, нужны лучшие `n`. Держи кучу размера `n`, у которой на вершине
**худший из лучших**. Пришёл новый: положи, если стало больше `n`, убери вершину.

```
n = 3, поток: 5, 50, 7, 100, 1
min-куча:  [5]  [5 50]  [5 7 50]  [7 50 100] (5 выбыл)  [7 50 100] (1 выбыл сразу)
```

Это min-куча, то есть `Reverse`. Обычная max-куча выкинула бы лучшего. Память `O(n)`, каждый элемент `O(log n)`.

## Ord, PartialOrd и сортировка

`sort()` и `BTreeMap` опираются на `Ord`. `derive(Ord)` сравнивает поля по порядку объявления, как строки в
словаре. Если нужный тебе порядок другой (сначала проверенные, потом по числу продаж, потом по имени),
пиши `cmp` руками и собирай цепочку:

```rust
impl Ord for Item {
    fn cmp(&self, other: &Self) -> Ordering {
        other.sold.cmp(&self.sold)                       // больше продаж раньше: аргументы наоборот
            .then_with(|| self.name.cmp(&other.name))    // при равенстве по имени
    }
}
impl PartialOrd for Item {
    fn partial_cmp(&self, other: &Self) -> Option<Ordering> { Some(self.cmp(other)) }
}
```

`then_with` смотрит на следующий критерий только при равенстве предыдущего. Два правила: `PartialOrd`
делегирует в `Ord` (иначе у типа два разных порядка), а `cmp` возвращает `Equal` ровно тогда, когда `==` даёт
`true`. Первое нарушенное правило ломает `BTreeSet`: он считает «равные» элементы одним и теряет второй.

Числа с плавающей точкой полным порядком не обладают: `NaN` не больше и не меньше ничего. `partial_cmp`
возвращает `None`, и `partial_cmp(..).unwrap()` в сортировке паникует на первом же `NaN` (а он появляется
от деления `0.0 / 0.0`). Есть `f64::total_cmp`, полный порядок (положительный `NaN` оказывается больше всего,
учитывай это, если `NaN` должен идти в конце при сортировке по убыванию).

Варианты сортировки:

```
sort / sort_by / sort_by_key     устойчивая: равные остаются в исходном порядке
sort_unstable*                   быстрее и без буфера, но равные могут поменяться
sort_by_cached_key(|x| key(x))   ключ считается один раз на элемент (дорогой ключ, строки)
```

`sort_by_key` вычисляет ключ при каждом сравнении. Если ключ дорог (например, `to_lowercase`), он посчитается
`n log n` раз, и `sort_by_cached_key` считает его один раз на элемент. Развернуть порядок ключа можно через `Reverse(x)`,
несколько критериев собрать в кортеж.

## Hash и Eq: договор

`HashMap` ищет в два шага. Сначала по хешу выбирается корзина, и только потом внутри неё сравниваются ключи
через `==`. Отсюда закон: **если `a == b`, то `hash(a) == hash(b)`**. Нарушение компилятор не видит. Если
`PartialEq` сравнивает только артикул, а `derive(Hash)` хеширует все поля, то «равные» ключи попадают в разные
корзины: поиск не находит то, что лежит в таблице, а вставка кладёт дубликат. Ошибка недетерминирована и
зависит от зерна и размера таблицы, поэтому тест то проходит, то нет.

Чинится одинаково: `eq` и `hash` смотрят на одни и те же данные.

```rust
impl PartialEq for Sku { fn eq(&self, o: &Sku) -> bool { self.code == o.code } }
impl Eq for Sku {}
impl Hash for Sku { fn hash<H: Hasher>(&self, h: &mut H) { self.code.hash(h) } }
```

Если равенство «без учёта регистра», то и хешировать надо нижний регистр, а не исходную строку.

## Borrow: искать без построения ключа

Карта `HashMap<String, V>` отвечает на `map.get("abc")`, хотя ключ `String`, а аргумент `&str`. Это работает
благодаря `Borrow`: `String: Borrow<str>`, и `get` принимает любой `&Q`, где `K: Borrow<Q>`, причём `Q` должен
хешироваться и сравниваться как `K`. Так же `Vec<T>: Borrow<[T]>`, и ключ-вектор ищется по срезу, не копируясь.

Свой тип-обёртку учат тому же одной строкой:

```rust
struct Sku(String);
impl Borrow<str> for Sku { fn borrow(&self) -> &str { &self.0 } }
```

Хеш `Sku` (при `derive(Hash)`) совпадает с хешем строки внутри, поэтому закон соблюдён. Иначе ключ собирают
заново на каждый запрос, и это лишняя аллокация ради поиска.

## retain, drain, dedup, отсортированный Vec

```rust
v.retain(|x| keep(x));         // оставить подходящие, один проход (retain_mut тоже есть)
let head: Vec<_> = v.drain(..n).collect();   // отрезать начало; n не больше len
v.dedup();                     // убирает ПОВТОРЫ ПОДРЯД, не все
v.dedup_by_key(|x| x.group);   // соседние с одним ключом
```

Цикл `while i < v.len() { if bad { v.remove(i); } i += 1; }` пропускает элемент после каждого удаления:
хвост сдвинулся на место удалённого. `retain` этой ошибки не знает. `dedup` не заменяет «каждый ровно один раз»,
для этого нужен `HashSet::insert` в `retain` или сортировка перед `dedup`.

Отсортированный `Vec` часто выигрывает у дерева: компактный, быстрый на чтение, а правится редко.
`binary_search(&x)` возвращает `Ok(позиция)` или `Err(куда вставить)`. `partition_point(|x| *x < lo)` считает,
сколько элементов в начале подходит под монотонное условие. Два таких вызова дают число элементов в `[lo, hi)`.
Для повторяющихся значений `binary_search` вернёт любую из позиций, а `partition_point` точно найдёт начало или
конец группы.

## Вторичные индексы

Основное хранилище ищет по id: `HashMap<u64, Order>`. Вопрос «заказы клиента» без индекса означает обход всего.
Вторичный индекс это ещё одна коллекция `клиент -> id заказов`, которую надо вести вручную. Вся сложность в
согласованности, и держится она на одном правиле: **любое изменение записи сначала снимает её старые следы
из индексов, потом ставит новые**.

```
orders: id -> Order            by_customer: клиент -> {(время, id)}
  добавить / заменить / передать / удалить: unindex(старый заказ), потом index(новый)
```

Типичные беды: удаление забыло индекс (в списке клиента «призрак»); правка поменяла клиента, а старый список
остался; последний заказ ушёл, а пустая запись клиента висит и портит счётчики. Лечится одной внутренней
функцией `unindex`, через которую проходят все изменения, и удалением пустых записей сразу.

## Типичные ошибки

- Выводить обход `HashMap` в ответ или сравнивать его с эталоном в тесте.
- Писать `PartialEq` и `Hash` независимо друг от друга.
- Сортировать `f64` через `partial_cmp().unwrap()`.
- Брать `sort_unstable`, когда порядок равных виден пользователю.
- Использовать `dedup` как «уникальные значения» на несортированном векторе.
- Забыть, что `range` паникует при перевёрнутых границах.
- Реализовывать «топ N» максимальной кучей или хранить весь поток.
- Забыть убрать запись из вторичного индекса при замене, правке или удалении.
