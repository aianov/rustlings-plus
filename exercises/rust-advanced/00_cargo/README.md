# Cargo, пакеты и зависимости

Представь, что ты неделю писал сервис, и у тебя всё работает. Коллега клонирует репозиторий, запускает
`cargo build` и получает три страницы ошибок: у него вышла свежая версия какой-то зависимости, а ты
собирал вчерашней. Через месяц CI падает на тесте, который «вроде проходил», потому что кто-то включил
feature в одном крейте, и она молча поменяла поведение в другом. В продакшене программа считает
счётчик правильно, а у тебя на ноутбуке паникует: релизная сборка завернула переполнение, а отладочная
его заметила.

Все эти истории про одно: Cargo делает за тебя много решений (какие версии взять, что включить, как
оптимизировать), и если не знать, где эти решения лежат, они случаются как будто сами.

Две анимации к главе открываются клавишей `v`: путь от `Cargo.toml` к `Cargo.lock` и сборке, и
диапазоны semver.

## Пакет, крейт и цели

Слова «пакет» и «крейт» в разговорах путают, а Cargo их различает.

**Пакет** (package) это то, что описано в одном `Cargo.toml` с секцией `[package]`. У него есть имя,
версия и набор исходников. **Крейт** (crate) это единица компиляции: то, что `rustc` получает на вход и
превращает в одну библиотеку или один исполняемый файл. Один пакет может содержать несколько крейтов.
Наконец, **цель** (target) это конкретный крейт внутри пакета с именем и видом: библиотека, бинарник,
пример, тест, бенчмарк.

Cargo находит цели по раскладке папок, ничего для этого писать не надо:

```
tiny-calc/
  Cargo.toml
  build.rs                  скрипт сборки (если есть)
  src/
    lib.rs                  библиотека, имя крейта tiny_calc
    main.rs                 бинарник с именем пакета, tiny-calc
    bin/
      bench.rs              бинарник bench
      seed/main.rs          бинарник seed (папка с main.rs внутри)
  examples/demo.rs          пример: cargo run --example demo
  tests/acceptance.rs       интеграционный тест, отдельный крейт
  benches/speed.rs          бенчмарк
```

Заметь, что у пакета `tiny-calc` библиотека называется `tiny_calc`. В имени пакета дефис законен, а в
имени крейта, как в любом идентификаторе Rust, его быть не может, поэтому дефис превращается в
подчёркивание. Пишешь `use tiny_calc::eval`, а в командной строке `cargo run --bin tiny-calc`.
Имя бинарника остаётся с дефисом, его в Rust-коде никто не пишет.

Автоматика не всегда угадывает. Когда нужно другое имя или нестандартный путь, цель объявляют сами:

```toml
[package]
name = "tiny-calc"
version = "0.1.0"
edition = "2024"
rust-version = "1.88"

[[bin]]
name = "calc-bench"
path = "src/bin/bench.rs"
```

Двойные скобки значат «элемент массива таблиц»: бинарников может быть много. Как только ты описал
`[[bin]]` вручную, это отменяет автоматику только для этого файла, остальные цели по-прежнему
находятся сами.

Поля `[package]`, о которых стоит знать с первого дня. `edition` выбирает диалект языка (2015, 2018,
2021, 2024) и задаётся для каждого крейта отдельно: проект на 2021 спокойно зависит от крейта на 2024.
Но код читается по правилам той эдиции, что объявлена в собственном манифесте. Цепочки
`if let ... && ...` появились в 2024, поэтому такой код соберётся только в крейте с `edition = "2024"`. `rust-version` задаёт
минимально допустимый компилятор (MSRV). Она ничего не скачивает, а лишь даёт Cargo повод остановиться
с понятным сообщением, а не с простынёй ошибок про неизвестные возможности. `publish = false` страхует
от случайного `cargo publish` внутреннего пакета.

Посмотреть, что Cargo увидел в пакете, можно командой `cargo metadata --no-deps --format-version 1`.
Это JSON, и тесты первых задач читают именно его.

## Библиотека и бинарник в одном пакете

Типичная ошибка новичка: в `main.rs` пишет `mod something;`, а в `lib.rs` тоже `pub mod something;`.
Оба корня крейта подключают один и тот же файл, и получаются **два независимых крейта**, каждый со
своей копией типов. Компилятор честно скажет: ожидался `Book`, а пришёл `Book`, и в сообщении будут
одинаковые имена. Это не баг компилятора. `mod` не импортирует модуль, а **включает файл в текущий
крейт**.

Правильная схема такая: весь код живёт в библиотеке, а бинарники это тонкая обёртка. Они видят
библиотеку как обычную внешнюю зависимость, по имени пакета:

```rust
// src/main.rs
use word_count::stats::analyze;

use std::io::Read;

fn main() -> std::io::Result<()> {
    let mut text = String::new();
    std::io::stdin().read_to_string(&mut text)?;
    println!("words: {}", analyze(&text).words);
    Ok(())
}
```

Выигрыши от такой раскладки практичные: логику можно вызвать из интеграционного теста, из второго
бинарника, из другого пакета; бинарнику не нужно знать, как устроены модули; а когда из пакета
вырастет воркспейс, библиотека уедет в отдельный крейт без переписывания.

## Версии и semver

Версия крейта это три числа: `major.minor.patch`. Договор semver такой: новая patch-версия чинит
ошибки, minor добавляет возможности и ничего не ломает, major вправе ломать. Поэтому, когда пишешь
зависимость, ты говоришь не «хочу версию 1.0.100», а «подойдёт любая, которая совместима с 1.0.100».
Это называется **требованием** (version requirement), и оно превращается в диапазон.

```toml
serde = "1.0.100"   # то же, что ^1.0.100: от 1.0.100 до 2.0.0 (не включая)
tokio = "~1.30"     # от 1.30.0 до 1.31.0
rand  = "=0.8.5"    # ровно эта версия
log   = "*"         # любая (crates.io такое не принимает)
```

Каретка `^` разрешает всё, что не меняет **самый левый ненулевой** номер. Для `^1.2.3` это
`>=1.2.3, <2.0.0`. Для нулевых версий действует **правило нуля**: пока крейт не дорос до 1.0, любое
изменение может ломать, поэтому границу ставят правее.

```
требование    нижняя    верхняя (не включая)
^1.2.3        1.2.3     2.0.0
^0.2.3        0.2.3     0.3.0       нули: главным становится minor
^0.0.3        0.0.3     0.0.4       два нуля: главным становится patch
^0.2          0.2.0     0.3.0
^0            0.0.0     1.0.0
~1.2.3        1.2.3     1.3.0       тильда: только патчи
~1            1.0.0     2.0.0
1.*           1.0.0     2.0.0
```

Самая частая ошибка в самописных проверках версий: считать, что `^0.2.3` пускает `0.3.0`. Не пускает.
Вторая: сравнивать версии строками, из-за чего `1.10.0` оказывается меньше `1.9.0`. Сравнивай числа.

Один разработчик в чужом проекте обновил `^0.8` до `0.9` и получил десять ошибок компиляции. Это не
вина автора крейта: переход 0.8 к 0.9 в semver обязан считаться ломающим, и каретка так и работает.

## Cargo.lock

Требование это диапазон, а собрать нужно одну конкретную версию. Выбор делает **резолвер**: берёт
из индекса реестра список опубликованных версий и для каждого крейта выбирает **максимальную из
подходящих**, учитывая всё дерево зависимостей сразу. Результат записывается в `Cargo.lock`:

```
Cargo.toml                 реестр                    Cargo.lock
serde = "1.0.100"  ──►  1.0.99, 1.0.100,   ──►  serde 1.0.200
                         1.0.200, 2.0.0           (с контрольной суммой)
```

После этого лок главнее реестра. Пока записанная версия подходит под `Cargo.toml`, `cargo build`
берёт её, даже если вышла более новая. Так у всех, кто собирает проект, получается один и тот же набор
версий. Новую версию ты получаешь осознанно:

```
cargo update               перевыбрать всё
cargo update -p serde      перевыбрать только serde, остальное не трогать
cargo build --locked       не менять лок: если лок надо править, упасть
cargo build --offline      не ходить в сеть, брать из локального кэша
```

`--locked` это страховка для CI. Если кто-то поправил `Cargo.toml` и забыл закоммитить лок, обычная
сборка тихо перепишет файл, и об этом никто не узнает. С флагом сборка упадёт, и недочёт будет виден.

Что коммитить. Для бинарников и сервисов `Cargo.lock` коммитят обязательно: он и есть воспроизводимость.
Для библиотек практика сегодня тоже в основном коммитить, чтобы CI был стабильным, но помни, что у
тех, кто подключит твою библиотеку, лок будет свой, а не твой. Поэтому библиотеку полезно проверять и
на самых свежих версиях зависимостей.

## Виды зависимостей

Не все зависимости нужны для одного и того же. У Cargo три секции, и каждая отвечает на вопрос «кто и
когда использует крейт».

```toml
[dependencies]            # код пакета: lib, bin
fmtkit = { path = "crates/fmtkit" }

[dev-dependencies]        # тесты, примеры, бенчмарки
testkit = { path = "crates/testkit" }

[build-dependencies]      # только build.rs
stamp = { path = "crates/stamp" }
```

Dev-зависимости не попадают к тем, кто подключит твой пакет, и не собираются при обычном
`cargo build`. Build-зависимости компилируются отдельно и видны только скрипту сборки: код пакета их не
видит, а `build.rs` не видит обычных. Ошибка «не в той секции» редко ломает сборку сразу (разве что
build.rs), зато незаметно раздувает чужие проекты.

Источник зависимости тоже выбирается в записи: версия из реестра (`serde = "1"`), локальный путь
(`path = "../util"`), репозиторий (`git = "https://..."`). Для путей версию можно не указывать, но при
публикации потребуется.

Управлять зависимостями удобно из командной строки, это правит `Cargo.toml` аккуратнее, чем руки:

```
cargo add serde --features derive      добавить в [dependencies]
cargo add --dev tempfile               в [dev-dependencies] (или -D)
cargo add --build cc                   в [build-dependencies]
cargo remove tempfile                  убрать
cargo tree                             всё дерево
cargo tree -i syn                      кто тянет syn (инвертированное дерево)
cargo tree -d                          крейты, которые собраны в нескольких версиях
cargo tree -e features                 какие features включены и кем
```

## Features

Feature это переключатель сборки. Он включает куски кода и опциональные зависимости, чтобы пользователь
платил только за то, чем пользуется. Объявляются features в `[features]`, а опциональные зависимости
помечаются `optional = true`:

```toml
[dependencies]
colorize = { path = "crates/colorize", optional = true }

[features]
default = ["json"]
json = []
color = ["dep:colorize"]
```

Справа в списке то, что feature включает: другие features или, с префиксом `dep:`, зависимость. Пустой
список значит «просто флаг для `cfg`». Запись `dep:colorize` включает зависимость и **прячет** её
неявную feature: наружу виден понятный `color`, а не случайное имя крейта. В коде feature проверяется
условной компиляцией:

```rust
#[cfg(feature = "json")]
pub fn format_json(level: &str, msg: &str) -> String { /* ... */ }

#[cfg(feature = "color")]
pub fn format_color(level: &str, msg: &str) -> String {
    colorize::red(&format!("[{level}] {msg}"))
}
```

Пользователь включает их так: `cargo build --features color`, `--no-default-features` отключает всё, что
перечислено в `default`, `--all-features` включает всё. Зависимость на крейт с features пишется
`serde = { version = "1", default-features = false, features = ["derive"] }`.

Главное свойство features: они **аддитивны**. Если в дереве зависимостей два пакета запросили один и
тот же крейт с разными features, Cargo соберёт крейт **один раз** с объединением features. (Есть
уточнение для edition 2021 и новее: features dev- и build-зависимостей не смешиваются с обычными, если
крейт собирается не для тестов. Увидишь это в `cargo tree -e features`: не пугайся двух строк.)

```
 твоя программа
   ├── A ── lib [fast]  ┐
   └── B ── lib [log]   ┴──►  lib собирается один раз: [fast, log]
```

Отсюда правило: feature может только **добавлять** возможности. Feature с отрицательным смыслом
(`no_log`, `no_std` в смысле «выключи»), которую кто-то один включил, лишит возможности всех. Если
хочется отключаемого поведения, делай его включаемым положительной feature (`log`), помещай в
`default` и отключай через `default-features = false`. Хорошая привычка: собери крейт с
`--all-features` и убедись, что ничего не пропало.

И ещё одна ловушка. Код, который использует опциональную зависимость, обязан висеть под `#[cfg]` той же
feature. Выражение `cfg!(feature = "color")` не годится: оно превращается в булево значение, обе ветки
остаются в программе, и без зависимости ветка не соберётся.

## Условная компиляция: cfg

`#[cfg(условие)]` вырезает следующий элемент до компиляции, если условие ложно. Условия бывают разные:

```rust
#[cfg(test)]                     // только при cargo test
#[cfg(debug_assertions)]         // отладочные проверки включены (профиль dev)
#[cfg(not(debug_assertions))]    // и наоборот
#[cfg(feature = "json")]         // включена feature
#[cfg(target_os = "linux")]      // платформа
#[cfg(all(unix, feature = "x"))] // комбинации: all, any, not
```

Три формы записи, которые нужно различать.

1. Атрибут `#[cfg(...)]` над элементом или выражением вырезает код целиком. Вырезанный код даже не
   проверяется на типы. Так делают функции, которых в release быть не должно.
2. Макрос `cfg!(...)` возвращает `true` или `false`, а код остаётся. Обе ветки обязаны
   скомпилироваться. Подходит для `if cfg!(debug_assertions) { println!(...) }`.
3. `#[cfg_attr(условие, атрибут)]` включает атрибут по условию. Самое частое применение:
   `#[cfg_attr(test, derive(Debug, PartialEq))]` даёт типу сравнение в тестах и не раздувает
   рабочую сборку.

Отдельно запомни `debug_assert!`. Он проверяет то, что в правильной программе невозможно, и не стоит
ничего в release. Но раз в release проверки нет, то поведение на неверных значениях задай отдельно
(например, ограничь значение), иначе баг молча уедет в продакшен.

## Переполнение целых

В Rust арифметика над целыми проверяет переполнение **в зависимости от профиля**: в dev это паника
`attempt to add with overflow`, в release значение молча завернётся по модулю. Это сделано ради
скорости в release, и это источник самых неприятных расхождений между «у меня работает» и продакшеном.

Поэтому там, где переполнение возможно, выбирай явный метод:

```
x.wrapping_add(1)       255u8 → 0, заворот по кругу (счётчики, хеши)
x.saturating_sub(5)     упирается в границу: 3u8 → 0 (здоровье, лимиты)
x.checked_add(1)        Some(результат) или None (суммы размеров, безопасная арифметика)
x.overflowing_add(1)    (результат, было_ли_переполнение)
```

Все четыре семейства есть для `add`, `sub`, `mul`, `neg`, `abs`, `pow`, `div` (у деления краевой случай
`i32::MIN / -1` и деление на ноль). Для среднего двух чисел вместо `(a + b) / 2` расширяй тип:
`(u16::from(a) + u16::from(b)) / 2`. Выбор метода это решение автора кода, а не следствие профиля.

## Профили

Профиль это набор настроек компилятора. Встроенных два: `dev` для `cargo build`/`cargo test` и
`release` для `cargo build --release`. Правятся они в `Cargo.toml`:

```toml
[profile.dev]
opt-level = 1             # 0 (по умолчанию) .. 3, ещё "s" и "z" ради размера

[profile.dev.package.heavy]
opt-level = 3             # отдельная настройка для одной зависимости

[profile.release]
lto = true                # оптимизация на уровне всей программы
codegen-units = 1         # медленнее собирается, лучше оптимизируется
panic = "abort"           # паника завершает процесс без размотки стека
overflow-checks = true    # проверки переполнения и в release
```

Что важно знать. `opt-level` определяет скорость кода, а `debug` определяет, будет ли отладочная
информация. Настройки отдельной зависимости пишутся в `[profile.dev.package.имя]`; запись с
`"*"` означает «все чужие пакеты», но **не членов твоего воркспейса**. `panic = "abort"` решает
владелец итоговой программы: библиотека не должна навязывать это своим пользователям. Любой параметр
профиля можно проверить: `cargo build -v` печатает полные команды `rustc` с флагами.

## Секция [lints]

Раньше правила проверок задавали флагами (`RUSTFLAGS="-D warnings"`) или атрибутами
`#![forbid(unsafe_code)]` в каждом корне крейта. Теперь их записывают в манифест один раз, и они
действуют на все цели пакета (библиотеку, бинарники, тесты, примеры):

```toml
[lints.rust]
unsafe_code = "forbid"

[lints.clippy]
all = { level = "warn", priority = -1 }
unwrap_used = "deny"
```

Уровни: `allow`, `warn`, `deny`, `forbid`. `forbid` сильнее `deny`: его нельзя ослабить локальным
`#[allow]`. Если в одной секции пересекаются группа (`all`) и конкретное правило, победитель
определяется приоритетом: у группы ставят отрицательный, чтобы конкретное правило имело последнее
слово. Проверяются lints командой `cargo clippy` (правила `clippy::...`) и обычной сборкой (правила
компилятора).

## build.rs

Если рядом с `Cargo.toml` лежит `build.rs`, Cargo сначала собирает и запускает его, и только потом
собирает сам пакет. Скрипт общается с Cargo через переменные окружения (вход) и строки в stdout
(выход):

```
build.rs запущен  ──►  читает env: OUT_DIR, CARGO_PKG_VERSION, CARGO_MANIFEST_DIR ...
        │              читает файлы пакета (рабочая папка скрипта: корень пакета)
        │              пишет сгенерированное в OUT_DIR
        └────────────► печатает директивы:
                         cargo::rerun-if-changed=data/words.txt
                         cargo::rustc-env=APP_BUILD=app 0.3.0
                         cargo::warning=текст для пользователя
```

Минимальный рабочий скрипт, который читает файл с данными и пишет сгенерированный код (другой
пример, чем в задачах: таблица цветов):

```rust
use std::{env, fs, path::PathBuf};

fn main() {
    println!("cargo::rerun-if-changed=data/colors.txt");
    let text = fs::read_to_string("data/colors.txt").expect("нет data/colors.txt");
    let names: Vec<&str> = text.lines().map(str::trim).filter(|l| !l.is_empty()).collect();
    let code = format!("pub const COLORS: &[&str] = &{names:?};\n");
    let out = PathBuf::from(env::var_os("OUT_DIR").expect("cargo задаёт OUT_DIR")).join("colors.rs");
    fs::write(out, code).expect("не удалось записать colors.rs");
    println!("cargo::rustc-env=COLORS_COUNT={}", names.len());
}
```

В самом скрипте переменные окружения читают во время работы (`env::var`, `env::var_os`). А в коде
пакета `env!("...")` читает их при компиляции. Не путай эти два случая. Формат `{names:?}` печатает
срез как литерал Rust с кавычками, так что результат можно сразу вставить в код.

Сгенерированный файл подключают так:

```rust
include!(concat!(env!("OUT_DIR"), "/words.rs"));
pub const BUILD: &str = env!("APP_BUILD");
```

`include!` вставляет файл как исходный текст, `env!` читает переменную окружения **на этапе
компиляции** (если её нет, это ошибка сборки, а не `None`). Подробности, которые отличают рабочий
скрипт от опасного.

- Писать можно только в `OUT_DIR`. Свои исходники скрипт сборки менять не должен: это пачкает
  репозиторий и ломает определение «изменилось ли что-то».
- Без единой `rerun-if-changed` Cargo перезапускает скрипт, когда меняется **любой** файл пакета.
  Как только директива появилась, следят только за перечисленными путями. Скопированная из примера
  строка `rerun-if-changed=build.rs` означает «следи за самим скриптом» и больше ни за чем, и данные
  после этого перестают быть видны. Указывай файлы с данными явно, можно целую папку.
- Старый синтаксис `cargo:имя=значение` (одно двоеточие) работает, но новый `cargo::` предпочтителен,
  начиная с Rust 1.77.

Отладить скрипт можно через `cargo build -vv`: он показывает вывод скрипта сборки.

## Как выбрать библиотеку

Каждая зависимость это чужой код в твоей программе, с чужой лицензией, чужими ошибками и чужим темпом
обновлений. Прежде чем добавить крейт, потрать пять минут.

1. **Лицензия.** Поле `license` в Cargo.toml крейта. `MIT`, `Apache-2.0` или их комбинация безопасны
   почти всегда. GPL и подобные заразные лицензии для закрытого кода часто неприемлемы.
2. **Свежесть.** Дата последнего релиза и состояние issue. Пять лет без релизов не обязательно
   плохо, но исправлений безопасности ждать не от кого.
3. **Популярность.** Загрузки и число зависимых крейтов. Это не гарантия качества, но чем больше
   пользователей, тем быстрее найдут ошибку.
4. **Размер дерева.** `cargo tree` покажет, сколько крейтов ты притащил. Сорок транзитивных
   зависимостей ради одной функции это повод написать её самому.
5. **unsafe и документация.** Много `unsafe` без объяснений тревожный знак. Хорошая документация на
   docs.rs и примеры признак ухода за крейтом.
6. **Features.** Умеет ли крейт отключать лишнее (`default-features = false`).

## Типичные ошибки

- Модуль подключён и в `lib.rs`, и в `main.rs`: типы «одинаковые, но разные».
- Требование `^0.2.3` и ожидание, что `0.3.0` подтянется само.
- Тестовая утилита в `[dependencies]`: она поедет в продакшен.
- Feature `no_something`: она поссорит два крейта в одном дереве.
- `cfg!(feature = "x")` там, где нужен `#[cfg(feature = "x")]`.
- В `build.rs` забыт `rerun-if-changed` на данные, а сгенерированный файл лежит в `src/`.
- Уверенность, что release считает так же, как debug.
- Не закоммитили `Cargo.lock` у сервиса: CI собрал не то, что ты тестировал.
