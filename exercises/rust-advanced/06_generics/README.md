# Generics углублённо

Склад хранит коробки, и кладовщику нужны три вещи: найти самую тяжёлую, напечатать этикетку и
посчитать общий вес. Для коробок с запчастями, для коробок с одеждой и для коробок «неизвестно что»
код одинаков, различается только то, что с содержимым вообще можно делать. Обобщённый код как раз про
это: пишешь один раз, а компилятор проверяет, что везде, где его вызывают, у типов есть всё
необходимое. Здесь разберём, как выражать «необходимое» точно (не больше и не меньше), как не
ломать свои типы лишними требованиями и как заставить компилятор ловить ошибки, которые обычно
находят тестами. Анимация (клавиша `v`) показывает типы-состояния: письмо переходит из черновика в
отправленное, и методы, недоступные в этом состоянии, гаснут.

## Границы и where

```rust
fn heaviest<T: PartialOrd + Copy>(boxes: &[T]) -> Option<T> { .. }

fn label_all<I>(items: I) -> Vec<String>
where
    I: IntoIterator,
    I::Item: std::fmt::Display,
{ .. }
```

`T: A + B` читается «T умеет и A, и B». Когда границ много или они не про сам параметр, их выносят в
`where`: так сигнатура остаётся читаемой, а `where` умеет то, чего не умеет запись в угловых скобках, например
границу на `I::Item`. Правило выбора границ простое: **ровно то, что делает тело**. Лишнее требование
отсекает типы, которые могли бы подойти. `Ord` там, где хватило бы `PartialOrd`, не пустит `f64`;
`Clone` там, где достаточно ссылки, заставит копировать.

## Границы на impl, а не на структуре

```rust
struct Shelf<T: Display> { boxes: Vec<T> }   // плохо: Shelf<Vec<u8>> теперь не создать
struct Shelf<T> { boxes: Vec<T> }            // хорошо
impl<T> Shelf<T> { fn add(&mut self, b: T) { .. } }
impl<T: Display> Shelf<T> { fn labels(&self) -> Vec<String> { .. } }
```

Граница на структуре заразна: она повторяется в каждом `impl`, в каждой функции, которая принимает
`Shelf<T>`, и в чужом коде. Поэтому структуру оставляют без границ, а требования ставят на те блоки
`impl`, где они нужны. Блоков может быть сколько угодно, и каждый добавляет методы только для своего
класса типов. Бывают и блоки для одного конкретного типа: `impl Shelf<u32> { fn total(&self) -> u32 { .. } }`.
Методы таких блоков существуют только у `Shelf<u32>`, а у `Shelf<String>` вызов не соберётся. Два блока,
дающие один метод одному и тому же типу, конфликтуют: компилятор не выбирает «более подходящий».

## Вывод типов, турбофиш и аннотации

Компилятор выводит типы из использования, но иногда в контексте нет ответа:

```rust
let n = "12".parse().unwrap();              // ошибка: type annotations needed
let n = "12".parse::<u16>().unwrap();       // турбофиш: тип прямо в вызове
let n: u16 = "12".parse().unwrap();         // аннотация переменной
let total: f32 = prices.iter().sum();       // sum тоже не знает, во что складывать
let words = text.split(' ').collect::<Vec<_>>();   // _ означает «выведи сам»
```

Турбофиш (`::<>`) удобен в середине цепочки, аннотация переменной читается лучше, когда результат
сразу попадает в `let`. Тип часто выводится из того, куда значение уходит (из возвращаемого типа
функции, из аргумента другой функции), поэтому бывает достаточно поставить аннотацию там, где
значение используется. Подумай и о том, какой тип выбираешь: `i32` не вместит счётчик лайков.

## Удобные параметры: Into, AsRef

Функция, которая хочет текст, проще всего принимает `&str`. А тому, кто вызывает её со `String`, придётся
писать `&s`, а с `Cow` или `Box<str>` писать преобразования. Два трейта снимают заботу:

```rust
fn rename(&mut self, name: impl Into<String>) { self.name = name.into(); }        // забираем владение
fn weigh(data: impl AsRef<[u8]>) -> usize { data.as_ref().len() }                // только читаем
```

`Into<String>` принимают, когда значение нужно **сохранить**: если дали `String`, она просто переедет,
если `&str`, выделится копия, и вызывающий не пишет `.to_string()`. Источников у `Into<String>` больше, чем кажется: `String`, `&str`, `char`, `Box<str>`, `Cow<str>`. `AsRef<T>` принимают, когда значение
нужно **прочитать**: `AsRef<str>` подходит для `&str`, `String`, `&String`, `Cow<str>`; `AsRef<[u8]>`
для `Vec<u8>`, срезов, массивов и строк. Цена: каждый тип аргумента порождает свою копию функции
(мономорфизацию), поэтому в тело длинной функции можно сразу вынести преобразование в обычный `&str`.

Отдельный частый случай: `&String` и `&Vec<T>` в параметрах. Они принимают меньше, чем `&str` и `&[T]`, а
дают столько же возможностей чтения. Любой `&String` сам приводится к `&str`, любой `&Vec<T>` к `&[T]`,
а ещё `&str` и `&[T]` принимают литералы, массивы и куски срезов. Clippy предупреждает об этом (`ptr_arg`).
Возвращаемое значение можно сделать таким же: вместо `&String` отдавать `&str`.

## FromStr и границы на ассоциированные типы

Трейт `FromStr` связывает тип с разбором из строки, а у каждой реализации свой тип ошибки:

```rust
fn read_setting<T: FromStr>(raw: &str) -> Result<T, String> {
    raw.trim().parse::<T>().map_err(|e| e.to_string())       // ошибка: T::Err не обязан быть Display
}
```

Ошибка тут в том, что про `T::Err` ничего не известно. Требование записывают на ассоциированный тип:
`where T: FromStr, T::Err: Display`. Так же ограничивают элементы итераторов: `I::Item: Display`,
`<I as Iterator>::Item: Ord`. `I::Item` это просто путь к ассоциированному типу, писать его можно где угодно, в том числе в теле
(`let first: I::Item = ..`). Граница на элементы нужна потому, что трейт `Iterator` ничего не знает о том,
что внутри: чтобы сложить элементы, пиши `I::Item: Sum`, чтобы сравнить, `I::Item: Ord`.

## PhantomData и типобезопасные id

```rust
struct Meters;
struct Feet;
struct Length<U> { value: f64, _unit: PhantomData<U> }
```

`Length<Meters>` и `Length<Feet>` это разные типы с одинаковым содержимым, и сложить их случайно не получится.
`U` нигде не хранится, но структура обязана его использовать: иначе ошибка «parameter `U` is never
used». `PhantomData<U>` занимает ноль байт и говорит компилятору «считай, что тут есть `U`». Форма
`PhantomData<fn() -> U>` ещё и не делает структуру зависимой от `Send`, `Sync` и деструктора `U`:
тип-метка остаётся только меткой.

Ловушка с `derive`. `#[derive(Clone, Copy, PartialEq)] struct Length<U> { .. }` разворачивается в
`impl<U: Clone> Clone for Length<U>`, то есть требует свойства от самого `U`, хотя он нигде не лежит.
Тогда `Length<Meters>` копируется, только если копируем `Meters`, а `Length<SomeBigStruct>` теряет `Copy`. Если
метка должна быть просто меткой, реализуй трейты вручную без границ на `U`:

```rust
impl<U> Clone for Length<U> { fn clone(&self) -> Self { *self } }
impl<U> Copy for Length<U> {}
```

## Операторы и индексирование

Операторы это трейты из `std::ops`: `a + b` значит `Add::add(a, b)`.

```rust
impl Add for Celsius { type Output = Celsius; fn add(self, rhs: Celsius) -> Celsius { Celsius(self.0 + rhs.0) } }
impl Mul<f64> for Celsius { type Output = Celsius; fn mul(self, k: f64) -> Celsius { Celsius(self.0 * k) } }
impl Mul<Celsius> for f64 { type Output = Celsius; fn mul(self, c: Celsius) -> Celsius { c * self } }
```

Параметр трейта (`Mul<f64>`) позволяет один тип умножать на разные правые части. Чтобы записать `2.0 * t`,
реализацию пишут для `f64` с твоим типом в параметре, и правило сироты это разрешает. `AddAssign` даёт `+=`,
`Neg` унарный минус, `std::iter::Sum` даёт `.sum::<Celsius>()`: реализация сворачивает итератор от нуля, например
`impl Sum for Celsius { fn sum<I: Iterator<Item = Celsius>>(iter: I) -> Celsius { iter.fold(Celsius(0.0), |a, b| a + b) } }`.
Для печати с нулями вроде `07` пригодится формат `{:02}`. Операторы сравнения живут отдельно
(`PartialEq`, `PartialOrd`).

Индексирование: `Index<I>` для `a[i]` на чтение, `IndexMut<I>` для записи и для `a[i] += 1`.
`Output` у `Index` может быть не размерным: `type Output = [T]` даёт срез. Главное в реализации
это проверка границ **по каждой оси**: если у сетки ширина 3 и ты проверяешь только общий индекс в
плоском векторе, пара `(3, 0)` тихо попадёт на соседнюю строку.

## Const generics

```rust
struct Window<const N: usize> { last: [i32; N] }
impl<const N: usize> Window<N> { fn average(&self) -> f64 { self.last.iter().sum::<i32>() as f64 / N as f64 } }
fn first_n<const N: usize>(xs: &[i32]) -> Option<[i32; N]> { xs.get(..N)?.try_into().ok() }
```

Число становится параметром типа: `Window<3>` и `Window<4>` разные типы, размер известен при
компиляции, куча не нужна. `N` можно использовать как значение в теле (`N as f64`, `0..N`) и в типах массивов.
Чтобы создать массив в обобщённом коде, нужно уметь его заполнить: `[T::default(); N]` при `T: Copy + Default`
(для `Copy`-значений массив копируется). Кольцо хранят так: массив, индекс следующей записи и счётчик занятых мест.
Не забывай крайний случай `N = 0`: деление и индексы вида `% N` ломаются. Выражения над `N` вроде
`[T; N + 1]` в стабильном Rust не поддерживаются.

## Builder

Когда у типа много необязательных полей, конструктор с десятью аргументами нечитаем. Builder собирает
значение по шагам:

```rust
let req = Request::builder().url("https://x.io").header("a", "b").timeout(5).build()?;
```

Каждый метод берёт `self` по значению и возвращает `Self` (или меняет `mut self` и возвращает его), а `build`
проверяет инварианты и возвращает `Result`. Цепочка по значению означает, что builder можно использовать
один раз: после `build` или промежуточного вызова старая переменная недоступна. Обязательные поля проверяют
в `build`, а ошибки называют вариантами `enum`.

## Typestate: ошибки порядка ловит компилятор

Идея: состояние объекта кодируется типом, а методы пишутся только в тех `impl`, где они допустимы.

```rust
struct Letter<S> { text: String, _s: PhantomData<S> }
struct Draft; struct Sealed; struct Sent;
impl Letter<Draft>  { fn write(mut self, t: &str) -> Self { .. }  fn seal(self) -> Letter<Sealed> { .. } }
impl Letter<Sealed> { fn send(self) -> Letter<Sent> { .. } }
impl<S> Letter<S>   { fn text(&self) -> &str { &self.text } }       // общее для всех состояний
```

Переход берёт `self` по значению и отдаёт значение другого типа: старое состояние нельзя использовать
по ошибке, а вызов `send` на черновике просто не собирается. Типичная дыра: метод перехода, объявленный в
общем `impl<S>`. Тогда он доступен во всех состояниях, и типы стали декорацией. Общими делай только
методы, которые безопасны в любом состоянии.

Обязательные поля в обычном builder'е хранят как `Option<String>`, а `build` превращает `None` в ошибку.
Для builder'а с обязательными полями так же используют параметры-состояния: `Builder<Name, Email>`, где каждый
параметр `Missing` или `Set`. Сеттер имени меняет первый параметр на `Set` и не трогает второй (поэтому он
объявлен для любого `E`), а `build` написан только для `Builder<Set, Set>`. Переходы, которые могут
не получиться, возвращают `Result<Новое, Старое>`, чаще в паре с причиной: `Err((Старое, Причина))`. Тогда при ошибке
состояние не теряется, а вызывающий знает, что пошло не так.

## Типичные ошибки

Ставить границы на структуру. Требовать `Ord`, когда хватает `PartialOrd`. Принимать `&String` и
`&Vec<T>` вместо `&str` и `&[T]`. Забыть `T::Err: Display` и получить ошибку далеко от причины. Вешать
`derive` на структуру с `PhantomData<T>` и удивляться, что `Copy` пропал. Не проверять каждую ось в `Index`.
Писать `N = 0` без мысли. Делать переход typestate в общем `impl<S>`.
