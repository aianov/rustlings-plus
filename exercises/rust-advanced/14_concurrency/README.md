# Потоки и общая память

Кассы концертного зала продают билеты на последний ряд. Остался один билет. Две кассы одновременно смотрят
на счётчик, видят «1», обе продают и обе записывают «0». Билет продан дважды, в зале скандал. В коде это
выглядело невинно: `let left = tickets; if left > 0 { tickets = left - 1; }`. Каждая строка по отдельности
верна, а вместе они ломаются, как только два потока оказываются между строками одновременно.

Эта глава о том, как несколько потоков безопасно работают с общими данными: что Rust проверяет за тебя
(и это много), что остаётся тебе (порядок замков, условие ожидания, видимость записей) и как собрать из
этого свой пул потоков. Сетевая асинхронщина с её каналами и замками разбирается позже, в разделе tokio:
там те же идеи, только поверх задач, а не потоков.

## Поток: spawn и join

```rust
use std::thread;

let handle = thread::spawn(|| {
    // эта часть бежит в новом потоке
    (1..=10).sum::<u32>()
});
let total = handle.join().unwrap();   // ждём конца и забираем результат
```

`thread::spawn` запускает замыкание в новом потоке операционной системы и сразу возвращает `JoinHandle`.
`join` блокирует вызывающего, пока поток не закончится, и отдаёт `Result`: `Ok` с тем, что вернуло замыкание,
или `Err`, если поток упал с паникой. Паника в потоке не валит программу. Она превращается в значение:

```rust
let result = thread::spawn(|| panic!("нет места")).join();
if let Err(payload) = result {
    // payload это Box<dyn Any + Send>; текст паники лежит внутри
    let text = payload.downcast_ref::<&str>();      // для panic!("литерал")
    let formatted = payload.downcast_ref::<String>(); // для panic!("код {n}")
}
```

Замыкание в `spawn` обязано быть `'static`: поток может пережить функцию, которая его запустила, поэтому
брать взаймы локальные переменные ему нельзя. Нужное отдают с `move`:

```rust
let name = String::from("касса-1");
thread::spawn(move || println!("{name} открыта"));   // имя переехало в поток
```

Если несколько потоков должны вернуть результаты, сначала запусти все (собери `JoinHandle` в `Vec`) и только
потом делай `join`. Запуск и `join` в одном цикле выстраивает потоки в очередь: каждый ждёт предыдущего.

### Потоки с областью

Часто данные лежат здесь же, в функции, и нужны нескольким потокам только на время вызова. Для этого есть
`thread::scope`: все потоки внутри гарантированно закончатся до выхода из области, поэтому им можно давать
ссылки на локальные данные, без `Arc` и без `'static`.

```rust
let prices = vec![120, 80, 300, 45];
let (left, right) = prices.split_at(2);
let (a, b) = thread::scope(|s| {
    let a = s.spawn(|| left.iter().sum::<u32>());
    let b = s.spawn(|| right.iter().sum::<u32>());
    (a.join().unwrap(), b.join().unwrap())
});
```

Правила заимствования никуда не делись. Две изменяемые ссылки на одну переменную не пройдут, зато
`chunks_mut` отдаёт непересекающиеся куски, и каждый поток спокойно пишет в свой:

```rust
let mut seats = vec![0u8; 100];
thread::scope(|s| {
    for part in seats.chunks_mut(25) {
        s.spawn(move || part.fill(1));
    }
});
```

Если потоков больше, чем ядер, ничего страшного, но порождать поток на каждую мелочь дорого: у потока свой
стек (мегабайты виртуальной памяти) и свой вызов в ядро. Для массовых мелких заданий нужен пул, о нём ниже.

## Send и Sync

Два маркерных трейта решают, что можно делать с типом между потоками. Их не пишут руками, компилятор выводит
их из полей.

```
Send   значение можно ПЕРЕДАТЬ в другой поток (владение переезжает)
Sync   на значение можно показывать &T из нескольких потоков (то же, что &T: Send)
```

Почему нужны оба. `Rc<T>` считает ссылки обычным числом, без синхронизации. Два потока, клонирующие один `Rc`,
испортят счётчик и приведут к двойному освобождению. Поэтому `Rc` не `Send`. `Cell` и `RefCell` позволяют менять
значение через общую ссылку без всяких замков. Передать такой `RefCell` в другой поток можно (он `Send`), а вот
показать `&RefCell` двум потокам нельзя: оба полезут менять. Поэтому он не `Sync`.

```
              Send    Sync
i32, String   да      да
Rc<T>         нет     нет
Cell/RefCell  да*     нет          (* если T: Send)
Arc<T>        да**    да**         (** если T: Send + Sync)
Mutex<T>      да      да           (если T: Send)
MutexGuard    нет     да           (замок отпускает тот же поток, что взял)
*const/*mut   нет     нет
```

Из таблицы выводится главное правило: `Arc<Mutex<T>>` это «общее значение, меняемое по очереди» (годится
почти для всего), `Arc<T>` без замка годится для данных, которые только читают. Ошибку про `Send` компилятор
выдаёт длинным сообщением, но читать нужно две строки: «cannot be sent between threads safely» и
«within ... the trait `Send` is not implemented for `Rc<...>`». Тип в этой фразе и есть виновник. Лечение
почти всегда парное: `Rc` на `Arc`, а `RefCell`/`Cell` на `Mutex` или атомик.

Если тебе придётся писать `unsafe impl Send for Свой`, значит, ты берёшь обязательство, которое компилятор
проверить не может. Об этом отдельная глава.

## Каналы: mpsc

`std::sync::mpsc` это очередь «много отправителей, один получатель». Хороший способ не делить память вовсе:
поток не лезет в чужие данные, а отправляет сообщение.

```rust
use std::sync::mpsc;

let (tx, rx) = mpsc::channel();
for id in 0..3 {
    let tx = tx.clone();                      // у каждого потока свой отправитель
    thread::spawn(move || tx.send(format!("касса {id}")).unwrap());
}
drop(tx);                                      // свой оригинал тоже отпускаем
for line in rx {                               // цикл кончится, когда закрыты ВСЕ отправители
    println!("{line}");
}
```

Канал закрывается, когда умирают все `Sender`. Именно поэтому в примере `drop(tx)` стоит до цикла: оригинал
такой же отправитель, как клоны, и пока он жив, получатель ждёт дальше. Забытый оригинал это самое частое
зависание при первой работе с каналами. Парная вещь: если умер получатель, `send` возвращает `Err`.

У получателя несколько способов читать. `recv()` ждёт вечно, `recv_timeout(d)` ждёт не дольше `d` и возвращает
`RecvTimeoutError::Timeout` (тихо) или `RecvTimeoutError::Disconnected` (отправителей больше нет, и это не
то же самое), `try_recv()` не ждёт вообще, а `try_iter()` отдаёт всё, что уже лежит.

Через канал можно отправлять не только данные, но и работу: `Box<dyn FnOnce() + Send>` это «любое
замыкание, которое выполнится один раз и может переехать в другой поток». `Send` в границе обязателен
(иначе компилятор не пустит задание в канал), `'static` подразумевается по умолчанию для `Box<dyn ...>`.

```rust
type Job = Box<dyn FnOnce() + Send>;
let (jobs, inbox) = mpsc::channel::<Job>();
let worker = thread::spawn(move || {
    for job in inbox { job(); }                // выполняем по порядку
});
jobs.send(Box::new(|| println!("печатаем билет"))).unwrap();
drop(jobs);                                    // закрыли очередь, рабочий выйдет
worker.join().unwrap();
```

## Mutex

`Mutex<T>` хранит значение внутри и выдаёт к нему доступ только через `lock()`. Вернувшийся охранник
(`MutexGuard`) разыменовывается как `&mut T`, а замок отпускается, когда охранник умирает (на закрывающей
скобке или раньше, если вызвать `drop`).

```rust
let tickets = Mutex::new(vec!["A1", "A2"]);
let taken = {
    let mut guard = tickets.lock().unwrap();   // замок взят
    guard.pop()                                // работаем с данными
};                                             // охранник умер, замок свободен
```

Правила хорошей работы с замком:

1. Держи его как можно короче. Всё, что не требует доступа к данным (форматирование, вычисления, вызов чужого
   кода, ввод-вывод), делай до или после. Пока замок у тебя, остальные ждут.
2. Не вызывай под замком код, который может взять тот же замок. `Mutex` не рекурсивный: поток, который
   просит замок, уже находясь внутри него, ждёт сам себя и не просыпается никогда. Публичные методы берут замок,
   а внутри работают с уже взятыми данными.
3. Смотри, когда умирает охранник. Временное значение живёт до конца выражения-объемлющей конструкции.
   В `match m.lock().unwrap().get(0) { ... }`, `if let Some(x) = m.lock().unwrap().pop() { ... }` и
   `while let Some(x) = m.lock().unwrap().pop() { ... }` охранник живёт до конца блока. Тело `while let` из-за
   этого выполняется под замком, и «параллельные» рабочие идут по одному. Достань значение отдельным
   `let item = m.lock().unwrap().pop();`, там охранник умирает на точке с запятой.

### Отравление

Если поток упал с паникой, держа охранника, `Mutex` помечается отравленным, и следующий `lock()` вернёт
`Err(PoisonError)`. Это предупреждение: данные могли остаться на середине изменения. Обычно `unwrap()` на нём
(пусть падает дальше) разумно. Но если данные простые и безопасно продолжить, доставай охранника из ошибки:

```rust
let guard = m.lock().unwrap_or_else(PoisonError::into_inner);
```

## Дедлоки и гонки логики

### Порядок захвата

Два замка и два потока, которые берут их в разном порядке, зависнут намертво:

```
поток X:  lock(hall) ... lock(box)        поток Y:  lock(box) ... lock(hall)

X держит hall и ждёт box.   Y держит box и ждёт hall.   Никто не продвинется.
```

Это дедлок: цикл «держу, жду». Лечение одно из двух: брать замки в одном и том же порядке везде (по номеру,
по адресу, по алфавиту ключа) или вообще не держать два замка сразу. Не нужно, чтобы порядок был «умным», нужно,
чтобы он был общим. Побочная ловушка: если порядок определяется по аргументам, случай «оба аргумента одно и
то же» берёт один замок дважды.

### Проверил, потом сделал

Самая коварная ошибка бывает и без дедлоков: каждое действие под замком, а логика всё равно ломается.

```rust
// плохо: места проверили под одним захватом, забронировали под другим
if !booked.lock().unwrap().contains(&seat) {
    booked.lock().unwrap().insert(seat);
}
```

Между двумя `lock()` другой поток успевает занять то же место. Условие и действие должны жить под ОДНИМ
захватом. Правило шире замков: любая пара «посмотрел, а потом решил» должна быть неделимой, иначе решение
принимается по устаревшим данным. Медленные подготовительные шаги (проверка формата, запрос в базу) делают
до замка, а под замком остаётся только «проверить занятость и вставить».

### RwLock

`RwLock<T>` пускает сколько угодно читателей (`read()`) или одного писателя (`write()`). Он выигрывает там, где
читают намного чаще, чем пишут (кэш). Ловушка: из читающего замка в пишущий не поднимешься. Писатель ждёт
ухода всех читателей, включая тебя самого:

```rust
let read = cache.read().unwrap();
if read.get(&key).is_none() {
    let mut write = cache.write().unwrap();   // ждёт ухода читателя, то есть тебя: вечное ожидание
}
```

Читающего охранника отпускают (в отдельном выражении или через `drop`), затем берут запись и ПЕРЕПРОВЕРЯЮТ
условие: пока ты ждал, кто-то мог уже положить значение. Эту схему называют «double-checked locking».

## Condvar: ждать условие

Мьютекс защищает данные, но не умеет ждать «пока что-то случится». Спать в цикле (`sleep`) значит или жечь процессор,
или реагировать с задержкой. Для этого есть `Condvar`: поток засыпает и просыпается по уведомлению.

```rust
use std::sync::{Condvar, Mutex};

let pair = (Mutex::new(false), Condvar::new());   // (флаг «зал открыт», звонок)

// ждущий
let (flag, bell) = &pair;
let opened = bell.wait_while(flag.lock().unwrap(), |open| !*open).unwrap();   // спим, пока не открыт

// будящий
*flag.lock().unwrap() = true;
bell.notify_all();                                 // или notify_one
```

Три правила, которые все выучили на ошибках.

1. Условие живёт в данных под мьютексом (флаг, очередь), а не в самом `Condvar`. Он только будит.
2. Условие проверяют в цикле. `wait_while` делает это за тебя, а ручной вариант это `while !ready { guard =
   cv.wait(guard).unwrap(); }`. Нужно, потому что бывают ложные пробуждения (без всякого `notify`) и потому что
   между уведомлением и моментом, когда ты снова взял замок, чужой поток мог всё забрать (одно значение, два
   проснувшихся потребителя).
3. Уведомление не копится. Если `notify` случился раньше, чем кто-то начал ждать, оно пропало. Именно поэтому
   состояние записывают в данные: ждущий, придя поздно, увидит поднятый флаг и не уснёт.

`notify_one` будит одного ждущего, `notify_all` всех. Для «все ждут открытия ворот» нужен `all`, для «одно
сообщение, один потребитель» хватает `one`. `wait_timeout_while(guard, d, условие)` ждёт не дольше `d` и
возвращает пару `(охранник, результат)`.

## Атомики

Для одного числа или флага замок избыточен: есть неделимые операции процессора. Типы `AtomicU64`, `AtomicBool`,
`AtomicUsize` в `std::sync::atomic`.

```rust
use std::sync::atomic::{AtomicU64, Ordering};

let sold = AtomicU64::new(0);
let number = sold.fetch_add(1, Ordering::Relaxed);   // вернёт значение ДО прибавления
sold.fetch_max(100, Ordering::Relaxed);              // максимум без гонки
let now = sold.load(Ordering::Relaxed);
```

Каждая операция неделима, но связка двух операций нет. `let v = a.load(..); a.store(v + 1, ..)` теряет обновления
точно так же, как с обычной переменной. Нужная операция должна быть одной: `fetch_add`, `fetch_max`, `swap`.
Для произвольного условия есть цикл с `compare_exchange(старое, новое, успех, неудача)`: он записывает новое,
только если значение всё ещё равно старому, иначе возвращает `Err` с актуальным, и ты пробуешь снова. Готовая
упаковка этого цикла: `fetch_update(успех, неудача, |v| Some(новое) или None)`.

### Ordering

Второй аргумент атомиков говорит, какие гарантии видимости даёт операция остальной памяти.

```
Relaxed   только сама операция неделима; никакого порядка относительно других записей
Release   запись: всё, что этот поток записал ДО неё, станет видно тем, кто прочитал её с Acquire
Acquire   чтение: увидев значение, записанное с Release, увидишь и всё, что ему предшествовало
AcqRel    и то и другое для операции «прочитать и записать» (fetch_add, compare_exchange)
SeqCst    всё то же и ещё единый общий порядок всех SeqCst-операций
```

Пара работает на ОДНОЙ переменной. Типичная публикация данных:

```
поток-писатель                       поток-читатель
data.store(42, Relaxed);             if ready.load(Acquire) {
ready.store(true, Release);   ───▶       data.load(Relaxed)   // гарантированно 42
                                     }
```

Если флаг на `Relaxed`, читатель может увидеть `ready == true`, но старое `data`. На x86 так бывает редко, на ARM
(телефоны, Apple Silicon) бывает сразу. Для обычных счётчиков, которые ни с чем не связаны, достаточно `Relaxed`.
Для `compare_exchange` ordering неудачи не может быть `Release` или `AcqRel` (при неудаче нечего выпускать),
компилятор такой код не пропустит. `SeqCst` нужен редко: когда несколько флагов должны быть согласованы между
всеми потоками. Начинай с пары Release/Acquire для публикации и Relaxed для счётчиков.

## Пул потоков

Порождать поток на каждое задание дорого, а десять тысяч одновременных потоков съедят память. Пул держит
фиксированное число рабочих, и все берут задания из общей очереди.

```
 execute(job) ──▶ ┌── очередь заданий (под Mutex) ──┐
                  │  job  job  job  job             │ ◀── Condvar «есть работа»
                  └─────────────────────────────────┘
                     ▲        ▲        ▲
                  рабочий  рабочий  рабочий     каждый: ждёт, берёт, выполняет БЕЗ замка
```

Что нужно продумать.

1. Состояние: очередь, число выполняющихся заданий, флаг «закрыто». Всё под одним `Mutex`, два `Condvar`: один
   для рабочих («появилась работа или закрыто»), второй для тех, кто ждёт опустевшей очереди.
2. Задание выполняется вне замка. Иначе пул станет однопоточным, а то и застрянет, если задание само пойдёт
   в пул.
3. Паника задания не должна убить рабочего: иначе после нескольких паник рабочих не останется, а очередь
   зависнет. Задание запускают под `std::panic::catch_unwind(AssertUnwindSafe(job))`, он возвращает `Err`, если
   внутри была паника, и поток остаётся жив.
4. Результат задания приходит по каналу (`mpsc`): `tx.send(job())` внутри задания. Упавшее задание не успеет
   отправить, `tx` умрёт, и `recv` вернёт `Err`: так «паника» становится обычной ошибкой для ждущего.
5. Остановка в `Drop`: закрыть очередь (рабочие доделают принятое и выйдут сами), затем `join` каждого потока.
   Если закрыть очередь забыть, рабочие ждут новую работу, `join` ждёт рабочих, и программа не завершится
   никогда. Если очередь держится на `mpsc`, закрыть значит уронить `Sender`, а он лежит в структуре, поэтому его
   хранят в `Option` и делают `take()`.

## Как проверять многопоточный код

Ошибки гонок не видны в обычном тесте: на одном потоке всё верно, а ломается под нагрузкой и не каждый раз.
Поэтому в тестах этой главы потоков много, повторов много, а ожидания всегда с таймаутом: зависание должно
стать ошибкой теста, а не повиснуть. Чтобы вынудить потоки встретиться в нужный момент, тесты используют
`Barrier` (все потоки ждут друг друга у барьера и стартуют вместе) и «точку встречи» с таймаутом (каждый
поток увеличивает счётчик и ждёт, пока его увидят все: если задания идут не одновременно, встречи не будет).

## Типичные ошибки

- Забытый оригинальный `Sender`: цикл по получателю не кончается.
- `join` в том же цикле, где запускаешь потоки: вся «параллельность» превращается в очередь.
- Охранник замка в условии `match`/`if let`/`while let`: замок держится дольше, чем кажется, и появляется самоблокировка.
- Два замка в разном порядке; один замок два раза в одном потоке.
- Проверка под одним захватом, действие под другим.
- `if` вместо `while` вокруг `Condvar::wait`; уведомление, которое никто не запомнил.
- Прочитать атомик, посчитать и записать назад вместо одной операции `fetch_*`.
- `Relaxed` для флага, за которым читают данные, и `SeqCst` «на всякий случай» там, где хватало пары Release/Acquire.
- Выполнение задания в пуле под замком очереди.
