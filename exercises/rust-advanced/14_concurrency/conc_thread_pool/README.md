# Проект: свой пул потоков

Рассылка уведомлений о новом посте не должна задерживать автора: пост сохранён, ответ получен, а сотни
уведомлений уходят в фоне. Порождать поток на каждое уведомление дорого и опасно (десять тысяч подписчиков
дают десять тысяч потоков), поэтому нужен пул: фиксированное число рабочих, общая очередь заданий,
результаты через канал, аккуратная остановка. Ты пишешь такой пул на `std`, без внешних крейтов.
Этот крейт потом станет основой фоновой рассылки сети.

## Что нужно сделать

В `crates/worker-pool/src/lib.rs` объявлены типы и сигнатуры, тела пустые. Поля структур добавь сам.

1. `ThreadPool::new(workers)` запускает `workers` потоков (если передан ноль, запусти один) и возвращает
   пул. `workers()` возвращает их число. Рабочие спят, пока заданий нет, и не жгут процессор.
2. `execute(job)` кладёт задание в общую очередь и будит рабочего. Если пул закрыт, возвращает `Err(PoolClosed)`.
3. `submit(job)` то же, но задание возвращает значение: результат приходит через канал, а в руки вызывающему
   попадает `JobHandle<T>`. `handle.join()` ждёт результата. Если задание запаниковало, это
   `Err(JobError::Panicked)`.
4. Паника в задании не должна убивать рабочего: следующие задания пул выполняет теми же потоками, и все
   `workers` потоков остаются живы.
5. `wait_idle()` блокирует вызывающего, пока очередь не опустеет и ни одно задание не выполняется. Ожидание
   построено на `Condvar` (`sleep` и `yield_now` в крейте не нужны).
6. `pending()` возвращает число заданий в очереди, которые ещё не начали выполняться.
7. `close()` запрещает новые задания, но уже принятые будут выполнены.
8. `Drop` у пула закрывает очередь, ждёт, пока рабочие закончат всё принятое, и присоединяет потоки. Роняя
   пул, нельзя ни потерять принятые задания, ни зависнуть.

## Как проверить

```
cargo test --workspace
```

Приёмочные тесты лежат в `crates/worker-pool/tests/acceptance.rs`, их менять нельзя. Все ожидания в них
идут с таймаутами, поэтому зависший пул покажет ошибку, а не повиснет.
