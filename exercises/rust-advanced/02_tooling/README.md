# Скрипты и окружение разработчика

В новый проект приходит человек и спрашивает: «Как это запускать?» Ему отвечают в чате: поставь вот этот
компилятор, форматируй вот с такой шириной, перед коммитом гони clippy с флагом `-D warnings`, сервисы
поднимай в трёх терминалах, переменные возьми из старого `.env` у Пети. Через месяц ответы в чате
расходятся с тем, что делает CI, и «у меня работает» становится постоянной шуткой.

Лечится это тем, что все повседневные команды живут в репозитории и запускаются одной короткой
строкой. Есть три способа (Makefile, cargo-make, xtask на Rust), и у каждого своя аудитория. Для них пишут
маленькие программы (аргументы командной строки, файлы и пути, запуск других программ), а версию
компилятора и правила стиля закрепляют в файлах, чтобы у всех был один и тот же результат.

Анимация к главе (клавиша `v`): порядок выполнения целей в make и cargo make, ловушка `.PHONY` и разница
между последовательным и параллельным запуском.

## Makefile

`make` старше большинства языков, на которых его используют, и есть почти везде. Файл `Makefile` это набор
правил: цель, её зависимости и команды (рецепт), которые приводят цель в готовое состояние.

```make
site: docs/index.md
	mdbook build docs

docs/index.md: README.md
	cp README.md docs/index.md
```

Читается так: «чтобы получить `site`, нужен `docs/index.md`; если он старее зависимостей, выполни
рецепт». Первоначально make придумали для сборки файлов, и до сих пор его главная идея именно такая:
сравнивать времена изменения файлов и пересобирать только устаревшее.

Две вещи, на которых спотыкаются все.

**Рецепт начинается с табуляции.** Не с пробелов, пусть даже восьми. Редактор, подменивший табуляцию
пробелами, даёт ошибку `missing separator`, и в самом сообщении про пробелы ни слова.

**Цель это имя файла.** Для нашей работы цели обычно не файлы, а команды (`test`, `lint`), и тогда нужно
сказать об этом make через `.PHONY`:

```make
.PHONY: test lint docs

test:
	cargo test

docs:
	cargo doc --no-deps
```

Без `.PHONY` достаточно появиться папке `docs/` (а она рано или поздно появится), чтобы
`make docs` ответил «up to date» и ничего не сделал. Эта ошибка тихая: ничто не падает, просто работа не делается.

Зависимости выполняются раньше цели и слева направо. Если написать `check: fmt lint test`, получится
порядок `fmt`, `lint`, `test`, а затем сама `check`. Зависимости зависимостей идут вглубь.

Посмотреть, что make сделает, не делая этого, можно флагом `-n`: он печатает рецепты вместо запуска.
Это самый дешёвый способ проверить Makefile.

### Переменные

```make
PORT ?= 8080
MODE = dev

serve:
	python3 -m http.server $(PORT)
```

Различие операторов важнее, чем кажется. Обычное `=` присваивает всегда. `?=` присваивает, только если
переменная ещё не определена. Откуда значение приходит, определяет приоритет:

```
make serve PORT=9000       аргумент командной строки: сильнее всего
PORT=9000 make serve       переменная окружения: сильнее обычного =, но слабее аргумента
PORT = 8080                присваивание в файле
PORT ?= 8080               присваивание в файле, уступающее окружению
```

Поэтому значения по умолчанию, которые пользователь может переопределить из окружения, пишут через `?=`.
Условные куски собирают функциями: `$(if $(filter prod,$(MODE)),--release,)` вставит `--release`,
только если `MODE=prod`. Эти функции работают даже в старом make 3.81 с macOS.

## cargo-make

У `make` есть слабые места. Он плохо работает с `.env`, у него неудобный синтаксис для условий, он не умеет
нормально запускать параллельно несколько задач и ничего не знает про воркспейсы Rust. `cargo-make` решает
это: задачи описываются в `Makefile.toml`, запускаются командой `cargo make имя`. Ставится он один раз:
`cargo install cargo-make`. Задачи главы с `cargo make` (tool_cargo_make, tool_cargo_make_fix,
tool_run_all, tool_dev_env) приёмка запускает по-настоящему, так что поставь его до начала. Без него
увидишь `no such command: make`, и это не ошибка в твоём `Makefile.toml`.

```toml
env_files = [{ path = ".env", defaults_only = true }]

[config]
default_to_workspace = false

[tasks.fmt]
command = "cargo"
args = ["fmt", "--all", "--check"]

[tasks.verify]
dependencies = ["fmt", "lint", "test"]
```

Задача это таблица `[tasks.имя]`. Поле `command` с `args` запускает программу, `script` выполняет
оболочку, `dependencies` перечисляет задачи, которые нужно выполнить раньше (по очереди). Переменные
окружения задаются таблицей `[env]` и файлами `env_files`.

Про `env_files` помни одно: по умолчанию значения из файла перекрывают окружение оболочки. Если
написать `defaults_only = true`, файл только дополняет то, что не задано. Для `.env` обычно нужно именно
так: разработчик должен иметь возможность написать `LOG_LEVEL=debug cargo make run`. Сама таблица `[env]`
в Makefile.toml сильнее и файла, и оболочки.

### Две ловушки cargo-make в воркспейсе

Первая: `default_to_workspace` по умолчанию включён. В корне воркспейса cargo-make тогда не выполнит
задачу, а обойдёт каждого члена и выполнит её там. Для задач вроде `cargo test --workspace` это лишняя
работа в N раз. Отключается в таблице `[config]`.

Вторая: у cargo-make есть встроенные задачи с привычными именами (`test`, `check`, `build`, `format`, `clean`).
Если объявить свою с тем же именем, поля сливаются. Твои `dependencies` добавятся, а встроенная
команда останется, и после твоих шагов выполнится ещё и чужой `cargo check`. Чтобы этого не было,
пиши в задаче `clear = true`. Найти эту проблему можно только прочитав, какие команды реально запускались:
cargo-make печатает их строками `Execute Command`.

### Параллельный запуск

Список `dependencies` выполняется последовательно. Чтобы запустить несколько задач одновременно,
используют `run_task`:

```toml
[tasks.start-all]
dependencies = ["build-all"]
run_task = { name = ["web", "worker", "queue"], parallel = true }
```

Сборку при этом выносят отдельной зависимостью: она выполнится один раз до запуска, а не по разу в каждой
параллельной задаче, которые иначе дрались бы за блокировку папки `target`.

## Аргументы командной строки руками

Позже мы встретим готовые парсеры, но маленькой утилите хватает стандартной библиотеки. Аргументы
это итератор строк: `std::env::args()`, первым идёт имя программы.

```rust
fn parse(args: &[String]) -> Result<Mode, String> {
    let Some((name, rest)) = args.split_first() else {
        return Err("нужна команда".to_string());
    };
    match name.as_str() {
        "serve" => {
            let mut iter = rest.iter();
            let mut port = 8080;
            while let Some(flag) = iter.next() {
                match flag.as_str() {
                    "--port" => {
                        let value = iter.next().ok_or("--port без значения")?;
                        port = value.parse().map_err(|_| "порт не число")?;
                    }
                    other => return Err(format!("неизвестный флаг {other}")),
                }
            }
            Ok(Mode::Serve(port))
        }
        other => Err(format!("неизвестная команда {other}")),
    }
}
```

Разбор лучше выносить в функцию от среза строк, а не читать `env::args()` прямо в ней: так её можно
проверить тестом. Ошибки возвращай значением и называй виноватый аргумент. Паниковать на чужом вводе
нельзя, а сообщение для человека формируется выше, там, где известен контекст.

## Файлы и пути

```rust
use std::path::{Component, Path, PathBuf};

let root = Path::new("/home/dev/site");
let page = root.join("posts").join("one.md");      // /home/dev/site/posts/one.md
for dir in page.ancestors() {                      // сам путь, его папка, и так до корня
    println!("{}", dir.display());
}
```

`Path` это не строка, а путь: у него есть компоненты, родитель, имя файла. Типы `Path` и `PathBuf` относятся
друг к другу как `str` и `String`. Скрипты разработчика обычно делают три вещи. Ищут корень проекта,
поднимаясь вверх от текущей папки или от `CARGO_MANIFEST_DIR`. Перечисляют содержимое папки через
`std::fs::read_dir` (порядок не гарантирован, сортируй сам) и создают папки через `create_dir_all`, которая
не жалуется, если папка уже есть.

Главная ловушка: `join` с абсолютным путём **заменяет** базу.

```rust
Path::new("/srv/app").join("/etc/passwd")   // это /etc/passwd, а не /srv/app/etc/passwd
```

Поэтому путь от пользователя нельзя просто склеивать с базовой папкой. Перед склейкой его разбирают
по компонентам и отвергают `RootDir`, `Prefix` и `ParentDir` (`..`). Искать подстроку «..» в тексте
ненадёжно, компоненты надёжнее.

## Запуск других программ

```rust
use std::process::Command;

let output = Command::new("git").args(["status", "--short"]).current_dir("repo").output()?;
```

У запуска два разных вида неудачи, и их нужно различать.

1. Программу не удалось запустить (её нет в PATH, нет прав). Тогда `output()` возвращает `Err`.
2. Программа запустилась, но завершилась с ошибкой. Тогда `output()` возвращает `Ok(Output)`, а ошибка
   спрятана в `output.status`.

Кто пишет `if cmd.output().is_ok() { "всё хорошо" }`, считает упавшую команду успешной. Правильная
проверка: `output.status.success()`; код возврата даёт `status.code()` (для процесса, убитого сигналом, это
`None`). Вывод читают через `String::from_utf8_lossy`, потому что программа может напечатать не UTF-8.
Ошибку упавшей команды объясняет её `output.stderr`: его стоит нести в сообщение, обрезав пробелы и
перевод строки по краям, как и stdout.
Если вывод запущенной программы нужен человеку «как есть», вместо `output()` используют `status()`:
дочерний процесс пишет прямо в твой терминал.

Цепочка шагов должна останавливаться на первой ошибке. Оператор `?` делает это одним символом, а
сообщение с именем шага и кодом возврата экономит полчаса чтения логов.

## xtask: скрипты на Rust

Makefile и cargo-make это внешние инструменты. У идеи xtask другая логика: скрипты разработчика
это обычный крейт воркспейса (`tools/xtask`), который пишется на Rust, собирается тем же cargo и
тестируется. Запускают его через **алиас** cargo в `.cargo/config.toml`:

```toml
[alias]
xtask = "run --quiet --package xtask --"
```

После этого `cargo xtask check` раскрывается в `cargo run --quiet --package xtask -- check`. Сам алиас
не волшебство: без записи в конфиге cargo ответит `no such command: xtask`. Программа xtask узнаёт корень
воркспейса от `CARGO_MANIFEST_DIR` (это папка самого xtask) и запускает остальные команды через тот
`cargo`, который её запустил: путь к нему лежит в переменной `CARGO`.

Плюсы xtask в портативности (не нужны ни make, ни cargo-make, работает там, где есть Rust) и в том, что
сложные скрипты проверяются тестами. Минус в том, что простые вещи (`make fmt`) короче в Makefile. Поэтому в
живых проектах часто сочетают: make как короткая дверь, cargo-make для параллельного запуска и `.env`, xtask
для того, что требует логики.

## Закреплённый компилятор и общие правила

Три файла в корне превращают договорённости в код.

```toml
# rust-toolchain.toml
[toolchain]
channel = "1.88.0"
components = ["rustfmt", "clippy"]
profile = "minimal"
```

`rustup` читает этот файл в текущей и родительских папках. Если указанного компилятора нет, он его
скачает. Точная версия (`1.88.0`, а не `stable`) убирает класс проблем «у меня другой clippy».

```toml
# rustfmt.toml                       # clippy.toml
max_width = 100                      disallowed-methods = [
use_field_init_shorthand = true          { path = "std::process::exit", reason = "верни ExitCode" },
                                     ]
                                     too-many-arguments-threshold = 5
```

Порог в `too-many-arguments-threshold` это максимально допустимое число: с пятёркой функции с пятью
аргументами проходят, а ругаться clippy начнёт на шестом.

`rustfmt.toml` настраивает форматирование, `clippy.toml` настраивает отдельные линты. Для `cargo fmt` режим
проверки это `--check`: он печатает отличия, завершается с ошибкой и ничего не меняет. Для CI нужен именно он.

И последнее: цель `check`, которой пользуется CI, запускают с `--locked`. Этот флаг запрещает cargo менять
`Cargo.lock`. Если файл устарел, сборка падает, а не переписывает его молча, и ошибка заметна сразу.

## Типичные ошибки

- В рецепте make пробелы вместо табуляции.
- Нет `.PHONY`, и цель молча не работает из-за одноимённой папки.
- `SERVICE = api` там, где нужно `?=`: переменную окружения такая запись перебивает.
- В воркспейсе забыли `default_to_workspace = false`, и задача выполняется в каждом крейте.
- Назвали свою задачу именем встроенной и получили чужую команду в придачу.
- `.env` перебивает оболочку, потому что нет `defaults_only = true`.
- `Path::join` с пользовательским путём без проверки: абсолютный путь выбрасывает базу.
- `command.output().is_ok()` вместо проверки статуса завершения.
- Цепочка шагов, которая идёт дальше после падения.
- `stable` в `rust-toolchain.toml`: версия плывёт, и закрепление ничего не закрепляет.
