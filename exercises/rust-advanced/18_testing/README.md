# Тестирование

В интернет-магазине ночью упал тест. Утром его перезапустили, он позеленел, и все решили, что это «флак». Через
неделю такой же флак упал на проверке перед релизом, и релиз ушёл на день позже. Разбор показал, что тест
считал сегодняшнюю дату, а CI в тот момент перевалил за полночь. Это один из трёх способов, которыми тесты
портятся: они бывают красными всегда, красными иногда и (самый вредный вариант) зелёными, хотя ничего не
проверяют. Основы (`#[test]`, `assert_eq!`, простой `should_panic`) ты уже знаешь. Здесь речь о том, как
устроить тесты так, чтобы им можно было верить: где они живут, что видят, чем заменяют базу и часы и как не
мешают друг другу.

Асинхронные тесты и `tokio::test` разбираются в разделе tokio. Строители данных, golden-файлы и конфиг из
окружения придут в разделе services. Здесь всё на обычном `std`.

## Три места, где живут тесты

```
 крейт cart
 ├── src/lib.rs          код + #[cfg(test)] mod tests   юнит-тесты: видят всё, даже приватное
 ├── src/pricing.rs      код + #[cfg(test)] mod tests   (каждый модуль может иметь свои)
 ├── tests/              каждый .rs файл = отдельный крейт; видят только pub
 │   ├── checkout.rs
 │   └── common/mod.rs   общие помощники (это не тест!)
 └── /// ```             примеры в документации: тоже отдельные программы, видят только pub
```

**Юнит-тесты** лежат в том же файле, что и код, в модуле `tests`. Они дети модуля, а ребёнок видит приватное
родителя, поэтому здесь проверяют внутренние функции:

```rust
fn round_to_five(cents: u64) -> u64 {
    (cents + 2) / 5 * 5
}

pub fn shipping(cents: u64) -> u64 {
    round_to_five(cents / 10)
}

#[cfg(test)]
mod tests {
    use super::*;   // достаём всё из родителя, в том числе приватное

    #[test]
    fn rounding_goes_to_nearest_five() {
        assert_eq!(round_to_five(7), 5);
        assert_eq!(round_to_five(8), 10);
    }
}
```

Атрибут `#[cfg(test)]` выкидывает модуль из обычной сборки целиком: тестовый код не попадает в бинарник и не
замедляет компиляцию релиза. Всё, что нужно только тестам (помощники, примеры данных, фейки), кладут внутрь
этого модуля, иначе обычная сборка скажет «функция нигде не используется». Не делай функцию публичной ради
того, чтобы до неё дотянулся тест: проверь её изнутри. Публичное зафиксировано обещанием, и менять его
потом нельзя.

**Интеграционные тесты** лежат в папке `tests/` рядом с `src/`. Каждый `.rs` файл в ней cargo собирает как
отдельный крейт, который подключает твою библиотеку так же, как любой внешний потребитель:

```rust
use cart::{Cart, Coupon};

#[test]
fn coupon_applies_to_whole_cart() {
    let mut cart = Cart::new();
    cart.add("чай", 300, 2);
    cart.apply(Coupon::percent(10));
    assert_eq!(cart.total(), 540);
}
```

Приватное им недоступно, и это хорошо: так они проверяют то, что обещано пользователю. Если ты поменяешь
внутренности и интеграционные тесты не заметят, значит, ты не сломал обещание.

Общий код для таких файлов делает ловушку. Файл `tests/common.rs` cargo тоже примет за тестовый крейт, и в
выводе появится строка `running 0 tests`. Правильное место для общих помощников: `tests/common/mod.rs`. Папки
в `tests/` cargo сам не собирает, а файлы подключаются так:

```rust
mod common;                      // ищет tests/common/mod.rs

#[test]
fn full_cart_has_three_lines() {
    let cart = common::cart_with(3);     // helper должен быть pub
    assert_eq!(cart.len(), 3);
}
```

У помощников два подводных камня. Они должны быть `pub`, иначе файл рядом их не увидит. И каждый тестовый
файл компилирует `common` у себя как часть своего крейта, поэтому функция, которой этот файл не пользуется,
вызывает предупреждение `dead_code`. Лечится строкой `#![allow(dead_code)]` в самом начале `common/mod.rs`:
так компилятору объясняют, что помощники общие, а не мёртвые.

Несколько режимов запуска пригодятся каждый день:

```
cargo test                       все тесты: юнит, интеграционные, документационные
cargo test coupon                только те, в имени которых есть "coupon" (фильтр)
cargo test --test checkout       только файл tests/checkout.rs
cargo test --lib                 только юнит-тесты библиотеки
cargo test --doc                 только примеры из документации
cargo test -- --nocapture        показать println! из тестов (иначе у прошедших вывод прячется)
cargo test -- --test-threads=1   по одному тесту за раз
cargo test -- --ignored          запустить помеченные #[ignore]
```

Всё после `--` относится не к cargo, а к самому тестовому бинарнику. Долгий тест помечают
`#[ignore = "причина"]`: он не мешает обычному прогону, а ночью его запускают отдельно.

**Документационные тесты** это блоки кода в комментариях `///`. Rustdoc вынимает каждый блок, компилирует
как отдельную программу и запускает. Пример в документации поэтому либо работает, либо ломает `cargo test`:

````rust
/// Скидка в процентах от суммы, округление вниз.
///
/// ```
/// use cart::discount;
///
/// assert_eq!(discount(1000, 15), 150);
/// assert_eq!(discount(999, 10), 99);
/// ```
pub fn discount(cents: u64, percent: u64) -> u64 {
    cents * percent / 100
}
````

Пример подключает крейт по имени, как внешний пользователь, и видит только публичное. Остальное в
блоках настраивается пометками и скрытыми строками:

- Строка, начинающаяся с `# `, компилируется, но в документации не показывается. Так прячут обвязку:
  `# use cart::Cart;`, `# fn main() {`.
- Для `?` в примере нужен `main`, возвращающий `Result`. Его делают скрытым: `# fn main() -> Result<(),
  CartError> {` в начале и `# Ok(()) }` в конце.
- ```` ```no_run ```` значит «собрать, но не запускать» (сервер, который не возвращается; запись в сеть).
- ```` ```compile_fail ```` значит «это обязано не собираться». Так фиксируют, что неверное использование API
  запрещено типами. Если код вдруг соберётся, тест упадёт.
- ```` ```should_panic ```` значит «должно запаниковать при запуске».
- ```` ```ignore ```` значит «не проверять вообще». Такой пример устареет и никто не заметит, поэтому
  держи его как последнее средство.

Любой пример без `assert_eq!` доказывает лишь, что код компилируется. Проверяй результат.

## Табличные тесты

Когда одно правило нужно проверить на десятке входов, вместо десяти почти одинаковых функций делают таблицу:

```rust
#[test]
fn shipping_by_zone() {
    let cases = [
        ("центр", 1_000, 0),
        ("область", 1_000, 150),
        ("область, большой заказ", 10_000, 0),
        ("другая страна", 1_000, 900),
    ];
    for (name, order, want) in cases {
        assert_eq!(shipping_for(name_to_zone(name), order), want, "случай «{name}»");
    }
}
```

Два правила делают таблицу полезной. У каждого случая есть имя, и сообщение при падении его называет:
иначе в отчёте будет «left: 150, right: 0» и придётся гадать, какая строка упала. И перебор не обрывается на
первой ошибке, если нужна полная картина: тогда ошибки собирают в вектор и падают один раз в конце.

А в таблицу кладут не «пять примеров, которые и так работают», а границы и ловушки: ноль, один, максимум,
максимум плюс один, пустую строку, пробелы по краям, юникод. Хороший способ проверить таблицу: мысленно
сломай код (замени `<` на `<=`) и посмотри, покраснеет ли хоть одна строка.

## Result, паника и вариант ошибки

Тест может возвращать `Result`. Тогда `?` внутри теста пробрасывает ошибку, а прогон показывает её целиком:

```rust
#[test]
fn parses_and_totals() -> Result<(), CartError> {
    let cart = Cart::parse("чай:300:2")?;      // упадёт с видимой ошибкой, а не с unwrap на Err
    assert_eq!(cart.total(), 600);
    Ok(())
}
```

Проверку «ошибка именно такая» пишут через `matches!`, а не через `is_err()`: последний не отличает «пусто»
от «число слишком большое»:

```rust
assert!(matches!(Cart::parse(""), Err(CartError::Empty)));
assert!(matches!(Cart::parse("чай:x:1"), Err(CartError::BadPrice(ref raw)) if raw == "x"));
```

`#[should_panic]` без текста принимает любую панику, в том числе ту, которую ты не планировал (деление на
ноль, выход за границу массива). Всегда пиши `#[should_panic(expected = "часть сообщения")]`: тест краснеет,
если паника случилась по другой причине.

## Фейк и мок

Код, который ходит в базу, в почту или в сеть, неудобно проверять настоящим. Поэтому зависимость прячут за
трейтом, и в тесте подставляют замену. Замены бывают двух видов, и путать их не стоит.

**Фейк** это упрощённая, но рабочая реализация: хранилище в `HashMap` вместо базы. Он ведёт себя как
настоящее в том, что видит сервис (положил и достал то же самое, удалил и пропало, список в порядке id),
поэтому через него можно гонять сложные сценарии.

**Мок** запоминает, как им пользовались, чтобы проверить поведение сервиса: сколько писем отправили, кому, с
каким текстом, в каком порядке.

```rust
pub trait Sms {
    fn send(&self, phone: &str, text: &str);
}

// в тесте: подсовываем шпиона и после действия читаем, что ему досталось
let spy = SpySms::default();
let orders = Orders::new(&spy);
orders.confirm("+7 900 000 00 00");
assert_eq!(spy.sent(), vec![("+7 900 000 00 00".to_string(), "Заказ подтверждён".to_string())]);
```

Шпиону нужен журнал, который меняется через `&self` (трейт берёт `&self`), то есть внутренняя изменяемость:
`RefCell` в одном потоке, `Mutex` там, где мок могут отправить в другой. Метод `sent()` отдаёт копию журнала,
а не охранника замка, чтобы тест не держал замок.

Теперь классическая ловушка. Мок отдают сервису по значению, а `derive(Clone)` на моке копирует журнал вместе
со всем остальным:

```rust
let spy = SpySms::default();
let service = Orders::new(spy.clone());   // сервис получил КОПИЮ, у неё свой журнал
service.confirm("+7...");
assert_eq!(spy.sent().len(), 1);          // красный: в оригинале пусто
```

Чтобы клон и оригинал смотрели в один журнал, он должен быть общим: `Arc<Mutex<Vec<_>>>`. Клонируется только
указатель, а данные остаются одни. Заодно мок становится `Send + Sync` и годится для сервиса, который живёт в
другом потоке. Ещё один способ обойтись без клонов: трейт реализуют и для ссылок (`impl<T: Sms> Sms for &T`),
и сервису отдают `&spy`.

## Время и номера как входы

Функция, которая сама зовёт `SystemTime::now()` или генерирует случайный id, получает скрытый вход. Тест
не может ни ускорить срок (сессия живёт десять минут: ждать их?), ни воспроизвести ошибку, которая случается
в 23:59:59. Лечится одинаково: время приходит снаружи.

```rust
pub trait Clock {
    fn now(&self) -> u64;
}

pub struct SystemClock;      // в проде читает настоящие часы
// в тестах: свой тип с тем же трейтом, время в нём стоит на месте, пока тест не сдвинет его вручную
```

Сервис держит `C: Clock`, а проверка границы срока купона превращается в две строки без `sleep`: сдвинули часы
на одну секунду меньше срока, купон ещё действует, сдвинули ещё на секунду, он просрочен. То же с генератором номеров: подставной выдаёт `1, 2, 3`, и тест
знает, какой номер получит заказ. Ловушка этого приёма: переделку надо довести до конца. Если часы лежат в
структуре, но один метод по старой памяти зовёт `SystemTime::now()`, всё выглядит правильно, а тест красный
по ночам.

## Изоляция: тесты идут параллельно

`cargo test` запускает тесты одновременно, в разных потоках одного процесса. Всё общее становится источником
странных падений: файл с фиксированным именем, глобальный счётчик, переменная окружения, порт. Правила такие.

- Файлы и папки в тестах получают уникальное имя (номер процесса плюс счётчик) и лежат во временном каталоге.
- Уборка живёт в `Drop`. Она срабатывает при выходе из области и при панике (стек разматывается). Вызов
  `remove_dir_all` в конце теста при упавшем `assert!` не выполнится, и мусор останется.
- Глобальное состояние в тестах лучше не заводить. Если без него никак, тесты, которые его делят,
  сериализуют общим `Mutex`, а не флагом `--test-threads=1` для всех: флаг лечит симптом и замедляет всё.

Охранник на `Drop` выглядит так (пример про счётчик активных подключений, а не про файлы):

```rust
struct Connected<'a>(&'a AtomicUsize);

impl<'a> Connected<'a> {
    fn new(active: &'a AtomicUsize) -> Self {
        active.fetch_add(1, Ordering::SeqCst);
        Connected(active)
    }
}

impl Drop for Connected<'_> {
    fn drop(&mut self) {
        self.0.fetch_sub(1, Ordering::SeqCst);    // сработает и при return, и при панике
    }
}
```

Временная папка устроена так же: конструктор создаёт папку с уникальным именем (номер процесса, глобальный
счётчик, метка теста), а `Drop` удаляет её вместе с содержимым.

## Крейт test-support

Фейки, ручные часы, генераторы и временные папки нужны тестам многих крейтов воркспейса. Копировать их в
каждый крейт глупо, поэтому они живут в одном крейте `test-support`. Две вещи важны, чтобы они не попали в
релиз.

Во-первых, тестовый крейт подключают как **dev-dependency**: он нужен только для `cargo test`, а `cargo build`
его не видит. Если записать его в обычные `[dependencies]`, подставные часы поедут в рабочий бинарник вместе с
остальным. Проверить это можно командой, которая показывает граф: `cargo tree -p core -e normal` (обычные
зависимости) и `-e dev` (добавляемые тестами).

Во-вторых, сами фейки прячут за **feature**: `[features] test-util = []`, а в коде `#[cfg(feature =
"test-util")]`. Тогда даже при ошибке с зависимостью компилятор не соберёт их без явной просьбы, а тесты
просят в одном месте: `test-support = { path = "../test-support", features = ["test-util"] }`. Помни, что
features складываются по всему воркспейсу: если хоть один крейт включил `test-util` в обычных зависимостях,
оно включено для всех. Поэтому `default` у такой feature не ставят.

## Тест, который не проверяет

Самые вредные тесты зелёные. `is_err()` вместо варианта ошибки. `should_panic` без текста. Пример в
документации без `assert_eq!`. Таблица, в которой все случаи «обычные». Тест, в котором ожидаемое значение
вычислено тем же кодом, который проверяется. Простой приём проверки: сломай код нарочно (поменяй `<` на `<=`,
убери `trim`, начни номера с нуля) и посмотри, покраснеет ли хоть что-то. Если нет, тест ничего не
охраняет. В проектах этой главы такие поломки подсовывает приёмка, а тебе остаётся покрыть их тестами.

## Типичные ошибки

- Тест проверяет только «не упало». Добавь значение, которое должно получиться.
- Две проверки в одном тесте с общим именем «works»: при падении непонятно, какая. Давай тестам имена, из которых
  видно правило: `cooldown_counts_from_the_last_post`.
- `tests/common.rs` вместо `tests/common/mod.rs`.
- `sleep` в тесте ради ожидания: либо подставные часы, либо ожидание условия с таймаутом.
- Фиксированный путь к файлу или порт в тестах.
- Мок с `derive(Clone)` и своим журналом.
- Фейк хуже настоящего: например, `all()` отдаёт случайный порядок, а база всегда сортирует.
