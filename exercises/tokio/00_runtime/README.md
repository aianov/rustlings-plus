# Рантайм и первый async

Открываешь профиль в соцсети. Серверу нужно достать пользователя, его последние посты и число
подписчиков: три запроса к хранилищу, каждый ждёт ответа. Пока первый запрос в пути, процессор
ничем не занят, и было бы глупо стоять над ним. Хочется, чтобы поток в это время занялся
запросами других пользователей, а к нашему вернулся, когда ответ придёт.

Эту работу делает рантайм: он держит очередь дел, вызывает твой код, пока тот может
что-то делать, и откладывает его, пока тот ждёт. `async` и `.await` в Rust только сообщают
рантайму, где можно отложить. Сам рантайм (в нашем курсе это tokio) в язык не встроен, его
подключают как библиотеку. Дальше: что он делает, как его запускают и какое одно правило
нельзя нарушать.

Если ты прошёл главы про Future и Pin в rust-advanced, половина механики тебе знакома: Future,
`poll`, `Waker`. Там ты сам писал `block_on`. Теперь возьмём готовый.

## Future ленив

Вызов `async fn` не выполняет ни одной строчки её тела. Он возвращает значение, которое
*описывает* работу, это и есть Future.

```rust
async fn fetch_user(id: u32) -> String {
    println!("иду в хранилище за {id}");
    format!("user{id}")
}

#[tokio::main]
async fn main() {
    let fut = fetch_user(7);          // ничего не напечатано
    println!("Future создан");
    let user = fut.await;             // вот теперь "иду в хранилище"
    println!("{user}");
}
```

Напечатается "Future создан", потом "иду в хранилище за 7", потом "user7". Если убрать `.await`,
вторая строка не появится никогда: Future просто выбросят неиспользованным. Компилятор
предупредит (`unused_must_use`), но предупреждение не остановит сборку. Многие ошибки
в async-коде выглядят так: всё собралось, а ничего не произошло. Читай предупреждения.

Из ленивости следует порядок событий: он определяется тем, где ты делаешь `.await`, а не тем,
где вызвал функцию.

```rust
let a = step("a");   // ничего
let b = step("b");   // ничего
b.await;             // выполняется b
a.await;             // выполняется a
```

Это удобно: Future можно собрать заранее, положить в структуру или в Vec и запустить позже.

## Что происходит на `.await`

Компилятор превращает `async fn` в конечный автомат: структуру со списком состояний и всеми
локальными переменными, которые должны пережить паузу. Каждый `.await` это граница между
состояниями.

```rust
async fn profile(id: u32) -> String {
    let user = load_user(id).await;      // граница 1
    let posts = load_posts(id).await;    // граница 2
    format!("{user}: {posts}")
}
```

```
 poll #1   |-- код до 1-го .await --|  load_user ещё не готов -> Pending
           (поток свободен, рантайм берёт другие задачи)
 poll #2   |-- load_user готов, код до 2-го .await --|  load_posts не готов -> Pending
           (поток снова свободен)
 poll #3   |-- load_posts готов, format! --|  -> Ready(строка)
```

Рантайм вызывает `poll`, Future выполняет работу *до ближайшего места, где ему нужно ждать*, и
возвращает `Pending`. Когда ожидаемое событие случилось (пришёл ответ, истёк таймер), `Waker`
сообщает рантайму: «эту задачу пора опросить снова». Между `poll` всё время принадлежит другим
задачам. Посмотри визуализацию `await_steps` (клавиша `v` в CLI курса): там видно, как шаги
двух функций перемешиваются на одном потоке.

Из этого следует важная вещь: **код между двумя `.await` выполняется без перерыва**. Пока он
работает, ни одна другая задача на этом потоке не сдвинется с места. Это пригодится ниже.

## Кто вызывает poll

Сам Future ничего не запускает. Нужен кто-то, кто держит очередь и вызывает `poll`. Это
`Runtime`. Точка входа в async-мир из обычного кода называется `block_on`: она занимает текущий
поток, крутит Future, пока он не завершится, и возвращает результат.

```rust
use tokio::runtime::Runtime;

fn main() {
    let rt = Runtime::new().unwrap();
    let answer = rt.block_on(async { 6 * 7 });
    println!("{answer}");
}
```

Макрос `#[tokio::main]` делает ровно это:

```rust
#[tokio::main]
async fn main() {
    run().await;
}
// превращается в
fn main() {
    tokio::runtime::Runtime::new()
        .unwrap()
        .block_on(async { run().await; })
}
```

`async fn main` не может быть настоящей точкой входа, потому что операционная система вызывает
обычную функцию. `#[tokio::test]` устроен так же: каждый тест получает свой рантайм, который
живёт, пока идёт тест. Поэтому тесты не мешают друг другу.

Когда макрос мешает (нужен нестандартный Builder, нужен рантайм внутри библиотеки или запуск
из чужого потока), всё то же самое пишется руками.

## Async-блоки

`async { ... }` создаёт Future без отдельной функции. Он такой же ленивый:

```rust
let job = async {
    tokio::time::sleep(Duration::from_millis(10)).await;
    42
};
// пока ничего не произошло
let n = job.await;
```

Блок, как замыкание, захватывает окружение по ссылке. А Future часто живёт дольше функции, в
которой он создан (его вернули, положили в Vec, отдали в `spawn`), и тогда ссылка повиснет.
Лечится так же, как с замыканиями: `async move` переносит владение внутрь.

```rust
fn banner_width(title: &str) -> impl Future<Output = usize> {
    let title = title.to_string();
    async move { title.chars().count() }   // без move: блок держал бы ссылку на локальную title
}
```

Если в блоке есть `?`, у блока должен быть выводимый тип ошибки. В обычной функции его задаёт
сигнатура, а у блока сигнатуры нет, и `?` умеет преобразовывать ошибки через `From`, так что по
одному `Ok(x)` тип не угадать. Тогда подсказываем:

```rust
let job = async {
    let total: i64 = line.trim().parse()?;
    Ok::<_, Box<dyn std::error::Error>>(total * 2)   // здесь указан тип ошибки блока
};
```

## spawn в двух словах

Иногда работу нужно не ждать на месте, а отдать рантайму и заниматься своим. Для этого есть
`tokio::spawn`: он кладёт Future в очередь рантайма и сразу возвращает `JoinHandle<T>`.

```rust
let handle = tokio::spawn(async { 2 + 2 });   // задача уже в очереди и скоро побежит
// ... можно делать другое ...
let four = handle.await.unwrap();             // JoinHandle это Future, его результат Result<T, JoinError>
```

Три факта пригодятся уже в этой главе. Задача стартует сразу после `spawn`, а не когда ты
сделаешь `.await` на хэндл. Хэндл нужен, чтобы дождаться результата: `.await` даёт
`Result<T, JoinError>`, где ошибка означает, что задача упала с паникой или её отменили.
Если хэндл выбросить, задача всё равно доработает. Подробно задачи разбираются в следующей
главе, пока этого достаточно.

## Два вида рантайма

Рантайм собирает `Builder`. Видов два, и разница принципиальная.

```
current_thread                          multi_thread (по умолчанию в Runtime::new)

  один поток                              N потоков-воркеров
  +-----------------+                     +----------+ +----------+ +----------+
  | очередь задач   |                     | воркер 1 | | воркер 2 | | воркер 3 |
  | A B C D         |                     | A  E     | | B  F     | | C  D     |
  +-----------------+                     +----------+ +----------+ +----------+
  задачи крутятся ТОЛЬКО                  воркеры берут задачи из общей очереди
  пока кто-то внутри block_on             и воровать друг у друга (work stealing)
```

```rust
use tokio::runtime::Builder;

let one = Builder::new_current_thread().enable_all().build().unwrap();

let many = Builder::new_multi_thread()
    .worker_threads(4)
    .thread_name("my-worker")
    .enable_all()
    .build()
    .unwrap();
```

Методы настройки берут `&mut self` и возвращают `&mut Builder`, чтобы их можно было
цеплять. Поэтому результат `Builder::new_multi_thread().worker_threads(4)` это ссылка на
временное значение, и если Builder нужно настраивать по условию, его кладут в `let mut`
и вызывают методы отдельными операторами, а `.build()` в конце.

`current_thread` не создаёт ни одного потока. Задачи выполняются на том потоке, который вызвал
`block_on`, и только пока он там. Когда `block_on` вернулся, не успевшие задачи выбрасываются. Поэтому он предсказуем: гонок между потоками нет, порядок
повторяется от запуска к запуску. Потому `#[tokio::test]` по умолчанию собирает именно его.
`multi_thread` использует все ядра, задачи могут оказаться на любом воркере. Это рабочий режим
сервисов. Макросы выбирают вид через атрибут: `#[tokio::main(flavor = "current_thread")]`,
`#[tokio::test(flavor = "multi_thread", worker_threads = 2)]`.

### Драйверы

Внутри рантайма живут два драйвера. Таймерный отвечает за `sleep`, `timeout`, `interval`.
Ввода-вывода слушает сокеты и говорит рантайму, что можно читать или писать. Они включаются в
Builder отдельно: `enable_time()`, `enable_io()`, или оба сразу, `enable_all()`. `Runtime::new()`
и макросы включают всё. Но `Builder::new_current_thread().build()` без `enable_*` соберёт рантайм
без драйверов, и паника случится только при первом `sleep` или `bind`:

```
A Tokio 1.x context was found, but timers are disabled. Call `enable_time` on the runtime builder to enable timers.
A Tokio 1.x context was found, but IO is disabled. Call `enable_io` on the runtime builder to enable IO.
```

Сообщение сразу говорит, что делать. В продакшне почти всегда `enable_all()`.

## Главное правило: не блокируй воркер

Помнишь, что код между двумя `.await` выполняется без перерыва? Если там окажется что-то
долгое, поток встанет, а вместе с ним все задачи, которые на нём должны были бы работать.

```
 один поток (current_thread):

 без блокировки:
   A: ##...##...##...      A и B чередуются, потому что оба
   B: ..##...##...##       отдают поток на .await

 с std::thread::sleep в A:
   A: ##############...    поток спит целиком
   B: (стоит, ждёт)        B не может даже начать
```

Посмотри `blocking_worker`: на анимации видно, как одна блокирующая задача останавливает
очередь. На `multi_thread` картина мягче (блокируется один воркер из N), но суть та же: чем
больше блокирующих задач, тем меньше воркеров остаётся для остальных, и сервис «внезапно
тормозит под нагрузкой», хотя процессор почти не занят.

Что блокирует:

- `std::thread::sleep` (заменяется на `tokio::time::sleep(..).await`);
- `std::sync::mpsc::Receiver::recv` и любые блокирующие ожидания чего-то, что должно прийти
  от другой задачи (заменяются каналами tokio, см. ниже);
- `std::fs`, блокирующие сетевые клиенты и драйверы БД;
- тяжёлые вычисления: хеширование пароля, сжатие, разбор огромного JSON.

Правило большого пальца: если между двумя `.await` проходит больше десятка миллисекунд, это
уже проблема. Чем заменять: ожидание нужно делать через `.await` на tokio-примитиве, а
неизбежно блокирующую работу уносить с воркеров через `tokio::task::spawn_blocking`. Про него
будет глава про задачи, пока запомни, что он существует.

Канал tokio выглядит почти как канал std, но ждётся через `.await`:

```rust
let (tx, mut rx) = tokio::sync::mpsc::unbounded_channel();   // приёмнику нужен mut
tx.send(1).unwrap();                                          // у unbounded send не async
while let Some(n) = rx.recv().await { /* None, когда все отправители ушли */ }
```

Самые коварные блокировки спрятаны. `sleep` в коде видно сразу, а вот `rx.recv()` из `std`
выглядит безобидно. На `multi_thread` баг может годами не проявляться, пока блокировка не
встретится на единственном свободном воркере. Тестируй на `current_thread`: он ловит такое сразу
(в этой главе так и сделано).

## Замороженное время в тестах

Тест, который ждёт `sleep(Duration::from_secs(3600))`, не должен идти час. Для этого есть
`#[tokio::test(start_paused = true)]` (нужна feature `test-util`, в нашем курсе она включена).
Время рантайма в таком тесте стоит на месте, а когда все задачи упираются в таймеры, рантайм сам
переводит часы к ближайшему из них. Час ожидания проходит мгновенно, а замер через
`tokio::time::Instant` показывает честные виртуальные часы:

```rust
#[tokio::test(start_paused = true)]
async fn waits_an_hour_in_no_time() {
    let started = tokio::time::Instant::now();
    tokio::time::sleep(Duration::from_secs(3600)).await;
    assert_eq!(started.elapsed(), Duration::from_secs(3600));   // виртуальный час, реально миллисекунды
}
```

Такой тест ещё и проверяет параллельность: две задачи по 5 мс, идущие одновременно, займут
5 мс виртуального времени, а идущие по очереди 10. Подробности в главе про время.

## Контекст рантайма и границы

Функции tokio вроде `tokio::spawn` и `tokio::time::sleep` не получают рантайм аргументом. Они берут
«текущий» из контекста потока: рантайм записывает себя туда, когда выполняет твой код. Отсюда три
паники, которые ты обязательно встретишь:

```
there is no reactor running, must be called from the context of a Tokio 1.x runtime
```
Ты вызвал `tokio::spawn`, `sleep` или создаёшь сокет в потоке, где нет контекста: в обычном
`std::thread`, в `main` до `block_on`, в синхронном колбэке. Лечится через `Handle`.

```
Cannot start a runtime from within a runtime. This happens because a function (like `block_on`) attempted to block the current thread...
```
Ты вызвал `block_on` из потока, который уже выполняет async-код. Лечится переделкой границы.

```
A Tokio 1.x context was found, but timers are disabled / IO is disabled
```
Контекст есть, но Builder не включил драйвер. Лечится `enable_time` / `enable_io`.

### Handle

`Handle` это дешёвый клон ссылки на рантайм. Его можно получить снаружи (`rt.handle()`) или
изнутри async-кода (`Handle::current()`) и отдать в любой поток.

```rust
let handle = rt.handle().clone();
std::thread::spawn(move || {
    handle.spawn(async { /* работает на рантайме */ });
    let n = handle.block_on(async { 1 + 1 });   // из обычного потока это можно
});

let _guard = rt.handle().enter();               // пока guard жив, поток "внутри" рантайма
let sleep = tokio::time::sleep(Duration::from_secs(1));
```

`Handle::block_on` из обычного потока допустим: это та же граница sync/async, пройденная в
другом месте. Но на `current_thread` есть оговорка: задачи, поставленные через `handle.spawn`, бегут только пока
кто-то выполняет `rt.block_on` на потоке, которому принадлежит рантайм. Если основной поток уже
успел выйти из `block_on`, а чужой поток вызвал `handle.block_on(..)`, его собственный Future
двигается, а spawn-нутые им задачи стоят. На multi_thread таких проблем нет.

### Граница sync и async проходится один раз

Самая частая причина «Cannot start a runtime from within a runtime»: кто-то глубоко в
программе вызвал синхронный помощник, а помощник решил сам запустить рантайм. Хорошая архитектура
такая: на самом верху один `block_on` (или `#[tokio::main]`), ниже всё async и вызывается через
`.await`. Если нужно позвать блокирующий код из async, его уносят в `spawn_blocking`, а если
нужно позвать async из обычного потока, берут `Handle`.

## Типичные ошибки

- Забыл `.await`: код собирается, ничего не происходит. Смотри `unused_must_use`.
- `std::thread::sleep` и другие блокирующие вызовы в async-функциях.
- Рантайм без `enable_time` / `enable_io`.
- `block_on` в async-коде, в том числе скрытый: синхронный помощник, который внутри запускает
  рантайм.
- `tokio::spawn` из обычного потока.
- Ожидание, что `join!` распараллелит: он выполняет ветки в одной задаче, и блокирующая ветка
  держит остальные.
- Ожидание, что spawn-нутая задача на `current_thread` сама побежит, пока main занят чем-то
  без `.await`: ей достанется поток только тогда, когда main его отдаст.
