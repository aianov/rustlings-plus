# Задачи tokio: spawn, JoinHandle, JoinSet

Админ просит импортировать в соцсеть десять тысяч пользователей из файла. Для каждого нужно
разобрать строку, посчитать хеш пароля и записать в хранилище. Если делать по одному, при
пяти миллисекундах на запись это почти минута, хотя процессор почти всё время простаивает:
он ждёт хранилище. Если запустить все десять тысяч сразу, упадёт хранилище (или кончатся
дескрипторы). Нужно что-то среднее: пусть работает сотня записей одновременно.

Единица такой работы в tokio называется **задачей** (task). Это глава про то, как задачи
рождаются (`spawn`), как за ними присматривают (`JoinHandle`, `JoinSet`), как их останавливают
(`abort`) и какие правила налагает на них компилятор (`'static`, `Send`).

## Что такое задача

Future сам по себе ничего не делает: его кто-то должен опрашивать. `tokio::spawn` отдаёт Future
рантайму, и тот опрашивает его независимо от того, что делаешь ты. Всё, что запущено через
`spawn`, называется задачей.

```rust
let handle = tokio::spawn(async { 2 + 2 });   // задача уже в очереди рантайма
// ... здесь можно заниматься чем-то другим ...
let four = handle.await.unwrap();             // получаем результат
```

```
 main                     очередь рантайма        воркеры
 ----                     ----------------        -------
 spawn(job) ───────────►  [ job ]
 (идёт дальше)                  │  свободный воркер забирает
                                └───────────────►  poll(job) ... Pending ... poll(job) ... Ready
 handle.await  ◄─────── результат в слоте JoinHandle ────────────┘
```

Главное отличие от обычного Future: **задача стартует сразу**, а хэндл нужен лишь чтобы дождаться
результата. Поэтому

```rust
let thumbs: Vec<_> = photos.iter().map(|p| resize(p)).collect();   // Future, никто не запущен
for t in thumbs { t.await; }                                       // уменьшаются по очереди

let thumbs: Vec<_> = photos.iter().map(|p| tokio::spawn(resize(p.clone()))).collect();  // все уже бегут
for t in thumbs { t.await.unwrap(); }                                                    // только собираем
```

Первый вариант не параллельнее простого цикла, второй да. Анимация `spawn_queue` показывает
этот путь: очередь, воркеры и слот результата в хэндле.

## JoinHandle и двойной Result

`JoinHandle<T>` при ожидании возвращает `Result<T, JoinError>`. `JoinError` это не ошибка
твоей программы, а судьба задачи: она могла упасть с паникой или быть отменена. Если сама
задача возвращает `Result<V, E>`, снаружи получается вложенность:

```rust
let job = tokio::spawn(fetch_balance(account));   // JoinHandle<Result<Money, BankError>>
let money = job.await??;
//               ││
//               │└─ ошибка самой задачи (BankError)
//               └── ошибка судьбы задачи (JoinError)
```

Если у твоей ошибки есть `From<JoinError>`, `??` читается легко. Не прячь внешний слой
через `unwrap()` в коде, где паника одной задачи не должна ронять всех.

## Две границы: `'static` и `Send`

`tokio::spawn` принимает только Future, который удовлетворяет обоим условиям.

**`'static`.** Задача может прожить дольше функции, которая её запустила, поэтому не имеет
права держать ссылки на локальные данные.

```rust
fn greet(user: &User) {
    tokio::spawn(async move { send_mail(user).await });   // ошибка: user не 'static
}
fn greet(user: &User) {
    let user = user.clone();                              // владение
    tokio::spawn(async move { send_mail(&user).await });  // ок
}
```

Общие данные для нескольких задач кладут в `Arc` и клонируют *до* `move`, внутри цикла:

```rust
let config = Arc::new(load_config());
for worker in 0..4 {
    let config = Arc::clone(&config);        // у каждой задачи свой клон
    tokio::spawn(async move { run_worker(worker, &config).await });
}
```

**`Send`.** Задача на multi_thread может переехать на другой воркер между двумя опросами, поэтому
всё, что в ней живёт, должно уметь путешествовать между потоками. Rc, сырые указатели
и guard от `MutexGuard` из std этого не умеют.

Тонкость в том, *что именно* считается живущим в задаче. Состояние Future хранит все переменные,
которые должны пережить точку `.await`. Значение, которое создано и умерло между двумя
`.await`, в состояние не попадает.

```rust
tokio::spawn(async {
    let cache = Rc::new(build_cache());
    warm_up(&cache);
    flush_to_disk().await;       // cache ещё жив здесь: Future не Send, не соберётся
    warm_up(&cache);
});

tokio::spawn(async {
    let report = { let cache = Rc::new(build_cache()); summarize(&cache) };  // cache умер до .await
    flush_to_disk().await;                                                  // ок, report это обычные данные
});
```

Замена типов, которые не годятся: `Rc` на `Arc`, `RefCell` на `Mutex` (из std, если замок держится коротко и без `.await`). Но иногда тип приходит из чужого кода, и заменить его нельзя: тогда его область видимости сужают так, чтобы он не дожил до `.await`.

Читать сообщение «future cannot be sent between threads safely» нужно до конца: компилятор
пишет, какая именно переменная и какой `.await` виноваты.

## Паника и отмена

Паника в задаче не убивает программу: tokio ловит её на границе задачи и отдаёт тому, кто
ждёт хэндл, в виде `JoinError`. Если хэндл никто не ждёт, паника уходит в stderr и пропадает.

```rust
match worker.await {
    Ok(report) => report,
    Err(e) if e.is_panic() => std::panic::resume_unwind(e.into_panic()),  // повторить панику у себя
    Err(e) => { /* e.is_cancelled(): задачу отменили */ Report::empty() }
}
```

Нагрузка паники лежит в `Box<dyn Any + Send>`. Текст из неё достают через `downcast_ref`:
`panic!("литерал")` даёт `&'static str`, а `panic!("код {code}")` даёт `String`.

## abort и его границы

`handle.abort()` просит рантайм отменить задачу. Что именно происходит: поднимается флаг, и
**когда задачу в следующий раз будут опрашивать, рантайм вместо этого уничтожит её**. Задача
останавливается в точке `.await`, там, где она всё равно отдаёт управление. Локальные
переменные при этом честно дропаются.

Отсюда два следствия. Первое: если задача сейчас выполняет код, abort её не прервёт, она
дойдёт до ближайшего `.await`. Второе, куда неприятнее: **цикл без `.await` отменить нельзя**.

```rust
tokio::spawn(async {
    loop { compress_next_block(); }                 // ни одного .await
});
// abort() здесь поднимет флаг, и никто его не увидит

tokio::spawn(async {
    loop { compress_next_block(); tokio::task::yield_now().await; }   // точка отмены есть
});
```

Посмотри анимацию `abort_points`: два цикла рядом. После `abort()` ожидание хэндла возвращает
`Err(JoinError)`, у которого `is_cancelled()` истинно. Если задача успела завершиться раньше,
придёт обычный `Ok`: отменить сделанное нельзя.

`AbortHandle` (метод `handle.abort_handle()`) это пульт без права на результат: он умеет
`abort()` и `is_finished()`. Его можно отдать другому, пока хэндл остаётся у тебя.

## Дроп JoinHandle не отменяет

В привычном `std::thread` выброс JoinHandle отсоединяет поток. Здесь так же: **задача продолжает
жить, просто результат никто не получит**. Иногда это нужно (fire and forget), но чаще
задача принадлежит какому-то владельцу (соединению, запросу), и её надо отменять вместе с ним.
Решение в Rust типичное: RAII-обёртка, у которой Drop делает уборку. Как временный файл,
который удаляется вместе со значением:

```rust
struct TempFile(PathBuf);
impl Drop for TempFile {
    fn drop(&mut self) { let _ = std::fs::remove_file(&self.0); }
}
```

Для задачи уборка это остановка. Какой метод хэндла для этого нужен, ты уже знаешь.

## Остановка рантайма убивает задачи

Задачи не держат рантайм живым. Когда `main` (или `block_on`) завершается, а рантайм
дропается, всё недоделанное выбрасывается: фоновый сброс на диск, отправка уведомления. Либо
дождись хэндлов (`JoinSet`, учёт задач в одной из следующих глав), либо сделай явную остановку.
Обычный drop рантайма ещё и ждёт блокирующие потоки, и один зависший вызов подвесит выход.
`runtime.shutdown_timeout(d)` ограничивает это ожидание.

## JoinSet

Вектор хэндлов привязывает порядок ожидания к порядку запуска. `JoinSet` держит задачи сам и
отдаёт их по мере готовности:

```rust
let mut set = JoinSet::new();
for clip in clips { set.spawn(transcode(clip)); }
while let Some(result) = set.join_next().await {
    // сюда приходит тот, чья перекодировка закончилась первой
}
```

У него два полезных свойства. Первое: **дроп `JoinSet` отменяет все ещё не завершённые задачи**
(как `abort_all`). Поэтому «первая ошибка отменяет остальных» пишется как обычный ранний
`return`. Второе: по `set.len()` видно, сколько задач в полёте, а значит, легко держать
скользящее окно:

```
limit = 3, элементов 7

 пока в наборе меньше 3:        { 1 2 3 }   запускаем
 join_next → закончилась 2:     { 1 3 }     освободилось место
 запускаем следующую:           { 1 3 4 }
 ...
```

Окно не ждёт, пока закончится вся пачка: освободилось место, сразу стартует следующая.
Это ответ на вопрос из начала главы: сотня записей одновременно, а не одна и не десять тысяч.

## Кооперативность и блокирующая работа

Рантайм не вытесняет задачи принудительно: переключение возможно только в `.await`. Длинный
цикл или тяжёлое вычисление между двумя `.await` держит воркер целиком (вспомни `blocking_worker`
из прошлой главы). Есть два лекарства, и они для разных случаев.

`tokio::task::yield_now().await` отдаёт поток и встаёт в конец очереди. Он годится, когда
работа по сути async, а цикл просто долгий: вставляй его не на каждом шаге, а раз в сотню или
тысячу. Это же способ сделать цикл отменяемым.

`tokio::task::spawn_blocking(|| ...)` выполняет *синхронное* замыкание в отдельном пуле
потоков и возвращает хэндл, который можно ждать через `.await`. Он годится для хеширования,
сжатия, блокирующих клиентов и всего, что нельзя переписать на async. Замыкание должно быть
`'static`, поэтому данные уезжают внутрь через `move`. Блокирующую задачу отменить нельзя:
начавшись, она доработает до конца.

## task_local вместо thread_local

Часто нужен контекст запроса (id, пользователь), который виден в любой глубине вызовов без
передачи через каждый аргумент. В синхронном коде для этого `thread_local!`. В async он
ломается: поток принадлежит не задаче, а рантайму. Пока одна задача ждёт, на том же потоке
работает другая и затирает значение, а на multi_thread задача ещё и переезжает между потоками.

```rust
tokio::task_local! { static REQUEST_ID: u32; }

REQUEST_ID.scope(42, async {
    handler().await            // внутри REQUEST_ID.get() и try_with видят 42
}).await;
```

Значение живёт рядом с Future и подставляется на каждый опрос. Вне `scope` обращение через
`try_with` вернёт ошибку, а `get` запаникует.

## Типичные ошибки

- Собрать Future в `Vec` и ждать по одному, ожидая параллельности. Нужен `spawn`.
- `async move` в цикле, забирающий один и тот же `Arc`. Клонируй до `move`.
- `Rc`, `RefCell` или `MutexGuard` из std, живущие через `.await` в spawn-нутой задаче.
- `.unwrap()` на ожидании хэндла там, где одна упавшая задача не должна ронять остальных.
- Ждать, что `abort` остановит цикл без `.await`.
- Думать, что дроп `JoinHandle` останавливает задачу.
- Запускать десять тысяч задач без ограничения.
- Тяжёлое вычисление прямо в async-функции вместо `spawn_blocking`.
- `thread_local!` для контекста запроса.
