# join и select

Карточка товара в магазине собирается из трёх источников: цена из каталога, остаток со склада,
отзывы из отдельного сервиса. Каждый отвечает за десятую долю секунды. Если спрашивать их по
очереди, покупатель ждёт три десятых, а если всех сразу, одну. Другая история: тот же товар лежит
на двух складах, и нужен ответ того, кто ответит первым, а второй запрос уже никому не нужен.

Для первой истории в tokio есть `join!`, для второй `select!`. Обе вещи работают внутри одной
задачи: ни `spawn`, ни каналов, просто несколько future, которые ждут вместе. Через пару глав
почти каждый обработчик у нас будет выглядеть как цикл с `select!`, поэтому разберёмся с ним
аккуратно: именно на нём ошибаются чаще всего.

## Future ленивый

Прежде чем что-то склеивать, одно свойство, о которое спотыкаются все, кто пришёл из JavaScript.

```rust
let stock = warehouse.stock(id);        // ничего не произошло, только создали значение
let price = catalog.price(id);          // и тут тоже
let s = stock.await;                    // вот теперь запрос ушёл и мы ждём его
let p = price.await;                    // и только теперь второй
```

Вызов async-функции возвращает future, но не запускает его. Работа начинается, когда future
опрашивают, то есть на `.await`. Поэтому два `await` подряд идут по очереди, даже если оба future
созданы заранее. Чтобы они шли вместе, их надо отдать одному ожидающему, который опрашивает
обоих. Это и делают `join!` и `select!`.

Посмотри `join_vs_seq`: те же три запроса, ждать подряд против ждать вместе.

## join!: ждём всех

```rust
let (price, stock, reviews) = tokio::join!(
    catalog.price(id),
    warehouse.stock(id),
    reviews.for_item(id),
);
```

`join!` опрашивает все future по очереди внутри одной задачи и возвращает кортеж результатов,
когда готовы все. Время равно времени самого долгого, а не сумме. Типы результатов могут быть
любыми разными, порядок в кортеже тот же, что в записи.

Три полезных следствия:

- Спавна нет, поэтому future не обязаны быть `'static` и могут брать данные по ссылке:
  `catalog` и `warehouse` выше просто заимствованы.
- Всё идёт в одной задаче, на одном потоке. Если в ветке окажется тяжёлый расчёт без `.await`
  (или блокирующий вызов), остальные ветки будут ждать его целиком. Конкурентность `join!` это
  ожидание вместе, а не вычисление вместе.
- Ветка не обязана быть вызовом функции: годится любой future, в том числе async-блок.
  Условную работу удобно прятать внутрь блока:

```rust
let discount = async {
    if user.is_member() { Some(loyalty.discount(user.id).await) } else { None }
};
let (price, discount) = tokio::join!(catalog.price(id), discount);
```

## try_join!: ждём всех, но уходим при первой ошибке

Если ветки возвращают `Result`, нужно другое поведение: при первой же ошибке остальное
ждать бессмысленно, страницу всё равно не собрать.

```rust
let (price, stock) = tokio::try_join!(catalog.price(id), warehouse.stock(id))?;
```

`try_join!` возвращает `Result<(A, B), E>`. Как только одна из веток дала `Err`, макрос
возвращает эту ошибку, а остальные ветки **уничтожаются** на полпути (подробнее о таком
уничтожении ниже). Ветки обязаны иметь один и тот же тип ошибки; если у них разные, приведи их
к общему прямо в ветке (`.map_err(..)`, `.map_err(Into::into)`).

Сравни с `join!` и `?` после: он дождался бы самой медленной ветки и только потом показал
первую ошибку.

## Сколько future неизвестно заранее

`join!` принимает ветки перечислением в коде. Для списка произвольной длины есть крейт `futures`:

```rust
use futures::future::join_all;

let prices: Vec<Price> = join_all(ids.iter().map(|id| catalog.price(*id))).await;
```

`join_all` возвращает результаты в порядке входа (а не готовности). Одновременно он запускает
**всех**: для списка из десяти тысяч id это десять тысяч запросов сразу. Ограничивать число
одновременных запросов будем в главе про стримы.

Когда результаты нужны по мере готовности, а не все вместе, берут `FuturesUnordered`:

```rust
use futures::stream::{FuturesUnordered, StreamExt};

let mut pending: FuturesUnordered<_> = warehouses
    .iter()
    .map(|w| async move { (w.name(), w.stock(id).await) })
    .collect();

while let Some((name, stock)) = pending.next().await {
    println!("{name}: {stock}");              // в порядке готовности
}
```

Это поток: `next().await` отдаёт ближайший готовый результат, `None` значит, что future кончились.
Можно остановиться раньше: когда `pending` уничтожится, недоделанные future уничтожатся вместе
с ним. Номер или имя источника кладут в результат сами, потому что порядок прихода о нём уже ничего
не говорит.

## select!: кто первый

```rust
tokio::select! {
    stock = north.stock(id) => println!("север: {stock}"),
    stock = south.stock(id) => println!("юг: {stock}"),
}
```

Каждая ветка: `шаблон = future => обработчик`. `select!` опрашивает все future и выбирает
**первый**, который стал готов. Его результат попадает в шаблон, выполняется обработчик, а все
остальные future **уничтожаются** (`Drop`) и больше не опрашиваются.

Уничтожаются они там, где остановились: на очередном `.await` внутри. Ни одна строка после этого
`.await` не выполнится, все локальные переменные просто умрут. В этом сила `select!`
(проигравший запрос не доработает впустую и не потратит соединение) и опасность (если
проигравший успел сделать полдела, эти полдела так и остались полдела). Порядок такой: сначала
уничтожаются проигравшие, потом выполняется обработчик победителя. Посмотри `select_cancel`.

Если победили сразу несколько готовых future, `select!` выбирает случайно: так ни одна ветка не
голодает. Про это ниже, в разделе про `biased`.

### Таймаут как частный случай

```rust
tokio::select! {
    reply = client.call(request) => handle(reply),
    _ = tokio::time::sleep(Duration::from_secs(2)) => handle_timeout(),
}
```

То же делает `tokio::time::timeout(dur, fut)`, он короче и возвращает `Result<_, Elapsed>`. Но
как только веток больше двух или нужны разные реакции, `select!` удобнее.

## select! в цикле

Чаще всего `select!` стоит в цикле: канал, таймер, сигнал остановки в одном месте.

```rust
let mut tick = tokio::time::interval(Duration::from_secs(5));
loop {
    tokio::select! {
        Some(order) = orders.recv() => process(order).await,
        _ = tick.tick() => report_stats(),
    }
}
```

Первый `tick()` у `interval` срабатывает сразу, в нулевую миллисекунду, а не через период. Если
первый тик тебе не нужен, прочитай его один раз до цикла. Для ветки `select!` это значит: в
первом обороте таймер уже готов.

Обрати внимание на `Some(order) = orders.recv()`. Шаблон слева может не совпасть. Тогда ветка
**выключается** до конца этого вызова `select!` и больше не опрашивается. `recv()` возвращает
`None`, когда канал закрыт и пуст, шаблон `Some(order)` не совпадает, и закрытый канал просто
выпадает из выбора, а остальные ветки живут дальше. Так можно слушать несколько каналов и не
спотыкаться о закрытые.

Когда выключены **все** ветки, `select!` без запасного пути паникует. Запасной путь называется
`else`:

```rust
let mut merged = Vec::new();
loop {
    tokio::select! {
        Some(line) = stdout.recv() => merged.push(format!("out: {line}")),
        Some(line) = stderr.recv() => merged.push(format!("err: {line}")),
        else => break,                       // оба потока закончились
    }
}
```

`else` срабатывает, только когда выключены все остальные ветки. Если одна из них (например, таймер)
жива всегда, до `else` дело не дойдёт, и закрытие каналов придётся ловить самому.

Два важных замечания про цикл:

- Выражение future в ветке **вычисляется на каждом обороте**. Вызов `orders.recv()` создаёт новый
  future каждый раз. Для `recv` это безвредно, а вот `sleep(Duration::from_secs(2))` на каждом
  обороте начинает отсчёт заново. Об этом дальше.
- Обработчики выполняются в теле функции, поэтому в них можно `break`, `return` и `?`, а также
  менять локальные переменные.

### Условие ветки: `, if`

```rust
let mut tokens = 5;
let mut refill = tokio::time::interval(Duration::from_secs(1));
loop {
    tokio::select! {
        Some(req) = incoming.recv(), if tokens > 0 => {
            tokens -= 1;
            serve(req).await;
        }
        _ = refill.tick() => tokens = 5,
    }
}
```

Пока токенов нет, запросы остаются лежать в канале, а таймер продолжает идти.

После шаблона и future можно добавить `, if условие`. Условие вычисляется до опроса, и если оно
ложно, ветка выключена на этот оборот: её future даже не создаётся. Ничего не забирается из канала
(это важно: сообщение остаётся в очереди, а не копится у тебя в памяти), не стартует операция.
Это основной способ «включать и выключать» ветки по состоянию.

### Порядок опроса: `biased`

По умолчанию `select!` каждый раз перемешивает порядок опроса, чтобы ни одна ветка не
заглушала другую. Если нужен строгий приоритет (скажем, «сигнал остановки важнее заданий»),
пишут `biased;` первой строкой:

```rust
loop {
    tokio::select! {
        biased;
        Some(alarm) = alarms.recv() => page_oncall(alarm).await,   // всегда проверяется первой
        Some(note) = notes.recv() => archive(note),
    }
}
```

Ветки опрашиваются сверху вниз, побеждает первая готовая. Цена: если верхняя ветка готова всё
время, нижние не получат слова. Поэтому наверх ставят то, что бывает готово редко и важно:
тревогу, остановку, отмену.

## Один future на много оборотов: `pin!` и `&mut`

Допустим, внутри цикла надо дождаться долгой операции, пока обрабатываются сообщения.

```rust
// неправильно: на каждом обороте отчёт строится заново
loop {
    tokio::select! {
        report = build_report(&db) => break report,
        Some(req) = requests.recv() => reply_busy(req),
    }
}
```

Каждый запрос уничтожает `build_report` и создаёт новый. Нужно создать future **один раз** до
цикла, а в ветке опрашивать его по ссылке:

```rust
use tokio::{pin, select};

let report = build_report(&db);
pin!(report);                                       // закрепили на месте
let ready = loop {
    select! {
        res = &mut report => break res,
        Some(req) = requests.recv() => reply_busy(req),
    }
};
```

Две детали. Во-первых, `&mut fut` опрашивается много раз, и ни один оборот не уничтожает future.
Во-вторых, для этого `Fut` должен быть `Unpin`, а async-блоки и async-функции такими не
являются (они могут хранить ссылки на собственные поля). Поэтому их закрепляют на месте: макрос
`tokio::pin!` или `Box::pin`. Без `pin!` компилятор скажет, что `Unpin` не выполнен, и подскажет
макрос.

### Готовый future опрашивать нельзя

`&mut report` в цикле означает, что на следующем обороте после завершения его опросят снова.
Async-функция в таком случае паникует: `` `async fn` resumed after completion ``. Лечение: флаг
(или `Option` с результатом) и условие `, if` на ветке, пока результата нет.

```rust
let mut uploaded = false;
loop {
    tokio::select! {
        url = &mut upload, if !uploaded => {
            uploaded = true;
            println!("загружено: {url}");
        }
        Some(m) = events.recv() => log(m),
        else => break,
    }
}
```

### Общий срок и «тишина дольше»

Две разные вещи, которые легко перепутать.

**Общий срок на весь цикл**: таймер создают один раз до цикла, закрепляют, опрашивают по ссылке.

```rust
let cooldown = tokio::time::sleep(Duration::from_secs(60));
pin!(cooldown);
let mut finished = false;
while !finished {
    select! {
        () = &mut cooldown => finished = true,         // кнопка снова доступна
        Some(_) = clicks.recv() => shake_button(),
    }
}
```

Если написать `_ = sleep(60 с) => break` прямо в цикле, таймер будет создаваться на каждом обороте и
сработает только после минуты полной тишины. Это ловушка номер один.

**Скользящий срок** («сессия истекает через пять минут после последней активности»): таймер
тоже один и закреплённый, но при каждой активности его срок сдвигают методом
`Sleep::reset(новый_момент)`. Он не создаёт таймер заново, а переносит срок существующего.
Момент это `tokio::time::Instant` (с `std::time::Instant` не соберётся), а так как таймер
закреплён, вызывать надо через `as_mut()`. Вместо переноса можно и пересоздавать `sleep` на каждом
обороте: тогда это просто «тишина дольше N», что для одного источника тоже верно. Но когда
источников несколько или срок общий с другими ветками, один закреплённый таймер с `reset` яснее.

## Отмена и что в ней теряется

Каждый раз, когда `select!` выбирает победителя, проигравшие future уничтожаются в произвольной
точке. Вопрос: безопасно ли это? Операцию называют **безопасной к отмене** (cancellation safe),
если ее досрочное уничтожение не теряет данных: либо операция не успела ничего сделать, либо
сделала всё.

| операция | безопасна? |
|---|---|
| `mpsc::Receiver::recv`, `watch::Receiver::changed`, `oneshot` | да: сообщение остаётся в канале |
| `Mutex::lock`, `Semaphore::acquire`, `sleep`, `interval.tick()` | да: пока не получили, ничего не заняли |
| `AsyncReadExt::read` | да: если вернулась порция, она уже у тебя |
| `AsyncReadExt::read_exact`, `read_to_end`, `read_line` | **нет**: часть байтов уже прочитана и пропадёт вместе с future |
| `AsyncWriteExt::write_all` | **нет**: часть могла быть записана, а сколько, ты не узнаешь |
| `Sender::send(value)` | сам по себе да, но значение в аргументе пропадёт |

Опасно, когда в ветке `select!` стоит операция «из нескольких шагов»: она успевает сделать
часть работы (забрала сообщение, прочитала байты), а потом её убивают. Для таких случаев есть два
приёма.

**Состояние держи снаружи future.** Не в локальных переменных, а в структуре, которая переживёт
уничтожение:

```rust
struct LineReader { rx: mpsc::Receiver<u8>, partial: Vec<u8> }

impl LineReader {
    async fn next_line(&mut self) -> Option<String> {
        loop {
            let byte = self.rx.recv().await?;        // отмена здесь безопасна
            if byte == b'\n' {
                return Some(String::from_utf8_lossy(&std::mem::take(&mut self.partial)).into_owned());
            }
            self.partial.push(byte);                  // состояние лежит в self
        }
    }
}
```

Отмена в любой точке теряет в худшем случае ничего: накопленное в `self.partial`, и следующий
вызов продолжит с него. Вынеси «полпути» из локальных переменных в поля.

**Раздели ожидание и действие.** У `Sender` для этого есть `reserve()`: он ждёт свободного места и
отдаёт разрешение, которое потом отправляет значение мгновенно.

```rust
tokio::select! {
    permit = out.reserve() => {
        let permit = permit?;
        permit.send(read_next_event());     // значение берётся только когда место уже есть
    }
    _ = stop.changed() => break,
}
```

Если бы тут стояло `out.send(read_next_event())`, значение было бы взято (прочитано, посчитано,
номер выдан) до ожидания, и при победе другой ветки пропало бы вместе с future.

## Типичные ошибки

- `sleep(..)` прямо в ветке цикла вместо общего таймера: срабатывает только в полной тишине.
- Шаблон `Some(x) = rx.recv()` без `else` или без другой всегда живой ветки: паника, когда все
  источники закрылись.
- Готовый future в цикле по `&mut` без флага: `resumed after completion`.
- `read_exact`, `read_line`, `write_all` в ветке `select!` с таймером: данные теряются на
  отмене. Читай порциями в буфер, который живёт снаружи.
- Блокирующая или тяжёлая работа внутри ветки `join!` или `select!`: остальные ветки стоят.
- `join_all` на огромном списке: сразу тысячи одновременных запросов.
- Забытый приоритет: сигнал остановки в той же куче, что и забитая очередь, проигрывает ей в половине
  случаев. Нужен `biased;` и правильный порядок.
- Мысль «проигравший доработает в фоне». Нет: он уничтожен. Если работа должна идти независимо,
  это `spawn`, а не ветка `select!`.
