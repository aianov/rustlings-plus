# Консоль задач

Сервис завис, а в логе ничего. Хочется открыть окно и увидеть живые задачи: как называются, в каком
состоянии, сколько раз опрошены, как давно чего-то ждут. Так устроена `tokio-console`. Пишем её
маленькую версию, которая живёт внутри процесса: все задачи сервиса запускаются через неё, а она
ведёт реестр. В сквозном проекте то же самое станет `spawn`-обёрткой `service-runtime`.

## Что уже есть

```
dbg_console/
  Cargo.toml
  crates/
    console/
      src/lib.rs            открытые типы и методы, тела пустые
    acceptance/
      src/lib.rs            пустой
      tests/acceptance.rs   приёмочные тесты (менять нельзя)
```

В `crates/console/src/lib.rs` готовы типы `State` и `TaskInfo` и сигнатуры методов `Console`.
Внутренности придумываешь ты. Внешний вид менять нельзя.

## Что нужно сделать

1. **Запуск.** `Console::spawn(name, future)` запускает `future` как обычную задачу tokio и возвращает
   её `JoinHandle` с тем же результатом. Задача получает номер: 1, 2, 3 и так далее в порядке
   запуска, общий для всех клонов `Console`. `Console` дёшево копируется (`Clone`), клоны видят один
   реестр, и задача может запускать другие задачи через свой клон.
2. **Состояния.** У каждой задачи есть `State`:
   `Waiting` (ещё не опрошена или последний опрос вернул `Pending`), `Running` (идёт `poll`),
   `Finished`, `Panicked`, `Cancelled` (задачу прервали до завершения: `abort` или уничтожение
   рантайма). Новая задача до первого опроса `Waiting`.
3. **Опросы.** `polls` растёт на один при каждом `poll`. `longest_poll` это самый долгий один опрос,
   измеренный настоящими часами (`std::time::Instant`).
4. **Ожидание.** Для задачи в состоянии `Waiting` поле `waiting_for` равно времени с момента, когда
   она последний раз оказалась в ожидании (по часам tokio, то есть на замороженном времени
   детерминировано). Для остальных состояний `None`.
5. **Паника.** Панику задачи реестр записывает как `Panicked`, а владелец `JoinHandle` всё равно
   получает ошибку-панику (`is_panic()`), как будто консоли не было.
6. **Отчёты.** `tasks()` возвращает снимок по возрастанию номеров, включая завершённые. `alive()` число
   задач в состояниях `Running` и `Waiting`. `prune()` выбрасывает из реестра все остальные записи и
   возвращает их число. `stuck(порог)` возвращает имена задач, ожидающих строго дольше порога, по
   возрастанию номеров.
7. **Дамп.** `dump()` возвращает текст точно такого вида (без завершающего перевода строки):

```
tasks alive=1 total=2
1 stuck Waiting polls=1 waiting=1500ms
2 done Finished polls=1 waiting=-
```

   Первая строка: сколько живых и сколько всего записей. Дальше по строке на задачу: номер, имя,
   состояние (как печатает `{:?}`), число опросов и время ожидания в целых миллисекундах (для
   не ожидающих `-`).
8. **Сторож долгих poll.** `on_long_poll(порог, f)` включает вызов `f(имя, длительность)` после каждого
   опроса, который длился строго дольше порога. Обратный вызов имеет право сам вызвать `tasks()`,
   поэтому реестр на время вызова не должен быть заблокирован.

## Критерии приёмки

`cargo test --workspace` в корне проекта: все тесты `crates/acceptance/tests/acceptance.rs`
проходят. Они проверяют номера и имена, состояния и число опросов, точное время ожидания и точный
текст дампа на замороженном времени, `stuck` с границей, панику (с сохранением ошибки для
владельца), отмену, `prune`, сторож долгих poll с обратным вызовом, смотрящим в реестр, и двести
задач из четырёх потоков. Решение должно проходить
`cargo clippy --workspace --all-targets -- -D warnings`.
