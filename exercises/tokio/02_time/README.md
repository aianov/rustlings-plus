# Время

В соцсети пора разлогинивать тех, кто молчит полчаса, раз в минуту собирать метрики и
отвечать на запрос профиля не дольше чем за две секунды, даже если одно из хранилищ
задумалось. Каждая из этих задач про время, и все они ломаются одинаково: кто-то написал
`sleep` в цикле, забыл про срок или проверил таймер тестом, который идёт полчаса.

В tokio всё про время живёт в модуле `tokio::time`. Это не обёртка над системными часами: у
рантайма свой таймерный драйвер (его включает `enable_time`, помнишь паники из первой главы),
а часы можно подменить в тестах. Поэтому всё, что связано с ожиданием, берём из `tokio::time`,
а не из `std`.

## sleep, Duration и Instant

`tokio::time::sleep(d).await` усыпляет задачу, а не поток: рантайм продолжает работать с
остальными. Это основа всех остальных инструментов.

```rust
use std::time::Duration;
use tokio::time::{sleep, Instant};

let started = Instant::now();
sleep(Duration::from_millis(1500)).await;
println!("{:?}", started.elapsed());          // около 1.5 с
```

`Duration` это длина промежутка, `Instant` это точка на часах, и они складываются по
правилам: `Instant + Duration` даёт Instant, `Instant - Instant` даёт Duration. Полезные
вещи, которые стоит знать заранее:

- `Duration::from_secs_f64`, `as_secs_f64()`, `as_millis()` для перевода в числа;
- `Duration` не бывает отрицательным: `a - b` при `b > a` паникует. Безопасные варианты:
  `checked_sub`, `saturating_sub` у Duration и `checked_duration_since`,
  `saturating_duration_since` у Instant;
- арифметика с переполнением: степень двойки для пауз растёт быстро, умножай через
  `saturating_mul`. Степень двойки бери как `1u64.checked_shl(n).unwrap_or(u64::MAX)`, а потом
  умножай на базу: `checked_shl` проверяет только величину сдвига (`n < 64`), а старшие биты,
  которые теряет сдвиг уже готового числа вроде `100 << 62`, не замечает и молча даёт ноль;
- sleep имеет разрешение около миллисекунды: двух событий в один и тот же момент не
  гарантирует никто.

`Sleep` это Future, и создаётся он сразу вместе с отсчётом: `let s = sleep(d);` запоминает срок
в момент создания, а не в момент первого `.await`. Если Future полежит, пока ты занят другим,
срок пройдёт.

## timeout: ограничить ожидание

```rust
use tokio::time::{timeout, error::Elapsed};

match timeout(Duration::from_secs(2), send_email(msg)).await {
    Ok(Ok(receipt)) => println!("отправлено {receipt:?}"),   // успели, и ответ хороший
    Ok(Err(e))      => println!("почтовик отказал: {e}"),     // успели, но отказ
    Err(Elapsed { .. }) => println!("не дождались"),          // срок вышел
}
```

`timeout` возвращает `Result<T, Elapsed>`, где T это то, что вернул внутренний Future. Если
Future сам возвращает Result, получается вложенность, и два слоя значат разное: внешний «успели
ли», внутренний «что нам ответили». Чаще всего их сводят в одну свою ошибку, где `Timeout` и
`Failed(..)` отличимы: на таймаут обычно отвечают повтором, на отказ нет.

Что именно происходит при срабатывании? `timeout` просто **дропает** внутренний Future и
возвращает `Err`. Ничего не откатывается, и никто не спрашивает, готов ли Future остановиться.
У этого есть следствие, которое мы разберём сразу после дедлайнов.

### Общий срок на цепочку

`timeout(d, ..)` отсчитывает `d` от своего вызова. Если у тебя три последовательных шага и перед
каждым свой `timeout(d, ..)`, цепочка может занять `3 * d`. Чтобы срок был общим, фиксируют
**момент**, а не длительность:

```rust
let deadline = Instant::now() + Duration::from_secs(2);
let user = tokio::time::timeout_at(deadline, load_user(id)).await??;
let feed = tokio::time::timeout_at(deadline, load_feed(&user)).await??;
let ads  = tokio::time::timeout_at(deadline, load_ads(&user)).await??;
```

Второй шаг получает ровно столько времени, сколько осталось от двух секунд после первого.
`sleep_until(deadline)` работает так же для паузы до заданного момента.

### Отмена посередине

Дроп Future происходит на ближайшем `.await`. (`select!`, о котором будет своя глава, тоже
дропает проигравшие ветки, так что всё сказанное ниже относится и к нему.) Всё, что операция успела выполнить до этой
точки, остаётся, а всё после не выполнится никогда. Поэтому код, который могут оборвать
(а любой код под `timeout` и в `select!` могут), нельзя писать так:

```rust
async fn publish(post: Post, index: &Index, storage: &Storage) {
    storage.write(&post);               // уже записали
    notify_followers(&post).await;      // обрыв здесь: пост есть, индекса нет
    index.add(&post);
}
```

Пост лежит в хранилище, но не попал в индекс, и так будет всегда. Лечится порядком: всё
медленное и ненадёжное (ожидание сети) делается *до* изменений состояния, а сами изменения
идут подряд без `.await` между ними. Тогда обрыв либо случился до первой записи, либо после
последней. Это свойство называют безопасностью к отмене (cancellation safety), и мы ещё не
раз к нему вернёмся.

## interval: расписание

`interval` выдаёт тики по расписанию, а не «через паузу после предыдущего дела».

```rust
let mut ticker = tokio::time::interval(Duration::from_secs(60));
loop {
    ticker.tick().await;
    collect_metrics().await;
}
```

Две особенности, о которых забывают.

**Первый тик приходит сразу.** `interval` считает, что нулевой момент это тоже момент. Если
первый запуск должен быть через период, используют `interval_at(Instant::now() + period, period)`.

**Расписание не дрейфует.** Сравни два варианта, период 60 секунд, работа 5 секунд:

```
sleep после работы:  работа 5 + пауза 60 = период 65, 130, 195 ...   (уплывает на 5 с каждый раз)
interval:            тики на 0, 60, 120, 180 ...                       (работа расписание не двигает)
```

Анимация `interval_drift` показывает это на шкале времени.

### Если работа не успела: MissedTickBehavior

Что будет, если работа на тике заняла дольше периода? Тики, которые пришлись на это время,
называются пропущенными, и `interval` обязан решить, что с ними делать. Решает политика:

| политика | что делает после затянувшейся работы | когда нужна |
|---|---|---|
| `Burst` (по умолчанию) | отдаёт пропущенные тики сразу один за другим, пока не догонит расписание | нельзя терять ни одной итерации |
| `Delay` | следующий тик через период после того, как работа кончилась; сетка сдвигается | работы не должны идти теснее периода |
| `Skip` | первый просроченный тик отдаёт сразу, остальные выбрасывает, дальше возвращается на исходную сетку | устаревшие тики бессмысленны |

```rust
ticker.set_missed_tick_behavior(MissedTickBehavior::Skip);
```

Burst по умолчанию коварен: после зависания получаешь лавину запусков подряд, которая
может добить и без того проблемную систему.

## Замороженное время в тестах

Тест на «сессия истекает через полчаса» не должен идти полчаса. Для этого у tokio есть
подменные часы (нужна feature `test-util`, у нас она включена):

```rust
#[tokio::test(start_paused = true)]
async fn session_expires_after_half_an_hour() {
    let session = Session::new();
    tokio::time::sleep(Duration::from_secs(30 * 60)).await;
    assert!(session.is_expired());
}
```

Что здесь происходит. С `start_paused` часы рантайма стоят. Пока у рантайма есть готовые к
работе задачи, время не движется. Как только все задачи упёрлись в таймеры, рантайм сам
**перематывает** часы к ближайшему из них и продолжает. Поэтому полчаса проходят мгновенно, а
порядок событий остаётся тем же, что в жизни.

Анимация `paused_clock` показывает, как часы прыгают к ближайшему таймеру.

Это даёт не только скорость, но и точность: `tokio::time::Instant::now()` в таком тесте даёт
виртуальное время, и `elapsed()` показывает ровно ту длительность, которую ты ждал. Хороший
способ проверить, что задачи идут параллельно: две задачи по 5 мс, запущенные вместе, займут
5 мс виртуального времени, а по очереди 10.

Ещё два инструмента.

`tokio::time::advance(d).await` сдвигает часы вручную на `d` (когда нужно проверять состояние
между тиками, а не просто дожидаться конца). Сдвиг будит таймеры, но не ждёт, пока разбуженные
задачи доработают: обычно хватает одной-двух передышек, например
`tokio::task::yield_now().await`, а чем длиннее цепочка задач, тем больше нужно. Двигай время небольшими шагами: один большой прыжок будит
таймеры разом, и интервалы, которые должны были сработать по одному, срабатывают пачкой.

И главная ловушка: **заморожены только часы tokio.** `std::time::Instant` показывает настоящее
время, и в таком тесте он «не видит» ни одного ожидания. Если в коде, который ты тестируешь,
осталась хоть одна проверка срока на std-часах, на замороженном времени она не сработает. Для
всего, что связано с таймерами tokio, бери `tokio::time::Instant`.

## Типичные ошибки

- `sleep` в цикле вместо `interval`: расписание уплывает на длительность работы.
- Ожидание первого тика через период, а получается сразу.
- Забытая политика пропуска: после зависания лавина тиков (Burst).
- `timeout` на каждый шаг цепочки вместо общего дедлайна.
- Между двумя связанными изменениями стоит `.await`, и операцию можно оборвать посередине.
- Вложенный Result от `timeout` не разобран, и таймаут путается с отказом.
- `std::time::Instant` в коде под замороженным временем.
- После `advance` сразу проверяется состояние, а задачи ещё не успели отработать.
- `std::thread::sleep` в тесте на замороженном времени: поток спит по-настоящему, а часы стоят.

## Задачи главы

Основа: sleep, Duration, Instant, backoff (tm1). Сроки: timeout, вложенный Result,
обрыв посередине, общий дедлайн (tm2 до tm5). Расписания: первый тик, дрейф, политики
пропуска (tm6 до tm8). Замороженное время: кэш с ttl, advance, ловушка std::time::Instant
(tm9 до tm11). Квиз tm_heartbeat собирает монитор сердцебиений на interval с политикой Skip,
timeout и общим бюджетом.
