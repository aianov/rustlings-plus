# Акторы и конвейеры

Билетная касса кинотеатра. Места лежат в таблице, и покупать их приходят сотни людей сразу. Первая
мысль: `Arc<Mutex<Seats>>`, и каждая покупка берёт замок. Пока покупка короткая, всё хорошо. Потом
к покупке добавляют проверку скидочной карты по сети, и замок оказывается занят чужим ожиданием
ответа. Касса стоит, хотя ничего не делает. Другой путь: у таблицы один хозяин, отдельная задача,
и она одна ходит в таблицу. Остальные кладут ей заявки в очередь и ждут ответа. Хозяин делает одно
дело за раз, поэтому гонок нет, а замка нет вовсе.

Это называется актор. В этой главе актор разрастается до целой инфраструктуры: пул воркеров,
конвейер из стадий, одно соединение на сотни ждущих, пул дорогих объектов, пакетная запись.
Всё это строится из того, что ты уже знаешь по каналам, и общая идея одна: **состоянием владеет
задача, остальные общаются с ней сообщениями**.

## Актор

```rust
enum Seats {
    Take { row: u8, seat: u8, reply: oneshot::Sender<bool> },
    Free { row: u8, seat: u8 },
}

fn spawn_box_office() -> mpsc::Sender<Seats> {
    let (tx, mut rx) = mpsc::channel(32);
    tokio::spawn(async move {
        let mut taken: HashSet<(u8, u8)> = HashSet::new();
        while let Some(msg) = rx.recv().await {
            match msg {
                Seats::Take { row, seat, reply } => {
                    let _ = reply.send(taken.insert((row, seat)));
                }
                Seats::Free { row, seat } => {
                    taken.remove(&(row, seat));
                }
            }
        }
    });
    tx
}
```

Из чего он состоит. Задача держит состояние (`taken`) в локальной переменной. Команды это обычный
`enum`: у каждого варианта своё имя и свои данные. Цикл `while let Some(..) = rx.recv().await` берёт
команды по одной, поэтому внутри цикла никто больше не трогает `taken`. Борроу-чекер доволен, замков
нет, а порядок команд тот же, в каком они легли в очередь.

Когда выброшены все `Sender`, `recv()` вернёт `None`, цикл кончится и задача закончится сама. Если
итог нужен снаружи, он уходит через `JoinHandle`: в конце `async move`-блока просто верни таблицу.
Посмотри `actor_mailbox`: там видно, как команды стоят в очереди и как актор разбирает их по одной.

### Запрос с ответом

Команда `Free` ответа не требует, а `Take` должна сказать, получилось ли занять место. Для этого
в команду кладут отправитель одноразового канала (`oneshot::Sender`), а получатель остаётся у
спросившего:

```rust
let (reply, answer) = oneshot::channel();
office.send(Seats::Take { row: 3, seat: 7, reply }).await?;
let got_it = answer.await?;
```

На каждый вопрос свой канал, поэтому перепутать ответы нельзя, сколько бы вопросов ни летело одновременно.
Две ошибки в этой строке значат разное. Ошибка у `send` означает «актора нет»: очередь закрыта. Ошибка
у `answer.await` означает «актор получил вопрос, но не ответил», например паниковал на нём. Обе
превращаются в одну «актор недоступен» в обёртке, которую мы сейчас напишем.

И ещё одна тонкость, на которой падают все. Сам актор делает `reply.send(..)`, а `send` у `oneshot`
возвращает `Result`: `Err`, если получатель уже выброшен (спросивший ушёл по таймауту или его задачу
остановили). Это обычная жизнь, не авария. `unwrap` здесь опасен: паника в задаче актора убьёт его
для всех остальных. Пиши `let _ = reply.send(..)`.

### Handle

Показывать всем `Seats`, `oneshot` и порядок отправки неудобно, и любой промах в этом протоколе
превращается в баг где-то далеко. Поэтому актора оборачивают в тонкую структуру с обычными
асинхронными методами:

```rust
#[derive(Clone)]
pub struct BoxOffice {
    tx: mpsc::Sender<Seats>,
}

impl BoxOffice {
    pub async fn take(&self, row: u8, seat: u8) -> Result<bool, Unavailable> {
        let (reply, answer) = oneshot::channel();
        self.tx.send(Seats::Take { row, seat, reply }).await.map_err(|_| Unavailable)?;
        answer.await.map_err(|_| Unavailable)
    }
}
```

Это `Handle`. Он `Clone` (клонируется `Sender`, не актор), живёт сколько угодно долго и годится для
любого числа задач. Снаружи актора не видно: есть только методы. Заодно именно здесь решается, что
считать «актор недоступен»: возвращать `Err(Unavailable)`, а не паниковать у вызывающего, который тут
не виноват.

### Когда актор останавливается

Актор закончит работу, когда не останется ни одного `Sender`. Значит, ни один `Sender` не должен
жить внутри самого актора. Типичная ловушка: актор шлёт команды сам себе (отложенные задачи,
напоминания) и для этого хранит клон своего `Sender`. Теперь «последний» отправитель это он сам, и
канал уже никогда не закроется. Лечится слабой ссылкой:

```rust
let me = tx.downgrade();                    // WeakSender: канал не держит
// ... позже, в отложенной задаче:
if let Some(tx) = me.upgrade() {            // Some, пока есть хоть один настоящий Sender
    let _ = tx.send(Reminder).await;
}
```

`WeakSender` не считается отправителем, а `upgrade()` возвращает `Some`, только если хотя бы один
настоящий `Sender` ещё жив. Проверить, закончилась ли задача, не дожидаясь её, можно через
`JoinHandle::is_finished()`.

## Пул воркеров

Если работа независимая (превращать картинки, считать хеши), одного хозяина мало: нужен пул.
У `mpsc` один получатель, а воркеров несколько, поэтому приёмник делят через `Arc` и замок:

```rust
let queue = Arc::new(tokio::sync::Mutex::new(rx));
for id in 0..workers {
    let queue = queue.clone();
    tokio::spawn(async move {
        loop {
            let next = queue.lock().await.recv().await;
            match next {
                Some(order) => process(id, order).await,
                None => break,
            }
        }
    });
}
```

Замок здесь `tokio::sync::Mutex`, потому что его держат через `.await` (ждут сообщения). Работает
такой пул, только если замок держится ровно время получения задания. Охранник замка это временное
значение, и если оно оказывается в заголовке `while let` или `if let`, то живёт до конца всего
тела цикла. Тогда воркеры выстраиваются в очередь за замком, и трудится один из N, а остальные
ждут. Всё выглядит правильно и даёт верный результат, просто медленно. Забирай задание отдельной
инструкцией, как выше: охранник умирает на точке с запятой.

Другое решение той же задачи: каждому воркеру своя очередь, а отправитель решает, кому отдать. Это
нужно, когда задания **связаны ключом**.

### Разбиение по ключу

Сообщения одной чат-комнаты должны приходить в порядке отправки, а разных комнат могут обрабатываться
одновременно. Общая очередь на всех воркеров порядка не даёт: два соседних сообщения комнаты
возьмут два воркера и закончат в любом порядке. Решение: свой приёмник у каждого воркера и
выбор воркера по ключу:

```rust
fn lane(room: u32, lanes: usize) -> usize {
    room as usize % lanes
}
// lanes[lane(room, lanes.len())].send(message).await
```

Одна и та же комната всегда попадает в одну и ту же очередь, а внутри очереди порядок сохраняется.
Хеш (`DefaultHasher`) или остаток от деления подходят одинаково, лишь бы выбор зависел только от ключа.
Если число воркеров поменять на ходу, ключи переедут на другие очереди, и старые сообщения могут
обогнать новые: смену правила делают при пустых очередях.

## Fan-in: много источников, один поток

Агрегатор погоды опрашивает несколько сервисов, у каждого своя задержка. Читателю нужен один
поток значений с пометкой, откуда они. Это обратная форма канала: много отправителей, один получатель.

```rust
let (tx, mut rx) = mpsc::channel(16);
for station in stations {
    let tx = tx.clone();
    tokio::spawn(async move {
        let reading = station.read().await;
        let _ = tx.send((station.name(), reading)).await;
    });
}
drop(tx);                                   // оригинал больше не нужен
while let Some((name, reading)) = rx.recv().await { /* ... */ }
```

Поток закончится, когда выброшены все клоны `Sender`, **включая оригинал**. Забытый оригинал,
например в той же функции, где читают, это самая частая причина «приёмник ждёт вечно». Имя источника
кладут в сообщение: порядок прихода о нём ничего не говорит.

## Конвейер с обратным давлением

Парсер логов состоит из трёх стадий: читать строки, разбирать, класть в индекс. Каждая стадия своя
задача, между ними каналы:

```
 читатель --> [ q1 ] --> разборщик --> [ q2 ] --> индексатор
```

Если индексатор медленный, а читатель быстрый, всё решает размер очередей. С `unbounded_channel` читатель
вычитает файл целиком и сложит его в память. С ограниченными каналами `send` в полной очереди ждёт, значит,
застревает разборщик, за ним читатель: **давление идёт назад по цепочке**, и память растёт не больше
суммы ёмкостей. Ёмкость в 1 или 2 для стадий обычно достаточна: её цель не буфер, а сцепка.

Закрытие идёт тоже по цепочке. Читатель закончил, выбросил свой `Sender`, разборщик видит `None` и
выходит, выбрасывая свой `Sender`, и так до конца. В обратную сторону работает ошибка `send`: если
индексатор упал, `send` разборщика вернёт `Err`, и тот должен выйти из цикла, а не продолжать,
иначе работа уйдёт в пустоту. Игнорировать ошибку отправки в стадии конвейера нельзя.

## Демультиплексор: одно соединение, много ждущих

Многие протоколы (HTTP/2, Redis с pipelining, RPC) позволяют послать много запросов подряд по одному
соединению, а ответы возвращаются в любом порядке с номером запроса. Клиенту нужно, чтобы каждая
задача получила ответ именно на свой запрос. Устройство такое:

```rust
struct Rpc {
    outbox: mpsc::Sender<Frame>,
    waiters: Arc<Mutex<HashMap<u32, oneshot::Sender<Bytes>>>>,
    counter: AtomicU32,
}
```

`call` берёт новый номер, кладёт в `waiters` отправитель `oneshot`, отправляет кадр и ждёт получателя.
Отдельная задача читает кадры с ответами, вынимает из `waiters` запись по номеру и отправляет ответ.
Замок над таблицей здесь `std::sync::Mutex`: держится на считанные строки без `.await`.

Две ловушки. **Закрытое соединение.** Когда читатель вышел, таблицу надо очистить, иначе отправители
`oneshot` продолжают жить в ней, и ждущие вызовы висят вечно: пока жив хоть один отправитель, получатель
не узнает, что ответа не будет. **Отменённый вызов.** Таймаут или `abort` обрывают `call` в `.await`, код
после ожидания не выполнится, и запись останется в таблице навсегда. Лекарство: охранник, который
знает таблицу и номер и убирает запись в `Drop` (так же, как в главе про задачи `Drop` останавливает
фоновую работу). Посмотри `demux_pending`: там видно, как запись остаётся без хозяина и как её убирает
охранник.

## Пул объектов

Когда объект дорог в создании (соединение с базой, большой буфер), его делают заранее и
одалживают. Пул это две вещи: счётчик свободных мест с ожиданием (`Semaphore`) и сами объекты
(`Mutex<Vec<T>>`).

```rust
struct BufferPool {
    free: Arc<std::sync::Mutex<Vec<Vec<u8>>>>,
    slots: Arc<Semaphore>,
}

struct Loan {
    buf: Option<Vec<u8>>,
    free: Arc<std::sync::Mutex<Vec<Vec<u8>>>>,
    _slot: OwnedSemaphorePermit,
}
```

`acquire_owned()` на `Arc<Semaphore>` возвращает `OwnedSemaphorePermit`: разрешение, которое не
заимствует семафор и поэтому может лежать в структуре. Его можно спрятать в `Loan` и вернуть на место, когда
`Loan` выбросят. Возврат делает `Drop`: он кладёт буфер обратно в список. Порядок важен: сначала
`Drop::drop` (объект вернулся), потом уничтожаются поля (разрешение отпущено). Иначе другой
ожидающий успеет получить разрешение и найти список пустым. Срок ожидания даёт `tokio::time::timeout`
вокруг `acquire_owned`; отмену он переживает без утечек: разрешение выдаёт только завершившийся `acquire`.

## Пакетирование

Писать по одной записи дорого: сетевой вызов, запись на диск. Выгоднее собрать пачку и отправить
разом. Пачка уходит, когда **набралось N штук или прошло T времени** с её начала, смотря что
раньше. Срок отсчитывается от первого элемента пачки, а не по часам: пустая пачка ничего не
ждёт, а одинокий элемент не должен ждать дольше T.

```rust
struct Batch<T> {
    items: Vec<T>,
    started: Option<Instant>,
}

impl<T> Batch<T> {
    fn deadline(&self, wait: Duration) -> Option<Instant> {
        self.started.map(|at| at + wait)
    }
}

loop {
    tokio::select! {
        msg = inbox.recv() => match msg {
            Some(item) => { /* push, при необходимости заведи started */ }
            None => { /* поток кончился */ break; }
        },
        _ = tokio::time::sleep_until(batch.deadline(wait).unwrap()), if batch.started.is_some() => {
            /* срок истёк: отправить то, что есть */
        }
    }
}
```

Условие `, if` отключает ветку таймера, пока пачка пуста. А теперь главное, на чём ошибаются
почти все: **после выхода из цикла в пачке могут лежать элементы**. Канал закрыт, а накопленное
не отправлено, и оно пропало бы вместе с функцией. Каждому пакетировщику нужен явный код «слить остаток»
на всех путях выхода. Пишут его не потому, что забывают, а потому что тест на счастливый путь
остановки не проверяет.

Второе: `tokio::time::interval` как «таймер пачки» кажется естественным, но он тикает по часам, а
не от первого элемента. Элемент, пришедший за миг до тика, уходит один; ночью пачки мельчают.

## Типичные ошибки

- `unwrap` на `reply.send(..)` в акторе: один ушедший клиент ломает всех.
- Клон `Sender` внутри самого актора: он никогда не остановится. Нужен `downgrade`.
- Охранник замка в заголовке `while let`: пул из N воркеров работает как один.
- Общая очередь там, где нужен порядок по ключу.
- Забытый оригинал `Sender` после раздачи клонов: поток не кончается.
- Неограниченный канал в середине конвейера: память растёт без предела.
- Проглоченная ошибка `send` в стадии: после ухода читателя цепочка крутится вхолостую.
- Таблица ожидания без очистки при закрытии соединения и без охранника на отмену.
- Пакетировщик, который теряет хвост при закрытии канала.
