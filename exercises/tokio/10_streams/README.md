# Стримы

Склад отдаёт заказы на проверку. Их тысячи, они приходят постепенно, и каждый надо показать
антифрод-сервису, который отвечает за 50 мс и выдерживает ровно восемь запросов одновременно. Можно
дождаться всех заказов, сложить в `Vec`, а потом проверять. Тогда память растёт вместе со складом, а
первая проверка начнётся после последнего заказа. Можно обработать по одному: тогда восемь запросов
в работе так и останутся мечтой, и тысяча заказов займёт пятьдесят секунд. Нужна трубка, из которой
заказы выходят по мере готовности, а проверка идёт сразу по восемь. Такая трубка называется `Stream`.

## Что такое Stream

`Stream` это асинхронный итератор. Итератор отвечает на `next()` значением сразу, стрим отвечает
«значения пока нет, но когда оно появится, я разбужу». По сути, у трейта один метод:

```rust
fn poll_next(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Option<Self::Item>>
```

`Ready(Some(x))` значит «вот элемент», `Ready(None)` значит «стрим кончился», `Pending` значит «пока
ничего, не забудь разбудить». Вызывать `poll_next` вручную тебе придётся редко, а использовать удобные
методы из `StreamExt`, как `Iterator`, но с `.await`. Трейт `Stream` и расширения живут в крейте
`futures` (в самом tokio их нет, они в отдельном `tokio-stream`, которого в нашем разделе нет, поэтому
мы часто будем писать мостики сами).

```rust
use futures::StreamExt;

let mut orders = stream::iter(vec!["A1", "B2", "C3"]);
while let Some(order) = orders.next().await {
    check(order).await;
}
```

Стрим ленив, как итератор. Пока никто не вызвал `next()` или терминальную операцию (`collect`, `fold`,
`for_each`), ничего не происходит: ни один элемент не запрашивается, ни одна функция в цепочке не
вызывается. Это хорошее свойство: потребитель, взявший три элемента из тысячи, платит за три. Посмотри
анимацию `stream_pull`: на ней видно, как запрос идёт от потребителя вниз по цепочке.

## Комбинаторы

Как у итераторов: `map`, `filter`, `take`, `skip`, `enumerate`, `collect`, `fold`, `chain`. Отличие
в том, что функции, которым может понадобиться ждать, возвращают future:

- `then(|x| async { ... })` применяет асинхронную функцию к каждому элементу, строго по одному.
  `map` с асинхронной функцией даст поток future, а не поток значений (это пригодится ниже).
- `filter(|x| ready(x.paid))`: замыкание возвращает future от `bool`. Для мгновенных условий
  подойдёт `std::future::ready`.
- `filter_map(|x| async { ... })` то же с `Option` внутри.
- `take(n)` перестаёт опрашивать источник после `n`-го элемента: на бесконечных потоках это основной
  способ остановиться.
- `fold(init, |acc, x| async move { ... })` свёртка с асинхронным шагом, терминальная.

Вспомни `Iterator::sum`, `max`, `count`. Для потока почти всё то же есть, а чего нет, делается
через `fold`.

### Закрепление: «cannot be unpinned»

Метод `next()` требует, чтобы стрим был `Unpin` (его можно двигать по памяти). Стрим из `iter` такой.
Стрим из `then`, `unfold`, `filter` с асинхронным замыканием обычно нет: он хранит внутри асинхронные
блоки, а те могут держать ссылки на себя же и после первого опроса двигаться не вправе. Компилятор
сообщает об этом так: «the trait bound `...` cannot be unpinned». Чинится закреплением:

```rust
use std::pin::pin;

let checked = stream::iter(ids).then(|id| async move { fetch(id).await });
let mut checked = pin!(checked);
while let Some(row) = checked.next().await { /* ... */ }
```

`pin!` закрепляет значение на стеке (получается `Pin<&mut T>`), `Box::pin(..)` в куче, а
`.boxed()` из `StreamExt` делает то же и стирает тип. Нужно закрепление только когда стрим читают
через `next()` вручную или кладут в коллекцию. Терминальные операции (`collect`, `fold`) забирают
стрим целиком и закрепляют сами.

## Ограниченная параллельность

Вернёмся к складу. Обработка по одному слишком медленна, а «все сразу» (то, что делает `join_all`
над тысячей future) положит антифрод. Нужно «не больше восьми одновременно». Это делают два
комбинатора, которые принимают стрим *future* и держат в работе окно из `n` штук:

```rust
let verdicts: Vec<Verdict> = orders
    .map(|order| fraud.check(order))   // поток future, ещё не запущенных
    .buffered(8)                        // окно из восьми, порядок как на входе
    .collect()
    .await;
```

- `buffered(n)` выдаёт результаты **в порядке входа**.
- `buffer_unordered(n)` выдаёт **по мере готовности**.

Разница не только в порядке, но и во времени. Если готов результат третьего задания, а первое
ещё идёт, `buffered` держит третий результат у себя, пока первый не выйдет, и он занимает место в окне:
новая работа не стартует. На заданиях разной длины это заметная потеря, поэтому, если порядок
не нужен, бери `buffer_unordered`. Когда порядок нужен, `buffered` проще, чем сортировать потом.

`join_all` над большим списком создаёт и запускает всё сразу: ни лимита, ни экономии памяти.
Поток с окном лучше и тем, что future создаётся лениво, прямо перед запуском. Есть и родственник
`for_each_concurrent(limit, f)`, когда результаты не нужны, а важен только эффект.

## Результаты и ошибки: TryStream

Если элементы стрима `Result<T, E>`, пригодится `TryStreamExt`. Он делает для потока то, что `?`
делает для функции:

- `try_next().await?` возвращает `Option<T>` и сам пробрасывает ошибку, поэтому цикл
  `while let Some(x) = s.try_next().await?` читается как обычный.
- `try_collect()` собирает `Ok`-значения в коллекцию или останавливается на первой ошибке.
- `map_ok`, `try_filter`, `try_fold` работают только с `Ok`, а `Err` пропускают.
- `try_flatten()` разворачивает поток, элементы которого сами стримы-`Result`.

Остановка на первой ошибке важна по существу: пока ты не вернулся к источнику, он не тянется. Если
сначала собрать всё в `Vec<Result<..>>`, а потом искать ошибку, источник будет вычитан до конца
зря. Выборки из баз данных (sqlx, scylla в разделе data) приходят ровно как такие потоки.

## unfold: поток из состояния

Иногда следующий элемент вычисляется из предыдущего состояния, и вычисление асинхронное.
`stream::unfold(состояние, |состояние| async { ... })` строит поток из такой функции: она получает
состояние, а возвращает `Some((элемент, новое_состояние))` или `None`, чтобы закончить. Пример
попроще склада: числа Фибоначчи, пока не превысят заданный предел.

```rust
let fib = stream::unfold((0u64, 1u64), |(a, b)| async move {
    if a > 1000 { None } else { Some((a, (b, a + b))) }
});
```

Состояние здесь пара чисел, и оно обязательно уходит в замыкание *по значению* и возвращается
обновлённым. Ровно так делают постраничную загрузку: состоянием служит курсор следующей страницы,
шаг запрашивает страницу и возвращает «её элементы и новый курсор». Конец потока это момент, когда
замыкание вернуло `None`. Следи за ошибками: если на ошибке замыкание вернуло `Some` с прежним
состоянием, поток будет бесконечно повторять одну и ту же попытку.

Страницы потом удобно развернуть в плоский поток: `map_ok` превращает страницу в поток элементов, а
`try_flatten` склеивает их. Лень сохраняется: следующая страница не запрашивается, пока не прочитан
хвост предыдущей.

## Канал как Stream

У приёмника канала `mpsc::Receiver` есть `recv().await`, а потоком он не является. Мостик делается
двумя способами. Либо готовым `unfold`: состояние это сам приёмник, шаг делает `recv`. Либо руками,
через `poll_recv`:

```rust
impl Stream for Inbox {
    type Item = Letter;
    fn poll_next(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Option<Letter>> {
        self.rx.poll_recv(cx)
    }
}
```

`poll_recv` возвращает то же самое `Poll<Option<T>>`, поэтому мостик тонкий.

## Свой Stream и обещание Waker

В `poll_next` нельзя писать `.await`: это обычная функция, которая обязана вернуть `Poll` сразу.
Вместо ожидания ты опрашиваешь нижние уровни тем же `cx`: `interval.poll_tick(cx)`,
`rx.poll_recv(cx)`, `reader.poll_read(cx, ..)`. Если вернуть их `Pending`, пробуждение уже
зарегистрировано внутри них, и дело сделано.

Если у тебя нет нижнего уровня, а ожидание своё (например, поток ждёт, пока другой поток положит
элемент в общую очередь), действует контракт: вернув `Pending`, ты обязан позаботиться о том, чтобы
тебя опросили ещё раз. То есть сохранить `cx.waker().clone()` в общем месте, откуда его вызовет
(`wake()`) тот, кто положит новый элемент. Забыл, и стрим молча зависнет: ни паники, ни ошибки, просто
никто не придёт. Рантайм опрашивает future только после пробуждения.

Не лечи это вызовом `cx.waker().wake_by_ref()` перед `Pending`: стрим будет опрашиваться без пауз,
жечь процессор и не пускать других на тот же поток (в тесте с замороженным временем он вообще не
даст времени пойти).

## Слияние и пачки

Склеить несколько потоков в один можно по-разному:

- `chain(a, b)`: сначала весь первый, потом весь второй.
- `select(a, b)`: что готово раньше, то и выдаётся; заканчивается, когда кончились оба.
- `select_all(коллекция)`: то же для многих. Требует, чтобы каждый стрим был `Unpin`: стрим из
  `unfold` для этого придётся упаковать (`.boxed()`).
- `zip`: пары, до первого конца.

Пачки: `chunks(n)` копит ровно `n` (на конце потока выдаёт остаток) и ждёт, сколько понадобится.
`ready_chunks(n)` отдаёт то, что готово прямо сейчас, до `n`, и не ждёт недостающего. Первый
для выгрузки, где данные придут всё равно, второй для живого потока, где пачка не должна стареть.

## Лень и отмена

Стрим ленив с двух сторон. Пока его не опрашивают, он не работает. Когда его бросили (`drop`), он
перестаёт существовать вместе со всеми future внутри. Это значит, что остановка потребителя останавливает
источник, если источник *часть* стрима (цепочка комбинаторов). Если же источник это отдельная
задача (`tokio::spawn`), которая пишет в канал, то она о потребителе ничего не знает. Единственный
способ узнать это ошибка `send`: приёмник уничтожен, значит, читать больше некому. Производитель
обязан проверять результат `send` и выходить. Игнорируешь его (`let _ = tx.send(..)`), получаешь
задачу, которая крутится вечно: на каждую брошенную подписку по одной.

## Типичные ошибки

- Забыт `use futures::StreamExt`: метода `next` нет.
- `.next()` на стриме из `then` или `unfold` без закрепления (`cannot be unpinned`).
- `then` вместо `map` плюс `buffered`: работает, но по одному.
- `join_all` вместо окна: нет лимита, память и нагрузка растут вместе с данными.
- `buffered`, когда порядок не нужен, и один медленный результат держит всех.
- Сбор `Vec<Result<..>>` вместо `try_collect`: источник вычитывается до конца после первой ошибки.
- В `unfold` на ошибке состояние осталось прежним: поток не кончается.
- `Pending` без сохранённого `Waker`: тихое зависание. `wake_by_ref` перед `Pending`: пустая трата процессора.
- Производитель в `spawn` игнорирует ошибку `send`: утечка задач.
- Вычисления сделаны до `stream::iter`, а не внутри комбинатора: лень потеряна.
