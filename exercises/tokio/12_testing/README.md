# Тестирование async-кода

Тест на таймер проходит у тебя и падает в CI раз из двадцати. Тест на очередь заданий висит на
чужом ноутбуке. Тест на «отмену» зелёный, а в продакшене после таймаута деньги пропадают. Общая
причина одна: конкурентный код зависит от времени, порядка и числа потоков, а тест их не
контролирует. Хороший тест async-кода не ждёт и не надеется, а строит ситуацию сам: останавливает
время, открывает и закрывает ворота у зависимостей, отменяет в нужный момент и проверяет состояние
между шагами. Основы `#[tokio::test]` и замороженного времени были в главах про рантайм и время,
фейки через трейты в разделе про Rust вглубь. Здесь то, что нужно именно конкурентному коду.

## Какой рантайм у теста

`#[tokio::test]` по умолчанию собирает `current_thread`: один поток, задачи переключаются только на
`.await`. Это удобно (детерминированно) и опасно одновременно.

- Гонки между потоками на таком рантайме не воспроизводятся. Код вида «прочитал атомик, подумал,
  записал» не разъедется никогда, потому что между чтением и записью нет `.await`. Тест зелёный,
  а в продакшене на многих потоках теряются обновления.
- `block_in_place` на нём паникует: он существует только для `multi_thread`.
- Зато тесты быстрые и повторяемые, поэтому `current_thread` остаётся выбором по умолчанию.

Для проверки параллельного кода просят многопоточный рантайм явно:

```rust
#[tokio::test(flavor = "multi_thread", worker_threads = 4)]
async fn limiter_is_safe_under_contention() { /* ... */ }
```

Число воркеров указывают всегда: без него берётся число ядер, и результат зависит от машины. С
одним воркером параллелизма нет, как и на `current_thread`.

## Замороженное время и его границы

С `start_paused = true` часы стоят, а рантайм прыгает вперёд на ближайший таймер, когда ему больше
нечего делать. Тест на таймаут в десять минут проходит за миллисекунды, а все замеры через
`tokio::time::Instant` точны. Три важных следствия.

**Перемотка срабатывает, когда рантайм простаивает.** «Простаивает» значит «у меня нет ни готовых
задач, ни событий», а не «ничего не происходит». Поэтому ожидание блокирующей работы
(`spawn_blocking`, внешний процесс, поток) выглядит для рантайма как простой, и часы прыгают к
ближайшему таймеру, не дожидаясь настоящей работы. `timeout` вокруг такого вызова срабатывает
мгновенно. Для всего, что идёт по настоящему времени, паузу выключают (или такие вызовы подменяют
асинхронной заглушкой).

**Блокировка не двигает замороженные часы.** `std::thread::sleep` в таком тесте задерживает тест в
реальности, но `Instant` этого не заметит.

**Время двигают вручную и в цепочке задач ждут.** `tokio::time::advance(d)` сдвигает часы на `d` и
один раз отдаёт ход, чтобы сработавшие таймеры успели разбудить задачи. Но если одна задача будит
другую, а та третью, одного хода мало. Тест, который проверяет состояние между шагами, должен
сначала дать цепочке дойти до конца. Для этого пишут вспомогательную функцию: она много раз
отдаёт ход рантайму (`yield_now` в цикле) и не трогает часы. После каждого `advance` её
вызывают, и только тогда смотрят на состояние.

```rust
async fn quiesce() {
    for _ in 0..50 {
        tokio::task::yield_now().await;
    }
}
```

Точное число зависит от длины самой длинной цепочки; берут с запасом.

## Фейки, которыми управляет тест

Зависимость (база, сеть, соседний сервис) в тесте заменяют. Для конкурентного кода мало фейка,
который «отвечает сразу». Нужны два других вида.

**Фейк с воротами.** Вызов фейка не отвечает, пока тест не откроет ворота. Внутри обычно одноразовый
канал `oneshot`: вызов оставляет в общей таблице пометку «я жду» и ждёт приёмника, а тест командой
`release` отправляет значение. Это позволяет проверить промежуточное состояние («пока зависимость
думает, второй запрос присоединился к первому, вызовов один») и потом довести дело до конца.

```rust
let door = Door::new();                       // фейк с воротами
let pending = tokio::spawn(service.fetch("k")); // запрос повис на воротах
settle().await;
assert_eq!(door.waiting("k"), 1);             // зависимость вызвана и держится
door.open("k", "значение");                   // теперь она отвечает
```

**Сценарный фейк.** Заранее записано, что ответит n-й вызов: успех, ошибка, ответ с задержкой.
Так проверяют повторные попытки, отступы, таймауты: «первые два раза ошибка, на третий успех, между
попытками ровно столько-то». Хороший сценарный фейк считает вызовы и громко ругается на лишний:
иначе сервис молча сделал вызов, которого автор теста не ждал. Сам фейк тоже код, и в нём бывают
баги (порядок шагов, счёт вызовов), поэтому его проверяют отдельным тестом. Если тест красный, а
логика сервиса выглядит верной, проверь сначала фейк.

## Проверка отмены

Любой `.await` это точка, где future можно выбросить: `timeout`, `select!`, `abort` делают это
каждый день. Если операция меняет состояние до `.await` и добивает после, отмена посередине
оставляет половину. Чтобы поймать это, тест должен отменять операцию в разные моменты, а не только
доводить до конца. С замороженным временем это просто: прогоняют отмену по сетке времён, и на каждой
точке проверяют **инвариант**, который верен и при отмене, и при успехе («сумма не изменилась»,
«заказ либо оплачен целиком, либо не тронут»).

```rust
for cut in 0..=20 {
    let shelf = Shelf::with(10);
    let _ = timeout(Duration::from_millis(cut), shelf.reserve(4)).await;
    let (free, held) = shelf.counts();
    assert_eq!(free + held, 10, "отмена на {cut} мс потеряла товар");
}
```

Лечится такая ошибка в самом коде: всё, что меняет состояние, делается между последним `.await` и
концом (без точек отмены внутри) или защищается охранником, который откатывает в `Drop`.

## Диалог с сокетом: tokio::io::duplex

`duplex(n)` даёт пару соединённых потоков в памяти: что записал в один, читается из другого. `n`
это размер буфера каждого направления. Маленький `n` намеренно: он выявляет код, который молча
рассчитывает, что всё поместится. Главное правило сценарного теста: клиент пишет и читает
**одновременно**. Версия «отправить все команды, потом прочитать все ответы» работает, пока обе
стороны помещаются в буферы. Как только сервер на пишущем клиенте заполнил свой буфер ответов,
он перестаёт читать команды, клиент перестаёт писать, и оба стоят. Лечится разделением потока
(`tokio::io::split`) и совместным выполнением записи и чтения (`join!`) или отдельной задачей
под запись. Сам сценарий сверяют стенограммой: список «отправил, ожидаю» целиком, включая конец
соединения после прощания, и оборачивают в `timeout`, чтобы зависший обмен падал с понятным
сообщением.

## Тесты на утечку задач

У рантайма есть счётчик живых задач (`Handle::current().metrics().num_alive_tasks()`). Тест на
утечку измеряет его до сценария и после и сравнивает с нулём разницы. Две ловушки. Нужна точка
отсчёта: в рантайме могут жить чужие задачи. И нужна пауза на хвосты: у исправного кода после
закрытия канала задача ещё допишет последнее, и если смотреть сразу, будет ложная тревога. Под
замороженным временем пауза ничего не стоит, поэтому подожди с запасом.

## Стресс-тесты гонок

Гонку по определению воспроизводит только параллелизм, и то не каждый раз. Три приёма делают её
воспроизводимой:

1. Рантайм `multi_thread` с несколькими воркерами.
2. Выравнивание старта: `tokio::sync::Barrier` держит все задачи у линии, пока последняя не
   подошла, и отпускает разом. Без него первая успевает закончить раньше второй.
3. Много повторов, каждый на свежем состоянии. Шанс попасть в щель за один раунд мал, за
   несколько сотен близок к единице.

Число раундов подбирают замером, а не наугад: на сломанной версии тест должен падать подряд много
раз, на исправной не падать ни разу. Тест, который ловит гонку в девяти запусках из десяти, хуже
отсутствия теста: он приучает игнорировать красный цвет.

## Тест, который проверяет тест

Зелёный тест не доказывает, что он что-то проверяет. Проверка проста: сломай код нарочно (мутант) и
посмотри, станет ли тест красным. Если нет, тест слеп к этой ошибке. Мутанты бывают механические
(заменить `>=` на `>`, убрать вызов) и осмысленные (потерять последнюю пачку при остановке,
перепутать порядок). В этой главе так устроены почти все задачи: рядом с исправной версией лежат
несколько сломанных, и тест должен проходить на первой и падать на каждой из остальных. Проект
главы устроен так же, только тесты пишешь ты с нуля.

## Типичные ошибки

- Гонка проверяется на `current_thread`: тест зелёный всегда.
- Таймаут вокруг `spawn_blocking` под замороженным временем срабатывает мгновенно.
- Состояние проверяется сразу после `advance`, не дав цепочке задач дойти до конца.
- Фейк «отвечает сразу»: не проверить промежуточные состояния и порядок событий.
- Тест проверяет только полное завершение и никогда не отменяет операцию.
- Сценарий клиента пишет всё, потом читает всё: зависает на маленьком буфере.
- Сравнение числа живых задач без точки отсчёта и без паузы на хвосты.
- Стресс-тест без `Barrier` или с одним раундом: «зелёный» ничего не значит.
- Тест ни разу не проверен на сломанной версии кода.
