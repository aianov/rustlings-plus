# Тесты для сервиса уведомлений

Код пишет кто-то другой, тесты пишешь ты. Сервис `notifier` собирает уведомления в дайджесты и
отправляет их пачками. В нём спрятано восемь поломок, каждая включается своей фичей Cargo
(`bug_*` в `crates/notifier/Cargo.toml`). Приёмка запускает твои тесты на исправном сервисе, они
должны проходить, а потом на каждой из восьми сломанных версий, и на каждой они обязаны падать.

Исходники сервиса менять нельзя, а читать сломанные куски (`#[cfg(feature = "bug_...")]`) значит
подсматривать ответ. Тесты должны отлавливать симптомы из ТЗ, а не знание кода.

## Что уже есть

```
tt_mutants/
  Cargo.toml
  crates/
    notifier/
      Cargo.toml                 фичи bug_*, зависимости (менять нельзя)
      src/lib.rs                 сервис (менять нельзя)
      tests/student.rs           твои тесты (пишешь ты)
    acceptance/
      tests/acceptance.rs        приёмка (менять нельзя)
```

## Как устроен сервис

Каждому пользователю копится свой дайджест: список текстов в порядке прихода. `Notifier::start(sink,
config)` запускает фонового актора и возвращает `Notifier` (дешёвый для копирования доступ) и
`Runner` (владелец актора). Готовые дайджесты уходят в `Sink::deliver(user, texts)`; для тестов есть
готовый `Recorder`, он запоминает всё, что доставлено (`deliveries()`).

## Требования (то, что сервис обязан делать)

1. **Слияние.** Уведомления одного пользователя в одном окне идут одним дайджестом, все, в
   порядке прихода.
2. **Окно.** Окно длится `window` с момента первого уведомления дайджеста. Новые записи окно не
   продлевают. Когда окно закрылось, дайджест уходит ровно один раз.
3. **Лимит.** Когда в дайджесте набралось `max` записей, он уходит сразу, не дожидаясь окна. Следующее
   уведомление открывает новое окно.
4. **Независимость.** Пользователи не влияют друг на друга: у каждого своё окно.
5. **Заглушение.** `mute(user)` отбрасывает накопленный дайджест и все новые уведомления пользователя,
   `unmute(user)` включает приём снова.
6. **Остановка.** `Runner::finish().await` сразу доставляет всё накопленное (не дожидаясь окон), по
   возрастанию номеров пользователей, и завершает актора. Ждать окна при остановке нельзя.
7. **После остановки.** `notify`, `mute` и другие методы возвращают `Err(Closed)`.
8. **Состояние.** После доставки сервис не хранит ничего о пользователе: `tracked_users()` считает
   пользователей с открытым дайджестом.

## Что нужно сделать

Напиши в `crates/notifier/tests/student.rs` тесты. Рекомендации:

- Время заморозь: `#[tokio::test(start_paused = true)]`, двигай часы `tokio::time::advance`. Тогда
  границы точны, а тесты мгновенны.
- После каждого действия дай актору обработать команду (вспомни `settle` из главы). Иначе ты проверяешь
  состояние, которого ещё нет.
- Один тест проверяет одну вещь. Тест, который проверяет всё сразу, при падении ничего не объясняет.
- Проверяй границы с обеих сторон: за миг до срока (ничего нет) и ровно в срок (есть).

## Критерии приёмки

`cargo test --workspace` в корне проекта. Приёмка запускает `cargo test -p notifier --test student`
без фичей (должен пройти, тестов не меньше шести) и с каждой из восьми фичей (обязан упасть именно
на тестах, а не на компиляции и не зависнуть). Время жизни одного прогона ограничено пятью
минутами. Первый запуск медленный: cargo собирает восемь вариантов.

Список поломок, которые ты ловишь (по симптомам): вторая запись затирает первую; запись отодвигает
закрытие окна; дайджест вмещает лишнюю запись; накопленное пропадает при остановке; после `mute`
уходит накопленное; порядок записей нарушен; состояние пользователя остаётся после доставки;
после остановки `notify` отвечает успехом.

## Что вспомнить из главы

Замороженное время и `advance`, `settle`, пошаговая проверка состояния (tt3), проверка отмены и
границ (tt6), проверка, что тест ловит мутанта (все задачи главы).
