# Отмена и остановка

Игровой сервер принимает игроков, ведёт матчи, раз в секунду сбрасывает счёт на диск и каждые пять
минут чистит устаревшие сессии. Работает неделями. Потом приходит релиз, и процесс надо
перезапустить. Если просто убить его, матчи оборвутся на середине, счёт последней секунды потеряется,
а игрок, выигравший партию, не получит награду. Нужна остановка по правилам: перестать принимать новых,
дать матчам доиграть, записать счёт, выйти. А если один матч завис, не ждать его вечно.

Запустить задачу в tokio проще простого. Остановить её так, чтобы ничего не потерялось, и ничего
не осталось висеть, нужно несколько механизмов. В готовом крейте `tokio-util` они есть (токен отмены,
учёт задач), но у нас его нет, и мы напишем всё сами. Это не упражнение ради упражнения: как только
напишешь свой токен, больше никогда не удивишься тому, как он устроен.

## Токен отмены

Сигнал «останавливаемся» должен дойти до многих задач, быть значением (клонируется, раздаётся) и
не терять событие, если слушатель пришёл поздно. Самое подходящее устройство для этого канал `watch`:
у него есть текущее значение, а не только события.

Токен получается из `Arc<watch::Sender<bool>>`: клонируется `Arc`, «пустой» сигнал это `false`.
Подать сигнал значит записать `true`, ждать сигнала значит подписаться и дождаться значения `true`.

Две вещи, на которые стоит смотреть внимательно. Во-первых, `wait_for` сначала смотрит на текущее
значение: слушатель, пришедший после сигнала, не зависнет. Это главное отличие от `Notify`, где
сигнал, посланный до подписки, пропадает (вспомни главу про синхронизацию). Метод называется
`Receiver::wait_for(|on| *on)`. Во-вторых, запись значения: обычный `send` у `watch` ничего не
записывает, когда получателей нет, и сигнал «стоп» до первого слушателя был бы потерян, а
`send_replace` записывает всегда.

Использовать такой токен удобно в `select!`:

```rust
loop {
    tokio::select! {
        biased;
        _ = stop.fired() => break,
        Some(order) = queue.recv() => cook(order).await,
    }
}
```

Приоритет (`biased;`) нужен затем, что сигнал не должен проигрывать забитой очереди. Это та же мысль,
что в главе про `select!`.

### Дерево токенов

Один токен на всё приложение это слишком грубо: иногда нужно остановить только часть. Тогда токены
собирают в дерево: у каждой подсистемы свой токен-ребёнок от общего корня. Сигнал идёт вниз
(отменили корень, значит, и все дети), но не вверх и не вбок. Реализовать это можно по-разному.
Можно повесить на родителя фоновую задачу, которая отменит ребёнка. Но она нужна на каждого ребёнка, и
`is_cancelled` ребёнка отстаёт на один поворот планировщика. Надёжнее хранить в ребёнке не только свой
сигнал, но и сигналы предков, и спрашивать всех. Тогда `is_cancelled` отвечает мгновенно, а `cancelled()`
ждёт, пока сработает любой из них.

## Учёт задач

Остановить сервис красиво значит дождаться всех его задач. Хранить для этого все `JoinHandle`
неудобно: задачи запускают задачи, обработчик соединения запускает чтение и запись. Вместо этого
считают живых: учёт задач (`TaskTracker` в `tokio-util`) увеличивает счётчик на запуске и уменьшает на
конце, а `wait` ждёт нуль.

Читая такие реализации, смотри на два места:

- **Когда растёт счётчик.** До `tokio::spawn`, в вызывающем коде. Если считать внутри самой задачи,
  между запуском и первым опросом есть щель, и `wait` в этот момент увидит нуль и вернётся, хотя задача
  вот-вот начнётся.
- **Кто убавляет.** Не код в конце задачи, а `Drop` небольшого охранника, который в задачу
  переносят. Код после `.await` не выполнится при панике и при `abort`, а `Drop` локальных переменных
  выполняется всегда.

Ждать нуль удобно на том же `watch`: `send_modify` меняет число, `wait_for(|n| *n == 0)` засыпает до нуля.

## Корректная остановка

У остановки две фазы, и их легко перепутать:

```
сигнал "стоп"  ──► перестали принимать новое ──► доделали взятое ──► вышли
                   (выход из цикла accept)        (tracker.wait())
```

Цикл приёма (`accept`, чтение очереди) выходит по токену. Всё, что уже взято в работу, живёт в отдельных
задачах и продолжает идти. После цикла сервер ждёт учёт задач и только тогда возвращается. Если вернуться
сразу после цикла, функция скажет «остановился», а задачи ещё будут работать без присмотра. Клиенты
получат «принято» и не получат результата.

Что делать с заданиями, которые лежат в очереди и ещё не взяты? Решать хозяину очереди: оставить для
следующего запуска, вернуть клиентам отказ, дописать в журнал. Остановка не должна молча выбрасывать их.

### Дедлайн и принудительная остановка

Вежливые задачи слушают токен. Невежливые бывают всегда: чужой код, забытая проверка, зависшая операция.
Остановка, у которой нет срока, однажды повиснет. Поэтому ждут не бесконечно, а до дедлайна, а потом
останавливают оставшиеся силой. Для этого задачи удобно держать в `JoinSet`:

```rust
let limit = Instant::now() + deadline;
while let Ok(Some(_)) = timeout_at(limit, matches.join_next()).await {}
matches.abort_all();
while matches.join_next().await.is_some() {}
```

Срок один на всех: момент (`limit`) вычисляют один раз, а не дают по таймеру на каждое ожидание.
Но смотри на последнюю строку: `abort_all` только ставит пометку, а задача уничтожится там, где
она сейчас ждёт на `.await`. Чтобы быть уверенным, что к моменту возврата все `Drop` выполнены,
`join_next` дочитывают до конца. И запомни главное ограничение: `abort` берёт только задачи с точками
`.await`. Цикл без единого `.await` и блокирующий поток им не остановить. Посмотри `graceful_shutdown`:
там видно обе фазы и дедлайн.

### Порядок остановки

Части сервиса связаны потоком данных: один порождает, другой обрабатывает, третий записывает. Остановка
идёт **по течению**: сначала источник (чтобы не рождалась новая работа), затем обработчики (они
доедают очереди и выходят, когда очередь закрылась и пуста), в самом конце приёмники (журнал, актор).
Остановить всё одним махом значит потерять то, что лежало в очередях между частями. Обработчику
отдельный токен часто не нужен: ему достаточно, чтобы закрылась его входная очередь, а это следствие
остановки источника.

Если приёмнику пишут и другие части, он сам не закроется (его очередь жива, пока жив хоть один
отправитель). Тогда ему нужен собственный токен, и отменять его надо только после того, как
закончили все, кто ему пишет, а перед выходом он должен дочитать то, что лежит в очереди.

## Супервизор

Фоновая задача иногда падает. Бросить её навсегда нельзя, но и перезапускать мгновенно и без
конца тоже: вечно падающая задача жжёт процессор и заваливает журнал. Нужен надзиратель, который:

- запускает задачу через `tokio::spawn` (паника тогда становится `Err(JoinError)` у `JoinHandle`, а не
  падением самого надзирателя);
- после падения ждёт паузу и запускает заново, но не больше N раз;
- слушает токен остановки **и** во время работы, **и** во время паузы.

Здесь живёт ловушка, которую знают все, кто писал надзирателей: выброшенный `JoinHandle` задачу не
останавливает, а лишь отпускает. Если надзиратель вышел по токену, не вызвав `abort()` у ребёнка, ребёнок
остаётся работать сиротой. Остановка ребёнка всегда явная: `abort()` и дождаться.

## В Drop нельзя ждать

`Drop::drop` обычная синхронная функция. Внутри неё нет `.await`, а блокирующее ожидание в рантайме
либо паникует (`block_on` внутри рантайма говорит «Cannot start a runtime from within a runtime»),
либо вешает поток, который нужен самому рантайму. Но при этом хочется, чтобы забытое закрытие не
теряло данные. Выход один: разделить работу. Основной путь это явный асинхронный `close().await`,
который делает всё как положено. Запасной путь в `Drop` ничего не ждёт: он передаёт данные
фоновой задаче через канал без ограничения (его `send` синхронный) и выходит.

```rust
impl Drop for Archive {
    fn drop(&mut self) {
        if !self.pending.is_empty() {
            let _ = self.rescue.send(std::mem::take(&mut self.pending));
        }
    }
}
```

Две детали. После `close` буфер должен быть пуст (его забрали), иначе `Drop` запишет то же самое
второй раз. И ошибка `send` в `Drop` не повод паниковать: если фоновой задачи уже нет, то, скорее
всего, рантайм закрывается, и потерять приходится молча.

## Типичные ошибки

- Остановка вернулась сразу после выхода из цикла, не дождавшись взятых задач.
- Счётчик задач растёт внутри самой задачи, а убавляется в конце кода вместо `Drop`.
- Сигнал отмены через `Notify` или `send` у `watch` без получателей: отмена до подписки пропала.
- Токен слушают только в ожидании работы, но не в паузе между попытками.
- Остановка всех частей разом: очереди между ними теряют данные.
- Выброшенный `JoinHandle` принят за остановку задачи.
- `abort_all` без дочитывания `join_next`: задачи ещё живы, а функция уже вернулась.
- Цикл без `.await` или блокирующая работа в задаче, которую собираются останавливать через `abort`.
- `block_on` или `.await` в `Drop`.
