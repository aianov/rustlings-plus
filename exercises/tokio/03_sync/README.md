# Синхронизация

Под постом двадцать человек одновременно ставят лайк. Каждый запрос выполняется в своей
задаче, счётчик один на всех. Если каждая задача прочитает «41», прибавит единицу и запишет
«42», лайков окажется не двадцать, а один. Общее состояние требует правил, и в async у этих
правил есть две особенности, которых нет в обычных потоках: задачи могут переключаться в
точках `.await`, а `Future` обязан оставаться `Send`.

Каналы, то есть передачу данных вместо разделения, разберём в следующей главе. Здесь замки,
лимиты, ожидание условий и ленивая инициализация.

## std Mutex или tokio Mutex

Звучит так, будто в async нужен «async-мьютекс». Нет: по умолчанию бери обычный
`std::sync::Mutex`.

```rust
let likes = Arc::new(Mutex::new(0u32));
// в каждой задаче:
*likes.lock().unwrap() += 1;     // короткая секция, внутри нет .await
```

Замок std блокирует поток, но если держать его микросекунды и не ждать ничего внутри,
блокировка незаметна и быстрее, чем у асинхронного. Правило: **всё медленное и всё с `.await`
делается до или после замка, а не внутри.**

`tokio::sync::Mutex` нужен, когда замок приходится держать через `.await` (например, пока
идёт запись в сокет, чтобы сообщения разных задач не перемешались). У него `lock().await`,
ожидающие встают в очередь без блокировки потока, а guard `Send`. Платишь скоростью и тем,
что все ждущие стоят, пока замок держат.

```rust
let guard = queue.lock().await;           // tokio::sync::Mutex
send_all(&guard).await;                   // держим замок через .await: можно
```

Для spawn есть `lock_owned()` у `Arc<Mutex<T>>`: он возвращает `OwnedMutexGuard` без
заимствования, который можно унести в задачу через `move`.

## Guard через .await и Send

Guard от `std::sync::Mutex` не `Send`. Всё, что живёт через `.await`, становится частью
состояния `Future`, поэтому такой код не отправить в `tokio::spawn`:

```rust
let mut jobs = queue.lock().unwrap();
let job = jobs.pop();
print_label(&job).await;          // jobs ещё жив: future не Send
```

Компилятор скажет «future cannot be sent between threads safely» и покажет, какая переменная
доживает до какого `.await`. Лечение всегда одно: сузить область жизни guard.

```rust
let job = queue.lock().unwrap().pop();    // guard умер на точке с запятой
print_label(&job).await;
```

### Спрятанный guard

Опаснее явного случай, когда guard создан во временном значении и ты его не видишь.
Временные значения живут до конца выражения, а у `match` и `if let` это конец всей
конструкции со всеми ветками:

```rust
match queue.lock().unwrap().pop() {      // guard живёт до закрывающей скобки match
    Some(job) => run(job).await,          // ...и через этот .await тоже
    None => {}
}
```

То же верно для `while let`. Обычный `if` с условием безопасен: условие вычисляется отдельно,
и guard умирает до входа в блок. Лекарство от остального прежнее: сначала `let` с
результатом, потом ветвление по нему. И ещё одно следствие: с tokio-замком в такой ситуации
Send не страдает, зато повторный `lock()` внутри ветки того же замка даст дедлок.

## Цена замка на медленной операции

Замок через долгий `.await` делает очередь из всех, кому нужны те же данные:

```
задача A: lock ----------- долгий .await (200 мс) ----------- unlock
задача B:       lock? ждёт.........................................  lock
задача C:       lock? ждёт..........................................
```

Анимация `mutex_await` показывает это. Правило: под замком забираем копию или значение,
замок отпускаем, долгую работу делаем над копией. Копия почти всегда дешевле очереди.

## RwLock

Если данные читают часто, а меняют редко, `RwLock` пускает читателей параллельно:

```rust
let table = RwLock::new(prices);
let p = table.read().await;        // читателей сколько угодно
let mut w = table.write().await;   // писатель один и без читателей
```

Замок tokio справедливый: пока писатель ждёт, новые читатели встают в очередь за ним.
Побочный эффект: если читатель, не отпуская `read()`, просит `read()` ещё раз, а между ними
встал писатель, оба застрянут.

## Semaphore: лимит

`Semaphore::new(n)` это n свободных мест. `acquire().await` берёт место (или ждёт), а когда
`SemaphorePermit` умирает, место возвращается. Возврат лежит в `Drop`, поэтому его нельзя
забыть, даже при панике и отмене.

```rust
let gate = Arc::new(Semaphore::new(5));
let _seat = gate.acquire().await.unwrap();   // имя с подчёркиванием, а не просто `_`; Err бывает,
                                              // только если семафор закрыли методом close()
upload(file).await;                           // не больше 5 одновременно
```

Голое `_` дропнуло бы разрешение немедленно. Если место должно уехать в `spawn`, берут
`gate.clone().acquire_owned().await` (`OwnedSemaphorePermit` без заимствования). Если брать
место не внутри задачи, а в цикле, до spawn, цикл сам притормаживает, и не получится десять
тысяч задач в памяти. Это называется обратным давлением.

## Notify: разбудить задачу

`Notify` это сигнал «что-то случилось», без данных.

- `notify_one()` будит одну ждущую задачу, а если ждущих нет, **запоминает одно** разрешение
  для того, кто придёт следующим. Два вызова подряд всё равно одно разрешение.
- `notify_waiters()` будит всех, кто ждёт прямо сейчас, и **ничего не запоминает**.

Отсюда потерянное пробуждение: `notify_waiters` позвали раньше, чем кто-то начал ждать, и
задача заснёт навсегда. Анимация `notify_lost` разыгрывает эту гонку.

Правильный шаблон ожидания условия не полагается на сигнал как на единственный источник
правды. Состояние хранится отдельно (флаг, очередь), а Notify только будит:

```rust
loop {
    let notified = signal.notified();          // создали ДО проверки
    if state_is_ready() { return; }
    notified.await;                            // любое пробуждение после создания не пропадёт
}
```

`Notified`, созданный до вызова `notify_waiters`, получит сигнал, даже если его ещё не
опрашивали. Цикл нужен, потому что проснуться можно впустую: условие успел забрать другой.

## OnceCell: один раз и лениво

```rust
let cell = OnceCell::new();
let client = cell.get_or_init(|| async { Client::connect().await }).await;
```

Двадцать параллельных вызовов запустят инициализацию ровно один раз, остальные подождут и
получат тот же результат. `get_or_try_init` принимает инициализатор, который может упасть:
при ошибке ячейка остаётся пустой, и следующий вызов пробует снова. Ручная версия «проверил
пусто, создал, положил» гонится: все двадцать увидят пусто разом.

## Шардирование

Один замок на огромную карту это узкое горлышко, даже если задачи трогают разные ключи.
Разбей карту на части, у каждой свой замок, и выбирай часть по хешу ключа:

```
ключ -> хеш % N -> шард (свой Mutex)
          0: [ k1, k9 ]   1: [ k2 ]   2: [ k3, k7 ]   ...
```

Обновления в разных шардах идут одновременно, в одном по очереди. Число шардов берут с
запасом относительно числа потоков (16, 64). Хеш нужен хороший: плохой собирает ключи в
одном шарде, и выигрыша нет. Голый `key % N` для ключей с шагом (скажем, кратных 64 при 16 шардах)
кладёт всё в один шард. Хеш берут из стандартной библиотеки:

```rust
use std::hash::{DefaultHasher, Hash, Hasher};

let mut hasher = DefaultHasher::new();
name.hash(&mut hasher);
let shard = hasher.finish() as usize % shards.len();
```


## Типичные ошибки

- `std::sync::MutexGuard` живёт через `.await`: future не Send.
- Временный guard в заголовке `match` или `if let`.
- tokio Mutex там, где хватило бы std: лишняя цена.
- Замок на время медленной операции, очередь из всех остальных.
- `let _ = sem.acquire().await` вместо `let _permit = ...`: место возвращается сразу.
- Разрешение берётся внутри задачи, а задач создано без счёта.
- `notify_waiters` без шаблона с проверкой состояния: потерянное пробуждение.
- Ожидание условия без цикла: проснулись, а условие уже занял другой.
- Ручное «проверил, создал» вместо OnceCell.
- Один замок на карту, к которой ходят все.
