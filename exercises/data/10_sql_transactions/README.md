# Транзакции, изоляция и блокировки

В банке перевод 100 рублей это два изменения: списать у Ивана, зачислить Анне. Если сервер упадёт между ними,
деньги исчезнут. Если два перевода с одного счёта пойдут одновременно, оба могут проверить «денег хватает» и
оба списать. Эти истории про любую базу, и в соцсети они выглядят так же: лайки, которые теряются, счётчики,
которые не сходятся, задачи, которые выполняются дважды. Эта глава про то, как база держит одновременную работу
в порядке и что остаётся на тебе.

Примеры в тексте про банковские счета (`accounts`), в задачах соцсеть. Тесты ведут несколько соединений sqlx
по шагам, а паузы `pg_sleep` в коде задач имитируют «работу между проверкой и записью».

## Транзакция и ACID

Транзакция это группа команд, которая выполняется как одна. Начало `BEGIN`, конец `COMMIT` (зафиксировать) или
`ROLLBACK` (отменить всё). Свойства ACID: атомарность (всё или ничего), согласованность (ограничения не
нарушены), изолированность (параллельные транзакции не портят друг друга) и долговечность (после COMMIT
данные пережили падение).

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

В sqlx это `let mut tx = pool.begin().await?; ... tx.commit().await?;`. Запросы выполняются на `&mut *tx`.
Если `tx` уничтожить без `commit` (например, выйти по `?`), sqlx откатит транзакцию. Запрос прямо на `pool`
берёт случайное соединение и сразу фиксируется: транзакцией это не является.

Ошибка внутри транзакции переводит её в состояние «aborted»: все следующие команды отвечают
`current transaction is aborted` (25P02), а `COMMIT` тихо превращается в откат. Чтобы пережить ожидаемую ошибку,
используют точки сохранения: `SAVEPOINT`, откат только до неё. В sqlx это вложенный `tx.begin()` (нужен
`use sqlx::Acquire`). Лучше не создавать ошибку вовсе: `ON CONFLICT DO NOTHING` вместо вставки с последующим
перехватом.

## MVCC: версии вместо блокировок чтения

Postgres не переписывает строки на месте. `UPDATE` создаёт новую версию, а старая остаётся. Каждая версия хранит
`xmin` (транзакция, создавшая её) и `xmax` (транзакция, удалившая или заблокировавшая её).

```
версия v1: xmin 90, xmax 101   <- удалена транзакцией 101
версия v2: xmin 101, xmax 0    <- создана транзакцией 101, жива
```

Читатель видит версию, если создавшая её транзакция закоммичена на момент его снимка, а удалившая нет. Поэтому
читатели не ждут писателей и писатели читателей. Цена: мёртвые версии копятся и чистятся `VACUUM`. Открой
`visuals/mvcc_versions.html`.

## Уровни изоляции

Уровень решает, какой снимок данных видит транзакция.

| уровень | снимок | что допускает |
|---|---|---|
| READ COMMITTED (по умолчанию) | на каждую команду | неповторяемое чтение, write skew |
| REPEATABLE READ | на всю транзакцию | write skew; конфликт правок даёт ошибку 40001 |
| SERIALIZABLE | на всю транзакцию + слежение за зависимостями | ничего; лишние транзакции получают 40001 |

Read Uncommitted в Postgres есть только по названию, он работает как READ COMMITTED. Уровень выбирается в
начале: `BEGIN ISOLATION LEVEL REPEATABLE READ` или `SET TRANSACTION ISOLATION LEVEL ...` первой командой.

**Неповторяемое чтение.** В READ COMMITTED два одинаковых `SELECT` внутри одной транзакции могут дать разное,
если между ними другой клиент закоммитил. Для отчётов из нескольких запросов берут REPEATABLE READ.

**Потерянное обновление.** «Прочитал значение, посчитал в коде, записал» теряет чужие изменения. Лечат
вычислением в базе (`SET x = x + 1`), блокировкой строки (`SELECT ... FOR UPDATE`) или уровнем REPEATABLE READ,
который вместо потери даёт ошибку.

**Ошибка 40001** (`could not serialize access`) не авария, а часть контракта: транзакцию надо выполнить заново
целиком, включая чтение. Повторяй с ограничением числа попыток.

**Write skew.** Две транзакции читают общее условие («закреплено меньше трёх»), каждая решает, что можно, и
пишут в разные строки. Блокировки строк их не сталкивают, правило нарушено. Лечения: заблокировать общую строку
(например, строку автора), или SERIALIZABLE с повтором при 40001, или ограничение в самой базе, если правило
выражается ограничением. Смотри `visuals/isolation_anomalies.html`.

**«Проверил, потом вставил».** Проверка «такого нет» и вставка отдельными запросами оставляют щель. Закрывает её
только ограничение (`UNIQUE`) плюс `INSERT ... ON CONFLICT DO NOTHING`, где `rows_affected()` говорит, выиграл ли ты.

## Блокировки строк

`UPDATE` и `DELETE` блокируют изменяемые строки до конца транзакции. Явно: `SELECT ... FOR UPDATE`. Другие
писатели той же строки ждут, читатели нет.

| фраза | когда |
|---|---|
| `FOR UPDATE` | сильная: строку удалят или поменяют ключ |
| `FOR NO KEY UPDATE` | правка, не меняющая ключ; не мешает вставкам в дочерние таблицы |
| `FOR SHARE`, `FOR KEY SHARE` | «чтобы строку не изменили» и «чтобы не удалили» (FK берёт второе) |

`NOWAIT` вместо ожидания сразу возвращает ошибку 55P03. Ограниченное ожидание: `SET LOCAL lock_timeout`
(в запросах с параметром используют `set_config('lock_timeout', '300ms', true)`). `SKIP LOCKED` пропускает
занятые строки.

**Дедлок.** Транзакция A держит строку 1 и ждёт 2, транзакция B держит 2 и ждёт 1. Postgres через
`deadlock_timeout` (1 секунда) находит цикл и прерывает одну транзакцию с ошибкой 40P01. Профилактика: все берут
блокировки в одном порядке (по возрастанию id). Открой `visuals/row_locks.html`.

**Кто кого держит.** `pg_blocking_pids(pid)` возвращает процессы, блокирующие данный. Представление `pg_locks`
показывает все блокировки, ожидающие это строки с `granted = false`. Самый частый виновник: транзакция в
состоянии `idle in transaction`, которая держит блокировки и ничего не делает.

## Очередь задач в таблице

```sql
UPDATE jobs SET status = 'running'
WHERE id = (
    SELECT id FROM jobs WHERE status = 'queued'
    ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1
)
RETURNING id;
```

Один оператор выбирает и помечает задачу. `SKIP LOCKED` позволяет воркерам брать разные строки, не ожидая друг
друга. Порядок обработки при этом не строгий. Чтобы упавший воркер не терял задачу, задачу «арендуют»: при взятии
сдвигают `visible_at` вперёд, а не помечают навсегда; не подтверждённая задача снова станет доступна, когда аренда
кончится (`visible_at <= now()`). Гарантия получается «минимум один раз», поэтому обработчики пишут идемпотентными.
Смотри `visuals/skip_locked_queue.html`.

## Advisory locks

Блокировка по числу, которое придумываешь ты, без привязки к строкам. `pg_try_advisory_xact_lock(ключ)` берёт
её или сразу отвечает false; снимается сама в конце транзакции. Годится для «один пересчёт на пользователя» и
«одна копия cron-задачи». Ключи общие на всю базу, поэтому разным назначениям нужны разные диапазоны.
Вариант `pg_advisory_lock` держится до конца сессии, и в пуле соединений его легко потерять или оставить.

## Типичные ошибки

- Несколько запросов на `pool` вместо одной транзакции: каждый фиксируется сам.
- Забытый `commit`: данные молча пропадают.
- Продолжать после ошибки внутри транзакции без точки сохранения.
- «Прочитал, посчитал в коде, записал» без блокировки: потерянное обновление.
- Проверка «нет такого» отдельным запросом перед вставкой вместо ограничения.
- Не повторять транзакцию при 40001 и 40P01.
- Блокировки в разном порядке: дедлоки.
- `FOR UPDATE` там, где хватает `FOR NO KEY UPDATE`: вставки в дочерние таблицы зависают.
- Долгая транзакция с паузами внутри (запрос во внешний сервис): блокировки держатся всё это время.
- Очередь на `SELECT` и отдельный `UPDATE`: два воркера берут одну задачу.
