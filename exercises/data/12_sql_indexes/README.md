# Индексы и планы запросов

Городская библиотека оцифровала каталог: триста тысяч книг, два миллиона выдач. Поиск «все книги этого автора»
в первые месяцы отвечал мгновенно. К весне читатели начали жаловаться, что страница думает по три секунды, а в
пятницу вечером сервер вообще перестал отвечать. Код не менялся, данные просто выросли. База делала то, что
делала всегда: читала таблицу целиком в поисках нужных строк. Эта глава о том, как заставить её читать меньше,
как проверить, что она это делает, и как не навредить записи.

Примеры в тексте про библиотеку (`books`, `loans`, `readers`), в задачах соцсеть. Почти все задачи это «создай индекс,
чтобы в плане исчезло то-то»: тест выполняет `EXPLAIN (FORMAT JSON)` и читает узлы плана, а не замеряет время.
Время зависит от машины, план нет.

## Как Postgres хранит таблицу

Таблица это файл из страниц по 8 КБ, а в страницах лежат версии строк в том порядке, в котором их вставляли. Порядка по
какому-либо столбцу нет. Когда ты просишь `WHERE reader_id = 42`, база не знает, где такие строки: единственный способ
найти их все, прочитать подряд каждую страницу. Это называется Seq Scan, и для маленьких таблиц, а также для запросов,
которым нужна заметная часть таблицы, он совершенно честный и быстрый: страницы читаются по порядку, и диск это любит.

Проблема начинается, когда нужна доля процента строк. Тогда чтение миллиона ради десятка это расточительство.

## B-tree: отсортированная копия с оглавлением

Индекс (по умолчанию B-tree) это отдельная структура: ключи в отсортированном порядке плюс адреса строк в таблице. Дерево
страниц делит диапазон на части, как оглавление в книге.

```
                  [ 300 | 600 ]                  корень: куда идти дальше
                 /      |      \
        [100|200]   [400|500]   [700|800]       внутренние узлы
        /  |  \
   листья: 100→(стр.7, стр.31) 140→(стр.2) ... 199→(стр.88)
                                             и ссылки на страницы таблицы
```

Поиск начинается с корня, на каждом уровне выбирается ветка по сравнению ключей, лист содержит ключи и адреса строк.
Высота дерева растёт логарифмически: на миллиард строк обычно четыре-пять уровней. Поэтому поиск одного значения стоит
около пяти чтений страниц, а не миллиона. Открой `visuals/btree_lookup.html`.

Два следствия вытекают сразу из устройства. Первое: индекс отсортирован, значит, он умеет не только искать равенство, но и
диапазоны (`BETWEEN`, `<`, `>`) и отдавать строки в нужном порядке (`ORDER BY`, `min`, `max`). Второе: каждый индекс
надо обновлять на каждой вставке и обновлении, так что индексы не бесплатны, они обмениваются скоростью записи на
скорость чтения.

## EXPLAIN: как база собирается выполнить запрос

```sql
EXPLAIN SELECT title FROM books WHERE author_id = 42 ORDER BY published_year DESC LIMIT 5;
```

```
 Limit  (cost=2410.12..2410.13 rows=5 width=40)
   ->  Sort  (cost=2410.12..2410.17 rows=22 width=40)
         Sort Key: published_year DESC
         ->  Seq Scan on books  (cost=0.00..2409.50 rows=22 width=40)
               Filter: (author_id = 42)
```

Читай снизу вверх и изнутри наружу: самый вложенный узел выполняется первым, его строки поднимаются к родителю.
Здесь база читает всю таблицу (`Seq Scan`), отбирает нужные строки (`Filter`), сортирует их, берёт пять. В скобках оценки
планировщика: `cost` (условные единицы, первое число это стоимость до первой строки, второе общая) и `rows` (сколько
строк узел, по мнению планировщика, выдаст).

`EXPLAIN` план только строит. `EXPLAIN ANALYZE` ещё и выполняет запрос (будь осторожен с `UPDATE` и `DELETE`: они
выполнятся по-настоящему) и добавляет факты: `actual time`, `actual rows`, `loops`. Опция `BUFFERS` показывает, сколько страниц
взято из кэша (`shared hit`) и с диска (`read`). Расхождение «ожидал 22, получил 22000» самый важный сигнал в плане.

Формат `FORMAT JSON` возвращает то же самое деревом: массив из одного объекта, в нём ключ `Plan`, а у каждого узла `Node Type`,
`Relation Name`, `Index Name`, `Plan Rows`, `Plans` (дети), а у плана с ANALYZE и BUFFERS ещё `Actual Rows`, `Shared Hit Blocks` и `Shared Read Blocks`. Такой план можно разобрать в Rust и проверить в тесте. Если
в запросе есть параметры `$1`, обычный EXPLAIN их не принимает: подставь литералы или используй
`EXPLAIN (GENERIC_PLAN)`.

## Откуда планировщик знает, сколько будет строк

Из статистики: для каждого столбца база хранит число различных значений, частые значения и гистограмму. Собирает её
команда `ANALYZE` (autovacuum запускает её по мере изменений таблицы). Запомни разницу: `VACUUM` чистит мёртвые
версии строк и ведёт карту видимости, `ANALYZE` собирает статистику для планов, `VACUUM ANALYZE` делает оба дела.

Если статистика устарела, планы рассчитаны на другую таблицу. Типичный случай: ночью загрузили миллион строк в
таблицу, которая утром была пустой, и до следующего запуска autovacuum все запросы строятся так, будто в ней пусто.
После массовых загрузок и удалений вызывай `ANALYZE` сам.

Вторая причина ошибок: планировщик считает условия на разные столбцы независимыми и перемножает вероятности. Если страна и
город всегда идут парой, условие `country = 'RU' AND city = 'Moscow'` он оценит в десятки раз ниже реального. Для таких случаев
есть расширенная статистика (`CREATE STATISTICS`), но первым делом полезно просто заметить расхождение в плане.

## Когда индекс не нужен

База не обязана использовать индекс, и часто справедливо не использует. Решает селективность: какую долю таблицы
отбирает условие. Если условие отбирает 0.1%, индекс выигрывает у перебора на порядки. Если 30%, прыгать по индексу
в десятки тысяч мест дороже, чем прочитать страницы подряд. Поэтому индекс по столбцу с двумя значениями (флаг
`is_active`) для частого значения бесполезен: он отбирает почти всю таблицу. Для редкого значения помогает частичный
индекс (ниже). Индекс это ставка на то, что выборка малая.

Лишний индекс стоит дороже, чем кажется: место на диске, время каждого INSERT и UPDATE, работа VACUUM. Индекс,
по которому никто не ищет, надо удалить. Полезно иногда смотреть `pg_stat_user_indexes` (столбец `idx_scan`).

## Составные индексы: порядок столбцов решает всё

Индекс по `(a, b)` отсортирован по `a`, внутри равных `a` по `b`. Это как телефонная книга, отсортированная по фамилии, а
внутри по имени.

```
индекс (reader_id, loaned_at):

   reader 7  | 2026-01-03
   reader 7  | 2026-02-11
   reader 7  | 2026-03-30      ← здесь «все выдачи читателя 7, по дате»
   reader 8  | 2026-01-15
   reader 9  | 2025-12-01
   ...
```

Найти всех Ивановых по такой книге легко. Найти всех Иванов нельзя: они рассыпаны по всей книге. Отсюда правило
префикса: индекс помогает условиям, которые ограничивают столбцы слева направо без пропусков (`a`, потом `a и b`). Условие
на `b` без `a` индекс не использует для поиска. Правило выбора порядка: сначала столбцы со сравнением на равенство, потом
столбец диапазона или сортировки.

Бонус: если за равенствами идёт столбец сортировки, база читает индекс в готовом порядке и вообще не сортирует. При `LIMIT`
она останавливается на нужной строке и не читает остальные. Отсутствие в плане узла `Sort` над большой выборкой это
признак того, что индекс подобран верно. Если порядок индекса совпадает лишь с началом `ORDER BY`, появляется
`Incremental Sort` (он дёшев, но всё же есть).

## Функции над столбцом ломают индекс

Индекс хранит значения столбца, а не результаты функций от него. Запрос `WHERE lower(title) = 'dune'` сравнивает не те
значения, которые лежат в индексе по `title`, поэтому не может его использовать. То же самое с `title || ''`, приведением
типа, арифметикой над столбцом и `date_trunc`. Два лекарства. Первое: индекс по выражению, `CREATE INDEX ... ON books
(lower(title))`, выражение в запросе должно совпадать с ним буква в букву. Второе: перенести работу на другую сторону сравнения.
Условие `loaned_at::date = current_date` превращают в диапазон: `loaned_at >= current_date AND loaned_at < current_date + 1`.
Диапазон на отрезок `[начало, следующее начало)` не теряет и не дублирует границу, а `BETWEEN` включает оба конца.

## Частичные и покрывающие индексы

Частичный индекс содержит только строки, подходящие под условие: `CREATE INDEX ... WHERE returned_at IS NULL`.
Если в таблице хранятся и «возвращено» (почти все строки), и «на руках» (доли процента), индекс по тем, что на руках, остаётся крошечным
и обслуживает самый частый запрос «кто сейчас должен книги». Планировщик использует его, только если может доказать, что условие
запроса влечёт условие индекса, так что в запросе условие надо писать так же.

Покрывающий индекс отвечает на запрос, не заглядывая в таблицу (`Index Only Scan`). Для этого в нём должны быть
все столбцы, нужные запросу. Столбцы, по которым не ищут, но которые нужны в ответе, добавляют через `INCLUDE`:

```sql
CREATE INDEX loans_reader_idx ON loans (reader_id, loaned_at DESC) INCLUDE (book_id);
```

Подвох в том, что видимость версий строк хранится в таблице, а не в индексе. Чтобы не проверять каждую строку, Postgres ведёт
карту видимости: страницы, помеченные «все видят все строки», проверки не требуют. Метки ставит `VACUUM`. В плане это
видно как `Heap Fetches: N`. Большое N значит, что пометок нет, и `Index Only Scan` по сути ходит в таблицу. Только что
загруженная таблица не имеет пометок, и планировщик даже не станет выбирать Index Only Scan, пока её не почистят.

## Страницы без OFFSET: keyset-пагинация

Классическая пагинация `LIMIT 20 OFFSET 2000` заставляет базу прочитать 2020 строк и выбросить две тысячи. Цена
страницы растёт с её номером, а ещё страницы «плывут», если между запросами что-то вставили или удалили. Keyset (она же
курсорная пагинация) запоминает не номер страницы, а значения последней показанной строки, и следующая страница это «всё, что
идёт после неё».

```sql
-- история выдач читателя, от старых к новым; ($2, $3) это loaned_at и id последней показанной выдачи
SELECT id, book_id, loaned_at FROM loans
WHERE reader_id = $1 AND (loaned_at, id) > ($2, $3)
ORDER BY loaned_at, id
LIMIT 20;
```

Курсор из одного столбца теряет строки, если значения в нём не уникальны: все записи с тем же временем, что у последней на странице,
оказываются «не больше курсора» и исчезают. Поэтому курсор всегда содержит уникальный хвост (`id`), а порядок полный.
Сравнение кортежей `(a, b) > ($1, $2)` Postgres превращает в условие индекса, и страница читается за те же три чтения, что и первая.
Хитрый эквивалент через `OR` часто превращается в фильтр, и база читает все строки до курсора; проверяй план. Цена keyset: на страницу
номер 57 прыгнуть нельзя, только вперёд или назад. Для бесконечной ленты это то, что нужно. Открой `visuals/keyset_vs_offset.html`.

## Соединения и внешние ключи

Для `JOIN` планировщик выбирает один из трёх алгоритмов. Nested Loop берёт каждую строку внешней стороны и ищет пару во внутренней:
он выигрывает, когда внешних строк мало, а по ключу соединения есть индекс. Hash Join строит хеш-таблицу меньшей стороны и
проходит по другой: подходит для больших выборок без индексов. Merge Join сливает две стороны, уже отсортированные по ключу.
Если оценка числа внешних строк занижена, планировщик выберет Nested Loop и будет делать тысячи индексных поисков вместо одного
прохода.

Важно помнить: Postgres сам создаёт индексы под PRIMARY KEY и UNIQUE, но не под FOREIGN KEY. Столбец `loans.book_id` без индекса
значит, что каждое соединение с `books` и каждое удаление книги читает все выдачи.

## Проверка планов в тестах

Утверждение «запрос быстрый» ничего не стоит, пока оно не проверено, а замер времени на тестовой машине шумит. Проверяют узлы плана: в
`EXPLAIN (FORMAT JSON)` нет `Seq Scan` по нужной таблице, нет `Sort` над большой выборкой, есть `Index Only Scan`. Обходить надо
всё дерево, потому что корень почти всегда `Limit` или `Aggregate`. Не забудь про статистику: свежие данные без `ANALYZE` дают
планы, которых в проде не будет. И про размер данных: на таблице из пяти строк планировщик справедливо читает её подряд.

## Типичные ошибки

- Индекс по столбцу с двумя-тремя значениями, когда условие отбирает большую долю таблицы.
- Составной индекс в порядке «как в SELECT», а не «равенство, потом диапазон или сортировка».
- Функция, приведение типа или арифметика над столбцом в `WHERE`.
- `BETWEEN` для суток и других полуинтервалов.
- Кто-то создал индекс «на всякий случай» и не удалил: он тормозит каждую запись.
- Забыть `ANALYZE` после массовой загрузки и `VACUUM` для Index Only Scan.
- Курсор по неуникальному столбцу.
- `CREATE INDEX` на живой большой таблице без `CONCURRENTLY` (об этом в главе про миграции).
