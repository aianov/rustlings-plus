# RESP: как Redis разговаривает

Открой терминал и поговори с Redis курса без всяких клиентов:

```
$ printf 'INCRBY visits:42 5\r\n' | nc -q1 127.0.0.1 56379
:5
$ printf 'LRANGE queue 0 -1\r\n' | nc -q1 127.0.0.1 56379
*0
$ printf 'WHATEVER\r\n' | nc -q1 127.0.0.1 56379
-ERR unknown command 'WHATEVER', with args beginning with:
```

Redis ответил, хотя мы не знали никакого «драйвера». Протокол настолько простой, что его можно набрать
руками. Он называется RESP (REdis Serialization Protocol), и в этом разделе ты напишешь для него свой кодек,
а в следующей главе клиент. Пока зубрим протокол, а не команды: что вообще бывает на проводе и как не
сломаться, когда байты приходят не так, как хотелось бы.

## Пять видов данных

У каждого вида свой первый байт, а дальше текст до пары `\r\n` (CRLF). Это вся грамматика RESP2.

```
+PONG\r\n                  простая строка (статус)
-WRONGTYPE bad type\r\n    ошибка: вид, пробел, пояснение
:1000\r\n                  целое число
$6\r\nfoobar\r\n           bulk string: длина, CRLF, ровно столько байтов, CRLF
$-1\r\n                    «нет значения» (null)
*2\r\n:1\r\n:2\r\n         массив: число элементов, потом сами элементы подряд
*-1\r\n                    «нет массива» (null)
```

Три первых вида целиком живут в одной строке, поэтому внутри них нельзя держать перевод строки: кадр на
этом кончится. Для произвольных данных есть bulk string. В ней граница значения определена не символом, а
длиной, значит внутри могут лежать любые байты: картинка, JSON с переносами, нули. Длина считается в байтах.
Слово «привет» в UTF-8 занимает двенадцать байтов, и `$6` для него было бы ошибкой.

Пустое и отсутствующее значения это разные вещи: `$0\r\n\r\n` значит «значение есть, оно пустое», а `$-1\r\n`
значит «такого ключа нет». Для массивов то же самое: `*0` и `*-1`.

## Команда это тоже массив

Клиент говорит с сервером тем же языком. Команда превращается в массив bulk-строк, по одной на слово, и все
аргументы строки, даже числа:

```
EXPIRE session:7 3600

*3\r\n$6\r\nEXPIRE\r\n$9\r\nsession:7\r\n$4\r\n3600\r\n
```

Поэтому ключи и значения могут быть любыми байтами, и поэтому работает «набрать руками» через `nc`:
сервер понимает и «встроенный» вид (слова через пробел), но приложения всегда шлют массив.
Хочешь убедиться: `printf '*1\r\n$4\r\nPING\r\n' | nc -q1 127.0.0.1 56379`.

Ответы устроены так же. `HGETALL` вернёт плоский массив `[поле, значение, поле, значение...]`, `EXEC` вернёт массив
ответов на каждую команду пачки, а внутри может лежать что угодно, в том числе вложенные массивы и ошибки.

## Данные приходят как получится

TCP не знает про кадры. Ответ на `LRANGE` из тысячи элементов придёт десятком кусков, а два коротких ответа
подряд могут прийти одним куском. Парсер кормят из буфера, который растёт по мере чтения, и ему нужно уметь три
исхода: «вот значение, оно заняло столько-то байтов», «пока не хватает данных» и «это не RESP».

Контракт «не хватает данных» главный. Если кадр неполный, парсер не должен ни убрать из буфера ни байта, ни
выдать пол-ответа. Покажу на игрушечном протоколе, где сообщение это четыре байта длины (big endian) и тело:

```rust
fn take_message(buf: &mut BytesMut) -> Option<Bytes> {
    if buf.len() < 4 {
        return None;
    }
    let size = u32::from_be_bytes([buf[0], buf[1], buf[2], buf[3]]) as usize;
    if buf.len() < 4 + size {
        return None;
    }
    buf.advance(4);
    Some(buf.split_to(size).freeze())
}
```

Видишь порядок? Сначала выяснили, что кадр целиком, и только потом `advance`. Если сделать `advance(4)` раньше проверки
тела, то в следующий раз длина уже съедена, и всё, что придёт после, будет разобрано неверно. У RESP та же логика, но
заголовки разной формы, а у массивов заголовок вложенный. Самый простой способ не запутаться: функция «разбери с позиции
`pos` и скажи, где кончилось» вообще не меняет буфер, а `advance` вызывает один раз тот, кто её позвал. Массив тогда
это цикл: разбираем первый элемент с позиции сразу за заголовком, второй с позиции, где кончился первый, и так
далее. Не дошли до конца буфера, значит весь массив пока неполный.

Неполный кадр разбирается заново с начала при каждой порции данных. Для коротких ответов это ничего не стоит.
Для одного ответа в сотни тысяч элементов уже заметно, и настоящие клиенты хранят состояние разбора. В курсе нам
хватает простого подхода, а об этой цене надо знать.

## Неполное и неверное это разное

«Пока не хватает данных» и «в данных ошибка» нельзя путать. Первое ждёт, второе закрывает соединение. После ошибки
протокола границы кадров потеряны: любая попытка «пропустить до ближайшего CRLF» может принять за границу кусок
из середины значения, и дальше клиент станет отдавать ответы не тем командам. Поэтому ошибка протокола фатальна для
соединения. Закрыли, подключились заново.

Ещё одно правило: сеть это недоверенный ввод. Парсер не может паниковать ни на каких байтах, и он не может
доверять числам из заголовков. Заголовок `$4000000000\r\n` занимает тринадцать байтов, а парсер, который в ответ
готовит четыре гигабайта памяти, превращает любого собеседника в хозяина твоего сервера. Пределы (самое
большое значение, самый длинный массив, самая глубокая вложенность) проверяют по заголовку, до чтения тела и до
рекурсии. Вложенность отдельно потому, что `*1` повторённое миллион раз закончит стек рекурсивного парсера.

## RESP3 в двух словах

Redis 6 добавил RESP3: переключается командой `HELLO 3`. Появились типы с первыми байтами `_` (null), `#` (булево),
`,` (дробное число), `%` (словарь), `~` (множество), `>` (push-сообщение от сервера вне очереди ответов) и другие.
Из-за push-сообщений RESP3 нужен настоящим клиентам для подписок. Курс использует RESP2: типов меньше, а всё
описанное выше (длины, CRLF, неполные кадры, пределы) в RESP3 устроено точно так же.

## Типичные ошибки

- Читать ответ построчно (`read_line`) и считать, что значение это строка. Пока в данных нет перевода строки,
  работает. Первое же значение с `\r\n` рассинхронизирует соединение.
- Считать длину в символах. Любой текст не на ASCII ломает команду.
- Забирать байты из буфера по ходу разбора. Если кадр неполный, они потеряны.
- Путать `$0` и `$-1`, `*0` и `*-1`. «Нет ключа» и «пустая строка» это разные ответы.
- Паниковать на мусоре. Один неверный байт от клиента не должен ронять сервис.
- Выделять память по числу из заголовка до проверки предела.
