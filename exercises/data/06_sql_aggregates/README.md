# Агрегаты и группировка

Страница профиля показывает «120 подписчиков, 34 поста, 560 лайков». Это не данные, которые лежат
в таблицах, а цифры, которые из этих данных получают: сложить, сосчитать, найти наибольшее.
Делать это в приложении значит скачать все строки ради одного числа; база считает на месте и
отдаёт одну строку. Но агрегаты коварны: самые частые ошибки с ними не вызывают ни исключений, ни
предупреждений, цифры просто получаются неверными. Эта глава про то, как их не получить.

Примеры в тексте про школу (`students`, `exams`, `grades`), задачи про соцсеть.

```
grades                          SELECT subject, count(*), avg(mark)
 student | subject | mark       FROM grades GROUP BY subject
 anna    | math    |  5
 boris   | math    |  3         subject | count | avg
 anna    | art     |  4   --->  math    |   2   | 4.0
 boris   | art     | NULL       art     |   2   | 4.0   (NULL пропущен)
```

## Агрегатные функции

Агрегат сворачивает много строк в одно значение: `count`, `sum`, `avg`, `min`, `max`. Без
`GROUP BY` весь результат одна строка:

```sql
SELECT count(*), sum(mark), avg(mark), min(mark), max(mark) FROM grades
```

Главное правило про NULL: **агрегаты его пропускают**. `sum`, `avg`, `min`, `max` работают по
известным значениям, и `avg` делит на число непустых значений, а не на число строк. Единственное
исключение `count(*)`, он считает строки как есть.

```sql
SELECT count(*)            -- сколько строк
     , count(mark)         -- у скольких оценка известна
     , count(DISTINCT mark)-- сколько разных оценок
FROM grades
```

Если в наборе нет ни одной строки или все значения NULL, `sum`, `avg`, `min`, `max` возвращают
**NULL**, а не ноль (`count` вернёт 0). Для отчёта, где нужен ноль, оберни снаружи:
`COALESCE(sum(mark), 0)`. Типы: `count` всегда `bigint` (читай в `i64`), `sum` от `integer` это
`bigint`, а `avg` это `numeric`. Среднее часто выходит с длинным хвостом знаков; округляет его
`round(число, сколько_знаков)`, например `round(avg(mark), 1)` даёт один знак после запятой.

## GROUP BY

```sql
SELECT subject, count(*) AS n, avg(mark) AS average
FROM grades
GROUP BY subject
ORDER BY subject
```

Строки раскладываются по группам с одинаковым значением ключа, из каждой группы получается ровно
одна строка результата. Открой `visuals/group_by.html`, там видно, как это происходит.

Из этого следует правило, на которое жалуются все новички: **в списке SELECT могут быть только
столбцы из GROUP BY и агрегаты**. Если написать `SELECT subject, teacher, count(*) ... GROUP BY
subject`, у группы «math» может быть несколько учителей, и база не знает, какого показать. Она
отвечает ошибкой «column must appear in the GROUP BY clause or be used in an aggregate function».
Чинить можно добавлением столбца в GROUP BY (группа станет мельче) или агрегатом. Особый случай:
если группировать по первичному ключу таблицы, остальные её столбцы разрешены, потому что ключ
однозначно определяет строку.

Группировать можно по выражению: `GROUP BY date_trunc('month', taken_at)` собирает строки по
месяцам. Номер столбца (`GROUP BY 1`) ссылается на первый столбец списка, удобно, но при перестановке
столбцов работает уже по-другому.

У времени есть тонкость в типе результата. `created_at::date` даёт тип `date` (просто день, `2026-09-28`),
а `date_trunc('day', created_at)` остаётся `timestamptz` и печатается с временем и поясом
(`2026-09-28 00:00:00+00`). Для групп по дням бери `::date`, а `date_trunc` оставь для месяцев и часов,
когда нужно сохранить тип времени.

## WHERE и HAVING

```sql
SELECT subject, count(*)
FROM grades
WHERE mark >= 3            -- отбираем строки до группировки
GROUP BY subject
HAVING count(*) >= 10      -- отбираем группы после группировки
```

WHERE видит отдельные строки и срабатывает до группировки. HAVING видит готовые группы и поэтому
может спрашивать про агрегаты. Агрегат в WHERE писать нельзя: групп ещё нет. Обратное тоже плохо:
условие по отдельной строке в HAVING либо не работает, либо тормозит. Если условие можно проверить
по одной строке, оно идёт в WHERE.

## FILTER: у каждого агрегата своё условие

```sql
SELECT subject,
       count(*) AS all_marks,
       count(*) FILTER (WHERE mark >= 4) AS good_marks
FROM grades GROUP BY subject
```

WHERE сузил бы все агрегаты сразу, а FILTER сужает один. Раньше для этого писали
`sum(CASE WHEN ... THEN 1 ELSE 0 END)`; FILTER делает то же короче.

## Склейка значений: string_agg и array_agg

```sql
SELECT subject, string_agg(student, ', ' ORDER BY student) AS students
FROM grades GROUP BY subject
```

`string_agg` склеивает строки группы в одну, `array_agg` собирает массив. Порядок внутри склейки
без явного ORDER BY случайный, а писать его нужно внутри скобок агрегата. Внешний `ORDER BY`
упорядочивает группы, а не содержимое. С массивом так же: `array_agg(mark ORDER BY taken_at DESC)`
вернёт оценки от последней к первой.

## Ловушки LEFT JOIN и подсчёта

Две ошибки, которые не дают исключения.

**1. `count(*)` после LEFT JOIN.** Ученик без оценок после `LEFT JOIN grades` даёт одну строку из
NULL, и `count(*)` скажет «1 оценка». Считай столбец правой таблицы, который не бывает пустым:

```sql
SELECT s.name, count(g.id) AS grades      -- а не count(*)
FROM students s LEFT JOIN grades g ON g.student_id = s.id
GROUP BY s.id
```

**2. Размножение строк.** Если подряд соединить две таблицы «один ко многим» (у ученика пять оценок
и три замечания), строки перемножаются: получается 5 × 3 = 15 строк на ученика, и любой счётчик
по ним врёт. Посмотри `visuals/join_fanout.html`. Лечится по-разному:

- `count(DISTINCT g.id)` и `count(DISTINCT r.id)`: годится для подсчёта, но не для `sum`;
- предагрегация: свернуть каждую связь в отдельном подзапросе до одной строки на ученика, а потом
  соединять. Подзапросы мы разберём подробно в одной из следующих глав;
- вообще не соединять: считать каждое число скалярным подзапросом в SELECT, то есть отдельным
  запросом в скобках прямо в списке столбцов:

  ```sql
  SELECT s.name,
         (SELECT count(*) FROM grades g WHERE g.student_id = s.id) AS marks,
         (SELECT count(*) FROM remarks r WHERE r.student_id = s.id) AS remarks
  FROM students s
  ```

  Подзапрос видит столбцы внешней строки и возвращает одно значение, поэтому строки не размножаются.

Тревожный признак: числа выглядят «круглыми» (произведения) или очень большими. Проверяй счётчики
на одном объекте, у которого ответ известен.

## Типичные ошибки

- `count(*)` вместо `count(столбец)` после LEFT JOIN.
- Два соединения «один ко многим» подряд и счётчики по ним.
- `sum` без COALESCE для случая «ничего нет», приложение получает NULL.
- Агрегат в WHERE, условие по строке в HAVING.
- Столбец в SELECT, которого нет в GROUP BY.
- `avg` делит не на то, на что ожидали: NULL не входит ни в сумму, ни в количество.
- Порядок внутри `string_agg` и `array_agg` не задан.
- Читать `count` в `i32` (в sqlx это ошибка выполнения).
