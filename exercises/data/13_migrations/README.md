# Миграции

Сеть кинотеатров выкатывает релиз в пятницу вечером, в самый час пик продажи билетов. В релизе одна строчка:
`ALTER TABLE tickets ADD COLUMN promo_code text`. Команда мгновенная, и на тестовой базе она занимает миллисекунду.
На проде она встаёт и не двигается, а через минуту не открывается ни одна страница сайта. Причина оказалась в чужой
забытой транзакции: сотрудник бухгалтерии открыл отчёт, не закрыл вкладку, и транзакция «висит». Миграция ждёт её
конца, а за ней в очереди стоят все покупки билетов. Эта глава о том, как менять схему так, чтобы ни одна из таких
историй не повторилась: как устроен раннер миграций, что такое блокировки DDL и как менять схему, пока сервис работает.

Примеры в тексте про кинотеатры (`tickets`, `halls`, `showings`), в задачах соцсеть. Тесты ведут несколько соединений
sqlx и смотрят в системные каталоги Postgres: проверяется не «похоже на правду», а состояние базы после каждого шага.

## Зачем миграции

Схема базы это тоже код. Если её меняют руками, то у разработчика она одна, на стенде другая, на проде третья, и никто
не знает, какая правильная. Миграция это файл с изменением схемы, у которого есть номер. Файлы лежат в репозитории рядом
с кодом, применяются по порядку, а база запоминает, какие уже применены. Тогда любой пустой Postgres за минуту
превращается в нужную схему, а прод получает ровно те же шаги, что и стенд.

Правило номер один: применённую миграцию не правят. Ошибку исправляет следующая миграция. Иначе у разных окружений
окажутся разные схемы, а поймать это нечем. Раннер проверяет контрольные суммы: при старте он сверяет записанную в
журнале сумму текста с текущим файлом и отказывается идти дальше, если они разошлись.

## Журнал и порядок

Раннер хранит состояние в самой базе, в служебной таблице:

```sql
CREATE TABLE schema_migrations (
    version    bigint PRIMARY KEY,
    name       text NOT NULL,
    checksum   text NOT NULL,
    applied_at timestamptz NOT NULL DEFAULT now()
);
```

Файлы называют `0001_создать_залы.sql`, `0002_билеты.sql`: номер потом имя. Порядок определяет номер, причём как число
(10 идёт после 2, хотя строка «10» меньше строки «2»), а не порядок в каталоге: файловая система отдаёт имена как попало. При запуске
раннер читает журнал, выбирает файлы, которых там нет, сортирует по номеру и применяет по одному. Полезные проверки: применённая
версия, файла которой уже нет в каталоге, это потерянная миграция (ошибка), а новая версия с номером меньше уже применённой это миграция «вне
очереди», которую большинство раннеров отвергают, потому что на других окружениях она выполнилась бы в другом порядке.

## Миграция и запись о ней: одна транзакция

DDL в Postgres транзакционный: можно открыть транзакцию, создать таблицу, изменить другую, сломаться и откатить всё, как будто
ничего не было. Это огромное преимущество перед базами, где `CREATE TABLE` фиксируется сам. Раннер должен им пользоваться:
команды файла и запись в журнал идут в одной транзакции. Тогда миграция либо применена целиком и записана, либо не применена вовсе.
Без этого между последней командой и записью есть щель, в которую может попасть падение процесса, и повторный запуск
начнёт с команды, объект которой уже создан.

Технические детали sqlx. `sqlx::query` готовит одну команду, а файл миграции это несколько команд через `;`, поэтому нужен `sqlx::raw_sql`:
он использует простой протокол и принимает любой текст. Составной текст, пришедший простым протоколом, сам выполняется как одна неявная
транзакция, но запись в журнал всё равно должна быть в той же, поэтому открывай транзакцию явно и выполняй всё на `&mut *tx`.
Если раннер для сообщений об ошибках делит файл на команды сам и выполняет по одной, то без явной транзакции ошибка на второй команде оставит
первую в базе.

## Несколько копий сервиса стартуют сразу

Сервис в проде запущен в трёх экземплярах, и при выкатке все три в одну секунду идут применять миграции. Каждый читает журнал, видит
«нет версии 7» и начинает её применять; один выигрывает, остальные падают с ошибкой «already exists» и не поднимаются.
Решение: пусть мигрирует один. Для этого подходят консультативные блокировки Postgres (advisory locks). Это блокировки без привязки к
таблицам и строкам: ключ придумывает приложение.

```sql
SELECT pg_advisory_lock(7575757);    -- ждёт, пока замок свободен, и берёт его
-- ... вся работа раннера ...
SELECT pg_advisory_unlock(7575757);
```

Замок принадлежит соединению (сессии) и живёт до явного снятия. Поэтому его берут на отдельном соединении из пула, держат всё время работы
и снимают на том же соединении, и обязательно при любом исходе, в том числе при ошибке миграции. Если снятие забыто, замок переживёт работу
раннера вместе с соединением, которое вернулось в пул, и следующий запуск зависнет навсегда. Журнал надо читать уже под замком: копия, дождавшаяся
очереди, должна увидеть то, что сделала предыдущая, а не устаревший список. Транзакционный вариант `pg_advisory_xact_lock` здесь не подходит: он исчезнет
с первой же транзакцией, а миграций несколько.

## Блокировки DDL

У каждой команды есть блокировка нужной силы. Для нас важны три:

```
ACCESS SHARE          берёт обычный SELECT
ROW EXCLUSIVE         берут INSERT, UPDATE, DELETE
ACCESS EXCLUSIVE      берёт большинство ALTER TABLE: несовместим со всеми, даже с SELECT
```

Блокировки идут в очереди, и очередь честная. Если ALTER хочет `ACCESS EXCLUSIVE`, а таблицу сейчас читает чья-то долгая транзакция, ALTER
встаёт ждать. Любой новый запрос, даже самый невинный `SELECT`, совместимый с этим читателем, тоже встаёт, но уже позади ALTER:
обогнать ждущего нельзя. Так одна забытая транзакция превращается в остановку всего сервиса. Открой `visuals/lock_queue.html`.

```
транзакция A (читает)      ALTER (ждёт A)      SELECT-ы пользователей
  держит замок        ←      в очереди      ←      в очереди за ALTER
```

Лекарство одно: не ждать замок долго. Параметр `lock_timeout` обрывает ожидание ошибкой `55P03` (`lock_not_available`).
Миграция получает отказ через 200-300 миллисекунд, очередь рассасывается, а раннер повторяет попытку через секунду. На время
команды параметр ставят так, чтобы он не оставался на соединении пула: `SELECT set_config('lock_timeout', '300', true)` внутри
транзакции (третий аргумент `true` значит «до конца транзакции»). Параметры `$1` в команде `SET` не работают, `set_config`
принимает их. Повторов конечное число, и повторять надо только `55P03`: синтаксическая ошибка от времени не пройдёт.

## Безопасные изменения живой таблицы

Что быстро и безопасно: добавить столбец без значения по умолчанию или с константой по умолчанию (в Postgres 11 и новее это меняет только каталог);
добавить таблицу. Что опасно на большой таблице: всё, что читает или переписывает все строки под жёсткой блокировкой. Приёмы:

- `NOT NULL`. Прямой `SET NOT NULL` читает всю таблицу под `ACCESS EXCLUSIVE`. Вместо него: `ADD CONSTRAINT ... CHECK (x IS NOT NULL) NOT VALID`
  (мгновенно), `VALIDATE CONSTRAINT` (читает всю таблицу, но под мягкой блокировкой, не мешая чтению и записи), и теперь `SET NOT NULL`
  мгновенен: он видит готовое доказательство.
- Внешний ключ. Так же: `ADD FOREIGN KEY ... NOT VALID`, потом `VALIDATE CONSTRAINT`. Новые строки проверяются сразу, старые отдельной командой.
- Индекс. Обычный `CREATE INDEX` блокирует запись на всё время построения. `CREATE INDEX CONCURRENTLY` не блокирует, но работает вне транзакции,
  ждёт завершения чужих транзакций и строит индекс в несколько проходов. Поэтому раннер должен уметь миграции вне транзакции (договор вроде
  комментария `-- no-transaction` в первой строке), и такие файлы пишут по одной команде: если упадёт вторая, первая уже в базе.
- Если `CONCURRENTLY` упал (дубликат для UNIQUE, отмена), остаётся индекс-обломок: `pg_index.indisvalid = false`. База его обновляет, но не
  использует и не проверяет им уникальность. Обломок удаляют (`DROP INDEX CONCURRENTLY`) и создают заново, когда причина устранена.

## Переименование без остановки: expand и contract

`RENAME COLUMN` мгновенный, но ломает старую версию приложения. Во время выкладки две версии кода живут одновременно, и схема должна устраивать
обе. Поэтому изменение, ломающее совместимость, делят на два релиза.

```
экспанд (расширение):   добавить новое, ничего не удаляя, и держать старое и новое синхронными
релиз приложения:       новая версия работает с новым, старой больше нет
контракт (сужение):     убрать старое
```

Для переименования расширение выглядит так: добавить новый столбец, поставить триггер `BEFORE INSERT OR UPDATE`, который копирует значение из заполненного
поля в пустое (для вставки) или из изменённого в неизменённое (для обновления), и перенести существующие данные. Порядок важен: триггер ставят до
переноса данных, иначе строки, вставленные в промежутке, останутся без нового значения. Новый столбец сначала nullable (старая версия не знает про него и не
заполняет), `NOT NULL` ставят на этапе сужения. Сужение: убрать триггер и его функцию, потом старый столбец, и всё это одной транзакцией, чтобы не было
окна, в котором триггер ссылается на уже удалённый столбец. Открой `visuals/expand_contract.html`.

## Заполнение пачками

После расширения новый столбец пуст у миллионов строк, и их нужно заполнить. Один огромный `UPDATE` держит блокировки на всех изменяемых строках до конца,
порождает по мёртвой версии на каждую (таблица раздувается вдвое) и громко бьёт по репликации. Поэтому заполняют пачками: небольшая выборка,
отдельная транзакция на каждую, пока не останется непустых. Условие «ещё не заполнено» в `WHERE` делает цикл возобновляемым после падения. Для
выборки пачки подходит подзапрос с `LIMIT` внутри `IN`. На настоящей таблице между пачками добавляют паузу, чтобы не давить на основную нагрузку.

## Проверка в тестах

Каждый шаг миграции проверяется состоянием базы: системные каталоги (`pg_index`, `pg_constraint`, `pg_trigger`, `information_schema`) отвечают на вопросы
«индекс пригоден?», «ограничение проверено?», «триггер остался?». Для гонок и блокировок тест держит открытую транзакцию на другом соединении и
смотрит, как ведёт себя раннер (ждёт ли он, обрывает ли ожидание, мешает ли читателям). Всегда закрывай такую транзакцию (`rollback`) до конца
теста, иначе удаление схемы повиснет.

## Типичные ошибки

- Править применённую миграцию вместо новой.
- Выполнять команды файла и запись в журнал отдельными транзакциями.
- Брать консультативный замок на соединении из пула и не снимать его при ошибке.
- `ALTER TABLE` без `lock_timeout` на таблице, которую кто-то читает.
- `SET NOT NULL` или `ADD FOREIGN KEY` на большой таблице одной командой.
- `CREATE INDEX` без `CONCURRENTLY`, а `CONCURRENTLY` внутри транзакции.
- Не заметить индекс-обломок после упавшего `CONCURRENTLY`.
- Поставить новый столбец `NOT NULL` на этапе расширения.
- Перенести данные до установки триггера.
- Один огромный `UPDATE` для заполнения миллиона строк.
