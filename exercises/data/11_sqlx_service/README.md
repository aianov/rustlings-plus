# sqlx в сервисе

Сервис бронирования номеров работает месяц без проблем. В пятницу вечером приходит акция, и в логах появляется
`PoolTimedOut`. База здорова, процессор в ней скучает, а сервис стоит. Через час выясняется, что обработчик
бронирования открывал транзакцию и внутри вызывал функцию, которая брала второе соединение из того же пула.
Пока людей мало, всё работает. Когда одновременных броней становится столько же, сколько соединений, каждая
держит одно и ждёт второе. Эта глава про такие места: где async встречается с базой, и код, который правильно
работает на ноутбуке, под нагрузкой ведёт себя иначе.

Примеры в тексте про отель (`rooms`, `bookings`, `guests`), в задачах соцсеть. В главе нет новой SQL-теории, все
приёмы про Rust-сторону: как держать соединения, как отменять запросы, как не размножать запросы и как не
собирать SQL из чужих строк. Транзакции и изоляцию из прошлых глав ты уже знаешь.

## Чем выполнять запрос: пул, соединение, транзакция

У `sqlx` запрос можно выполнить на трёх разных вещах, и функции репозитория должны уметь работать со всеми:

```
&PgPool            берёт любое свободное соединение, запрос фиксируется сразу
&mut PgConnection  одно конкретное соединение (из pool.acquire())
&mut *tx           то же соединение, но внутри открытой транзакции
```

Транзакция разыменовывается в соединение, поэтому функция, которая принимает `&mut PgConnection`, подходит и для
соединения из пула, и для транзакции:

```rust
async fn room_price(conn: &mut PgConnection, room: i64) -> Result<i32, sqlx::Error> {
    sqlx::query_scalar("SELECT price FROM rooms WHERE id = $1").bind(room).fetch_one(conn).await
}

let mut tx = pool.begin().await?;
let price = room_price(&mut tx, 7).await?;
```

Запись `&mut tx` превращается в `&mut PgConnection` автоматически. Почему не писать `impl Executor` везде? `Executor`
реализован для `&PgPool` и для `&mut PgConnection`, но запрос забирает его по значению. Ссылку на пул можно
скопировать, а `&mut PgConnection` только переместить: после первого `fetch_one(db)` второй запрос на том же `db`
не соберётся, компилятор скажет про использование перемещённого значения. Если функции нужно несколько запросов
подряд, пусть она берёт `&mut PgConnection` и передаёт в каждый запрос `&mut *conn`: это короткий заём, а не
передача владения.

Когда функция сама хочет решить, нужна ли ей транзакция, она принимает `impl Acquire`:

```rust
use sqlx::{Acquire, Postgres};

async fn cancel_booking<'a, A>(db: A, booking: i64) -> Result<(), sqlx::Error>
where
    A: Acquire<'a, Database = Postgres>,
{
    let mut tx = db.begin().await?;
    // ... несколько изменений ...
    tx.commit().await
}
```

`begin()` на пуле открывает новую транзакцию, а на соединении, которое уже внутри транзакции, ставит точку
сохранения (`SAVEPOINT`): откатится только эта функция, а внешняя транзакция останется рабочей. `acquire()` вместо
этого просто отдаёт соединение, без всякой атомарности. Выбирай осознанно: нужно «всё или ничего» для этой
операции, значит `begin()`.

## Повтор транзакции

На уровнях REPEATABLE READ и SERIALIZABLE и при взаимных блокировках Postgres иногда отвечает «я не смог, попробуй
ещё раз»: `40001` (serialization_failure) и `40P01` (deadlock_detected). Это не ошибка кода, а штатный способ базы
сохранить корректность. Транзакцию в таком случае нужно повторить целиком, с самого начала. Рецепт:

```rust
let mut attempt = 1;
loop {
    match run_transaction().await {
        Err(sqlx::Error::Database(e)) if attempt < LIMIT && is_retryable(e.code().as_deref()) => attempt += 1,
        other => return other,
    }
}
```

Три правила. Повторять можно только эти два кода: нарушение уникальности повтором не исчезнет. Предел обязателен,
иначе два конфликтующих клиента застрянут навсегда. И повторяется вся транзакция, не одна команда: после ошибки
транзакция «отравлена», её можно только откатить. Внутри `run_transaction` не должно быть побочных эффектов вне
базы (письмо, HTTP-вызов), иначе при повторе они случатся дважды.

## Пул под нагрузкой

Пул это очередь на соединения. Его настройки определяют, как сервис ведёт себя при пике:

```rust
let pool = PgPoolOptions::new()
    .max_connections(20)
    .acquire_timeout(Duration::from_secs(3))
    .idle_timeout(Duration::from_secs(600))
    .after_connect(|conn, _meta| {
        Box::pin(async move {
            sqlx::query("SELECT set_config('application_name', 'booking', false)").execute(conn).await?;
            Ok(())
        })
    })
    .connect(&url)
    .await?;
```

`max_connections` ограничивает число соединений: у Postgres их конечное число на весь кластер, и десять сервисов
по сто соединений сложат базу. `acquire_timeout` говорит, сколько ждать свободное соединение, прежде чем
вернуть `PoolTimedOut`: чем короче, тем быстрее перегрузка превращается в понятную ошибку, а не в зависший
сервис. `idle_timeout` закрывает простаивающие соединения. `after_connect` выполняется для **каждого** нового
соединения пула (а их пул открывает и пересоздаёт сам), поэтому настройки сессии (`application_name`,
`statement_timeout`) ставят именно здесь, а не одной командой после открытия пула. Команда `SET имя = значение`
не принимает параметры `$1`, поэтому значение передают функцией `set_config('имя', $1, false)`: третий
аргумент говорит, действует ли настройка только до конца транзакции (`true`) или на всю сессию (`false`).

Остановка работы сервиса это `pool.close().await`: он дожидается возврата соединений и закрывает их.

### Самозапирание

Главная беда пула описана в начале главы. Нарисуем её на двух соединениях:

```
        пул на 2 соединения
  обработчик 1: begin()  → соединение 1  ─┐
  обработчик 2: begin()  → соединение 2  ─┤ оба вызывают репозиторий с &pool
  обработчик 1: repo(&pool) ждёт свободного ┤ свободных нет, пока кто-то не сделает commit
  обработчик 2: repo(&pool) ждёт свободного ┘ а commit будет после repo
```

База ни при чём, блокировок в ней нет, поэтому ни `pg_locks`, ни логи ничего не покажут. Выручает
только `acquire_timeout`. Лекарство одно: всё, что выполняется внутри транзакции, получает соединение этой
транзакции (`&mut tx`), а не пул. Открой `visuals/pool_exhaustion.html`.

Родственная беда: `await` на чём-то медленном внутри транзакции. Транзакция держит блокировки строк до `commit`,
а HTTP-вызов к платёжному шлюзу может длиться секунды. Все, кому нужна эта строка, стоят в очереди, а
соединение занято и ничего не делает. Правило: в транзакции только работа с базой; внешний вызов делай до начала
или после `commit`. Для надёжной связки «записать в базу и сообщить наружу» понадобится outbox (запись о
сообщении в той же транзакции и отдельный отправитель), но это отдельная тема.

## Отмена и таймауты

Самая частая ошибка с таймаутами: думать, что `tokio::time::timeout` останавливает запрос.

```rust
let res = tokio::time::timeout(Duration::from_secs(2), sqlx::query("SELECT pg_sleep(30)").execute(&pool)).await;
```

Через две секунды `res` будет `Err(Elapsed)`, но это всего лишь клиент перестал ждать: future выброшен. Серверу никто
ничего не сообщил, он продолжает считать тридцать секунд, а соединение пула остаётся занятым до конца ответа:
следующий запрос на нём подождёт хвост. Так под нагрузкой копятся «призраки»: клиентов давно нет, запросы
работают, соединения заняты. Открой `visuals/query_cancel.html`.

Остановить запрос по-настоящему может только сама база. Параметр `statement_timeout` ограничивает время выполнения
одной команды, после этого база прерывает её и отвечает ошибкой `57014` (`query_canceled`). Ставить его принято на
уровне транзакции, чтобы лимит не утёк на соединение пула:

```sql
BEGIN;
SELECT set_config('statement_timeout', '800', true);   -- true: только до конца транзакции
SELECT ...;                                            -- длиннее 800 мс будет прерван
COMMIT;
```

`SET LOCAL statement_timeout = 800` делает то же самое. А вот `SET` без `LOCAL` меняет сессию, а сессия принадлежит
пулу: лимит достанется следующему случайному запросу. Ошибку `57014` ловят так же, как другие коды:
`sqlx::Error::Database(e)` и `e.code()`. Хорошая практика: ставить оба таймаута, клиентский чуть больше серверного.

## Выгрузка потоком

`fetch_all` читает всю выдачу в `Vec`: миллион строк займёт гигабайт. Метод `fetch` возвращает поток, строки
приходят по одной, по мере чтения из сокета, и пока твой код медленный, сервер сам притормаживает отправку.

```rust
let mut rows = sqlx::query_as::<_, (i64, String)>("SELECT id, name FROM guests ORDER BY id").fetch(&pool);
while let Some((id, name)) = rows.try_next().await? {
    send_to_client(id, name).await;
}
```

`try_next` приходит из трейта `TryStreamExt` крейта `futures`. В заданиях курса отдельный крейт не подключён, поэтому
трейт доступен как `course_support::pg::TryStreamExt`; в своём проекте добавь `futures = "0.3"`. Пока поток не
дочитан или не выброшен, соединение занято: внутри цикла не бери второе соединение из того же пула без нужды.
Выход из цикла по `break` безопасен: sqlx дочитает хвост ответа сам, и соединение останется годным.

## Много строк за раз

Вставить тысячу строк тысячей команд значит тысячу походов в сеть. Есть два пути.

Первый: передать столбцы массивами и развернуть их в таблицу функцией `UNNEST`.

```sql
INSERT INTO guests (name, phone) SELECT * FROM UNNEST($1::text[], $2::text[]) ON CONFLICT DO NOTHING
```

Параметров ровно столько, сколько столбцов, сколько бы ни было строк. В Rust это `.bind(&names).bind(&phones)`, а
приведение `::text[]` подсказывает базе тип массива.

Второй: `QueryBuilder::push_values`, который сам пишет `VALUES ($1, $2), ($3, $4), ...`. Он гибче, когда в строке
много разнородных полей, но упирается в потолок протокола: **не больше 65535 параметров на команду**. Это
число параметров, а не строк: четыре столбца дают не больше 16383 строк. Бить надо на пачки (`rows.chunks(N)`),
а если пачки должны быть атомарными, то в одной транзакции. Пустой вход тоже надо учесть: `push_values` без строк
выдаёт синтаксически неверный SQL.

## Размножение запросов (N+1)

Лента броней: один запрос за списком и по одному запросу на каждую бронь за именем гостя. На разработческих данных
пять броней, шесть запросов, незаметно. На проде пятьдесят броней и пятьдесят один запрос на каждый показ ленты.
Лекарство называется гидрацией: собрать ключи, взять всех одним запросом, расставить по словарю.

```rust
let guest_ids: Vec<i64> = bookings.iter().map(|b| b.guest_id).collect();
let guests: HashMap<i64, String> = sqlx::query_as::<_, (i64, String)>("SELECT id, name FROM guests WHERE id = ANY($1)")
    .bind(&guest_ids)
    .fetch_all(&pool)
    .await?
    .into_iter()
    .collect();
```

Если гости лежат в той же базе, проще `JOIN`. Гидрация нужна там, где JOIN невозможен: данные другого сервиса,
другого хранилища, или когда соединение удвоило бы строки. Проверять отсутствие N+1 надо не по времени (оно
шумит), а по числу команд: считай запросы на проводе, и тест не будет ложно срабатывать на нагруженной машине.

## Запрос, который собирается из пришедшего

Поиск по броням с необязательными фильтрами: период, статус, гость. Форма запроса зависит от набора фильтров,
значения от клиента. `QueryBuilder` делает ровно это:

```rust
let mut qb = QueryBuilder::new("SELECT id FROM bookings WHERE TRUE");
if let Some(status) = &filter.status {
    qb.push(" AND status = ").push_bind(status);
}
if let Some(min) = filter.min_nights {
    qb.push(" AND nights >= ").push_bind(min);
}
qb.push(" ORDER BY id");
let ids: Vec<i64> = qb.build_query_scalar().fetch_all(&pool).await?;
```

`push` добавляет **текст запроса** (только твой, из кода), `push_bind` добавляет **значение** параметром. Всё, что пришло
от клиента, идёт только через `push_bind`. `WHERE TRUE` убирает вопрос «это первое условие или нет».

Имена столбцов параметром передать нельзя: `ORDER BY $1` не сортирует по столбцу, а сортирует по постоянной
строке, то есть никак, и без ошибки. Поэтому сортировка по запросу клиента (`?sort=nights`) решается белым
списком: клиентская строка разбирается в `enum`, а в SQL идёт строка из кода, которую вернул метод enum.
Экранирование кавычек тут не поможет, имя столбца не строковый литерал.

Отдельная ловушка у `LIKE` и `ILIKE`: символы `%` и `_` в **значении** параметра работают как шаблон, а
обратная косая черта экранирует. Параметр защищает от инъекции, но «50%» всё равно найдёт всё, что начинается с
«50». Пользовательский текст превращают в шаблон, где перед `\`, `%` и `_` стоит `\`. Проходи по символам
за один раз, а не цепочкой `replace`: порядок замен легко перепутать, и сам символ экранирования надо
экранировать первым.

## Граница с доменом

Строка таблицы не равна доменному типу. В базе статус это текст, число лайков знаковое, и никто не мешает записать
туда мусор. Репозиторий не должен выпускать эти строки наружу. Принято держать внутри приватную структуру строки
и преобразование в доменный тип:

```rust
impl TryFrom<RoomRow> for Room {
    type Error = RepoError;
    fn try_from(row: RoomRow) -> Result<Room, RepoError> { /* проверки, отказ вместо подмены */ }
}
```

Неправильное в базе это ошибка, о которой надо громко сообщить, а не молчаливая подмена «пусть будет значение по
умолчанию». Для одной строки получается `Option<Result<_>>` после `fetch_optional` и `map`, `transpose()`
превращает его в `Result<Option<_>>`. Сам репозиторий прячется за трейтом: сервис выше зависит от трейта,
а не от Postgres, и в тестах подставляется любая реализация.

## Тесты на своей схеме

Тесты репозитория идут параллельно, и каждому нужна своя схема, иначе они будут видеть чужие таблицы. Схему
создают с уникальным именем (номер процесса и счётчик), а `search_path` выставляют **параметром подключения**:

```rust
let options = PgConnectOptions::from_str(&url)?.options([("search_path", schema.as_str())]);
let pool = PgPoolOptions::new().connect_with(options).await?;
```

Параметр действует на каждое соединение пула. Команда `SET search_path` подействовала бы на одно, и тест,
проходивший на одном соединении, начал бы случайно падать, когда пул откроет второе. В конце теста пул закрывают и
удаляют схему `DROP SCHEMA ... CASCADE`; пока соединения открыты, они держат блокировки и удаление зависает.

## Типичные ошибки

- Внутри транзакции вызвать функцию, которая берёт `&pool`: на пуле из одного соединения зависнет сразу, на
  большом под нагрузкой.
- Забыть `commit` на одном из путей: данные тихо откатываются при уничтожении транзакции.
- Считать, что `tokio::time::timeout` останавливает запрос на сервере.
- Поставить `SET statement_timeout` без `LOCAL` на соединении из пула.
- Повторять транзакцию при любой ошибке или без предела.
- Склеить имя столбца из запроса клиента в SQL текстом, не пропустив через белый список.
- Забыть пустой вход в `push_values` и 65535 параметров.
- Ходить в базу за связанной записью в цикле по результатам.
