# Транзакции, скрипты и сообщения Redis

Одна команда Redis атомарна, но жизнь редко укладывается в одну команду. Перевести очки между двумя счетами, купить последний билет, записать событие и увеличить счётчик: всё это несколько шагов, между которыми другие клиенты не должны вклиниваться. А ещё Redis умеет быть шиной сообщений: pub/sub для живых событий и Streams для очередей с подтверждением. Примеры в этой главе про сервис бронирования переговорных: слоты, брони, уведомления сотрудникам. Задачи будут про соцсеть.

## MULTI и EXEC

```
MULTI
DECRBY room:5:free 1          -> QUEUED
SADD room:5:bookings anna     -> QUEUED
EXEC                          -> [9, 1]
```

После MULTI команды не выполняются, а встают в очередь, сервер отвечает на каждую `QUEUED`. EXEC выполняет очередь подряд, ни с чем не смешивая, и возвращает массив результатов. Что важно знать:

- **это изоляция, а не откат**. Если команда упала при выполнении (например, не тот тип ключа), остальные всё равно выполнены, а в массиве EXEC на её месте лежит ошибка. Каждый элемент ответа надо проверять. Синтаксическая ошибка при постановке в очередь отменяет всю транзакцию;
- **внутри нельзя решать**: результаты придут только в EXEC, поэтому «прочитать и списать, если хватает» транзакцией не написать;
- **транзакция живёт на соединении**. Если соединение общее (мультиплексированное), чужие команды между твоими MULTI и EXEC попадут в твою очередь. Транзакцию отправляют одной неделимой пачкой или по выделенному соединению.

## WATCH: оптимистичная транзакция

```
WATCH room:5:free
GET room:5:free               -> 1
MULTI
DECR room:5:free
EXEC                          -> nil, если room:5:free изменили после WATCH
```

WATCH говорит серверу: «если этот ключ изменится до моего EXEC, отмени транзакцию». Клиент читает, решает, отправляет MULTI и EXEC, и если в ответ пришёл nil, повторяет всё сначала. Это работает хорошо, пока гонок немного; при сильной конкуренции повторы множатся. WATCH тоже состояние соединения, поэтому каждому участнику нужно своё. `UNWATCH` снимает слежку, если транзакция не понадобилась.

## Скрипты Lua

Самый мощный способ: отправить на сервер маленькую программу, которую Redis выполнит целиком, ни с чем не смешивая. Внутри можно читать, решать и писать:

```
EVAL "
  local free = tonumber(redis.call('GET', KEYS[1]) or '0')
  if free < 1 then return 0 end
  redis.call('DECR', KEYS[1])
  redis.call('SADD', KEYS[2], ARGV[1])
  return 1
" 2 room:5:free room:5:bookings anna
```

Ключи передаются отдельным списком `KEYS` (после числа ключей), остальные значения списком `ARGV`. Текст скрипта не собирают из данных: в кластере Redis по KEYS решает, на каком узле выполнять, и все ключи скрипта должны жить на одном узле. Пока скрипт работает, сервер не делает ничего другого, поэтому скрипты пишут короткими.

Сервер кэширует скрипты по SHA1 текста: `SCRIPT LOAD` возвращает хеш, `EVALSHA хеш ...` вызывает без пересылки текста. Кэш пропадает при перезапуске и `SCRIPT FLUSH`, и тогда EVALSHA отвечает ошибкой `NOSCRIPT`. Надёжный клиент в этом случае один раз отправляет EVAL с полным текстом: он и выполнит скрипт, и вернёт его в кэш.

## Pub/sub

```
SUBSCRIBE rooms:events        -> ["subscribe", "rooms:events", 1]
                                 ["message", "rooms:events", "room 5 booked"]   (приходит само)
PUBLISH rooms:events "room 5 booked"     (с другого соединения)
```

После SUBSCRIBE соединение меняет режим: сервер сам присылает кадры `["message", канал, данные]`, когда кто-то публикует. На таком соединении разрешены только команды подписки, PING и QUIT, поэтому у сервиса с подписками два соединения: одно слушает, другое работает.

Pub/sub ничего не хранит. Сообщение получают только те, кто подписан в момент PUBLISH; отключившийся на секунду подписчик пропустит всё за эту секунду. Это хорошо для живых событий (кто-то печатает, обнови экран) и плохо для того, что нельзя терять.

## Streams

Стрим это журнал записей с возрастающими id (`1729600000000-0`: время и номер):

```
XADD room:events MAXLEN ~ 10000 * kind booked room 5
XREAD COUNT 10 BLOCK 5000 STREAMS room:events 1729600000000-0
XRANGE room:events - + COUNT 5
```

- запись хранится, и её можно читать сколько угодно раз и с любого места;
- `MAXLEN ~ N` обрезает стрим примерно до N записей при каждой записи. С тильдой Redis удаляет только целые внутренние узлы, это почти бесплатно; точная обрезка дороже;
- `XREAD BLOCK` ждёт записи новее указанного id без опроса, но на время ожидания занимает соединение.

## Группы потребителей

Группа превращает стрим в очередь задач для нескольких воркеров:

```
XGROUP CREATE room:events mailers $ MKSTREAM
XREADGROUP GROUP mailers worker-1 COUNT 10 STREAMS room:events >
XACK room:events mailers 1729600000000-0
XPENDING room:events mailers
XAUTOCLAIM room:events mailers worker-2 60000 0-0 COUNT 100
```

- каждое сообщение достаётся одному воркеру группы; `>` значит «ещё никому не выданные»;
- выданное сообщение числится в списке ожидающих (pending) за воркером, пока он не подтвердит его XACK;
- если воркер упал до XACK, сообщение висит за ним. XAUTOCLAIM переписывает на другого воркера сообщения, которые ждут дольше срока. Срок берут больше обычного времени обработки, иначе медленный, но живой воркер потеряет работу;
- `MKSTREAM` создаёт стрим вместе с группой, а повторное создание отвечает ошибкой `BUSYGROUP`, которую при старте воркера считают успехом.

Это гарантия «хотя бы один раз»: при сбое между действием и XACK сообщение обработается повторно. Поэтому обработчик должен быть идемпотентным. Посмотри визуализации «WATCH и оптимистичная транзакция» и «Группы потребителей в Streams».

## Streams или JetStream

Обе вещи дают журнал с группами потребителей и подтверждением. Redis Streams живут в памяти, просты и быстры, хороши, когда Redis уже есть, а объём умеренный. JetStream из раздела про сервисы хранит на диске, умеет повторы по расписанию, дедупликацию, репликацию между узлами и потребителей в разных местах. Для важной шины событий между сервисами чаще берут JetStream, для внутренних очередей одного сервиса хватает Streams.

## Типичные ошибки

- Ждать отката от EXEC; не проверять элементы его ответа.
- MULTI по общему мультиплексированному соединению отдельными командами.
- «Прочитать и решить» внутри MULTI вместо WATCH или Lua.
- Собирать текст скрипта из данных вместо KEYS и ARGV; долгие скрипты.
- EVALSHA без запасного EVAL на NOSCRIPT.
- Обычные команды на соединении подписчика.
- Pub/sub для событий, которые нельзя терять.
- Стрим без MAXLEN; XREADGROUP > в надежде получить зависшие сообщения.
