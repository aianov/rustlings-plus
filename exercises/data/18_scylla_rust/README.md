# Драйвер scylla

CQL ты уже знаешь, теперь нужно говорить на нём из Rust. Официальный драйвер это крейт `scylla` (у нас версия 0.12). Он асинхронный, работает поверх tokio, знает топологию кластера и сам отправляет запросы туда, где лежат данные. В этой главе все примеры про журнал датчиков умного дома: таблица `readings (sensor_id, at, value, unit)`, ключ партиции датчик, внутри по времени. Задачи будут про чат.

## Session и SessionBuilder

`Session` это всё соединение с кластером: пул соединений ко всем узлам (на каждый шард узла по соединению), знание топологии, схемы и подготовленных запросов. Строится она через `SessionBuilder`:

```rust
let session: Session = SessionBuilder::new()
    .known_node("10.0.0.5:9042")
    .connection_timeout(Duration::from_secs(5))
    .build()
    .await?;
```

Достаточно указать один узел: остальные драйвер узнает от него. Адрес берут из окружения, а не из кода. Сессия дорогая в создании и потокобезопасна, поэтому на сервис она одна: её кладут в `Arc<Session>` и раздают обработчикам клоны указателя. Сессию можно переключить на keyspace (`use_keyspace`), но если сервисы делят кластер или сессию, надёжнее писать имя keyspace прямо в запросах: `SELECT ... FROM home.readings`.

## Запросы и параметры

`session.query(текст, значения)` выполняет запрос. Значения передаются вторым аргументом, а в тексте на их месте стоят маркеры `?`:

```rust
session
    .query("INSERT INTO readings (sensor_id, at, value, unit) VALUES (?, ?, ?, ?)", (sensor, at, 21.5_f64, "°C"))
    .await?;
```

Значения никогда не вклеиваются в текст: никакого экранирования, никаких инъекций, типы проверяются драйвером. Пустой набор значений это `()`. Вклеивать в текст можно только то, что задаёт сам сервис: имена keyspace и таблиц.

## Чтение строк

`QueryResult` содержит строки ответа. Типизированное чтение:

```rust
let res = session.query("SELECT at, value FROM home.readings WHERE sensor_id = ?", (sensor,)).await?;
for row in res.rows_typed::<(CqlTimestamp, f64)>()? {
    let (at, value) = row?;
}
```

Ошибка возможна на двух уровнях: у ответа вообще нет строк (`rows_typed` вернёт ошибку) и отдельная строка не подошла по типу (ошибка у элемента). Есть помощники для частых случаев: `first_row_typed` (ровно хотя бы одна строка), `maybe_first_row_typed` (одна строка или ничего), `single_row_typed` (ровно одна).

Строку можно читать и в структуру через `#[derive(FromRow)]`:

```rust
#[derive(FromRow)]
struct Reading { at: CqlTimestamp, value: f64, unit: Option<String> }
```

Важно: в драйвере 0.12 FromRow читает столбцы **по позиции**, имена не сравниваются. Поэтому список в SELECT пишут явно и в порядке полей. `SELECT *` отдаёт все столбцы таблицы в её порядке и меняется с каждым ALTER TABLE.

Любой столбец вне ключа может быть NULL (его не записали, удалили или он истёк). Поле для такого столбца это `Option<T>`. Пустая коллекция в Scylla тоже читается как NULL: у пустой коллекции просто нет ячеек.

Типы: `int` это `i32`, `bigint` это `i64`, `text` это `String`, `boolean` это `bool`, `double` это `f64`, `uuid` это `uuid::Uuid`, `timeuuid` это `CqlTimeuuid`, `timestamp` это `CqlTimestamp` (миллисекунды, без фичи chrono), `set<T>` это `HashSet<T>` или `Vec<T>`, `list<T>` это `Vec<T>`, `map<K, V>` это `HashMap<K, V>`.

## Запись структурой

Для записи есть `#[derive(SerializeRow)]`, и она, в отличие от чтения, связывает поля **по именам**: драйвер знает имена столбцов за маркерами из метаданных подготовленного запроса.

```rust
#[derive(SerializeRow)]
struct NewReading { sensor_id: i32, at: CqlTimestamp, value: f64, unit: String }

session.query("INSERT INTO home.readings (unit, value, at, sensor_id) VALUES (?, ?, ?, ?)", &reading).await?;
```

Порядок столбцов в запросе теперь не важен, а пропущенное поле даёт понятную ошибку.

## NULL и unset

У значения в запросе три состояния: значение, NULL и «не задано». NULL означает удалить значение (это запись надгробия). «Не задано» означает пропустить столбец. В Rust `Option::None` сериализуется как NULL, а для пропуска есть `scylla::frame::value::MaybeUnset`:

```rust
let unit = MaybeUnset::Unset;              // столбец unit не трогать
let value = MaybeUnset::Set(22.0_f64);     // а value записать
session.execute(&update, (value, unit, sensor, at)).await?;
```

Частичное обновление через Option стирает всё, что клиент не прислал. Через MaybeUnset один подготовленный запрос обслуживает любые сочетания полей.

## Подготовленные запросы

`session.prepare(текст)` разбирает запрос на сервере один раз и возвращает `PreparedStatement`; `session.execute(&prepared, значения)` выполняет его. Плюсы:

- сервер не разбирает текст каждый раз, по сети уходят только идентификатор и значения;
- драйвер знает типы параметров и проверяет их до отправки;
- драйвер знает, какие параметры образуют ключ партиции, считает токен на клиенте и отправляет запрос сразу на реплику-владельца (token-aware routing). Посмотри визуализацию «Маршрутизация по токену».

Кстати, `query` с непустыми параметрами внутри всё равно готовит запрос, просто каждый раз заново, а это лишний круг. Поэтому store-слой готовит свои запросы один раз при создании и хранит в полях. Ошибка в тексте запроса тогда всплывает на старте сервиса, а не на первом вызове.

У подготовленного запроса есть свойства:

- `set_consistency(Consistency::Quorum)`: сколько реплик должны ответить. QUORUM на запись и на чтение вместе гарантируют, что чтение увидит подтверждённую запись;
- `set_is_idempotent(true)`: обещание, что запрос безопасно повторить. Драйвер повторяет после ошибок и делает спекулятивные дубли только для таких. Вставка с готовым ключом идемпотентна, прибавление счётчика нет;
- `set_page_size(n)`: размер страницы ответа (без него ответ приходит целиком).

## Страницы

Scylla умеет отдавать большие ответы страницами. В драйвере 0.12 размер страницы по умолчанию не задан, и тогда ответ приходит целиком: на большой партиции это вся партиция в памяти сервиса. Поэтому у запросов, которые могут вернуть много строк, размер страницы задают явно. Важная ловушка: с заданным размером `query` и `execute` возвращают **одну страницу**. Если в партиции больше строк, ответ выглядит полным, но это не так.

Три способа работы со страницами:

- `execute_paged(&prepared, значения, состояние)` выполняет одну страницу. В результате поле `paging_state: Option<Bytes>`: закладка, с которой сервер продолжит. `None` значит, что больше ничего нет;
- состояние непрозрачно: клиент только хранит и возвращает его. Из него получается курсор для API «загрузить ещё»: сервис превращает байты в строку, отдаёт клиенту и ничего не помнит между запросами (визуализация «Состояние пагинации как курсор»);
- `execute_iter(prepared, значения)` возвращает поток строк, который сам ходит за следующими страницами. В памяти одна страница, поэтому так читают выгрузки и отчёты любого объёма:

Поток читают в цикле через `next().await` из трейта `futures::StreamExt`: каждый элемент это `Result` со строкой, а `into_typed::<T>()` превращает поток сырых строк в поток значений нужного типа. Цикл кончается, когда страницы закончились.

## Ошибки

Почти всё возвращает `QueryError`. Внутри него:

- `QueryError::DbError(DbError, String)`: ошибку вернул сервер. Варианты `DbError`: `Invalid` и `SyntaxError` (запрос неверен, это баг), `Unavailable` (живых реплик меньше, чем требует consistency), `Overloaded`, `ReadTimeout` и `WriteTimeout` (реплики не ответили в срок), `AlreadyExists`, `Unauthorized` и другие;
- `QueryError::IoError`: оборвалось соединение;
- `QueryError::TimeoutError` и `RequestTimeout`: истёк срок на стороне клиента.

Store-слой переводит их в свои варианты, по которым код выше принимает решения: повторить позже, отдать 503, считать багом. Помни про таймауты записи: запись могла примениться, просто ответ не дошёл. Повторять можно только идемпотентное.

## Схема и миграции

DDL (CREATE TABLE, ALTER) в кластере расходится по узлам не мгновенно. Следующий запрос может попасть на узел, который о новой таблице ещё не знает. Поэтому миграции после DDL вызывают `session.await_schema_agreement().await?` и ждут, пока все узлы договорятся о версии схемы.

## Типичные ошибки

- Новая сессия на каждый запрос вместо одной в Arc.
- Значения, вклеенные в текст запроса через format!.
- `SELECT *` в структуру, которая читается по позиции.
- Поле String для столбца, который может быть NULL.
- Частичное обновление через Option вместо MaybeUnset.
- `prepare` при каждом вызове.
- `query` по большой партиции в надежде получить все строки.
- Повтор неидемпотентного запроса после таймаута.
