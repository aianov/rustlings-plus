# Хранилища вместе

У соцсети теперь три хранилища. Postgres хранит правду: пользователей, посты, подписки, лайки. Scylla хранит ленты, потому что ленты огромные и читаются одной партицией. Redis хранит кэши и счётчики, потому что они должны отвечать за миллисекунды. Каждое хранилище ты уже умеешь использовать по отдельности. Эта глава про стыки: как изменение в Postgres доезжает до Scylla и Redis без потерь, без дублей и в правильном порядке. Примеры в этой главе про сервис заказов в ресторане: заказ в Postgres, экран кухни как проекция, кэш статусов для клиента. Задачи будут про соцсеть.

## Двойная запись

Самое очевидное решение: записать заказ в Postgres и тут же отправить событие в брокер (или обновить Scylla, или сбросить кэш). Это двойная запись, и она не работает при сбоях:

- **событие до коммита**: транзакция может откатиться, а событие уже ушло. Кухня готовит заказ, которого нет;
- **событие после коммита**: процесс может упасть между коммитом и отправкой. Заказ есть, а кухня о нём не узнала никогда.

Две разные системы нельзя обновить атомарно, и никакой порядок вызовов это не исправит.

## Outbox

Решение: событие тоже пишется в Postgres, в таблицу `outbox`, **той же транзакцией**, что и заказ.

```sql
BEGIN;
INSERT INTO orders (id, table_no, dishes) VALUES (501, 7, '...');
INSERT INTO outbox (aggregate_id, kind, payload) VALUES (501, 'order_placed', '{"table": 7}');
COMMIT;
```

Либо есть и заказ, и событие, либо ни того, ни другого. Отправкой в брокер занимается отдельный процесс, relay: он читает неотправленные строки outbox, публикует их и отмечает отправленными. Брокер может лежать хоть час, события не потеряются, а накопятся.

## Relay

```sql
BEGIN;
SELECT id, aggregate_id, kind, payload FROM outbox
 WHERE sent_at IS NULL ORDER BY id LIMIT 100
 FOR UPDATE SKIP LOCKED;
-- публикация каждого события
UPDATE outbox SET sent_at = now() WHERE id = ANY($1);   -- только опубликованные
COMMIT;
```

- `FOR UPDATE SKIP LOCKED` позволяет запустить несколько relay: каждый забирает свою пачку, а занятые строки другие просто пропускают;
- отправленными отмечают только реально опубликованные события. Ошибка публикации останавливает пачку, остаток уйдёт на следующем проходе;
- если relay упал после публикации и до коммита, событие уйдёт ещё раз. Доставка «хотя бы один раз», и с этим работают потребители.

**Порядок.** SKIP LOCKED не держит порядок внутри агрегата: пока один relay медленно публикует «заказ принят», другой может взять «заказ отменён» того же заказа. Если порядок важен, relay берёт событие, только когда у агрегата нет более ранних неотправленных событий (условие `NOT EXISTS` в выборке), или агрегаты распределяются по relay хешем, как партиции.

**Пробуждение.** Опрос outbox раз в секунды добавляет задержку. Postgres умеет будить слушателей: `NOTIFY канал` в транзакции заказа доходит до тех, кто сделал `LISTEN`, сразу после коммита. Уведомления не хранятся, поэтому опрос остаётся страховкой: relay просыпается от уведомления или по таймеру, и в любом случае читает outbox целиком.

## Inbox

Потребитель получает каждое событие хотя бы один раз, а иногда дважды. Inbox делает эффект однократным: id события записывается в таблицу `inbox` той же транзакцией, что и эффект.

```sql
BEGIN;
INSERT INTO inbox (event_id) VALUES (9001) ON CONFLICT DO NOTHING;   -- 0 строк значит дубль
UPDATE kitchen_stats SET orders = orders + 1;                         -- только если строка вставилась
COMMIT;
```

Уникальный ключ закрывает и гонку двух одновременных дублей: вторая вставка дождётся первой транзакции и получит конфликт. Отметка и эффект должны быть одной транзакцией, иначе сбой между ними даёт дубль или потерю.

## Проекции

Проекция это производные данные, построенные из событий: экран кухни, лента подписчика в Scylla. События приходят повторно и не по порядку, и проекция должна выдерживать оба случая.

- **Идемпотентность.** Запись проекции по ключу (`INSERT` в Scylla это upsert) повторяется безопасно.
- **Порядок через версии.** Если у события есть версия (момент события в микросекундах), её можно записать как метку времени: `INSERT ... USING TIMESTAMP ?` и `DELETE FROM ... USING TIMESTAMP ? WHERE ...`. Scylla сама оставит более позднюю версию, и запоздавшее «создан» не воскресит удалённое.

Для Redis тот же приём делается скриптом: хранить версию рядом со значением и обновлять, только если версия события больше. Или проще: по событию не обновлять кэш, а удалять ключ, и тогда порядок вообще неважен, а следующий читатель пойдёт в базу.

## Сверка

Даже правильно собранный конвейер однажды разойдётся с источником правды: баг, ручная правка, частичный сбой. Поэтому производные данные периодически сверяют: пересчитывают из Postgres и чинят только расхождения.

```sql
UPDATE kitchen_stats s SET orders = c.n
  FROM (SELECT ...) c
 WHERE ... AND s.orders <> c.n
RETURNING s.day;
```

Число исправлений идёт в метрики: если оно растёт, где-то сломан конвейер.

Посмотри визуализацию «Outbox, relay и потребители»: весь путь события от транзакции до ленты и кэша, включая повтор после сбоя.

## Типичные ошибки

- Публикация события до коммита или сразу после него вместо outbox.
- Outbox, записанный отдельной транзакцией от данных.
- Несколько relay без SKIP LOCKED; отметка отправленными всей пачки, даже неопубликованной.
- Нарушение порядка событий одного агрегата параллельными relay.
- Потребитель без inbox или с отметкой отдельно от эффекта.
- Проекция, которая зависит от порядка доставки.
- Отсутствие сверки: расхождения копятся молча.
