# ScyllaDB и CQL

Представь службу доставки. Каждая посылка за свою жизнь получает десятки событий: принята, на сортировке, в пути, в пункте выдачи. Посылок миллиарды, событий в сотни раз больше, и пишутся они непрерывно со всех складов. А читают их почти всегда одинаково: «покажи историю этой посылки, свежие сверху». Postgres справится с этим до определённого объёма, а дальше упрётся в один сервер. ScyllaDB создана ровно под такую нагрузку: много записей, предсказуемые запросы по ключу, горизонтальное масштабирование добавлением узлов.

Чат соцсети это та же история: сообщений очень много, пишутся они постоянно, а читаются кусками одного чата. Поэтому в нашем бэкенде сообщения будут жить в Scylla. Эта глава про язык CQL и про то, как устроено хранение: без второго запросы CQL кажутся набором странных запретов.

## Кольцо узлов и токены

Кластер Scylla это несколько равноправных узлов, главного нет. Каждая строка таблицы принадлежит **партиции**, а партиция определяется **ключом партиции**. Ключ хешируется (Murmur3) в число, токен. Все возможные токены образуют кольцо, и каждый узел отвечает за свои участки кольца.

```
            токен 0
         ┌───────────┐
   узел C│           │узел A        token(parcel 'RU123') = 58
         │   кольцо  │                      │
   ......│           │.....                 ▼
         └───────────┘               попадает в участок узла B,
            узел B                   копии на следующих по кругу
```

Отсюда главное свойство: зная ключ партиции, клиент или координатор сразу знает, на каких узлах лежат данные. Запрос по ключу идёт в несколько узлов, а не во все. Запрос без ключа партиции не знает, куда идти, и вынужден спрашивать всех. Посмотри визуализацию «Кольцо токенов и партиции».

**Репликация** задаётся у keyspace (пространства ключей, аналог базы данных): сколько копий каждой партиции хранить. `SimpleStrategy` раскладывает копии по следующим узлам кольца и годится для одного дата-центра и разработки, `NetworkTopologyStrategy` задаёт число копий в каждом дата-центре и используется в бою.

```sql
CREATE KEYSPACE IF NOT EXISTS delivery
  WITH replication = {'class': 'NetworkTopologyStrategy', 'dc_moscow': 3};
```

## Путь записи

Запись в Scylla очень дешёвая, и важно понимать почему:

1. запись дописывается в конец **commitlog** на диске (последовательная запись, переживает падение узла);
2. запись кладётся в **memtable**, отсортированную структуру в памяти; клиенту уже можно отвечать;
3. переполненная memtable сбрасывается на диск в новый неизменяемый файл **SSTable**;
4. со временем **уплотнение** (compaction) сливает SSTable в более крупные и выбрасывает старые версии.

Никакого чтения перед записью, никакого поиска места на диске, никаких блокировок. Цена переносится на чтение: строка может быть размазана по memtable и нескольким SSTable, и чтение склеивает версии. Для каждой ячейки побеждает версия с **большей меткой времени записи** (last write wins). Это не та запись, что пришла последней, а та, у которой метка больше. Визуализация «Путь записи» показывает это по шагам.

Из той же неизменяемости следует судьба удалений: стереть строку из готового SSTable нельзя, поэтому DELETE это тоже запись, маркер-**надгробие** (tombstone). Чтение обязано его увидеть, а физически данные уходят при уплотнении после `gc_grace_seconds`.

## Ключ партиции и ключ кластеризации

Первичный ключ в CQL состоит из двух частей:

```sql
CREATE TABLE parcel_events (
    parcel_id text,
    at        timestamp,
    status    text,
    place     text,
    PRIMARY KEY (parcel_id, at)
) WITH CLUSTERING ORDER BY (at DESC);
```

- `parcel_id` это **ключ партиции**: все события одной посылки лежат вместе, на одних узлах;
- `at` это **ключ кластеризации**: он различает строки внутри партиции и задаёт, в каком порядке они хранятся на диске. `CLUSTERING ORDER BY (at DESC)` хранит свежие первыми, и «последние 5 событий» это просто первые 5 строк партиции.

Ключ партиции может быть составным, тогда он берётся в дополнительные скобки:

```sql
PRIMARY KEY ((warehouse_id, day), scanned_at, parcel_id)
```

Здесь партиция это склад за один день. Хеш считается от **пары целиком**, поэтому запрос обязан указать равенством оба столбца: склад без дня найти нельзя, разные дни одного склада лежат на разных узлах. Так режут партиции, которые иначе росли бы без предела.

И главное правило: первичный ключ однозначно определяет строку. Если два события посылки придут в одну миллисекунду, а ключ `(parcel_id, at)`, второе молча заменит первое. Ключ кластеризации должен быть уникальным внутри партиции: добавляют ещё столбец или используют timeuuid.

## Что разрешено в WHERE

Запреты CQL выглядят странно, пока не вспомнишь, как лежат данные. Все они следуют из одного: Scylla выполняет только запросы, для которых известно, **куда идти** и **откуда и докуда читать**.

- Ключ партиции указывается **целиком и равенством** (или `IN` по списку значений).
- Столбцы кластеризации ограничиваются **по порядку**: все предыдущие равенством, а последний ограниченный может быть диапазоном (`<`, `>`, `<=`, `>=`).
- Условие на обычный столбец или на столбец кластеризации «через голову» предыдущего требует `ALLOW FILTERING`.

Для ключа `PRIMARY KEY ((warehouse_id, day), scanned_at, parcel_id)`:

```sql
-- можно: партиция целиком, диапазон по первому столбцу кластеризации
SELECT * FROM scans WHERE warehouse_id = 5 AND day = 20261020 AND scanned_at > '2026-10-20 12:00:00+0000';
-- нельзя: parcel_id без scanned_at, строки с нужным parcel_id разбросаны по всей партиции
SELECT * FROM scans WHERE warehouse_id = 5 AND day = 20261020 AND parcel_id = 'RU123';
```

`ALLOW FILTERING` это не «разрешить запрос», а согласие на полный обход: прочитать всё и выбросить лишнее. На десяти строках незаметно, на миллиардах это минуты и нагрузка на весь кластер. В Scylla принято иначе: под каждый новый запрос заводят **новую таблицу**, где нужный столбец стоит в ключе, и пишут данные в обе таблицы.

## Запись: upsert без проверок

`INSERT` и `UPDATE` в Scylla почти одно и то же: оба пишут значения перечисленных столбцов по ключу. Существует ли строка, никто не проверяет:

- нет ошибки «уже существует»: вставка с тем же ключом перезаписывает значения;
- `UPDATE` несуществующей строки её создаёт;
- столбцы, которых нет в команде, не трогаются;
- явный `null` это не «пропусти», а запись надгробия: значение удаляется.

```sql
-- обновили только место: статус и всё остальное остались как были
UPDATE parcel_last SET place = 'Казань' WHERE parcel_id = 'RU123';
```

Это делает записи **идемпотентными**: повторить запись после таймаута безопасно. Но это же значит, что «занять имя, если свободно» обычным INSERT не сделать: второй молча перезапишет первого. Для таких случаев есть лёгкие транзакции, о них глава про продвинутую Scylla.

## Удаление

`DELETE` умеет три вещи: удалить строку, удалить отдельные столбцы строки и удалить диапазон строк партиции.

```sql
DELETE FROM parcel_events WHERE parcel_id = 'RU123' AND at = '2026-10-20 10:00:00+0000';
DELETE place FROM parcel_events WHERE parcel_id = 'RU123' AND at = '2026-10-20 11:00:00+0000';
DELETE FROM parcel_events WHERE parcel_id = 'RU123' AND at < '2026-01-01 00:00:00+0000';
```

Каждое это надгробие. Одно надгробие на диапазон гораздо дешевле миллиона надгробий на отдельные строки: и для записи, и для каждого будущего чтения, которое будет сквозь них продираться.

## timeuuid

`timeuuid` это UUID версии 1: в нём зашито время создания, а остальные биты делают его уникальным. Сравниваются такие значения сначала по времени, поэтому таблица с `id timeuuid` в ключе кластеризации сама сортирует строки по времени, а одновременные записи не сталкиваются.

- `now()` создаёт новый timeuuid текущего момента;
- `toTimestamp(id)` достаёт из него время;
- `minTimeuuid(t)` и `maxTimeuuid(t)` дают самый маленький и самый большой timeuuid момента `t`. Они нужны только для условий в запросах, а не как значения новых строк: они не уникальны.

Например, события сканера за 20 октября:

```sql
SELECT toTimestamp(id), status FROM scanner_log
 WHERE scanner_id = 9
   AND id > maxTimeuuid('2026-10-19 23:59:59+0000')
   AND id < minTimeuuid('2026-10-21 00:00:00+0000');
```

Подумай, какой из двух вариантов нужен на каждой границе, если граница включается и если нет: у одной миллисекунды много разных timeuuid.

## Коллекции, frozen и UDT

У столбца может быть тип-коллекция: `set<text>`, `list<int>`, `map<text, int>`. Элементы коллекции хранятся как отдельные ячейки, поэтому их можно добавлять без чтения:

```sql
UPDATE parcels SET labels = labels + {'хрупкое'}, attempts['курьер'] = 2 WHERE parcel_id = 'RU123';
```

Свой составной тип объявляется через `CREATE TYPE` (UDT, user-defined type):

```sql
CREATE TYPE address (city text, street text);
```

Внутри коллекции UDT не раскладывается на ячейки и должен быть **frozen**: сериализуется целиком в одно значение и меняется только заменой целиком. `frozen` можно поставить и на коллекцию: тогда она тоже становится одним значением.

Коллекции хороши для небольших наборов. Коллекция читается целиком вместе со строкой, а каждое изменение элемента это ещё одна ячейка или надгробие, поэтому список на десятки тысяч элементов это ошибка модели.

## Static-столбцы

Иногда у партиции есть данные, общие для всех её строк: получатель посылки, название склада. Хранить их в каждой строке расточительно, а в отдельной таблице неудобно. Для этого есть `STATIC`:

```sql
CREATE TABLE parcel_events (
    parcel_id text, at timestamp, status text,
    recipient text STATIC,
    PRIMARY KEY (parcel_id, at)
);
INSERT INTO parcel_events (parcel_id, recipient) VALUES ('RU123', 'Анна');
```

Static-столбец хранится один раз на партицию и виден из каждой её строки. Записывать его можно, указав только ключ партиции.

## LIMIT и PER PARTITION LIMIT

`LIMIT n` ограничивает весь ответ. `PER PARTITION LIMIT n` ограничивает число строк **в каждой партиции** ответа, и вместе с порядком кластеризации он даёт «первые n строк каждой партиции» одним запросом:

```sql
SELECT parcel_id, at, status FROM parcel_events
 WHERE parcel_id IN ('RU1', 'RU2', 'RU3') PER PARTITION LIMIT 1;
```

`IN` по ключу партиции удобен для небольших списков: координатор опросит несколько партиций. На тысячах значений он перегружает координатор, и тогда лучше отдельная таблица под этот запрос.

## Типичные ошибки

- Ключ кластеризации не уникален: одновременные записи молча затирают друг друга.
- Сортировка на лету вместо порядка кластеризации в схеме.
- `ALLOW FILTERING` «чтобы заработало» вместо отдельной таблицы под запрос.
- Явный `null` в INSERT ради «остальных полей», который стирает данные.
- Ожидание, что INSERT проверит уникальность.
- Удаление миллионами одиночных DELETE вместо диапазона или TTL.
- Партиция без предела роста: всё в одном ключе на годы.
