# sqlx: Postgres из Rust

До сих пор мы говорили с базой на её языке. Теперь приложение на Rust должно делать то же самое
само: принять запрос пользователя, сходить в Postgres, превратить строки в структуры и вернуть
ответ. Неприятная часть в том, что на границе двух миров ошибки прячутся. Тип в базе один, в Rust
другой, столбец назвали иначе, чем поле, где-то лежит NULL, а программа об этом не знала.
Компилятор тут помогает меньше, чем привычно, и многое всплывает только при запуске. Поэтому в этой
главе мы разбираем не только как позвать базу, но и где именно она обычно ломается.

Примеры в тексте про приют для животных (`animals`, `adopters`), задачи про соцсеть. Перенеси идею.

## Пул, а не соединение

Соединение с Postgres дорого открывать (сеть, рукопожатие, авторизация) и по нему одновременно идёт
один запрос. Поэтому приложение держит пул: несколько открытых соединений, которые выдаются на время
запроса и возвращаются обратно.

```rust
use sqlx::PgPool;

let pool = PgPool::connect("postgres://user:pass@127.0.0.1:5432/shelter").await?;
```

`PgPool` дёшево клонируется (внутри `Arc`), его кладут в состояние сервиса и раздают задачам.
Адрес берут из переменной окружения, а не зашивают в код: в курсе это `RUSTLINGS_PG_URL`.
Если свободных соединений нет, запрос ждёт своей очереди, но не вечно: через `acquire_timeout` (по умолчанию 30 секунд) вместо результата придёт ошибка `PoolTimedOut`. Поэтому подключение к адресу, где никто не слушает, тоже падает не сразу.

Подключение возвращает `Result`, и это нормально: база может быть недоступна, а решать, что с этим
делать (повторить, упасть с понятным сообщением), должен вызывающий код, а не паника внутри.

## Путь одного запроса

Открой визуализацию `visuals/query_roundtrip.html`, она показывает всё по шагам. Если коротко:

```
 твоя задача              PgPool                     Postgres
     |  fetch_one(&pool)    |                           |
     |--------------------->| выдаёт свободное c1       |
     |                      |---- Parse: текст с $1 --->|  разбор, план, запомнил как s1
     |                      |---- Bind: $1 = 7 -------->|  значения отдельно от текста
     |                      |---- Execute ------------->|
     |<-- DataRow, строки с типами ---------------------|
     |                      | c1 вернулось в пул        |
```

Запрос состоит из двух частей, которые едут по проводу раздельно: текст с метками `$1`, `$2` и
значения. Сервер разбирает текст один раз (на соединении он запоминает результат под именем, это кэш
подготовленных запросов), а потом подставляет значения как данные. Из этого следуют два важных
вывода. Первый: значение никогда не становится кодом, поэтому SQL-инъекции через параметры
невозможны. Второй: если у соединения уже есть готовый разбор, повторный запрос идёт быстрее.

А вот что параметрами быть не может: названия таблиц и столбцов, ключевые слова. Метка `$1` это
всегда значение. Запрос с `'$1'` в кавычках не получит параметра вовсе: для сервера это просто
строка из двух символов. Лишний `bind` при этом принимается молча, а ошибка придёт из другого места: `WHERE id = '$1'` попытается превратить текст `$1` в число bigint и упадёт на этом.

## Запрос, bind и чтение результата

```rust
use sqlx::Row;

let rows = sqlx::query("SELECT name, age FROM animals WHERE species = $1 AND age >= $2")
    .bind("cat")
    .bind(3_i32)
    .fetch_all(&pool)
    .await?;

for row in &rows {
    let name: String = row.get("name");
    let age: i32 = row.get("age");
}
```

`query` собирает запрос, `bind` добавляет значения по порядку (первый `bind` это `$1`), последний
метод запускает. Из строки значение достаёт `row.get("столбец")`; тип можно указать слева от
`=` или через `get::<String, _>`. Если тип Rust не подходит к типу столбца или столбца с таким
именем нет, `get` паникует, а его осторожная версия `try_get` возвращает `Result`. Паника в
обработчике запроса это не то, чего хочется, поэтому дальше мы почти не читаем строки вручную.

### Какой fetch выбрать

| метод | сколько строк ждёшь | что вернёт |
|---|---|---|
| `fetch_all` | сколько угодно, включая ноль | `Vec<Row>` |
| `fetch_optional` | ноль или одна | `Option<Row>` |
| `fetch_one` | ровно одна | `Row`, а если строки нет, ошибка `RowNotFound` |
| `execute` | строки не нужны | сколько строк затронуто (`rows_affected()`) |

Выбор метода это часть контракта функции. Типичная беда: «найти приюта кота по кличке» написано
через `fetch_one`, и на отсутствующую кличку приложение отвечает 500 вместо 404. Если «нет такой
строки» нормальный исход, нужен `fetch_optional`. А `fetch_one` оставь для случая, когда строка
обязана быть и её отсутствие означает баг. Не лечи это `.ok()` на всём результате: он заодно
спрячет упавшую базу.

`UPDATE` и `DELETE` не находят нужную строку без ошибки: просто затрагивают ноль строк. Узнать,
что произошло, помогает `rows_affected()`. Проверку «эта строка моя» удобно встроить в `WHERE`
(`... WHERE id = $1 AND owner_id = $2`), тогда проверка и действие становятся одной командой,
и между ними никто не вклинится.

## Структуры вместо ручного чтения

```rust
#[derive(sqlx::FromRow)]
struct Animal {
    id: i64,
    name: String,
    age: i32,
}

let cats: Vec<Animal> = sqlx::query_as::<_, Animal>("SELECT id, name, age FROM animals WHERE species = $1")
    .bind("cat")
    .fetch_all(&pool)
    .await?;
```

`FromRow` сопоставляет поля со столбцами **по имени**. Лишние столбцы в результате не мешают, а
отсутствующий даёт ошибку `ColumnNotFound` при выполнении, не при компиляции. Если в запросе
столбец называется иначе, чем поле, переименуй его псевдонимом (`SELECT shelter_name AS name`)
или атрибутом на поле (`#[sqlx(rename = "shelter_name")]`). Псевдоним в запросе чаще лучше:
структура не привязана к схеме.

Когда нужно одно значение, структура лишняя. Для этого есть `query_scalar`:

```rust
let has_dogs: bool = sqlx::query_scalar("SELECT EXISTS (SELECT 1 FROM animals WHERE species = 'dog')")
    .fetch_one(&pool)
    .await?;
```

Новую строку, вместе со значениями, которые проставила база, читают за один запрос через
`INSERT ... RETURNING` и `query_as`. Ещё один запрос после вставки не нужен.

## Типы: что чему соответствует

Sqlx строго сверяет типы столбца и типа Rust при выполнении и не округляет и не сужает молча.

| Postgres | Rust |
|---|---|
| `smallint` | `i16` |
| `integer` | `i32` |
| `bigint` | `i64` |
| `real`, `double precision` | `f32`, `f64` |
| `boolean` | `bool` |
| `text`, `varchar` | `String` (или `&str` при передаче) |
| `bytea` | `Vec<u8>` |
| `uuid` | `uuid::Uuid` |
| `timestamptz` | `chrono::DateTime<Utc>` |
| `timestamp` (без пояса) | `chrono::NaiveDateTime` |
| `date` | `chrono::NaiveDate` |
| `jsonb` | `serde_json::Value` или `sqlx::types::Json<T>` |
| массив `bigint[]` | `Vec<i64>` |
| любой столбец, допускающий NULL | `Option<тип выше>` |
| `numeric` | нужен отдельный крейт (`rust_decimal`, `bigdecimal`), в курсе его нет |

Из таблицы вытекают три классические ошибки, и каждая падает только при выполнении:

- **`COUNT(*)` в `i32`.** Функция возвращает `bigint`, а не `integer`. Читай в `i64`. Похожая ловушка:
  `SUM` от `integer` даёт `bigint`, но `SUM` от `bigint` уже `numeric`, а `AVG` от целых даёт `numeric` (только от
  `real` и `double precision` он даёт `double precision`). Лечится приведением в запросе (`AVG(age)::float8`).
- **NULL в `String`.** Если столбец допускает NULL, поле обязано быть `Option`. Заменять NULL пустой
  строкой молча sqlx не будет, и правильно: «не задано» и «пусто» разные вещи.
- **`NaiveDateTime` для `timestamptz`.** Это разные типы. Момент времени с поясом читается в
  `DateTime<Utc>`.

Агрегат по пустому набору тоже возвращает NULL (`SUM`, `MAX`): оберни в `COALESCE(..., 0)` или читай
в `Option`.

### Свои типы: enum

Тип с фиксированным набором значений в Postgres бывает «родным» enum:

```sql
CREATE TYPE temperament AS ENUM ('calm', 'playful', 'shy');
```

Для него в Rust заводят enum с `derive(sqlx::Type)`:

```rust
#[derive(sqlx::Type)]
#[sqlx(type_name = "temperament", rename_all = "lowercase")]
enum Temperament { Calm, Playful, Shy }
```

`type_name` говорит, как тип называется в базе, `rename_all` приводит `Playful` к метке `playful`.
Без него sqlx отправит «Playful», и сервер ответит, что такого значения в enum нет. Такой enum
нельзя дёшево менять (метку добавить легко, убрать почти нельзя), поэтому многие держат статус
обычным `text` с `CHECK`; разбор в главе про моделирование данных.

### Список значений: `ANY`

`WHERE id IN (1, 2, 3)` нельзя собрать из параметров переменной длины, а склеивать строку опасно.
Выручает массив одним параметром:

```rust
let ids: Vec<i64> = vec![4, 8, 15];
let found = sqlx::query_as::<_, Animal>("SELECT id, name, age FROM animals WHERE id = ANY($1)")
    .bind(&ids)
    .fetch_all(&pool)
    .await?;
```

`ANY` порядок не сохраняет. Если порядок нужен, добавь `ORDER BY array_position($1, id)`.
Пустой массив работает как есть: ничего не находится, и это не ошибка.

## Ошибки базы

Когда сервер отвергает запрос, ты получаешь `sqlx::Error::Database(ошибка)`. У неё два нужных поля:
`code()`, это SQLSTATE (`23505` уникальность, `23503` внешний ключ, `23514` CHECK, `23502` NOT NULL),
и `constraint()`, имя нарушенного ограничения.

```rust
enum AdoptError { NameTaken, MicrochipTaken, Db(sqlx::Error) }

impl From<sqlx::Error> for AdoptError {
    fn from(e: sqlx::Error) -> Self {
        if let sqlx::Error::Database(db) = &e {
            match db.constraint() {
                Some("animals_name_uniq") => return AdoptError::NameTaken,
                Some("animals_chip_uniq") => return AdoptError::MicrochipTaken,
                _ => {}
            }
        }
        AdoptError::Db(e)
    }
}
```

С таким `From` в функциях хватает `?`. Два принципа. Первый: превращай в доменную ошибку только то,
что узнал, остальное оставляй `Db`. Иначе упавшая база выглядит как «кличка занята». Второй:
не проверяй уникальность запросом заранее. Между проверкой и вставкой другой запрос успеет вставить
такую же строку, а единственная надёжная проверка это сама база, которая отказывает всем, кроме
первого. Приложение лишь переводит её отказ.

Имена ограничений в коде это скрытая связь со схемой. Если ограничение переименовали, ветка
перестанет срабатывать, и никакой компилятор не скажет. Тест, который вставляет дубль, обязателен.

## Транзакция

Несколько команд, которые должны примениться все вместе или не примениться совсем:

```rust
let mut tx = pool.begin().await?;
let id: i64 = sqlx::query_scalar("INSERT INTO adopters (name) VALUES ($1) RETURNING id")
    .bind("Мария")
    .fetch_one(&mut *tx)
    .await?;
sqlx::query("UPDATE animals SET adopter_id = $1 WHERE id = $2")
    .bind(id)
    .bind(animal_id)
    .execute(&mut *tx)
    .await?;
tx.commit().await?;
```

Три правила, и почти все ошибки с транзакциями нарушают одно из них.

1. **Запросы идут на `&mut *tx`**, а не на пул. Транзакция это одно конкретное соединение. Запрос
   на пуле возьмёт другое соединение и окажется вне транзакции: он не увидит ещё не
   закоммиченных строк и не откатится вместе с ней.
2. **Без `commit` ничего не сохранится.** Если значение `tx` уничтожить, не вызвав `commit`
   (например, выйти из функции оператором `?` или забыть), sqlx откатит транзакцию. Это хорошо для
   ошибок: ранний возврат безопасен. И плохо для забывчивости: функция вернула `Ok`, а данных нет.
3. **Внутри транзакции держится одно соединение**, и запрос на пуле при исчерпанном пуле ждёт
   свободного соединения, а через 30 секунд (`acquire_timeout`) падает с `PoolTimedOut`. Об этом подробнее в главе про sqlx в сервисах.

Вспомогательные функции, которые могут работать внутри транзакции, принимают `&mut PgConnection`,
а не пул: транзакция разыменовывается в него (`&mut tx` или `&mut *tx`). Счётчик `IDENTITY` при
откате не возвращается: номера пропускаются, и это нормально.

## Схема из Rust и несколько команд

Запрос `query` отправляется протоколом с параметрами, где допустима ровно одна команда. Файл
схемы с десятком `CREATE TABLE` так не выполнить. Для скриптов у sqlx есть `raw_sql`:

```rust
sqlx::raw_sql(include_str!("schema.sql")).execute(&pool).await?;
```

Он отправляет текст «простым запросом», целиком. Параметров тут нет, зато можно много команд,
комментарии и точки с запятой внутри строк. Бонус: сервер выполняет простой запрос как одну
неявную транзакцию, поэтому ошибка в конце файла не оставляет схему применённой наполовину.
Файл пишут идемпотентным (`CREATE TABLE IF NOT EXISTS`), чтобы запускать при каждом старте.

Когда у каждого сервиса своя схема Postgres, соединения пула должны смотреть именно в неё.
`SET search_path` для этого не годится: он действует на одно соединение, а в пуле их несколько.
Правильно задать параметр подключения, тогда его получит каждое новое соединение:

```rust
use std::str::FromStr;
use sqlx::postgres::{PgConnectOptions, PgPoolOptions};

let options = PgConnectOptions::from_str(&url)?.options([("search_path", "shelter")]);
let pool = PgPoolOptions::new().max_connections(8).connect_with(options).await?;
```

Саму схему при этом надо сначала создать (`CREATE SCHEMA IF NOT EXISTS`), поэтому сначала открывается обычное временное соединение, потом основной пул. Её имя подставляется
в SQL форматированием, потому что идентификатор нельзя передать параметром; значит, оно должно
приходить только из конфигурации, никогда от пользователя. Так же устроены тесты курса: каждому
тесту своя схема, и сотня тестов не мешает друг другу.

## Макросы `query!` и почему мы начинаем без них

В sqlx есть макросы `query!` и `query_as!`: они при **компиляции** ходят в живую базу, проверяют
запрос и выводят типы. Ошибки ловятся рано, это сильная сторона. Цена: для сборки нужна работающая
база (или заранее сохранённые метаданные), а проект сложнее собирать в CI и в контейнере. Функции
`query`, `query_as`, `query_scalar`, которыми мы пользуемся, проверяются только при выполнении,
зато ничего не требуют от сборки. Всё, что ты узнал о соответствии типов, действует и в макросах.

## Типичные ошибки

- `fetch_one` там, где строки может не быть (500 вместо 404).
- `format!` вместо параметров: инъекция и сломанный запрос на апострофе.
- `COUNT(*)` в `i32`, NULL в `String`, `numeric` в `f64`, `NaiveDateTime` для `timestamptz`.
- Совпадение имени столбца и поля «на глаз» после `JOIN`: в результате имена те, что в запросе.
- Запросы на пуле внутри открытой транзакции.
- Забытый `commit`.
- Проверка «такого нет» отдельным SELECT вместо ограничения в базе.
- Любую ошибку базы превращают в «не найдено» или «уже существует».
- `SET search_path` на одном соединении пула вместо параметра подключения.
