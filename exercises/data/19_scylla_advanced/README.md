# Глубже в Scylla

Обычные записи в Scylla быстрые, потому что ничего не проверяют: upsert без чтения, последняя по метке времени побеждает, удаление это тоже запись. Но приложению иногда нужно больше: уникальность, правка без потерь, счётчики, данные со сроком жизни, запись в несколько таблиц сразу. Для каждой такой задачи в Scylla есть свой инструмент со своей ценой. Примеры в этой главе про онлайн-кинотеатр: брони мест на сеанс, рейтинги, временные промокоды. Задачи будут про чат.

## Лёгкие транзакции (LWT)

Условие в записи превращает её в лёгкую транзакцию:

```sql
INSERT INTO seats (session_id, seat, holder) VALUES (42, 'B7', 1001) IF NOT EXISTS;
UPDATE seats SET holder = 1002 WHERE session_id = 42 AND seat = 'B7' IF holder = 1001;
DELETE FROM seats WHERE session_id = 42 AND seat = 'B7' IF EXISTS;
```

Проверка и запись выполняются атомарно, даже если сто клиентов одновременно бронируют одно место: побеждает ровно один. Ответ на условную запись это строка с булевым столбцом `[applied]`. Если запись не применилась, в той же строке приходят текущие значения, и проигравший сразу видит, кто его опередил.

Внутри работает протокол Paxos между репликами партиции: подготовка с номером голосования, чтение текущего значения, предложение, фиксация. Это примерно четыре круга вместо одного, поэтому LWT используют точечно: уникальность (место, ник, личный чат), оптимистичная правка по версии. Визуализация «Лёгкая транзакция и Paxos» показывает фазы.

Два правила:

- не смешивай условные и обычные записи одних и тех же строк: обычная запись не участвует в Paxos и может нарушить его гарантии;
- у LWT два уровня согласованности: обычный для фиксации и последовательный (`SERIAL` или `LOCAL_SERIAL`) для фазы проверки.

Оптимистичная блокировка выглядит так: читаешь строку вместе с версией, правишь, пишешь с `IF version = прочитанная` и увеличиваешь версию. Если `[applied] = false`, перечитываешь и пробуешь снова.

## Счётчики

```sql
CREATE TABLE ratings (movie_id int PRIMARY KEY, likes counter, dislikes counter);
UPDATE ratings SET likes = likes + 1 WHERE movie_id = 7;
```

Счётчик хранится как набор приращений от реплик и собирается при чтении. Отсюда правила:

- значение нельзя установить, только прибавить или отнять (INSERT в счётчик невозможен);
- в таблице со счётчиками все столбцы вне ключа должны быть счётчиками;
- прибавление не идемпотентно: после таймаута неизвестно, применилось ли оно, и повтор может посчитать дважды.

Поэтому счётчики хороши для приблизительной статистики (лайки, просмотры) и плохи для всего, где важна точность. Когда нужно точное «сколько непрочитанных», модель строят иначе: отметка «прочитано до» и подсчёт новых строк с пределом.

## TTL: данные со сроком жизни

```sql
INSERT INTO promo_codes (code, discount) VALUES ('SPRING', 20) USING TTL 3600;
CREATE TABLE trailers_cache (movie_id int PRIMARY KEY, url text) WITH default_time_to_live = 86400;
SELECT TTL(discount) FROM promo_codes WHERE code = 'SPRING';
```

У каждой ячейки может быть свой срок жизни в секундах, после которого она читается как отсутствующая. `default_time_to_live` у таблицы задаёт срок всем записям без своего. Это надёжнее фоновых задач очистки, но помни: TTL ставится на ячейки. UPDATE одного столбца с другим сроком даст строку, части которой исчезнут в разное время.

## Метки времени записи

Каждая ячейка хранит метку времени записи в микросекундах, и при конфликте побеждает большая метка. По умолчанию её ставит координатор, когда запрос пришёл. Метку можно передать явно, и тогда порядок задаёт тот, кто знает настоящий порядок событий:

```sql
UPDATE prices USING TIMESTAMP 1792000000000000 SET amount = 450 WHERE movie_id = 7;
SELECT amount, WRITETIME(amount) FROM prices WHERE movie_id = 7;
```

Это спасает от опоздавших сообщений очереди: старое изменение с меньшей меткой не перетрёт новое, даже если пришло позже. Все, кто пишет одну ячейку, должны использовать одни единицы (микросекунды): метки в миллисекундах навсегда проиграют.

## Надгробия

Удаление в Scylla это запись маркера-надгробия, а не стирание: SSTable неизменяемы. Надгробия появляются от DELETE, от записи null, от истечения TTL и от перезаписи коллекции целиком. Чтение обязано их учитывать, поэтому партиция, где надгробий тысячи, читается медленно, а при превышении порога чтение и вовсе отвергается. Физически данные и надгробия уходят при уплотнении после `gc_grace_seconds` (по умолчанию 10 дней): раньше нельзя, иначе реплика, которая пропустила удаление, «воскресит» данные.

Как жить с надгробиями:

- удалять диапазоном, а не по одной строке;
- менять коллекции поэлементно (`seats_left = seats_left - {'B7'}`), а не перезаписывать целиком;
- не писать null ради «пустых» полей (для этого есть unset);
- для данных с TTL выбирать стратегию уплотнения по времени (TimeWindowCompactionStrategy), которая выбрасывает истёкшие файлы целиком.

## Batch

```sql
BEGIN BATCH
  INSERT INTO bookings_by_session (session_id, seat, user_id) VALUES (42, 'B7', 1001);
  INSERT INTO bookings_by_user (user_id, session_id, seat) VALUES (1001, 42, 'B7');
APPLY BATCH;
```

Logged batch (обычный `BEGIN BATCH`) даёт атомарность в смысле «всё или в итоге всё»: координатор сначала сохраняет batch в журнал на других узлах, а если сам упадёт, batch доиграют. Изоляции нет: читатель может увидеть одну таблицу раньше другой. Это ровно то, что нужно денормализации, когда одно событие пишется в несколько таблиц.

Batch не ускоритель. Unlogged batch по многим партициям перекладывает работу на одного координатора: тот держит пачку в памяти и сам рассылает части по узлам, а размер batch ограничен. Массовую загрузку делают параллельными подготовленными запросами с пределом одновременных: каждый идёт сразу на свой узел. Unlogged batch оправдан, когда все строки в одной партиции.

## Уровни согласованности

Уровень говорит, сколько реплик должны ответить:

| уровень | смысл |
|---|---|
| `ONE` | одна реплика: быстро, может отдать устаревшее |
| `QUORUM` | большинство реплик (2 из 3) |
| `LOCAL_QUORUM` | большинство в своём дата-центре |
| `ALL` | все реплики: ломается от падения любой |

Главное правило: чтение гарантированно видит подтверждённую запись, если реплик записи плюс реплик чтения больше, чем всего реплик (W + R > N). QUORUM на запись и QUORUM на чтение при трёх репликах это 2 + 2 > 3. ONE + ONE такой гарантии не даёт. Уровень выбирают под операцию: важные данные с QUORUM, эфемерные (кто сейчас смотрит фильм) с ONE.

## Стратегии уплотнения

- **SizeTieredCompactionStrategy** (по умолчанию): сливает файлы похожего размера. Хороша для записи, но временами требует много свободного места.
- **LeveledCompactionStrategy**: держит данные уровнями без перекрытий. Чтение быстрее, записи на диск больше.
- **TimeWindowCompactionStrategy**: группирует данные по окнам времени. Идеальна для данных во времени с TTL: истёкшее окно удаляется целым файлом без надгробий.
- **IncrementalCompactionStrategy** (ScyllaDB): как size-tiered, но без всплесков расхода места.

## Типичные ошибки

- LWT на каждой записи «на всякий случай».
- Счётчики для денег или точных остатков.
- Повтор неидемпотентного запроса после таймаута.
- Перезапись коллекции целиком при добавлении одного элемента.
- Удаление по одной строке там, где можно диапазоном или TTL.
- Batch «для скорости» по сотням партиций.
- ONE на запись и ONE на чтение там, где пользователь должен видеть своё.
