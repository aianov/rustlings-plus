# Возможности Postgres: jsonb, поиск, партиции, триггеры

Сайт с рецептами начинался с таблицы `recipes (id, title, body)`. Потом пришли просьбы. Автор хочет хранить пометки к
рецепту: время готовки, острота, «подходит вегетарианцам», и у каждого рецепта набор пометок свой. Читатель хочет искать
«борщ без свёклы» и находить «борща», «борщи». Редактор жалуется, что поиск повара «Петрова» не находит «Петров» и
«Петроф». Главная страница считает самые любимые блюда недели и тормозит. А таблица просмотров за пять лет выросла до
полумиллиарда строк, и каждое удаление старых просмотров вешает базу на ночь.

Всё это Postgres умеет сам. Глава про то, какими средствами и какой у каждого счёт: в задачах будет соцсеть, здесь рецепты.

## jsonb: документ внутри строки

Когда набор полей у строк разный или меняется чаще, чем успеваешь писать миграции, помогает столбец `jsonb`:

```sql
CREATE TABLE recipes (
    id    bigint PRIMARY KEY,
    title text NOT NULL,
    meta  jsonb NOT NULL DEFAULT '{}'
);
INSERT INTO recipes VALUES (1, 'Борщ', '{"minutes": 90, "spicy": false, "diet": {"vegan": false}, "tags": ["суп", "свёкла"]}');
```

`json` хранит текст как есть, `jsonb` разбирает его в двоичный вид: не помнит порядок ключей и дубликаты, зато быстрее
читается, умеет индексы и операторы. Для данных, которые ты запрашиваешь, всегда нужен `jsonb`.

Достать значение:

```sql
SELECT meta -> 'diet'              -- jsonb: {"vegan": false}
     , meta ->> 'minutes'          -- text:  90
     , meta #>> '{diet,vegan}'     -- text по пути: false
     , meta -> 'tags' ->> 0        -- первый элемент массива: суп
FROM recipes;
```

Стрелки с двумя угловыми скобками (`->>`, `#>>`) возвращают text и заканчивают цепочку; с одной (`->`, `#>`) возвращают
jsonb, и за ними можно писать следующий оператор. Нет такого ключа: NULL, а не ошибка. Не забывай привести тип, если
нужно сравнивать числа: `(meta ->> 'minutes')::int < 30`.

Спросить про содержимое:

```sql
meta @> '{"diet": {"vegan": true}}'    -- документ содержит такой кусок (с учётом вложенности и типов)
meta ? 'spicy'                         -- есть ключ верхнего уровня (значение не важно)
meta ?| array['spicy','sweet']         -- есть хотя бы один из ключей
meta ?& array['spicy','sweet']         -- есть оба
```

`@>` сравнивает с типами: `{"minutes": 90}` содержит `{"minutes": 90}`, но не содержит `{"minutes": "90"}`. И
`?` смотрит только на верхний уровень: `meta ? 'vegan'` не найдёт `vegan`, спрятанный в `diet`.

Изменить кусок, не переписывая документ руками:

```sql
UPDATE recipes SET meta = jsonb_set(meta, '{diet,vegan}', 'true') WHERE id = 1;  -- по пути, значение jsonb
UPDATE recipes SET meta = meta || '{"minutes": 75}';                              -- слить ключи верхнего уровня
UPDATE recipes SET meta = meta - 'spicy';                                         -- убрать ключ
UPDATE recipes SET meta = meta #- '{diet,vegan}';                                 -- убрать по пути
```

У `jsonb_set` две особенности. Значение должно быть jsonb (строку надо превратить через `to_jsonb('текст'::text)`), и функция
создаёт только последний ключ пути: если промежуточного объекта нет, она не делает ничего и не жалуется. `||` сливает
только верхний уровень: если у обоих есть ключ `diet`, правый объект целиком заменяет левый.

Из Rust jsonb читают и пишут через `sqlx::types::Json<T>`. Оборачиваешь свою структуру в `Json(...)` при `bind` и
запрашиваешь столбец как `Json<T>`: serde берёт на себя разбор, `#[serde(default)]` и пропуск лишних ключей делают код
устойчивым к документам старых форматов.

### Индекс по документам

Обычный B-tree по jsonb умеет только равенство документов целиком. Для `@>` и `?` нужен GIN. У него два класса
операторов:

```sql
CREATE INDEX recipes_meta_idx  ON recipes USING gin (meta);                 -- jsonb_ops: @>, ?, ?|, ?&
CREATE INDEX recipes_meta_idx2 ON recipes USING gin (meta jsonb_path_ops);  -- только @>, но компактнее и быстрее
```

Выбирай по реальным запросам. Индекс «на всякий случай» стоит записи, а размер любого GIN важен: он обновляется на
каждую вставку.

Если поле запрашивают постоянно и оно есть у всех, ему место в обычном столбце. jsonb хорош для того, что действительно
разное у разных строк.

### Ответ одним документом

Страница рецепта хочет всё сразу: сам рецепт, автора, ингредиенты. Агрегаты `jsonb_agg` (в массив) и
`jsonb_build_object` (в объект) собирают такой ответ в базе, одним запросом:

```sql
SELECT jsonb_build_object(
         'title', r.title,
         'cook',  jsonb_build_object('id', c.id, 'name', c.name),
         'steps', COALESCE((SELECT jsonb_agg(s.text ORDER BY s.n) FROM steps s WHERE s.recipe_id = r.id), '[]'::jsonb)
       )
FROM recipes r JOIN cooks c ON c.id = r.cook_id
WHERE r.id = $1;
```

Две ловушки. Агрегат считает то, что дало соединение: если соединить рецепт и с шагами, и с ингредиентами, строки
перемножатся (10 шагов на 12 ингредиентов это 120 строк), и массивы заполнятся дублями. Независимые коллекции собирают
каждую в своём подзапросе. И агрегат над пустым набором возвращает NULL, а не пустой массив; клиенту нужен `[]`,
поэтому `COALESCE`.

## Массивы

`ingredients text[]` лежит в той же строке, что и рецепт:

```sql
SELECT id FROM recipes WHERE 'укроп' = ANY(ingredients);          -- есть этот элемент
SELECT id FROM recipes WHERE ingredients @> ARRAY['сыр','мука'];   -- есть все
SELECT id FROM recipes WHERE ingredients && ARRAY['мёд','сахар'];  -- есть хоть один
SELECT unnest(ingredients) AS item, count(*) FROM recipes GROUP BY item;  -- массив в строки
```

Массив подходит для короткого списка, который читают и пишут вместе со строкой. Если у элемента есть своя жизнь (оценки
рецепта, лайки с датой, ссылка на другую таблицу), нужна таблица: каждая правка массива переписывает всю строку, внешний
ключ на элемент поставить нельзя, а список в миллион элементов превращает любое чтение строки в тяжёлое.

## Полнотекстовый поиск

`LIKE '%борщ%'` не знает падежей, не умеет «без свёклы» и читает всю таблицу. Полнотекстовый поиск устроен иначе:

```
  текст рецепта ──► разбор на токены ──► словарь (конфигурация) ──► tsvector
  "Борщи с укропом"                     "борщи", "с", "укропом"     'борщ':1 'укроп':3   (с: стоп-слово)

  запрос "борщ -свёкла" ──► тот же путь ──► tsquery   'борщ' & !'свёкл'

  tsvector @@ tsquery  ──► да / нет
```

Конфигурация (`'russian'`, `'english'`, `'simple'`) задаёт словарь: `russian` приводит слова к основе («борщи», «борща» →
«борщ») и выбрасывает стоп-слова, `simple` только режет по словам и приводит к нижнему регистру. **Конфигурации текста и
запроса должны совпадать**, иначе основы разойдутся и поиск молча ничего не найдёт. Открой `visuals/fts_pipeline.html`.

Строку запроса из поля поиска разбирает `websearch_to_tsquery`: слова через пробел это «и», `or` это «или», минус
исключает, кавычки значат «подряд». На любой ввод она отвечает без ошибки, в отличие от `to_tsquery`, которая ждёт
синтаксис tsquery (`&`, `|`, `!`).

```sql
SELECT id FROM recipes
WHERE to_tsvector('russian', title || ' ' || body) @@ websearch_to_tsquery('russian', 'борщ -свёкла');
```

Так работает, но `to_tsvector` вычисляется для каждой строки каждый раз, и индекс тут не поможет. Вектор надо хранить, а
поддерживать актуальным должна база. Для этого есть **generated-столбец**: значение вычисляется из других столбцов
при каждой вставке и обновлении и хранится физически. Выражение должно быть неизменяемым (immutable), поэтому
конфигурацию пишут явно: `to_tsvector('russian', ...)`, а не `to_tsvector(...)`, который зависит от настройки сессии.

```sql
ALTER TABLE recipes ADD COLUMN fts tsvector GENERATED ALWAYS AS (
    setweight(to_tsvector('russian', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('russian', coalesce(notes, '')), 'C')
) STORED;
CREATE INDEX recipes_fts_idx ON recipes USING gin (fts);
```

`setweight` помечает лексемы буквой A, B, C или D: это вес для ранжирования. GIN строит обратный указатель
«лексема → строки», поэтому запрос читает только нужные списки.

**Ранг и выдержка.** `ts_rank(fts, query)` оценивает, насколько строка подходит, и учитывает веса (по умолчанию A весит 1.0,
B 0.4, C 0.2, D 0.1). `ts_headline(config, текст, query, опции)` берёт исходный текст и возвращает выдержку с выделенными
словами. Он дорогой (разбирает текст заново), поэтому его считают после отбора страницы, а не для всей выдачи. И он не
делает вывод безопасным для HTML: полные теги он вырезает, но оборванный тег и символы `<` и `&` оставляет как есть.
Если выдержку вставляют в страницу как разметку, текст надо экранировать до вызова.

## pg_trgm: похожесть строк

Триграммы это все подряд идущие тройки символов строки с двумя пробелами в начале и одним в конце. Две строки похожи,
если у них много общих троек, и опечатка портит лишь несколько.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;        -- один раз на базу
SELECT similarity('Петров', 'Петроф');         -- число от 0 до 1
SELECT name FROM cooks WHERE name % 'Петроф';  -- похоже (порог по умолчанию 0.3)
CREATE INDEX cooks_name_trgm ON cooks USING gin (name gin_trgm_ops);
```

Один индекс обслуживает и оператор `%`, и `LIKE '%кусок%'`, `ILIKE`, и регулярные выражения: обычный B-tree для
шаблона с процентом в начале бессилен. Для коротких слов триграмм мало, и результат бывает шумным, поэтому порог и
`LIMIT` подбирают на живых данных.

## Материализованные представления

Обычное представление (`VIEW`) это сохранённый запрос: каждое чтение выполняет его заново. Материализованное хранит
**результат**, как таблица:

```sql
CREATE MATERIALIZED VIEW favorites AS
    SELECT recipe_id, count(*) AS stars FROM votes WHERE at > now() - interval '7 days' GROUP BY recipe_id;
CREATE UNIQUE INDEX favorites_pk ON favorites (recipe_id);
REFRESH MATERIALIZED VIEW CONCURRENTLY favorites;
```

Читать его быстро и можно вешать индексы, но данные меняются только при `REFRESH`. Простой `REFRESH` берёт эксклюзивную
блокировку: пока идёт пересчёт, читатели ждут. `CONCURRENTLY` строит новую версию рядом и применяет разницу, читатели не
блокируются, но для него нужен уникальный индекс по столбцам без условия. Окно «за семь дней» считается в момент обновления
и до следующего «замерзает». Обновляют по расписанию или по событию; частоту выбирают из допустимой устарелости, а не
из любви к свежести.

## Партиционирование

Большая таблица делится на части (партиции) по значению столбца, а запросы видят одну таблицу:

```sql
CREATE TABLE views (
    recipe_id bigint NOT NULL,
    at        timestamptz NOT NULL,
    PRIMARY KEY (recipe_id, at)
) PARTITION BY RANGE (at);

CREATE TABLE views_2031_q1 PARTITION OF views FOR VALUES FROM ('2031-01-01') TO ('2031-04-01');
CREATE TABLE views_2031_q2 PARTITION OF views FOR VALUES FROM ('2031-04-01') TO ('2031-07-01');
```

Верхняя граница диапазона **не входит**, поэтому границы соседей совпадают: строка с `at = '2031-04-01'` уйдёт во вторую партицию.
Запрос с условием на `at` читает только подходящие партиции (отсечение партиций, partition pruning), а удаление старого
квартала это `DROP TABLE views_2030_q4`: мгновенно, без раздувания и работы для vacuum. Цена:

- первичный ключ и уникальные ограничения обязаны включать столбец партиционирования;
- запрос без условия на него читает все партиции;
- для будущего периода партицию надо создать заранее, иначе вставка упадёт (чаще всего это делает задание по расписанию);
- тысячи партиций замедляют планирование: большое число мелких частей хуже, чем умеренное.

Есть и `PARTITION BY LIST` (по перечню значений) и `HASH` (равномерно по ключу).

## Триггеры и их цена

Триггер это функция, которую база вызывает сама до или после вставки, обновления, удаления. Строчные триггеры
получают `OLD` и `NEW`:

```sql
CREATE FUNCTION lowercase_name() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    NEW.name := lower(NEW.name);
    RETURN NEW;
END $$;
CREATE TRIGGER cooks_lower BEFORE INSERT OR UPDATE ON cooks FOR EACH ROW EXECUTE FUNCTION lowercase_name();
```

`BEFORE` может поменять строку перед записью (изменить `NEW` и вернуть его, или вернуть `NULL`, чтобы пропустить
строку), `AFTER` видит уже записанное и годится для побочных действий. Условие `WHEN (OLD.* IS DISTINCT FROM NEW.*)`
отсекает пустые обновления, не запуская функцию.

Триггеры выполняются на каждой строке, их не видно в коде приложения, и они делят транзакцию с командой. Для
служебных полей (даты изменения, нормализация, журнал аудита) это удобно. Для бизнес-логики и счётчиков плохо:
`UPDATE recipes SET votes = votes + 1` в триггере на каждый голос превращает параллельную запись в очередь за блокировкой
одной строки. Счётчики копят пачками или считают при чтении.

## Типичные ошибки

- Конфигурация текста и запроса разные: поиск молчит.
- `to_tsvector(text)` без конфигурации в generated-столбце или индексе: ошибка «not immutable».
- GIN по jsonb с классом по умолчанию, когда нужен только `@>`: индекс вдвое больше необходимого.
- Забыли про `COALESCE` у агрегатов: клиент получает `null` вместо `[]`.
- Материализованное представление без уникального индекса: `CONCURRENTLY` недоступен.
- Партиционированная таблица без столбца партиции в запросах: читаются все партиции.
- Партиция на следующий месяц не создана: в последний день месяца вставки начинают падать.
- Триггер BEFORE заменён на AFTER с новым UPDATE: бесконечная рекурсия.
