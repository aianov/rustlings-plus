# Подзапросы, CTE и рекурсия

Приходит задача: «покажи покупателей, чьи заказы дороже среднего заказа». Ответ состоит из двух
вопросов: сначала «сколько составляет средний заказ», потом «чьи заказы выше этого числа». Можно
сделать два запроса и передать число через приложение, но тогда между ними данные успеют измениться,
да и лишний круг до базы стоит времени. SQL умеет вкладывать один запрос в другой, и этой главе
посвящена вся эта техника: подзапросы, `WITH`, `LATERAL`, изменяющие запросы внутри `WITH` и рекурсия
для деревьев. Без неё нельзя прочитать дерево комментариев, папок или категорий.

Примеры в тексте про магазин (`customers`, `orders`) и файловые папки, в задачах соцсеть.

```
customers                     orders
 id | name | referrer_id       id | customer_id | total
  1 | Мария | NULL              10 |      1      |  500
  2 | Олег  |  1                11 |      1      |  700
  3 | Яна   |  1                12 |      2      |  300
```

## Подзапрос: запрос внутри запроса

Подзапрос это `SELECT` в скобках. Его можно поставить в трёх местах, и в каждом он играет свою роль.

**В WHERE** он даёт значение или список для сравнения.

```sql
-- заказы дороже среднего
SELECT id, total FROM orders WHERE total > (SELECT avg(total) FROM orders);

-- покупатели, у которых есть заказы
SELECT name FROM customers WHERE id IN (SELECT customer_id FROM orders);
```

Подзапрос после `>` должен вернуть одну строку и один столбец (его называют скалярным), иначе
Postgres ответит ошибкой «more than one row returned by a subquery». Подзапрос после `IN` возвращает
один столбец и сколько угодно строк.

**В SELECT** скалярный подзапрос считает значение для каждой строки:

```sql
SELECT c.name, (SELECT max(total) FROM orders o WHERE o.customer_id = c.id) AS biggest
FROM customers c;
```

Если заказов нет, `max` вернёт NULL, и строка покупателя останется. Это отличие от `JOIN`, который
потерял бы Яну. Если бы подзапрос вернул две строки, получилась бы ошибка, а если ни одной, то NULL.

**В FROM** он становится временной таблицей со своим именем (псевдоним обязателен):

```sql
SELECT c.name, t.spent
FROM customers c
JOIN (SELECT customer_id, sum(total) AS spent FROM orders GROUP BY customer_id) t
  ON t.customer_id = c.id;
```

Этот приём называют предагрегацией: таблицу сначала сворачивают до одной строки на ключ, и только
потом соединяют. Вспомни главу про агрегаты: две связи «один ко многим» в одном `JOIN` перемножают
строки. Если свернуть каждую связь в подзапросе заранее, перемножать станет нечего.

## Коррелированные подзапросы

Если подзапрос ссылается на столбец внешней строки (как `o.customer_id = c.id` выше), он называется
коррелированным. Логически он выполняется заново для каждой внешней строки. Планировщик часто
переписывает такое в соединение и работает быстро, но писать и читать запрос можно так, будто
вычисление идёт по строкам.

```sql
-- самый крупный заказ каждого покупателя
SELECT o.customer_id, o.id, o.total
FROM orders o
WHERE o.total = (SELECT max(x.total) FROM orders x WHERE x.customer_id = o.customer_id);
```

Если у покупателя два заказа на одну и ту же максимальную сумму, вернутся оба. Для строгого «один»
нужен ещё критерий, чтобы выбор стал однозначным (про `DISTINCT ON` и окна ты узнаешь позже).

## EXISTS и NOT EXISTS

`EXISTS (подзапрос)` истинно, если подзапрос вернул хотя бы одну строку. Что именно он выбирает,
не важно, обычно пишут `SELECT 1`.

```sql
-- покупатели, которые хоть раз заказывали дороже 400
SELECT name FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.total > 400);
```

У `EXISTS` два преимущества перед `JOIN`. Он не размножает строки: у Марии два заказа дороже 400, но в
результате она встретится один раз, и `DISTINCT` не нужен. И он останавливается на первой
найденной строке. `NOT EXISTS` читается как «нет ни одной такой строки» и есть главная форма
анти-join (кого нет).

### Ловушка: NOT IN и NULL

```sql
SELECT name FROM customers WHERE id NOT IN (SELECT referrer_id FROM customers);
```

Хочется получить покупателей, которые никого не привели. Но в `referrer_id` у Марии NULL, а
`x NOT IN (1, NULL)` раскрывается в `x <> 1 AND x <> NULL`. Второе сравнение никогда не истинно, и
запрос возвращает пустоту без единой ошибки. `NOT EXISTS` с условием `r.referrer_id = c.id` такой
проблемы не имеет. Правило: для «нет в списке» пиши `NOT EXISTS`, а `NOT IN` оставь для списков из
литералов или столбцов с `NOT NULL`.

## Операции над множествами

Два запроса с одинаковым числом и типами столбцов можно объединять как множества:

```sql
SELECT customer_id FROM orders WHERE total > 600
UNION                    -- объединение, без повторов
SELECT customer_id FROM orders WHERE total < 400;
```

| операция | результат |
|---|---|
| `UNION` | все строки обоих наборов, повторы убираются |
| `UNION ALL` | все строки обоих наборов, ничего не убирается |
| `INTERSECT` | строки, которые есть в обоих наборах |
| `EXCEPT` | строки первого набора, которых нет во втором |

Всё, кроме `UNION ALL`, убирает повторы, а для этого сортирует или хэширует результат. Поэтому
привычка такая: пиши `UNION ALL`, пока тебе действительно не понадобится схлопнуть дубли. У каждой
операции есть вариант `ALL` (`EXCEPT ALL`, `INTERSECT ALL`), который сохраняет кратность. `ORDER BY`
пишется один раз после всей цепочки и видит только имена столбцов результата (по первому запросу).
Сравниваются строки целиком, и NULL при этом считается равным NULL (в отличие от `=`).

Приоритет у операций разный: `INTERSECT` связывает сильнее, чем `UNION` и `EXCEPT`, а они между собой идут слева направо. Если нужен другой порядок, ставь скобки вокруг части цепочки: `(A UNION B) EXCEPT C`. Скобки с `ORDER BY` внутри тоже пишутся явно.

## WITH: запрос по шагам

Три вложенных подзапроса читаются изнутри наружу, как скобки в арифметике. `WITH` даёт каждому
шагу имя, и запрос читается сверху вниз:

```sql
WITH per_customer AS (
    SELECT customer_id, sum(total) AS spent FROM orders GROUP BY customer_id
),
average AS (
    SELECT avg(spent) AS a FROM per_customer
)
SELECT c.name, p.spent
FROM per_customer p
JOIN customers c ON c.id = p.customer_id
CROSS JOIN average
WHERE p.spent > average.a;
```

Каждая CTE видит те, что объявлены выше. Название расшифровывается как Common Table Expression,
но думай о ней как о временном имени для подзапроса. Начиная с 12-й версии Postgres встраивает
простую CTE в запрос, как подзапрос, а если её читают в двух местах, считает один раз. Нужное
поведение можно заказать явно: `AS MATERIALIZED (...)` или `AS NOT MATERIALIZED (...)`.

## LATERAL: подзапрос, который видит соседей

Обычный подзапрос в `FROM` не знает о таблицах слева от себя. Со словом `LATERAL` он их видит, и
выполняется заново для каждой левой строки. Классическое применение «первые N на группу»:

```sql
-- два самых крупных заказа каждого покупателя
SELECT c.name, t.id, t.total
FROM customers c
CROSS JOIN LATERAL (
    SELECT id, total FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY total DESC
    LIMIT 2
) t;
```

`LIMIT` внутри подзапроса действует на каждого покупателя отдельно: именно для этого приём и нужен.
Покупатель без заказов даёт пустой подзапрос, и `CROSS JOIN LATERAL` (или просто `JOIN LATERAL ... ON
true`) его выбросит. Чтобы сохранить, берут `LEFT JOIN LATERAL (...) t ON true`; `ON true` нужен
потому, что синтаксис требует условия, а настоящая связь уже внутри подзапроса. Открой
`visuals/lateral_topn.html`: там видно, что происходит с постом без комментариев в обоих режимах.

## Изменяющие CTE

В `WITH` можно писать не только `SELECT`, но и `INSERT`, `UPDATE`, `DELETE` с `RETURNING`. Результат
`RETURNING` доступен дальше как таблица:

```sql
WITH new_order AS (
    INSERT INTO orders (customer_id, total) VALUES ($1, $2) RETURNING id
)
INSERT INTO order_items (order_id, product_id)
SELECT new_order.id, unnest($3::bigint[]) FROM new_order;
```

Заказ и его позиции создаются одним оператором, а оператор атомарен: либо есть всё, либо ничего.
Две особенности, на которых ошибаются. Первая: изменяющая CTE выполняется целиком, даже если основной
запрос её не читает. Вторая: все части видят одну и ту же версию данных, как на момент начала
оператора. Поэтому `WITH gone AS (DELETE FROM t RETURNING id) SELECT count(*) FROM t` посчитает ещё
не удалённые строки. Результат изменения читается только через `RETURNING`.

### Вставь или верни существующее

Задача, которая встречается постоянно: получить id бренда по названию, создав его, если нет. Короткая
запись `ON CONFLICT (name) DO UPDATE SET name = EXCLUDED.name RETURNING id` работает, но каждый вызов
пишет новую версию строки. Версия копится в таблице, пока её не уберёт `VACUUM`, и это на горячей таблице
заметно. Вариант без записи при существующей строке:

```sql
WITH ins AS (
    INSERT INTO brands (name) VALUES ($1) ON CONFLICT (name) DO NOTHING RETURNING id
)
SELECT id FROM ins
UNION ALL
SELECT id FROM brands WHERE name = $1
LIMIT 1
```

Для нового бренда id даёт вставка, для существующего вставка пуста, и его находит второй `SELECT`. Та же идея работает для любой «идемпотентной» вставки: сначала `INSERT ... ON CONFLICT DO NOTHING RETURNING`, потом при пустом ответе чтение существующей строки.
Оговорка: при одновременной вставке одного имени двумя клиентами проигравший может не увидеть
строку победителя (общий снимок оператора) и получить пустой ответ. Тогда вызов повторяют.

## WITH RECURSIVE: деревья

Папки хранятся так: у каждой есть `parent_id`, у корня он NULL. Вопрос «покажи всё содержимое папки,
на любую глубину» заранее не решить `JOIN`ом, потому что глубина неизвестна. Рекурсивная CTE
повторяет шаг, пока он находит новые строки:

```sql
WITH RECURSIVE sub AS (
    SELECT id, name, 0 AS depth          -- затравка
    FROM folders WHERE id = $1
    UNION ALL
    SELECT f.id, f.name, s.depth + 1     -- шаг
    FROM folders f JOIN sub s ON f.parent_id = s.id
)
SELECT * FROM sub ORDER BY depth, name;
```

Как это исполняется:

```
затравка  : { папка 1 }                       <- рабочая таблица
итерация 1: дети строк рабочей таблицы        { 2, 3 }
итерация 2: дети строк с прошлого шага        { 4, 5 }
итерация 3: дети { 4, 5 }                     { }  -> пусто, стоп
результат = затравка + все итерации
```

Важно, что шаг читает не всю накопленную `sub`, а только строки, добавленные на прошлой итерации.
Затравка может быть и составной (`SELECT ... UNION ALL SELECT ...` в первой части), рекурсивной должна быть только последняя часть. Остановка наступает, когда шаг не нашёл ничего. Открой `visuals/recursive_cte.html` и пройди все
три режима.

**Вверх и вниз.** Вниз (от корня к детям) идёт соединение «ребёнок ссылается на родителя из рабочей
таблицы» (`f.parent_id = s.id`). Вверх условие зеркальное:

```sql
WITH RECURSIVE chain AS (
    SELECT id, parent_id, name, 0 AS hops FROM folders WHERE id = $1
    UNION ALL
    SELECT f.id, f.parent_id, f.name, c.hops + 1
    FROM folders f JOIN chain c ON f.id = c.parent_id
)
SELECT name FROM chain ORDER BY hops DESC;   -- от корня к стартовой папке
```

Рабочая строка ссылается на родителя, и шаг ищет эту папку по её `id`. Цепочка вверх одна, без
ветвления, поэтому идти вверх дёшево. Порядок «корень первым» получается из счётчика шагов `hops`,
отсортированного по убыванию: сами строки результата никакого порядка не обещают.

**Глубина и порядок.** Рекурсивная CTE ничего не гарантирует о порядке строк. Счётчик `depth`
показывает уровень вложенности. Пример выше выводит дерево слоями (сначала все дети корня, потом все внуки). Человеку
нужно, чтобы потомок стоял прямо под предком (обход в глубину). Для этого каждая строка носит с
собой путь от корня, массив id: затравка создаёт массив из одного id, шаг дописывает в конец id новой строки, а сортировка идёт по
этому столбцу. Массивы сравниваются поэлементно, и родитель
(префикс) всегда стоит раньше своих потомков. Сортировка по `id` или по времени создания так не
работает: папка, созданная позже, но внутри раннего родителя, окажется в середине чужой ветки.

**Цикл: беда, которая не приходит сама.** Если в данных папка оказалась собственным предком, шаг
всегда находит новые строки, и запрос работает вечно, съедая память и диск, а ошибки так и не
будет. Данные так не должны ломаться, но ломаются: импорт, ручная правка, баг. Защит две.

```sql
-- 1) идея: в шаге не пускать строку, чей id уже есть в массиве пути (он описан выше)

-- 2) готовая форма Postgres 14+: пометить строку, которая замкнула цикл
WITH RECURSIVE sub AS (...)
CYCLE id SET is_cycle USING cycle_path
SELECT * FROM sub WHERE NOT is_cycle;
```

И вежливая страховка: `WHERE s.depth < 50`, чтобы даже без цикла пользователю не вернули дерево в
тысячи уровней. Один лишь предел глубины от цикла не спасает: за 50 шагов строки успеют повториться
десятки раз.

## Типичные ошибки

- `NOT IN (подзапрос)` по столбцу, где бывает NULL: результат пуст, ошибки нет.
- Скалярный подзапрос, который вернул две строки: «more than one row returned by a subquery».
- `UNION` там, где нужен `UNION ALL`: потеряны законные повторы, да и сортировка зря.
- `CROSS JOIN LATERAL` вместо `LEFT JOIN LATERAL ... ON true`: пропали строки без пары.
- Ожидание, что основной запрос увидит результат изменяющей CTE через таблицу, а не через `RETURNING`.
- Рекурсия без условия остановки и без защиты от цикла.
- Сортировка рекурсивной CTE по `id` вместо пути.
- `DO UPDATE SET x = EXCLUDED.x` ради `RETURNING`: на каждый вызов новая версия строки.
