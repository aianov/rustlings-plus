# Паттерны на Redis

Типы данных и атомарные операции у тебя есть, теперь из них собирают настоящие вещи: кэш над базой, лимиты частоты, блокировки, сессии, присутствие, рейтинги, кэш ленты, накопление счётчиков. Идеи кэша и лимитов ты уже встречал в разделе про сервисы, там они жили в памяти одного процесса. Здесь их распределённая версия: несколько экземпляров сервиса делят один Redis, и у каждого паттерна появляется своя гонка. Примеры в этой главе про интернет-магазин: карточки товаров, корзины, распродажи. Задачи будут про соцсеть.

## Кэш над базой (cache-aside)

Схема: сначала Redis, при промахе база, найденное кладём в Redis со сроком.

```
GET shop:product:42                      -> nil (промах)
SELECT name, price FROM products ...     -> найдено
SET shop:product:42 '{"name":...}' EX 600
```

Срок это страховка: если инвалидацию где-то забыли, устаревшее значение проживёт не дольше него. Дальше три проблемы, у каждой своё решение.

**Сброс до коммита.** Меняя товар, сервис удаляет ключ кэша и обновляет базу. Если удалить до коммита, читатель успеет промахнуться, прочитать из базы ещё старую версию (транзакция не закоммичена) и положить её обратно в кэш на весь срок. Сбрасывают после коммита. Остаётся узкое окно: читатель прочитал базу до коммита, а записал в кэш после нашего сброса. Его закрывают повторным сбросом после того, как закончились идущие пересчёты, версиями в значении или событиями об изменениях (следующая глава). Посмотри визуализацию «Гонка сброса кэша».

**Лавина при массовом истечении.** Если миллион ключей лёг в кэш за минуту с одинаковым сроком, они истекут тоже за минуту, и база получит всё сразу. Срок дают с разбросом: базовый плюс случайная или зависящая от ключа добавка.

**Толпа на один ключ (dog-pile).** Дорогой ключ истёк, и сто читателей одновременно запускают один и тот же тяжёлый запрос. Лечится замком на пересчёт: `SET key:lock 1 NX PX 2000` удаётся одному, он считает и кладёт значение, остальные ждут его в кэше. Срок замка страхует от вычислителя, который упал. Вариант мягче: держать значение дольше, чем считать свежим, и отдавать старое, пока идёт пересчёт.

## Лимиты частоты

**Фиксированное окно**: счётчик на календарную минуту, `INCR` и срок. Просто, но вокруг границы окна проходит вдвое больше лимита. И главное: INCR и установка срока должны быть одним шагом. Если сервис упадёт между ними, ключ останется без срока навсегда, и пользователь будет заблокирован вечно. Скрипт или `EXPIRE key 60 NX` в той же транзакции.

**Скользящее окно**: sorted set, где каждый член это событие, а счёт его время. Удалить всё старше окна, посчитать, добавить, если меньше лимита. Точно, но память растёт с числом событий в окне. Всё одним скриптом, иначе одновременные запросы проскочат мимо подсчёта.

**Token bucket**: ведро на N жетонов, которое пополняется с постоянной скоростью. Хранятся два числа: жетоны и момент последнего пересчёта. При запросе считаем, сколько накапало, ограничиваем вместимостью и списываем жетон. Разрешает короткий всплеск и держит среднюю скорость. Опять одним скриптом.

```lua
local tokens = math.min(capacity, stored + (now - ts) * rate / 1000)
```

Если лимитов несколько (на пользователя и на IP), жетон списывают из всех, только когда все разрешили: иначе отказ одного лимита съедает жетоны другого.

## Распределённые блокировки

```
SET shop:lock:sale-42 <случайный токен> NX PX 10000
```

- **Токен** нужен, чтобы снять только свою блокировку. Если работа заняла больше срока, блокировка уже чужая, и простой DEL снимет её. Снимают скриптом: сравнить значение с токеном и удалить, одним шагом.
- **Продление**: пока работа идёт, владелец продлевает свою блокировку (тоже скриптом с проверкой токена).
- **Fencing token**: даже с продлением процесс может зависнуть дольше срока (пауза сборщика мусора, своп), блокировку возьмёт другой, а первый проснётся и запишет поверх. Защищает только проверка в самом ресурсе: при захвате выдаётся растущий номер, и хранилище отвергает запись со старым номером. Визуализация «Истечение блокировки и fencing token» показывает это по шагам.

Вывод из разбора Мартина Клеппмана: блокировка на Redis хороша для эффективности (не делать работу дважды), а для корректности (никогда не испортить данные) нужна проверка на стороне данных.

## Сессии

Сессия это ключ `session:<токен>` с id пользователя и сроком. Скользящий срок продлевается при каждом запросе: `GETEX key EX 1800` читает и продлевает одной командой. Отзыв сессии это DEL. Чтобы «выйти на всех устройствах», рядом держат множество токенов пользователя: вход добавляет токен (в той же пачке, что и сессию), выход удаляет все сессии из множества одним DEL.

## Присутствие

«В сети» это ключ со сроком, который клиент продлевает heartbeat-ом: перестал присылать, и через срок пользователь сам стал не в сети, без фоновой чистки. Проверка сотни друзей это MGET или pipeline, одним обменом.

## Рейтинги и кэш ленты

Рейтинг это sorted set: `ZINCRBY` прибавляет очки, `ZRANGE ... REV` даёт топ, `ZREVRANK` место. Экран, собранный из нескольких команд, собирают pipeline-ом. Кэш ленты это список id постов: `LPUSH` и `LTRIM` на каждого подписчика, вся раскладка одним pipeline.

## Накопление счётчиков

Лайки и просмотры копят в Redis (`HINCRBY` в хеш ожидающих) и раз в секунду переносят в базу одним UPDATE на пост. Перенос должен отделить снимок от новых поступлений: `RENAME` хеша ожидающих в рабочий ключ атомарен, новые лайки начинают копиться в новом хеше, а рабочий ключ спокойно переносится и удаляется. Чтение и обнуление раздельными командами теряют всё, что пришло между ними. Повторный перенос рабочего ключа после сбоя удваивает лайки, поэтому в бою перенос делают идемпотентным (отметка в базе в той же транзакции).

## Типичные ошибки

- Сброс кэша до коммита.
- Одинаковый срок у массово заполненных ключей.
- Сто одинаковых тяжёлых запросов на промах одного ключа.
- INCR и EXPIRE отдельными командами.
- Лимит без атомарности: подсчёт и запись разными командами.
- DEL блокировки без проверки токена; блокировка как гарантия корректности.
- Поиск сессий по маске вместо индекса.
- Сотни команд по одной там, где нужен MGET или pipeline.
- Чтение и обнуление счётчиков раздельно.
