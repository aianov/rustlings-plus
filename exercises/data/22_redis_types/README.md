# Типы данных Redis

Свой RESP-клиент ты уже написал, теперь пора понять, что лежит по ту сторону. Redis это не просто «кэш ключ-значение», а сервер структур данных в памяти: строки, хеши, списки, множества, упорядоченные множества, HyperLogLog и другие. У каждой структуры свои команды, и правильно выбранная структура превращает задачу в одну команду, а неправильная в цикл с гонками. Примеры в этой главе про сервис коротких ссылок: переходы, рефереры, топ ссылок. Задачи будут про соцсеть.

Задачи ходят в Redis через клиент из course-support (`course_support::redis::Client`). У него тот же API, что получился у тебя: `client.cmd(&["SET", "k", "v"]).await` и `client.pipeline(&[...]).await`, ответ это `Value` с помощниками `text()`, `int()`, `is_nil()`, `list()`, `texts()`.

## Как Redis выполняет команды

Redis выполняет команды **по одной**: пока идёт одна, остальные ждут в очереди. Отсюда два следствия, на которых держится вся глава:

- **каждая команда атомарна**: никто не увидит её наполовину выполненной и не вклинится в середину;
- **долгая команда останавливает всех**: пока Redis обходит миллион ключей, ни один клиент не получит ответа.

При этом последовательность команд одного клиента **не** атомарна: между твоими GET и SET успеют выполниться чужие команды.

## Имена ключей

У Redis нет таблиц: всё пространство это один словарь. Структура данных живёт в именах ключей, и их проектируют так же внимательно, как схему:

```
shortener:link:abc12:target        куда ведёт ссылка
shortener:link:abc12:clicks        счётчик переходов
shortener:user:42:links            ссылки пользователя
```

Пространство имён впереди, дальше сущность, id и поле через двоеточие. Это читаемо, позволяет искать по маске и не даёт разным частям системы наступать друг на друга.

## Строки и сроки

Строка это самое простое значение: текст, число или байты до 512 МБ.

```
SET shortener:link:abc12:target https://example.com EX 86400
GET shortener:link:abc12:target
INCR shortener:link:abc12:clicks
MGET shortener:link:abc12:clicks shortener:link:xyz99:clicks
```

- **Срок** ставится той же командой (`EX` секунды, `PX` миллисекунды) или отдельно (`EXPIRE`). Отдельно опасно: процесс упал между SET и EXPIRE, и ключ стал вечным. `TTL key` показывает оставшиеся секунды (-1 значит «без срока», -2 «ключа нет»).
- **SET перезаписывает ключ целиком**, и срок старого ключа пропадает. Чтобы оставить срок, есть опция `KEEPTTL`.
- **Условная запись**: `NX` пишет, только если ключа нет, `XX` только если есть. Ответ nil значит «не записано». `SET key value NX EX 30` это бронь со сроком одной командой.
- **Счётчики**: `INCR`, `INCRBY`, `DECR` читают, прибавляют и пишут внутри одной команды и возвращают новое значение. Чтение через GET с записью через SET под нагрузкой теряет обновления.
- **Много ключей разом**: `MGET` и `MSET` делают одну команду вместо N. Помни, что Redis отвечает за микросекунды, а обмен по сети стоит сотни: число обменов почти всегда важнее числа команд.

## Pipeline

Если команды разные, их можно отправить пачкой и прочитать ответы пачкой: это pipeline. Один обмен вместо N, но **не атомарность**: между командами пачки могут выполниться чужие. Атомарные пачки будут в следующей главе.

## Хеши

Хеш это маленький словарь в одном ключе. Поля читаются и меняются по отдельности:

```
HSET shortener:link:abc12 target https://example.com owner 42 clicks 0
HGET shortener:link:abc12 target
HINCRBY shortener:link:abc12 clicks 1
HGETALL shortener:link:abc12        -> массив: поле, значение, поле, значение...
```

Объект в хеше лучше объекта в JSON-строке: можно поменять одно поле без чтения остальных, а HINCRBY атомарен. Ограничение: срок ставится на весь ключ, а не на поле.

## Списки

Список это последовательность с быстрыми операциями на концах:

```
LPUSH shortener:link:abc12:referrers "t.me"
LTRIM shortener:link:abc12:referrers 0 99      оставить только первые 100
LRANGE shortener:link:abc12:referrers 0 9      первые 10
LREM shortener:link:abc12:referrers 0 "t.me"   убрать все вхождения
```

Пара LPUSH и LTRIM даёт «последние N» без роста. Список это не множество: одинаковые значения в нём повторяются, и если нужна уникальность, её делают сами.

## Множества

Множество хранит уникальные строки без порядка:

```
SADD shortener:link:abc12:countries RU KZ BY
SISMEMBER shortener:link:abc12:countries RU     -> 1
SCARD shortener:link:abc12:countries            -> 3
SINTER shortener:user:42:tags shortener:user:43:tags
```

Пересечение, объединение и разность считаются на сервере, по сети едет только результат.

## Упорядоченные множества

Sorted set это множество, где у каждого элемента есть счёт (число с плавающей точкой), и элементы всегда отсортированы по нему:

```
ZADD shortener:top 120 abc12 75 xyz99
ZINCRBY shortener:top 1 xyz99
ZRANGE shortener:top 0 9 REV WITHSCORES        десять лучших с очками
ZREVRANK shortener:top abc12                   место (с нуля, по убыванию)
ZREMRANGEBYSCORE shortener:top -inf (10        удалить всех со счётом строго меньше 10
```

Топы, лидеры, ленты по времени, очереди с приоритетом, скользящие окна лимитов: всё это sorted set. По умолчанию ZRANGE идёт по возрастанию счёта, опция `REV` разворачивает порядок. Круглая скобка у границы делает её исключающей.

## HyperLogLog

Сколько уникальных посетителей у ссылки? Множество посетителей даёт точный ответ, но растёт с каждым посетителем. HyperLogLog отвечает приблизительно (ошибка около 0,81%) и занимает не больше 12 КБ при любом числе элементов:

```
PFADD shortener:link:abc12:visitors 10.0.0.1 10.0.0.2
PFCOUNT shortener:link:abc12:visitors
```

Узнать, был ли конкретный посетитель, или удалить его нельзя: структура хранит статистику хешей, а не элементы.

## Поиск ключей: KEYS и SCAN

`KEYS shortener:link:*` возвращает все ключи по маске, но делает это одной командой по всей базе. На миллионах ключей это сотни миллисекунд, когда Redis не отвечает никому. В коде сервиса KEYS не используют.

`SCAN курсор MATCH маска COUNT n` обходит ключи порциями: отдаёт новый курсор и пачку ключей. Начинают с курсора 0, заканчивают, когда сервер вернул 0. Между шагами Redis обслуживает остальных. Цена: ключ может прийти дважды, а ключи, созданные во время обхода, могут не попасть. Ещё лучше не искать по маске вовсе, а держать нужный набор явно, например множество ссылок пользователя.

## Память, вытеснение и диск

Redis держит всё в памяти. Когда память кончается (`maxmemory`), работает политика вытеснения: `allkeys-lru` удаляет давно не использованные ключи, `volatile-lru` только ключи со сроком, `noeviction` отвечает ошибкой на запись. Для кэша выбирают вытеснение, для данных, которые нельзя терять, отдельный экземпляр с noeviction.

На диск Redis сохраняет снимки (RDB) и журнал команд (AOF). Даже с журналом Redis чаще используют как быстрый слой рядом с базой-источником правды, а не вместо неё.

## Типичные ошибки

- SET без срока там, где данные временные; срок отдельной командой.
- SET на ключ со сроком без KEEPTTL.
- GET, вычисление и SET вместо INCR.
- N команд по сети вместо MGET или pipeline.
- Список там, где нужно множество, и наоборот.
- KEYS в коде сервиса.
- Множество для подсчёта уникальных на миллионах элементов.
