# Таблицы и ограничения

Код приложения ошибается. Не потому что программисты плохие, а потому что кода много, запросов
много, а ночью в пятницу кто-то запустит ручной скрипт с опечаткой. Через год в таблице окажутся
читатели без имени, выдачи книг, которых не существует, и две карточки с одним номером. Потом
всё это вылезет в отчёте, а чинить придётся данные руками.

Схема базы это последняя линия обороны. Если правило записано в таблице, никакой код его не
нарушит: Postgres просто откажет, и ошибка случится там, где она сделана, а не через год.
В этой главе мы пишем схему так, чтобы мусору было негде жить. Примеры в тексте про библиотеку
(читатели, книги, выдачи), а в задачах будет соцсеть: перенеси идею на свой случай.

## CREATE TABLE и типы

```sql
CREATE TABLE readers (
    id          bigint,
    full_name   text,
    birth_date  date,
    registered  timestamptz
)
```

У каждого столбца имя и тип. Типы, которые тебе понадобятся почти всегда:

- целые: `smallint` (2 байта, до 32 767), `integer` (4 байта, до 2,1 млрд), `bigint` (8 байт,
  до 9·10¹⁸). Всё, что только растёт (идентификаторы, счётчики), делай `bigint`: ошибка
  «integer out of range» в продакшене приходит неожиданно и больно;
- текст: `text`. `varchar(n)` ограничивает длину, но быстрее не работает: в Postgres они хранятся
  одинаково, а лимит потом приходится расширять миграцией. Если нужен предел, ставь его через
  CHECK (ниже);
- дробные: `numeric(p, s)` точный (деньги, оценки, проценты), `double precision` и `real`
  двоичные и неточные, как `f64` и `f32` в Rust;
- `boolean`, `date`, `timestamptz` (момент времени, о нём в прошлой главе), `uuid`, `jsonb`.

## Ключи

Первичный ключ (`PRIMARY KEY`) однозначно называет строку. Он автоматически значит «уникально и
не NULL», и по нему строится индекс, поэтому поиск по ключу быстрый. Откуда брать значения:

```sql
CREATE TABLE books (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL
)
```

`GENERATED ALWAYS AS IDENTITY` значит: номер выдаёт база по внутреннему счётчику, а попытка
подставить свой отвергается. Вариант `BY DEFAULT` разрешает передать своё значение (удобно при
переносе данных). Старый способ `serial` делает то же, что BY DEFAULT, но через неявную
последовательность; в новых схемах используй IDENTITY.

Второй вариант, когда нельзя выдавать подряд идущие номера (по номеру 41 легко угадать 42):

```sql
CREATE TABLE tickets (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    ...
)
```

`DEFAULT` подставляется, только если столбец не указан в INSERT. Своё значение передать можно.
Цена случайных ключей в том, что вставки попадают в случайные места индекса и он растёт
быстрее, чем у последовательных.

## NOT NULL и DEFAULT

Каждый столбец, который может быть пустым, добавляет в систему ещё одно состояние, которое должны
учитывать все запросы (прошлая глава о том, что бывает, когда забыли). Поэтому по умолчанию
пиши `NOT NULL`, а пустое разрешай только там, где «нет значения» действительно что-то значит.

```sql
CREATE TABLE loans (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    taken_at  timestamptz NOT NULL DEFAULT now(),
    returned  boolean     NOT NULL DEFAULT false,
    note      text
)
```

`DEFAULT` и `NOT NULL` решают разные задачи. DEFAULT работает, когда столбец пропущен;
явный `NULL` он не заменит, это уже дело NOT NULL.

## UNIQUE

```sql
CREATE TABLE readers (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    card  text NOT NULL,
    CONSTRAINT readers_card_uniq UNIQUE (card)
);
CREATE TABLE reservations (
    reader_id bigint NOT NULL,
    book_id   bigint NOT NULL,
    CONSTRAINT reservations_pair_uniq UNIQUE (reader_id, book_id)
)
```

Составной UNIQUE говорит о **сочетании**: один читатель может бронировать много книг, одну книгу
могут бронировать многие, но не одна и та же пара дважды. Два отдельных UNIQUE запретили бы
читателю брать вторую книгу, это совсем другое правило.

Ограничению полезно давать имя: в ошибке база назовёт его, и приложение сможет понять, какое
именно правило нарушено (карточка или пара). Автоматическое имя тоже существует, но зависит от
имён столбцов. Ещё одна тонкость: два `NULL` для UNIQUE считаются разными, поэтому в
уникальном столбце, допускающем NULL, пустых значений может быть сколько угодно.

## CHECK

```sql
CREATE TABLE books (
    ...
    pages integer     CHECK (pages > 0),
    isbn  text        CHECK (length(isbn) IN (10, 13))
)
```

`CHECK (условие)` проверяется при каждой вставке и обновлении, и строка отвергается, если условие
**ложно**. Если условие дало NULL, строка проходит: поэтому `pages` выше может быть пустым, а
для обязательного значения нужен ещё и NOT NULL. Условие видит только текущую строку; сослаться
на другую таблицу CHECK не может, для этого есть внешние ключи.

## FOREIGN KEY: связь «один ко многим»

У книги много выдач, а у выдачи ровно одна книга. Такую связь хранит внешний ключ:

```sql
CREATE TABLE loans (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    book_id bigint NOT NULL REFERENCES books (id)
)
```

Теперь в `book_id` нельзя записать номер несуществующей книги, а книгу, на которую есть выдачи,
нельзя удалить (поведение по умолчанию). Такую гарантию не даст никакой код: между проверкой
«книга есть» и записью другой процесс успеет её удалить. Цена внешнего ключа: каждая вставка
проверяет существование строки, а каждое удаление родителя ищет детей. Чтобы второй поиск был
быстрым, на столбец ссылки обычно нужен индекс (в главе про индексы вернёмся к этому).

### ON DELETE: что делать с детьми

Поведение при удалении родителя задаётся явно:

```sql
REFERENCES books (id)                      -- по умолчанию (NO ACTION): удалить нельзя, пока есть дети
REFERENCES books (id) ON DELETE RESTRICT   -- то же, но проверка сразу, не в конце транзакции
REFERENCES books (id) ON DELETE CASCADE    -- удалить родителя = удалить и детей
REFERENCES books (id) ON DELETE SET NULL   -- у детей ссылка станет NULL
```

Выбор это решение о судьбе данных. CASCADE хорош для «частей целого» (страницы книги вместе
с книгой), а на «ценных» данных тихо унесёт чужую работу: удалишь читателя, исчезнут его выдачи,
а бухгалтерия их ещё не закрыла. SET NULL нужен для необязательных ссылок: столбец обязан
допускать NULL, иначе удаление упадёт с ошибкой нарушения NOT NULL. RESTRICT и умолчание
(оно называется NO ACTION) отвечают «нельзя», пока остались дети. Разница тонкая: NO ACTION
проверяют в конце команды или транзакции, RESTRICT сразу. Открой визуализацию `visuals/fk_on_delete.html`: она
показывает, как одно удаление расходится по таблицам.

## Многие ко многим и ссылка на себя

Книга может быть написана несколькими авторами, у автора много книг. Две таблицы с обратными
ссылками такую связь не выразят, нужна третья, таблица-связка, где каждая строка это одна пара:

```sql
CREATE TABLE book_authors (
    book_id   bigint NOT NULL REFERENCES books (id)   ON DELETE CASCADE,
    author_id bigint NOT NULL REFERENCES authors (id) ON DELETE CASCADE,
    PRIMARY KEY (book_id, author_id)
)
```

Ключом служит сама пара: суррогатный id не нужен. Заодно PRIMARY KEY создаёт индекс по
(book_id, author_id), то есть быстро найдёт авторов книги, а вот «все книги автора» потребует ещё
одного индекса, но это позже.

Таблица может ссылаться на себя: у книги бывает «продолжение»:

```sql
ALTER TABLE books ADD COLUMN sequel_of bigint REFERENCES books (id) ON DELETE SET NULL
```

Так же устроены ответы на комментарии и деревья категорий. Здесь особенно важно правило
удаления: CASCADE по самоссылке сносит всё поддерево.

## ALTER TABLE: менять, не теряя данные

Схема живёт дольше первой версии, и таблицу приходится менять, когда в ней уже лежат данные:

```sql
ALTER TABLE books RENAME COLUMN title TO name;
ALTER TABLE books ADD COLUMN lang text NOT NULL DEFAULT 'en';
ALTER TABLE books DROP COLUMN legacy_code;
ALTER TABLE books ADD CONSTRAINT books_isbn_uniq UNIQUE (isbn);
ALTER TABLE books DROP CONSTRAINT books_isbn_uniq;
ALTER TABLE books RENAME TO volumes;
ALTER TABLE books ALTER COLUMN lang SET NOT NULL;        -- и DROP NOT NULL в обратную сторону
ALTER TABLE loans ADD FOREIGN KEY (book_id) REFERENCES books (id);
ALTER TABLE books ALTER COLUMN pages TYPE integer USING pages::integer;
```

Смена типа заслуживает отдельного слова. Если столбец `pages` был `text` и в нём лежат строки
вроде `'320'`, Postgres не угадает, как их превращать: он потребует явное выражение после
`USING`, которое для каждой старой строки вычисляет новое значение. Если в данных попадётся
`'n/a'`, команда упадёт целиком, ничего не изменив (DDL в Postgres транзакционный), так что
перед такой миграцией полезно посмотреть на данные запросом.

Новый обязательный столбец к заполненной таблице добавляется вместе с `DEFAULT`: у старых строк
должно быть значение. «Удалить и создать заново» не годится, пока в таблице данные пользователей.
Для живой базы у ALTER есть тонкости (блокировки), им посвящена глава про миграции.

## Схемы и search_path

Схема в Postgres это пространство имён внутри базы: `library.books` и `archive.books` две разные
таблицы. По умолчанию всё живёт в схеме `public`. Имя без префикса Postgres ищет по списку
`search_path`, слева направо, а **новые** таблицы создаёт в первой схеме списка.

```sql
CREATE SCHEMA archive;
CREATE TABLE archive.books (id bigint);
SET search_path TO archive, public;
SELECT * FROM books;         -- читает archive.books: она раньше в списке
```

`SET search_path` действует на текущее соединение, а не на базу. На этом держатся тесты курса:
каждому тесту создаётся своя схема, соединения настраиваются на неё, и сотня параллельных тестов
не мешает друг другу. Удаляется схема одной командой `DROP SCHEMA имя CASCADE`.

## DROP, TRUNCATE, IF EXISTS

```sql
DROP TABLE IF EXISTS reservations_old;       -- удалить таблицу, не падая, если её нет
TRUNCATE loans RESTART IDENTITY;             -- выбросить все строки, счётчик с начала
DELETE FROM loans;                           -- удалить построчно (можно с WHERE), счётчик не трогает
```

`IF EXISTS` делает скрипт безопасным для повторного запуска. `TRUNCATE` быстрее `DELETE` на
больших таблицах, но блокирует таблицу целиком и не умеет WHERE. Если на таблицу ссылаются внешние
ключи, TRUNCATE откажет без `CASCADE`, а `CASCADE` очистит и таблицы-дети. Перед `DROP` и
`TRUNCATE` на чужой базе остановись и перечитай имя таблицы.

## Как тесты проверяют схему

В задачах главы ты возвращаешь SQL-скрипт, а тест выполняет его в пустой схеме и **пробует
нарушить**: вставляет мусор, удаляет родителей, дублирует пары. Ждёт он конкретные коды ошибок
Postgres (SQLSTATE): `23502` нарушение NOT NULL, `23503` внешний ключ, `23505` уникальность,
`23514` CHECK, `23001` RESTRICT (удалить родителя с детьми, когда выбрано правило RESTRICT),
`428C9` попытка вписать своё значение в столбец `GENERATED ALWAYS`. Ещё тест может спросить у каталога `information_schema`, какие в таблице столбцы
и типы. Хорошая схема отвергает именно то, что должна, а не всё подряд, поэтому в тестах есть
и вставки, которые обязаны пройти.

## Типичные ошибки

- `integer` для идентификаторов и счётчиков, `varchar(n)` без нужды, `real` для денег.
- Забытый NOT NULL: «в таблице почему-то есть строки без автора».
- Один UNIQUE на каждый столбец пары вместо одного на пару.
- CASCADE там, где данные ценные; SET NULL на столбце с NOT NULL.
- Внешний ключ без индекса на ссылающемся столбце: удаление родителя сканирует всю таблицу детей.
- CHECK, который «защищает» от NULL: он этого не делает.
- `TRUNCATE` и `DROP` без `IF EXISTS` в скриптах, которые запускаются повторно.
