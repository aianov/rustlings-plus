# INSERT, UPDATE, DELETE

Читать данные мы умеем. Но данные надо ещё и менять, и здесь SQL строже, чем кажется. Одна
команда может случайно затронуть всю таблицу. Два пользователя нажимают кнопку одновременно, и
один результат теряется. Запрос «добавь, если нет» работает на тесте и ломается в проде, когда
два клиента сделали это в одну миллисекунду. В этой главе четыре команды (INSERT, UPDATE, DELETE
и их вариации с RETURNING и ON CONFLICT) и привычки, которые делают их безопасными.

Примеры в тексте про интернет-магазин (товары, остатки, заказы), а задачи в соцсети. Таблицы
задач описаны в `seed.sql`, а тест создаёт их в своей схеме, как и раньше.

## INSERT: добавить строки

```sql
INSERT INTO products (sku, title, price)
VALUES ('A-100', 'Mug', 9.50)
```

Всегда перечисляй столбцы. Порядок значений привязан к списку, а столбцы, которых нет в списке
(идентификатор, `created_at`, остаток по умолчанию), база заполнит сама значениями DEFAULT.
Запись `INSERT INTO products VALUES (...)` без списка работает до первой миграции, а потом
ломается: появится новый столбец, и порядок сместится.

Много строк за раз:

```sql
INSERT INTO products (sku, title, price) VALUES
    ('A-101', 'Cup', 7.00),
    ('A-102', 'Plate', 12.00)
```

Одна команда с тремя строками быстрее трёх команд: меньше обменов с сервером, а вся пачка
атомарна, то есть вставится целиком или не вставится вовсе. Данные можно брать и из другой таблицы:

```sql
INSERT INTO products_archive (sku, title)
SELECT sku, title FROM products WHERE discontinued
```

Столбцы результата SELECT идут в столбцы списка INSERT **по позиции**, а не по именам. Имена
столбцов в SELECT ничего не значат, поэтому список столбцов пиши с обеих сторон.

## RETURNING: получить, что записалось

После вставки приложению часто нужны значения, которые проставила база: номер из счётчика,
значения по умолчанию, время. Второй запрос SELECT для этого не нужен:

```sql
INSERT INTO products (sku, title, price) VALUES ('A-103', 'Bowl', 8.00)
RETURNING id, created_at
```

Команда вернёт строки так же, как SELECT. RETURNING есть у INSERT, UPDATE и DELETE, и это не
удобство, а гарантия: ты читаешь именно то, что записал, и между записью и чтением никто не
вклинился.

## UPDATE: менять существующее

```sql
UPDATE products SET price = price * 1.1, updated_at = now()
WHERE category = 'mugs'
```

В SET можно менять несколько столбцов через запятую, а справа использовать текущие значения
этой же строки. WHERE выбирает строки так же, как в SELECT. **Без WHERE обновятся все строки
таблицы.** База не переспросит. Привычка, которая спасает: сначала напиши тот же WHERE в SELECT и
посмотри, сколько строк он находит; потом заменяй SELECT на UPDATE. В приложении проверяй
`rows_affected()`: ждали одну строку, а затронуто тысяча, значит что-то не так.

### «Прочитал, посчитал, записал» против одного UPDATE

Остаток товара на складе, и два покупателя нажали «купить» одновременно. Наивный код:

```
1. SELECT stock FROM products WHERE id = 7        ← оба читают 5
2. new = stock - 1                                ← оба считают 4
3. UPDATE products SET stock = 4 WHERE id = 7     ← оба пишут 4
```

Продано два, а остаток уменьшился на один: потерянное обновление. Правильно переложить
вычисление в базу:

```sql
UPDATE products SET stock = stock - 1 WHERE id = 7
```

UPDATE блокирует строку на время выполнения. Второй запрос (в режиме по умолчанию) подождёт, потом прочитает уже
новое значение и вычтет из него. Ничего не теряется, и приложение вообще не знает остатка.

## DELETE

```sql
DELETE FROM orders WHERE status = 'cancelled' AND created_at < now() - interval '1 year'
RETURNING id, customer_id
```

То же самое: без WHERE удалится всё, а RETURNING отдаёт удалённые строки. Это основа очередей
на базе: «забрать задачу и тут же получить её».

## ON CONFLICT: вставить или обработать конфликт

Кнопка «добавить в избранное» нажата дважды. Если на пару (customer_id, product_id) наложен
уникальный ключ, второй INSERT упадёт с ошибкой. Хорошо, что дубль не появился, плохо, что
приложение получило ошибку из-за совершенно нормального повтора. Варианты ответа на конфликт
записываются в самом INSERT.

### DO NOTHING

```sql
INSERT INTO favorites (customer_id, product_id) VALUES (5, 7)
ON CONFLICT DO NOTHING
```

Если такая пара уже есть, команда молча ничего не делает, затронутых строк ноль. Повторять
такую команду безопасно: это называется идемпотентностью, и в системах, где запросы приходят по
сети, она нужна постоянно (повторы случаются).

### DO UPDATE и EXCLUDED

```sql
INSERT INTO stock_levels (product_id, qty) VALUES ($1, $2)
ON CONFLICT (product_id) DO UPDATE SET qty = stock_levels.qty + EXCLUDED.qty
```

Это «upsert» (update + insert): если строки нет, она вставится; если есть, обновится. В скобках
после ON CONFLICT указывается, какой именно уникальный ключ считается конфликтом. В `DO UPDATE`
доступны две строки: существующая (её называют по имени таблицы, `stock_levels.qty`) и та, что
пыталась вставиться (она называется `EXCLUDED`). Просто `qty` Postgres не примет: он не знает,
какую из двух строк ты имеешь в виду.

Открой визуализацию `visuals/upsert_flow.html`: на ней видно, что происходит с таблицей в
каждом из вариантов.

### Цель конфликта требует уникальности

`ON CONFLICT (sku)` работает только если на `sku` есть уникальное ограничение или уникальный
индекс. Без него Postgres откажет с ошибкой «there is no unique or exclusion constraint matching
the ON CONFLICT specification». А вот запись `ON CONFLICT DO NOTHING` без цели на таблице без
уникальности запустится, и дубль вставится молча, потому что конфликта-то нет. Уникальность
всегда задаёт схема, а ON CONFLICT только выбирает, что делать при нарушении. Если её нет, а
скрипт должен работать сам по себе, создай индекс в том же скрипте:
`CREATE UNIQUE INDEX IF NOT EXISTS имя ON таблица (столбец);`, оператор за оператором через `;`.

### Ловушка: DO NOTHING и RETURNING

```sql
INSERT INTO brands (name) VALUES ('Acme')
ON CONFLICT (name) DO NOTHING
RETURNING id
```

Для нового бренда вернётся id. Но если бренд уже был, вставки нет, и RETURNING возвращает
**пустой набор**: возвращать нечего. Код приложения, который ждёт одну строку, упадёт. Выходов
несколько. Один из них в том, чтобы при конфликте строка всё же оказалась «затронутой» (RETURNING
возвращает строки, которые команда вставила или изменила):

```sql
INSERT INTO brands (name) VALUES ('Acme')
ON CONFLICT (name) DO UPDATE SET name = EXCLUDED.name
RETURNING id
```

Присваивание тут ничего не меняет по смыслу, но строка считается обновлённой, и id вернётся в
обоих случаях. У такого приёма есть цена: каждый вызов
пишет новую версию строки и раздувает таблицу. Другой выход, без этого эффекта, появится позже
(изменяющие CTE, глава про подзапросы).

## UPDATE ... FROM и DELETE ... USING

Данные для изменения часто лежат в другой таблице. В UPDATE она подключается через FROM, в
DELETE через USING, а связь записывается в WHERE:

```sql
UPDATE products SET price = n.new_price
FROM price_changes n
WHERE products.sku = n.sku
```

```sql
DELETE FROM carts USING customers
WHERE carts.customer_id = customers.id AND customers.blocked
```

Забудешь условие связи, и каждая строка соединится с каждой: все товары получат какую-то одну
из новых цен, и ошибки не будет. Ещё одна тонкость: если для строки подходит несколько строк
из FROM, обновление применится к одной из них, какой именно, не определено. Такие данные нужно
сначала свести к одной строке на ключ.

## Как тесты проверяют изменения

Тест создаёт свою схему с данными из `seed.sql`, выполняет твой запрос и смотрит на таблицы
после него. Для запросов с RETURNING он смотрит на возвращённые строки. Там, где важна
гонка (счётчики, «получить или создать»), тест запускает твой запрос много раз параллельно с
разных соединений и проверяет итог. А там, где запрос принимает значения, они передаются
параметрами `$1`, `$2` (из прошлых глав): не подставляй значения литералами в текст запроса, пиши в нём метки `$1`, `$2`, а значения тест передаст отдельно.

## Типичные ошибки

- `UPDATE` или `DELETE` без WHERE.
- «Прочитал в приложении, посчитал, записал» вместо `SET n = n + 1`.
- `INSERT` без списка столбцов.
- `INSERT ... SELECT` с разным порядком столбцов и надеждой, что их сопоставят по именам.
- `ON CONFLICT (столбцы)` на столбцах без уникального ключа.
- `DO NOTHING ... RETURNING` в ожидании строки при конфликте.
- В `DO UPDATE SET x = x + 1` забыто, что `x` неоднозначен: нужно имя таблицы или `EXCLUDED`.
- `UPDATE ... FROM` без условия связи.
