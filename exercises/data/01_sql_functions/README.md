# Выражения, функции и NULL

Профиль в соцсети показывает «зарегистрирован 994 дня назад», «последний вход: давно», «о себе:
не заполнено», а в ленте у поста написано «13.9% лайков». Ни одного из этих чисел в таблице нет.
В таблице лежит сырьё: дата регистрации, дата входа, лайки, просмотры. Всё остальное считается
прямо в запросе, и чем больше ты умеешь делать на стороне базы, тем меньше данных ездит по сети
и тем меньше кода пишешь руками.

Вторая половина главы про вещь, которая сломала больше запросов, чем любая другая: NULL.

## Данные главы

Та же маленькая соцсеть, но таблицы чуть богаче (смотри `seed.sql` рядом с задачей):

```
users: id, username, email, display_name (может быть пусто), status (может быть пусто),
       bio (пусто, '' или одни пробелы), tz (часовой пояс), created_at, last_login_at
posts: id, author_id, body, likes, views, created_at
```

В этой главе пользователей девять, а не двенадцать, и данные другие, чем в прошлой. Посты с 1 по 12 написаны в фиксированные даты, а посты 13 и далее «сегодняшние»: их время
считается от `now()`, то есть от момента, когда тест создал данные. Как тесты запускают твои
запросы, написано в предыдущей главе: каждый тест получает свою схему с этими таблицами.

## Арифметика и целочисленное деление

В SELECT работают привычные `+ - * /` и `%` (остаток). Первая ловушка: **целое, делённое на
целое, остаётся целым**.

```sql
SELECT 7 / 2          ← 3
SELECT -7 / 2         ← -3 (к нулю, не вниз)
SELECT 7 / 2.0        ← 3.5
SELECT 7::numeric / 2 ← 3.5
```

В процентах это бьёт особенно больно: `likes / views` у любого поста с лайков меньше просмотров
даёт ноль, и запрос при этом выполняется без единой жалобы. Приводи один из операндов к
`numeric` до деления (`likes::numeric / views` или `likes * 100.0 / views`), а не после.

## numeric против float, ROUND, CEIL, FLOOR

`ROUND(x, n)` округляет до n знаков, `CEIL` всегда вверх, `FLOOR` вниз:

```sql
SELECT ROUND(13.9444, 1), CEIL(1.8), FLOOR(1.8)    ← 13.9, 2, 1
SELECT ROUND(2.5::float8)                         ← у float8 только форма с одним аргументом
```

Заметь: `ROUND(x, n)` с двумя аргументами существует только для `numeric`. Для `float8` запрос `ROUND(x::float8, 2)` упадёт с «function round(double precision, integer) does not exist», сначала приведи к numeric.

Дробные числа бывают двух семейств. `float8` (он же `double precision`) хранит число двоично, как
`f64` в Rust, и точно представить 0.1 не умеет. `numeric` хранит десятичные цифры и считает
по-человечески, но медленнее. Всё, что потом сверяют глазами (деньги, проценты), держи в `numeric`.

```sql
SELECT 0.1::float8 + 0.2::float8 = 0.3::float8   ← false
SELECT 0.1::numeric + 0.2::numeric = 0.3::numeric ← true
```

Литерал `0.1` без приведения в Postgres и так `numeric`. Поэтому `likes * 100.0 / views` считается
точно, а `likes * 100 / views` обрезает.

## Строки

```sql
SELECT '@' || LOWER(username)        ← склейка и регистр: @alice
SELECT TRIM('  Alice A.  ')          ← Alice A.
SELECT LENGTH('Rust is fun')         ← 11 (символов, не байтов)
SELECT LEFT(city, 3)                 ← первые 3 символа
SELECT SPLIT_PART(tz, '/', 1)        ← первая часть строки «Europe/Berlin» до символа «/», номера с единицы
SELECT REPLACE(email, '@', ' at ')     ← замена подстроки
SELECT concat_ws(' ', username, display_name)   ← склейка через разделитель, NULL пропускается
```

Оператор `||` с NULL даёт NULL: `'id: ' || NULL` это NULL. Поэтому подпись из необязательных
кусков собирают через `concat` или `concat_ws`: они значения NULL просто игнорируют.

## Приведение типов

`CAST(x AS тип)` и короткая запись Postgres `x::тип` делают одно и то же:

```sql
SELECT '12'::integer * 2             ← 24
SELECT length(id::text)              ← число цифр в id: length(число) не существует, нужен текст
SELECT '2025-12-25'::date - 7        ← 2025-12-18
```

Приведений «само собой» в Postgres мало, и это полезно: `'abc'::int` падает ошибкой, а не
превращается в ноль. Склеить число со строкой через `||` получится и без `::text` (`1 || 'a'` работает), но явное приведение понятнее. А вот функции строк вроде `length(id)` для числа не определены, там без `::text` не обойтись.

## CASE: условие внутри запроса

```sql
SELECT id,
       CASE
           WHEN likes >= 100 THEN 'hot'
           WHEN likes >= 20  THEN 'popular'
           ELSE 'quiet'
       END AS heat
FROM posts
```

`CASE` проверяет `WHEN` сверху вниз и берёт первую подошедшую ветку. Поэтому границы пишут
«от самой строгой к самой мягкой» и не повторяют верхнюю границу. Без `ELSE` непокрытые случаи
превращаются в `NULL`: пиши `ELSE` всегда.

## NULL и трёхзначная логика

В обычном языке у условия два исхода. В SQL три: **TRUE, FALSE и NULL («неизвестно»)**. NULL
означает «значения нет или оно неизвестно», и вычисления с неизвестным дают неизвестное:

```sql
SELECT NULL = NULL        ← NULL
SELECT NULL <> 'x'        ← NULL
SELECT 5 + NULL           ← NULL
SELECT NULL AND false     ← false (чем бы ни было неизвестное, AND с false даёт false)
SELECT NULL OR true       ← true
SELECT NULL AND true      ← NULL
```

А теперь главное правило: **WHERE оставляет строку только когда условие TRUE.** FALSE и NULL
отбрасываются одинаково. Вот отсюда растёт целый класс тихих багов.

```
users.status:  active  banned  NULL  pending

WHERE status <> 'banned'
   active  <> 'banned'  TRUE    остаётся
   banned  <> 'banned'  FALSE   отброшена
   NULL    <> 'banned'  NULL    отброшена  <- её никто не банил!
   pending <> 'banned'  TRUE    остаётся
```

Открой визуализацию `visuals/null_logic.html`: строки проходят условие по одной, и видно, как NULL
исчезает. Чтобы сохранить пользователей без статуса, у тебя три способа:

```sql
WHERE status <> 'banned' OR status IS NULL
WHERE status IS DISTINCT FROM 'banned'
WHERE COALESCE(status, 'none') <> 'banned'
```

`IS DISTINCT FROM` это «не равно», которое считает NULL обычным значением: `NULL IS DISTINCT FROM
'x'` true, `NULL IS DISTINCT FROM NULL` false. Парная форма: `IS NOT DISTINCT FROM`, а это
«равно», которое умеет сравнивать NULL с NULL.

Заметь, что `x = NULL` не проверка на пустоту. Для неё есть `IS NULL` и `IS NOT NULL`.

Похожая ловушка живёт в `NOT IN`: `3 NOT IN (1, 2, NULL)` даёт NULL, а не true, и WHERE такую
строку отбросит. Эту ловушку мы разберём подробно, когда дойдём до подзапросов.

## COALESCE и NULLIF

`COALESCE(a, b, c)` возвращает первое значение, которое не NULL: подстановка запасного.
`NULLIF(a, b)` возвращает NULL, если `a = b`, и `a` иначе: превращает «пустое» в NULL.

```sql
SELECT COALESCE(nickname, 'аноним')                      ← запасное значение
SELECT COALESCE(NULLIF(TRIM(city), ''), 'unknown')       ← пустая и пробельная строка тоже «нет»
SELECT likes::numeric / NULLIF(views, 0)                 ← деление на ноль превращается в NULL
```

Порядок важен: `ROUND(COALESCE(x, 0), 3)` даст `0.000`, а `COALESCE(ROUND(x, 3), 0)` вернёт `0` без знаков после запятой, потому что подставленный ноль не прошёл округление. Запасное значение подставляй до форматирования.

Деление на ноль в Postgres не возвращает NULL, а бросает ошибку и валит весь запрос. Из-за одного
странного поста в таблице из миллиона. `NULLIF(делитель, 0)` делает из нуля NULL, результат
деления становится NULL, а `COALESCE` подставляет то, что нужно по смыслу. Заранее подумай,
подходит ли 0: «нет просмотров» и «доля лайков ноль» не одно и то же, иногда честнее показать
прочерк, то есть оставить NULL.

## Дата и время

```sql
SELECT now()                                  ← текущий момент (timestamptz)
SELECT DATE_TRUNC('year', created_at)         ← начало года: 2026-01-01 00:00:00+00
SELECT EXTRACT(hour FROM created_at)          ← час, 0..23 (тип numeric!)
SELECT EXTRACT(week FROM created_at)::int     ← номер недели года

День недели даёт `EXTRACT(isodow ...)` (понедельник 1, воскресенье 7) или `EXTRACT(dow ...)` (воскресенье 0, понедельник 1). Квартал: `EXTRACT(quarter ...)`.
```

`now()` внутри одной транзакции всегда возвращает один и тот же момент (начала транзакции), а
`clock_timestamp()` каждый раз настоящее время. `DATE_TRUNC` пригодится в главе про агрегаты: по
нему группируют по дням и месяцам.

### Интервалы

```sql
SELECT now() - interval '3 hours'             ← три часа назад
SELECT created_at + interval '1 week'
SELECT timestamptz '2026-10-01 00:00+00' - created_at   ← результат: interval
SELECT EXTRACT(day FROM timestamptz '2026-10-01 00:00+00' - created_at)  ← полных дней в разности
```

Обрати внимание: разность двух моментов времени и разность двух `date` дают разное. Если зарегистрировались вечером, а сравниваем утром следующего дня, то интервал ещё не набрал полных суток (`EXTRACT(day ...)` даст на единицу меньше, чем разность календарных дат).

Условие вида `created_at > now() - interval '3 hours'` хорошо дружит с индексом: столбец стоит один, а
вся арифметика справа. Поставишь вычисления на столбец, и индекс использовать нельзя (в главе про
индексы это окажется важным).

### timestamptz против timestamp и часовые пояса

Это самое неочевидное место главы. Названия сбивают с толку:

- `timestamptz` (timestamp with time zone) хранит **момент времени** (внутри это UTC). Пояс **не
  хранится**: при вводе время переводится в UTC, при выводе в пояс сессии (`TimeZone`).
- `timestamp` (without time zone) хранит **настенные часы** без пояса: «2026-03-01 23:30», и
  непонятно, где это и когда на самом деле.

```
момент:   2024-03-01 23:30 UTC
           |
  Берлин   2024-03-02 00:30   Нью-Йорк  2024-03-01 18:30   Токио  2024-03-02 08:30
```

Оператор `AT TIME ZONE` переводит между двумя представлениями. Для `timestamptz` он даёт настенное
время в заданном поясе (тип `timestamp`), для `timestamp` наоборот, говорит «эти часы показаны в
таком поясе» и даёт момент:

```sql
SELECT created_at AT TIME ZONE 'Asia/Tokyo'          ← 2024-03-02 08:30:00 (timestamp)
SELECT (published_at AT TIME ZONE 'Europe/Paris')::date ← календарная дата в Париже
```

Классический баг: `created_at::date` берёт дату в поясе **сессии**, то есть сервера или
подключения, и для пользователя из Токио это бывает вчера. Правило: храни моменты в
`timestamptz`, пояс пользователя храни отдельным столбцом, переводи при показе. Соединения тестов в
курсе настроены на UTC, так что результаты на любой машине одинаковые.

## Типичные ошибки

- `likes / views` с целыми числами: везде ноль, и ошибок нет.
- `status <> 'x'` по столбцу, где бывает NULL: пропадают строки без значения.
- `'id: ' || NULL`: вся строка превращается в NULL.
- Деление на столбец, который бывает нулём: ошибка посреди запроса.
- `timestamp` без пояса там, где нужен момент времени, и `::date` без `AT TIME ZONE`.
- `EXTRACT` возвращает `numeric`: без `::int` в тексте результата будут хвосты и лишние знаки.
- `CASE` без `ELSE`: непокрытое молча становится NULL.
