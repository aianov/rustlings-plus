# SELECT с нуля

В нашей соцсети тысячи пользователей и сотни тысяч постов. Открываешь ленту, и приложение
должно ответить на вопрос вроде «покажи двадцать самых свежих постов людей, на которых я
подписан». Хранить всё это в памяти процесса мы уже пробовали: процесс перезапустился, и
соцсеть забыла всех. Поэтому данные живут в базе, а приложение задаёт ей вопросы на языке SQL.

Эта глава про самый частый вопрос на свете: SELECT. Если научиться читать и писать его
уверенно, дальше всё (соединения, агрегаты, индексы) будет надстройкой, а не магией.

## Таблица, строка, столбец

Таблица это набор строк. У каждой строки одни и те же столбцы, и у каждого столбца есть тип
(число, текст, время). Строка не знает своего номера в таблице и ни с кем не стоит рядом:
порядка у строк нет, пока ты сам его не попросишь. Запомни это сразу, на этом ломаются
половина ошибок новичков.

Во всех задачах главы живёт одна и та же маленькая соцсеть из двух таблиц:

```
users                                                  posts
id  username  email              country age status    id  author_id  body                  likes created_at
 1  alice     alice@example.com  DE      28  active     1  1          Hello, world!           12  2026-09-01 ...
 2  bob       bob@example.com    US      34  active     2  1          Rust is fun             30  2026-09-03 ...
 3  carol     carol@mail.org     DE      41  banned     3  2          Coffee first, ...        7  2026-09-04 ...
 ...                                                    ...
12  bob_2     bob2@mail.org      US      22  active    18  7          Morning run              4  2026-09-19 ...
```

Ещё у пользователя есть `created_at` (когда зарегистрировался) и `last_login_at` (когда заходил
последний раз, а у тех, кто ни разу не заходил, там пусто). Полностью данные лежат в файле
`seed.sql` рядом с задачей: открой его и посмотри, там 12 пользователей и 18 постов.

## Как устроены задачи этой главы

В каждой задаче ты пишешь SQL-запрос строкой в обычной Rust-функции:

```rust
fn contacts() -> &'static str {
    "SELECT username, email FROM users"
}
```

А тест делает за тебя всю остальную работу. Он подключается к Postgres курса, создаёт
собственную пустую схему с уникальным именем (схема это отдельное пространство имён внутри базы:
в ней свои таблицы, и они не пересекаются с чужими), заливает в неё `seed.sql`, выполняет твой
запрос и сравнивает ответ с ожидаемым. Потом схема удаляется. Тесты идут параллельно и друг другу
не мешают, потому что у каждого своя схема. Именно поэтому в запросах таблицы пишутся просто
`users`, без всякого префикса: соединение тестов настроено так, что имена ищутся в схеме теста.

Если Postgres отвергнет твой запрос, тест покажет текст запроса и ошибку базы. Читай её
внимательно, в ней обычно сказано всё: какого столбца нет, где опечатка, что нельзя сравнить.

Для задач ничего запускать вручную не нужно: тесты сами ходят в Postgres на `127.0.0.1:55432`.
Хочешь поиграть руками? Подними базу (`docker compose up -d` в корне курса), создай свою схему
и залей данные:

```
(echo 'CREATE SCHEMA play; SET search_path TO play;'; cat seed.sql) | docker exec -i rustlings-postgres psql -U rustlings
docker exec -it rustlings-postgres psql -U rustlings
rustlings=# SET search_path TO play;
rustlings=# SELECT username, email FROM users WHERE id < 5;
```

## SELECT и FROM: что и откуда

Самый короткий осмысленный запрос:

```sql
SELECT username, email FROM users
```

После `SELECT` идёт список того, что вернуть, после `FROM` таблица, откуда брать. Вместо списка
можно поставить звёздочку `*`, и придут все столбцы. В консоли это удобно. В коде приложения
пиши столбцы явно: тогда после `ALTER TABLE` ответ не поменяется сам по себе.

В списке можно не только перечислять столбцы, но и считать:

```sql
SELECT username, age * 12 AS age_in_months, age + 1 AS next_age FROM users
```

`AS` даёт результату имя. Оно живёт только в этом ответе. Если имени не дать, Postgres назовёт
столбец сам (`?column?`), и клиентский код потом не поймёт, что это.

## Кавычки: одинарные и двойные

В SQL кавычки означают разное, и это первая ловушка:

- `'alice'` в одинарных кавычках это **значение**, строка;
- `"alice"` в двойных кавычках это **имя**: столбец, таблица, псевдоним.

```sql
SELECT id FROM users WHERE email = 'bob@example.com'    ← ищем строку
SELECT id FROM users WHERE email = "bob@example.com"    ← ошибка: нет столбца bob@example.com
```

Если в строке должна быть одинарная кавычка, её удваивают: `'it''s'`.

## WHERE: оставить нужные строки

`WHERE` проверяет условие для каждой строки отдельно и оставляет только те, для которых оно
истинно.

```sql
SELECT id FROM posts WHERE likes > 20
SELECT id FROM posts WHERE author_id = 1 AND likes >= 10
SELECT id FROM posts WHERE NOT (likes > 20 OR author_id = 3)
```

Сравнения: `=`, `<>` (не равно), `<`, `<=`, `>`, `>=`. Равенство это **один** знак `=`. Условия
склеиваются через `AND`, `OR`, `NOT`. `NOT` стоит перед условием и переворачивает его; он связывает
сильнее, чем AND, поэтому почти всегда его пишут со скобками: `NOT (a OR b)`.

### AND сильнее OR

Как в арифметике умножение сильнее сложения, так в логике `AND` сильнее `OR`. Поэтому:

```sql
WHERE author_id = 1 AND likes > 20 OR likes = 0
```

читается как `(author_id = 1 AND likes > 20) OR likes = 0`, то есть «популярные посты первого
автора, а ещё вообще все посты без лайков». Если ты имел в виду другое, поставь скобки:

```sql
WHERE author_id = 1 AND (likes > 20 OR likes = 0)
```

Правило на всю жизнь: смешал AND и OR, поставь скобки, даже если приоритет и так совпадает с
задумкой.

### BETWEEN, IN, LIKE

Три сокращения, которые делают условия короче.

```sql
WHERE likes BETWEEN 10 AND 30               ← likes >= 10 AND likes <= 30, обе границы включены
WHERE likes NOT BETWEEN 10 AND 30
WHERE author_id IN (1, 3, 7)                ← author_id = 1 OR author_id = 3 OR author_id = 7
WHERE author_id NOT IN (1, 3, 7)
```

`LIKE` сравнивает строку с шаблоном. В шаблоне `%` это любое количество любых символов (хоть ноль),
а `_` ровно один любой символ:

```sql
WHERE body LIKE 'Rust%'          ← текст начинается с Rust
WHERE body LIKE '%thread'        ← оканчивается на thread
WHERE body NOT LIKE '%Postgres%' ← не содержит Postgres
WHERE body LIKE '_ello%'         ← первый символ любой: Hello, Jello...
WHERE body ILIKE '%LINUX%'       ← ILIKE не различает регистр
```

`LIKE` различает регистр, `ILIKE` нет (это расширение Postgres). Заметь: подчёркивание внутри
шаблона всегда значит «любой один символ», в том числе когда в нике настоящее подчёркивание
(`bob_2`).

## NULL: значения нет

У `last_login_at` бывает пусто: пользователь не заходил ни разу. В SQL это особое значение
`NULL`, и оно значит «неизвестно», а вовсе не ноль и не пустая строка. Из этого следует странное:
любое сравнение с NULL даёт не «истина» и не «ложь», а снова NULL.

```sql
SELECT NULL = NULL      ← NULL, а не true
SELECT 5 > NULL         ← NULL
```

`WHERE` пропускает только строки, где условие **истинно**. Поэтому

```sql
SELECT id FROM orders WHERE shipped_at = NULL    ← всегда пусто, и ошибки нет (таблица orders для примера)
```

не находит никого. Запрос не падает, а тихо возвращает пустоту, и это страшнее ошибки. Для проверки
есть отдельные формы:

```sql
WHERE shipped_at IS NULL
WHERE shipped_at IS NOT NULL
```

В главе про выражения мы разберём эту «трёхзначную логику» целиком. Пока достаточно правила:
на NULL проверяют только через `IS NULL`.

## ORDER BY: порядок строк

Без `ORDER BY` порядок строк не определён. Сегодня они приходят по id, завтра после обновления
таблицы иначе, и оба раза Postgres прав. Хочешь порядок, проси:

```sql
SELECT id, author_id, likes FROM posts ORDER BY author_id ASC, likes DESC
```

Ключей может быть несколько: по второму упорядочиваются строки, у которых первый равен.
`ASC` (по возрастанию) стоит по умолчанию, `DESC` (по убыванию) указывается у каждого ключа свой.
`ORDER BY a, b DESC` сортирует `a` по возрастанию, а `DESC` относится только к `b`.

### Где окажутся NULL

Postgres считает NULL **больше любого значения**. Поэтому при `ASC` пустые идут в конце, а при
`DESC` в начале. Для списка «кто заходил недавно» это ровно наоборот: сверху окажутся те, кто не
заходил никогда. Положение задаётся явно:

```sql
ORDER BY shipped_at DESC NULLS LAST
```

### Равные значения и стабильный порядок

Допустим, в списке пользователей несколько человек из одной страны, и ты сортируешь
`ORDER BY country`. В каком порядке будут эти люди внутри страны? Postgres не обещает ничего. Для одного запроса это не страшно, а для страниц
(«первые пять», «следующие пять») катастрофа: пост, стоящий на границе страниц, может оказаться
на обеих или ни на одной (то же случится с постами с равным числом лайков). Лекарство простое: в конце `ORDER BY` добавь уникальный столбец,
обычно `id`:

```sql
ORDER BY country, id
```

## LIMIT и OFFSET: страницы

```sql
SELECT username FROM users ORDER BY id LIMIT 5 OFFSET 10
```

`LIMIT 5` отдаёт пять строк, `OFFSET 10` пропускает десять перед этим. Третья страница по пять
строк это `LIMIT 5 OFFSET 10`. Без `ORDER BY` обе команды бессмысленны: «первые четыре» из
неупорядоченного набора это случайные четыре. А ещё `OFFSET` не перепрыгивает, а честно читает и
выбрасывает все пропущенные строки, так что глубокие страницы медленные. Лучшая замена,
пагинация по курсору, ждёт тебя в главе про индексы.

## DISTINCT: убрать повторы

```sql
SELECT DISTINCT likes FROM posts                  ← каждое число лайков один раз
SELECT DISTINCT author_id, likes FROM posts       ← каждая пара один раз
```

`DISTINCT` считает повтором совпадение **всей** строки результата, а не первого столбца. Выбрать
«любой статус для каждой страны» он не умеет. Кстати, DISTINCT стоит денег: Postgres сортирует
или хеширует весь результат. Если ты ставишь его, чтобы убрать странные дубли после соединения
таблиц, ищи ошибку в соединении, а не в данных.

## В каком порядке запрос выполняется на самом деле

Пишем мы `SELECT ... FROM ... WHERE ... ORDER BY ... LIMIT`, но выполняется всё иначе:

```
 FROM       взять таблицу(ы)
   |
 WHERE      оставить строки, где условие истинно
   |
 GROUP BY   (в главе про агрегаты)
   |
 HAVING     (тоже там)
   |
 SELECT     вычислить выражения, дать псевдонимы
   |
 ORDER BY   упорядочить
   |
 LIMIT      отрезать лишнее, OFFSET пропускает начало
```

Откуда следует вещь, на которой спотыкаются все. Псевдоним рождается на шаге `SELECT`, а `WHERE`
выполняется раньше. Поэтому:

```sql
SELECT length(body) AS len FROM posts WHERE len > 10                ← ошибка: столбца len нет
SELECT length(body) AS len FROM posts WHERE length(body) > 10       ← работает
SELECT length(body) AS len FROM posts ORDER BY len                  ← работает: ORDER BY позже SELECT
```

Открой визуализацию (клавиша `v` в интерфейсе курса, файл `visuals/select_order.html`): на ней
видно, как строки проходят этапы, и есть переключатель, который воспроизводит эту ошибку.

## Параметры вместо склейки

Сейчас в наших запросах значения написаны прямо в тексте: `author_id = 1`. В настоящем приложении
номер автора приходит от пользователя. Первая мысль: склеить строку,
`format!("... WHERE author_id = {a}")`. Не делай так никогда. Если пользователь пришлёт
`1 OR 1=1`, он перепишет твой запрос и получит чужие посты (это называется SQL-инъекция, и из-за
неё утекали целые базы).

Правильно так: в тексте запроса стоят **метки** `$1`, `$2`, ... (нумерация с единицы), а сами
значения отправляются на сервер отдельно, как данные. Postgres разбирает текст запроса один раз, и
никакое значение уже не сможет стать частью SQL:

```sql
SELECT id FROM posts WHERE author_id = $1 AND likes >= $2
```

```rust
let ids: Vec<i64> = sqlx::query_scalar(sql).bind(1i64).bind(10i32).fetch_all(&pool).await?;
```

Метки заменяют только **значения**. Имя столбца или таблицы меткой не подставить (`ORDER BY $1`
не сортирует по столбцу, а сортирует по константе). Об этом ещё поговорим, когда будем писать
динамические фильтры. Весь Rust-код дальше в курсе пишет запросы только с метками.

## Типичные ошибки

- Двойные кавычки вместо одинарных вокруг строки: «column "alice" does not exist».
- `= NULL` вместо `IS NULL`: пустой ответ без ошибки.
- `AND` и `OR` без скобок: лишние строки в ответе, которых не видно на маленьких данных.
- `ORDER BY ... DESC` по столбцу с пропусками: пустые значения оказываются сверху.
- `LIMIT` без `ORDER BY` или с `ORDER BY` по столбцу с повторами: страницы «плывут».
- Псевдоним из `SELECT` в `WHERE`: «column does not exist».
- Значения, склеенные в текст запроса, вместо `$1`.
