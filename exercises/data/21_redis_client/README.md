# Свой клиент Redis

Кофейня. Кассир принимает заказ, несёт его на кухню, стоит и ждёт, пока приготовят, несёт стакан гостю, и только
потом берёт следующий заказ. Кухня простаивает, очередь растёт, хотя бариста мог бы делать десять напитков
подряд. Умный кассир складывает заказы на кухню пачкой, а напитки раздаёт в том порядке, в каком их принял.
Клиент Redis решает ту же задачу, и вся глава о том, как это сделать и не перепутать стаканы.

## Соединение и порядок

Redis по одному соединению выполняет команды строго по очереди и отвечает строго в том же порядке. Идентификаторов
запросов в протоколе нет: ответ номер три принадлежит команде номер три, потому что она была третьей. На этом
держится всё остальное, и от этого же все беды: стоит одному ответу потеряться или достаться не тому, и каждый
следующий ответ уедет не к тому вызывающему. Ошибки не будет, просто чужие значения.

Простейший клиент это сокет, буфер и метод `call`: записал команду, читай, пока в буфере не появится целый ответ.
Читать надо в цикле «разбери то, что есть, а если не хватает, дочитай»: ответ приходит кусками, а два ответа
иногда приходят одним куском (это та самая работа с неполными кадрами из прошлой главы). Буфер принадлежит
соединению, а не вызову: остаток после ответа принадлежит следующему.

## Pipelining

Круг по сети стоит сотни микросекунд, а сам Redis выполняет команду за единицы. Если ждать ответ на каждую
команду, клиент в основном ждёт сеть. Pipelining это когда команды отправляют не дожидаясь ответов, а потом читают
столько ответов, сколько отправлено:

```
по одной:   → A ← a   → B ← b   → C ← c      три круга
пачкой:     → A B C   ← a b c                  один круг
```

Подвох в ошибках внутри пачки. Если команда B отработала с ошибкой, ответ на неё всё равно приходит и занимает
своё место, и клиент обязан прочитать его, а не вернуться раньше. Иначе ответы на B и C останутся в сокете, и
следующий вызов получит чужие.

## Мультиплексирование: один актор на соединение

Приложение с сотней задач не станет выстраивать пачки руками. Можно положить соединение под `Mutex`, но тогда замок
держится на всё время похода в сеть, и вся сотня стоит в очереди. Лучше другая схема. Соединением владеет одна
задача, актор. Остальные присылают ему команды по каналу и каждая ждёт свой ответ в собственном `oneshot`:

```
задача 1 ─┐                       ┌─ [ответчик 1][ответчик 2][ответчик 3] очередь
задача 2 ─┼─ канал ─→ актор ──────┤
задача 3 ─┘                       └─→ сокет: GET, INCR, GET  ──→ Redis
                       ответ 1 → ответчик 1,  ответ 2 → ответчик 2, ...
```

Актор делает два дела одновременно (для этого `select!`): принимает новые команды, пишет их в сокет и ставит
ответчика в конец очереди (`VecDeque`), и читает ответы, раздавая их ответчикам с начала очереди. Пока в пути
несколько команд, получается pipelining без единой строчки о пачках у вызывающих. Очередь ограничивают: если сервер
замер, неограниченная очередь съест всю память. Пока она полна, актор не берёт новые команды из канала, и
давление уходит вызывающим.

Тот же скелет на другом примере, чтобы стало видно форму (калькулятор, а не Redis):

```rust
struct Question {
    expr: String,
    answer: oneshot::Sender<f64>,
}

async fn calculator(mut rx: mpsc::Receiver<Question>) {
    while let Some(q) = rx.recv().await {
        let _ = q.answer.send(evaluate(&q.expr));
    }
}
```

Когда исчезла последняя копия отправителя, `recv` возвращает `None`, цикл заканчивается, а вместе с ним
закрывается всё, чем актор владел. Закрытие соединения получается само.

## Отмена посреди ответа

В async Rust любое будущее можно бросить на любом `await`: таймаут, `select!`, закрытый запрос. Если клиент без
актора отправил команду, начал читать ответ и был отменён, то ответ остался в пути, и его получит следующий вызов.
С актором всё проще: вызывающий ушёл, а ответчик в очереди остался, и актор прочитает ответ и выбросит. Главное
правило: место в очереди нельзя пропускать, ответ нужно прочитать в любом случае.

Для клиента без актора лечение другое: считать соединение испорченным и заменить. Метку «обмен не завершён» ставят
до первого `await` и снимают после полного ответа. Тогда обрыв в любом месте оставит её поднятой.

## Обрывы и переподключение

Redis перезапустят, сеть моргнёт. Команды, которые уже ушли в оборванное соединение, находятся в неопределённом
состоянии: сервер мог выполнить `INCR` и не успеть ответить. Клиент не повторяет их сам. Они получают ошибку, и
решает тот, кто знает, идемпотентна ли команда. Команды, которые ещё ждут в канале, можно спокойно отправить в
новое соединение, поэтому актор переживает обрыв: внешний цикл ждёт паузу, подключается заново и продолжает брать
запросы из того же канала. Пауза нужна, чтобы тысяча клиентов не атаковала только что поднявшийся сервер одновременно.

## Сроки

TCP-соединение открывает ядро, когда программа ещё не вызвала `accept`: зависший сервер охотно принимает подключения
и молчит. Поэтому «подключились» ничего не значит, и подключением считают момент, когда сервер ответил на PING
(плюс `AUTH` и `SELECT`, если они нужны). Срок ставят на всё подключение целиком, и ещё один на каждую команду. С актором
срок на команду безопасен: отмена ожидания не трогает соединение, поздний ответ будет прочитан и выброшен.

## Блокирующие команды, MULTI и пул

`BLPOP` и `XREAD BLOCK` ждут, и пока ждут, остальные команды того же соединения стоят за ними. Поэтому на общем
мультиплексированном соединении их держать нельзя: фоновый воркер, ждущий задачу, заморозит весь сервис. Им дают
отдельное соединение. Для `MULTI` причина другая: между `MULTI` и `EXEC` не должно вклиниваться чужих команд, а на
общем соединении они вклиниваются. Раз таких соединений нужно несколько, нужен пул: не больше N, свободные
переиспользуются, ожидающие встают в очередь. Разрешение на соединение хранится в охраннике (`Drop` возвращает его в
пул), а испорченное соединение возвращать нельзя.

## Типичные ошибки

- Один `read` на ответ. Работает на коротких ответах и ломается на длинных.
- Возврат из пачки при первой ошибке: остальные ответы остаются в сокете.
- `BufWriter` без `flush`: команда в буфере, клиент ждёт ответ.
- Таймаут вокруг `call` без защиты соединения: следующий вызов читает запоздавший ответ.
- Пропуск ответчика брошенного вызова.
- Блокирующая команда на общем соединении.
- Автоматический повтор неидемпотентных команд после обрыва.
- Переподключение без паузы.
