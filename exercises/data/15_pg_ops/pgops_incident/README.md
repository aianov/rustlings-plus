# Инцидент: база тормозит

Пятница, вечер, дежурный получает алерт: ответы соцсети стали медленными, пул соединений забит, графики показывают
растущую очередь. Руками разбираться в `psql` можно, но в следующий раз будет то же самое. Пора превратить разбор
в библиотеку `pg_incident`, которую запускает команда на дежурстве: она находит виновников, аккуратно снимает затор,
чистит накопившийся мусор и закрывает дыру, из-за которой всё случилось.

## Что уже есть

- `src/lib.rs`: тип `Diagnosis` и четыре функции с `todo!()`. Сигнатуры менять нельзя.
- `tests/acceptance.rs`: приёмочные тесты. Каждый тест создаёт свою схему в Postgres курса (`RUSTLINGS_PG_URL`) и
  разыгрывает «инцидент»: сеансы с разными ролями (имена приложений начинаются с префикса теста), которые держат
  замки, снимки и открытые транзакции. Схему тест удаляет в конце.

## Что нужно сделать

Во всех функциях `app_prefix` это префикс `application_name` сеансов, которыми занимается библиотека. Сеанс, из
которого вызывают функции, и сеансы с другими префиксами не трогаются.

1. `diagnose(pool, app_prefix)` возвращает `Diagnosis` с четырьмя списками имён приложений, каждый отсортирован:
   - `waiting`: сеансы, которые ждут чужой замок;
   - `blockers`: сеансы, которые держат замок, нужный кому-то из ждущих;
   - `idle_in_tx`: сеансы в любом из состояний `idle in transaction` (включая `(aborted)`);
   - `horizon_holders`: из простаивающих в транзакции те, что держат горизонт очистки (активный снимок или
     выданный номер транзакции). Транзакция, которая ничего не прочитала и не записала, ничего не держит.
2. `resolve(pool, app_prefix)` закрывает соединения всех `blockers` и всех `horizon_holders` и возвращает отсортированный
   список имён закрытых. Ждущие, не причастные простаивающие и обычные соединения остаются живы.
3. `vacuum_bloated(pool, min_dead_pct)` находит таблицы текущей схемы, где мёртвых версий не меньше `min_dead_pct`
   процентов от всех (по статистике), чистит каждую обычным `VACUUM` без блокировок на чтение и запись и возвращает
   отсортированные имена обработанных таблиц. Пустые таблицы не должны ронять функцию.
4. `harden_role(pool, role, password)` создаёт роль приложения: вход по паролю, `statement_timeout` 1 секунда,
   `idle_in_transaction_session_timeout` 2 секунды, права только на данные (SELECT, INSERT, UPDATE, DELETE) во всех
   таблицах текущей схемы (и счётчиках), включая таблицы, которые владелец создаст позже. DDL и TRUNCATE ей недоступны.

## Критерии приёмки

`cargo test` в корне проекта: все тесты из `tests/acceptance.rs` проходят. Они проверяют каждый список диагностики,
что `resolve` снимает затор (ждущий завершает обновление), закрывает ровно тех, кого нужно, и что после этого `vacuum_bloated`
действительно убирает мёртвые версии, а роль ведёт себя как положено.

## Структура

```
pg_incident/
  Cargo.toml
  src/lib.rs          функции и типы (твоя работа)
  tests/acceptance.rs приёмочные тесты (не менять)
```

## Как запускать

Postgres курса должен работать (`docker compose up -d` в папке курса). Потом `cargo test`.

## Подсказки по теории

Всё есть в README главы: `pg_stat_activity` и `pg_blocking_pids`, разница между `pg_cancel_backend` и
`pg_terminate_backend`, `backend_xmin` и `backend_xid` как признак держателя горизонта, статистика
`pg_stat_user_tables`, `VACUUM` и `VACUUM FULL`, настройки роли и права по слоям (схема, таблицы, счётчики, права по умолчанию).
