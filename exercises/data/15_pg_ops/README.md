# Postgres в эксплуатации

Интернет-магазин, чёрная пятница. В восемь вечера оформление заказа начинает отвечать по десять секунд, в пол девятого
вообще перестаёт. Разработчики смотрят графики процессора: он почти свободен. Память в норме, диск скучает. Приложение
не менялось уже неделю. Что случилось? Кто-то в бухгалтерии запустил в `psql` обновление цен, открыл транзакцию и ушёл
пить чай. Транзакция держит замок на строки товаров, оформление заказа ждёт этот замок, ожидающие занимают соединения,
пул пуст. А таблица заказов за ночь раздулась до трёх размеров, потому что очистка не приходит. Эта глава о том, как
увидеть такие вещи, как их снять и как устроить базу так, чтобы они не повторялись.

В задачах будет соцсеть, здесь магазин.

## Что делает база прямо сейчас: pg_stat_activity

У каждого соединения с Postgres есть отдельный процесс, и представление `pg_stat_activity` показывает по строке на
каждый:

```sql
SELECT pid, application_name, state, wait_event_type, now() - xact_start AS xact_age, left(query, 60) AS query
FROM pg_stat_activity
WHERE datname = current_database() AND pid <> pg_backend_pid()
ORDER BY xact_start;
```

Читай так:

- `state`: `active` (выполняет запрос), `idle` (ждёт следующую команду, транзакции нет), `idle in transaction` (транзакция
  открыта, запроса нет), `idle in transaction (aborted)` (транзакция уже сломалась ошибкой, но не закрыта).
- `xact_start` начало транзакции, `query_start` начало текущего (или последнего) запроса. Возраст `idle in transaction`
  считают по `xact_start`: запроса-то уже нет. Осторожно: у сеанса после ошибки (`aborted`) это поле пусто.
- `wait_event_type = 'Lock'` значит, что соединение стоит и ждёт чужой замок.
- `application_name` приложение сообщает само (параметр подключения). Привычка называть соединения по сервису и версии
  экономит часы при разборе. `pid <> pg_backend_pid()` исключает запрос, который смотрит сам.

Два вида проблемных сеансов: долго выполняющиеся запросы и «забытые» транзакции. Вторые коварнее: процессор они не
грузят, зато держат замки и снимки.

## Кто кого блокирует

Запрос на изменение строки берёт на неё замок до конца транзакции. Остальные, кому нужна та же строка, ждут в очереди.

```
   сеанс A:  BEGIN; UPDATE products SET price = 90 WHERE id = 7;     (держит замок строки 7, транзакция открыта)
   сеанс B:  UPDATE products SET price = 95 WHERE id = 7;            (ждёт A)
   сеанс C:  UPDATE products SET stock = 4  WHERE id = 7;            (ждёт A и B, очередь растёт)
```

Увидеть цепочку без разбора `pg_locks` вручную можно функцией `pg_blocking_pids(pid)`: она возвращает массив pid-ов тех,
кто держит замок, нужный этому процессу.

```sql
SELECT w.pid AS waiting, w.application_name, b.pid AS blocker, b.application_name, b.state
FROM pg_stat_activity w
CROSS JOIN LATERAL unnest(pg_blocking_pids(w.pid)) AS bp(pid)
JOIN pg_stat_activity b ON b.pid = bp.pid;
```

Снять затор можно двумя способами:

- `pg_cancel_backend(pid)` отменяет текущий **запрос**; соединение и транзакция остаются. У сеанса в `idle in transaction`
  запроса нет, поэтому здесь отмена ничего не делает.
- `pg_terminate_backend(pid)` закрывает **соединение**; открытая транзакция откатывается, замки снимаются.

Выбирай, кого закрывать, внимательно: убирают держателя, а не ждущих. Ждущие ни в чём не виноваты, и закрытие
сеанса обрывает работу клиента (в приложении это ошибка соединения).

### Страховка: таймауты на роли

Дежурить руками можно, но лучше, чтобы затор не копился. Три настройки сеанса:

```sql
ALTER ROLE shop_app SET statement_timeout = '5s';                        -- запрос дольше пяти секунд прерывается
ALTER ROLE shop_app SET idle_in_transaction_session_timeout = '30s';     -- забытая транзакция закрывается вместе с соединением
ALTER ROLE shop_app SET lock_timeout = '2s';                             -- на замок не ждём дольше двух секунд
```

`ALTER ROLE ... SET` хранится в базе и применяется к **новым** сеансам роли. Ставить такие ограничения на роль
приложения нужно, а роли для миграций и отчётов нужны другие значения (долгий `CREATE INDEX` не должен разбиваться о
`statement_timeout`). Прерванный по таймауту запрос это обычная ошибка (SQLSTATE `57014` у `statement_timeout`,
`55P03` у `lock_timeout`, `25P03` у `idle_in_transaction`), и код приложения обязан её обработать.

## Откуда берутся мёртвые строки

Postgres не перезаписывает строку на месте. `UPDATE` помечает старую версию удалённой и пишет новую; `DELETE`
только помечает. Благодаря этому читатели не блокируют писателей (каждый видит свою версию), и откат дёшев. Но старые
версии надо кому-то убирать. Этим занимается VACUUM.

```
   страница таблицы после UPDATE цены товара 7 три раза:
   ┌──────────────────────────────────────────────┐
   │ v1 (удалена)  v2 (удалена)  v3 (удалена)  v4 │   v4 живая
   └──────────────────────────────────────────────┘
   VACUUM помечает место v1..v3 свободным для новых версий
```

- Обычный `VACUUM` не блокирует ни чтение, ни запись, освобождает место **внутри файла** для новых версий, но файл не
  уменьшает. Он же обновляет карты видимости (из-за них возможны `Index Only Scan`) и замораживает старые номера
  транзакций.
- `VACUUM FULL` переписывает таблицу в новый файл и возвращает место системе, но берёт эксклюзивную блокировку:
  пока идёт перепись, таблицу нельзя ни читать, ни писать. На живой нагрузке его избегают.
- **Autovacuum** запускает очистку сам, когда мёртвых версий набирается больше порога: `autovacuum_vacuum_threshold`
  (по умолчанию 50) плюс `autovacuum_vacuum_scale_factor` (0,2) от числа строк. Для маленьких таблиц это нормально, а для
  таблицы в сто миллионов строк порог в двадцать миллионов мёртвых версий слишком высок, и его снижают на самой таблице:
  `ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.01)`.

Сколько мёртвых версий сейчас, видно в `pg_stat_user_tables` (`n_live_tup`, `n_dead_tup`, `last_autovacuum`), а точный
подсчёт даёт расширение `pgstattuple`. Статистика приходит с небольшой задержкой и обнуляется при некоторых аварийных
перезапусках; оценивая «долю мёртвых», делят на сумму живых и мёртвых и не забывают про пустые таблицы.

### Горизонт очистки

VACUUM может убрать версию только если она не нужна **никому**: ни одной текущей транзакции и ни одному снимку.
Самый старый такой снимок называется горизонтом очистки. Его определяют по полям `backend_xmin` (снимок сеанса) и
`backend_xid` (номер транзакции на запись) в `pg_stat_activity`.

```
   время →
   tx 100: BEGIN REPEATABLE READ; SELECT ... (аналитик, снимок; потом пошёл на обед)
   tx 101: UPDATE ...
   tx 102: UPDATE ...
   VACUUM: горизонт = tx 100. Версии, удалённые после неё, остаются, пока аналитик не завершится.
```

Открой `visuals/vacuum_horizon.html`: на одной строке видно, как долгая транзакция останавливает очистку **во всей базе**,
даже таблиц, которых она не касалась. Простаивающая транзакция в режиме read committed безобидна для очистки: после
каждого запроса она отпускает снимок. Опасны repeatable read и serializable (снимок на всю транзакцию) и любые
транзакции с записью (занятый номер). Лечение: найти (`ORDER BY age(backend_xmin) DESC`), закрыть, поставить
`idle_in_transaction_session_timeout`, длинные отчёты вынести на реплику.

### HOT-обновления

Обновление дешёвое, если новая версия строки помещается на **ту же страницу** и в строке не изменился ни один
проиндексированный столбец. Тогда индексы не трогаются: версии связываются цепочкой внутри страницы (heap-only tuple, HOT), а
старые подрезаются при обычном чтении страницы. Горячие счётчики (просмотры, лайки) ломают оба условия: по ним строят
индексы для сортировки, а страницы заполнены до краёв. Лечится схемой: счётчик в узкую отдельную таблицу без лишних
индексов и с запасом места на странице (`WITH (fillfactor = 70)`; параметр действует на вновь заполняемые страницы, поэтому
таблицу переписывают или создают заново). Доля HOT видна в `pg_stat_user_tables`: `n_tup_hot_upd` к `n_tup_upd`.

## Размеры и ненужные индексы

```sql
SELECT pg_size_pretty(pg_table_size('orders'))        AS таблица_с_toast,
       pg_size_pretty(pg_indexes_size('orders'))      AS индексы,
       pg_size_pretty(pg_total_relation_size('orders')) AS всё_вместе;
SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) FROM pg_stat_user_indexes ORDER BY idx_scan, 3 DESC;
```

Индекс, в который не заглядывали ни разу (`idx_scan = 0`), стоит записи, места и кэша. Но не всё, что не читали, лишнее:
уникальный индекс и первичный ключ проверяют ограничение при каждой вставке, и удалять их нельзя. А `idx_scan`
считается с последнего сброса статистики, поэтому решение принимают по данным за длинный срок.

## Роль приложения

Приложение подключается не владельцем схемы и тем более не суперпользователем. Владелец (или отдельная роль для
миграций) создаёт и меняет схему, роль приложения работает с данными:

```sql
CREATE ROLE shop_app LOGIN PASSWORD '...';
GRANT USAGE ON SCHEMA shop TO shop_app;                                        -- можно заходить в схему
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA shop TO shop_app; -- работа с данными
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA shop TO shop_app;               -- нужно для serial и bigserial
ALTER DEFAULT PRIVILEGES IN SCHEMA shop GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO shop_app;  -- для будущих таблиц
```

`GRANT ... ON ALL TABLES` касается только уже существующих таблиц, будущие закрывает `ALTER DEFAULT PRIVILEGES` (он
действует на объекты, которые создаст та роль, от имени которой выполнена команда). Права на создание объектов
(`CREATE` на схему), владение таблицами и `TRUNCATE` приложению не выдают: баг или взломанный сервис с такими правами
уничтожит данные одной командой. Хорошо ещё и разделять роли по сервисам: у сервиса рассылок нет доступа к платежам.

## Сколько соединений нужно

Одно соединение это отдельный процесс сервера, десятки мегабайт при работе и место в таблицах блокировок. А
одновременно работать полезно столько запросов, сколько ядер и дисков, и тысяча активных соединений не быстрее
двадцати. Когда сервисов много, `max_connections` кончается раньше, чем нагрузка. Решение: пулер между сервисами и базой
(например, PgBouncer), который мультиплексирует много клиентских соединений на несколько серверных. Ограничение режима
«соединение на транзакцию»: нельзя полагаться на состояние сессии (`SET`, сессионные advisory-замки, `LISTEN`,
подготовленные запросы без поддержки пулера). В коде приложения это значит: размер пула в `sqlx` считают от
возможностей базы, делённых на число экземпляров, а не от аппетитов одного сервиса.

## Типичные ошибки

- Искать виновника по возрасту транзакции, не глядя на то, держит ли она замок или снимок.
- `pg_cancel_backend` для забытой транзакции: запроса нет, отмена не работает.
- Закрывать ждущих вместо держателей.
- Считать долю мёртвых строк делением на живые: на пустой таблице деление на ноль.
- `VACUUM FULL` как плановая процедура.
- `ALL PRIVILEGES` для роли приложения.
- Забыть права на счётчики: вставка в таблицу с `bigserial` падает с «permission denied for sequence».
- Выдать права на существующие таблицы и не выдать на будущие.
- Выставить `statement_timeout` на всю базу и сломать этим миграции.
