# JOIN: соединение таблиц

Хорошая схема раскладывает данные по таблицам: покупатели отдельно, заказы отдельно, в заказе только
номер покупателя. Это правильно (имя хранится один раз), но человеку нужен список вроде «заказ 17,
Мария, 1200 рублей». Склеить такое из двух таблиц и есть работа JOIN. Если делать это в приложении,
получится N запросов на N заказов и склейка вручную; база делает то же одним запросом и лучше.

Примеры в тексте про магазин (`customers`, `orders`), в задачах соцсеть.

```
customers                 orders
 id | name                 id | customer_id | total
  1 | Мария                10 |      1      |  500
  2 | Олег                 11 |      1      |  700
  3 | Яна                  12 |      2      |  300
```

## INNER JOIN: только найденные пары

```sql
SELECT o.id, c.name, o.total
FROM orders o
JOIN customers c ON c.id = o.customer_id
```

Каждая строка `orders` ищет в `customers` строки, для которых условие после `ON` истинно, и результат
получает по строке на каждую найденную пару. `JOIN` без слова это `INNER JOIN`. Строка, для которой
пары не нашлось, из результата исчезает: Яна без заказов в этом запросе не появится, и никакой
ошибки не будет. Для списка «заказы с покупателями» это ровно то, что нужно.

Если пар несколько, строка размножается: у Марии два заказа, значит, в результате Мария встретится
дважды. Запомни: на этом держатся агрегаты в следующей главе.

## Псевдонимы и неоднозначные столбцы

`orders o` и `customers c` дают таблицам короткие псевдонимы. Это не только для краткости.
Когда в обеих таблицах есть столбец с одним именем (`id`, `created_at`), голое `id` приведёт к
ошибке «column reference is ambiguous»: Postgres не догадывается, какой имеется в виду. Пиши
`псевдоним.столбец` везде, где таблиц больше одной, а выходным столбцам давай имена через `AS`
(`o.id AS order_id`): иначе в результате будет два столбца `id`, и клиент, читающий по имени, получит
не тот.

## LEFT JOIN: сохранить левую сторону

```sql
SELECT c.name, o.id AS order_id, o.total
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
```

Теперь каждый покупатель остаётся в результате. Если заказов нет, правые столбцы заполняются NULL:
Яна выйдет одной строкой с `NULL` вместо заказа. Левая это та таблица, что стоит перед словом
`JOIN`. Поменяешь таблицы местами, и сохраняться будет другая.

```
c LEFT JOIN o                      результат
 Мария  -> заказ 10                 Мария | 10
        -> заказ 11                 Мария | 11
 Олег   -> заказ 12                 Олег  | 12
 Яна    -> (пары нет)               Яна   | NULL
```

`RIGHT JOIN` то же самое, зеркально; его почти никогда не пишут, переставляют таблицы и берут LEFT.
`FULL JOIN` сохраняет обе стороны сразу и в прикладных запросах встречается редко.

## Где писать условие: ON или WHERE

Самая частая ошибка с LEFT JOIN. Пусть нужны покупатели и их крупные заказы (от 600).

```sql
-- неправильно: Олег и Яна пропали
SELECT c.name, o.id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.total >= 600

-- правильно: все покупатели, а крупных заказов может не быть
SELECT c.name, o.id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.total >= 600
```

WHERE работает **после** соединения. У Яны (и у Олега, чей заказ мелкий) в этот момент `o.total` равно
NULL, условие `NULL >= 600` не истинно, и строку выбрасывает WHERE. LEFT JOIN превратился в INNER
JOIN, и это без единой ошибки. Условие в ON участвует в поиске пар: пара не найдена, и левая строка
остаётся с NULL. Открой `visuals/join_rows.html`, там это видно по шагам.

Правило такое. Условие про **правую** таблицу, которое решает, какие её строки допускаются к паре,
идёт в ON. Условие, которое должно отфильтровать итог, идёт в WHERE. И обратная ловушка: условие по
**левой** таблице в ON не отфильтрует левые строки, они всё равно останутся с NULL справа. Хочешь
оставить только Марию, пиши `WHERE c.name = 'Мария'`.

Параметры подставляются так же: «покупатель смотрит свои заказы» это часть условия пары,
`LEFT JOIN orders o ON o.customer_id = c.id AND o.status = $1`.

## Много таблиц, одна таблица дважды

JOIN можно цеплять: каждый следующий опирается на любые уже подключённые таблицы, не только на
предыдущую.

```sql
SELECT o.id, c.name AS buyer, m.name AS manager
FROM orders o
JOIN customers c ON c.id = o.customer_id
JOIN staff m     ON m.id = o.manager_id
```

Цепочка тоже допустима: связь можно вести через промежуточную таблицу. Для «позиции заказа, имя
покупателя» берут `items i JOIN orders o ON o.id = i.order_id JOIN customers c ON c.id = o.customer_id`,
и последнее ON смотрит на `o`, а не на `i`.

Если одна таблица нужна в двух ролях, подключай её дважды под разными псевдонимами и называй их по
роли. Частный случай, **self join**, это когда таблица ссылается сама на себя. Пример: у комментария
есть `reply_to`, id комментария, на который он отвечает, или NULL у корневого.

```sql
SELECT c.id, c.text, parent.text AS answered
FROM comments c
LEFT JOIN comments parent ON parent.id = c.reply_to
```

Тут нужен LEFT: у корневого комментария родителя нет, и INNER JOIN молча убрал бы корни ветки.

## Анти-join: кого нет

«Покупатели, у которых нет ни одного заказа». Через LEFT JOIN у таких правая сторона пустая, то есть
NULL; остаётся оставить именно их:

```sql
SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL
```

Условий в ON может быть несколько, в том числе с параметром: «покупатели, у которых нет заказа
в статусе $1» пишется как `LEFT JOIN orders o ON o.customer_id = c.id AND o.status = $1`
с проверкой `WHERE o.id IS NULL`. Параметр сужает, какие заказы считаются парой.

Проверять на NULL нужно столбец, который в самой таблице пустым быть не может (ключ). Столбец с
допустимым NULL не годится: нельзя отличить «пары нет» от «пара есть, а значение пустое». Тот же
результат даёт `WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)`; про
подзапросы будет отдельная глава.

## Пустые места: generate_series и LEFT JOIN

Чтобы отчёт «заказы по дням» показывал дни без заказов, нужен ряд дат, которого в данных нет. Его
создаёт `generate_series`, а факты пристыковываются слева направо:

```sql
SELECT d::date AS day, o.id
FROM generate_series(date '2026-03-01', date '2026-03-07', interval '1 day') AS d
LEFT JOIN orders o ON o.created_at::date = d::date
```

Здесь `generate_series` с датами и интервалом возвращает `timestamptz`, поэтому в SELECT и в ON
стоит приведение `::date`: сравниваются календарные дни. Для `timestamptz` день считается в часовом
поясе сессии, и в другом поясе событие около полуночи окажется в соседнем дне. Календарь слева, данные справа. Поменяешь стороны или напишешь INNER, пустые дни исчезнут.

## USING и NATURAL

Если столбец связи называется одинаково в обеих таблицах, есть сокращение `JOIN t USING (col)`: оно
заодно склеивает столбец в один. `NATURAL JOIN` соединяет по всем одноимённым столбцам сам, и его
не используют: добавил в таблицу столбец `created_at`, и соединение молча изменилось. Мы пишем
`ON` явно.

## Типичные ошибки

- Условие по правой таблице в WHERE после LEFT JOIN: пропали строки без пары.
- Условие по левой таблице в ON, от которого ждали фильтра.
- Неоднозначное `id` и два одноимённых столбца в результате.
- Забыли про размножение: у покупателя три заказа, и в результате он трижды.
- INNER JOIN там, где нужно сохранить корни дерева или пустые дни.
- Проверка анти-join по столбцу, который допускает NULL.
- Параметр `$1` в WHERE вместо ON: покупатели без заказов этого статуса пропадают.
